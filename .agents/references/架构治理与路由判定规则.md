# 架构治理与路由判定规则

## 1. 定位与规则所有权

本文是项目 Agent 选取、治理边界与共享工作区交接的判定规则，由 Router 的 policy 引用。项目 TOML 是供 Agent 读取的约定，不是已实现的自动路由执行器、CI 门禁或文件系统安全隔离。

| 对象 | 负责内容 | 不负责 |
|---|---|---|
| AGENTS.md | 启动入口、全局原则及全局写入边界 | 持续扩张的任务关键词和详细技术清单 |
| Agent | 角色、边界、输入输出和必须遵守的规则 | 重复 Workflow 的详细步骤 |
| Workflow | 执行顺序、交接、检查与交付 | 复制各技术 Skill 的完整规范 |
| Skill | 技术决策与检查清单 | 自行扩大任务授权 |
| Router | 候选路由、主 Agent 选择入口 | 业务规则和技术实现 |

源码说明当前实现事实，已确认规范说明目标要求；两者不一致时登记偏差，不把当前实现自动提升为目标，也不依据文档假称代码已实现。新的业务决策由用户确认并由 Planner 主导设计，治理 Agent 只落实授权的治理修改。

## 读取职责

- 公共启动与读取去重以 `AGENTS.md` 为唯一入口；不在各角色、工作流和 Skill 重复维护同一套启动清单。
- Agent 声明职责、边界和输出，读取步骤交给命中的 Workflow；Workflow 组织业务执行顺序，通过技能组入口选择专项 Skill；Skill 保留专项规则、业务条件和必要参考。
- Skill 中引用已选 Agent、Workflow 或上层 index 是上下文依赖，不重新选择角色或重跑流程；首次直接使用 Skill 时仍须补齐公共启动要求。
- 跨 Skill 的双向引用可以表达真实业务依赖，按根规则只补齐尚未读取的适用内容，不递归回溯已读入口。总纲、能力地图和源码的业务触发条件不因去重改变。
- 技能路由只在对应技能组索引维护，Workflow 不再复制整张清单。按本次新增或改变的行为选择，区分“使用现有能力”和“修改其实现”：调用既有会话、仓储、控件或 DTO，不自动加载其全部设计资料；本次改变事务、锁顺序、权限或契约时仍补齐相应规则并核实依赖源码。
- 当目标实现、直接依赖及相关测试已足以确定本次修改与验证范围时开始实施；仅在出现具体疑点、失败或新影响面时扩大读取，不为覆盖索引中的所有条目继续检索。
- 普通小改从目标源码、直接调用方和相关测试出发；只有本次改变业务职责、状态/数量口径、跨域契约或架构边界时才读取相应总纲/地图章节，新增或重构页面切片时才展开切片教程。已确认且仍适用的设计不重新规划；未知边界或相关失败证据出现时再补读，不省略必要技术约束。

## 2. 路由判定顺序

1. 先识别用户要做什么（审计、规划或实现）及目标对象（治理规则、业务设计、代码/测试），再读取候选路由。triggers 只是召回线索，不能按首个关键词命中或路由排列决定职责。
2. 用户明确指定角色时，在角色职责与授权写入范围相容的前提下采用；不相容则说明冲突并请求澄清，不能借指定角色扩大权限。
3. 未指定角色时，修改或审计 Agent/Workflow/Skill/开发门禁等规则使用 `architecture-governor`。只审计时仍然只读；治理文件路径出现在输入资料中不代表任务就是治理任务。
4. 业务能力、模块/页面边界、API/DTO 用例或数据模型设计使用 `planner`；不能仅因“治理”“DTO”“页面”误转治理、后端或前端 Agent。Planner 输出方案，不因输出需要落盘而自动扩大其只读范围。
5. 纯代码审查使用 `reviewer`，包括 WPF、API 和 Grid；按审查对象额外读取对应专项 Skill。日常 Review 的范围和按业务影响加载专项规则以代码审查工作流为准，不默认全仓库审计。实现过程中的自查仍由当前实现 Agent 完成，不自动创建独立 reviewer、任务或子 Agent；用户明确指定 Grid Architect 做专项审查时遵守第 2 条且保持只读。
6. 实现或补测按目标职责选择：WPF 页面/客户端测试为 `frontend`；React Web 应用/测试为 `web-frontend`；后端服务/接口为 `backend`；EnterpriseGrid 框架及其专项测试为 `wpf-enterprise-grid-architect`。Grid 架构/API 设计亦由该专项 Agent 负责。Web 任务只读参考 WPF ShellWindow、导航或产品页时仍归 Web，不套用 WPF MVVM/Mapster/STA 规范，也不获得 WPF/后端写入权。客户端任务出现 API、权限、批量保存等词不自动转后端；真实服务/DTO 变更另按授权处理。
7. 前后端都需改且尚未拆清时，先由 `planner` 拆任务、契约和验收，再按用户授权交给实现角色；未指定实现主次的混合治理/业务变更同样先拆解，不静默扩权。仅内容不足且影响角色或边界时询问用户；普通规划默认仍为 `planner`。
8. 选定主 Agent 后，从其候选路由中选择最贴合任务的工作流；同一前端任务命中多个横向门禁时仍只有一个 Frontend 主 Agent，按技术触发条件读取全部相关 Skill，不让单一路由漏掉其他门禁。

小范围明确实现无需先转 Planner；只有新业务决策、职责/契约设计未清或跨角色范围未拆清时才进入规划。选中 Skill 后只读取本次适用的依赖，不因词语出现重选角色。

开始执行前简述：主 Agent、Workflow、意图/对象判定理由、允许写入范围；只读任务明确“无文件写入”。只选择角色不等于创建新任务或启动子 Agent。

## 3. 范围、偏差与豁免

- 治理 Agent 可写根规则、Agent 治理目录和项目 Skill 目录内当前已授权文件；目录在白名单内不等于可以改动未授权业务规则。
- 业务代码和测试缺陷交还相应实现角色，治理任务不顺手修复。
- 未触碰历史偏差记录后继续；任务会修改、复制或扩大偏差时说明依据、影响和最小方案。已有明确授权覆盖的纯机械治理修正可执行；业务语义不明、权限扩大、门禁豁免或范围扩张必须先由用户决定。
- 不另造三个阶段的技术规范：运行时安全、页面架构、质量门禁仍各归既有 Skill。治理只检查接线和一致性。

差异先分类，不把所有文档差异都视为实施阻断：

| 类型 | 判断与处理 |
| --- | --- |
| 已确认架构原则 | 当前实现不自动覆盖原则；本次确需改变时按授权提交变更依据 |
| 已确认业务目标 | 以确认依据和所属契约为准；未实现不等于目标失效，不以当前代码改写目标 |
| 当前源码事实 | 从实际调用方、契约、DI及实现核对；存在源码不等于已部署或已验收 |
| 过期实现描述 | 记录当前证据；不恢复旧接口、不重启旧阶段，已授权的机械同步可直接执行 |
| 未确认设计变化 | 标记待确认，只暂停依赖该决策的实施，继续不依赖它的工作 |

当前地图已替换旧偏差表，不要求为普通任务寻找退役偏差 ID。有仍有效的账本则复用其 ID，没有时在本任务记录来源位置、有效目标、事实、影响及待确认者，不自动新建全局账本。确认的无关历史偏差记录后继续；本次触碰且需要改变有效目标、扩大授权或豁免质量门禁时才请求决定。

普通交付仅在业务契约或架构边界发生实质变化时即时同步对应权威文档，记录确认依据；缺少文档写入授权时完成其他工作并明确交接。内部实现小改不要求重写总纲、地图或全仓索引，无关历史差异只记录。规则更新只写对应权威位置，其余入口引用。

## 4. 共享工作区交接

- 同一文件同一时刻只允许一个写入任务；只读核对可以同时进行，但不得把检查快照当成永久不变基线。
- 接管前通过任务完成/停止状态或原执行者明确确认停止写入来确认交接；超时、失败提示、额度错误、无输出不构成充分证据。
- 无法确认写入者停止时保持只读，请求用户协调，不重复启动同一实施任务。
- 确认停止后重新读取 Git 状态、目标内容与 diff，合并交付结果后才开始修改；不得覆盖用户或其他任务新增改动。
- 即使原任务已停止，也需遵守当前请求的任务创建与委派授权；治理角色不是自动调度器。
- 旧窗口恢复先核对当前工作目录、规则版本、原授权、目标文件及共享依赖的当前差异；同一 HEAD 不证明未提交内容未变。复用现有任务书或交付摘要记录最后完成点、待决事项和验证范围，不强制为小改新增报告；Worktree 操作另见 [使用说明](../../docs/Worktree并行开发说明.md)。

## 5. 路由验收场景

以下是规则场景，不是自动执行器测试。每次修改判定规则时逐项核对，并记录预期与实际判断。

| 请求 | 主 Agent | Workflow | 边界/判定依据 |
|---|---|---|---|
| 新增 DTO 命名门禁 | architecture-governor | 架构治理工作流 | 修改规范，不实现 DTO |
| 只审计 Skill 触发冲突 | architecture-governor | 架构治理工作流 | 只读，不修文件 |
| 规划采购页面与 DTO 用例 | planner | 业务模块设计治理工作流 | 业务设计，不被 DTO 关键词转给 Backend |
| 修改 WPF 页面及 DTO 映射 | frontend | 前端NET10工作流 | 客户端与必要契约，不改后端实现 |
| 参考 .NET 10 ShellWindow 实现 Web 主壳 | web-frontend | Web前端工作流 | Web 是写入目标；WPF 仅只读参考，工程组合仍需实际验收 |
| 实现 Web Grid 的未失焦输入保护 | web-frontend | Web前端工作流 | 加载编辑/工作区技能，不转 WPF Grid Architect |
| 审查 Web 保存结果分类代码 | reviewer | 代码审查工作流 | 只读，加载 Web 入口及 API/编辑/交付技能 |
| 同步 Web Skills 和工作流 | architecture-governor | 架构治理工作流 | 治理文件写入，不生成 Web 工程 |
| 规划 Web 页面及后端契约变更 | planner | 业务模块设计治理工作流 | 拆出业务设计及后端接入门槛，不因 Web 关键词进入实现 |
| 为客户端 ViewModel 补回归测试 | frontend | 前端NET10工作流 | 客户端测试，不弱化断言迁就缺陷 |
| 实现采购确认 API | backend | 后端API工作流 | 后端实现，按分层写入 |
| 实现 Grid 筛选框架 | wpf-enterprise-grid-architect | WPF企业级DataGrid工作流 | 框架及对应专项测试 |
| 只审查 WPF、API 或 Grid 代码 | reviewer | 代码审查工作流 | 只读，加载相应技术 Skill |
| 实现尚未拆分的跨前后端需求 | planner | 业务规划工作流 | 先拆解，不自动改代码 |
| 指定治理 Agent 修复业务保存逻辑 | 不进入实现，先澄清 | 暂不进入写入步骤 | 显式角色与允许写入范围冲突 |

验收还应检查：路由与角色名唯一、引用存在、旧路由 ID 保留、默认 Planner 未改变、前端多 Skill 触发不改变主 Agent，以及未经授权不启动并发任务。
