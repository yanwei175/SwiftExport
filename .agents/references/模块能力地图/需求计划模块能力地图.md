## 2026-09-06 当前修订

统一口径以业务总纲第 24.7 节为准：来源需求（原毛需求/GrossDemand）幂等汇聚销售、品质售后，是 PL 必需的选源与交付额度入口；物料需求（原净需求/NetDemand）及 Allocation 不作发货前提。销售只定义销售事实，正式客户出库通过来源需求追溯原始来源。旧“需求可选”仅指物料计划，不允许绕过来源需求。先执行[来源需求汇聚与交付治理](../领域治理/00A-来源需求汇聚与交付治理.md)，售后订单池归属单独证明，不伪造销售单。

以[业务总纲第 24 节](../业务架构总纲.md#24-订单级客供件池与领域解耦2026-09-06)为当前目标，不代表源码已实现。

客供件父子关系解释组成，不决定库存归属；实际目标由采购固定，库存按订单池共享。Allocation 降为计划域兼容/可选建议，先迁移库存/销售消费者再审计物理收敛，不直接删表/历史。毛需求后台表达来源，物料需求收拢操作入口；下文旧“两主工作台”“四实体必须保留”及父计划送达规则属于兼容基线，不是新执行前提。

实施步骤与提示词见[本领域治理方案](../领域治理/05-需求计划治理.md)。

## 1. 使命、用户与非目标

为计划员、采购员及销售/售后跟踪人员接收实物需求，保存拆解事实、制定计划建议、协调采购承接、处理需求变化和查询履约。需求计划拥有自己的生命周期，不拥有销售单、售后服务单、采购单或库存的状态。

售后维修/补件仅将服务领域认可的配件、补货等实物行接入；受理、工时、服务过程和结案留在服务领域。本次不实现服务单或生产工单，不建立自动 MRP 抵扣、库存预留、跨来源单采购合并、消息队列或分布式流程引擎。

## 2. 已确认决策与权威模型

| 能力/事实 | 所有者 | 决策与边界 |
|---|---|---|
| 来源确认/业务变更/取消 | 销售或服务领域 | 自己维护商业状态，通过明确契约通知/协调需求，不直接维护需求内部表 |
| 来源需求接收 | GrossDemand | 来源认可实物行后自动幂等接收；手工需求为独立入口；不自动拆解或下采购 |
| BOM 拆解与历史修订 | NetDemand | 保留拆解版本，不被当前 BOM 或采购结果改写；当前 NetQty 未自动扣库存 |
| 执行方式、数量、交期、供应商建议 | NetDemandAllocation | 计划建议而非采购命令；无建议供应商仍可被采购选择，实际供应商由采购确定 |
| 哪份需求被哪个执行单据承接 | DemandExecutionLink | 保留实际执行关联与历史贡献；不复制采购、收货状态，不把计划变更当采购减量 |
| 采购创建、确认、减量、取消、继续备货 | 采购领域 | 需求拉取和手工采购都是合法入口；不必先修改 Allocation 才能确定实际供应商 |
| 入库、库存事实 | 入库/库存领域 | 依赖合法执行凭证，不依赖需求是否仍活动；见入库地图交接矩阵 |
| 履约完成情况 | 来源认可的正式履约事实的查询投影 | 销售参考正式客户出货；服务由服务领域认可实物履约，不以收货或采购覆盖冒充服务完成 |

来源、拆解、采购承接职责保持分离，不合并宽表；Allocation 先退出跨域必经链，再审计计划建议及历史的物理收敛，不再强制四实体永久保留。计划命令幂等记录和 BusinessOperationLog 分开，本轮仅文档治理。

## 3. 来源接收、变更与结束

| 命令/阶段 | 准入与责任 | 结果/阻断 |
|---|---|---|
| 接收来源实物需求 | 来源已确认/认可，来源头行 Uid 和版本可证明；领域间授权 | 幂等建立毛需求与快照；重复同意图返回原结果；过期版本不能覆盖新要求 |
| 显式拆解 | 需求活动、无受影响待处置变更、版本/BOM 有效；拆解权限 | 保存拆解修订和初始计划；无供应商建议不是拆解失败 |
| 修改计划建议 | 计划编辑权限，评估受影响数量与已接受承诺 | 未承接部分可调整；已承接部分保留历史，不能普通覆盖执行关联 |
| 采购交接 | 需求允许新承接、未承接数量有效；采购创建权限 | 采购确认实际供应商和目标；订单与接受结果一致、幂等，全成全败 |
| 提出业务变更 | 来源领域决定减少/取消/日期等变化，或手工需求授权操作 | 记录原/新要求、原因和版本，暂停受影响需求行的新转采购，已有执行继续按本领域规则 |
| 影响评估 | 需求变更处置权限，当前执行事实可读 | 区分未承接计划、采购草稿、已确认承诺、已收货/已出货；形成差额和处置清单 |
| 明确处置 | 计划员记录需求处置，采购员在采购领域减量/取消/确认继续备货 | 引用执行结果或明确保留承诺的结论，不从需求页面直接操作采购表或反向入库 |
| 完成变更 | 受影响项都有结论、版本与执行结果一致 | 更新当前要求和计划修订，保留旧需求/承诺解释链；未决差额不能冒充已解决 |
| 履约完成展示 | 来源认可的正式事实 | 只读计算，不因为已经转采购、收到货或覆盖足量而自动完成 |
| 显式关闭/终止 | 关闭权限；未完成关闭须原因及遗留承诺处置记录 | 停止该需求新计划/承接，不级联关闭来源单或采购，不删除真实库存事实 |

“申请—评估—处置—完成”是目标业务阶段，不直接映射为现有枚举。来源商业状态可变化，但需求处置未完成时必须显示差异，不静默宣称两边同步完成。增加或修改已接受的需求同样不能直接覆盖历史承诺。

纠错取消确认与业务取消分开：无不安全下游时沿用原安全回退及毛需求双路径；已有采购承诺后的客户取消走业务变更，不要求倒退真实收货。手工需求在未拆解时可窄编辑；已有执行后同样走影响评估。

## 4. 数量、关系与一致性

- 来源键使用来源类型 + 来源头/行 Uid；来源版本用于并发，不以 SKU/单号推测重复。重新确认生成新活动需求时保留既有历史规则，不能以历史存在为由误判重复。
- 当前需求、当前计划建议、历史已承接数量和变更差额分别呈现。原“所有活动 Allocation 合计必须等于当前 NetQty”的检查只适用于同一有效计划版本且无待处置差额的正常计划，不能通过删历史凑平。
- 剩余可转数量须按同一需求/计划版本及已接受结果计算，不能因来源刷新或建议供应商改变重置。存在未决变更时受影响行的新承接阻断，不能绕路重复采购。
- 库存、在途仅供参考，不自动抵扣 NetQty 或形成预留；同一供给出现在多条需求的参考信息中不代表各条都已独占。
- 需求减少本身不修改 Link.ReleasedQty 或采购行 Quantity。采购明确减量/取消后才协调执行关联结果；继续备货保留采购承诺和原始追溯，不假装满足已取消需求。
- 需求终止不删除历史 Link，也不使原采购失去收货资格。收货覆盖只针对当前有效需求按总纲 13.5 计算；历史贡献与当前覆盖分开，不用覆盖量判断专属库存。
- 同来源单内可按兼容产品、单位、收货目标合并采购行；来源单之间继续隔离，不能因供应商相同跨单合并。
- 单体内经领域契约协调接受数量与采购创建，失败回滚；不引入消息基础设施来替代清晰的职责。源码迁移时必须覆盖并发变更与转采购、幂等冲突和失败重试。

字段快照与实时值明确标识：SKU/描述/单位/来源交期为接收或拆解快照，建议供应商来自计划，实际供应商/送达目标来自采购，收货来自正式入库，客户发货来自正式出库。缺少可选关联返回空或明确未承接，不内联过滤掉合法独立采购。

沿用 DTO 门禁：业务 DTO 仅在同概念/角色、字段单位空值、来源权限、校验生命周期与演进一致且至少两个真实消费者时复用；未来服务单不是预先抽象万能 DTO 的理由。公开类型独立文件；UI 状态留在 Model，结构转换使用 Mapster，数量与状态决策显式表达。

| 2 | Backend：采购创建所有权及统一交接，来源隔离、建议/实际供应商 | 无建议供应商可选择；无效订单不创建；接收数量与采购原子一致；手工采购独立 |
| 3 | Backend：需求变更评估、处置与显式关闭 | 未决变更只暂停新承接；已有采购/合法收货不自动停止；历史承诺与差额清晰 |
| 4 | Frontend：工作台职责、采购预览、变更详情及只读跟踪 | 按新契约建立窄 Model、Mapster、权限/未保存/异步门禁，不越界实现后端规则 |
| 5 | Reviewer：跨来源—计划—采购—库存联合验收 | 检查业务行为、事务/并发、契约与 WPF 测试；旧强耦合断言须按批准规则有依据调整，不直接删除 |

业务场景（待实现验证，不代表本次运行）：

1. 销售/售后实物重复接收只生成一次需求，非实物服务不进入计划；来源旧版本不能覆盖新要求。
2. 库存/在途只参考不抵扣；建议供应商为空仍可被采购选择，实际供应商不同不需先改计划。
3. 来源单隔离；手工采购不调用需求，需求交接共用采购创建规则；失败不留孤立 Link。
4. 已确认采购后取消需求，暂停受影响新承接，但既有采购和合法收货仍可继续；处置必须显式减量、取消或继续备货。
5. 计划改变不覆写已接受的供应商/收货目标；继续备货不伪装为满足已取消需求。
6. 部分收货覆盖可重算，不等于预留、可用库存或正式履约；原入库不因需求取消而反向。
7. 已转采购/已入库不自动完成需求；未完成关闭有原因和遗留承诺处置记录，不级联关闭来源单。
8. 同一需求变更与转采购并发、重试、跨来源部分失败均有明确原子边界，不能重置剩余量导致重复承接。

已有测试见 SwiftExport.Application.Tests/Orders/SalesOrderCancellationPolicyTests.cs、DemandPlanning/GrossDemandDecompositionPlannerTests.cs、NetDemandPlanReplacementPlannerTests.cs、PurchaseDraftPreviewBuilderTests.cs 等。现有覆盖不能证明新增生命周期已实现；未来服务履约口径须由服务领域在实现前定义，不在本地图伪造完成事件。

## 9. 客户交付与修订回传补充

销售来源同时读取 [销售地图](销售模块能力地图.md)，以总纲第 7 节为权威。销售同号受控变更、行级终止、商业关闭/恢复通过需求领域契约协调，不能让销售直接操作需求内部表。销售已生效减量/终止立即约束新交付及相应新需求承接，需求处置尚未完成必须可见，已有合法采购/收货仍按执行领域规则继续。

销售允许先关闭、保留遗留事项和责任，不级联关闭需求/采购；销售重开或恢复行只提供当前有效要求及版本，需求重新评估差额，不复活旧采购承诺或重置履约。非标可先接收和计划，正式库存动作前的显式产品关联保留原快照并协调下游身份，不通过重新拆解覆盖已有历史。换品以关联新销售行承接新要求，旧行剩余终止，不能原位替换执行身份。

同时读取 [PackingList 地图](PackingList模块能力地图.md)、[出库地图](出库模块能力地图.md)。合法销售/售后客户实物交付凭证直接提供计划出货来源，需求、拆解或活动 Allocation 不是必经准入。未采购、未报货好可保存合法草稿；不得为了选源伪造需求链。

履约来自来源可识别的正式最终客户出库及纠错/反向净额；B 消耗、草稿、ReadyQty 均不是客户交付。已有需求按来源接收事实，无需求执行可合法结束追溯。修订不能改写历史贡献或双计反向；真实错发保留实际交付，补发使用新售后实物来源，不同时重新开放原来源需求交付额度。需求收货覆盖继续是只读投影，不是客户库存所有权或预留。

## 10. 主数据与当前 BOM 交接补充

同时读 [主数据地图](主数据模块能力地图.md)、[BOM 地图](BOM模块能力地图.md)。BOM 只有单套当前结构，保存生效；修改记录不是可选择版本。需求拆解 revision 保留，每次保存实际采用的一致完整结构/路径/比例/单位/角色快照，不能以旧 BomVersion 字段引入多方案选版。子 BOM 更新不修改已有拆解快照。

主数据停用禁止新引用/新增承诺，不抹历史或自动停止既有采购；新承接与既有执行分别判断。独立采购确认保存自己的 BOM/消耗快照，需求不作为其前置条件；有需求采购沿用已接受拆解依据，不静默刷新当前 BOM。
