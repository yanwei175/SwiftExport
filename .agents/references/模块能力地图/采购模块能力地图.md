# 采购模块能力地图

## 2026-09-16 需求承接归属收口

采购候选、预览、创建、减量、取消及 Link 释放全部归 Procurement 页面、API 和 Application 服务。需求驱动采购在草稿创建时同时创建 `TargetType=PO` 的活动 `DemandExecutionLink`，草稿阶段即预留需求贡献；独立采购不制造 Link。`NetDemandAllocation` 已物理退出，采购不得读取或回写该结构。采购取消确认只回到草稿并保留 Link；草稿删行、整单作废或未来明确设计的减量命令才累计 `ReleasedQty`。全部贡献释放后物料需求才能安全回退。

## 2026-09-15 采购反向操作实施补充

本节替代下文“取消确认暂未开放”的旧记录。实现入口为 `IProcurementOrderReversalService`，取消确认、草稿指定行删除和整单作废分别保留命令、原因、权限及幂等回执。

- 取消确认：活动已确认采购回到待确认，清除当前确认标记，保留所有活动需求 Link 和历史确认批次。
- 草稿删行：在详情页预览并确认后立即提交，按版本软删选定行，只取消这些行的活动 Link，`ReleasedQty=AllocatedQty`。禁止删除全部剩余行，使用整单作废。
- 整单作废：活动待确认或已确认采购均可在下游安全时直接作废，保留原头行和确认信息，释放本单全部活动贡献；取消确认后再作废是需要先回草稿编辑的路径，不是释放 Link 的唯一前置。本轮不提供恢复。
- 取消确认与作废共用整单下游资格检查；草稿、未反过账收货、异常来源或不完整原/反向流水阻断。供应商反馈只提示影响并保留历史。
- 写操作遵循来源需求、物料需求、Link、采购头行锁序；状态、引用、日志及回执同事务。客户端按用户和采购身份保存冻结命令，未知结果仅重试原命令，成功后只重读。
- 取消使用确认权限，删行使用编辑权限，作废使用独立 `ProcurementOrderVoid` 权限。未保存编辑必须先保存或放弃，不夹带到删行命令。
- 来源物料仍按整组回退，任一 Link 的 `AllocatedQty - ReleasedQty > 0` 即阻断；采购不自动回退物料或修改来源。
- 需求来源已有确认历史的剩余行复用原结构依据，重新确认创建新批次；没有历史确认依据或明确收货目标的来源采购仍阻断，首次确认衔接待业务口径明确。

验证记录见仓库根目录 `采购反向操作验收记录.md`。编译成功不代表部署或桌面闭环验收完成。

## 2026-09-14 采购执行链收口补充

- 旧 `PurchaseOrderWorkspace` 的 Refit、Controller、Application Service 与 Repository 已从生产链路移除；采购管理继续使用 Manager 专用查询与新建/保存/确认命令。
- 供应商跟进已迁移到 `IPurchaseOrderProgressApi` / `PurchaseOrderProgressService` / `PurchaseOrderProgressQueryRepository`；只提供搜索、详情和追加反馈，收货数量以 `InboundDocumentLine.SourceLineId → PurchaseOrderLine.Uid` 汇总，不依赖需求 Link。
- 采购取消确认、采购草稿取消/释放/释放预览、需求侧采购来源追踪与取消暂未开放；对外 API 和客户端写调用已断开，UI 只给出不会修改状态的提示。
- 取消确认的内部安全实现和少量旧 DTO 仍作为不可达残留保留，不得重新注册或暴露路由。该残留不代表功能已开放。

## 2026-09-14 入库消费者迁移补充

- 本批只迁移 `PurchaseOrderManagerView` 直接使用的 `PurchaseOrderManagerQueryRepository`：采购入库由 `InboundDocument.DocumentType=10` 解释，明细以 `InboundDocumentLine.SourceLineId → PurchaseOrderLine.Uid` 定位，不再读取已删除的入库 `SourceType/SourceUid`，也不依赖 `DemandExecutionLink`。
- Manager 列表和从表复用同一采购行预聚合：草稿不计入，当前暂与入库 Manager 保持 `PostingStatus IN(1,8)` 的有符号数量口径。历史版本 309fb5f3 曾采用“原单改 Reversed、库存追加负流水”而未形成负入库行，与当前入库查询口径存在冲突；待入库侧反向模型完成后联合冻结，现阶段不扩张到旧 Workspace 或其它采购安全仓储。
- 正式采购入库若 `SourceLineId` 为空或找不到采购行，Manager 查询按既有 `BUSINESS_BLOCKED` 响应失败，不静默显示零收货。由于此类记录已失去采购归属，检查会阻断整个 Manager 查询；部署前必须完成历史预检与清洗。
- INB-010 仅完成 Manager 列表/从表消费者；`ProcurementOrderRepository`、`PurchaseOrderDraftRepository`、旧 `PurchaseOrderWorkspaceRepository` 等其它入库引用待入库侧完成后另行重构，不能宣称采购入库消费者全链完成。

## 2026-09-14 入库交接现状补充

新入库非过账链使用 `InboundDocumentLine.SourceLineId → PurchaseOrderLine.Uid`，不要求需求 Link；Picker 不接收目标仓条件，仓库由入库草稿独立选择。旧 Workspace 已删除，非过账 API 已实现，Manager 前端接线和数据库部署尚未完成。与此冲突的下文旧“入库仓库必须由采购选源确定”不再约束当前 Picker。

`PurchaseOrderManagerQueryRepository` 已按上节迁移；其它采购服务和仓储仍可能以旧入库 `SourceType/SourceUid` 消费，和精简实体不一致（INB-010 部分开放）。后续必须在入库反向模型稳定后迁移上游安全检查；本批不把通过 C# 构建视为 SQL 已兼容，也不恢复已删字段来掩盖偏差。采购确认/取消、旧 Workspace 和 PackingList 的正式收货联验仍待后续。

> 文档性质：采购页面、API 和契约边界的目标权威设计，同时记录当前源码偏差。业务流程、状态和数量事实仍以 `../业务架构总纲.md` 为最高业务依据。

## 2026-09-16 PackingList 供货交接

采购可以独立于需求建立。PurchaseConfirmationLine/Node 是 PackingList 供货和客供件执行依据；采购向 Preview/Post 提供确认状态、产品单位、收货目标、正式净收货和剩余可收容量，不承担交付额度或库存余额。

## 1. 模块使命与边界

采购模块负责维护可履约采购单、安全草稿及确认状态，并以追加式供应商进度报告支撑跟单。需求转采购、手工采购、独立外部导入都是合法入口；后两者可无需求关系，但不得把来源损坏伪装为独立采购。

采购拥有供应商、采购数量、产品单位与明确收货目标；需求驱动部分通过 Link 保持贡献守恒。执行单据与入库交接见 [入库地图](入库模块能力地图.md) 第 2 节；库存事实见 [库存地图](库存模块能力地图.md)。

采购模块不负责：

- 决定 BOM 拆解和净需求数量。
- 修改 NetDemand 拆解事实或为独立采购伪造 DemandExecutionLink。
- 把供应商已备好量写成库存。
- 建立、过账或反向入库单。
- 管理供应商虚拟仓余额和库存流水。
- 维护供应商主数据。

| 能力 | 所属模块 | 上游 | 正式结果 | 下游 |
|---|---|---|---|---|
| 需求交接采购 | 需求提供可承接内容，Procurement 负责创建 | 合法需求及未承接额度、采购实际选择 | 采购草稿与一致的接受结果/执行关联 | 采购订单管理 |
| 采购订单管理 | Procurement/PurchaseOrders | 采购草稿及可选需求 Link | 采购头行、确认状态、商务字段 | 跟进、入库来源 |
| 供应商跟进 | Procurement/PurchaseOrders | 有效采购行 | 追加 SupplierProgressReport | 跟单查询、装柜计划 |
| 采购 Trace | Procurement/PurchaseOrders | 采购头行、Link、跟进和入库聚合 | 只读追溯投影 | 审查、导出 |
| 采购入库 | Inventory/Inbounds | 合法已确认采购行，不强制需求关联 | 入库单、库存流水、余额 | 库存、PackingList |
| 供应商虚拟仓 | Inventory | 活动供应商和库存事实 | WarehouseSite、余额、流水 | 入库、出库 |

| 采购订单跟进 | Procurement/PurchaseOrders | 跟进筛选、采购行浏览、追加反馈、纠错原因、历史展示 | 修改采购数量、采购商务字段、库存或入库事实 |

采购订单详情仍是采购草稿编辑和复杂确认绑定的完整编排入口。采购管理页可提供快速确认/取消确认，但只调用与详情相同的权威命令 API/Application Service；管理页不复制 BOM、消耗绑定、下游收货或取消资格判断，需要补充绑定时转入详情。

## 5. 目标 API 用例边界

| API 边界 | 用例 |
|---|---|
| PurchaseOrder Manager Query | 新链管理专用多条件分页搜索、读取管理从表；只使用 Manager 专用 DTO |
| PurchaseOrder Commands | 详情与管理快速入口共用确认上下文、确认和取消确认命令；命中同一 Application Service |
| Supplier Progress | 跟进专用搜索、读取采购行跟进详情、读取历史、追加报告 |
| PurchaseOrder Trace | 读取采购全链追溯和导出所需只读数据 |
| Demand-to-Purchase Handoff | 两侧共用 Preview/Create 交接；需求提供额度和接受结果，采购负责订单创建 |
| Purchase Lifecycle | 采购显式取消安全草稿、减量及继续备货处置，协调执行关联结果；不由需求取消自动调用 |

目标上不要求一次性重命名所有接口，但新增方法必须进入正确能力边界；触碰现有混合接口时应先提醒拆分。

### 6.1 独立采购与收货覆盖的目标增量

需求接收、变更和采购交接须同时读取 [需求计划地图](需求计划模块能力地图.md)。本轮补充确认：计划供应商仅建议，实际供应商由采购最终确定；继续按来源单隔离，不跨销售/服务单合并。未指定建议供应商不阻断选择需求；正式建单必须补齐合法采购信息。

需求变更仅暂停受影响的新承接；既有采购/收货不自动停止。采购员显式减量、取消或确认继续备货；不通过普通采购保存修改需求，不要求撤销真实入库。采购已接受的目标和供应商不随计划改变。相关源码偏差复用 DP-002/003/008，不改写为已完成。

- 手工/独立导入采购创建归 Procurement，不借用要求物料需求的转采购命令。详情仍是草稿与确认的唯一页面写入口。
- 后续创建使用专用 Command/Result，表达来源方式、采购行、数量、供应商和收货目标；本次不提前新增类型或路由。详细编辑/导入协议须在实现前冻结。
- 采购数量按执行贡献与明确未关联数量守恒；这不同于当前需求满足程度。需求取消不自动释放贡献/减采购；采购显式处置才协调结果。继续备货保留原始关联但不计已终止需求当前覆盖，不把缺失关系当作无需求。
- 采购确定收货目标，入库不读取当前 NetDemand 建议推导；不同目标不合并一行。无需求 Trace 合法为空，不补造关系。
- 需求收货覆盖按总纲 13.5 查询计算，不塞入采购编辑命令，不代表当前库存或已发货。首次新增覆盖 DTO 先确认真实消费者，不为假设复用创建万能模型。

| PROC-009 | 新 Manager 曾通过数据范围切换混入旧 Workspace 查询 | 新旧契约、字段语义和命令权限互相污染 | `PurchaseOrderManagerView` 只消费新 Manager API；旧 Workspace API/DTO 暂留兼容但不得注入 Manager，旧页面如需人工访问须恢复独立冻结入口，旧链删除另立任务 |
| PROC-005 | `PurchaseOrderLineEditorModel` 同时服务编辑与跟进展示 | 编辑状态和只读跟进职责混合 | 分为 EditModel 与 ProgressLineModel |
| PROC-006 | `PurchaseOrderDetailDto`/Line 同时携带来源贡献、跟进和操作历史 | 详情契约过宽，查询成本和权限耦合 | 详情保留必要摘要，完整历史迁入 Progress/Trace 契约 |
| PROC-007 | Header `Load` 和 Line `FromDto` 大量手写逐字段转换 | 容易漏字段并违背 Mapster 门禁 | 触碰映射时迁入前端 MapsterConfig，模型只保留窄适配入口 |
| PROC-008 | `PurchaseOrderDocumentOpenRequest` 声明在 ViewModel 文件 | 一个公开类型一文件和模型组织不一致 | 触碰时移动到 Models/Requests 独立文件 |

独立采购与新的采购行收货边界是本轮确认的目标，并非上述现有链路已全部支持。普通收货按 Link 选源的限制登记在 INB-001，PackingList 联动风险登记在 INB-008，不复制为新 PROC 编号。手工/导入创建协议及覆盖查询列为后续契约与后端任务。

## 9. Agent 执行门禁

采购相关任务开始前必须读取本地图并核对真实源码：

- 未触碰偏差：正常执行，最终说明相关已知债务。
- 修改或复制上述偏差：先输出门禁偏差提醒，引用偏差 ID，给出最小重构与兼容方案，然后暂停等待用户决定。
- 用户未授权时不得自动执行跨页面、跨 API 或跨 Contracts 的重构。
- 新发现偏差必须补入本地图或在任务交付中明确提出治理更新建议。

## 10. 验收场景

- 新增采购跟进筛选时使用 Progress 专用契约，不扩张采购管理列表 DTO。
- 修改采购工作台时不新增草稿保存、确认或跟进写命令。
- 修改采购详情时所有写命令仍经 Application Service，并保留版本和状态校验。
- 新增收货能力时进入 Inventory/Inbounds，不写入采购页面。
- Trace 页面保持只读，查询数量来自 Link、SupplierProgressReport、入库和流水聚合；无 Link 时仍可追溯独立采购收货。
- 需求覆盖遵循总纲 13.5，不固定每批收货归属，不替代库存可用量或正式发货。
- 手工/独立导入采购合法确认后可收货；数量与目标明确，无需求不补造关联。
- 无推荐供应商可由采购选择实际供应商；需求变更不自动停原采购，实际与建议不同不要求先改 NetDemand 建议。
- 跨来源单仍隔离，交接失败不能留下孤立采购或重复接受数量。

## 11. PackingList 供货与自动入库交接

计划出货和正式交付见 [PackingList 地图](PackingList模块能力地图.md)。PackingList 草稿不要求已有采购，也不预占采购容量；正式过账时，每条标准产品数量必须完整绑定到已确认采购行及 PurchaseConfirmationLine / PurchaseConfirmationNode 快照。

采购向 PackingList 提供采购行、确认批次/行/节点快照、产品单位、收货目标、正式净收货和剩余可收容量。服务端 Preview 先使用已有库存，再建议一个或多个采购行补足缺口；用户确认或调整建议，Post 重新锁定并校验。自动入库与人工收货共同计入采购行正式净收货，跨 PackingList 的有效绑定与自动入库合计不得超出采购确认容量。

采购确认快照同时是客供件计算依据；PackingList 不读取当前 BOM 重算。非标 PackingList 行不绑定采购、不自动入库、不消耗客供件。ReadyQty 只作查询提示，不是供货证明、库存额度或过账准入。

## 12. 主数据与当前 BOM 交接补充

同时读 [主数据地图](主数据模块能力地图.md)、[BOM 地图](BOM模块能力地图.md)。无需求父产品采购确认时，通过一致 BOM 读取能力固定本次必要组成/客供件消耗快照，与确认原子完成；有需求采购使用已接受拆解依据，差异显式处理，不读取最新 BOM 替换历史。无 BOM 与读取失败分别表达；实际供应商/送达目标仍由采购决定，快照不替代收货凭证。缺口沿 BOM-004 与 PL 消耗依据链整改。

停用客户/供应商/产品禁止新行、新引用和增量承诺，已确认合法采购仍可履行、收货；身份缺失、单位不符或订单失效仍阻断。默认供应商/价格及产品默认加客户包装覆盖只在明确采用时保存单据快照；更名不改旧单，停用不自动取消承诺。
