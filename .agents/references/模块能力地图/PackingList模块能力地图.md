# PackingList 模块能力地图

本文定义 PackingList 的活动业务能力、目标模型和实施边界。源码事实优先于本文；目标能力未落地前必须记录为偏差，不得把规划描述成已实现。

核对日期：2026-09-16。相关权威文档：[业务架构总纲](../业务架构总纲.md)、[工程架构总纲](../工程架构总纲.md)、[数据模型与状态规则](../数据模型与状态规则.md)。直接交接地图：[需求计划](需求计划模块能力地图.md)、[采购](采购模块能力地图.md)、[入库](入库模块能力地图.md)、[库存](库存模块能力地图.md)、[出库](出库模块能力地图.md)。实施顺序见 [PackingList 与出库治理](../领域治理/04-PackingList与出库治理.md)。

## 1. 使命

PackingList 是装箱资料、来源履约和自动库存编排的业务入口。

- 草稿保存客户、来源、包装、仓库和运输资料，不预占交付额度、采购容量或库存。
- 正式过账把来源交付、采购供货依据、必要自动入库、最终客户出库和客供件消耗组成一次原子业务动作。
- 有效已过账 PackingList 行是来源正式交付净额的权威；反向后相应数量退出净额。
- 每条来源、供货和消耗依据均形成历史快照，历史展示和反向不依赖当前主数据或当前 BOM。

PackingList 不负责销售商业变更、采购确认、任意库存调整、实际客户退货、售后结算、打印、导出或通用 Trace。

## 2. 当前事实

### 2.1 已实现

- WPF 已有 Manager、Detail 和来源 Picker。
- IPackingListApi 已有列表、详情、来源候选、创建草稿、更新草稿和删除草稿六个接口。
- PackingListHead / PackingListLine 是单据权威；行以 GrossDemandId 标识交付来源，并保存产品、仓库、包装等快照。
- 草稿创建、更新和删除已有头行并发版本、命令幂等、来源额度复核和事务提交。
- 草稿不产生入库、出库或库存流水。

### 2.2 尚未实现

- 正式过账预览、正式过账、整单反向预览和整单反向。
- 采购供货依据绑定、必要自动入库、最终客户出库和客供件消耗。
- 非标来源的无库存正式过账。
- 本图规划的行来源快照、供货绑定和消耗明细目标结构。

### 2.3 当前实现偏差

当前来源查询实现仍限定部分来源类型且要求标准产品身份；目标能力要求所有满足准入条件的活动 GrossDemand 均可进入 Picker，非标来源也可建立草稿并正式过账。该偏差只在后续实施阶段修复，本轮文档不代表源码已经改变。

## 3. 目标能力

### 3.1 统一来源准入

GrossDemand 是 PackingList 唯一的交付来源入口，不按 SourceType 建立来源类型白名单。候选必须同时满足：

1. 来源活动且未删除，具有稳定 GrossDemandId。
2. 客户身份可证明，并与 PackingList 头客户一致。
3. 正式剩余交付量大于零。
4. 来源数量、单位、状态和版本可复核。

来源类型、来源单号和来源行号只用于业务追溯与展示，不决定准入。正式剩余量按来源允许交付量减去有效已过账且未反向的 PackingList 行净额计算。草稿数量不占用额度；保存和过账均重新校验，过账时在事务内锁定权威数量。

### 3.2 标准与非标来源

| 来源类别 | 草稿 | 正式过账 | 仓库 | 库存与采购动作 |
|---|---|---|---|---|
| 标准产品 | 允许 | 允许 | 过账前必填有效 WarehouseSiteId | 必须完成供货依据绑定、必要自动入库、最终出库及适用的客供件消耗 |
| 非标来源 | 允许 | 允许 | 必须为空 | 不创建入库、出库、库存流水、供货绑定或客供件消耗 |

非标行仍计入来源正式交付净额。非标不是“待补产品”的临时标准行；若业务需要库存事实，必须先在来源侧形成可证明的标准产品身份，再按标准行处理。

### 3.3 库存产品身份

库存统一按 WarehouseSiteId + ProductId 管理。客户差异、包装差异或商业 SKU 差异由 Product/SKU 主数据表达，不在库存余额、库存流水或客供件库存上增加客户、销售订单或来源需求维度。

最终客户出库负责记录库存减少；来源履约归属由 PackingList 行负责。出库行不得再次成为另一套 GrossDemand 履约权威。

### 3.4 供货依据与自动入库

每条标准产品 PackingList 行的全部数量都必须绑定可证明的已确认采购依据：

- 已有库存部分使用已过账采购收货中尚未分配给其他有效已过账 PackingList 的数量作为供货依据。
- 库存缺口部分使用同一采购行仍可收的确认容量自动入库。
- 绑定数量合计必须等于 PackingList 行数量。
- 自动入库数量只等于正式过账时的实际库存缺口，不能因绑定数量较大而重复收货。

服务端在过账预览中先使用现有库存，再按确定性规则建议一个或多个已确认采购行补足缺口。用户可确认或调整建议；正式过账必须重新校验采购确认状态、剩余可收量、既有有效绑定、库存、来源额度和所有相关版本。

预览不预留库存、采购容量或交付额度。并发提交时，只有在事务内成功锁定并重新校验的请求可以过账。

### 3.5 客供件消耗

客供件在 PackingList 正式过账时扣减。计算只能读取绑定采购行的 PurchaseConfirmationLine / PurchaseConfirmationNode 快照，不读取当前 BOM。

- 按确认节点保存的路径、比例、单位和消耗仓库计算。
- 部分交付使用“累计应耗减去历史有效已耗”得到本次增量。
- 数量统一保留四位小数，并在最后一批处理累计尾差。
- 缺少确认快照、客供件产品、消耗仓库或可用库存时阻断标准行过账。
- 客供件库存同样只按 WarehouseSiteId + ProductId 核算，不建立客户或销售订单库存池。

## 4. 上下游

| 领域 | 提供给 PackingList 的权威事实 | PackingList 输出 | 禁止事项 |
|---|---|---|---|
| 来源需求 | GrossDemand 身份、客户、来源快照、产品/非标语义、单位、允许交付量、状态和版本 | 有效已过账行的正式交付净额 | 不直接联查具体来源业务表决定准入 |
| 采购 | 采购行、确认批次、确认行与确认节点快照、正式净收货和剩余可收容量 | 供货绑定和本次自动入库引用 | 不以草稿或预览预占采购容量 |
| 入库 | 采购收货事实、自动入库单据和反向能力 | TriggerPackingListId 与供货绑定依据 | 手工入库页面不得处理 PL 自动单据 |
| 库存 | 仓库产品余额、流水、锁定与原子过账能力 | 最终出库、客供件消耗及反向流水 | 不增加客户/销售订单库存维度，不允许负库存 |
| 出库 | 最终客户出库、客供件消耗和反向单据 | TriggerPackingListId 与原始业务依据 | 手工出库页面不得处理 PL 自动单据；不重复计算来源履约 |

## 5. 页面

| 页面/组件 | 当前能力 | 目标能力 | 边界 |
|---|---|---|---|
| Manager | 查询、筛选、分页、新建、打开、删除草稿 | 展示 Draft/Posted/Reversed 及过账摘要 | 不承担详情保存或库存计算 |
| Detail | 编辑客户、来源行、包装、仓库和运输资料；保存草稿 | 发起 Post Preview、Post、Reverse Preview、Reverse | 已过账只读；命令失败保留用户输入 |
| Source Picker | 按客户查询剩余来源并选择数量 | 支持任意准入 GrossDemand 与非标语义 | 不读取具体来源业务表决定资格，不预占额度 |
| Post Preview | 未实现 | 展示采购建议、自动入库、最终出库、客供件消耗、库存前后值、警告与阻断 | 只读，不生成业务事实 |
| Reverse Preview | 未实现 | 展示本单全部有效库存事实的反向影响及下游阻断 | 只支持整单，不提供选行或部分数量 |

本轮终态不规划已过账修订、库存纠错、打印、导出或 Trace 页面。

## 6. 状态与命令

### 6.1 状态

| 状态 | 可执行命令 | 说明 |
|---|---|---|
| Draft | Update Draft、Delete Draft、Post Preview、Post | 可编辑；不产生库存或正式交付事实 |
| Posted | Reverse Preview、Reverse | 单据和行快照只读；正式交付与库存事实有效 |
| Reversed | 查询 | 原单和反向事实均保留；正式交付净额退出 |

删除仅适用于活动且未过账草稿，采用软删除并级联软删有效行。已过账单据不得通过普通更新、删除或数据库补丁改变业务事实。

### 6.2 命令与权限

- Create/Update/Delete、Post、Reverse 均使用稳定 CommandId、事务级并发保护和 BusinessOperationLog。
- 相同用户、操作、命令和语义指纹重试返回首次完整结果；相同命令不同内容返回幂等冲突。
- Post 提交原单版本、Preview Token、用户确认后的供货绑定和稳定 CommandId。
- Token 只证明用户确认的预览输入，不代表资源预留；状态、版本、数量或余额变化后必须拒绝或重新预览。
- Reverse 使用独立 CommandId、原单版本和 Preview Token；不得复用 Post 命令。

查询和草稿继续使用 Module.Shipping.Access。正式过账和整单反向分别规划独立权限：

- Shipping.PackingList.Post
- Shipping.PackingList.Reverse

## 7. 实体关系

### 7.1 PackingListHead / PackingListLine

PackingListHead / PackingListLine 继续作为单据权威。目标行模型：

- GrossDemandId：稳定交付来源。
- ProductId：可空；标准行必填，非标行为空。
- WarehouseSiteId：标准行过账前必填，非标行必须为空。
- IsNonStandardSnapshot：保存来源在采用时的非标语义。
- SourceTypeSnapshot、SourceDocumentNoSnapshot、SourceLineNumberSnapshot：历史展示不依赖当前来源表。
- 产品、单位、描述、颜色、图片、包装等已采用信息继续按快照保存。

### 7.2 PackingListSupplyBinding

正式过账时持久化，草稿和预览不创建：

| 字段职责 | 说明 |
|---|---|
| PackingListLineId | 归属标准产品行 |
| PurchaseOrderLineId | 采购业务行依据 |
| PurchaseConfirmationBatch/LineId | 已确认批次和确认行依据 |
| BasisQuantity | 本条依据绑定数量 |
| AutoInboundQuantity | 本次因库存缺口自动入库数量 |
| Version/审计字段 | 并发、历史和反向校验 |

跨 PackingList 必须按采购行和确认批次锁定正式净收货、已有效绑定数量和剩余容量。失效或已反向的绑定不占用当前有效数量，但历史记录不得删除。

### 7.3 PackingListConsumptionDetail

正式过账时保存每条客供件计算依据和结果：

- PackingList 行与供货绑定。
- PurchaseConfirmationNodeId、确认路径和比例快照。
- 客供件 ProductId、消耗 WarehouseSiteId。
- 累计应耗、本次计算数量、舍入/尾差依据。
- 生成的客供件出库行身份。

### 7.4 自动库存单据

- 自动入库、最终出库和客供件消耗的头均保存 TriggerPackingListId。
- 一条业务依据对应一条库存行，不合并丢失原始依据。
- 自动入库行以采购行为 SourceLineId，以 PackingListSupplyBinding 为原始业务依据。
- 最终客户出库行以 PackingListLine 为原始依据。
- 客供件消耗行以 PackingListConsumptionDetail 为原始依据。

## 8. API 与 DTO

### 8.1 保留的六个接口

IPackingListApi 现有六个查询/草稿接口保持路由和签名稳定：列表、详情、来源候选、创建草稿、更新草稿、删除草稿。

来源候选与行 DTO 目标上将 ProductId 改为可空，并增加非标及来源快照语义。资格由 GrossDemand 投影提供，不直接联查具体 SO/CR 表。

### 8.2 规划新增接口

- POST /api/shipping/packing-lists/{uid}/post-preview
- POST /api/shipping/packing-lists/{uid}/post
- POST /api/shipping/packing-lists/{uid}/reverse-preview
- POST /api/shipping/packing-lists/{uid}/reverse

PostPreviewResult 至少包含稳定 Token、当前单据版本、采购建议、确认快照依据、自动入库、最终出库、客供件消耗、库存前后值、警告和阻断。PostCommand 至少包含原版本、Token、确认后的绑定和稳定 CommandId。

ReversePreviewResult 返回本单全部有效生成事实及反向后的库存/交付影响。ReverseCommand 包含原版本、Token、原因和稳定 CommandId。

Query、Command、Preview Result 和执行 Result 分离；Entity 不进入 Contracts，权威业务计算不放入 Mapster 映射。

## 9. 事务

正式过账在同一 DbSession 事务内按确定顺序完成：

1. 锁定 PackingList 头和全部有效行，校验 Draft、版本、客户和行结构。
2. 锁定所有 GrossDemand，复核活动状态、客户和剩余交付量。
3. 锁定供货涉及的采购行、确认快照、正式净收货、有效绑定和剩余可收容量。
4. 锁定涉及的仓库产品余额，校验禁止负库存。
5. 持久化供货绑定并创建必要自动入库。
6. 创建最终客户出库与客供件消耗，追加库存流水并更新余额投影。
7. 持久化消耗明细，更新 PackingList 为 Posted，写入操作日志和幂等结果。

任一步失败全部回滚。锁顺序必须按稳定业务键排序，多个 PackingList 并发不能超交付、重复使用采购容量或造成负库存。

整单反向也在一个事务内完成：

1. 锁定已过账 PackingList、生成单据、供货绑定、消耗明细和相关余额。
2. 校验所有事实仍为本单当前有效事实且下游允许反向。
3. 先反向最终客户出库和客供件消耗。
4. 再反向本单自动入库。
5. 更新绑定/消耗明细有效性和 PackingList 为 Reversed，写入日志及幂等结果。

整单反向不等于实际客户退货。客户已实际退回的业务必须进入独立售后/收货能力。

## 10. 偏差

| ID | 当前事实 | 目标 |
|---|---|---|
| PL-001 | 来源候选仍限定部分来源类型和标准产品 | 统一按 GrossDemand 准入，支持非标无库存过账 |
| PL-002 | 行缺少完整来源类型/单号/行号及非标快照，ProductId 不可空 | 补齐历史快照并允许非标空产品 |
| PL-003 | 无供货绑定和过账预览 | 建立建议、用户确认、Post 重验和绑定持久化 |
| PL-004 | 无自动入库、最终出库和客供件消耗 | 原子生成全部库存事实，任何失败全回滚 |
| PL-005 | 无正式过账与反向 API、权限和状态命令 | 增加四个独立接口及 Post/Reverse 权限 |
| PL-006 | 无整单反向编排 | 按出库/消耗在先、自动入库在后的顺序完整反向 |

## 11. 实施阶段

1. **通用来源与非标**：扩展 GrossDemand 投影、DTO、可空产品与来源快照；完成同客户、剩余量和非标无库存规则。
2. **供货绑定和预览**：建立 PackingListSupplyBinding、PackingListConsumptionDetail 及 Post Preview；实现多采购行建议、累计耗用和 Token。
3. **原子过账**：实现独立权限、事务锁、自动入库、最终出库、客供件消耗、库存流水、状态和幂等闭环。
4. **整单反向**：实现 Reverse Preview/Reverse、下游阻断、全量反向和交付净额恢复。

每阶段先同步 Contracts/实体/数据库契约，再实现 Application、Repository、WebApi 与 WPF；不得创建只返回“待开发”的后端占位接口。

## 12. 验收

### 12.1 来源与草稿

- 任意来源类型的活动 GrossDemand 只按统一准入进入 Picker。
- 跨客户来源拒绝；同客户多来源允许。
- 标准与非标来源均可保存草稿；非标仓库必须为空。
- 草稿不预留交付额度、采购容量或库存。

### 12.2 过账预览与提交

- 库存充足时不自动入库，但全部标准数量仍有采购确认依据。
- 库存不足时可建议一个或多个采购行，自动入库只补实际缺口。
- 采购容量不足、确认快照缺失、单位/产品不一致时明确阻断。
- 非标行计入正式交付净额且不产生任何库存、绑定或消耗事实。
- 客供件按确认快照累计计算，部分交付和最后一批尾差正确。
- Post 重新校验旧 Preview 的所有资源；并发不得超交付、超采购容量或负库存。
- 同 CommandId 同内容重试返回首次结果，不重复生成单据或流水；不同内容冲突。
- 任一步注入失败时头行、绑定、自动单据、流水、余额、状态和日志全部回滚。

### 12.3 整单反向

- 反向最终出库与客供件消耗后，再反向本单自动入库。
- 正式交付净额、采购有效绑定和库存余额同时恢复。
- 存在不可反向下游事实时整单拒绝，不允许部分成功。
- 不提供选行、部分数量或以反向代替真实客户退货。

### 12.4 文档门禁

- PackingList 及直接交接文档对来源、库存键、采购确认快照、非标、过账和反向口径一致。
- 新增链接可解析，定点术语搜索无客户/销售订单库存池口径。
- git diff --check 通过。
- 纯文档治理不运行后端构建、测试或数据库脚本。
