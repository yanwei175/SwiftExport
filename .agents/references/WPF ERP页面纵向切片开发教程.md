# SwiftExport WPF ERP 页面纵向切片开发教程

## 1. 适用目标

本教程用于把已经确认的模块能力地图，逐页实现为 `.NET 10 WPF + CommunityToolkit MVVM + Refit + Mapster` 功能。推荐以“一个页面承接一个主要用户任务”的纵向切片推进，而不是先一次性重写整个模块，也不是让多个任务同时修改同一批 DTO、API 和页面。

治理任务负责维护能力地图、边界和偏差；一个页面切片按现有写入边界串行交给后端、前端和验收任务，每个任务仍只选择一个主 Agent。WPF 仍是桌面客户端，不照搬浏览器技术栈；借鉴的是成熟 ERP 的页面分工和按用例设计查询契约的方法。

## 2. 核心判断：窄职责，不是少字段

DTO 的“窄”按职责判断，不按属性数量判断。

- `PurchaseOrderManagementListItemDto` 只服务采购管理列表。为了完成识别、筛选、状态判断和导航，它可以包含供应商、数量、金额、状态、进度摘要等全部必需字段。
- `ProcurementOrderDetailDto` 只服务采购单详情。头、行、版本、可执行能力和稳定展示信息都属于同一次详情加载时，它可以是较大的组合契约。
- 跟进、Trace、打印、导出和业务命令的字段口径、权限或生命周期不同，应使用各自契约，不能因为字段相似共用一个万能 DTO。
- 页面必需字段缺失、为显示一行发起多次补查、由前端猜测或拼装权威业务事实，都不是“保持 DTO 窄”，而是查询契约不完整。

一句话标准：**用例内完整，用例间隔离；允许合理重复，不允许职责混杂。**

## 3. 页面类型与职责边界

| 页面类型 | 主要职责 | 推荐查询契约 | 禁止承担 |
|---|---|---|---|
| 管理列表 | 搜索、筛选、排序、分页、识别对象、进入详情 | `XxxSearchRequest`、`XxxManagementListItemDto` | 承担完整单据编辑、Trace、复杂跨域过账 |
| 单据详情 | 查看、创建、编辑一个单据，执行该单据的权威命令 | `XxxDetailDto`、`Create/UpdateXxxRequest`、显式 Command/Result | 变成全模块统计和多对象批处理工作台 |
| 过程跟进工作台 | 围绕一类过程任务批量筛选、更新和反馈 | `XxxProgressSearchRequest`、`XxxProgressItemDto`、专项命令 | 复制采购单详情保存或库存过账实现 |
| Trace | 展示来源、去向、状态和历史链路 | `XxxTraceDto` | 修改权威业务事实 |
| Preview/Dialog | 为一个动作选择、预览、确认输入 | `XxxPreviewDto`、`XxxDialogRequest/Result` | 长期持有完整单据状态 |

参考 SAP Fiori 的常见 ERP 页面分工：List Report 用于发现、筛选和选择业务对象，Object Page 用于查看、创建和编辑单个业务对象；面向逐项处理的工作应进入 Work List/专项工作台，而不是继续堆进列表或详情页。

## 4. 一个页面切片的标准流程

### 4.1 选定一个可验收用户任务

任务标题应具体到页面和结果，例如“采购管理列表可按供应商与状态分页查询并打开详情”，不要写成“完成采购模块前端”。开始前读取命中的能力地图、偏差 ID、目标源码和全部相关调用方。

### 4.2 写页面契约卡

编码前先写清：

1. 页面主要用户与唯一主要任务。
2. 页面必须展示、编辑和执行的动作。
3. 明确不属于该页面的职责。
4. 入口、返回路径、Tab identity 和重复打开策略。
5. 权限、状态准入、错误反馈和未保存关闭规则。
6. 可验收场景，包括空数据、失败、并发和权限不足。

若这些内容无法确定，先回到能力地图，不创建 DTO。

### 4.3 建立字段处置矩阵

修改旧 DTO 或旧页面前，必须列出字段，而不是凭新页面原型删减：

| 旧字段 | 当前调用方 | 本页用途 | 权威来源 | 处置 | 验证证据 |
|---|---|---|---|---|---|
| 示例：`SupplierName` | 管理列表、详情 | 列表识别供应商 | 供应商主数据只读投影 | 管理列表 DTO 保留；详情按其用例决定 | 契约测试 + 页面验收 |

允许的处置只有：保留、迁移到专用查询、留在前端 UI Model、完成调用方迁移后废弃。未确认调用方或没有验证证据时，默认保留旧契约并新增专用契约；禁止为了“变窄”直接删除。

### 4.4 设计读写契约

读模型按页面用例返回完整信息，允许由 Dapper 联表或聚合多个实体。写模型按业务动作拆分：创建、更新、确认、取消确认、过账、反向分别使用显式 Request/Command/Result。查询 DTO 不作为保存命令原样回传。

同一页面可以消费多个 DTO，但首屏主要任务应避免碎片化补查。只有当数据体量、权限、加载时机或独立刷新确实不同，才拆成延迟加载区段或专项查询。

### 4.5 实现后端纵向链路

按项目分层依次确认 Contracts DTO/Refit API、Application Interface/Service、必要的 Repository 查询、Controller 转发。业务事务和状态校验由 Application 权威承担；Controller 不编排，WPF 不补写后端规则。

### 4.6 实现 WPF 页面

- ViewModel 负责 UI 状态、命令顺序和结果接纳。
- 可编辑数据进入 EditModel/LineModel；筛选、选中、展开、Busy 和验证提示留在前端 Model。
- DTO 与 Model 的结构性复制使用 Mapster；业务计算和状态决策保留显式代码。
- 一个页面出现多个 API 时不自动建立 Service；只有真实跨调用协调或结果归一化才建立 Feature Service。
- 页面每次只增加当前验收所需功能，不预建未来扩展点；未来需求出现时扩展对应切片。

### 4.7 验证并收口

至少完成：契约字段/路由检查、相关单元或契约测试、前后端受影响项目构建、页面人工验收、实际 diff 检查。确认旧字段的每个消费者已迁移后，才允许在后续独立任务中删除兼容契约。

## 5. 总控任务与实现任务的推荐协作

不建议让一个总控任务把同一个页面同时拆给多个可写任务。共享 DTO、API 和 ViewModel 很容易发生上下文丢失和互相覆盖。页面纵向切片是计划与验收单位，不改变 Agent 的分层写入权限。

推荐方式：

1. 治理任务维护能力地图、页面契约卡模板、偏差和实施顺序，不直接开发业务代码。
2. 若切片缺少后端能力，先创建后端任务，交付 Contracts、API、Application/Repository 实现、契约测试和字段清单；不要同时启动前端写入。
3. 后端契约稳定并验证后，再创建前端任务，只实现该页面的 View、ViewModel、Model、Mapster 和客户端测试。
4. 最后使用验收/审查任务核对页面契约卡、字段处置矩阵、构建结果和能力地图偏差；通过后再开始下一个页面。
5. 如果后端已经具备完整契约，可以直接从前端任务开始；如果前端发现契约缺口，停止猜测和本地拼装，交回后端任务补齐后再继续。
6. 新需求以后出现时，先判断属于现有页面主要任务、独立区段还是新工作台，再决定扩展；不预先把所有可能性塞入当前页面。

用户可以自己控制切片顺序和验收，但不需要亲自指定每个类。给实现任务提供“页面契约卡 + 字段处置矩阵 + 不做范围”，比只说“把 DTO 做窄”更可靠。

## 6. SwiftExport 推荐起步顺序

采购模块适合用兼容迁移建立第一条样板链路：

1. **采购管理列表只读切片**：建立专用列表查询契约，字段以当前页面完整任务为准；旧共享 DTO 暂不删除，避免跟进页丢字段。
2. **采购订单详情切片**：完成手工独立采购的读取、编辑、保存及明确状态命令；详情 DTO 可以完整，不用追求少字段。
3. **采购跟进工作台切片**：建立自己的 Progress 契约，只承接跟进职责，不复用管理列表行模型。
4. **采购 Trace 切片**：只读来源与履约链路。
5. 再按能力地图进入入库、库存和 PackingList 的交接切片。

若真实源码已存在能力地图偏差，触碰前必须先发门禁偏差提醒，由用户选择“本切片重构”或“保留兼容层”；不得把旧偏差静默复制进新 DTO。

## 7. 可直接用于新任务的提示词

先用规划任务确定一个页面，不写代码：

```text
按 SwiftExport 的“页面纵向切片”方法规划【页面名称】。先读取 AGENTS、Router、业务模块能力地图和《WPF ERP页面纵向切片开发教程》。本次只定义【主要用户任务】，不实现业务代码，不包含【不做范围】。

输出页面契约卡、现有 DTO 全部调用方、字段处置矩阵、读写 DTO 新建/复用理由、命中的偏差 ID、后端任务书、前端任务书和验证标准。窄 DTO 指职责单一，不得删除本页或未迁移调用方仍需要的字段；会触碰偏差时先提醒并等待我的选择。
```

规划确认后，启动一个后端任务：

```text
实施【页面名称】纵向切片的后端契约任务。以已确认的页面契约卡和字段处置矩阵为准，只修改 Contracts、WebApi、Application、Core、Infrastructure 及相关后端测试。本次交付完整支撑【主要用户任务】的查询 DTO/API 和必要命令，不修改 WPF。不得以“窄 DTO”为由删除未迁移调用方需要的字段；触碰偏差先提醒并等待选择。完成后提供给前端的契约清单、构建和测试证据。
```

后端验证通过后，再启动一个前端任务：

```text
实施【页面名称】纵向切片的 WPF 前端任务。读取已确认的页面契约卡、字段处置矩阵和后端契约清单，只修改 SwiftExport.Client.Wpf、必要的客户端测试和已授权 Contracts。完成【主要用户任务】，不实现【不做范围】，不修改后端业务代码。DTO 缺字段时停止本地猜测或手写权威事实，明确列出契约缺口并交回后端。按 Mapster、CommunityToolkit MVVM 和页面质量门禁验证。
```

## 8. 外部设计依据

- [Microsoft：Implement reads/queries in a CQRS microservice](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/cqrs-microservice-reads)：查询模型应按客户端需要塑形，可聚合多个实体或表；长期契约优先使用显式静态 DTO。
- [SAP Help：List Report Page and Object Page](https://help.sap.com/docs/SAPUI5/b2f662dd9d7a4ec680056733050b4d34/c0eec49db81a441e878f528c8f3d28de.html)：List Report 负责筛选和处理对象集合，Object Page 负责单对象的查看、创建和编辑。
- [SAP Fiori Design System：Worklist](https://www.sap.com/design-system/fiori-design-web/v1-136/discover/frameworks/sap-fiori-elements/list-report/worklist-sap-fiori-elements)：面向待办集合的专项工作台是简化的 List Report，并有自己的搜索、表格操作和个性化边界。

这些资料提供页面和查询模型原则，不替代 SwiftExport 的模块能力地图、分层边界和 WPF 技术规范。
