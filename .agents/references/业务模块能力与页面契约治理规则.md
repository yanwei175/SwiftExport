# 业务模块能力与页面契约治理规则

## 1. 目的

本规则把业务设计稳定地传递到页面、API、DTO 和前端 Model。模块设计必须遵循以下顺序：

```text
业务目标与权威事实
  -> 模块能力与上下游
  -> 页面职责与显式命令
  -> API 用例
  -> Request / Response / Command / Result
  -> 前端 Model 与映射
  -> 验收场景
```

页面、数据库表、现有目录和已有 DTO 都不能反向决定业务边界。

## 2. 能力地图最低内容

每个业务模块能力地图必须包含：

1. 模块使命、业务用户和不做范围。
2. 上游输入、下游输出和跨模块调用方向。
3. 权威 Entity、历史快照、查询聚合和禁止缓存的事实。
4. 页面清单、页面职责、禁止职责、打开入口和主要用户。
5. 页面命令、状态准入、阻断条件、反向流程和权限要求。
6. API 用例、DTO、前端 Model、字段来源和真实消费者。
7. DTO 新建/复用判断及契约演进边界。
8. 当前源码事实、目标设计和偏差账本。
9. 可验收的阶段性实施顺序。

## 3. 页面边界门禁

- 页面围绕用户任务建立，不按数据库表机械建立。
- 管理列表、单据详情、过程跟进、Trace 和正式过账职责不同，默认不得合并为万能工作台。
- 同一业务命令只能有一个权威编排入口；多个页面可以导航到该入口，不得复制实现。
- 只读 Trace 不执行保存、确认、过账或反向命令。
- 改变库存的页面归库存单据与过账能力，不归采购、销售或需求查询页面。
- 页面专用筛选、选中、展开、Busy、脏状态和验证提示放前端 Model，不进入 Contracts DTO。

## 4. API 与 DTO 门禁

- API 以业务用例和命令边界组织，不以页面控件或数据库 CRUD 组织。
- 列表、详情、跟进、Trace、Preview、Command 和 Result 使用各自窄契约。
- “窄契约”指职责、权限口径、数据来源和演进原因单一，不表示字段数量越少越好。一个详情或工作台查询 DTO 可以包含较多字段，但必须完整支撑该用例的一次主要加载；因拆分导致页面必需字段缺失、N+1 调用或前端重新拼装权威业务事实，属于契约缺陷。
- 查询 DTO 按用户任务组织，可联结多个实体或聚合的只读字段；命令 DTO 只携带执行业务动作所需输入，不得把查询展示字段原样回传充当更新依据。
- DTO 复用必须满足 `.codex/skills/aspdotnet10/contracts-dto-models/references/DTO复用与文件组织门禁.md`。
- 能力地图必须记录每个 DTO 的使用角色、消费者、数据来源、权限口径和是否允许复用。
- 新页面不得先创建 DTO 再寻找业务用途；先确认页面动作和 API 用例。
- 前端可编辑状态转换为 EditModel/LineModel；结构性转换使用 Mapster，业务规则保持显式。
- 拆分、替换或收窄已有 DTO 前，必须建立“字段处置矩阵”，逐项记录旧字段、真实调用方、页面用途、权威来源和 `保留 / 迁移 / 改由专用查询提供 / 仅 UI Model 持有 / 待废弃` 结论。调用方未迁移并验证前不得删除字段，也不得只为满足 DTO 命名或字段数量目标制造破坏性变更。

## 5. 目标、事实和偏差

能力地图同时维护：

- **目标边界**：后续开发和重构必须遵循的权威设计。
- **当前事实**：从真实源码确认的页面、API、DTO 和调用关系。
- **偏差账本**：当前事实与目标边界的差异、影响和建议治理顺序。

不能为了匹配现有代码而悄悄降低目标边界，也不能把目标设计描述成已经实现。

## 6. Agent 偏差处理门禁

Agent 在实现、审查或规划模块任务前必须比较能力地图与真实源码：

| 情况 | 处理 |
|---|---|
| 实现符合目标 | 正常继续 |
| 存在偏差但任务不触碰 | 正常继续，最终报告提示相关技术债 |
| 任务会修改、复制或扩大偏差 | 修改前输出门禁偏差提醒并暂停，等待用户选择 |
| 用户明确授权重构 | 把重构列入计划，按最小可验收切片实施 |

门禁偏差提醒固定包含：

1. 命中的目标规则。
2. 当前源码事实和文件位置。
3. 本次任务会如何扩大或固化偏差。
4. 最小重构方案及影响范围。
5. 暂不重构的兼容方案和后续代价。

不得自动顺带重构；不得只说“建议优化”而省略具体偏差和影响。

## 7. 模块地图索引与跨域读取

Agent/Workflow 统一按本索引选择地图，不另设各角色自己的模块名单。跨域任务同时读取所有直接交接地图；目标设计与当前事实必须分开记录。

| 任务对象 | 必读地图 |
|---|---|
| 产品、客户、供应商、双方产品关系、分类/颜色/主型号、包装/资料/默认配置 | [主数据模块能力地图](模块能力地图/主数据模块能力地图.md) |
| 当前 BOM、组成编辑、树、校验、修改记录、一致结构读取 | [BOM 模块能力地图](模块能力地图/BOM模块能力地图.md)、主数据地图 |
| 编码更名、主数据停用/恢复、单位变更、默认值采用 | 主数据地图及实际受影响的销售/需求/采购/入库/库存/PackingList/出库地图 |
| 来源需求、物料需求、拆解、计划建议、来源生命周期 | [需求计划模块能力地图](模块能力地图/需求计划模块能力地图.md) |
| 销售订单、商业变更、行级终止、关闭/恢复、非标关联 | [销售模块能力地图](模块能力地图/销售模块能力地图.md) |
| 售后来源生命周期 | [售后模块能力地图](模块能力地图/售后模块能力地图.md)；涉及实物交付再读需求计划与 PackingList 地图 |
| 采购管理、确认组成、跟进、独立采购、采购容量 | [采购模块能力地图](模块能力地图/采购模块能力地图.md) |
| 来源选择、入库列表/详情、草稿、过账、反向、采购收货 | [入库模块能力地图](模块能力地图/入库模块能力地图.md) |
| 仓库、余额、流水、库存 Trace、期初、统一过账 | [库存模块能力地图](模块能力地图/库存模块能力地图.md) |
| PackingList Manager/Detail/Picker、通用 GrossDemand 来源、非标、草稿 | [PackingList 模块能力地图](模块能力地图/PackingList模块能力地图.md) |
| PackingList 供货绑定、过账预览、自动入库、客供件消耗、整单反向 | PackingList、采购、入库、库存、出库五份地图及 [PackingList 与出库治理](领域治理/04-PackingList与出库治理.md) |
| 正式客户出库、客供件消耗、出库 Trace、整单反向 | [出库模块能力地图](模块能力地图/出库模块能力地图.md)、PackingList 与库存地图 |
| 采购—入库—库存交接、来源标识、需求收货覆盖 | 采购、入库、库存三份地图；涉及需求生命周期再读需求计划地图 |

已有地图必须先读；未建立的模块不得套用采购字段作为通用模型。地图是执行约定，不是已实现的自动路由或 CI 检查。业务设计由 Planner 主导，确认后的治理落盘由 architecture-governor 按授权维护，不改变角色写入范围。

## 8. 能力地图维护

- 模块地图放 `.agents/references/模块能力地图/{模块}模块能力地图.md`。
- 业务规则改变时先更新业务架构总纲，再同步能力地图。
- 页面/API/DTO 边界改变时同步能力地图和偏差账本。
- 完成偏差重构并验证后，从偏差账本移除或标记已完成，并记录验收证据。
- 历史资料只能用于追溯，不能覆盖当前能力地图。

## 9. 页面纵向切片实施入口

新增或重构 WPF 业务页面时，按 [WPF ERP 页面纵向切片开发教程](WPF ERP页面纵向切片开发教程.md) 从一个可验收用户任务贯通页面、查询/命令契约、后端实现、前端 Model 和验证。能力地图继续定义边界，教程只定义实施方法；两者冲突时先修正能力地图或记录偏差，不得由实现任务静默改写业务边界。
