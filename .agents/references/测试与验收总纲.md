# 测试与验收总纲

本文是 SwiftExport 后续任务完成后的验收基准。目标不是一次性建立重型测试体系，而是让每次改动都能说明“改了什么、怎么证明可用、还有什么风险”。

## 验收总原则

每次任务结束必须说明：

- 改了哪些文件。
- 是否修改业务代码。
- 运行了哪些构建、测试或检查。
- 未运行的检查及原因。
- 是否需要人工业务验收。
- 是否存在连接字符串、编码、未提交改动、构建环境或数据迁移风险。

验证顺序：

1. 静态范围检查：确认只改任务相关文件。
2. 构建检查：按改动范围选择最小可靠构建。
3. 契约检查：涉及 API、DTO、Refit 时核对前后端路由和模型。
4. 手工业务验收：涉及 ERP 流程时跑关键业务场景。
5. 风险说明：列出未覆盖场景和需要用户确认的部分。

## 构建矩阵

当前常用构建：

```powershell
dotnet build .\SwiftExport.Client.Wpf\SwiftExport.Client.Wpf.csproj
dotnet build .\SwiftExport-WebAPI.slnx
msbuild .\SwiftExport.slnx /p:Configuration=Debug /p:Platform=AnyCPU
```

当前前端解决方案构建：

```powershell
dotnet build .\SwiftExport-Frontend.slnx
```

- `SwiftExport.Client.Wpf` 是当前 .NET 10 WPF 主线。
- `SwiftExport-WebAPI.slnx` 用于后端 WebApi、Application、Core、Infrastructure、Contracts 改动。
- `SwiftExport.slnx` 用于跨前后端或发布前综合验证。
- `SwiftExport-Frontend.slnx` 用于 Client、Contracts 和 EnterpriseGrid 的前端综合验证。

## 按改动类型验收

后端业务代码：

- 优先运行 `dotnet build .\SwiftExport-WebAPI.slnx`。
- 检查 WebApi、Application、Core、Infrastructure、Contracts 分层。
- 涉及 SQL、Repository、DbSession、事务时检查 Dapper skill。
- 涉及单据、库存、需求链路时补充手工业务验收。

当前 .NET 10 WPF 前端：

- 优先运行 `dotnet build .\SwiftExport.Client.Wpf\SwiftExport.Client.Wpf.csproj`。
- 检查 CommunityToolkit 源生成器写法。
- 检查 ViewModel、LineModel、SearchModel、DI、页面路由和 XAML 绑定。
- 不从 Git 历史或归档分支把旧 MVVMLight、VSTO、MateWpfThemes 规则带进当前客户端。

Contracts / DTO / Refit：

- 检查 DTO 字段、Refit Interface、Controller 路由、HTTP 方法、返回包装是否一致。
- 前端依赖变更时检查 API 注册。
- 不返回 Entity，不把 UI 状态放进 DTO。
- 业务命令有明确接口，不藏在普通保存接口里。

数据库 / SQL：

- 检查脚本是否幂等。
- 检查 `Uid`、业务键、索引、软删除、审计字段、`Version`。
- 库存流水只新增，不普通修改或删除。
- `DemandExecutionLink` 是净需求执行追溯的权威来源。

纯文档 / Agent / Skill：

- 不运行构建。
- 检查入口路径存在。
- 检查是否误改业务代码。
- 检查是否还有旧 wiki 默认路由残留。
- 解析全部 Agent/Router TOML，检查角色名、路由 ID 唯一及 policy、Workflow、Skill、Reference 引用可达。
- 按 `.agents/references/架构治理与路由判定规则.md` 的场景核对意图、主 Agent 与写入范围；这是规则审查，不代表已有自动路由执行器或 CI 门禁。
- 检查工作流编号、重复权威入口及写入边界一致性；运行 `git diff --check` 并单独检查新增文件，对比初始基线保护已有改动。

## API 契约验收

涉及 Controller、DTO、Refit、Swagger/OpenAPI 时至少检查：

- Controller 路由与 Refit 路由一致。
- HTTP 方法一致。
- Request / Response DTO 一致。
- 返回包装遵循项目统一响应模型。
- 新增 API 已注册到前端 DI，或明确当前只定义契约不接前端。
- DTO 字段是业务语言，不暴露数据库细节。
- 错误消息和错误码可被非 WPF 客户端理解。

## 前端页面验收

WPF 页面改动至少检查：

- 页面能通过 DI 创建。
- Refit API 已注册。
- 页面路由或打开入口可用。
- 加载、搜索、分页、刷新可用。
- 未保存变更在刷新、搜索、分页、关闭前有提示。
- 保存成功后行状态清理。
- 删除新增行和删除已持久化行行为正确。
- 命令按钮启用/禁用状态正确。
- Busy 状态防止重复提交。
- 错误提示不会静默吞掉关键异常。

### WPF 运行时安全验收

涉及异步加载、保存/业务命令、导航生命周期或资源释放时，至少按改动范围验证：

- 连续触发两次搜索、筛选、分页或详情切换：旧请求被取消；即使旧 API 忽略取消并较晚返回，也不能覆盖新结果。
- 请求完成前离开或关闭页面：旧请求不得修改集合、选中项、分页、状态消息或验证摘要。
- 双击按钮、快捷键与程序调用同时触发保存/确认/过账：只允许一个写命令进入；失败不清理编辑内容和脏状态。
- 写成功后刷新失败：反馈必须区分“写入成功、刷新失败”，不能把已成功提交描述为保存失败。
- 嵌套加载或保存后刷新：同一用户操作只有一个 Busy owner，Busy 与命令状态最终恢复。
- HTTP 401、403、409，字段验证、业务失败、网络中断、真实超时、用户取消和未知异常能够稳定分类；不得靠异常消息文本猜测。
- 同一失败只产生一次用户反馈；技术异常由 API/基础设施边界记录，ViewModel 不暴露堆栈或重复记录同一异常。
- 首次进入、离开、重复进入和初始化失败均有明确结果；重复进入不重复订阅、不隐式覆盖未保存编辑。
- 离开或释放后事件、Messenger、Timer、CancellationTokenSource 和子对象被对称清理；多次释放安全。
- 搜索、刷新、分页、切换记录和关闭前检查真实变更集；用户取消放弃时恢复动作前页面状态；写命令执行中默认不可关闭。

阶段一实施时允许以代表性手工场景和静态审查完成验收；阶段三门禁生效后，本段不再构成自动化测试豁免。若底层契约暂时不能表达稳定错误码或字段错误，必须记录限制和最小后续改造，禁止在 ViewModel 中按消息文本兼容。

### WPF 页面架构边界验收

涉及页面依赖、权限、普通表单验证、导航/Document Tab 或 Dialog/抽屉/子页面时，至少按改动范围验证：

- 简单窄用例允许 ViewModel 直接注入 Refit；多接口编排、跨调用协调或结果归一化进入 Feature Service，且 Service 不持有页面 UI 状态、不弹窗、不访问控件。
- ViewModel 不处理 HTTP client、BaseAddress、序列化或 Refit 注册细节；新增 API/Feature Service/ViewModel 均已在正确组合根注册，DTO↔Model 继续通过既有 Mapster/DTO 门禁。
- 导航访问、页面操作、字段编辑权限分别表达；无权入口按产品语义隐藏或禁用，代码不硬编码角色名，401/403 后端结果不会被前端判断覆盖。
- 字段、本地跨字段、异步、服务端字段错误和业务/状态失败各有 owner；无效表单阻断保存并反馈首错，失败保留输入、验证错误和脏状态。
- 打开请求类型、文件位置、Tab identity 和重复打开/激活策略明确；不同路由不会因裸业务 ID 偶然碰撞，重复激活不会静默覆盖未保存编辑。
- Dialog/抽屉/子页面明确输入、确认/取消/关闭结果和未保存检查；调用方仅接纳确认结果，业务 ViewModel 不 new View/Window 或依赖 WPF-UI 具体控件。
- 同时触发阶段一主题时继续执行“WPF 运行时安全验收”，不得在新页面架构实现中另造 Busy、生命周期、错误分类或未保存规则。

阶段二实施时仍以静态审查和代表性手工场景为主；阶段三门禁生效后，本段不再排除自动化测试与非功能质量验证。

### WPF 测试与非功能质量验收

客户端本次相关测试、夹具和测试数据由 Frontend 在 `SwiftExport.Client.Wpf.Tests/**` 内维护。Grid 框架专项测试由 Grid Architect 在 `SwiftExport.Wpf.EnterpriseGrid.Tests/**` 内按授权维护；运行测试不等于获得源码写入权限。补测不得删除有效断言、绕过失败或借机改变后端业务行为。

涉及行为、控件、格式、性能、日志、缓存或文件输入输出时，按改动范围验证：

- ViewModel/策略/Converter/映射/验证/缓存使用普通单元测试；Dispatcher、Binding、焦点、键盘、Popup、DataGrid 和控件生命周期使用 STA/WPF 测试；Refit/DTO/路由使用契约检查。
- 测试断言可观察行为和不变量，不以源码文本、私有字段、方法行数或生成代码字符串作为主要证据。
- 核心流程可全键盘完成，焦点顺序与返回正确；图标/无文本控件有 Automation 名称，高对比度可用，颜色不是唯一状态线索。
- 文案资源所有权清楚；日期/时区、金额、数量、百分比、单位、空值、输入解析和文件名有明确文化语义，契约与业务计算不依赖显示文化。
- UI 线程没有同步网络/磁盘/大文件工作；大集合保持分页/虚拟化/增量通知，不缓存 DataGridRow/Cell，不靠关闭虚拟化修复功能，并以代表性规模验收。
- 日志 owner 与级别适当，不记录 Token、密码、连接字符串、Authorization Header、完整敏感 DTO 或文件内容；技术堆栈不直接显示给用户，前端日志不替代后端审计。
- 缓存声明 owner、key、用户/租户/文化/权限隔离、生命周期、TTL/写后/登出失效和并发策略；页面状态不冒充共享缓存，未设计离线协议时不宣称离线支持。
- 导入导出明确当前视图/选中/全部数据语义、权限与敏感字段；覆盖类型、大小、编码、CSV/Excel 公式注入、路径、取消、进度、失败与临时文件清理。
- 未新增自动化测试时说明豁免理由、替代检查、人工验收和残余风险；历史无测试或 WPF 难测不能单独构成高风险行为豁免。

常用验证：

```powershell
dotnet test .\SwiftExport.Client.Wpf.Tests\SwiftExport.Client.Wpf.Tests.csproj
dotnet test .\SwiftExport.Wpf.EnterpriseGrid.Tests\SwiftExport.Wpf.EnterpriseGrid.Tests.csproj
dotnet build .\SwiftExport-Frontend.slnx
```

`SwiftExport-Frontend.slnx` 当前不包含两个 WPF 测试项目，因此前端解决方案构建通过不能替代上述 `dotnet test`。详细决策和交付检查分别见 `.codex/skills/wpf-dotnet10-design/quality-gates/references/前端质量门禁矩阵.md` 与 `检查清单与代表性验收.md`。

质量门禁只定义完成证据和非功能边界；页面职责与协议服从页面架构 Skill，并发、生命周期和反馈服从运行时安全 Skill，Grid 业务无关能力服从对应 Grid Skill。

搜索控件重点检查：

- 搜索关键字和选中对象显示不混用。
- 控件不直接调用 API。
- 选择结果由页面 ViewModel 负责回填。
- DataGrid 内搜索编辑器不破坏行高和编辑体验。

## ERP 主流程手工验收

涉及销售、需求、采购、入库、出库、PackingList 的任务，应按影响范围选择场景。

主数据与 BOM：

主数据与 BOM 的跨域前置场景见 [主数据地图](模块能力地图/主数据模块能力地图.md)、[BOM 地图](模块能力地图/BOM模块能力地图.md)：

- 编码专用更名保持 Uid，验证唯一性、旧接口/导入映射及引用，不改历史单据快照、不串到另一对象。
- 主数据停用禁止新引用、新行及增量承诺；已有已确认合法收货/交付可继续，身份、单位、数量及单据状态仍需校验；停用供应商不自动停仓，仓库自身停用门禁保留。
- 有正式库存流水后基础单位冻结，即使余额为零；无流水纠正也检查订单/BOM/执行影响，不只检查单位字典。
- 产品默认加客户包装覆盖正确，未配置与合法零值区分，非法值不能回退掩盖；单据采用后快照不随模板变更，删除资料记录不删除真实文件。
- 当前 BOM 保存即生效且记录差异，无版本发布/切换；需求拆解 revision 与 BOM 修改记录分开，旧执行快照不变。
- 多层结构读取一致，不能半新半旧；无 BOM 与缺失/循环/读取失败区分；同父重复阻断，跨路径共用组件合法，跨父并发形成环须拒绝。
- 独立采购无需求，在确认时固定必要 BOM/消耗依据；有需求采购沿接受的拆解快照，当前结构改变不覆盖历史；缺历史证据不伪造。
- 全部写入口同口径校验，保存结构和修改记录失败全回滚；同意图重试不重复记录，权限/并发冲突拒绝。保留已有 BomStructureValidator、ProductUnitPolicy、默认供应商及关系页测试，不弱化断言。
- MD/BOM 偏差与关联模块联合验收；此清单不是已执行测试，不意味着停用或独立采购快照已实现。

销售订单具体场景：

- 新建销售订单并保存。
- 编辑待确认订单头字段和明细行。
- 确认订单后生成毛需求。
- 已确认订单禁止普通删除或越界编辑。
- 取消确认遵守状态机边界。
- 按 [销售地图](模块能力地图/销售模块能力地图.md) 联验同号受控变更、行级终止、关闭/恢复和非标关联；保留取消确认安全双路径测试，不以商业关闭能力放宽纠错回退。
- 部分发货后减量/终止只限制剩余承诺；不重复扣同一终止量，不截断真实已交付量，未受影响行继续。
- 客户更换另建关联单、换品新增关联行；旧行和执行历史不改写；未确认增量和变更草稿不产生新交付额度。
- 生效销售限制与 PackingList 提交并发时旧预览不能超交付；需求处置未完成不阻断无关执行，无 Allocation 的合法交付不漏算，B 消耗不算发货。
- 发完不自动关闭；允许先关闭且遗留事项/责任可见，采购和合法收货继续；恢复须授权、原因、预览，不重置已交付或复活旧采购，重开订单不自动恢复独立终止行。
- 非标可先接单/确认/计划，正式库存动作前显式关联产品单位并保留原快照；未知历史关系不得猜测迁移。
- 销售主数据更新不刷新历史商业快照，销售修订不覆盖已出货 PL 编号；真实退回不自动重开销售额度，售后补发不双开额度。
- 销售只承诺 CNY/USD，其他币种不能默认按 USD 计算；多对多履约查询不重复计量，无可选关联不丢订单行。
- 独立履约跟踪无跨域写入口；权限/字段可见范围由服务端校验；覆盖版本冲突、重复命令及失败回滚。SO 偏差清单不代表这些测试已执行或能力已实现。

毛需求 / 净需求：

- 销售订单行到毛需求是一对一。
- 毛需求拆解生成多条净需求。
- BOM 拆解保留来源、父子关系、数量和物料类型。
- 客供件根据子物料 `MaterialType` 被识别。
- 重复拆解不会产生重复有效净需求。

需求来源、变更与生命周期：

- 来源确认/服务认可实物行后幂等接收；非实物服务不入计划，旧版本不覆盖新要求。
- 纠错取消确认保留历史安全双路径；已执行后的业务取消走影响评估，不强制反向真实入库。
- 待处置变更仅暂停受影响的新转采购，原采购和合法收货不自动停止；采购显式记录减量、取消或继续备货。
- 当前需求、建议计划、历史承诺和差额分别表达，不能删除历史或重置剩余量凑平。
- 完成来自来源认可的正式履约事实；显式关闭，未完成关闭有原因与遗留承诺处置，不级联关闭来源单或采购。
- 库存/在途只参考、不抵扣、不预留；服务工时/结案不由需求计划负责。
- 对照需求计划地图 DP 偏差及既有取消、拆解、采购测试，更新断言须依据批准规则，不机械删断言。

净需求转采购：

- 计划可建议供应商；无建议仍可选择，采购确定实际供应商/目标，实际不同不要求先修改 Allocation。
- 两侧共用采购交接能力；按来源单隔离，建单与需求接受结果原子一致，失败不留孤立 Link。
- 变更与交接并发、版本冲突或重试不重复承接；手工采购不依赖需求计划。
- 多条净需求聚合到采购行时写入 `DemandExecutionLink`。
- 净需求展示执行数量、执行单号、剩余数量正确。
- 生产/外协暂未实现时，不误转采购。

采购 / 入库：

- 采购单保存、查询、详情加载正常。
- 待入库行能被选择。
- 入库过账生成正式入库单。
- 入库过账生成库存流水并更新库存余额。
- 入库后采购净收货和需求收货覆盖正确查询计算，不回写采购/需求/Link 的过程数量缓存。
- 无需求关联的已确认采购可正常收货；仅 Allocation 或未确认采购不能收货。
- 需求甲 60、乙 40，收货 70 时覆盖 60/10；反向后净收货 50 时覆盖 50/0；覆盖不当作库存预留、可用库存或已发货。
- 同采购来源重复行先合计校验；多草稿只提示、不预占；并发过账不超收。
- 收货仓以采购明确目标为准，计划变化不得静默改仓；没有需求不伪造 Link。
- 按 [模块地图索引](业务模块能力与页面契约治理规则.md) 核对入库与库存场景及 INB/INV 偏差；地图场景清单不等于已运行测试。

出库 / PackingList：

- PackingList 保存和详情加载正常。
- PackingList 过账触发需要的自动入库和出库。
- 自动入库也必须生成正式入库单；需求覆盖不作来源库存，无法证明缺口时阻断自动补入库，不重复补已有正式实收。
- 自动出库必须生成正式出库单。
- 客供件按父物料累计实际出货和历史已耗计算本次增量，覆盖部分出货、最后一批尾差及反向，不能只等整单完成才消耗。
- 每个库存动作都有库存流水。
- 按 [PackingList 地图](模块能力地图/PackingList模块能力地图.md)、[出库地图](模块能力地图/出库模块能力地图.md) 联验：无采购/无 Allocation/未报货好可进入合法计划草稿，草稿不预占，确认实际出货独立于保存/打印。
- 同客户多销售/售后来源及不同 InvoiceNo 分组保留；跨客户拒绝，来源身份不靠编号代替；备件交付不误算 B 消耗。
- 已证明同客户库存优先；未知客户归属不能当零再补；自动入库必须有合法采购头行和容量，人工/自动净收货合计不超收。
- 重复来源、多贡献及跨单并发不重复使用客户库存/采购容量/交付额度；同库存键最终出库与 B 消耗合计校验，成品补入库不隐式掩盖 B 缺口。
- B 依据缺失阻断正式提交；B 不足正常阻断；特殊类型 90 必须权限、原因和审计，不能伪造 B 入库或借其他客户库存。
- 提交与纠错中途失败全部回滚，超时同意图重试不重复入出库；事务中间恢复库存不暴露给并发任务。
- 同号文档修订不动库存；库存/履约纠错保留原—反向—替代链及有效修订，历史打印/导出可追溯。
- 真实错发保留原发货；未实际退回不加库存，补发来自新售后交付来源且不双开原销售额度；整单反向检查全部生成单据和后续依赖。
- 核对 PL/OUT 与关联 INB/INV 偏差；不得削弱原有测试通过门禁。本清单不是已执行测试或已实现自动 CI。

改单 / 反过账 / 红冲：

- 库存流水之前，允许按轻量改单机制回退未过账下游并重跑。
- 已产生库存流水后，不靠删除或普通编辑修正。
- 需要反过账或红冲的场景有明确命令和审计原因。
