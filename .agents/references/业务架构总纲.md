# SwiftExport ERP 业务架构总纲

> 文档状态：业务与目标数据模型权威文档<br>
> 最近整理：2026-07-30<br>
> 适用范围：当前 `.NET 10 WPF + ASP.NET Core + Dapper + SQL Server` 主线<br>
> 重要说明：本文描述目标业务模型，不为旧数据库、旧表名或阶段性兼容代码背书。

快速理解端到端流程时，先读 [ERP业务流程导航图](ERP业务流程导航图.md)；涉及权威业务规则、实体职责和数量口径时，以本文为准。

## 1. 文档定位与使用规则

本文件用于统一解释 SwiftExport 的业务流程、实体职责、数据事实来源、状态边界、数量口径、反向流程和目标数据库模型。未来设计或修改业务功能时，应先用本文判断“业务事实应由谁保存”，再进入 Entity、DTO、Application、Repository、API 和 WPF 页面实现。

| 优先级 | 事实来源 | 用途 |
|---:|---|---|

### 1.4 跨任务协作与决策持久化

- 本文是跨 Codex 任务、跨开发窗口和跨模块协作的长期业务事实源；新任务必须先读取本文，再读取真实源码。
- 每轮讨论一旦确认了实体职责、权威关系、数量口径、状态边界、准入条件、反向规则或外部集成锚点，应在进入实现前写回本文。
- `弃用资料/_codex_handoff/**` 仅保存历史专项的实施细节、进度和临时上下文，不得继续写入，也不得只在交接文档中冻结长期业务规则。
- 代码实现与本文不一致时，应将差异明确登记为“当前源码偏差”；不得为了迁就阶段性实现而悄悄改变本文的目标规则。
- 尚未确认的方案应标记为待确认，不得以确定语气写入权威规则；确认后的规则应同时说明受影响模块和验收口径。

## 2. 系统定位与业务原则

SwiftExport 是面向小团队内部使用的外贸 ERP。系统围绕产品与 BOM、销售订单、需求拆解、采购、供应商跟单、供应商虚拟仓、入库、库存、PackingList、出库和全链路追溯建立闭环。

| 原则 | 业务含义 |
|---|---|
| 可追溯优先 | 任一采购、入库、库存变化和客户发货都能回到来源需求 |
| 事实与计划分离 | 净需求保存拆解事实，Allocation 保存可修改计划，正式单据保存执行事实 |
| 状态分层 | 生命周期、确认、过账和查询进度不能塞入一个万能状态 |
| UID 为权威关系 | 跨模块关系使用稳定 Uid；业务编码用于查账和历史快照 |
| 正式事实不可抹除 | 已确认、已过账或已形成流水后，不靠删除解决错误 |
| 反向而非篡改 | 错误库存通过反向流水；错误计划通过替代记录；历史反馈通过修正报告 |
| 轻审批、强提示 | 小团队不建立过重审批，但危险操作必须权限、原因、预览和日志齐全 |
| 派生量不重复存储 | 已备好、已入库、已发货、剩余量、齐套量从各自事实查询计算 |

## 3. 端到端业务主线

```text
主数据
  -> 销售订单 / 手工需求 / 投诉补货
  -> 毛需求 GrossDemand
  -> BOM 拆解事实 NetDemand
  -> 执行计划 NetDemandAllocation
  -> 执行追溯 DemandExecutionLink
  -> 采购订单与供应商跟单
  -> 入库单过账
  -> 供应商虚拟仓库存与流水
  -> PackingList 装柜与提交
  -> 正式出库及客供件消耗
  -> 来源、单据、库存和操作日志追溯
```

### 3.1 模块职责

| 阶段 | 主要输入 | 权威实体 | 主要输出 | 是否改变库存 | 主要操作人 |
|---|---|---|---|---|---|
| 主数据 | 产品、客户、供应商资料 | Product、Customer、Supplier、关系表、Bom | 可被单据引用的活动主数据 | 否 | 产品、销售、采购资料维护人员 |
| 销售订单 | 客户 PO 和销售明细 | SalesOrderHeader、SalesOrderLine | 已确认销售需求来源 | 否 | 销售人员 |
| 毛需求 | 销售行、手工需求、投诉补货 | GrossDemand | 可拆解的原始业务需求 | 否 | 计划人员、销售人员 |
| 净需求 | 毛需求与 BOM 快照 | NetDemand | 一次拆解修订中的物料需求事实 | 否 | 系统拆解、计划人员审核 |
| 执行计划 | 净需求、供货方式、默认供应商 | NetDemandAllocation | 当前采购、生产或外协计划 | 否 | 计划人员 |
| 执行追溯 | Allocation 与执行命令 | DemandExecutionLink | 从需求贡献到执行明细的数量关系 | 否 | 系统 |
| 采购与跟单 | 可采购 Allocation | PurchaseOrderHead、PurchaseOrderLine、SupplierProgressReport | 采购单和供应商累计进度 | 否 | 采购、跟单人员 |
| 入库 | 采购到货、客供件收货、PackingList 补入库 | InboundDocument、InboundDocumentLine | 已过账入库事实 | 是，增加 | 跟单、仓库或 PackingList 编排服务 |
| 虚拟仓与库存 | 已过账入出库 | WarehouseSite、InventoryBalance、InventoryLedgerEntry | 当前余额和不可变流水 | 是 | 系统过账服务 |
| PackingList | 可出货 Allocation、库存、装柜资料 | PackingListDocument、PackingListContributionLine | 最终客户出货编排 | 草稿否，提交是 | 出货、跟单人员 |
| 出库 | PackingList 贡献行 | OutboundDocument、OutboundDocumentLine | 客户发货和客供件消耗事实 | 是，减少 | PackingList 编排服务 |
| 日志与追溯 | 成功业务命令 | BusinessOperationLog、各单据和流水 | 人工可读操作历史与技术诊断 | 否 | 系统 |

### 3.2 当前工作台入口

| 工作台 | API 根路由 | 当前业务定位 |
|---|---|---|
| 销售订单 | `/api/sales-orders/workspace` | 销售订单保存、确认、取消确认、关闭和删除草稿 |
| 毛需求 | `/api/demand-planning/gross-demands` | 查询、手工需求、拆解、回退和追溯 |
| 净需求 | `/api/demand-planning/net-demands` | 查询、计划替代、转采购、采购草稿取消和释放 |
| 采购 | `/api/procurement/purchase-orders` | 采购查询、草稿维护、确认、取消确认和供应商进度 |
| 供应商虚拟仓 | `/api/inventory/warehouse-sites` | 虚拟仓维护 |
| 库存余额与流水 | `/api/inventory` | 余额、流水、期初和追溯 |
| 入库 | `/api/inventory/inbounds` | 来源选择、草稿、过账、反向和追溯 |
| 出库 | `/api/inventory/outbounds` | 查询正式出库和追溯；不提供普通人工出库写入口 |
| PackingList | `/api/shipping/packing-lists` | 草稿、预览、提交、反向、追溯和导出 |
| 业务操作日志 | 暂无独立工作台 | 当前由关键业务服务写入，后续补统一只读查询入口 |

## 4. 核心概念

| 概念 | 定义 | 不承担的职责 |
|---|---|---|
| Product | 公司内部稳定产品主数据；保存产品身份、物料角色、供货方式和当前默认供应商 Uid | 不保存客户专属 SKU、供应商 SKU、历史单据数量或当前库存 |
| CustomerProduct | 客户与 Product 的业务关系；保存客户 SKU、客户描述、客户价格和客户专属约定 | 不替代 Product，不保存销售订单历史事实 |
| SupplierProduct | Supplier 与 Product 的采购关系；保存供应商 SKU、采购价格和供应商描述 | 不替代 Product.DefaultSupplierId，不直接改变既有 Allocation 或采购单 |
| Bom | 某父产品、某 BOM 版本下的组成行和用量比例 | 不保存执行供应商、当前库存或采购状态 |
| GrossDemand | 来源业务提出的原始需求 | 不保存 BOM 展开明细、采购进度或发货进度 |
| NetDemand | 某次毛需求拆解修订产生的物料需求事实 | 不保存当前执行供应商，不普通覆盖历史 |
| NetDemandAllocation | 净需求“如何执行、由谁执行、何时交付”的计划 | 不代表采购已下单、供应商已备好或库存已到账 |
| DemandExecutionLink | Allocation 对某执行明细贡献数量的权威关系 | 不替代采购行、入库单、出库单或库存流水 |
| SupplierProgressReport | 供应商对采购行的累计进度反馈历史 | 已备好不等于已入库或库存 |
| InventoryLedgerEntry | 每一次库存增加、减少或反向的不可变事实 | 不允许人工覆盖或删除 |
| InventoryBalance | 按仓库和产品汇总的当前库存投影 | 不是原始事实，可由流水重建 |
| PackingListContributionLine | 本次最终出货对某个销售/需求/Allocation 的精确贡献 | 不允许仅靠 SKU 聚合而丢失来源 |

## 5. 主数据模型

### 5.1 主数据实体职责

| 目标实体/表 | 中文职责 | 权威关系/业务键 | 应保存的事实或快照 | 不应保存 |
|---|---|---|---|---|
| Customer | 客户主数据 | `CustomerCode` 活动唯一 | 名称、联系人、地址、默认贸易条款、默认币种和交付方式 | 销售订单历史金额和发货进度 |
| Supplier | 供应商主数据 | `SupplierCode` 活动唯一 | 名称、联系人、人民币采购条件、默认交期 | 采购单历史供应商名称和库存余额 |
| Product | 产品主数据 | `Sku` 活动唯一；`DefaultSupplierId` 逻辑关系 | 描述、颜色、物料类型、供货方式、BOM 版本 | 默认供应商代码、供应商 SKU、客户 SKU、过程数量 |
| ProductCategory | 产品分类 | 分类编码或同级名称业务唯一 | 父分类、排序和显示名称 | 产品交易事实 |
| ProductColor | 颜色主数据 | 唯一颜色编码 | 中英文名称 | 产品或订单数量 |
| ProductMaster | 主型号资料 | `MasterSku` 唯一 | 主型号层级默认描述和分类 | 具体 SKU 的交易事实 |
| ProductDetail | 产品文件资料 | `ProductId` 或稳定产品关系 | 图纸、说明书、条码、规格文件路径 | 仅靠可变 SKU 作为唯一关系 |
| ProductPackage | 产品包装规格 | `ProductId + PackageType`；一个默认规格 | 装率、尺寸、净重、毛重、体积和包材 | 销售行或 PackingList 的历史包装快照 |
| CustomerProduct | 客户产品关系 | `(CustomerId, CustomerSku)` 活动唯一 | Product Uid、客户 SKU、客户描述、客户价格、MOQ | Supplier 信息和库存 |
| SupplierProduct | 供应商产品关系 | `(SupplierId, ProductId)` 活动唯一 | 供应商 SKU、未税价、含税价和供应商描述 | Product 当前默认供应商之外的全局默认状态 |
| CustomerPoConfig | 客户采购单默认配置 | 客户 Uid/代码对应的有效配置 | 包装、标贴、说明书、人员等默认要求 | 已生成采购单的历史快照 |
| Bom | BOM 组成行 | `(ParentProductId, BomVersion, LineNumber)` 唯一 | `ComponentProductId`、分子、分母和备注 | 供应商、执行方式、库存和进度 |

### 5.2 默认供应商规则

| 规则 | 说明 |
|---|---|
| 权威字段 | `Product.DefaultSupplierId` |
| 设置入口 | 产品管理批量保存可从全部活动供应商中选择；SupplierProduct 关系页也可执行“设为产品默认供应商”命令 |
| 必要校验 | Product 与 Supplier 均活动，并校验 Product.Version；产品管理入口不要求预先存在 SupplierProduct 关系 |
| 兼容字段 | 当前库在保存 `DefaultSupplierId` 时同步权威 `DefaultSupplierCode` 供旧链路兼容；`DefaultSupplierSku` 仍属于 SupplierProduct，目标重建后只保留 Uid 权威关系 |
| 历史影响 | 修改 Product 默认供应商不自动修改既有 NetDemandAllocation、采购单或历史快照 |
| 无默认供应商 | 毛需求拆解放行，采购型 Allocation 进入待分配供应商 |
| 失效默认供应商 | 新命令不得使用；工作台强提示并要求修复主数据或人工计划 |

### 5.3 BOM 与物料角色

| 规则 | 说明 |
|---|---|
| BOM 有效性 | `Product.BomVersion = 0` 表示无 BOM；大于 0 时应存在对应版本组成行 |
| 用量 | `父需求数量 × Numerator ÷ Denominator`，分子、分母必须大于 0 |
| SupplyType | 只表达采购、生产、外协，不表达是否有 BOM |
| 客供件 | 是 Product 的物料角色；应为采购型终端物料，不继续展开 BOM |
| 历史解释 | 拆解时将 BOM 行、版本、路径、物料类型和供货方式写入 NetDemand 快照 |
| 修改影响 | 修改当前 BOM 只影响后续拆解；既有净需求和出货消耗继续按历史拆解快照解释 |

## 6. 实体关系与一致性

| 上游 | 关系 | 下游 | 一致性规则 |
|---|---:|---|---|
| Customer | 1:N | CustomerProduct | CustomerProduct 必须引用活动客户 |
| Product | 1:N | CustomerProduct | 标准客户产品必须引用活动 Product |
| Supplier | 1:N | SupplierProduct | SupplierProduct 必须引用活动供应商 |
| Product | 1:N | SupplierProduct | 同一活动供应商和产品只能有一条活动关系 |
| Product | 1:N | Bom（父产品） | BOM 版本与 Product.BomVersion 一致 |
| Bom | N:1 | Product（组件） | 组件使用稳定 Product Uid |
| Supplier | 1:1 | 活动供应商 WarehouseSite | 第一阶段每个活动供应商一个活动虚拟仓 |
| SalesOrderHeader | 1:N | SalesOrderLine | `(SalesOrderId, LineNumber)` 活动唯一 |
| SalesOrderLine | 1:1 | 活动 GrossDemand | 销售确认时按来源行幂等生成 |
| GrossDemand | 1:N | NetDemand | 按 `DecompositionRevision` 保存拆解历史 |
| NetDemand | 1:N | NetDemandAllocation | 按 PlanRevision 保存替代历史；首期一条活动计划 |
| A Allocation | 1:N | B Allocation | B 通过 `DeliveryTargetAllocationId` 指向具体 A 计划 |
| NetDemandAllocation | 1:N | DemandExecutionLink | 支持部分和多次转执行 |
| PurchaseOrderHead | 1:N | PurchaseOrderLine | `(PurchaseOrderId, LineNumber)` 活动唯一 |
| PurchaseOrderLine | 1:N | DemandExecutionLink | 多个来源贡献可以合并到同一采购行 |
| PurchaseOrderLine | 1:N | SupplierProgressReport | 追加历史，Sequence 严格递增 |
| InboundDocument | 1:N | InboundDocumentLine | 明细不能脱离入库头存在 |
| WarehouseSite + Product | 1:1 | InventoryBalance | `(WarehouseSiteId, ProductId)` 唯一 |
| InventoryBalance | 1:N | InventoryLedgerEntry | 余额由流水顺序过账，可重建 |
| PackingListDocument | 1:N | PackingListContributionLine | 每条贡献保留精确来源和仓库 |
| PackingListContributionLine | 1:N | OutboundDocumentLine | 正常产品和客供件消耗分别形成正式出库贡献 |

### 6.1 外键和快照策略

| 关系类型 | 数据库策略 | Application 责任 |
|---|---|---|
| 单据头与自身明细 | 可建立强 FK | 校验状态、版本和行号唯一 |
| 同聚合替代关系 | 可建立强 FK，例如 Allocation 替代和流水反向 | 防循环、校验同一业务聚合 |
| 跨模块业务关系 | 默认逻辑外键并建立索引 | 校验目标存在、活动、类型和数量兼容 |
| 主数据到历史单据 | Uid 逻辑关系 + 必要快照 | 新单据只引用活动主数据；历史不随主数据刷新 |
| 编码和名称快照 | 不是外键 | 仅供历史解释、Excel 和人工查账 |

## 7. 销售订单

### 7.1 流程

| 动作 | 允许条件 | 事务结果 | 阻断条件 | 反向或后续动作 |
|---|---|---|---|---|
| 保存草稿 | Open + 待确认；版本匹配 | 保存头和完整活动行集合，稳定行号 | 客户、产品关系无效；数量或价格非法；版本冲突 | 可继续修改或删除草稿 |
| 确认 | Open + 待确认 | 订单变已确认；每条活动销售行幂等建立一条 GrossDemand | 行为空、来源重复、产品关系损坏 | 未拆解时可取消确认 |
| 取消确认 | Open + 已确认；填写原因 | 恢复待确认；从未拆解且无任何净需求历史的毛需求物理删除；曾拆解并已完整安全回退的毛需求保留为 Voided | 活动拆解、执行 Link、入出库、装箱、库存事实，或 revision/历史不完整 | 先完成下游取消或正式反向，再安全回退拆解 |
| 关闭 | Open；填写原因 | DocumentStatus=Closed，记录人、时间、原因 | 已关闭；必要业务校验失败 | 不自动撤销历史需求或执行事实 |
| 删除草稿 | Open + 待确认且无下游 | 软删除订单头行 | 已确认、已关闭或已有毛需求 | 无 |

### 7.2 销售订单事实

| 类别 | 保存位置 | 规则 |
|---|---|---|
| 当前客户关系 | Header.CustomerId | 新建时必须指向活动客户 |
| 客户和贸易条款快照 | Header | 确认后不因客户主数据变化而自动刷新 |
| 产品关系 | Line.ProductId | 标准行必填；非标行为空 |
| 客户产品关系 | Line.CustomerProductId | 标准行可保存，用于带出客户 SKU 和价格 |
| 产品、客户 SKU、描述、颜色、规格快照 | Line | 保存订单成立时事实 |
| 数量、价格、金额 | Line；必要汇总在 Header | 金额是订单商业快照，不是履约进度 |
| 客户已发货量和最后发货日 | 查询正式 OutboundDocumentLine | 不进入 SalesOrderLine 目标实体 |

## 8. 毛需求 GrossDemand

### 8.1 来源

| 来源类型 | SourceUid | SourceLineId | 生成规则 |
|---|---|---|---|
| 销售订单 SO | SalesOrderHeader.Uid | SalesOrderLine.Uid | 销售确认时一行生成一条活动毛需求 |
| 手工需求 MD | 自身 Uid | 自身 Uid | 建立时生成稳定手工需求号 |
| 投诉补货 CR | 投诉或补货单 Uid | 来源明细 Uid | 进入同一毛需求和净需求链路，不形成孤岛 |

### 8.2 流程

| 动作 | 允许条件 | 事务结果 | 阻断条件 | 反向流程 |
|---|---|---|---|---|
| 建立手工需求 | 标准产品有效，或明确非标 | GrossDemand=Active + Pending | 数量不大于 0；标准产品无效 | 未拆解时可修改、关闭 |
| 修改手工需求 | 手工来源、Active、Pending、版本匹配 | 更新原始需求事实和快照 | 已拆解、已关闭、版本冲突 | 先安全回退拆解 |
| 拆解 | Active + Pending | 同事务写 NetDemand、初始 Allocation，revision+1，状态 Decomposed | BOM 损坏、循环、数量不守恒或已有不完整活动拆解 | 无活动 Link 时可回退 |
| 回退拆解 | Active + Decomposed，且无活动 Link | Allocation 取消；NetDemand RolledBack；GrossDemand 回 Pending | 任一活动 Link、数量或 revision 状态损坏 | 先取消安全采购草稿或做正式反向 |
| 关闭手工需求 | 手工来源、Active、无活动拆解 | Lifecycle=Closed，记录原因 | 已有活动净需求或执行关系 | 回退后关闭 |

### 8.3 毛需求实体边界

| 保存 | 不保存 |
|---|---|
| 来源类型、来源头行 Uid、单号行号快照 | 采购单号快捷字段 |
| ProductId 或非标标识 | 已转采购、已入库、已发货数量 |
| SKU、客户型号、描述、颜色、规格、图片快照 | 当前供应商或执行方式 |
| DemandQty、RequiredDate、备注 | 齐套率和履约状态缓存 |
| 生命周期、拆解状态、拆解 revision 和审计 | 旧 ApprovalStatus、OrderStatus 万能状态 |

### 8.4 销售订单取消确认时的毛需求双路径

取消确认是销售订单聚合命令，不是毛需求列表中的普通删除。订单头、订单行、关联毛需求、净需求/计划分配/执行关系范围、订单状态恢复和业务操作日志必须处于同一事务，并按该顺序锁定。

| 毛需求事实 | 取消确认结果 | 原因 |
|---|---|---|
| `DecompositionRevision=0`、Active + Pending，且从未产生任何 NetDemand 历史 | 物理删除 GrossDemand | 该记录只是本次销售确认派生出的可重建中间事实，没有独立历史价值 |
| `DecompositionRevision>0`、Active + Pending，全部 revision 的 NetDemand 与 Allocation 历史完整且均已回退、作废、取消或替代，无活动 Link 和正式履约事实 | GrossDemand 保留，改为 `LifecycleStatus=Voided`、`IsDeleted=0` | 毛需求是已发生拆解历史的 Trace 根，删除会形成孤儿或掩盖历史 |
| revision 不连续、历史缺失、存在活动拆解/Allocation/Link，或已有采购履约、入库、出库、PackingList、库存流水 | 整张销售订单取消确认失败 | 无法证明安全时不得猜测清理，也不得部分成功 |

同一销售订单可以同时包含物理删除行和 Voided 保留行，两类处理必须全成全败。取消确认原因 Trim 后必填，最长 1000 字符；每次实际提交生成 `CommandId`，以 `SalesOrder + CancelConfirmation + CommandId` 写入 `BusinessOperationLog`。同一命令、订单和原因的重试返回首次结果；CommandId 换订单或换原因重用必须拒绝。

重新确认时，被物理删除的来源行生成新的 GrossDemand Uid；旧的 Voided GrossDemand 及其 Trace 保持不变，同一来源行再生成新的活动 GrossDemand Uid。活动来源唯一约束只约束 Active 且未删除记录。

### 8.5 外部销售订单导入与需求池判定

外部销售订单必须先落为内部 `SalesOrderHeader/Line`，并为外部系统、外部订单和外部行建立稳定的内部 Uid 映射。不得只凭销售单号、SKU 或可变行号判断是否已经进入需求池。

| 判断目标 | 权威查询 | 规则 |
|---|---|---|
| 销售行是否已有毛需求 | `GrossDemand(SourceType=SO, SourceUid=SalesOrderHeader.Uid, SourceLineId=SalesOrderLine.Uid)` | 活动来源关系必须幂等唯一 |
| 是否已经拆解 | `GrossDemand.DecompositionStatus` 与当前 `DecompositionRevision` | 状态与活动 NetDemand 不一致时视为数据损坏 |
| 当前拆解有哪些物料 | 当前 revision 的活动 `NetDemand` | 不通过 SKU 从全局净需求中猜测 |
| 当前准备如何执行 | 活动 `NetDemandAllocation` | 供应商、执行方式和计划交期以 Allocation 为准 |
| 已转下游多少 | 活动 `DemandExecutionLink` 有效贡献合计 | 有效贡献为 `AllocatedQty-ReleasedQty` |

`GrossDemand.SourceNo`、SKU 和来源行号都是历史查账快照或辅助筛选，不替代来源头行 Uid。

## 9. 净需求 NetDemand 与执行计划

### 9.1 拆解事实和计划必须分离

| 内容 | NetDemand | NetDemandAllocation |
|---|---|---|
| 表达问题 | 这次拆解需要什么 | 这项需求准备如何执行 |
| 是否可普通修改 | 否 | 通过替代命令修改 |
| 数量 | GrossQty、NetQty | PlannedQty |
| 日期 | 原需求 RequiredDate | 可调整 PlannedDeliveryDate |
| 供应商 | 不保存当前执行供应商 | PurchaseSupplierId |
| A/B 结构 | 父、根、送达目标 NetDemand | 具体目标 Allocation 和目标供应商 |
| 历史方式 | 拆解 revision + 生命周期 | PlanRevision + ReplacesAllocationId |

### 9.2 初始 Allocation

| 场景 | ExecutionType | PurchaseSupplierId | AssignmentSource | 结果 |
|---|---|---|---|---|
| 标准采购产品有默认供应商 | Purchase | Product.DefaultSupplierId | ProductDefault | 可转采购 |
| 标准采购产品无默认供应商 | Purchase | 空 | Unassigned | 拆解放行，工作台强提示 |
| 非标需求 | Purchase | 空 | Unassigned | 生成采购型待分配根计划 |
| 生产产品 | Production | 空 | ProductDefault 或计划来源 | 保留计划，等待未来生产工作台 |
| 外协产品 | Outsourcing | 按未来规则 | ProductDefault 或计划来源 | 保留计划，等待未来外协工作台 |

### 9.3 客供件 A/B 规则

| 概念 | A：父产品 | B：客供件 |
|---|---|---|
| 采购供应商 | A 自身执行供应商 | B 自身采购供应商，二者可不同 |
| 送达目标 | 无 | 指向 A 的具体活动 Allocation |
| 实际收货仓 | A 执行供应商虚拟仓 | 同样进入 A 执行供应商虚拟仓 |
| A 供应商改变 | 替代 A Allocation | 同事务替代 B 的送达目标，B 采购供应商不变 |
| B 采购供应商改变 | A 不变 | 只替代 B 自身采购计划 |
| Link 已存在 | 相关 A/B 计划变更阻断 | 先处理下游执行关系 |

### 9.4 计划替代

1. 锁定当前活动 Allocation、关联 A/B Allocation 和活动 Link 范围。
2. 存在相关活动 Link 时阻断。
3. 旧 Allocation 置为 `Superseded`。
4. 新增 `PlanRevision + 1` 的 Allocation，`ReplacesAllocationId` 指向旧记录。
5. A 的供应商改变时，同事务替代所有依赖该 A 的 B 送达目标。
6. 记录变更原因、操作人和时间；列表只显示活动计划，Trace 显示全部历史。

### 9.5 转采购规则

| 规则 | 说明 |
|---|---|
| 三个入口 | 人工勾选、按来源单一键转采购、采购工作台拉取；共用 Preview/Create 内核 |
| 人工数量 | `0 < PurchaseQty <= RemainingQty`，默认全部剩余 |
| 一键数量 | 只允许全部剩余量，不允许部分 |
| 来源隔离 | 禁止跨来源单合并；采购头最小分组为来源单 + 采购供应商 |
| 行组织 | 默认保持来源明细；用户可选择合并兼容行 |
| 交期合并 | 不同交期可强确认合并，采购交期取最早日期，Link 仍逐来源保存 |
| A/B | 可分开转采购；只转 A 时提示仍有 B 未执行；B 缺送达目标时阻断 |
| 采购资料 | 缺 SupplierProduct 或价格允许建草稿并标记待补；缺供应商或 B 送达目标阻断 |
| 币种 | 固定人民币 CNY |
| Preview | 数量、合并模式或目标草稿变化后 Token 失效，必须重新 Preview |
| 幂等 | ExecutionRequestId 控制请求；CommandItemId 控制逐贡献 Link |

### 9.6 需求模型阅读与操作入口

需求计划领域在用户界面上只暴露“毛需求”和“净需求”两个工作台，但权威事实按职责分表保存。各表不是四个并列业务模块。

`GrossDemand`、`NetDemand`、`NetDemandAllocation` 和 `DemandExecutionLink` 不合并为毛需求、净需求两张物理表：来源事实、拆解事实、可替代执行计划和多对多执行贡献具有不同生命周期、修改频率、基数和反向规则。通过聚合查询收拢用户认知，不通过万能宽表收拢权威事实。

| 当前问题 | 首要入口 | 必要关联 | 不应写入 |
|---|---|---|---|
| 来源业务是否进入需求池 | GrossDemand | SalesOrderLine 或其他来源行 | 采购、收货、发货进度 |
| BOM 拆出了哪些物料 | NetDemand | GrossDemand | 当前供应商和下游单号 |
| 当前准备如何采购/生产/外协 | 活动 NetDemandAllocation | NetDemand、GrossDemand | 已收货、已发货缓存 |
| 已经转到哪些执行单行 | DemandExecutionLink | Allocation 和目标单据行 | 入库、跟单过程数量 |
| 实际收了多少 | 已过账 InboundDocumentLine 和反向事实 | Link、Allocation、库存流水 | 四张需求计划表 |

净需求工作台的列表主入口是“活动 `NetDemandAllocation` + `NetDemand` + `GrossDemand` + Link/入库/出库聚合”的 Query DTO。业务人员不需要分别读取物理表；详情和 Trace 才展开拆解、计划替代及执行历史。

`NetDemandPlanCommandLog` 只保存计划命令幂等结果，不是第五类业务需求。未来可治理为跨模块通用的 Command Receipt/Idempotency Record，但不得并入 NetDemand，也不得与面向人工审计的 `BusinessOperationLog` 混为一个无边界万能日志。

## 10. DemandExecutionLink

### 10.1 权威语义

`DemandExecutionLink` 表示某条 `NetDemandAllocation` 对某个下游执行明细贡献了多少数量。采购行可以合并多个来源，但每个来源贡献必须保留独立 Link。

| 字段类别 | 目标内容 |
|---|---|
| 关系 | NetDemandId、NetDemandAllocationId、TargetType、TargetHeadId、TargetLineId |
| 人工查账快照 | TargetNo、DemandRequiredDate、PlannedDeliveryDate |
| 数量 | AllocatedQty、ReleasedQty；有效贡献=`AllocatedQty-ReleasedQty` |
| 状态 | Active、Cancelled、Reversed |
| 幂等 | ExecutionRequestId、CommandItemId |
| 反向审计 | Cancelled/Reversed 的时间、人和原因 |

### 10.2 约束

| 约束 | 目标规则 |
|---|---|
| Allocation 关系 | 新 Link 的 NetDemandAllocationId 必填，且必须属于同一 NetDemandId |
| CommandItemId | 全局唯一，防止重复贡献 |
| 数量 | `AllocatedQty > 0`、`0 <= ReleasedQty <= AllocatedQty` |
| 活动贡献 | 只汇总 Active Link 的有效贡献 |
| 过程数量 | 不保存 CompletedQty、ReceivedQty；从进度、入库和出库事实查询 |
| 删除 | 不物理删除；取消或反向保留历史 |

### 10.3 外部采购订单导入锚点

需求驱动的外部采购订单导入，权威需求锚点是 `NetDemandAllocation`，并通过 `DemandExecutionLink` 将每一份来源数量贡献连接到采购订单行。导入程序不直接以 GrossDemand 作为采购执行锚点。

```text
PurchaseOrderLine
        ↑
DemandExecutionLink
        ↓
NetDemandAllocation
        ↓
NetDemand
        ↓
GrossDemand
```

| 导入内容 | 规则 |
|---|---|
| 最佳外部锚点 | 外部系统保存并回传 `NetDemandAllocationId` 和稳定 `CommandItemId`/外部需求行键 |
| Link 必填关系 | `NetDemandId`、`NetDemandAllocationId`、采购头行 Uid、采购单号快照和贡献数量 |
| 一致性 | `Allocation.NetDemandId` 必须等于 `Link.NetDemandId` |
| 毛需求关系 | 通过 `Allocation -> NetDemand -> GrossDemand` 权威推导；无需在采购行重复保存权威 GrossDemandId |
| 单一来源采购行 | 可保存来源类型、来源 Uid、来源行和单号快照作为人工快捷入口 |
| 多来源合并采购行 | 每个来源单独建立 Link；采购行 SourceLineId 为空，不得任取一个毛需求冒充全部来源 |
| 只有销售行锚点 | 先解析内部 SalesOrderLine，再沿 GrossDemand、当前 NetDemand revision 和活动 Allocation 定位 |
| 只有 SKU/供应商/数量 | 不足以自动建立需求 Link；必须人工计划分配或进入明确的计划外采购流程 |

导入前必须锁定并验证 Allocation 活动、供应商和执行类型兼容、剩余可执行数量充足、CommandItemId 未使用。外部历史采购若无法证明需求来源，不得伪造 DemandExecutionLink。

## 11. 采购订单与供应商跟单

### 11.1 采购头行职责

| 实体 | 保存 | 不保存 |
|---|---|---|
| PurchaseOrderHead | 单号、供应商 Uid 与快照、来源头快照、人民币、生命周期、确认状态、商务要求、日期、幂等请求 | 行数、总数量、已备好、已入库、已发货等过程缓存 |
| PurchaseOrderLine | 产品 Uid、产品与供应商 SKU 快照、采购数量、价格金额、计划交期、B 送达目标、来源摘要 | ReadyQty、ReceivedQty、ShippedQty、LastReceivedDate |
| SupplierProgressReport | 采购行、Sequence、安排状态、累计 ReadyQty、预计备好日、报告日、备注、修正原因、CommandId | 库存和实际发货 |

### 11.2 采购流程

| 动作 | 允许条件 | 事务结果 | 阻断条件 | 反向流程 |
|---|---|---|---|---|
| 创建草稿 | 有可采购 Allocation、供应商和有效 Preview | 写采购头行与 Link；状态 Active + 待确认 | 剩余量不足、版本变化、B 目标缺失、Preview 失效 | 安全取消或释放数量 |
| 更新草稿商务字段 | Active + 待确认、版本匹配 | 修改价格、备注、日期等允许字段 | 已确认、已关闭、已作废、存在不安全下游 | 取消确认后处理 |
| 确认采购 | Active + 待确认，资料完整 | ConfirmationStatus=已确认，写业务日志 | 供应商失效、数量不守恒、必要价格缺失 | 未入库、无库存事实时可取消确认 |
| 取消确认 | Active + 已确认，无正式入库/库存事实 | 恢复待确认并记录原因 | 已收货或已有库存流水 | 先做入库反向 |
| 供应商进度 | 有效采购行 | 追加 SupplierProgressReport | ReadyQty 非法；向下修正无原因 | 用新修正报告，不覆盖旧报告 |
| 取消安全草稿 | Active + 待确认，无收货/库存事实 | 采购头 Voided，Link Cancelled，净需求剩余量恢复 | 已确认、已入库或已有库存流水 | 正式反向流程 |
| 减少采购数量 | 安全草稿，提交版本和原因 | 按规则释放 Link，更新采购行 | 增量、供应商变化或已存在正式事实 | 重新从剩余 Allocation 转采购 |

### 11.3 已备好分配

供应商累计已备好量用于跟单和装柜计划，不等于库存。采购行合并多个需求来源时，展示层按以下稳定顺序分配覆盖量：

```text
DemandRequiredDate 升序
  -> SourceLineNumber 升序
  -> NetDemandAllocation Uid 升序
```

该分配只是查询投影。PackingList 的实际出货归属由其贡献行决定，并以正式出库为最终事实。

### 11.4 创建、追加与释放的事务规则

| 规则 | 说明 |
|---|---|
| 同一来源原子性 | 同一来源单即使生成多个供应商采购头，也必须全部成功或全部回滚 |
| 跨来源隔离 | 一次请求可包含多个来源单；按来源顺序执行独立事务，并返回 Succeeded、AlreadyApplied 或 Failed |
| 默认新建 | 后续再次转采购默认新建草稿，避免静默修改已交给老板或供应商查看的单据 |
| 安全追加 | 只允许同来源、同供应商、Active + 待确认、Version 匹配且无收货/库存事实的草稿 |
| 一键入口 | 始终新建采购草稿，不允许追加 |
| 减量释放 | 必须先 Preview；按原需求交期降序、来源行号降序、Allocation Uid 降序释放 Link |
| 修改供应商 | 不直接修改采购头；应取消安全草稿、重新计划 Allocation 后重新转采购 |
| 锁顺序 | GrossDemand → NetDemand → Allocation → Link 范围 → 幂等范围 → 目标采购头行 |

采购 Create 执行时必须重新读取 Version、RemainingQty、供应商、送达目标和聚合事实，不能只信任 Preview 返回或客户端提交的数据。

## 12. 供应商虚拟仓与库存

### 12.1 仓库规则

| 规则 | 说明 |
|---|---|
| 第一阶段仓库 | 每个活动供应商一个活动供应商虚拟仓 |
| 权威关系 | WarehouseSite.SupplierId；供应商代码和名称只作快照 |
| 编码 | WarehouseSite.Code 业务唯一，目标表不沿用 WhseCode 等旧列名 |
| 停用 | 有库存余额或流水的仓库不能删除；可按规则停用 |
| 内部仓 | 模型可预留 SiteType，但当前业务只启用 SupplierVirtual |
| 客供件 | 进入父产品执行供应商的虚拟仓，而不是客供件采购供应商仓 |

### 12.2 余额和流水

| 实体 | 业务性质 | 写入规则 |
|---|---|---|
| InventoryBalance | 当前投影 | `(WarehouseSiteId, ProductId)` 唯一；只由统一库存过账服务更新 |
| InventoryLedgerEntry | 原始库存事实 | 只追加；Sequence 与 CommandItemId 唯一；不修改、不软删除 |

### 12.3 库存流水类型

| 数值 | 类型 | 数量方向 |
|---:|---|---:|
| 10 | PurchaseReceiptInbound | 正数 |
| 11 | CustomerSuppliedReceiptInbound | 正数 |
| 12 | PackingListAutoReceiptInbound | 正数 |
| 20 | FinalCustomerShipmentOutbound | 负数 |
| 21 | CustomerSuppliedConsumptionOutbound | 负数 |
| 90 | NegativeStockExceptionOutbound | 负数，仅特殊授权缺口 |
| 100 | OpeningBalance | 按期初方向 |
| 900 | Reversal | 与被反向流水相反 |

### 12.4 负库存异常

正常过账禁止形成负库存。PackingList 确实需要放行时，只允许具备特殊权限的用户对本次被阻断缺口执行异常放行：

1. 显示缺口、仓库、SKU、来源需求和预计影响的强提示。
2. 必须填写原因并记录 BusinessOperationLog。
3. 正常可用库存写普通出库流水；缺口部分单独写 `NegativeStockExceptionOutbound`。
4. 不修改供应商 ReadyQty，不伪造入库事实。
5. 后续补录真实入库后自然冲平负库存；不得删除原异常流水。

## 13. 入库

### 13.1 入库类型

| 数值 | 类型 | 来源 | 目标仓库 |
|---:|---|---|---|
| 10 | PurchaseReceipt | 已确认采购行和 Link | Allocation 的执行/送达目标供应商虚拟仓 |
| 11 | CustomerSuppliedReceipt | 客供件 B 的已确认采购行和活动 Link | 父产品 A 的活动执行供应商虚拟仓 |
| 12 | PackingListAutoReceipt | PackingList 本次来源缺口 | 对应贡献行的供应商虚拟仓 |
| 100 | OpeningBalance | 经授权的期初命令 | 指定活动仓库 |

客供件 B 的正常收货不得仅凭活动 Allocation 建立。Allocation 表示“计划采购”，活动 Link 和已确认采购订单表示“已经下单”；只有后者才构成正常收货凭证。

### 13.2 入库流程

| 动作 | 允许条件 | 事务结果 | 阻断条件 | 反向流程 |
|---|---|---|---|---|
| 创建草稿 | 来源可证明、同一仓库、数量大于 0 | 写 InboundDocument 和明细，不改库存 | 来源、产品、仓库不完整或超来源剩余量 | 可修改或作废草稿 |
| Preview 过账 | 草稿、版本匹配 | 返回将产生的库存变化和警告，不写库 | 来源事实变化 | 重新 Preview |
| 过账 | Preview 有效 | 同事务置 Posted、写流水、更新余额和业务日志 | 重复命令、超收、仓库失效、版本变化 | 执行反向 |
| 反向 Preview | 已过账 | 返回反向影响 | 已被后续出库消耗导致无法安全反向 | 先反向下游 |
| 反向 | Preview 有效、填写原因 | 写反向流水，状态 Reversed，余额恢复 | 破坏下游库存守恒 | 不删除原入库和流水 |

### 13.3 数量规则

- 第一阶段不允许超采购、超 Allocation 或超 PackingList 来源缺口入库。
- 采购入库和客供件入库必须精确保留 `DemandExecutionLinkId`、`NetDemandAllocationId` 或可证明的来源 Uid。
- PackingList 自动入库只补本次来源缺口：

```text
自动入库数量 = max(本次贡献出货数量 - 当前可用于该来源的正式库存, 0)
```

- SupplierProgressReport.ReadyQty 不直接生成库存；自动入库也不得超过当前可证明的来源范围。

### 13.4 客供件可收货来源池

入库页面不得让用户自由输入一个客供件 SKU 后直接收货。页面必须先提供只读“客供件可收货来源池”，用户从可证明来源中选择并填写本次实收数量。

客供件 B 进入正常可收货池必须同时满足：

1. B 属于当前活动拆解 revision，且是客供件终端物料。
2. B 的活动 Allocation 为采购执行，并通过 `DeliveryTargetAllocationId` 指向活动 A Allocation。
3. B 存在活动 `DemandExecutionLink`，Link 指向有效采购行。
4. 采购订单已确认，且未关闭、作废或取消确认。
5. Link 有效贡献 `AllocatedQty-ReleasedQty` 大于已过账净收货数量。
6. A 的活动 Allocation 有有效执行供应商，且该供应商存在唯一活动虚拟仓。
7. Product、单位、采购供应商、送达目标和仓库关系可被服务端证明。

正常客供件收货链路固定为：

```text
B NetDemand
  -> B NetDemandAllocation
  -> DemandExecutionLink
  -> B PurchaseOrderLine
  -> InboundDocumentLine
  -> InventoryLedgerEntry
  -> A 供应商虚拟仓 InventoryBalance
```

客供件的采购供应商是 B 自身供应商；实际收货仓由 B 的 `DeliveryTargetAllocationId` 指向 A Allocation，再由 A 的执行供应商解析其虚拟仓。入库页面不得让用户把 B 随意改收至 B 供应商仓或其他仓库。

| 可收货池字段 | 权威来源 |
|---|---|
| 采购单和采购行 | PurchaseOrderHead/Line |
| B 产品、SKU、单位 | NetDemand、PurchaseOrderLine 快照 |
| B 采购供应商 | B Allocation/采购单 |
| 送达 A 供应商 | B.DeliveryTargetAllocationId -> A Allocation |
| 目标虚拟仓 | A Allocation.PurchaseSupplierId -> WarehouseSite |
| 有效采购贡献 | Link.AllocatedQty-Link.ReleasedQty |
| 已过账净收货 | 该 Link 对应的已过账 InboundDocumentLine 和反向净额 |
| 可收数量 | 有效采购贡献-已过账净收货 |

只有 `可收数量 > 0` 的来源进入选择池。入库行必须保留 Link、Allocation、产品、来源采购行和必要毛需求/销售快照；实际收货量只写 InboundDocumentLine，过账时形成库存流水和余额，不反写 GrossDemand、NetDemand、Allocation 或 Link 的收货缓存。

活动入库草稿不属于正式收货事实，但页面应单独显示或扣减其他活动草稿占用，降低重复建草稿风险。正式过账必须重新锁定来源并按已过账净收货量校验，不得因已有草稿而跳过超收校验。

“无采购单客供件收货”不属于正常入口，第一阶段不开放。未来如确有必要，应建立独立的无单收货异常流程，要求特殊权限、原因、待匹配状态和 BusinessOperationLog；不得伪造 Link 或混入正常可收货池。

## 14. PackingList 与出库

### 14.1 PackingList 业务边界

| 规则 | 说明 |
|---|---|
| 客户范围 | 一张 PackingList 只对应一个最终客户 |
| 来源范围 | 可包含多个销售订单和多个供应商虚拟仓 |
| 明细粒度 | 同 SKU、不同销售行仍保留不同贡献行；界面可视觉聚合，数据不能丢来源 |
| 草稿 | 不改变库存 |
| 提交 | 在最外层事务中编排必要自动入库、最终产品出库、客供件消耗和日志 |
| 已发货权威 | 已过账 OutboundDocumentLine/InventoryLedgerEntry，不是 PackingList 草稿数量 |
| 已提交单据 | 业务字段不可普通编辑；通过整单反向后再重建 |

### 14.2 PackingList 流程

| 动作 | 允许条件 | 事务结果 | 阻断条件 | 反向流程 |
|---|---|---|---|---|
| 建立/更新草稿 | 来源 Allocation 可出货，客户一致，版本匹配 | 保存文档和精确贡献行 | 来源无效、客户混用、数量超过可出货范围 | 可作废未提交草稿 |
| Post Preview | 草稿有效 | 计算各仓库库存、自动入库、A 出库、B 消耗和警告 | 来源或库存变化 | 任一相关修改后重新 Preview |
| 提交 | PreviewToken 有效 | 同事务写自动入库、正式出库、流水、余额和日志，PackingList=Posted | 正常库存不足、客供件比例不可证明、版本变化 | 特殊授权负库存或修正业务数据 |
| Reverse Preview | 已提交 | 展示所有将反向的入库、出库和库存影响 | 存在后续依赖导致无法恢复 | 先处理后续依赖 |
| 整单反向 | Preview 有效、原因必填 | 按反向顺序生成反向流水和状态，PackingList=Reversed | 任一子步骤失败 | 整个事务回滚 |

### 14.3 客供件消耗

- 使用 PackingList 贡献行对应的历史 NetDemand/Allocation 和拆解比例，不读取当前 BOM 重算历史。
- 父产品 A 从其执行供应商虚拟仓出库到最终客户。
- 客供件 B 从同一 A 执行供应商虚拟仓按历史比例消耗。
- B 的实际采购供应商不决定其消耗仓；送达目标 Allocation 决定仓库。

### 14.4 出库边界

| 出库类型 | 来源 | 写入口 |
|---|---|---|
| FinalCustomerShipment | PackingList 最终产品贡献 | 仅 PackingList 提交编排 |
| CustomerSuppliedConsumption | PackingList 对应客供件消耗 | 仅 PackingList 提交编排 |

出库工作台第一阶段只负责查询、详情和 Trace，不提供绕过 PackingList 的普通人工出库。负库存特殊授权体现在缺口流水类型 90，不伪装成正常出库事实。

## 15. 状态模型

### 15.1 持久化状态

| 聚合 | 状态维度 | 目标值 | 说明 |
|---|---|---|---|
| SalesOrderHeader | DocumentStatus | Open=0、Closed=9 | 与确认、发货进度分离 |
| SalesOrderHeader | ConfirmationStatus | 待确认=0、已确认=1 | 取消确认恢复待确认 |
| GrossDemand | LifecycleStatus | Active=0、Closed=8、Voided=9 | 不承载拆解进度 |
| GrossDemand | DecompositionStatus | Pending=0、Decomposed=1 | 表示是否存在活动拆解 |
| NetDemand | LifecycleStatus | Active=0、RolledBack=8、Voided=9 | 回退保留历史 |
| NetDemandAllocation | LifecycleStatus | Active=0、Superseded=8、Cancelled=9 | 修改计划采用替代记录 |
| DemandExecutionLink | LinkStatus | Active=0、Cancelled=8、Reversed=9 | 取消和反向不删除 |
| PurchaseOrderHead | LifecycleStatus | Active=0、Closed=8、Voided=9 | 草稿不是生命周期值 |
| PurchaseOrderHead | ConfirmationStatus | 待确认=0、已确认=1 | 草稿=`Active + 待确认` |
| InboundDocument | LifecycleStatus | Active=0、Closed=8、Voided=9 | 与过账分离 |
| InboundDocument | PostingStatus | Unposted=0、Posted=1、Reversed=8 | 反向保留原单 |
| OutboundDocument | LifecycleStatus | Active=0、Closed=8、Voided=9 | 正式出库由 PackingList 产生 |
| OutboundDocument | PostingStatus | Posted=1、Reversed=8 | 第一阶段无人工未过账出库草稿 |
| PackingListDocument | LifecycleStatus | Active=0、Closed=8、Voided=9 | 与提交状态分离 |
| PackingListDocument | PostingStatus | Unposted=0、Posted=1、Reversed=8 | 提交后只能反向 |

持久化枚举数值一旦进入正式数据不得重排。Entity 中不得继续用无语义的 `byte` 代替已经冻结的业务枚举。

### 15.2 查询计算状态

| 展示状态 | 计算来源 | 是否持久化 |
|---|---|---|
| 销售未发货/部分发货/已发货 | 销售行数量与正式最终出库净额 | 否 |
| 毛需求未执行/部分执行/已执行 | 活动 Allocation 和 Link 有效贡献 | 否 |
| 净需求待分配供应商 | 采购型活动 Allocation.SupplierId 为空 | 否 |
| 净需求送达目标待分配 | B 的目标 Allocation 或目标供应商为空 | 否 |
| 可转/部分转/已转采购 | PlannedQty 与活动 Link 有效贡献 | 否 |
| 下游草稿/已确认 | Link 目标采购头生命周期和确认状态 | 否 |
| 采购未安排/已安排 | 最新 SupplierProgressReport.ArrangementStatus | 否 |
| 已备好覆盖 | 最新 ReadyQty 按来源贡献顺序分配 | 否 |
| 已入库 | 已过账入库和反向流水净额 | 否 |
| 当前库存 | InventoryBalance，并可由 Ledger 校验 | Balance 是投影，不是流程状态 |
| 齐套数量 | 父件可用量、客供件可用量和历史 BOM 比例 | 否 |

## 16. 数量事实来源

| 业务数量 | 权威来源 | 编辑方式 | 禁止缓存位置 |
|---|---|---|---|
| 销售数量 | SalesOrderLine.Quantity | 草稿期修改 | 无 |
| 毛需求数量 | GrossDemand.DemandQty | 按来源状态维护 | 销售头、状态字段 |
| 拆解理论数量 | NetDemand.GrossQty | 拆解生成 | Allocation、采购头 |
| 净需求数量 | NetDemand.NetQty | 拆解事实；普通用户不直接改 | 采购行、状态字段 |
| 计划数量 | 活动 NetDemandAllocation.PlannedQty | 计划替代命令 | NetDemand 当前状态字段 |
| 已转执行数量 | Active Link 的 `AllocatedQty-ReleasedQty` 合计 | 由创建、取消、释放命令变化 | NetDemand、Allocation 缓存 |
| 剩余可转数量 | PlannedQty - 活动 Link 有效贡献 | 查询计算 | 任何 Entity |
| 采购数量 | PurchaseOrderLine.Quantity | 采购业务命令 | PurchaseOrderHead 汇总缓存 |
| 供应商累计已备好 | 最新 SupplierProgressReport.ReadyQty | 追加报告；减少需修正原因 | 采购头行、Allocation |
| 已入库数量 | 已过账 InboundDocumentLine 和反向流水净额 | 过账/反向 | 采购头行、Link |
| 当前库存 | InventoryBalance.OnHandQty | 统一库存过账服务 | 主数据和单据 |
| 已发货数量 | 已过账最终出库明细/流水净额 | PackingList 提交/反向 | SalesOrderLine、采购行、PackingList 草稿 |
| 客供件消耗量 | 已过账客供件消耗出库明细/流水净额 | PackingList 提交/反向 | NetDemand、BOM |
| 齐套数量 | 历史比例与可用事实查询计算 | 不允许直接编辑 | 所有 Entity |

### 16.1 数量守恒

| 守恒关系 | 规则 |
|---|---|
| 拆解 | 同一 NetDemand 的活动 Allocation 计划量合计应等于 NetQty |
| 转采购 | 同一 Allocation 的活动 Link 有效贡献不得超过 PlannedQty |
| 采购行 | 由需求生成的采购行 Quantity 应等于指向该行的活动 Link 有效贡献合计 |
| 采购释放 | ReleasedQty 增加后，采购行数量与剩余 Link 贡献必须同步守恒 |
| 入库 | 来源累计已过账净入库不得超过可证明来源数量 |
| 库存 | 某仓库产品余额应等于其全部有效流水 QuantityDelta 累计 |
| PackingList | 贡献行数量、正式出库行和对应库存流水必须逐来源守恒 |

## 17. 日志、审计与追溯

### 17.1 四类记录不得混用

| 记录 | 用途 | 是否业务权威 | 写入规则 |
|---|---|---|---|
| Serilog 技术日志 | 异常、性能、HTTP 和诊断 | 否 | 可按技术策略滚动和清理 |
| BaseEntity 审计字段 | 最近创建/修改人和时间 | 部分 | 随实体写入打戳，不保存完整历史 |
| BusinessOperationLog | 面向业务人员的关键操作历史 | 是，操作事实 | 与成功业务事务同提交，只追加 |
| InventoryLedgerEntry | 库存数量变化原始事实 | 是，库存事实 | 统一过账服务写入，只追加 |

### 17.2 BusinessOperationLog 规则

| 规则 | 说明 |
|---|---|
| 事务 | 业务成功与日志同事务；业务回滚时日志也回滚 |
| 幂等 | 使用 Module + OperationType + CommandId 防重复 |
| 关联 | CorrelationId 贯穿一次请求；RelatedObjects 保存必要关联摘要 |
| 内容 | 使用字段白名单保存 ChangedFieldsJson，不保存完整 DTO、密码、Token 或连接信息 |
| 原因 | 取消、反向、强制放行、供应商进度向下修正必须填写原因 |
| 查询 | 后续建立只读查询工作台，不允许编辑或删除业务日志 |

### 17.3 必须记录的关键操作

| 模块 | 操作示例 |
|---|---|
| 销售 | 确认、取消确认、关闭 |
| 毛需求 | 手工建立、拆解、回退、关闭 |
| 净需求 | 计划替代、应用默认供应商、批量分配 |
| 采购 | 创建、确认、取消确认、取消草稿、释放数量、进度修正 |
| 库存 | 建立/停用虚拟仓、期初、负库存异常 |
| 入库 | 过账、反向 |
| PackingList | 建立、提交、负库存放行、整单反向 |
| 出库 | 由 PackingList 产生的正式出库和反向 |

## 18. 目标实体与数据库模型

### 18.1 公共技术字段

| 字段 | 类型原则 | 规则 |
|---|---|---|
| Uid | `uniqueidentifier` | 应用生成顺序 Guid；技术主键 |
| Version | `int` | 新增为 1；更新按 Uid + Version 乐观并发并递增 |
| IsDeleted | `bit` | 主数据和未过账普通单据可软删除；正式流水始终为 false |
| CreatedDate/CreatedBy | datetime2 / nvarchar | Infrastructure 统一打戳 |
| UpdatedDate/UpdatedBy | datetime2 / nvarchar | 更新时打戳；追加式事实通常不更新 |

所有业务数量统一使用 `decimal(18,4)`。金额精度由具体币种和财务需求单独冻结，不复用数量精度规则。

### 18.2 主链路实体目录

### 19.3 必须保留的历史快照

## 20. 当前源码偏差与重建前整改

当前页面和业务服务已经覆盖主要工作台，但现有 Entity 特性和 Dapper SQL 仍带有旧库兼容设计。数据库不能直接按当前代码重建。

| 当前偏差 | 风险 | 重建前目标 |
|---|---|---|
| GrossDemand/NetDemand 仍映射 IndependentDemand/DependentDemand | 新库继续继承旧概念，SQL 到处使用旧列名 | Entity、Repository、DTO 查询别名统一为 GrossDemand/NetDemand |
| SupplierProgressReport 仍映射 FollowUpLog | 通用日志和采购进度职责混乱 | 独立 SupplierProgressReport 表和仓储 |
| Warehouse、Inventory、PurchaseReceive、PackingList 使用旧表和旧列别名 | Entity 属性与 INSERT/SELECT 列不一致，按实体建表后运行即失败 | 表、列、实体和显式 SQL 同名 |
| PackingList Entity 保留 Legacy Id 和只读兼容标记 | 兼容状态会被错误带入新库 | 删除兼容字段，异常状态只在 Query DTO 表达 |
| Link 仍允许新计划关键 Uid/幂等键为空 | 新链路可能无法守恒或追溯 | 新库关键关系和 CommandItemId 收紧非空 |
| Link 保存 CompletedQty/ReceivedQty | 与跟单、入库正式事实产生双重真相 | 删除过程缓存，查询聚合 |
| Inbound/Outbound LifecycleStatus、WarehouseSite.SiteType 使用裸 byte | 枚举语义可能漂移 | 使用冻结的共享枚举类型 |
| Product 仍保存默认供应商/客户兼容代码和 SKU | 多关系重复表达且容易不一致 | 只保留 DefaultSupplierId，其他进入关系表或 Query DTO |
| SalesOrderLine 保存 LastShippedDate | 出库反向后容易失真 | 从正式出库净额查询 |
| BOM 使用 ParentSkuId/SubSkuId 等含混命名 | Uid 与业务 SKU 语义不清 | 改为 ParentProductId/ComponentProductId，字符串仅作快照 |
| CustomerSuppliedReceipt 当前可直接从客供件 Allocation 选源 | 尚未转采购或采购未确认的客供件也可能被当作可收货来源 | 统一从活动 Link + 已确认采购行建立客供件可收货池；Allocation 只解析 B 计划和 A 送达仓 |
| 003–015 迁移以旧库增量兼容为目标 | 不适合实体同名全量重建 | 仅作历史参考，另建开发库全量重建脚本 |

实体清理必须沿以下影响链同步完成：

```text
Core Entity
  -> Repository Interface
  -> Infrastructure Dapper SQL 与列别名
  -> Application 校验和事务
  -> Contracts DTO / 枚举 / Refit
  -> Controller
  -> WPF Model / ViewModel / Binding
  -> 全量建表脚本、约束和示例数据
```
