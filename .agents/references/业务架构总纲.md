# SwiftExport ERP 业务架构总纲

> **2026-09-16 采购确认职责修正：** 采购确认只校验采购事实并锁定订单、允许入库；不读取完整 BOM、不创建新 BOM 确认节点、不绑定消耗仓，也不要求首次确认存在历史快照。旧快照数据暂保留，专用追溯查询链已移除。草稿建立的未释放 Link 阻断需求回退；取消确认不释放，删行或作废才释放。客供件消耗归 PackingList 正式出货过账，实际仓和数量届时确定；跨供应商用料先调拨，禁止任意仓扣减。该自动消耗、选仓与调拨接线尚未实现。本轮不新增分解快照表。


## 2026-09-16 来源—物料—采购链路与数据库基线

当前正向主链固定为 `销售/售后确认 → GrossDemand → BOM 拆解 → NetDemand → 采购草稿及 DemandExecutionLink(TargetType=PO) → 采购确认 → 采购入库 → PackingList/正式客户出库`。`NetDemand` 多对一归属 `GrossDemand`；采购行与 NetDemand 的多对多数量贡献只由 Link 表达。`NetDemandAllocation` 与计划命令日志已经物理退出，禁止以任何新名称恢复。

需求驱动采购采用“草稿即预留”：创建采购草稿时同事务建立活动 Link，采购确认不重复建链；取消确认只回到草稿并保留 Link；草稿删行或整单作废才释放对应贡献。Link 的有效贡献固定为 `AllocatedQty - ReleasedQty`，任一 Link 仍有正数剩余时阻断物料回退；全部释放后整组物料修订可转 RolledBack，并保留修订、人员、时间和原因。

当前完整纠错反向链固定为 `正式客户出库反过账 → 采购入库反过账 → 采购取消确认回草稿 → 草稿删行或整单作废释放 Link → NetDemand 安全回退 → 销售/售后取消确认并退出 GrossDemand`。每一步由所属领域显式执行，不自动级联。无物料历史的来源需求在取消确认时物理删除；存在完整安全回退历史的来源需求转 Voided。来源退出以物料状态作为采购/入库的传递证明，并另由 Shipping 核验有效 PackingList 与正式客户出库已经安全退出；普通手工仓库出库不计来源履约。

来源需求经理页继续作为受权限控制的管理入口，保留来源查询、手工来源维护和物料导航；销售与售后用户从各自单据取消确认并复用来源退出能力。上述完整反向链属于纠错取消确认；已有执行但不全部反向的客户减量、终止或继续备货仍走独立业务变更，不得降低安全回退条件。

本节是冻结目标，不得写成全部已经实现。当前来源退出仍存在直接扫描 NetDemand、Link 和入库事实的旧实现，Shipping 来源交付核验契约尚未接入；该差距统一登记为需求计划地图 DP-009。在代码完成前继续失败关闭，不能因文档更新放宽取消确认。

数据库结构以 Core 中显式 `[Table]` 的 Entity 及其 `DatabaseSchema` 元数据为唯一事实源。索引、CHECK、逻辑关系、序列和不可变规则均声明在 Entity；逻辑关系不生成数据库外键。仓库只保留 `SwiftExport.Infrastructure/Database/Generated/SwiftExport.Schema.sql`，仅支持已创建的全新空库，不提供旧库升级、回填或迁移。生成与验证流程见数据库目录 README。

## 2026-09-08 来源需求主体与职责收窄

来源需求（现 GrossDemand）作为需求主体，统一接收销售与品控/售后领域确认的实物要求；确认与幂等接收保持事务一致。物料需求（现 NetDemand）是来源需求拆解后的下一级，来源需求的接收和本体查询不依赖物料需求存在，也不承担物料明细维护、单据执行进度或需求完成率查询。拆解/回退由物料领域交接用例承担，来源页可以提供导航。

PL 仍以来源需求为交付要求入口。正式交付聚合、剩余交付额度计算归交付职责，售后结案由售后用例判断；来源需求提供有效要求、生命周期及版本校验。此职责收窄不撤销防超发、终止并发保护或历史安全检查，现有交付兼容接口须在消费者安全切换后收窄。采购可选来源和客供件实际消耗预览规则继续有效。本文旧段落中将交付进度/完成判定交给来源需求的内容按本节解释；当前代码尚未完成该职责迁移。

源码现状与最小收窄步骤见[来源需求职责与依赖核对](领域治理/来源需求职责与依赖核对-2026-09-08.md)。

## 2026-09-08 售后事实与来源交接

本节明确售后特殊边界，优先于旧文档把全部来源都引入采购的泛化描述。售后以 AfterSalesHeader/AfterSalesLine 两表保存同一客户的投诉事实和认可实物要求；同行区分问题成品与实际补件，人民币行金额属于售后责任成本，不创建采购订单。

保存不接入需求；显式确认只把 Quantity>0 的行按 CR、头 Uid、售后单号、行 Uid 交给 GrossDemand，NULL/0 行只作投诉追溯。确认后锁定相关事实，取消确认由来源需求安全撤回后解锁。售后结案只核验正式交付完成或下游合法关闭，不提供终止剩余要求入口。

后端第一批已实施：事实保存、查询、确认/撤回、生命周期、权限与审计。部分补发由 PackingList 承担；附件、WPF 页面及无采购特殊自动入出库尚未在本批实施，不能把来源接收成功解释为已具备库存供货依据。详见[售后模块能力地图](模块能力地图/售后模块能力地图.md)。

## 2026-09-07 采购来源可选与独立供货修正

本节为最新确认口径，优先于本文旧目标、验收和执行提示词中的冲突描述：

- 撤销“采购必须归属唯一销售订单”“独立采购必须选择销售单”及其强制字段、回填、阻断要求。采购可选关联来源需求（GrossDemand），不能将来源需求身份直接等同 SalesOrderId；未关联上游是合法业务，不是历史异常。
- 独立采购只维护采购事实，可无来源需求、物料需求和 Link 创建、确认及执行正常入出库。收货按采购行及实际收货仓核算容量，不依赖 Link 数量或上游订单存在。
- PL 的交付要求与供货依据分开：仍从来源需求取得客户交付要求和剩余额度，但允许明确选择未关联该需求的独立采购供货。PL 保存本次交付与采购/库存执行的数量关系，不反向强迫采购补绑上游。本次没有把采购数量自动变成客户交付额度，也没有新增无来源需求的 PL 模式。
- 客供件在 PackingList 正式出货时按父子供料关系及本次数量扣减，实际消耗仓在执行时确定，跨供应商用料先调拨；计算与选仓尚待实现，不以缺少采购确认节点作为阻断条件。
- 来源关联是可选追溯/数量承接关系，不是库存所有权。不得直接把 DemandSourceUid 改解释为 GrossDemandId；先核对现有类型、头行粒度和 Link，优先复用最小关系。旧“同销售单合并”限制不再作为所有采购的全局规则；是否扩大既有需求合并功能须另行确定，本次不自动增加跨来源合并功能。
- 当前代码与数据库未因本次文档修正自动完成迁移；实施按阶段 02、03、04、05、06 分别接线验收。

## 2. 系统定位与业务原则

SwiftExport 是面向小团队内部使用的外贸 ERP。系统围绕产品与 BOM、销售订单、需求拆解、采购、供应商跟单、供应商虚拟仓、入库、库存、PackingList、出库和全链路追溯建立闭环。

| 原则 | 业务含义 |
|---|---|
| 可追溯优先 | 任一入库、库存变化均可追到合法执行凭证；有需求关联时继续追到需求，无需求采购不伪造关联；客户出货仍保留正式贡献归属 |
| 事实与执行分离 | NetDemand 保存拆解事实和当前推荐供应商，DemandExecutionLink 保存对执行行的数量贡献，正式单据保存采购、入库和出库事实 |
| 状态分层 | 生命周期、确认、过账和查询进度不能塞入一个万能状态 |
| UID 为权威关系 | 跨模块关系使用稳定 Uid；业务编码用于查账和历史快照 |
| 正式事实不可抹除 | 已确认、已过账或已形成流水后，不靠删除解决错误 |
| 反向而非篡改 | 错误库存通过反向流水；错误计划通过替代记录；历史反馈通过修正报告 |
| 轻审批、强提示 | 小团队不建立过重审批，但危险操作必须权限、原因、预览和日志齐全 |
| 派生量不重复存储 | 已备好、已入库、已发货、剩余量、齐套量从各自事实查询计算 |

## 3. 端到端业务主线

```text
主数据
  -> 销售订单 / 手工需求 / 投诉补货
  -> 毛需求 GrossDemand
  -> BOM 拆解事实 NetDemand
  -> 物料推荐采购供应商（NetDemand）
  -> 采购草稿 + 执行贡献 DemandExecutionLink(TargetType=PO)
  -> 采购确认与供应商跟单
  -> 入库单过账
  -> 供应商虚拟仓库存与流水
  -> PackingList 装柜与提交
  -> 正式出库及客供件消耗
  -> 来源、单据、库存和操作日志追溯
```

### 3.1 模块职责

| 阶段 | 主要输入 | 权威实体 | 主要输出 | 是否改变库存 | 主要操作人 |
|---|---|---|---|---|---|
| 主数据 | 产品、客户、供应商资料 | Product、Customer、Supplier、关系表、Bom | 可被单据引用的活动主数据 | 否 | 产品、销售、采购资料维护人员 |
| 销售订单 | 客户 PO 和销售明细 | SalesOrderHeader、SalesOrderLine | 已确认销售需求来源 | 否 | 销售人员 |
| 毛需求 | 销售行、手工需求、投诉补货 | GrossDemand | 可拆解的原始业务需求 | 否 | 计划人员、销售人员 |
| 净需求 | 毛需求与 BOM 快照 | NetDemand | 一次拆解修订中的物料需求事实 | 否 | 系统拆解、计划人员审核 |
| 物料建议 | 物料需求、供货方式、默认供应商 | NetDemand.SuggestedPurchaseSupplierId | 当前推荐采购供应商，不代表实际采购决定 | 否 | 计划人员 |
| 执行追溯 | NetDemand 与执行命令 | DemandExecutionLink | 从需求贡献到执行明细的数量关系 | 否 | 系统 |
| 采购与跟单 | 可采购物料需求，或手工/外部独立采购 | PurchaseOrderHead、PurchaseOrderLine、SupplierProgressReport | 采购单和供应商累计进度 | 否 | 采购、跟单人员 |
| 入库 | 采购到货、客供件收货、PackingList 补入库 | InboundDocument、InboundDocumentLine | 已过账入库事实 | 是，增加 | 跟单、仓库或 PackingList 编排服务 |
| 虚拟仓与库存 | 已过账入出库 | WarehouseSite、InventoryBalance、InventoryLedgerEntry | 当前余额和不可变流水 | 是 | 系统过账服务 |
| PackingList | 合法客户实物交付来源、库存、装柜资料 | PackingListHead、PackingListLine | 最终客户出货编排 | 草稿否，过账是 | 出货、跟单人员 |
| 出库 | PackingList 贡献行 | OutboundDocument、OutboundDocumentLine | 客户发货和客供件消耗事实 | 是，减少 | PackingList 编排服务 |
| 日志与追溯 | 成功业务命令 | BusinessOperationLog、各单据和流水 | 人工可读操作历史与技术诊断 | 否 | 系统 |

### 3.2 当前工作台入口

| 工作台 | API 根路由 | 当前业务定位 |
|---|---|---|
| 销售订单 | `/api/sales-orders/workspace` | 销售订单保存、确认、取消确认、关闭和删除草稿 |
| 来源需求 | `/api/demand-planning/gross-demands` | 来源查询及手工来源需求的创建、修改和关闭；物料建立与回退由物料需求入口承接 |
| 物料需求 | `/api/demand-planning/net-demands` | 物料事实查询、来源建立、安全回退及推荐采购供应商维护；不承担采购取消、释放或追溯写操作 |
| 采购 | `/api/procurement/purchase-orders`、`/api/procurement/purchase-drafts` | 独立采购及需求选取、预览、创建、草稿维护、确认、反向操作和供应商进度 |

| 入库 | `/api/inventory/inbounds` | 来源选择、草稿、过账、反向和追溯 |
| 出库 | `/api/inventory/outbounds` | 查询正式出库和追溯；不提供普通人工出库写入口 |
| PackingList | `/api/shipping/packing-lists` | 草稿、预览、提交、反向、追溯和导出 |
| 业务操作日志 | 暂无独立工作台 | 当前由关键业务服务写入，后续补统一只读查询入口 |

## 4. 核心概念

| 概念 | 定义 | 不承担的职责 |
|---|---|---|
| Product | 公司内部稳定产品主数据；保存产品身份、物料角色、供货方式和当前默认供应商 Uid | 不保存客户专属 SKU、供应商 SKU、历史单据数量或当前库存 |
| CustomerProduct | 客户与 Product 的业务关系；保存客户 SKU、客户描述、客户价格和客户专属约定 | 不替代 Product，不保存销售订单历史事实 |
| SupplierProduct | Supplier 与 Product 的采购关系；保存供应商 SKU、采购价格和供应商描述 | 不替代 Product.DefaultSupplierId，不直接改变既有 NetDemand 建议或采购单 |
| Bom | 某父产品的单套当前组成行和用量比例；保存即生效 | 不保存执行供应商、当前库存或采购状态 |
| GrossDemand | 来源业务提出的原始需求 | 不保存 BOM 展开明细、采购进度或发货进度 |
| NetDemand | 某次毛需求拆解修订产生的物料需求事实 | 不保存当前执行供应商，不普通覆盖历史 |
| DemandExecutionLink | NetDemand 对某采购明细贡献数量的权威关系；当前仅冻结 `TargetType=PO` | 不替代采购行、入库单、出库单或库存流水，不扩展为通用执行单协议 |
| SupplierProgressReport | 供应商对采购行的累计进度反馈历史 | 已备好不等于已入库或库存 |
| InventoryLedgerEntry | 每一次库存增加、减少或反向的不可变事实 | 不允许人工覆盖或删除 |
| InventoryBalance | 按仓库和产品汇总的当前库存投影 | 不是原始事实，可由流水重建 |
| PackingListLine | 本次最终出货对 GrossDemand 的精确贡献及来源快照 | 不按 SourceType 建白名单，不仅靠 SKU 聚合丢失来源 |

## 5. 主数据模型

### 5.1 主数据实体职责

| 目标实体/表 | 中文职责 | 权威关系/业务键 | 应保存的事实或快照 | 不应保存 |
|---|---|---|---|---|
| Customer | 客户主数据 | `CustomerCode` 活动唯一 | 名称、联系人、地址、默认贸易条款、默认币种和交付方式 | 销售订单历史金额和发货进度 |
| Supplier | 供应商主数据 | `SupplierCode` 活动唯一 | 名称、联系人、人民币采购条件、默认交期 | 采购单历史供应商名称和库存余额 |
| Product | 产品主数据 | `Sku` 活动唯一；`DefaultSupplierId` 逻辑关系 | 描述、颜色、物料类型、供货方式、当前 BOM 状态 | 默认供应商代码、供应商 SKU、客户 SKU、过程数量 |
| ProductCategory | 产品分类 | 分类编码或同级名称业务唯一 | 父分类、排序和显示名称 | 产品交易事实 |
| ProductColor | 颜色主数据 | 唯一颜色编码 | 中英文名称 | 产品或订单数量 |
| ProductMaster | 主型号资料 | `MasterSku` 唯一 | 主型号层级默认描述和分类 | 具体 SKU 的交易事实 |
| ProductDetail | 产品文件资料 | `ProductId` 或稳定产品关系 | 图纸、说明书、条码、规格文件路径 | 仅靠可变 SKU 作为唯一关系 |
| ProductPackage | 产品包装规格 | `ProductId + PackageType`；一个默认规格 | 装率、尺寸、净重、毛重、体积和包材 | 销售行或 PackingList 的历史包装快照 |
| CustomerProduct | 客户产品关系 | `(CustomerId, CustomerSku)` 活动唯一 | Product Uid、客户 SKU、客户描述、客户价格、MOQ | Supplier 信息和库存 |
| SupplierProduct | 供应商产品关系 | `(SupplierId, ProductId)` 活动唯一 | 供应商 SKU、未税价、含税价和供应商描述 | Product 当前默认供应商之外的全局默认状态 |
| CustomerPoConfig | 客户采购单默认配置 | 客户 Uid/代码对应的有效配置 | 包装、标贴、说明书、人员等默认要求 | 已生成采购单的历史快照 |
| Bom | 单套当前 BOM 组成行 | 父产品 Uid、当前行号；既有 BomVersion 仅兼容，不在本轮改约束 | `ComponentProductId`、分子、分母和备注 | 供应商、执行方式、库存和进度 |

### 5.2 默认供应商规则

| 规则 | 说明 |
|---|---|
| 权威字段 | `Product.DefaultSupplierId` |
| 设置入口 | 产品管理批量保存可从全部活动供应商中选择；SupplierProduct 关系页也可执行“设为产品默认供应商”命令 |
| 必要校验 | Product 与 Supplier 均活动，并校验 Product.Version；产品管理入口不要求预先存在 SupplierProduct 关系 |
| 兼容字段 | 当前库在保存 `DefaultSupplierId` 时同步权威 `DefaultSupplierCode` 供旧链路兼容；`DefaultSupplierSku` 仍属于 SupplierProduct，目标重建后只保留 Uid 权威关系 |
| 历史影响 | 修改 Product 默认供应商不自动修改既有 NetDemand 推荐供应商、采购单或历史快照 |
| 无默认供应商 | 来源拆解放行，NetDemand 推荐采购供应商为空；采购可选择需求并确定实际供应商 |
| 失效默认供应商 | 不得作为合法建议或实际供应商使用；提示修复，采购另选合法供应商无需先修改计划或默认值 |

### 5.3 BOM 与物料角色

| 规则 | 说明 |
|---|---|
| 当前方案 | 每产品只有一套当前 BOM，保存即生效并记录修改；不提供多版本选择、发布或切换 |
| 兼容字段 | 当前源码以 Product.BomVersion=0/大于0 区分无 BOM/对应组成；本轮不删字段、不重排值、不赋予多版本管理语义 |
| 用量 | `父需求数量 × Numerator ÷ Denominator`，分子、分母必须大于 0 |
| SupplyType | 只表达采购、生产、外协，不表达是否有 BOM |
| 客供件 | 是 Product 的物料角色；应为采购型终端物料，不继续展开 BOM |
| 历史解释 | 拆解时保存实际采用的完整结构、路径、用量、单位、物料角色及读取依据；需求拆解 revision 不等于 BOM 业务版本 |
| 修改影响 | 保存后影响后续当前结构读取；多层树须一致读取，既有需求/采购/消耗按历史执行快照解释 |
- 独立采购与需求来源采购均按采购事实确认，不读取 BOM；主数据读取能力保留供需求拆解使用，客供件消耗归 PackingList 出货。
| 保存门禁 | 校验最终完整图、自引用、循环、重复直接组件、正比例及父标识一致；修改记录与保存原子完成，失败不留半套结构 |

### 5.4 主数据身份与生命周期

Uid 是关系权威，SKU、客户/供应商编码可通过专用更名命令纠正：验证权限、原因、版本、唯一性及引用，记录旧新值，Uid 和历史单据快照不变。仍依赖编码的接口、导入、资料和外部映射须明确兼容，不自动模糊关联或假定旧编码永久别名。

停用只阻止新引用、新行和增量承诺；已有已确认合法单据可按历史身份、单位快照和自身状态/数量规则继续履行，不因主数据停用自动取消采购或阻断收货/出货。“有效性校验”必须区分新承接与既有承诺，不能只检查 IsActive/IsDeleted。对象缺失、身份冲突、单据关闭/取消、单位不兼容仍是阻断；停用不等于删除或执行冻结，历史查询/关联保留。恢复不自动恢复旧单据或承诺。

有正式库存流水的产品冻结基础单位，即使余额为零也不能普通改单位；换单位新建产品身份。无正式流水的纠正仍需检查 BOM、订单和执行引用。当前单位字典校验不代表已实现此门禁。供应商停用不自动停其仓库；仓库自身停用、负库存和反向规则仍按库存章节，不在本次放宽。

### 5.5 包装、资料与执行快照

产品维护通用包装，客户产品维护客户专属覆盖；明确客户覆盖优先，未覆盖沿用产品默认，非法值不能靠回退隐藏。单据采用后保存独立快照，模板变化不刷新既有销售/采购/PL。CustomerPoConfig 的文字要求与定量包装分开，不自动改 BOM 或产生消耗。主型号只提供新建产品默认资料，不是库存身份；分类、颜色负责组织显示；产品资料按稳定 ProductId 关联，记录删除不自动删除实际文件。

BOM 维护影响后续需求分解，不影响既有采购确认。采购不新增结构快照，已有历史依据保留；PackingList 消耗计算与实际选仓接线后续实现，不用最新 BOM 补造历史。

页面、契约、证据与偏差见 [主数据地图](模块能力地图/主数据模块能力地图.md)、[BOM 地图](模块能力地图/BOM模块能力地图.md)。这些是目标，旧编码关系、单位冻结、停用准入及独立采购快照缺口必须按账本治理。

## 7. 销售订单

### 7.1 流程

| 动作 | 允许条件 | 事务结果 | 阻断条件 | 反向或后续动作 |
|---|---|---|---|---|
| 保存草稿 | Open + 待确认；版本匹配 | 保存头和完整活动行集合，稳定行号 | 客户、产品关系无效；数量或价格非法；版本冲突 | 可继续修改或删除草稿 |
| 确认 | Open + 待确认 | 订单变已确认；每条活动销售行幂等建立一条 GrossDemand | 行为空、来源重复、产品关系损坏 | 未拆解时可取消确认 |
| 取消确认 | Open + 已确认；填写原因 | 恢复待确认；从未拆解且无任何净需求历史的毛需求物理删除；曾拆解并已完整安全回退的毛需求保留为 Voided | 活动拆解、执行 Link、入出库、装箱、库存事实，或 revision/历史不完整 | 先完成下游取消或正式反向，再安全回退拆解 |
| 关闭 | Open；关闭权限、版本、原因和遗留事项/责任明确 | DocumentStatus=Closed，停止新交付，记录审计；遗留执行继续跟踪 | 已关闭、版本冲突或缺必要记录；已有采购待处置本身不阻断 | 不级联关闭需求/采购，不自动撤销历史执行事实 |
| 删除草稿 | Open + 待确认且无下游 | 软删除订单头行 | 已确认、已关闭或已有毛需求 | 无 |

### 7.2 销售订单事实

| 类别 | 保存位置 | 规则 |
|---|---|---|
| 当前客户关系 | Header.CustomerId | 新建时必须指向活动客户 |
| 客户和贸易条款快照 | Header | 确认后不因客户主数据变化而自动刷新 |
| 产品关系 | Line.ProductId 与受控关联历史 | 标准行必填；非标接单时可空，正式库存动作前显式关联有效产品，原非标快照保留 |
| 客户产品关系 | Line.CustomerProductId | 标准行可保存，用于带出客户 SKU 和价格 |
| 产品、客户 SKU、描述、颜色、规格快照 | Line | 保存订单成立时事实 |
| 数量、价格、金额 | Line；必要汇总在 Header | 金额是订单商业快照，不是履约进度 |
| 客户已发货量和最后发货日 | 查询正式 OutboundDocumentLine | 不进入 SalesOrderLine 目标实体 |

### 7.3 商业变更、终止和恢复

销售拥有商业承诺，需求拥有计划处置，采购拥有实际执行。已确认订单采用同号受控变更，保留原/新要求、原因、业务修订及行身份；业务修订与并发 Version 分离。价格、说明等不影响实物需求的修改，不无条件重建需求。数量、产品、交期变化经需求领域契约记录差异，销售不直接维护需求内部表。

- 已确认客户不原位替换，换客户另建关联订单；换品终止旧行剩余交付并新增关联替代行，不改写已有执行身份。
- 支持行级终止剩余交付，其他行继续。已生效减量/终止立即限制相应新交付和新需求承接；增加量须销售确认，临时编辑或变更草稿不产生额度。
- 生效与交付限制一致更新，经领域契约登记需求变更；需求/采购处置可以未完成，已有合法采购与收货继续，不因销售变更自动反向库存。
- 当前订购、正式交付净额、终止剩余量、当前允许新交付量、待处置差额分开表达。减量/终止不得重复扣同一承诺，不能将数量减到低于真实交付后靠截断掩盖冲突；冲突进入明确纠错/售后处理。
- 发完只是查询进度，不自动关闭；关闭可以先于采购处置完成，但必须保留遗留事项与责任、显示执行处置未完成。关闭不把未交付量算成已发完。
- 恢复订单/行交付走独立权限、原因和影响预览，校验当前来源/版本并重算额度、协调需求差额；不重置已交付量、不自动复活旧采购承诺。重开订单不自动恢复此前独立终止的行。
- 取消确认仍按 8.4 的历史安全双路径，是纠错回退而非客户业务取消；不能为了新关闭能力降低其阻断条件。

### 7.4 客户交付、非标与商业资料

销售只定义销售事实，认可实物要求及版本幂等进入来源需求；品质售后按同一协议汇聚。来源需求向 PL 提供统一来源身份、客户、产品单位、有效要求和版本，提交时复核可发量；来源需求必需，物料需求和 Link 不必需。上游变更经来源需求同步并与发货协调并发，旧预览不得超交付。客供件消耗、草稿、货好或收货覆盖均不是客户发货。

非标可先接单、确认和计划，在正式库存动作前通过受控关联建立有效产品身份，保留原非标快照与历史；明确协调已有下游，不通过普通保存替换产品，不猜测历史 SKU。销售不另建非标库存体系。

InvoiceNo 为自定义形式发票号，与 PackingList 的销售来源 InvoiceNo 同义；客户采购单号另列，来源 Uid 不以这些编号替代。商业/产品快照不跟随主数据变化自动刷新；销售客户交期及运输要求与 PL 实际装运字段各自归属。销售修改不能静默覆盖已出货 PL 的历史编号；PL 纠错走自身修订流程。真实退回不自动重开来源需求交付额度，补发走新售后来源，不能重复开放原销售承诺。

本期销售仅承诺 CNY/USD，非 CNY 不得一律按 USD 算金额；保留已有历史商业金额，不在此擅自合并双价格含义、建立通用汇率折算或扩展财务结算。

### 7.5 页面、契约与现状

销售订单管理负责查询导航；详情是编辑和生命周期命令权威入口；独立只读履约跟踪按客户/订单行汇总交期、需求处置、采购/货好、正式交付和遗留事项；变更预览/历史为详情组件。销售页只导航采购、计划出货和库存动作，不复制执行工作台。

目标契约、字段来源、源码偏差与后续切片见 [销售模块能力地图](模块能力地图/销售模块能力地图.md)。当前关闭仍受下游执行阻断，发货查询仍依赖需求链，修订/行终止/恢复/非标关联尚未建立；不得把本节目标当作已实现能力。

| 来源类型 | SourceUid | SourceLineId | 生成规则 |
|---|---|---|---|
| 销售订单 SO | SalesOrderHeader.Uid | SalesOrderLine.Uid | 销售确认时一行生成一条活动毛需求 |
| 手工需求 MD | 自身 Uid | 自身 Uid | 建立时生成稳定手工需求号 |
| 投诉补货 CR | 投诉或补货单 Uid | 来源明细 Uid | 进入同一毛需求和净需求链路，不形成孤岛 |
| 未来售后服务实物需求 | 服务单 Uid | 配件/补货实物行 Uid | 服务领域认可后幂等接收；受理、工时、服务过程和结案不进入物料计划；不预分配来源枚举值 |

### 8.2 流程

| 动作 | 允许条件 | 事务结果 | 阻断条件 | 反向流程 |
|---|---|---|---|---|
| 建立手工需求 | 标准产品有效，或明确非标 | GrossDemand=Active + Pending | 数量不大于 0；标准产品无效 | 未拆解时可修改、关闭 |
| 修改手工需求 | 手工来源、Active、Pending、版本匹配 | 更新原始需求事实和快照 | 已拆解、已关闭、版本冲突 | 先安全回退拆解 |
| 拆解 | Active + Pending | 同事务写一组 NetDemand，revision+1，状态 Decomposed | BOM 损坏、循环、数量不守恒或已有不完整活动拆解 | 全部 Link 剩余贡献为零时可回退 |
| 回退拆解 | Active + Decomposed，且相关 Link 的有效贡献均为零 | 整组 NetDemand 转 RolledBack，保留修订、原因、人员和时间；GrossDemand 保持来源事实 | 任一 Link 的 `AllocatedQty-ReleasedQty > 0`、数量或 revision 状态损坏 | 先在采购侧删行或作废并释放 Link；存在正式下游时先做正式反向 |
| 关闭手工需求 | 手工来源、Active、无活动拆解 | Lifecycle=Closed，记录原因 | 已有活动净需求或执行关系 | 回退后关闭 |

### 8.3 毛需求实体边界

| 保存 | 不保存 |
|---|---|
| 来源类型、来源头行 Uid、单号行号快照 | 采购单号快捷字段 |
| ProductId 或非标标识 | 已转采购、已入库、已发货数量 |
| SKU、客户型号、描述、颜色、规格、图片快照 | 当前供应商或执行方式 |
| DemandQty、RequiredDate、备注 | 齐套率和履约状态缓存 |
| 生命周期、拆解状态、拆解 revision 和审计 | 旧 ApprovalStatus、OrderStatus 万能状态 |

### 8.4 销售订单取消确认时的毛需求双路径

取消确认是销售订单的纠错聚合命令，不是已有执行后的客户业务取消，也不是毛需求列表中的普通删除。销售通过需求领域的安全退出契约协调，需求内部历史校验与写入由需求领域负责。现有订单、需求与日志的原子性及下述历史安全条件保留；后续在单体事务内封装领域契约，不让来源服务直接维护需求内部表。

| 毛需求事实 | 取消确认结果 | 原因 |
|---|---|---|
| `DecompositionRevision=0`、Active + Pending，且从未产生任何 NetDemand 历史 | 物理删除 GrossDemand | 该记录只是本次销售确认派生出的可重建中间事实，没有独立历史价值 |
| 存在 NetDemand 历史，全部修订历史完整且已为 RolledBack/Voided，并且 Shipping 已证明无有效 PackingList/正式客户出库贡献 | GrossDemand 保留，改为 `LifecycleStatus=Voided`、`IsDeleted=0` | 毛需求是已发生拆解历史的 Trace 根，删除会形成孤儿或掩盖历史 |
| 物料历史缺失或不完整、存在活动物料修订，或 Shipping 无法证明正式交付已退出 | 整张销售订单取消确认失败 | 来源层不重复解释 Link、采购或入库表；无法证明安全时不得猜测清理，也不得部分成功 |

同一销售订单可以同时包含物理删除行和 Voided 保留行，两类处理必须全成全败。取消确认原因 Trim 后必填，最长 1000 字符；每次实际提交生成 `CommandId`，以 `SalesOrder + CancelConfirmation + CommandId` 写入 `BusinessOperationLog`。同一命令、订单和原因的重试返回首次结果；CommandId 换订单或换原因重用必须拒绝。

重新确认时，被物理删除的来源行生成新的 GrossDemand Uid；旧的 Voided GrossDemand 及其 Trace 保持不变，同一来源行再生成新的活动 GrossDemand Uid。活动来源唯一约束只约束 Active 且未删除记录。

### 8.5 外部销售订单导入与需求池判定

外部销售订单必须先落为内部 `SalesOrderHeader/Line`，并为外部系统、外部订单和外部行建立稳定的内部 Uid 映射。不得只凭销售单号、SKU 或可变行号判断是否已经进入需求池。

| 判断目标 | 权威查询 | 规则 |
|---|---|---|
| 销售行是否已有毛需求 | `GrossDemand(SourceType=SO, SourceUid=SalesOrderHeader.Uid, SourceLineId=SalesOrderLine.Uid)` | 活动来源关系必须幂等唯一 |
| 是否已经拆解 | `GrossDemand.DecompositionStatus` 与当前 `DecompositionRevision` | 状态与活动 NetDemand 不一致时视为数据损坏 |
| 当前拆解有哪些物料 | 当前 revision 的活动 `NetDemand` | 不通过 SKU 从全局净需求中猜测 |
| 当前推荐如何采购 | `NetDemand.SuggestedPurchaseSupplierId` | 只表达物料建议；实际供应商与收货目标以采购单为准 |
| 已转下游多少 | 活动 `DemandExecutionLink` 有效贡献合计 | 有效贡献为 `AllocatedQty-ReleasedQty` |

`GrossDemand.SourceNo`、SKU 和来源行号都是历史查账快照或辅助筛选，不替代来源头行 Uid。

### 8.6 来源生命周期与需求生命周期解耦

- 销售拥有商业确认、业务变更和关闭；未来服务拥有受理、实物需求认可和结案。需求计划只拥有来源实物需求的接收、拆解、计划、变更处置、终止与履约跟踪。
- 来源确认/认可实物行后自动幂等接收毛需求，不自动拆解或转采购。接收契约包含稳定来源类型/头行 Uid、来源版本、实物内容与命令标识，来源领域不提交需求内部四张表。
- 重复同意图接收返回既有结果，旧来源版本不得覆盖新要求；同标识不同内容冲突。重新确认仍遵循 8.4 的活动来源与历史双路径。
- 纠错取消确认遵循 8.4；已有承诺后的减少/取消走业务变更，不要求为撤销需求反向真实收货。
- 变更阶段为提出、影响评估、明确处置、完成；记录原/新要求、原因、来源版本、受影响数量、执行单据及处置结果。这是目标用例，当前枚举和协议尚需后续实现，不新增万能 OrderStatus。
- 待处置期间暂停受影响需求行的新转采购；不自动停止既有采购、跟单或合法收货。来源商业变更与需求处置进度分别展示，未完成不能冒充已同步。
- 采购在自己的领域明确减量、取消或继续备货；需求仅协调处置与引用结果。需求数量减少不直接改采购数量、ReleasedQty 或删除 Link；继续备货保留承诺及原需求历史，不伪装为满足已取消需求。
- 未承接部分可以调整计划；已接受部分保留执行承诺，当前需求、当前建议、历史承诺和变更差额分别表达，不通过重算或删除历史凑平。
- 履约完成依据来源认可的正式事实查询；销售使用正式客户出货，服务实物履约由服务领域认可。采购完成、入库、需求覆盖都不等于来源履约完成。
- 计划员显式关闭需求；未完成关闭须原因及遗留承诺处置记录，未决事项不能静默遗忘。关闭停止新承接，不级联关闭销售/服务、采购或入库。

## 9. 物料需求（原净需求 NetDemand）与采购承接

Allocation 已退出。当前物料需求由 NetDemand 保存拆解事实、推荐采购供应商和修订生命周期；采购承接只由 `DemandExecutionLink(TargetType=PO)` 表达。本轮不为生产、外协或未来执行类型设计通用中间模型。

### 9.1 拆解事实与采购执行分离

| 内容 | 权威事实 | 规则 |
|---|---|---|
| 物料组成、数量、交期 | NetDemand | 由 GrossDemand 与 BOM 拆解生成，按 revision 保留历史，不普通覆盖 |
| 推荐采购供应商 | NetDemand.SuggestedPurchaseSupplierId | 仅是当前建议；采购可在准入规则内选择实际供应商 |
| 实际采购头行与供应商 | PurchaseOrderHead/Line | 由采购领域拥有，不回写为物料事实 |
| 物料对采购行的数量贡献 | DemandExecutionLink | 有效贡献固定为 `AllocatedQty-ReleasedQty`；多个 NetDemand 可指向同一采购行 |
| 收货、出库与库存 | 正式单据及库存流水 | 不缓存到 NetDemand 或 Link |

### 9.2 初始物料需求

| 场景 | 推荐采购供应商 | 结果 |
|---|---|---|
| 标准采购产品有默认供应商 | Product.DefaultSupplierId | 生成 NetDemand 并初始化推荐供应商，可转采购 |
| 标准采购产品无默认供应商 | 空 | 拆解放行，提示建议未指定；采购建立草稿时选择实际供应商 |
| 非标需求 | 空 | 生成待补齐采购资料的 NetDemand，不伪造供应商 |
| 生产或外协产品 | 按当前物料规则保存 | 不在本轮建立执行协议；出现明确业务场景后单独设计 |

### 9.3 客供件 A/B 物料与执行

| 概念 | A：父产品 | B：客供件 |
|---|---|---|
| 计划供应商 | 自身执行供应商建议 | B 自身采购供应商建议，二者可不同 |
| 计划送达关系 | 无 | 客供件送达供应商由采购确定，实际仓库由库存动作确定，库存按仓库产品管理 |
| 实际供应商与收货仓 | 由采购/执行单据确定 | 由 B 采购确定的送达目标负责，不从父物料需求推断当前仓库 |
| 未承接计划变化 | 允许调整 NetDemand 建议 | 同步评估未承接 B 的送达建议 |
| 已有执行承诺 | 保留历史，变化走影响评估 | 不静默改写 B 已接受的采购供应商或目标 |

建议未指定不阻断采购选择需求；采购建立订单时补齐实际供应商及必要目标，未满足采购准入不得生成无效订单。实际选择与建议不同不要求先改 NetDemand 建议。需求计划不代替采购最终校验。

### 9.4 建议调整与已承接边界

1. 读取并发版本、当前 NetDemand、执行关联及待处置变更。
2. 未承接部分允许修改建议；受影响已承接部分进入 8.6 的变更评估，不再因任一 Link 存在就一律阻断所有建议调整。
3. 拆解修订保留历史；已接受采购关联不得因建议变化被移动、删除或重置为可再承接。
4. A 建议变化只调整允许变化的 B 建议；不自动改变已下单的送达目标。
5. 记录原因、原/新版本与差额；界面分别展示当前要求、当前建议及历史实际承诺。
6. 需求关闭/业务取消不令已接受采购失去合法收货资格；采购改变由采购明确命令决定。

### 9.5 转采购交接规则

| 规则 | 说明 |
|---|---|
| 三个入口 | 人工勾选、按来源单一键转采购、采购工作台拉取；共用交接能力，不另造采购创建规则 |
| 领域所有权 | 需求提供可承接内容与额度；采购创建合法订单并返回接受结果；手工采购独立于需求 |
| 人工数量 | `0 < PurchaseQty <= RemainingQty`，默认全部剩余；RemainingQty 按同一版本及已接受结果计算 |
| 一键数量 | 全部剩余；受影响行有待处置变更时阻断新承接，不停止既有采购 |
| 来源隔离 | 禁止跨来源单合并；采购头最小分组为来源单 + 采购最终选择的供应商 |
| 行组织 | 默认保留来源明细，允许显式合并同来源内产品、单位、收货目标等兼容行 |
| 交期合并 | 不同交期可强确认合并，采购交期取最早日期，贡献仍逐来源明细保存 |
| A/B | 可分开交接；只转 A 提示未执行 B；计划目标是建议，采购必须确定合法实际收货目标 |
| 采购资料 | 无建议供应商可选择；实际供应商和必要目标由采购建立订单时补齐；缺 SupplierProduct/价格仍按采购草稿规则处理 |
| 币种 | 固定人民币 CNY |
| Preview | 数量、实际供应商、目标、合并模式、需求版本变化后重新预览；提交重新校验 |
| 幂等与原子性 | 接受额度、采购订单及执行关联结果一致；重复意图不重复承接，失败不得留下孤立关联；保留单体事务协调，不引入消息队列 |
| 采购后续 | 确认、跟单、取消、减量归采购；需求变化是评估输入，不是采购自动停单指令 |

### 9.6 需求模型阅读与操作入口

需求计划以物料需求操作视图收拢入口，GrossDemand 后台表达来源并可追溯；不要求用户先进入毛需求工作台逐层操作。拆解仍是明确动作，不因此自动下采购。物理迁移见第 24.3 节。

来源、拆解和采购承接数量仍分清责任，不合成万能宽表。当前推荐采购供应商直接属于 NetDemand，新采购承接直接建立 Link，不创建或依赖 Allocation。

| 当前问题 | 首要入口 | 必要关联 | 不应写入 |
|---|---|---|---|
| 来源业务是否进入需求池 | GrossDemand | SalesOrderLine 或其他来源行 | 采购、收货、发货进度 |
| BOM 拆出了哪些物料 | NetDemand | GrossDemand | 当前供应商和下游单号 |
| 当前推荐由谁采购 | NetDemand.SuggestedPurchaseSupplierId | NetDemand、GrossDemand | 实际采购供应商、收货目标及已收货/已发货缓存 |
| 已经转到哪些采购行 | DemandExecutionLink | NetDemand 和采购头行 | 入库、跟单过程数量 |
| 实际收了多少 | 按采购行聚合的已过账 InboundDocumentLine 和反向事实 | 库存流水；需求视图按 Link 计算收货覆盖 | 四张需求计划表 |

物料需求列表以 NetDemand 与来源为主，聚合推荐供应商和有效采购承接；不读取 Allocation，也不因缺少 Allocation 过滤物料需求或阻断采购。当前 Manager 不提供旧详情/Trace 聚合，后续追溯须另建只读用例，不能恢复旧工作台契约。

当前 NetQty 未自动抵扣库存或在途，通常等于拆解所需数量；相关供给只读参考，不预留、不自动分配。不得把同一参考库存计为多个需求各自独占的供给，也不宣称已实现 MRP 净算。

`NetDemandPlanCommandLog` 只保存计划命令幂等结果，不是第五类业务需求。未来可治理为跨模块通用的 Command Receipt/Idempotency Record，但不得并入 NetDemand，也不得与面向人工审计的 `BusinessOperationLog` 混为一个无边界万能日志。

## 10. DemandExecutionLink

### 10.1 权威语义

`DemandExecutionLink` 表示某条 `NetDemand` 对某个采购明细贡献了多少数量。采购行可以合并多个来源，但每个来源贡献必须保留独立 Link。当前只允许 `TargetType=PO`，不存在 Allocation 外键。

| 字段类别 | 目标内容 |
|---|---|
| 关系 | NetDemandId、TargetType、TargetHeadId、TargetLineId |
| 人工查账快照 | TargetNo、DemandRequiredDate、PlannedDeliveryDate |
| 数量 | AllocatedQty、ReleasedQty；有效贡献=`AllocatedQty-ReleasedQty` |
| 状态 | Active、Cancelled、Reversed |
| 幂等 | ExecutionRequestId、CommandItemId |
| 反向审计 | Cancelled/Reversed 的时间、人和原因 |

### 10.2 约束

| 约束 | 目标规则 |
|---|---|
| 目标类型 | 当前固定为 PO；其他执行类型出现明确业务场景后另行设计 |
| CommandItemId | 全局唯一，防止重复贡献 |
| 数量 | `AllocatedQty > 0`、`0 <= ReleasedQty <= AllocatedQty` |
| 活动贡献 | 只汇总 Active Link 的有效贡献 |
| 过程数量 | 不保存 CompletedQty、ReceivedQty；从进度、入库和出库事实查询 |
| 删除 | 不物理删除；取消或反向保留历史 |

### 10.3 外部采购订单导入锚点

独立导入保存采购内容与稳定外部行身份，不要求销售单或需求锚点。有物料需求承接时用 Link 保存数量；无法证明需求来源时不得伪造 Link。

```text
PurchaseOrderLine
        ↑
DemandExecutionLink
        ↓
NetDemand
        ↓
GrossDemand
```

| 导入内容 | 规则 |
|---|---|
| 最佳外部锚点 | 独立采购使用稳定外部采购行身份；需求承接另保存稳定 `CommandItemId`/外部需求行键 |
| Link 必填关系 | `NetDemandId`、采购头行 Uid、采购单号快照和贡献数量 |
| 一致性 | Link 的 `TargetType` 固定为 PO，目标头行必须属于同一采购事实 |
| 来源需求关系 | 通过 `NetDemand -> GrossDemand` 权威推导；无需在采购行重复保存权威 GrossDemandId |
| 单一来源采购行 | 可保存来源类型、来源 Uid、来源行和单号快照作为人工快捷入口 |
| 多来源合并采购行 | 每个来源单独建立 Link；采购行 SourceLineId 为空，不得任取一个毛需求冒充全部来源 |
| 只有销售行锚点 | 先解析内部 SalesOrderLine，再沿 GrossDemand 和当前 NetDemand revision 定位；不得跳过物料需求伪造 Link |
| 只有 SKU/供应商/数量 | 不足以自动建立需求 Link；必须人工计划分配或进入明确的计划外采购流程 |

需求驱动导入须验证需求允许新承接、目标类型为 PO、版本及剩余可执行量、CommandItemId；实际采购供应商有效且目标明确，不要求等于 NetDemand 的建议供应商。外部历史采购若无法证明需求来源，不得伪造 DemandExecutionLink。

## 11. 采购订单与供应商跟单

采购模块的目标页面、API、DTO、前端 Model 边界及当前偏差账本，统一见 [采购模块能力地图](模块能力地图/采购模块能力地图.md)。本节仍是采购业务事实、状态和数量口径的权威来源；能力地图不得改写这些业务事实。

### 11.1 采购头行职责

| 实体 | 保存 | 不保存 |
|---|---|---|
| PurchaseOrderHead | 单号、供应商 Uid 与快照、来源头快照、人民币、生命周期、确认状态、商务要求、日期、幂等请求 | 行数、总数量、已备好、已入库、已发货等过程缓存 |
| PurchaseOrderLine | 产品 Uid、产品与供应商 SKU 快照、采购数量、价格金额、计划交期、B 送达目标、来源摘要 | ReadyQty、ReceivedQty、ShippedQty、LastReceivedDate |
| SupplierProgressReport | 采购行、Sequence、安排状态、累计 ReadyQty、预计备好日、报告日、备注、修正原因、CommandId | 库存和实际发货 |

### 11.2 采购流程

下表涉及 Link 的创建、释放和回退适用于需求驱动采购；独立采购不伪造这些步骤，入口与数量边界见 11.4。

| 动作 | 允许条件 | 事务结果 | 阻断条件 | 反向流程 |
|---|---|---|---|---|
| 需求转采购草稿 | 有可承接需求，采购已选择实际供应商和必要目标，有效 Preview | 采购创建头行，协调需求接受结果及 Link；Active + 待确认 | 剩余量不足、待处置变更、版本变化、采购资料/目标无效 | 采购显式取消或减量后协调关联结果 |
| 手工/独立导入采购草稿 | 明确独立来源，供应商、数量、产品单位和收货目标有效 | 保存采购头行，不生成虚假 Link；待确认 | 来源方式不明、资料无效；具体命令协议后续冻结 | 按采购状态安全修改/作废，不回退不存在的需求 |
| 更新草稿商务字段 | Active + 待确认、版本匹配 | 修改价格、备注、日期等允许字段 | 已确认、已关闭、已作废、存在不安全下游 | 取消确认后处理 |
| 确认采购 | Active + 待确认，资料完整 | ConfirmationStatus=已确认，写业务日志；不重复建立 Link | 供应商失效、数量不守恒、必要价格缺失 | 未入库、无库存事实时可取消确认 |
| 取消确认 | Active + 已确认，无正式入库/库存事实 | 恢复待确认并记录原因；保留 Link 及需求占用 | 已收货或已有库存流水 | 先做入库反向 |
| 供应商进度 | 有效采购行 | 追加 SupplierProgressReport | ReadyQty 非法；向下修正无原因 | 用新修正报告，不覆盖旧报告 |
| 删除草稿行/作废草稿 | Active + 待确认，无收货/库存事实 | 对应 Link 的 ReleasedQty 补足 AllocatedQty，净需求剩余量恢复 | 已入库或已有库存流水 | 正式反向流程 |
| 作废已确认整单 | 下游安全且通过最终事务内复核 | 采购头 Voided，释放全部 Link；也可先取消确认进入可编辑草稿再作废 | 已入库或已有库存流水 | 先做入库反向 |
| 减少采购数量 | 安全草稿，提交版本和原因 | 按规则释放 Link，更新采购行 | 增量、供应商变化或已存在正式事实 | 从 NetDemand 剩余额度重新建草稿 |

### 11.3 已备好分配

供应商累计已备好量用于跟单和装柜计划，不等于库存。采购行合并多个需求来源时，展示层按以下稳定顺序分配覆盖量：

```text
DemandRequiredDate 升序
  -> SourceLineNumber 升序
  -> DemandExecutionLink Uid 升序
```

该分配只是查询投影。PackingList 的实际出货归属由其贡献行决定，并以正式出库为最终事实。

### 11.4 创建、追加与释放的事务规则

本节 Link 校验针对需求驱动交接，需求提供接受边界、采购拥有订单写入；不是要求所有采购必须有需求关联。手工建立、独立外部导入可以没有需求关联；它们仍须形成合法采购头行，明确数量、供应商和收货目标并经过确认，才可正常收货。无需求不等于无单收货，不伪造 Link。

需求驱动部分按 Link 守恒；采购行可以有明确未关联部分，数量 = 有效 Link 贡献合计 + 未关联采购数量，后者非负。纯需求驱动行未关联部分为零；纯独立采购行为采购行全量。创建来源必须明确，不得把丢失的 Link 自动解释成独立采购；手工/导入写命令与来源标识的具体实现后续按采购地图任务冻结。已确认或已有正式事实时不得用“补关联”静默改变历史；后续关联调整另行设计。

需求生成采购时可从 NetDemand 及其物料关系推导送达目标，形成采购后由采购单拥有明确送达目标；客供件采购供应商与收货目标供应商分别表达。入库只验证采购确定的目标及仓库有效性，不重新读取当前物料建议决定收货仓。同一采购行不能合并不同送达目标，建议改变不得静默改写已下单目标。

| 规则 | 说明 |
|---|---|
| 同一来源原子性 | 同一来源单即使生成多个供应商采购头，也必须全部成功或全部回滚 |
| 跨来源隔离 | 一次请求可包含多个来源单；按来源顺序执行独立事务，并返回 Succeeded、AlreadyApplied 或 Failed |
| 默认新建 | 后续再次转采购默认新建草稿，避免静默修改已交给老板或供应商查看的单据 |
| 安全追加 | 只允许同来源、同供应商、Active + 待确认、Version 匹配且无收货/库存事实的草稿 |
| 一键入口 | 始终新建采购草稿，不允许追加 |
| 减量释放 | 必须先 Preview；按原需求交期降序、来源行号降序、Link Uid 降序释放 Link |
| 修改供应商 | 已形成采购单的供应商变更走采购明确业务命令或安全取消重建；不强制先改变 NetDemand 建议，不静默改写历史目标 |
| 锁顺序 | GrossDemand → NetDemand → Link 范围 → 幂等范围 → 目标采购头行 |

需求驱动采购 Create 经领域契约重新验证需求版本、RemainingQty 与接受额度；采购验证实际供应商、目标及订单事实，不能只信任 Preview 或客户端。上述锁顺序是现有需求驱动单体协调顺序，不是独立采购的需求前置条件。

需求业务减少/取消与本节采购减量不同：前者不直接释放 Link 或更新采购数量；采购显式处置后协调结果。继续备货保留原始执行贡献追溯，但不再计为已终止需求的当前覆盖。采购数量守恒与当前需求满足程度不得混为一个公式。

## 12. 供应商虚拟仓与库存

### 12.1 仓库规则

| 规则 | 说明 |
|---|---|
| 第一阶段仓库 | 每个活动供应商一个活动供应商虚拟仓 |
| 权威关系 | WarehouseSite.SupplierId；供应商代码和名称只作快照 |
| 编码 | WarehouseSite.Code 业务唯一 |
| 停用 | 任一产品非零库存阻断软删除；历史流水或业务引用不阻断软删除，历史保留 |
| 内部仓 | 模型可预留 SiteType，当前业务只启用 SupplierVirtual |
| 客供件 | 进入采购明确的实际目标仓，不从当前 BOM 或物料建议推断 |

### 12.2 余额和流水

| 实体 | 业务性质 | 写入规则 |
|---|---|---|
| InventoryBalance | WarehouseSiteId + ProductId 当前投影 | 组合唯一；只由统一库存过账服务更新 |
| InventoryLedgerEntry | 原始库存事实 | 只追加；Sequence 与 CommandItemId 唯一；不修改、不软删除 |

客户差异、包装差异和商业 SKU 差异由 Product/SKU 主数据表达。库存余额、流水和客供件库存不增加客户、销售订单或来源需求维度。

### 12.3 库存流水类型

| 数值 | 类型 | 数量方向 |
|---:|---|---:|
| 10 | PurchaseReceiptInbound | 正数 |
| 11 | CustomerSuppliedReceiptInbound | 正数 |
| 12 | PackingListAutoReceiptInbound | 正数 |
| 20 | FinalCustomerShipmentOutbound | 负数 |
| 21 | CustomerSuppliedConsumptionOutbound | 负数 |
| 100 | OpeningBalance | 按期初方向 |
| 900 | Reversal | 与被反向流水相反 |

所有正式库存动作必须由合法单据产生，不允许直接修改余额。正常过账和 PackingList 编排均禁止负库存，不规划特殊负库存授权。

## 13. 入库

### 13.1 领域边界与来源

入库依赖合法执行单据，不依赖采购最初是否来自需求计划。采购负责供应商、产品单位、采购数量、收货目标、状态和可收货条件；入库负责实际收货、过账及反向；库存负责流水和余额。物料需求和 Link 属于计划与执行追溯领域，不是通用入库准入条件。

| 值/范围 | 类型 | 合法凭证 | 收货目标 |
|---|---|---|---|
| 10 | PurchaseReceipt | 已确认且允许收货的采购行；可无 Link | 采购单明确的收货目标对应的活动供应商虚拟仓 |
| 11 | CustomerSuppliedReceipt | 客供件已确认采购行；不得仅凭物料建议或 Link | 采购确定的送达目标供应商虚拟仓，与采购供应商分别表达 |
| 12 | PackingListAutoReceipt | PackingList 实际出货缺口及合法已确认采购头行、剩余可收容量 | PackingList 编排确定的合法仓库 |
| 100 | OpeningBalance | 独立授权期初命令 | 有效虚拟仓；归库存能力，不走普通采购收货入口 |
| 待实现 | 客户实际退回收货 | 原发货/售后关联和实际收回产品、数量、客户及仓库；不冒充采购收货，不预分配枚举 | 实际接收的合法仓库 |
| 未来 | 生产完工收货 | 生产领域提供的合法执行凭证、可收数量及准入结论 | 生产执行单据确定的合法目标；尚未开放，不预分配枚举值 |

普通入库入口只允许已开放的采购收货类型；PackingList 自动入库由其编排专用入口产生与整单反向。未来完工/质检条件属于生产领域，不由入库复制判断。

### 13.2 入库流程

| 动作 | 允许条件 | 正式结果 | 阻断/反向边界 |
|---|---|---|---|
| 来源查询 | 来源查看权限，合法采购行，采购已确认且活动、未关闭/作废 | 只读可收来源池 | 来源、产品单位、目标或仓库无效；无需求关联本身不阻断 |
| 建立/更新草稿 | 编辑权限；更新须 Active + Unposted、版本匹配 | 保存实收草稿与快照，不改变库存 | 数量不大于零、同单不同目标仓、按来源合计超收 |
| 作废草稿 | 作废权限、Active + Unposted、版本与原因有效 | 作废并保留历史，不写库存流水 | 已过账不能用作废代替反向；当前缺接口须后续实现 |
| Post Preview | 过账权限，草稿及来源有效 | 真实前后数量、阻断和预览标识 | 只读，无正式业务写入 |
| Post | 有效预览、状态/版本/幂等匹配 | 单据状态、库存流水、余额与日志同事务提交 | 重新锁定/验证来源及库存，按来源汇总本单数量；失败全部回滚 |
| Reverse Preview / Reverse | 反向权限、Posted、版本匹配、原因及预览有效 | 原事实保留，追加反向流水，状态 Reversed | 下游消耗、破坏库存守恒或正常负库存时阻断；先处理下游 |

同一业务意图重试复用 CommandId/CommandItemId；相同标识不同内容冲突。来源、库存或输入变化后重新预览，预览不能替代最终校验。反向不能把正常入库变为 PackingList 特殊负库存入口。

### 13.3 数量与草稿口径

- 第一阶段普通收货不得超过有效采购数量；不使用 NetDemand 数量或 Link 贡献限制整条采购行收货。
- 正式净收货量按执行行聚合已过账入库和反向净额，不混入草稿、供应商备好或需求覆盖；反向影响只计算一次。
- 正式剩余可收量 = 采购行允许收货的数量 - 正式净收货量；负值是业务一致性异常，不静默当零掩盖。
- 同单重复来源行先合计再校验，跨单并发在事务中复核，防止逐行检查放行超收。
- 活动草稿不预占额度。单独展示其他活动草稿数量，编辑时排除当前单；允许提醒重复选源，不扣减正式可收量。正式过账不因存在草稿而跳过超收校验。
- 不向 GrossDemand、NetDemand、Link 或采购头行写已入库缓存。

PackingList 自动入库仍只补本次经证明的来源缺口：

```text
自动入库缺口 = max(本次按仓库/产品合计的最终出库数量 - 当前可用库存, 0)
```

需求覆盖不是库存，不得代入公式。缺口须由产品单位、目标仓一致且允许收货的已确认采购行证明，自动入库保留采购行与供货绑定，计入采购正式净收货，并与人工收货共用剩余容量。同一库存键和采购行跨贡献先聚合、跨单并发重验。库存充足不重复入库；ReadyQty 不是收货事实，成品自动入库不得伪造客供件入库或掩盖客供件缺口。

### 13.4 采购与客供件可收货池

可收货池以采购头行为主粒度；多需求合并行不能因联接 Link 被重复计算，无需求行不能被 inner join 排除。

| 字段 | 权威来源 |
|---|---|
| 来源类型、头行 Uid、单号 | 采购头行；SourceUid 不得冒称采购行却装入 Link Uid |
| 产品、SKU、描述、单位 | 采购行及其已验证快照；主数据有效性单独校验 |
| 采购供应商 | 采购头供应商 |
| 送达目标供应商/仓库 | 采购确定的收货目标及有效 WarehouseSite；不是当前物料建议 |
| 采购数量、状态和版本 | 采购头行，由采购领域校验可收货性 |
| 正式净收货/剩余可收 | 按采购行聚合入库和反向事实 |
| 其他草稿数量 | 同来源活动未过账草稿，编辑时排除当前单 |
| 需求追溯 | 可选的采购行 → Link → NetDemand → GrossDemand，不参与通用收货准入 |

有需求的 A/B 采购在生成采购时推导 B 送往 A 执行供应商；采购形成后由其明确目标负责，计划变化不得自动改仓。无需求客供件采购也必须明确合法目标，不能任意输入 SKU 或绕过采购收货。无采购单客供件收货首期不开放。

入库事实保留执行单据头行和产品/单位/仓库快照；需求关联可通过采购行和 Link 追溯，不要求入库行固定一个 Link。无法证明执行来源的记录报告异常，不伪造关系。

### 13.5 需求收货覆盖：只读投影

第一阶段不持久化每笔收货对各需求的固定分摊，也不建立库存预留。采购行实收事实与需求当前覆盖分别表达。

- 当前覆盖只选择仍有有效需求的贡献，已终止需求的历史 Link 保留追溯但不计当前覆盖；不得因此使采购失去收货资格。对这些贡献按 DemandRequiredDate 升序、SourceLineNumber 升序、Link Uid 升序排序；空日期/行号排在有值项之后。
- 以正式净收货量为覆盖预算，依次覆盖各 Link 的有效贡献，单项不超过贡献，总量不超过净收货。无需求关联不伪造覆盖，未覆盖到当前需求的实收量单列；其中历史需求已终止与原本无关联应区分说明，不改写历史归属。
- 采购数量 = 有效关联贡献 + 明确未关联采购数量；关联合计大于采购数量或来源关系不完整时报告异常，不静默截断为正常结果。
- 需求交期等查询输入合法改变、收货反向后可重算覆盖；它不是每批货的历史归属，也不是当前可用库存或已发货数量。
- PackingList 的实际出货归属由贡献行及正式出库保存，不能由覆盖排序反推或改写。
- 例：甲贡献 60、乙 40，甲优先，收货 70 → 覆盖 60/10；反向后净收货 50 → 50/0；完全无需求的采购正常收货，需求覆盖为空。

页面、契约、偏差与实施切片见 [入库模块能力地图](模块能力地图/入库模块能力地图.md)、[库存模块能力地图](模块能力地图/库存模块能力地图.md)。

## 14. PackingList 与出库

### 14.1 使命与统一来源

PackingList 是装箱资料、来源履约和自动库存编排的业务入口。GrossDemand 是唯一交付来源，不按 SourceType 建立白名单。来源必须活动、客户可证明且与 PackingList 头一致，并有正的正式剩余交付量。

草稿不预占交付额度、采购容量或库存。有效已过账且未反向的 PackingList 行形成来源正式交付净额；最终出库只记录库存事实，不重复承担 GrossDemand 履约归属。

### 14.2 标准与非标

- 标准产品行在过账前必须具有 ProductId、单位和 WarehouseSiteId，并进入供货绑定与库存编排。
- 非标行允许建立草稿并正式过账，ProductId 和 WarehouseSiteId 为空；只形成正式交付净额，不创建入库、出库、库存流水、供货绑定或客供件消耗。
- 一张 PackingList 只属于一个客户，可包含该客户的多个合法 GrossDemand 来源。

PackingListLine 保存 IsNonStandardSnapshot 以及来源类型、单号、行号等历史快照，避免历史展示依赖当前来源表。

### 14.3 供货绑定和预览

每条标准产品行的全部数量必须通过 PackingListSupplyBinding 绑定到已确认采购行及确认批次/行。已有库存部分使用已过账采购收货中尚未分配给其他有效 PackingList 的数量作为依据；库存缺口使用采购行剩余可收容量自动入库。

服务端 Post Preview 先使用 WarehouseSiteId + ProductId 的现有库存，再建议一个或多个采购行补足缺口。用户确认或调整建议；Preview 返回稳定 Token、采购建议、自动入库、最终出库、客供件消耗、库存前后值、警告和阻断，但不预留任何资源。Post 必须重新锁定并校验。

绑定数量合计等于 PackingList 行数量，自动入库数量只等于正式过账时实际缺口。人工收货、自动入库和其他有效绑定共享采购行容量校验。

### 14.4 客供件消耗

客供件在 PackingList 正式出货过账时扣减；通过物料需求父子关系识别消耗对象，实际比例、数量和仓库的执行接线后续设计，不依赖采购预绑定仓库或采购 BOM 快照。

部分交付按累计应耗减历史有效已耗计算本次增量，统一保留四位小数并处理最后一批尾差。PackingListConsumptionDetail 保存实际供料关系、采用比例、客供件产品、实际消耗仓库、计算数量和生成出库行。缺少实际消耗依据、实际仓库、产品或可用库存时阻断，不允许负库存。

### 14.5 原子过账

同一 DbSession 事务依次锁定并校验 PackingList、GrossDemand、采购行/确认状态/容量和库存键，然后：

1. 持久化供货绑定并创建必要自动入库。
2. 创建最终客户出库和客供件消耗。
3. 追加库存流水并更新余额。
4. 保存消耗明细，更新 PackingList 为 Posted。
5. 写入 BusinessOperationLog 和幂等结果。

自动单据头保存 TriggerPackingListId。自动入库行以采购行为 SourceLineId、供货绑定为原始依据；最终出库行以 PackingListLine 为原始依据；客供件消耗行以 PackingListConsumptionDetail 为原始依据。一条业务依据对应一条库存行。任一步失败全部回滚。

### 14.6 整单反向与页面边界

Reverse Preview 只读展示本单全部有效事实及反向影响。Reverse 在同一事务先反向最终客户出库和客供件消耗，再反向本单自动入库，最后更新 PackingList 为 Reversed。首版只支持整单，不支持选行或部分数量。

手工入出库页面不得处理 TriggerPackingListId 非空的自动单据。整单反向不等于实际客户退货；真实退货属于独立售后/收货能力。本轮终态不规划已过账修订、库存纠错、打印、导出或 Trace。

详细页面、契约、实体和偏差见 [PackingList 模块能力地图](模块能力地图/PackingList模块能力地图.md)、[入库模块能力地图](模块能力地图/入库模块能力地图.md)、[库存模块能力地图](模块能力地图/库存模块能力地图.md)与[出库模块能力地图](模块能力地图/出库模块能力地图.md)。

### 16.1 数量守恒

| 守恒关系 | 规则 |
|---|---|
| 拆解/计划 | 无待处置差额的正常计划按同一有效版本守恒；发生需求变化时当前要求、计划、历史承诺和差额分别核对，不能删历史凑平 |
| 转采购 | 同一 NetDemand 的活动 Link 有效贡献不得超过 NetQty |
| 采购行 | Quantity = 活动 Link 有效贡献合计 + 明确未关联采购数量；纯需求驱动行未关联部分为零 |
| 采购释放 | ReleasedQty 增加后，采购行数量与剩余 Link 贡献必须同步守恒 |
| 入库 | 普通收货按执行行累计净入库不超过允许收货的采购数量；草稿不预占；自动入库另须证明缺口 |
| 库存 | 某仓库产品余额应等于其全部有效流水 QuantityDelta 累计 |
| PackingList | 贡献行数量、正式出库行和对应库存流水必须逐来源守恒 |

### 17.1 四类记录不得混用

## 20. 当前源码偏差与重建前整改

当前页面和业务服务已经覆盖主要工作台，但现有 Entity 特性和 Dapper SQL 仍带有旧库兼容设计。数据库不能直接按当前代码重建。

| 当前偏差 | 风险 | 重建前目标 |
|---|---|---|
| GrossDemand/NetDemand 仍映射 IndependentDemand/DependentDemand | 新库继续继承旧概念，SQL 到处使用旧列名 | Entity、Repository、DTO 查询别名统一为 GrossDemand/NetDemand |
| SupplierProgressReport 仍映射 FollowUpLog | 通用日志和采购进度职责混乱 | 独立 SupplierProgressReport 表和仓储 |
| Warehouse、Inventory、PurchaseReceive、PackingList 使用旧表和旧列别名 | Entity 属性与 INSERT/SELECT 列不一致，按实体建表后运行即失败 | 表、列、实体和显式 SQL 同名 |
| PackingList Entity 保留 Legacy Id 和只读兼容标记 | 兼容状态会被错误带入新库 | 删除兼容字段，异常状态只在 Query DTO 表达 |
| Link 仍允许新计划关键 Uid/幂等键为空 | 新链路可能无法守恒或追溯 | 新库关键关系和 CommandItemId 收紧非空 |
| Link 保存 CompletedQty/ReceivedQty | 与跟单、入库正式事实产生双重真相 | 删除过程缓存，查询聚合 |
| Inbound/Outbound LifecycleStatus、WarehouseSite.SiteType 使用裸 byte | 枚举语义可能漂移 | 使用冻结的共享枚举类型 |
| Product 仍保存默认供应商/客户兼容代码和 SKU | 多关系重复表达且容易不一致 | 只保留 DefaultSupplierId，其他进入关系表或 Query DTO |
| SalesOrderLine 保存 LastShippedDate | 出库反向后容易失真 | 从正式出库净额查询 |
| BOM Entity 已有 ParentProductId/ComponentProductId，API/WPF 仍沿用 ParentSkuId/SubSkuId 兼容别名 | 契约命名与编码查询仍需统一，不能误报实体尚未改名 | 按 BOM 地图核对调用链；稳定 Uid 权威，保留必要兼容，不在本次改业务源码 |
| 普通入库按 Link、客供件按 Allocation 选源 | 无需求采购被排除，或计划被当作收货凭证；目标仓依赖活动计划 | 统一按合法已确认采购行收货，收货目标由采购确定；详见入库地图 INB-001/002 |
| 003–015 迁移以旧库增量兼容为目标 | 不适合实体同名全量重建 | 仅作历史参考，另建开发库全量重建脚本 |

实体清理必须沿以下影响链同步完成：

```text
Core Entity
  -> Repository Interface
  -> Infrastructure Dapper SQL 与列别名
  -> Application 校验和事务
  -> Contracts DTO / 枚举 / Refit
  -> Controller
  -> WPF Model / ViewModel / Binding
  -> 全量建表脚本、约束和示例数据
```

## 24. PackingList 自动库存编排决策（2026-09-16）

### 24.1 权威边界

| 领域 | 权威事实 | PackingList 使用方式 |
|---|---|---|
| 来源需求 | GrossDemand 身份、客户、产品/非标、允许交付量、状态和版本 | 统一选源和正式额度复核，不按来源类型白名单 |
| 采购 | 采购行、确认状态与批次、正式净收货和剩余可收容量 | 供货绑定、自动入库和客供件计算依据 |
| 入库 | 采购收货、自动入库及反向 | 由 PackingList 最外层事务调用 |
| 库存 | WarehouseSiteId + ProductId 余额与不可变流水 | 锁定、过账和反向；不增加客户/订单维度 |
| 出库 | 最终客户出库、客供件消耗及反向 | 记录库存事实，不重复计算来源履约 |
| PackingList | 装箱资料、来源正式交付净额、供货绑定、消耗明细、过账和整单反向 | 统一编排并保留历史依据 |

### 24.2 数据模型

PackingListHead / PackingListLine 继续作为单据权威。PackingListLine.ProductId 目标改为可空，并增加 IsNonStandardSnapshot、来源类型/单号/行号快照。

新增 PackingListSupplyBinding，关联 PackingList 行、采购行、采购确认批次、依据数量和自动入库数量。新增 PackingListConsumptionDetail，保存实际供料关系、采用比例、客供件产品、实际消耗仓库、计算数量和生成出库行。草稿与 Preview 不创建正式绑定或消耗事实。

### 24.3 命令和权限

保留现有六个查询/草稿接口，新增：

- POST /{uid}/post-preview
- POST /{uid}/post
- POST /{uid}/reverse-preview
- POST /{uid}/reverse

查询和草稿继续使用 Module.Shipping.Access；过账和整单反向分别使用 Shipping.PackingList.Post 与 Shipping.PackingList.Reverse。Post/Reverse 使用版本、Preview Token、稳定 CommandId、事务锁和完整幂等结果。

### 24.4 实施顺序

1. 通用 GrossDemand 来源和非标无库存过账。
2. 供货绑定、实际客供件消耗计算和 Preview。
3. 必要自动入库、最终出库、客供件消耗的原子 Post。
4. 全部生成事实的整单 Reverse。

阶段验收必须覆盖跨客户拒绝、非标、库存充足、采购缺口、多采购行、容量不足、实际消耗依据缺失、累计耗用、并发超交付、幂等、事务回滚和整单反向。
