## 2. 规则状态与范围

### 已确认要求及保留边界

1. 同 SKU 默认兼容合并；仍保留“保持来源明细”的可选方式。合并不扩大为跨来源单合并，不只比较 SKU 文本。
2. 物料供应商是建议，采购拥有实际采购方与实际送达方；采用建议后可由采购明确修正，不回写物料建议。客供件采购方与送达方是两个概念。
3. 一个合并采购行可以关联多个 NetDemand；逐条 Link 保存各自贡献数量，不能把整行数量重复记给每个需求。
4. 保留现有数量额度、事务、版本、幂等、独立采购、追加草稿及生命周期规则。创建请求按 ExecutionRequestId/CommandItemId 安全重试，不增加阻断合法重试的过滤器。
5. 使用现有公共 `IDialogService`，页面内部展示提示和确认，不嵌套打开 Dialog；公共 Dialog 实现不属于本批修改范围。

### 本文优化建议的地位

下述四轮是拟实施方案，不是新的审批或采购数量政策。实施授权应明确覆盖对应轮次。修复状态丢失、过期响应和信息丢失不改变业务数量规则；允许部分来源单独创建、跨来源合并、超额关联、改写价格或交期政策等新规则均不在授权推定范围内。

## 4. 第 1 轮：修复会话与预览有效性

**目的：先保证用户看到和提交的是同一份有效选择，不丢结果，不重复采购。**

- 把“新打开会话”和“返回后更新选择”分开。按 NetDemandId 对比增删项，保留未变项输入、已选合并方式；移除项使旧预览失效。
- 输入修改递增修订号；预览响应同时核对请求身份、输入修订和页面生命周期。过期响应不得清除 IsStale、重建目标或恢复创建按钮。
- 有效预览的输入变化后，立即失效并清除旧警告确认；重新计算后才能创建。
- 已产生成功/AlreadyApplied 结果时，累计 HasAppliedResults 不得被后续失败、返回选择或重新预览清空；关闭后管理页仍刷新。
- 成功项从可重提交集合中排除或明确锁定。失败重试保留原命令身份与负载；用户改变已提交负载不能在同一个幂等键下静默重用。先核实后端重放协议，必要时把明确修改后的待执行项作为新尝试，并保留先前结果；不改后端幂等裁决。
- 返回选择仍保留输入；提交期间禁止返回/重复创建。结果未知时不自动换请求 ID 再创建。

**验收：** 返回再前进不丢输入；请求 A 飞行中修改为 B，A 返回仍失效；成功后再操作失败，关闭仍刷新；同负载重试不重复建单；部分成功和未知结果可辨认。没有证据不得宣称不会重复创建。

## 5. 第 2 轮：默认兼容合并与来源辨认

**目的：默认合并可合并物料，并让用户看懂为什么合并或没有合并。**

- 新会话默认 `MergeCompatibleLines`，返回选择不重置用户手动选择。新请求默认行为和前端显式传参保持一致，不擅自更改历史序列化枚举值。
- 合并范围先按来源类型+来源头 Uid、实际采购供应商隔离，再检查产品身份/SKU、计量单位、实际送达方及当前价格、供应商型号、精度等条件。复用 MergeKey，不另写前端合并算法。
- 同 SKU 但单位、供应商、送达方或价格不一致时分行，并给出简短原因。不同物料/客供属性、非标身份和不可用一个字段表达的快照差异须核对，不能 BuildLine 取第一条而悄悄丢信息。
- 交期不同继续沿用“取最早日期+明确确认”，展示原交期和采用交期；本批不另改交期策略。
- 预览行补齐图片、产品型号 LinkSku、描述、单位、采购供应商、实际送达方；图片必须属于该物料，不默认使用父件图片。已有 DTO 字段优先投影，仅为真实缺口加窄字段。
- 合并行可展开贡献明细：来源单号/行号、物料 SKU、原剩余量、本次贡献量、原交期。以 NetDemandId 保持身份，UID 不作为主要显示文本。
- 顶部显示选中物料数、采购单数、合并前后行数；不同单位不能相加成一个无单位“总数量”。

**验收：** 默认兼容合并；切回保持明细有效；不同来源/单位/采购方/送达方/价格不误合并；合并行量等于贡献合计；图片型号准确；贡献可追溯；交期差异可见且确认后才创建。

## 6. 第 3 轮：阻断可定位、可修正

**目的：保留安全校验，让用户知道哪一行出了什么问题、在哪里处理。**

| 分类 | 规则 | 页面动作 |
|---|---|---|
| 硬阻断 | 数量非法、版本失效、实际供应商缺失/失效、客供目标缺失、来源事实损坏 | 禁止创建；定位对象，给出可操作修复入口或明确刷新/移除选择建议 |
| 明确确认 | 不同交期合并取最早、父件采购后关联客供件仍有未采购量 | 展示影响明细，在本页面确认；不强迫父子一起采购 |
| 普通提示 | 缺少价格或供应商产品资料 | 允许创建草稿，标记具体待补资料，不升级为审批 |

- 保留全批阻断策略：任一已选来源存在阻断，本次不创建；显示受影响来源/物料。不自动跳过，不新增“仅创建有效来源”政策。
- 警告按稳定身份保留影响集合；若聚合展示，必须合并全部 NetDemandIds/供应商/来源信息，不能 GroupBy 后只取第一条。界面一次确认覆盖范围要明确；后端现有按来源+警告代码确认若保持不变，显示也按同一范围聚合，不能冒充逐行独立确认。
- 提供实际采购供应商和客供件实际送达方的补选/修改入口；推荐信息只读对照，不回写 NetDemand。选择变更使旧预览和确认失效，服务端复核合法性。
- 父件已有实际采购方与建议不一致时显示差异及依据；有多个实际方必须明确选择，不取第一条。不具备证明依据时提示不能推断，不能自动代填。
- 问题显示“来源单/物料型号/SKU—原因—处理动作”；技术错误码放辅助详情。点击问题定位对应行；按钮旁明确“还有几项阻断/待确认”。没有修复路径不能只写“请先修复数据”。
- 若实际供应商编辑会牵涉本批外新业务决策，只冻结该具体边界并报告，不扩大到采购替换、履约或供应商主数据维护。

**验收：** 无建议仍可在采购补选；失效供应商阻断；客供采购方/送达方独立；父实际与建议差异显式；同来源同类多条警告不漏行；修改后须重新确认；缺价格仍可建草稿；任一阻断不发生静默部分创建。

- 顶层结构化非冲突错误视为确定失败，不进入未知写入状态；审核失效并允许返回准备修正。没有稳定错误代码的传输失败、空结果或未识别异常继续视为真正未知，保留原 `_pendingCreateCommand`、`ExecutionRequestId`、`CommandItemId` 和冻结负载，只允许原命令重试，且禁止返回、关闭、刷新和修改。

### 页面差异与验证边界

- 准备页只在现有顶部操作区增加“刷新待采购数据”，原来源区、筛选、候选 Grid、供应商编辑、反选/全选、父件联动和警告区不变。
- 审核页只从顶部操作区移除“刷新预览”及其专用提示，并把创建、返回按钮左移；左侧单据、19 列单头、明细、来源贡献、比例、间距、Logo、备注和滚动区域均不调整。
- 自动测试以公开状态和 API 调用计数验证刷新保留、失败保留、迟到响应、Busy/输入释放、重新校验复用、确定冲突、未知重试和部分成功不重发。受既有 `obj` Access denied 约束时，只记录实际命令失败，不提权、不清理、不换输出目录规避；真实缩窗滚动、鼠标/键盘和供应商编辑仍需人工联验。

### Busy 通知缺口续修

本轮锁死现象还存在一个可由源码静态证明的直接通知缺口：`ReturnToPreparationCommand.CanExecute` 依赖 `IsNotBusy`，但原构造器没有把返回命令注册为 Busy-aware；预览成功或失败时，预览状态通知发生在 `RunBusyAsync` 内部，只能观察到返回不可用，`EndBusy` 又不会通知该命令，WPF 因而可能持续保留禁用状态。现已把返回命令接入既有 Busy 通知集合，不修改公共基类。

创建按钮原先同时绑定 `CreateCommand` 与同义的 `CanCreateCurrent`。预览状态在 Busy 内通知该属性时值仍为 `false`，而 `EndBusy` 只刷新已注册命令，不会刷新普通计算属性，形成第二个确定的通知缺口。由于该属性没有其它调用者，现已删除冗余属性与 `IsEnabled` 绑定，创建按钮统一服从 `CreateCommand.CanExecute`。测试监听返回和创建命令的 `CanExecuteChanged`，并在通知回调中读取最终值，覆盖预览成功、预览失败、创建确定冲突和未识别异常进入未知结果后的 Busy 释放。上述结论属于静态调用链证明，仍不宣称已经动态复现原现场。

## 14. 采购草稿客户快照持久化缺口修复（2026-09-13）

1. 根因是需求采购写模型已经从锁定后的客户主数据预览文档生成 `CustomerId`、`CustomerCode`、`CustomerNameSnapshot`，但 `PurchaseOrderDraftRepository` 的头 INSERT 只写入 `CustomerCode`；随后草稿仓储和旧采购工作台的 `HeadColumns` 也未读取客户 Uid 与名称快照，导致确认读取把既有客户误判为空。
2. 草稿 INSERT 现显式写入三个字段，两个旧链头投影也显式读取三个字段。名称始终使用创建时快照，不联查当前客户名称覆盖历史；独立采购创建路径保持不变。
3. 安全追加只新增采购行并推进原头版本，不更新客户字段；追加门禁补充 `CustomerId` 一致性检查。客户主数据改名或改码不会覆盖既有采购头名称/代码快照。
4. 历史上已由缺陷路径创建的空 `CustomerId` 或空 `CustomerNameSnapshot` 记录不会自动回填，仍会被确认校验拒绝并需要人工核实。`ActiveConfirmationId` 继续由确认流程生成、取消确认清空；`PackagingRequirements` 没有权威来源时继续为空。
5. 同类审查发现需求草稿旧链仍未显式设置或持久化 `OriginKind`，实体注释定义 1 为需求，但现有路径保持默认 0。本次没有获得历史分类、兼容查询和回填规则，因此只登记影响，不擅自扩展。
6. 新增/更新测试覆盖写模型三字段、INSERT 列与参数、两个头读取投影、追加客户一致性和不覆盖快照。受既有 `obj` Access denied 约束，本轮仅做静态检查，不运行构建或测试。
