# 需求计划治理

## 目标

来源需求统一接收及可交付能力已前置到[阶段 0](00A-来源需求汇聚与交付治理.md)，不能等到本阶段才实现。PL 必须认识来源需求，但不认识物料需求/Allocation 内部计划结构。本阶段复用阶段 0，不另造来源汇聚表。

毛需求后台表达来源，物料需求表达拆解结果及待采购建议，采购承接用数量关联表达。库存与销售交付不认识计划内部结构。保留一来源多物料、多物料同销售单内合并采购行，不能为简化改成一对一。

## 当前实体与重构边界

- GrossDemand 的来源头行、拆解 revision、生命周期可保留。来源接收可后台自动，BOM 拆解是否自动不在本次扩大；前端可从销售/物料需求入口直接触发拆解，不强制先进入毛需求工作台。
- NetDemand 保存 Parent/Root/BomPath 与比例依据的历史含义；这些是组成关系，不是客供件库存所有权。DeliveryTargetNetDemandId/DeliveryMode 降为可选建议/兼容，实际执行目标由采购固定。
- Allocation 当前含 PlannedQty、供应商、目标父计划、替代链。阶段 1—4 解开消费者后，再审计计划编辑、幂等记录和历史 Link；优先保留最小建议模型，不继续扩展多层计划状态机。
- Link 已有 NetDemandId、采购头行、贡献与释放量，优先复用而非另加平行追溯体系。新承接输入可用物料需求身份；旧 Allocation 关联须兼容/迁移，不能直接设 null 破坏剩余量。

## 实施分步

1. 搜索全部 Allocation/DeliveryTarget 消费者，分类为计划内部、采购承接、库存执行、销售查询、历史读取。先证明外部新执行链不再强依赖。
2. 将采购创建规则留在采购领域，需求只提供同订单可承接量并接纳结果；接受量与采购创建在单体事务中一致，重复导入/点击不重复承接。
3. 比较两个方案：保留简化 Allocation，或将必要建议字段收敛到物料需求并让 Link 直接锚定需求。只在能证明调用方和历史可迁移时选择后者；不得把“方向授权”当成直接删表授权。
4. 拆解和采购承接版本分开，重新拆解不能把旧采购当不存在。当前要求、有效承接、取消释放与历史数量可解释，不强制上游取消先撤真实库存。
5. 物料需求页聚合来源、建议、可承接量和采购摘要，毛需求保留追溯/后台状态，不新增每实体独立窗口。收货覆盖是参考查询，不是订单池可用量。

## 验收

销售行拆多物料；同销售单两需求合并一采购行贡献守恒；不同销售单拒绝合并；部分承接、释放和重试正确；建议供应商变化不改已下单采购；改 BOM/重新拆解不改历史执行；无需求独立采购不受影响；客供件不再要求父 Allocation 才能入库消耗。
