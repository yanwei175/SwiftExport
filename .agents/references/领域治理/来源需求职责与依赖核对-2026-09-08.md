# 来源需求职责与依赖核对（2026-09-08）

## 已确认目标与本次范围

来源需求（现 GrossDemand）是需求主体：销售、品控/售后领域认可的实物需求在上游确认事务内自动幂等汇聚，再由下游消费。物料需求（现 NetDemand）是来源需求拆解产生的下一级事实，来源需求的接收、保存和本体查询不以物料需求存在为前提。来源需求不承担采购、收货、出货的单据进度查询，也不承担需求完成率查询。

本次只核对源码、更新文档；以下“建议”均未实施。没有运行构建、测试或数据库迁移；测试文件存在不等于本轮已验证通过。不批量改名、不删除历史表，也不移除现有有效的交付额度保护。

## 当前真实落点

下列路径均相对仓库根目录。

| 能力 | 当前源码证据 | 结论 |
|---|---|---|

| 售后自动接收 | Application/Services/QualityControl/AfterSalesService.cs：ConfirmDemandAsync | 已有真实接线；正数量实物行以 CR、售后头 Uid、稳定售后行 Uid 接收，使用 head.Version+1；纯投诉不生成来源需求。不能据此宣称所有品控单据均已接入 |

| 需求本体 | Core/Entities/DemandPlanning/GrossDemand.cs | 已保存来源身份/版本、客户、产品单位快照、数量、交期和生命周期；实体没有已采购/已收/已发缓存，但混有拆解状态、修订号、时间、人 |

## 依赖来源需求的消费者

| 消费者 | 依赖方式 | 收窄后的安排 |
|---|---|---|
| 物料拆解、回退及需求转采购 | GrossDemandWorkspaceService、PurchaseDraftCreationService 使用 IGrossDemandRepository；NetDemand 通过 GrossDemandId 关联 | 保留物料需求向来源需求读取稳定身份、版本、有效数量的方向；拆解/回退编排归物料需求或明确交接用例 |
| PL | 当前 `PackingListService` / `PackingListRepository` 直接按 GrossDemand 校验查询和草稿额度；正式提交尚未实现 | 保留来源需求作为交付要求入口；后续正式交付与库存动作接入独立履约边界，不恢复旧物料计划链 |
| 销售履约及订单查询 | SalesFulfillmentManagerRepository、SalesFulfillmentDetailRepository、SalesOrderHeadRepository 联查 GrossDemand | 保留在销售/履约查询侧，先聚合事实再关联，不搬回来源需求页面 |
| 售后结案 | AfterSalesService 调用 ISourceDemandClosureService | 售后拥有结案决定；所需正式交付证据经交付查询取得，来源需求仅给出需求状态和有效要求 |
| 采购、入库、出库及追溯查询 | PurchaseOrderWorkspaceRepository、InboundSourceRepository、InboundDocumentRepository、OutboundDocumentRepository 等存在 GrossDemand SQL 引用 | 分别核对准入和历史追溯；SQL 引用不等于所有采购都必须有来源需求。独立采购继续合法无上游 |

上游销售、售后是接收协议调用方，并非物料拆解消费者。当前既有手工需求入口仍存在；本次没有授权删除或改变其准入。

## 推荐收窄顺序

1. **先收窄来源列表和详情。** 移除来源管理契约的 ExecutionProgress/ExecutionProgresses、下游数量统计与执行进度筛选；对应 GrossDemandListItemDto、GrossDemandSearchRequest、GrossDemandRepository、WPF GrossDemandRowModel/WorkspaceViewModel/WorkspaceView。保留来源身份、需求内容、版本、生命周期、操作日志和上游导航。跨单据 Trace 改为独立查询入口或下游导航，不在来源详情装入整套执行树。验收：来源本体查询不 JOIN NetDemand、Link、Inbound、Outbound 来计算进度；无物料需求的来源行正常显示。
2. **将拆解编排归还物料需求。** 迁出 GrossDemandWorkspaceService 中的 BOM 展开、NetDemand/Allocation 写入和回退校验；复用 GrossDemandDecompositionPlanner 等已存在计算逻辑。来源页可保留“拆解”导航，发起的是物料领域用例。DecompositionStatus/Revision/At/By 先保留历史解释，待全部写入者和消费者切换后决定是否只保留交接回执/投影，不立即删列。验收：来源接收及本体服务不注入物料仓储，物料侧通过窄契约取得并校验来源版本，失败整体回滚。
3. **移出履约查询和售后完成判定。** SourceDemandDeliveryService 当前的正式已发聚合、剩余交付计算迁至交付职责；SourceDemandClosureService 的完成判定迁回售后结案用例。来源需求只提供有效要求、状态、来源/需求版本及锁定校验。既有接口先兼容转发再切换真实 PL/售后调用方，不新增第二套额度权威，也不以新缓存数量替代出库事实。验收：来源页面没有完成率；PL 仍按 GrossDemandId 选源；来源终止/版本更新与 PL 提交串行协调，重复提交不超发；售后结案规则仍有真实交付证据。
4. **最后收窄取消确认和变更的跨域安全检查。** 当前接收服务经 GrossDemandRepository 检查物料历史、Allocation、Link 和库存事实。将这些事实检查交由下游影响评估/交接用例，来源只根据明确处置结果执行自身生命周期变更。不得以“取消依赖”为由删除阻断或物理清理历史。验收：保留从未拆解删除、已安全回退保留作废的历史规则；有执行事实时不得静默覆盖要求；不级联取消采购或反向库存。

以上是业务职责迁移；不要求机械拆分所有 Service/DTO，不预设新建全套五层文件。

## 需单独验证的现有风险

- GrossDemandRepository 将多个物料 Link/收货数量加总后与来源成品 DemandQty 比较以计算 ExecutionProgress。BOM 组件数量可能不是同一产品/单位，不能据此表示需求完成；建议删除该来源进度口径，不另造完成率公式。
- SourceDemandReceptionService.Apply 每次较新版本更新都会把 DecompositionStatus 写为 Pending。同内容高版本的更新路径未要求下游处置，可能保留既有物料记录却重置拆解状态；应补“已拆解、同内容、新头版本”的回归检查，元数据推进不能改写拆解事实。
- SourceDemandDeliveryItemDto 混入 OrderPoolSalesOrderId、IsInventoryActionAllowed、InventoryBlockerCode；SQL 对 CR 固定返回 ORDER_POOL_OWNERSHIP_REQUIRED。订单池和库存动作资格应由实际交付/消耗上下文证明，不能由来源类型统一拒绝所有售后或无客供件场景。
- 当前来源服务既决定有效要求，又读取下游交付。迁移时必须保留共享 DbSession.Transaction、固定锁序和提交最终重验；“不做完成率查询”不等于“取消防超发约束”。
- 已有 SourceDemandReceptionServiceTests、SourceDemandDeliveryContractTests、AfterSalesServiceTests、AfterSalesSqlTests、SourceDemandClosureTests 和拆解测试；本次只静态核对，没有重新执行。尤其真实 SQL 并发、历史反向净额、版本推进和各模块最新接线需在对应实现切片中验证。

## 完成标准

来源需求的核心可以在没有物料需求、采购及库存数据时接收并查询合法实物要求；销售和售后同一命令重试不新增有效需求；物料需求以来源需求为上一级，来源本体不维护物料明细。单据进度、履约完成率、售后结案和库存池准入各归其消费者。职责切换必须保持需求身份、版本、历史追溯和交付并发保护。
