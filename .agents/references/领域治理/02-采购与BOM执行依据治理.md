# 采购与 BOM 执行依据治理

## 基线与目标

独立采购已建立，应扩展而非重建。PurchaseOrderHead 已有 OriginKind、CustomerId、DemandSourceType/Uid、ActiveConfirmationId；PurchaseOrderLine 已有 UnlinkedQty、DeliveryWarehouseSiteId，也残留 DeliveryTargetAllocationId。PurchaseConfirmationLine/Node 已提供组成指纹、路径、原比例、累计比例及消耗仓库。

采购独立于需求计划，但一采购单唯一对应一销售单。客户身份不是销售订单身份；UnlinkedQty 表示未关联需求的采购量，不代表无订单归属。采购供应商、实际收货仓库、客供件消耗仓库是不同语义。

## 分步治理

1. 检查独立创建/导入、保存/确认服务的实际文件和测试，确认 DemandSourceType/Uid 可否作为唯一销售归属；若不足，设计一次有明确兼容映射的字段迁移，不新增并行权威来源。
2. 采购创建及确认校验唯一销售单与客户一致，需求转入只接受同销售单的贡献。导入通过稳定外部行键/命令身份防重复；不要求 Allocation，不允许客户单号模糊匹配。
3. 收货能力返回采购头行、销售单、产品/库存单位、目标仓、状态版本、允许收货数量。最终提交校验已确认采购量减有效净收货，人工和 PL 自动收货共用容量；不按 Link 数量限制整采购行。
4. 复用现有确认快照固定组成。需求转入可采用已接受拆解依据，独立采购读取一致 BOM；两条路径输出同一种可消费的采购执行依据。不读取当前 BOM 改写旧批次。
5. 消耗节点保存父子/路径用于解释比例，消耗仓库负责定位订单池，不绑定父 Allocation 库存。PL 可通过采购行和确认批次取得客供件单位用量与仓库。
6. 暂不新建角色、生产工单、采购万能来源引擎，也不扩大普通采购保存修改已承接贡献的权限。

## 迁移与交付

将旧 DeliveryTargetAllocationId 可证明的目标迁到实际仓库，保留原关系快照；多目标或未知不能随意选一个。历史仅有 CustomerId/订单号不够时，先人工核实销售单。BOM-004 更新为已有结构的消费闭环验证，不以“类型已存在”关闭。

本领域输出三个窄协议：销售归属、可收货上下文、执行组成上下文，后两者供入库/PL 使用。DTO 不暴露可编辑采购全对象或要求下游写入确认表。

验收：无需求独立采购正常确认；两销售单混入一采购被拒绝；客供件可送至非采购供应商的目标仓；无 BOM 与读取失败不同；当前 BOM 改动不改变旧采购消耗；多 Link 不倍增采购可收量；重复导入不建重复采购。
