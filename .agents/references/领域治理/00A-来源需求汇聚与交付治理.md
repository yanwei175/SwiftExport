# 来源需求汇聚与交付治理

本阶段在 PL 接线前完成，先于 Allocation 物理精简。权威为业务总纲第 24.7 节；原毛需求统一叫“来源需求”（现 GrossDemand），原净需求叫“物料需求”（现 NetDemand）。只改变业务语义，不要求批量重命名现有类型、表、路由或文件。

## 责任与协议

- 销售维护销售事实，品质售后维护本领域事实，通过窄接收/变更协议提交认可的实物需求；来源需求不回写上游业务。
- 来源需求保存来源类型、头行身份、来源版本、需求意图、客户、产品单位、有效要求与生命周期，汇聚成 PL 唯一选源入口。
- 幂等键须区分业务意图和传输重试：相同来源/意图更新同一有效要求，相同命令不同内容拒绝；旧版本不覆盖新版本。不能每次同步生成新可发量。
- 提供统一可交付列表、交付上下文及事务内额度复核。有效已发由关联来源需求的正式客户出库聚合，不计客供件消耗，不要求物料拆解或 Allocation。
- 变更/终止与 PL 提交协调版本及并发；来源状态已失效或可发不足时阻断正式提交。不能只靠 UI 或过期 me/页面缓存判断。
- PL 贡献保存来源需求 Uid；原始销售/售后身份用于追溯。售后补发独立需求意图，不双增原销售额度。
- 可发数据来源资格与最终能否过账分开：订单池归属、采购组成和库存容量仍在提交时验证。售后无可证明订单池不能自动借用同客户库存；记录待补执行依据，不伪造销售单。

## 契约与迁移

复用现有 GrossDemand SourceType/Uid/LineId 等字段并审计版本/幂等缺口。建议协议职责：接收/变更来源需求、查询可交付来源、复核来源额度；具体名称服从现有契约。无源码验证不得宣称已有版本保护。

已有来源需求优先复用；从销售、售后与历史 PL 做确定性映射，重复/多解隔离，不重新生成第二份交付额度。来源需求不是新的物料计划前置审批；不自动采购，不建设完整品质售后模块。

验收：销售/售后重复接收不增量；两种来源均能无 NetDemand/Allocation 进入 PL 草稿；旧版本更新拒绝；并发发货不超来源额度；销售变更使旧预览失效；售后补发不增加原销售已发；未知池归属不能绕过库存校验。
