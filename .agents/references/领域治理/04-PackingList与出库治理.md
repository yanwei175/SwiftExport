# PackingList 与出库治理

本文是 [PackingList 模块能力地图](../模块能力地图/PackingList模块能力地图.md) 的实施路线。它只描述目标顺序、交接和完成门禁，不替代源码、数据库设计或阶段任务计划。

## 1. 目标

把 PackingList 从查询与草稿切片推进为完整的装箱资料、来源履约和自动库存编排入口，最终支持：

- 所有满足统一条件的活动 GrossDemand 来源。
- 标准产品的供货绑定、必要自动入库、最终客户出库和客供件消耗。
- 非标来源的无库存正式过账。
- 原子正式过账和整单反向。

本路线不包含已过账修订、库存纠错、打印、导出、Trace、实际客户退货或部分反向。

## 2. 共同约束

1. GrossDemand 是唯一交付入口，来源类型只作快照与追溯，不作白名单。
2. 头客户必须与每条来源客户一致；正式交付净额只由有效已过账且未反向的 PackingList 行形成。
3. 库存键统一为 WarehouseSiteId + ProductId，不增加客户或销售订单维度。
4. 标准产品必须完成供货依据绑定；非标来源不创建任何库存、采购绑定或客供件事实，仓库必须为空。
5. 客供件只读取绑定采购行的 PurchaseConfirmationLine / PurchaseConfirmationNode 快照。
6. Preview 不预留资源；Post/Reverse 必须重新锁定并校验状态、版本和全部权威数量。
7. 不允许负库存，不规划特殊放行。
8. PackingList 自动生成的入库和出库只能由 PackingList 命令编排，手工入出库页面不得编辑、过账或反向这些单据。

## 3. 阶段一：通用来源与非标

### 3.1 数据与契约

- PackingListLine.ProductId 改为可空。
- 增加 IsNonStandardSnapshot、来源类型、来源单号和来源行号快照。
- 来源候选与行 DTO 同步可空产品及非标/来源快照语义。
- 来源投影从 GrossDemand 取得客户、产品/非标、单位、允许交付量、状态、版本和展示快照，不直接联查具体来源业务表决定准入。

### 3.2 业务规则

- 候选只要求来源活动、未删除、客户可证明、剩余交付量为正。
- 标准行草稿可暂缺仓库，但正式过账前必须有有效仓库、产品和单位。
- 非标行仓库必须为空；草稿保存和正式过账均允许。
- 草稿保存重新校验同客户和当前剩余额度，但不占用额度。

### 3.3 完成门禁

- 任意 SourceType 的合法来源均可选，跨客户拒绝。
- 标准/非标草稿查询、保存、并发和幂等测试通过。
- 非标行无法携带仓库或进入库存动作。

## 4. 阶段二：供货绑定和预览

### 4.1 目标结构

建立 PackingListSupplyBinding，保存 PackingList 行、采购行、确认批次/行、依据数量和本次自动入库数量。建立 PackingListConsumptionDetail，保存确认节点、比例、客供件产品、消耗仓库、计算数量和生成出库行。

草稿和 Preview 不写这两类正式事实；Post 成功时才持久化。

### 4.2 Post Preview

新增 POST /api/shipping/packing-lists/{uid}/post-preview。服务端按稳定顺序：

1. 读取草稿、有效行和 GrossDemand 剩余额度。
2. 汇总各标准行的仓库产品库存。
3. 先分配已有库存对应的已过账采购收货依据。
4. 对库存缺口建议一个或多个已确认采购行，并计算本次自动入库量。
5. 从建议/确认采购行的确认节点快照计算客供件累计应耗和本次增量。
6. 返回 Token、采购建议、自动入库、最终出库、客供件消耗、库存前后值、警告和阻断。

用户可确认或调整采购绑定，但不能改变产品、确认批次或容量等权威事实。

### 4.3 Reverse Preview

新增 POST /api/shipping/packing-lists/{uid}/reverse-preview。只读取本单当前有效的供货绑定、消耗明细、自动入库、最终出库、库存流水和下游依赖，返回整单反向影响。不得接受选行或部分数量。

### 4.4 完成门禁

- 库存充足、单采购行缺口、多采购行缺口、容量不足均有确定结果。
- 绑定数量合计等于 PackingList 行数量，自动入库量只等于实际缺口。
- 确认快照缺失或客供件库存不足明确阻断。
- Preview 不改变数据库中的交付、采购或库存事实。

## 5. 阶段三：原子过账

### 5.1 API 与权限

新增 POST /api/shipping/packing-lists/{uid}/post，使用独立权限 Shipping.PackingList.Post。命令提交原单版本、Preview Token、确认后的供货绑定和稳定 CommandId。

### 5.2 事务顺序

在同一 DbSession 事务内：

1. 锁定 PackingList 头行并校验 Draft、版本和行结构。
2. 锁定 GrossDemand 并复核客户、状态和剩余交付量。
3. 锁定采购行、确认快照、净收货、有效绑定和剩余可收容量。
4. 锁定所有仓库产品余额并校验禁止负库存。
5. 持久化供货绑定，创建必要自动入库及库存流水。
6. 创建最终客户出库与客供件消耗及库存流水。
7. 保存消耗明细，更新 PackingList 为 Posted，写入操作日志和幂等结果。

所有锁按稳定业务键排序。任一步失败，头行、绑定、自动单据、库存流水、余额、状态和日志全部回滚。

### 5.3 库存单据依据

- 自动单据头保存 TriggerPackingListId。
- 自动入库行的 SourceLineId 指向采购行，原始依据指向供货绑定。
- 最终出库行原始依据指向 PackingList 行。
- 客供件消耗行原始依据指向消耗明细。
- 一条业务依据对应一条库存行，不得为减少行数而丢失追溯关系。

### 5.4 完成门禁

- 并发 PackingList 不超交付、不重复使用采购容量、不产生负库存。
- 非标行只形成正式交付净额，不生成库存事实。
- 同 CommandId 同内容重试只返回首次结果；不同内容冲突。
- WPF 明确展示阻断、警告与提交结果，不在客户端计算权威库存。

## 6. 阶段四：整单反向

### 6.1 API 与权限

新增 POST /api/shipping/packing-lists/{uid}/reverse，使用独立权限 Shipping.PackingList.Reverse。命令提交原单版本、Reverse Preview Token、原因和稳定 CommandId。

### 6.2 事务顺序

1. 锁定 Posted PackingList、全部有效绑定/消耗明细、生成单据和相关库存键。
2. 校验本单所有生成事实仍可整单反向。
3. 先反向最终客户出库和客供件消耗。
4. 再反向本单自动入库。
5. 使对应绑定与消耗明细退出有效数量，更新 PackingList 为 Reversed。
6. 写入操作日志和幂等结果。

任何依赖不可反向时整单拒绝，不允许部分成功。整单反向只纠正本单系统事实，不代表客户已经实际退货。

### 6.3 完成门禁

- 库存、采购有效绑定和 GrossDemand 正式交付净额同时恢复。
- 原单、反向单据、流水和操作日志完整保留。
- 重试不重复反向；并发 Post/Reverse 只有一个合法状态迁移成功。

## 7. 分层与交接

- Contracts：Query、Command、Preview Result、执行 Result 分离，保持 netstandard2.0 兼容。
- Core：单据、供货绑定、消耗明细和仓储接口；不依赖 Application/Infrastructure。
- Application：权限复核、业务校验、事务编排、幂等和状态迁移。
- Infrastructure：Dapper 查询、锁定、正式净额聚合和原子写入；不承担业务准入决策。
- WebApi：显式路由、认证授权和 HTTP 映射；不直接写 SQL。
- WPF：展示、用户确认和命令协调；不缓存或推导权威余额。

采购确认快照是供货与客供件执行依据；库存只维护仓库产品事实；最终出库不重复承担 GrossDemand 履约归属。

## 8. 总体验收

必须覆盖：任意 GrossDemand 类型、同客户校验、跨客户拒绝、非标无库存过账、库存充足、采购缺口、多采购行建议、采购容量不足、确认快照缺失、客供件累计耗用、最后一批尾差、并发超交付、并发采购容量、幂等重试、事务中途失败全回滚和整单反向。
