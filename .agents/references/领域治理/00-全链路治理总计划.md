# 全链路领域治理总计划

> **2026-09-07 口径修正：** 以《业务架构总纲》开头“采购来源可选与独立供货修正”为准。本文旧“采购必须对应一个销售单”、强制销售归属迁移及相关验收/提示词已撤销。采购可选关联来源需求；无上游的独立采购可正常入出库，PL 可选择其供货，交付要求仍来自来源需求。客供件池仅在实际消耗时明确归属并经用户批准，不得将订单池约束提升为所有采购的必填条件。阶段 02 使用已修订提示词。

日期：2026-09-06。权威业务规则见 [业务架构总纲第 24 节](../业务架构总纲.md#24-订单级客供件池与领域解耦2026-09-06)。本组文件是实施方案，不是已完成报告或数据库变更授权。

## 范围与基线

覆盖销售、需求计划、采购与执行 BOM、入库、供应商库存、PackingList、出库和履约查询。当前工作区另有系统设置代码、测试和计划书改动，本次不触碰。后续执行者重新检查 Git 与共享文件所有权，不因本计划而启动并行任务。

已核对相关 Core 实体，包括 GrossDemand、NetDemand、NetDemandAllocation、DemandExecutionLink、采购头行/确认行节点、入出库头行、余额流水、PL 头贡献行、销售行、WarehouseSite 与 Bom；认证和字典等无关实体不作本次重构对象。抽查了入库来源、PL 来源和销售发货 SQL；未将字段存在认定为完整业务闭环。

## 执行顺序

| 顺序 | 方案 | 交付与依赖 |
|---|---|---|
| 0 | [来源需求汇聚与交付](00A-来源需求汇聚与交付治理.md) | 销售/品质售后幂等接收、版本变更、PL 统一可交付契约；必须先于 PL |
| 1 | [销售领域](01-销售领域治理.md) | 固定销售事实与来源需求接收契约；来源需求提供交付额度；最终聚合待出库改造接线 |
| 2 | [采购与执行依据](02-采购与BOM执行依据治理.md) | 复用独立采购，单一销售单归属、采购可收能力、确认组成；依赖销售身份 |
| 3 | [入库与订单池](03-入库与订单池治理.md) | 订单池持久化、入库来源解耦、迁移与统一过账；依赖采购交接 |
| 4 | [PackingList 与出库](04-PackingList与出库治理.md) | 客户交付/消耗分流、用户确认、原子过账；依赖前三项 |
| 5 | [需求计划](05-需求计划治理.md) | 脱离库存链后简化 Allocation 与承接协议；不先删表 |
| 6 | [联验与切换](06-全链路验收与切换.md) | 销售履约最终接线、前端贯通、历史兼容、回归与部署说明 |

各领域都采用“后端/契约 → 前端 → 本领域验证”小切片。第 1 阶段不建立虚构返回数据；最终数据接线明确留给第 6 阶段。新增兼容字段不能无期限双写两套权威，记录迁移截止条件。

## Core 字段与关系处置矩阵

| 实体/字段 | 当前事实 | 目标处置 |
|---|---|---|
| SalesOrderLine.SalesOrderId / Uid / Qty | 销售头行与数量存在 | 保留，作为交付身份/数量依据，修订与并发按既有规则 |
| GrossDemand.SourceType/Uid/LineId | 来源已分离，包含拆解状态 | 来源需求汇聚销售/品质售后并作为 PL 必需交付锚点，审计幂等/版本缺口；不要求用户逐层操作 |
| NetDemand.GrossDemandId / BomPath / Parent/RootNetDemandId | 一对多拆解与树证据 | 保留来源和结构解释；父关系不表示库存分配 |
| NetDemand.DeliveryTargetNetDemandId / DeliveryMode | 父件送达含义 | 停止作为执行事实；先迁移收货消费者，再评估保留为建议或废弃 |
| NetDemand.GrossQty / NetQty | 未做库存抵扣 | 不新增 MRP；审计消费者后决定去重，不机械删除历史数量 |
| Allocation.PlannedQty / Supplier / DeliveryTargetAllocationId / Revision | 当前完整计划/替代链 | 先缩为计划域依赖；是否物理收敛由阶段 5 决定，不直接删历史 |
| Link.NetDemandId / AllocationId / TargetHeadId/LineId / AllocatedQty/ReleasedQty | 已有数量承接关系 | 优先复用，新增链以物料需求及采购行承接，旧 Allocation 锚点迁移后可选/历史；严格贡献守恒 |
| PurchaseOrderHead.DemandSourceType/Uid / CustomerId | 通用来源与客户，没有专门 SalesOrderId 属性 | 验证并固定单一销售订单权威；复用或迁移选一个方案，不并列两个来源权威 |
| PurchaseOrderLine.UnlinkedQty | 与需求贡献无关数量，独立采购可全部未关联 | 保留此语义；无 Link 不等于无销售订单 |
| PurchaseOrderLine.DeliveryWarehouseSiteId | 已有独立收货仓库 | 作为执行目标，保留仓库快照；不由活动 Allocation 回推 |
| PurchaseOrderLine.DeliveryTargetAllocationId | 仍有旧父计划关联 | 兼容历史，不作新入库/客供件池前提，迁移后再清理 |
| PurchaseConfirmationLine/Node | 已有确认批次、指纹、组成路径、比例、消耗仓库 | 复用，不新造第二套 BOM 快照；父节点解释用量，不占有库存 |
| InboundDocumentLine.SourceType/SourceUid | 来源标识存在；旧查询有 Link/Allocation 来源 | 类型与真实采购行一致，旧值显式映射；订单池归属需持久化，不能只保留订单号 |
| InventoryBalance / InventoryLedgerEntry | 仅仓库产品余额/流水，无订单归属维度 | 补订单归属事实及投影或扩展维度，择一；保持总账可重建和对账，未知单列 |
| PLContribution.GrossDemandId/NetDemandId/AllocationId | 非空 Guid；SalesOrderId/LineId 可空 | 新销售交付链反转为来源需求必要、物料需求/Allocation 可选；原始销售/售后头行由来源需求追溯；历史/其他来源不盲目设为非空 |
| PLContribution 与采购行 | 当前实体未见直接采购执行数量关系 | 增加窄的采购执行分配关系，支持一贡献多采购行；不能仅从 SKU 推断 |
| OutboundLine.AllocationId / PackingListContributionId | 当前单行强绑定计划及单贡献 | 计划改历史可选；共享池消耗保留一对多计算明细，不以单贡献冒充多个父件归属 |
| InventoryLedgerEntry.CommandId/ItemId/ReversalOfLedgerId | 已有幂等与反向锚 | 保留；订单池与总量同事务、原池反向，新增唯一约束须核对现有数据 |

本矩阵是字段组审计，不是全部 Core 字段删除清单。现有快照和供应商/客户商务字段无本轮删除授权。

## 偏差与已有成果

- DP-001/002/003、SO-003、INB-001/002/008、INV-006、PL-001/003/005、OUT-001 继续作为对应整改索引，实施时重新定位。

- BOM-004 的旧“无确认实体”描述已过时；现有实体不能证明 PL 已接线，应验证消费与事务后再关闭偏差。
- 新增订单池维度与强确认能力是目标缺口，不用 UI 上增加一个订单字段或确认按钮冒充后端闭环。

## 数据迁移与风险

采购来源、需求关联、入库来源类型、PL/出库关系、订单库存归属分别生成可预览映射。以稳定 Uid 和实际单据证据匹配，不按 SKU/同客户猜测。区分“明确无需求”与“历史关系未知”。核对旧采购量、净收货量、客户出库量、客供件净耗和总库存守恒；多解记录隔离人工核实。

先兼容读取与补字段，再回填有证据数据，最后切换写入及查询；禁止第一步删旧字段。不得修改正式库存流水来伪装历史订单归属；补充归属证明或有审计的纠正必须与原流水可核对。生产迁移单独由用户执行或明确授权。

## 所有执行提示词的共同约束

最新口径以业务总纲第 24.7 节为准：来源需求（GrossDemand）是必需交付汇聚口，物料需求（NetDemand）及 Allocation 对发货可选；销售只定义销售事实。所有旧“无需求”描述在独立采购语境不构成 PL 绕过来源需求的授权。阶段 0 先完成来源能力，阶段 5 只做剩余计划精简。

先读 AGENTS.md、当前角色/Workflow/必要 Skill、业务总纲第 24 节和本领域方案。禁止启动子 Agent、全仓无差别读取、重复创建已有功能。业务接口与 DTO 必须核对真实调用方；新增源码补中文职责注释。模型名称不要由文档强制覆盖用户设置。

实施提示词是将来用户复制后的范围授权，本次文档任务不执行它们。每阶段先复核前置成果，缺关键契约时只推进独立工作并报告缺口，不伪造成功；检查 diff、运行最小相关构建与有意义测试，不弱化有效断言。每阶段记录实际文件、契约、迁移、测试、未决事项，不能只说“阶段完成”。

## 尚需实施时明确的有限事项

普通消耗确认默认不批准负库存；若用户需要改变例外口径再单独确认。Allocation 物理删除、订单池具体存储方案及历史不明归属需在相应阶段给出证据和决策，不能从本次方向授权推导删除/猜测权限。未来生产、无销售来源备货和完整售后模块不在本轮新增范围。
