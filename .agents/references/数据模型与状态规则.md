# 数据模型与状态规则

## 主键与业务键

新模型优先使用 `Uid` 作为技术主键。

业务编码用于人工查账和唯一约束，例如：

- `Sku`
- `CustomerCode`
- `SupplierCode`
- `WhseCode`
- `OrderNo`
- `ReceiveNo`
- `OutboundNo`
- `PackingListNo`

## 外键策略

跨模块追溯优先使用：

```text
Uid + 业务编码冗余
```

例如：

- `SourceUid`
- `SourceNo`
- `SourceLineId`
- `TargetHeadId`
- `TargetNo`
- `TargetLineId`

数据库侧以索引和唯一约束保障查询；跨模块一致性由 Application Service 校验。头行强父子关系可按模块补强数据库外键。

## 软删除

- 主数据默认软删除。
- 业务单据默认软删除。
- 已过账单据不靠删除解决。
- 库存流水不可删除。

## 库存模型

- `Inventory` 保存当前余额。
- `InventoryTransaction` 只新增，不修改，不删除。
- 错误通过反向流水或红字流水修正。
- 入库、出库、PackingList 过账必须生成正式单据和库存流水。

## 追溯模型

`DemandExecutionLink` 是净需求到采购/生产/外协/入库/出库的主追溯表。

`DependentDemand.TargetNo/TargetLineId` 只做快速入口，不替代正式追溯关系。

## 单据状态分层

不要把所有状态塞进 `OrderStatus`。

建议分层：

- `DocumentStatus`：草稿、有效、关闭、作废。
- `ConfirmStatus`：未确认、已确认、取消确认。
- `ExecutionStatus`：未执行、部分执行、已执行。
- `PostStatus`：未过账、已过账、已反过账、已红冲。
- `ChangeStatus`：正常、改单中、已变更。

展示状态可以汇总，但业务判断应使用明确执行节点和命令。

## 改单边界

- 未生成下游：可直接改上游。
- 下游草稿/未过账：允许删除或回退后重跑。
- 已确认但未生成库存流水：允许取消确认到安全边界。
- 已入库/出库/库存流水产生：必须反过账或红冲。
- 库存流水之后不允许靠删除下游来掩盖业务变化。
