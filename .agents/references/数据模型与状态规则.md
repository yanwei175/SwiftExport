# 数据模型与状态规则

## 权限五实体与关系（2026-09-27 目标）

`SysUser` 持有账号状态与凭据版本；`SysRole` 持有不可变 RoleCode、展示名、活动与内置标记；`SysUserRole` 只存用户/角色 Uid；`SysPermission` 持有稳定 PermissionKey 及目录展示元数据；`SysRolePermission` 只存角色/权限 Uid。角色名和权限显示名不是授权身份，关系表不冗余这些当前展示字段。用户名、RoleCode、PermissionKey 不复用，角色和权限不继承，用户没有直接授权关系。

RoleCode、PermissionKey 分别唯一；`SysUserRole(UserId,RoleId)` 与 `SysRolePermission(RoleId,PermissionId)` 对活动关系唯一，并为反向查询建立必要索引。关系均是逻辑外键，由 Application 校验存在、启停、软删除、可分配性和最后管理员边界。整组替换以用户/角色聚合 Version 为并发依据，事务内锁定与重验；数据库结构从 Core 元数据生成，不手改 Generated SQL。当前代码尚有直接权限表与旧字段，退出进度见[实施交接记录](../../docs/权限管理收敛实施/06-实施交接与Review记录.md)。

## 主键与业务键

新模型优先使用 `Uid` 作为技术主键。

业务编码用于人工查账和唯一约束，例如：

- `Sku`
- `CustomerCode`
- `SupplierCode`
- `WhseCode`
- `OrderNo`
- `ReceiveNo`
- `OutboundNo`
- `PackingListNo`

## 外键策略

跨模块追溯优先使用：

```text
Uid + 业务编码冗余
```

例如：

- `SourceUid`
- `SourceNo`
- `SourceLineId`
- `TargetHeadId`
- `TargetNo`
- `TargetLineId`

数据库不创建 `FOREIGN KEY`；包括头行关系在内均使用逻辑外键。数据库侧以索引、唯一约束和检查约束保障查询及局部不变量，关系存在性、一致性和删除边界由 Application Service 校验。

## 软删除

- 主数据停用与删除分开；历史引用保留，不能把软删除标志直接当已实现的停用机制。
- 业务单据默认软删除。
- 已过账单据不靠删除解决。
- 库存流水不可删除。

## 库存模型

主数据更名保持 Uid 和历史快照，专用命令记录影响与旧新编码；停用禁止新引用/增量承诺，但既有已确认合法单据仍按自身准入履行。不能统一删除有效性检查，也不自动停仓。产品有正式库存流水后冻结基础单位，余额为零不例外；详见 [主数据地图](模块能力地图/主数据模块能力地图.md)。

- `InventoryBalance` 保存 WarehouseSiteId + ProductId 的当前余额投影，只由统一过账服务更新。
- `InventoryLedgerEntry` 保存数量变化事实，只新增，不普通修改，不删除。
- 客户差异由 Product/SKU 主数据表达，库存余额、流水和客供件库存不增加客户或销售订单维度。
- 错误通过受控反向流水修正；不允许负库存。
- 标准产品 PackingList 正式过账必须生成必要自动入库、最终客户出库、客供件消耗和库存流水；非标行不产生库存事实。
- PackingList 自动单据以 TriggerPackingListId 标识，手工入出库页面不得处理。
- 本轮只规划 Draft、Posted、Reversed 与整单反向，不规划已过账修订或库存纠错。
- 真实错发保留实际出库，实际退回才增加库存；整单反向不等于客户实际退货。

## 追溯模型

统一语义：GrossDemand 为来源需求汇聚口，NetDemand 为物料需求。所有满足统一准入条件的活动 GrossDemand 都可作为 PackingList 来源，SourceType 只作快照与追溯。正式交付净额由有效已过账且未反向的 PackingList 行计算；最终出库只记录库存事实，不建立第二套来源履约权威。

BOM 只有单套当前结构，保存即生效；修改记录、需求拆解 revision、采购执行快照是不同事实，不建立版本选择/发布/切换。现有 BomVersion 仅保留兼容，不在本轮改表或重排值。需求拆解和独立采购确认各自固定实际采用的一致完整结构，既有消耗不读当前 BOM 重算；详见 [BOM 地图](模块能力地图/BOM模块能力地图.md)。

`DemandExecutionLink` 保存需求分配对执行单据行的贡献关系，不是所有入库的必填凭证。采购可以没有需求关联；入库先追到执行单据，有需求关系再沿 Link 追溯，禁止伪造关系。

来源 Uid 表达真实对象，不能用 Link Uid 冒称采购行 Uid。需求收货覆盖是查询投影，不保存为入库固定分摊、预留或需求收货缓存。数量及历史迁移边界见 [业务架构总纲](业务架构总纲.md) 第 13 节；地图按 [模块地图索引](业务模块能力与页面契约治理规则.md) 读取。

## 单据状态分层

销售单据生命周期、确认状态、行交付终止、商业修订、执行处置进度和查询履约分别表达，不能合成万能状态。全部发完不自动关闭；商业关闭允许执行处置未完成，不级联改采购。恢复走独立命令，不重置正式交付。详见 [销售地图](模块能力地图/销售模块能力地图.md)，本次不增补枚举或冻结修订物理表。

不要把所有状态塞进 `OrderStatus`。

建议分层：

- `DocumentStatus`：草稿、有效、关闭、作废。
- `ConfirmStatus`：未确认、已确认、取消确认。
- `ExecutionStatus`：未执行、部分执行、已执行。
- `PostStatus`：未过账、已过账、已反过账、已红冲。
- `ChangeStatus`：正常、改单中、已变更。

展示状态可以汇总，但业务判断应使用明确执行节点和命令。

## 改单边界

- 未生成下游：可直接改上游。
- 下游草稿/未过账：允许删除或回退后重跑。
- 已确认但未生成库存流水：允许取消确认到安全边界。
- 已入库/出库/库存流水本身需要纠错：通过合法反过账或红冲处理，保留原事实。
- 库存流水之后不允许靠删除下游来掩盖业务变化。

来源业务减少/取消不等于库存事实错误。需求按 [需求计划地图](模块能力地图/需求计划模块能力地图.md) 评估影响，暂停受影响的新承接；采购明确减量、取消或继续备货，已有合法收货不自动停止。当前需求、计划建议、历史执行承诺和差额分开，不通过删除历史凑平数量。
