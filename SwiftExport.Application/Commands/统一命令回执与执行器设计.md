# 统一命令回执与执行器设计

状态：首批已接入公共执行器与成功回执，入库、出库草稿的创建、修改、删除已迁移。真实 SQL Server 锁、唯一约束与原子性尚未完成隔离库验证；数据库未部署。其余模块仍按后续批次迁移。

## 1. 这个能力放在哪里

公共命令机制的归属目录为 `SwiftExport.Application/Commands/`，本文就放在这里。它为不同业务模块提供相同的执行协议，不属于某张页面或某一种单据。

现有业务服务继续使用 `Application/Interfaces/<模块>` 和 `Application/Services/<模块>` 的组织方式。Commands 是内部公共机制，接口与实现可以在能力目录内相邻放置，不再建立万能 CommonServices 或第二套事务框架。

当前首批文件布局如下；后续只在真实消费者需要时增加能力：


不新增通用 CommandController，不向客户端开放“传一个类型名即可执行任意命令”的接口。Core 不依赖 Application，Infrastructure 不引用 Application 中的执行上下文。

## 2. 先分清三个问题

“用 GUID”“放 HTTP Header”“结合用户身份”并不互相矛盾：

| 问题 | 本项目建议 |
|---|---|
| ID 怎么生成？ | 客户端在形成一次提交意图时调用 `Guid.NewGuid()` |
| ID 放在哪里传？ | 放在具体命令请求体的 `commandId` 字段，沿用现有 DTO |
| 服务端怎么判断重复？ | 按 CommandId 找回执，再比较真实用户、命令类型、请求目标和内容指纹 |

CommandId 不需要拼接用户名、日期、单号或操作名称，也不是整个请求的哈希。相同内容可能代表两次合法的新建操作，不能仅因内容相同就合并成一次。

`Guid.NewGuid()` 生成 UUID v4，适合作为本方案的随机命令身份；它不是密码或访问凭证。参见 [Microsoft Guid.NewGuid 文档](https://learn.microsoft.com/en-us/dotnet/api/system.guid.newguid)。

HTTP 请求头与请求体是两个不同位置。“请求体里的 Header”如果指 `Header.CustomerId` 这样的 JSON 对象，那是业务单头，不是 HTTP Header。CommandId 属于整个命令，放在顶层，不塞进单头对象。

有些 API 用 `Idempotency-Key` HTTP 请求头传同类标识，例如 [Stripe 的幂等设计](https://stripe.com/blog/idempotency)。这是传输约定的选择，不意味着必须从请求头生成 ID。本项目本期不新增该请求头入口，也不同时维护头、体两份身份来源。

## 3. 各种 ID 各管什么

| 名称 | 标识什么 | 谁生成或提供 | 同一命令重试时 |
|---|---|---|---|
| CommandId | 一次业务提交意图 | 客户端，第一次发送前生成 | 保持不变 |
| CorrelationId | 一次请求或调用链 | 追踪边界；当前中间件可接纳请求头或生成 | 新一次 HTTP 尝试使用新的标识 |
| BusinessOperationLog.Uid | 一条业务操作日志记录 | 服务端 | 重放不新增该条日志 |
| CommandReceipt.Uid | 一条回执记录的数据库主键 | 服务端 | 重放读取原记录 |
| 单据 Uid | 同一张业务单据 | 创建单据的业务用例 | 同一单据的多个命令都可引用它 |
| ActorUid | 当前真实操作者 | 服务端从认证上下文取得 | 必须符合原命令操作者约束 |
| CommandItemId | 命令内部一条不可重复的输出事实 | 客户端或模块按明确规则生成 | 对应事实的身份不变 |
| ExpectedVersion | 客户端提交所依据的单据版本，不是 ID | 从服务端读取后随命令提交 | 原命令重试保持原值 |

常说“CommandId 要与另一个 ID 分开”，通常是在说 CorrelationId。日志主键 Uid 也要独立，但它不是请求链路标识。

一次命令可以生成多条审计日志和库存事实，因此 CommandId、日志 Uid、CommandItemId 不应被强行一对一化。CommandItemId 也不是必须给所有普通 DTO 明细增加的字段。

示例：第一次过账已经提交，但响应丢失。

```text
第一次请求：CommandId = A，CorrelationId = R1
数据库提交：单据 + 库存事实 + 回执 C + 审计日志 L
客户端未收到响应

第二次请求：CommandId = A，CorrelationId = R2，内容保持原样
服务端读取回执 C，返回第一次的业务结果
不再修改库存，也不再追加日志 L
技术日志分别记录 R1、R2，并关联到 A
```

## 4. 客户端请求约定

以已有入库过账接口为例：

```http
POST /api/inventory/inbounds/{uid}/post
Authorization: Bearer <登录令牌>
X-Correlation-ID: <本次调用标识>
Content-Type: application/json

{
  "commandId": "45d517bc-e411-4baf-8d30-4d5d127f2dd0",
  "expectedVersion": 7
}
```

上面的地址仅说明请求组成；具体路由保持对应 Controller 与 Refit 契约，不以本文示意重命名路由。

客户端应在用户确认提交时生成 CommandId，并保存“ID + 完整请求快照”，然后发送。不要在自动重试委托、HTTP Handler 或每次点击重试时重新生成。

- 网络超时、断线、500、503、COMMAND_BUSY：保留原身份和内容，先确认或重试原命令。
- 已确认业务拒绝、没有待确认的早先提交，用户修改内容重新提交：形成新命令、新 CommandId。
- 已成功后再次执行另一个业务动作：新命令；例如保存与过账、过账与反过账分别有自己的 ID。
- COMMAND_CONFLICT：停止执行并核对原身份与内容，不自动换 ID 绕过冲突。
- 应用重启后的恢复需要客户端持久化待确认请求；仅保存在 ViewModel 内存不能承诺重启恢复。初期不实现通用离线队列，也不声称已经覆盖该能力。

服务器拒绝 Guid.Empty 或缺少 CommandId 的正式命令，不在收到请求后偷偷补一个随机 ID。

## 5. 用户身份与查重范围

本项目当前按单业务数据库设计：`CommandReceipt.CommandId` 在该数据库中全局唯一，不按用户或模块重新划分唯一键。

这意味着相同 ID 被用于其他用户、操作或目标时，不能作为一个全新的命令执行。权限检查通过后，回执身份不符统一返回 COMMAND_CONFLICT，不泄露原用户或原结果。

ActorUid 必须由 ICurrentUser 得到，不能信任客户端传入的用户字段。CommandType 必须由服务端用例确定，例如 `Inventory.Inbound.Post`，不取客户端任意字符串或可能重命名的 C# 类全名。

“用户 + 操作 + CommandId”作为复合查重键是其他系统可以选择的策略，并非 GUID 的组成方式。本项目选择全局唯一，是为了避免同一个 ID 换用户或操作后被当成新命令。

若将来引入独立租户或多数据库，再明确身份与唯一范围；本期不添加无实际需求的 TenantId。拥有 CommandId 也绝不等于有权读取结果。

## 6. 回执实体与表的最小设计

实体名和表名均为 `CommandReceipt`，专用仓储仅保存成功提交的不可变回执。

| 字段 | 建议类型 | 含义 |
|---|---|---|
| Uid | Guid | 回执自身主键，与 CommandId 独立 |
| CommandId | Guid | 客户端命令身份，非空、全局唯一 |
| ActorUid | Guid | 认证得到的操作者 |
| CommandType | 有长度上限的字符串 | 服务端定义的稳定用例标识 |
| RequestTargetUid | Guid，可空 | 请求明确针对的对象；创建命令允许为空 |
| FingerprintVersion | int | 输入规范化与指纹协议版本 |
| RequestFingerprint | 固定长度字符串 | 规范化输入的 SHA-256 摘要 |
| ResultVersion | int | 首次结果快照的结构版本 |
| ResultJson | JSON 字符串 | 首次成功的最小业务结果，不保存 HTTP 响应头 |
| RecordedAtUtc | UTC 时间 | 同事务写入回执的时间，不冒充数据库精确提交时刻 |

结果中的新建单据 Uid 来自业务执行，不与 RequestTargetUid 混为一谈；一个命令生成多张单据时，由其专用结果 DTO 表达，不把通用回执扩展成万能业务表。

沿用项目 Uid 主键规范。若复用 BaseEntity，Version/IsDeleted 等继承字段不开放普通 CRUD：回执只追加，查重不加 `IsDeleted=0`，CommandId 唯一约束不做软删除过滤，禁止靠软删除释放命令身份。

数据库应有 CommandId 唯一索引、非空身份与非空指纹约束、ResultJson 的 JSON 校验及结果版本约束。只通过受控仓储写入，并按实体元数据规范表达不可变要求。不能只靠先查再插或内存缓存防重。

本期不创建 Pending/Failed 状态表、后台扫描器或重试任务队列。执行中的竞争由事务持有的命令锁控制；回执与业务写入成功后一起可见，失败一起回滚。

因此，该方案保证成功命令可重放；失败未提交时不会冻结一个永久失败回执。客户端仍不得任意改变同一 ID 的含义，但没有已提交回执时，服务端不能声称已记住此前每一次失败请求的指纹。这是本期明确的语义边界。

回执不设置随意到期删除策略。删除回执会损失对旧 CommandId 的查重能力；将来如需归档，必须仍能阻止旧命令被当成新命令执行。

## 7. 指纹不是 CommandId

CommandId 用于找到“哪一次命令”；指纹用于验证“内容有没有换”。

```text
身份核对：ActorUid + CommandType + RequestTargetUid
指纹输入：协议版本 + 上述身份 + 规范化业务输入
不包含：CommandId 本身、CorrelationId、JWT、日志 Uid、发送时间
```

ExpectedVersion、数量、原因、业务日期、PreviewToken 等影响执行语义的字段必须纳入业务输入。路由 uid 也必须进入身份核对，不能只哈希 body。

不得直接哈希原始 HTTP JSON：空格、属性顺序、数值格式等不应造成不同意图。模块提供明确输入投影，公共组件做确定性编码与哈希；只有业务上无序的集合可以排序，不能擅自排序具有顺序含义的明细，也不能把所有 null、空串或小数精度随意视为相同。

已存回执的指纹和结果版本必须仍可解释；升级期间不能因无法解码就再次执行业务。遇到不能识别的历史结构应停止重放、返回结果未知并人工处理，或在发布前完成明确的数据转换。

## 8. 执行器的事务边界

1. 用例确定 CommandType、操作者及细权限；完成基础格式和数据访问授权检查。不能因为有回执而跳过当前权限。
2. 公共执行器确认自己是最外层事务所有者，复用当前 request scope 的 DbSession。首批草稿使用连接默认隔离级别；后续命令按一致性风险明确事务策略，不统一写死 Serializable。
3. 通过回执仓储取得事务级命令锁；锁键仅由已解析的 CommandId 生成，同一 ID 在各模块使用同一锁空间。
4. 查询回执。相同身份和内容返回首次业务结果；不同身份或内容返回 COMMAND_CONFLICT；无法解码返回 OUTCOME_UNKNOWN，禁止重新执行。
5. 无回执时，由模块按稳定顺序锁定业务资源，校验 ExpectedVersion、状态、来源、数量及必要的事务内授权条件。
6. 模块写单据、库存或其他业务事实，并根据真实变更追加审计。执行器不猜测审计文案或变更字段。
7. 模块返回最小成功结果；执行器写回执，然后共同提交。确认提交成功后返回。
8. 失败安全回滚；清理异常不能覆盖原异常。提交结果无法确认时返回 OUTCOME_UNKNOWN，客户端保留原命令。

已存在回执的重试先走重放，再做首次执行所需的当前版本判断；否则第一次成功已增加版本，原请求重试会被错误地判为过期。当前身份和访问授权仍须先检查。

回执仓储负责 SQL Server 事务级命令锁与锁结果判定，执行器将竞争超时映射为 COMMAND_BUSY。唯一索引是最终防线；发生唯一键竞争后，必须结束失败事务并在有效事务中读取和核对回执，不能直接当作成功。

公共执行器在最外层 Application 用例的委托下管理事务，不允许内部服务再次调用执行器开启嵌套提交。PackingList 编排自动入出库时，只由外层命令使用执行器；内部库存端口继续使用现有事务和明细唯一约束。统一回执不能替代库存事实的 CommandItemId 防重。

执行器不统一写死 Serializable，不决定业务锁集合，不处理 HTTP，不发送外部消息，也不自动重试整个业务流程。外部副作用不在一个 SQL 事务的保障范围内，本期不引入 Outbox 或消息总线。

取消只在可回滚阶段响应。已确认提交不能再返回“取消且未执行”；回执用于恢复提交后丢失的响应。所有仓储调用透传 CancellationToken。

## 9. 审计继续承担什么

BusinessOperationLog 保留 CommandId，作为从业务历史关联命令的入口。ChangedFieldsJson 恢复为实际变更摘要，RelatedObjectsJson 恢复为相关单据或流水摘要。

日志 CorrelationId 来自本次追踪上下文，不能再由 CommandId 字符串代替。重放只记录技术访问日志，不重复写成功业务审计；原业务日志关联首次执行时的 CorrelationId。

业务日志条数由业务事实决定，一个命令允许多条。回执查询不再经过 IBusinessOperationLogRepository，也不解析审计 JSON 恢复返回值。

## 10. 当前事实与实施顺序

当前源码：通用 `CommandReceipt`、专用仓储和 `BusinessCommandExecutor` 已存在，入出库草稿六类命令已切换，审计 JSON 不再承担这些命令的重放。采购仍有 `ProcurementCommandReceipt`；入出库过账/反向、库存内部端口、箱单、售后、销售、来源需求、物料需求及采购进度等仍调用审计命令查询，不能提前删除共享接口。

建议实施批次：

1. 首批已建立回执 Entity/元数据、专用仓储和执行器，并接入入库、出库草稿；两份草稿的旧私有执行框架已移除。
2. 隔离 SQL Server 上的命令锁竞争、唯一约束和跨业务写入的原子性仍待验证；单表脚本仅供审阅，未执行。
3. 后续接入采购及其余外层正式命令；内部端口保留事务参与职责，不机械增加独立回执。
4. 全部消费者切换并验证后，删除采购专用回执与仓储方法、审计回执查询接口和旧 JSON 重放逻辑；直接改写相关文档。
5. 再按查询、来源、草稿、过账和反向拆业务服务与接口。

结构变更以 Entity 元数据为源，空库基线由生成器维护。独立的[命令回执建表脚本](数据库/命令回执独立建表.sql)只摘取该表的结构，供选定目标数据库部署审阅，未执行，也不迁移历史结果。现有业务库若需切换，须另行确定一次性数据转换；不能把缺失新回执等同于旧命令从未执行。删除旧代码不授权删除业务数据。

## 11. 验收标准

- 相同 ID、身份和内容并发到达，最多提交一次业务写入，重复请求返回首次结果或 COMMAND_BUSY。
- 已成功的同一 ID 更换用户、操作、目标、ExpectedVersion 或业务内容，不执行第二次。
- 成功后的网络中断，重试使用原 ID 和旧 ExpectedVersion，返回原结果，不重复生成单号、库存事实或审计。
- 业务写入、审计或回执任一步失败，全部回滚；提交确认丢失不得谎称未执行。
- 当前权限不足时不披露原回执；客户端伪造 ActorUid 无效。
- RequestTargetUid 为空的新建请求也能重放服务端生成的单据身份。
- 内部库存端口不提交外层事务；外层失败不留下孤立回执。
- CorrelationId 可区分两次调用，CommandId 可关联同一意图，日志 Uid 保持独立。
- JSON 排序和等价格式不误报冲突；真正业务差异必须冲突；不支持的结果版本不得重执行业务。
- Preview 零写入，不创建回执；普通查询不经过命令执行器。
- 最终无旧回执读取分支、无失去消费者却保留的接口、无已删除旧协议的文档要求。

## 12. 设计依据与已知文档偏差

项目依据：业务命令 Skill、事务与预览规则、后端文件组织 Skill，以及真实采购、入出库实现。回执属于基础设施协议，不能用它推断全部业务流程已正确。

当前业务命令参考文档仍出现 VALIDATION_ERROR、IDEMPOTENCY_CONFLICT；实际公共错误码已为 VALIDATION、COMMAND_CONFLICT。本设计使用实际统一契约，实施时同步更正相关规则。本次不顺带修改 Skill。

- [Stripe：HTTP 幂等键设计](https://stripe.com/blog/idempotency)
- [Stripe：幂等请求协议](https://docs.stripe.com/api/idempotent_requests)
