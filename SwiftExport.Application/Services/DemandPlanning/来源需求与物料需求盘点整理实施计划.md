# 来源需求与物料需求盘点整理实施计划

日期：2026-09-24。状态：第一至第五批已分别实施并验证；后续独立协议批次待实施。

## 1. 目标与范围

一起规划来源需求和物料需求，先整理来源，再整理物料，最后收拢仓储和 HTTP 契约目录。盘点阶段由 planner 使用业务规划工作流及 backend-file-organization 技能；第一批实施由 backend 使用后端 API 工作流完成。

保留五层架构，以文件夹说明真实能力。不机械套用 Draft、Confirmation、Posting：需求模块实际拥有查询、手工维护、来源接收、物料建立、回退和退出评估。

销售、售后、采购、Shipping 只迁移直接依赖和测试替身，不在本轮重构其业务。没有业务库，不连接 SQL Server/LocalDB、不运行建表、种子或数据迁移。保留其他任务未提交改动。

已确认的公共能力差异：

- 物料建立和回退已有 CommandId，第三批已改用 `CommandReceipt`；`BusinessOperationLog` 只记录可读业务审计。
- 来源接收也从 BusinessOperationLog 重放，却必须参加销售/售后事务。现有 BusinessCommandExecutor 明确拒绝已有事务，不能直接嵌套。
- 手工创建/修改/关闭、推荐供应商更新没有 CommandId；接公共回执需要请求协议和客户端一起改，不能服务端临时生成 ID 冒充安全重试。
- `PermissionKeys` 已有 `ModuleDemandPlanningAccess` 及独立的物料建立、回退操作键；两项正式命令在 Application 边界检查独立权限，来源交付仍检查模块访问。其他需求入口的权限边界本批未扩展。
- `MaterialDemandEstablishmentContractTests` 已移除旧审计重放断言，新增真实服务入口和公共执行器的内存行为验证。
- 需求能力地图包含历史追加说明，其中“自动消耗尚未实现”等描述可能落后于现有 Shipping/Inventory 实现。收尾直接修正相关正文和失效说明，不再追加相互冲突的版本声明。

## 3. 必须保持的业务和事务边界

| 入口 | 当前事务所有者 | 本轮约束 |
|---|---|---|
| 销售/售后确认 → ReceiveAsync | 销售/售后外层 | 来源参与同一事务，不提交、不另开事务 |
| 来源取消确认/关闭 → 退出评估 | 销售/售后外层 | 同时消费物料历史证明和 Shipping 交付证明，证明缺失则阻断 |
| 手工创建/修改/关闭 | 手工来源用例 | 保持原子性，活动物料存在时禁止直接改/关 |
| 物料建立 | 建立用例的 `BusinessCommandExecutor` | 整个 Items 一次事务，按 GrossDemandId 排序加锁；不是按来源部分成功 |
| 物料回退 | 回退用例的 `BusinessCommandExecutor` | 整批成功或失败；活动 Link 剩余贡献大于零即阻断 |
| 推荐供应商修改 | 建议维护用例 | 保留版本检查、相同值不递增版本、空值清除语义 |
| 需求转采购 | 采购用例 | 保留每来源事务、允许部分成功及 ExecutionRequestId/CommandItemId 协议 |

来源身份、SourceVersion、GrossDemand.Version、DecompositionRevision 各司其职，不合并为一个 Version。来源接收不自动拆 BOM；物料建立不自动采购。采购草稿已形成 Link，取消确认不释放，删行/作废才释放。退出不级联反向采购或库存。
