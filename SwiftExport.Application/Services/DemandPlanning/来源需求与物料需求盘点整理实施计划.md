# 来源需求与物料需求盘点整理实施计划

日期：2026-09-24。状态：第一批已实施并验证，第二批起待实施；下文目标目录不代表后续批次已完成。

## 1. 目标与范围

一起规划来源需求和物料需求，先整理来源，再整理物料，最后收拢仓储和 HTTP 契约目录。盘点阶段由 planner 使用业务规划工作流及 backend-file-organization 技能；第一批实施由 backend 使用后端 API 工作流完成。

保留五层架构，以文件夹说明真实能力。不机械套用 Draft、Confirmation、Posting：需求模块实际拥有查询、手工维护、来源接收、物料建立、回退和退出评估。

销售、售后、采购、Shipping 只迁移直接依赖和测试替身，不在本轮重构其业务。没有业务库，不连接 SQL Server/LocalDB、不运行建表、种子或数据迁移。保留其他任务未提交改动。

已确认的公共能力差异：

- 物料建立和回退已有 CommandId，但从 BusinessOperationLog 的 ChangedFieldsJson/RelatedObjectsJson 读取结果和指纹。
- 来源接收也从 BusinessOperationLog 重放，却必须参加销售/售后事务。现有 BusinessCommandExecutor 明确拒绝已有事务，不能直接嵌套。
- 手工创建/修改/关闭、推荐供应商更新没有 CommandId；接公共回执需要请求协议和客户端一起改，不能服务端临时生成 ID 冒充安全重试。
- 当前 PermissionKeys 有 ModuleDemandPlanningAccess；来源交付显式检查该权限，其他上述服务未发现同等显式检查。不能将此描述为整个系统完全无认证，也不能自行发明细权限。
- MaterialDemandEstablishmentContractTests 仍断言存在 GetByCommandAsync；回执改造时需替换成新的行为保障，不能仅删掉断言让测试通过。
- 需求能力地图包含历史追加说明，其中“自动消耗尚未实现”等描述可能落后于现有 Shipping/Inventory 实现。收尾直接修正相关正文和失效说明，不再追加相互冲突的版本声明。

## 3. 必须保持的业务和事务边界

| 入口 | 当前事务所有者 | 本轮约束 |
|---|---|---|
| 销售/售后确认 → ReceiveAsync | 销售/售后外层 | 来源参与同一事务，不提交、不另开事务 |
| 来源取消确认/关闭 → 退出评估 | 销售/售后外层 | 同时消费物料历史证明和 Shipping 交付证明，证明缺失则阻断 |
| 手工创建/修改/关闭 | 手工来源用例 | 保持原子性，活动物料存在时禁止直接改/关 |
| 物料建立 | 建立用例 | 整个 Items 一次事务，按 GrossDemandId 排序加锁；不是按来源部分成功 |
| 物料回退 | 回退用例 | 整批成功或失败；活动 Link 剩余贡献大于零即阻断 |
| 推荐供应商修改 | 建议维护用例 | 保留版本检查、相同值不递增版本、空值清除语义 |
| 需求转采购 | 采购用例 | 保留每来源事务、允许部分成功及 ExecutionRequestId/CommandItemId 协议 |

来源身份、SourceVersion、GrossDemand.Version、DecompositionRevision 各司其职，不合并为一个 Version。来源接收不自动拆 BOM；物料建立不自动采购。采购草稿已形成 Link，取消确认不释放，删行/作废才释放。退出不级联反向采购或库存。

验收：来源接收重放、同版本不同内容、旧版本、退出证明缺失、活动物料阻断及交付阻断；新增只读拆分无需机械编写镜像测试。

4. 保留整批事务、既有审计重放与错误码，先验证结构迁移。删除 INetDemandManagerService/实现及旧宽建立接口方法。

### 第三批：已有 CommandId 的物料命令接公共机制

范围仅建立与回退。使用 CommandPipeline、自动扫描 Validator、BusinessCommandExecutor、CommandReceipt；事务隔离级别保持原值。成功业务、审计、回执同事务，回执失败整体回滚。

建立指纹包含按 GrossDemandId 排序的 Items、SourceDemandVersion、SourceVersion；回退包含排序后的 Items、DecompositionRevision 和 Trim 后原因。公共执行器已纳入操作人/命令类型，不能另写一套哈希框架。不得改写客户端命令对象进行规范化。

回执应先于会随业务变化的版本/状态检查读取，以保证首次成功后重试仍能返回原结果。命令类型分别固定为 DemandPlanning.Material.Establish 和 DemandPlanning.Material.Rollback；集合命令目标使用 null，由完整集合指纹确定身份。

删除这两项命令的审计回放、结果反序列化和自有事务包装；审计仍保存可读业务摘要。无旧业务库，不做审计历史回执迁移，不新增表。来源接收的事务内回执另见第七批，不得顺手嵌套执行器。

本批实施前需确定权限方案；不能借接入 Pipeline 私自扩大或缩小权限。错误码迁移需列旧码与统一码对应，并检查直接消费者；不是无行为变更的文件移动。

验收重点：同 ID 同输入重放、排序变化等价、同 ID 改内容/操作人冲突、业务失败和回执失败均回滚、取消清理、旧版本重放成功与新命令版本冲突区分。

### 第四批：仓储按读模型与写事实拆分

按第 4 节的方法归属拆接口和实现。迁移需求各服务、采购 PurchaseDraftCreationService、PurchaseDraftPreviewService、PurchaseDraftCandidateService、DI 和全部替身后删除旧宽仓储。

保留 SQL 字段、过滤、排序、UPDLOCK/HOLDLOCK、事务传递和稳定加锁顺序。采购创建仍使用同一 DbSession，预览不得写入。ExecutionLink 仓储保持既有窄接口，不额外扩张。

验收：来源与物料分组、候选完整性、剩余贡献公式、修订锁、来源退出 SQL、采购预览及创建直接消费者；只做静态 SQL 和内存替身验证，不声称真实并发已经验证。

### 第五批：Controller、DTO、Refit 和文档收尾

Controller 按 Sources/Query、Sources/Manual、Sources/Delivery、Materials/Query、Materials/Establishment、Materials/Reversal、Materials/SupplierSuggestion 归位；允许相关查询共用一个 Controller，不为每方法造类。

核对现有 15 项 HTTP 动作：来源 6、物料 7、交付 2。保持 HTTP 方法、完整路径、参数、返回类型、Refit BaseAddress 和方法签名。保持交付已有权限边界，避免纯迁移取消防护。

拆 ManualGrossDemandRequests.cs；DTO 与 Refit 按能力物理归位但保留公开 namespace。同步静态测试的路径，保留其业务断言。相关旧文档直接替换失效描述，旧接口/文件无消费者后删除，不追加兼容转发。

验收：15 项路由对照、Contracts 构建、旧类型引用清零、实际 diff、文档链接。结构批次不用全量 WPF/数据库测试。

### 后续独立批次：无 CommandId 的公开写入口（本轮不实施）

手工创建/修改/关闭与建议供应商修改共有 4 项。若批准统一协议，DTO 增加 CommandId，客户端一次业务意图生成一次 ID、未知结果重试沿用原 ID，输入变更后新建意图；同步 Refit/调用方和必要测试。保留现有 Version 字段，不机械改名 ExpectedVersion。

用户已确认先拆职责、命令协议另批实施。因此本项另立计划，不纳入本轮实施；不因其他批完成而宣称这些入口已有持久化幂等。不得服务端生成随机 ID 后声称支持客户端安全重试。

### 第七批：来源接收事务内回执与历史兼容清理（设计门禁）

先清点销售/售后的外层命令回执和传入 CommandId 的生成位置，再确定来源子命令身份。公共 CommandReceipt 按 CommandId 全局查找，父子复用同一 ID 会冲突；不能简单将原审计读取替换成同 ID 的公共回执。

优先评估由外层确认命令承担最终回执、来源只参与事实写入；只有确有独立子命令重试需求，才设计共享事务中的回执机制。不得让内层提交外层事务，也不得取消现有幂等保障后等后续任务补齐。设计确定前保留现行接收保障，并明确尚未收口，销售/售后大重构仍不在本轮。

SourceDemandReceptionService 存在 LegacyBusinessContentMatches 历史空版本补齐逻辑。用户明确不保留旧模块兼容：实施时证明销售/售后现行写入均提供来源版本后删除历史兼容路径及对应说明；手工来源没有上游版本是合法业务，不能因此把所有 SourceVersion 改成非空。只删除已证明属于历史兼容的行为，不删除当前合法入口。
