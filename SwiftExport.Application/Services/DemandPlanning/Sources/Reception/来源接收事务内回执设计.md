# 来源接收事务内回执设计

日期：2026-09-24。状态：已按审核意见完善，待分批实施，本文不代表代码已完成。范围为销售、售后确认的 Confirmation 切片、客户端确认重试及 `ISourceDemandReceptionService.ReceiveAsync` 回执职责收口；来源退出、关闭、查询及其他需求命令继续按各自现状处理。销售、售后其余切片另批规划，不因本次只做确认而取消后续模块重构。

## 1．业务边界与当前证据

销售或售后认可实物要求后，同一业务提交既改变来源单的确认状态，又创建或更新 `GrossDemand`。只有两部分一起提交，才能把确认结果告诉调用方。`ReceiveAsync` 是事务参与者：先要求请求级 `DbSession.Transaction` 已存在，随后锁定活动来源行、核验身份与来源版本、写入来源事实和审计；它不创建、提交、释放或清空事务。销售服务以连接默认隔离级别开启外层事务，售后写命令显式使用 `Serializable`。未来不能在来源服务内嵌套现有 `BusinessCommandExecutor`，因为该执行器明确拒绝已存在的事务。

当前仅有两处生产 `ReceiveAsync` 调用：`SalesOrderDetailService.ConfirmAsync` 和 `AfterSalesService.ConfirmDemandAsync`。销售取消确认、关闭及草稿删除分别调用 `CancelConfirmationAsync`、`ClosePendingAsync`、`HasActiveAsync`；售后取消确认、作废分别调用 `CancelConfirmationAsync`、`HasActiveAsync`。这些方法没有接收命令回执，不能随接收改造而机械纳入子回执。Controller、Refit 和 WPF 只调用销售/售后外层 HTTP 用例，没有公开的来源接收 HTTP 入口。

| 外层入口及来源动作 | CommandId 生成与父子关系 | 当前回执所有者及事务所有者 | 失败与重试、审计职责 |
|---|---|---|---|
| 销售 `ConfirmAsync` → `ReceiveAsync` | `SalesOrderManagerViewModel.CreateConfirmCommand` 与 `SalesOrderDetailViewModel.CreateConfirmCommand` 各在调用时 `Guid.NewGuid()`；服务把该 ID 原样传给来源。来源无独立子 ID。 | 销售确认没有自身的持久化确认结果；来源 `BusinessOperationLog(Module=SourceDemand, Operation=Receive, CommandId=父 ID)` 保存指纹和接收结果，销售 `ExecuteTransactionAsync` 拥有默认隔离事务。 | 请求成功后再次用同 ID 可由来源日志重放，销售重新读取订单并重组返回结果；来源事实已推进后仍可能受现状态影响。两个 WPF 入口再次触发时创建新 ID，网络结果未知时并不保留外层原 ID。来源日志还记录接收数量、操作者和链路；销售确认本身没有专用业务审计日志。 |
| 售后 `ConfirmDemandAsync`（正数量）→ `ReceiveAsync` | WPF `AfterSalesDetailViewModel` 的 `CommandId("confirm", …)` 生成确认 ID；`AfterSalesFeatureService` 先用另一个 `confirm-save` ID 保存，再把确认 ID 原样交给来源。来源无独立子 ID。 | 售后 `BusinessOperationLog(Module=AfterSales, Operation=Command, CommandId=父 ID)` 保存完整外层结果、指纹和前后快照；来源另外用同 ID、不同模块分类的审计日志保存接收结果。售后 `WriteAsync` 拥有 `Serializable` 事务。 | 售后先查本模块日志再校验头版本，重放时不再次调用来源。保存阶段与确认阶段是两个独立 HTTP 命令、两个事务；保存成功而确认失败可以单独重试确认。当前 WPF `CompleteCommand` 对任何结构化错误（包括 `OUTCOME_UNKNOWN`）清除待重试 ID，重新执行“保存并确认”也可能重新保存并改变确认版本。两份日志当前同时承担审计和重放。 |
| 售后 `ConfirmDemandAsync`（无正数量） | 外层仍有确认 CommandId，但业务委托提前返回，不构造来源命令。 | 只有售后日志充当外层回执；售后拥有事务。 | 相同 ID 由售后日志重放；不得为了统一路径向不接受空明细的来源服务发送命令。 |
| 销售 `CancelConfirmationAsync` → 来源退出 | 取消命令由销售两个 WPF 入口各自生成新 ID；`CancelConfirmationAsync` 的来源退出参数不含 CommandId。 | 销售取消日志保存结果并承担重放；销售拥有默认隔离事务。 | 原 ID 重试先查销售取消日志，再决定是否进入来源退出；来源退出无独立回执，日志保留取消原因和数量。当前 WPF 再次触发仍新建 ID。本设计不改取消命令。 |
| 售后 `CancelDemandConfirmationAsync` → 来源退出 | 售后 WPF 生成独立取消 ID；来源退出参数不含 CommandId。 | 售后 `Command` 日志承担重放；售后拥有 `Serializable` 事务。 | 外层已重放时不再次退出来源；来源负责物料历史和 Shipping 交付证明，售后日志记原因与前后快照。本设计不改取消命令。 |
| 销售 `CloseAsync`、`DeleteDraftAsync`；售后 `VoidAsync` → 来源其他方法 | 销售关闭/删草稿请求没有接收用的子 ID；售后作废有自己的外层 ID。 | 各由外层服务拥有事务；不产生来源 `Receive` 回执。 | 分别调用 `ClosePendingAsync` 或 `HasActiveAsync`，只维持其既有资格和失败语义，不进入本次回执迁移。 |

`CommandReceiptRepository.FindAsync` 只按 `CommandId` 全局查询；实体以 `UX_CommandReceipt_CommandId` 保证全局唯一。执行器还核对 ActorUid、CommandType、目标与指纹。因此如果外层确认和来源接收把相同 ID 各写一条公共回执，第二条必然冲突；即使先查到了父回执，也不能把父结果反序列化为来源结果。当前业务日志按模块、操作、CommandId 组合隔离，允许销售/售后与来源用同 ID，不能据此推导公共回执也允许。

## 2．推荐：外层持久化完整确认回执，来源只参与事实写入

一个可重试的正式命令只由最外层确认用例拥有事务和 `CommandReceipt`。建议为销售确认、售后确认分别采用稳定 `CommandType`（例如 `Sales.Order.Confirm`、`QualityControl.AfterSales.ConfirmDemand`），以现有客户端 CommandId 为公共回执键，`RequestTargetUid` 为来源单头 Uid。指纹纳入认证操作者、命令类型、目标与实际请求版本；两者不共享命令类型。首次业务仍用既有头行锁序、来源版本计算、来源接收及状态更新。销售使用连接默认隔离，售后显式 `Serializable`；业务事实、两域业务审计和外层完整结果回执在同一事务提交。业务版本/状态校验位于回执查找之后，保证首次成功后旧版本的同 ID 请求能得到首次结果；首次新 ID 仍按现有资格重验。取消确认、关闭、作废不借此变成公共命令。

销售外层结果为 `SalesOrderConfirmationResultDto`，包含确认后版本、状态和实际接收行数；售后外层结果为 `AfterSalesCommandResult`，包含确认后头版本、状态和能力。售后现有 `AlreadyApplied` 重放标记可由执行器的 `IsReplay` 映射，保持公开 DTO 形状。来源服务只返回本次事务内接收计数供父命令构造结果，不保存可独立重放的机器结果；`SourceDemandReceptionCommand.CommandId` 在过渡实现中仍作为父命令身份和审计关联值，不因此生成第二条 `CommandReceipt`。

**授权边界**：销售确认要求有效登录和现有 `ModuleSalesAccess`；售后确认要求有效登录及现有 `ModuleQualityControlAccess`。复用现有权限服务和 Admin 规则，在回执查询及事务之前校验，未登录 401、无权限 403，不新增销售/售后细权限。销售此前没有显式认证授权，需如实记录这一行为收紧。不能为方便而给整个旧 Controller 新增类级权限并改变所有其他动作，只调整确认入口和 Application 确认切片。来源服务内部不另加面向销售/售后的 HTTP 权限。

**客户端重试边界**：外层 DTO、路由和 Refit 签名无需加字段，现有 CommandId 已存在。销售管理页与详情页为同一未决确认保存原 CommandId、目标和请求版本的不可变快照，重试原请求；管理页不能把 A 单的未决 ID 用到 B 单。售后明确区分两个阶段：

| 阶段 | 保存的未决上下文 | 重试动作 |
|---|---|---|
| 保存结果未知 | 原保存 ID、目标、创建/更新标记、完整原保存请求 | 原样重试保存；成功取得确定版本前不发确认 |
| 保存成功、确认尚未发出 | 保存返回的目标和版本、独立确认 ID | 发确认，不重复保存 |
| 确认结果未知 | 原确认 ID、目标、保存成功返回的版本 | 只重试原确认请求，不重复保存 |
| 已确定成功或明确拒绝 | 记录结果，刷新当前事实 | 结束该意图；新业务输入使用新 ID |

`OUTCOME_UNKNOWN`、网络超时，以及请求已发出后无法证明未提交的取消，不能清除未决上下文。命令忙也沿用原 ID。不要仅修改 `CompleteCommand` 而遗漏随后重新保存或刷新覆盖版本的路径。保存阶段仍使用现有保存幂等协议，本批不把其他售后写命令迁入公共执行器。

结果未知期间，编辑、刷新或点击放弃不会取消服务端事务，不能据此丢弃旧身份并发新意图。先用原请求重放取得确定结果，或完成能证明原命令结局的核实，再结束未决状态。普通详情刷新不是命令未提交的证明。旧回执表示当时的结果，不代表当前最新单据状态；重放后重新加载详情，不能用历史版本覆盖当前已发生的后续业务。

本批在页面实例生命周期内保存未决上下文；有未决写入时阻止普通关闭/切单丢失上下文并提供重试入口，不新增磁盘缓存或跨进程恢复框架，不承诺强制退出程序后自动恢复。`PreventDuplicateRequest` 和 Busy 不能代替持久化回执。

## 3．备选：确有独立重试需求时使用事务内子回执

只有将来来源接收出现**脱离销售/售后外层确认的正式可重试入口**，或同一外层命令会多次独立提交可区分的来源子意图，才增加事务内子回执。目前两处生产调用都只在父事务内运行一次；售后纯投诉不调用来源，销售接收结果只用于父结果计数，没有单独重试消费者，因此当前没有建立这套机制的证据。

若需求成立，子 ID 必须与父 CommandId 不同且稳定地由父 ID、明确操作、来源类型/头身份及子项身份派生，并记录父子关系；不能在重试时随机生成。事务内子回执组件只能使用现有 `DbSession.Transaction` 和 `ICommandReceiptRepository` 的全局命令锁/回执仓储，不得调用会新开事务的 `BusinessCommandExecutor.ExecuteAsync`，也不得提交、释放或清空外层事务。需另外验证父回执先于子回执的读取顺序、授权操作者、跨类型冲突、结果格式、父失败时两份回执同时回滚，以及 SQL 锁顺序。代价是新增派生 ID 协议、事务参与式执行逻辑和更多失败组合；在没有独立消费者前不预建框架或新表。

## 4．让接收审计退出重放职责的安全次序

1. 先为销售确认和售后确认建立外层回执的内存行为测试，分别覆盖同 ID 同输入结果重放、改用户/目标/内容冲突、旧版本重放、提交结果不明、来源写入或审计失败整体回滚；在尚未切换实现前保留来源审计重放及售后审计回放。核对现有销售确认“已确认且新 CommandId”路径和售后“纯投诉无来源”路径的现有语义。
2. 先抽出销售 Confirmation 窄接口和服务，再接公共执行器；同步两个销售 WPF 确认入口的重试。维持默认隔离和原来源锁序，首次成功的销售头状态、来源事实、来源审计、销售确认审计和公共回执同事务。此时来源仍保留旧日志重放作为过渡保障；采用上述已明确权限口径。
3. 抽售后 Confirmation 窄接口和服务并接公共执行器，显式维持 `Serializable`、命令锁先于头锁及正数量/纯投诉分支。首次执行中按“公共回执锁 → 既有售后命令锁 → 头行锁 → 来源锁”协调仍用旧 WriteAsync 的其他命令；核对同 ID 用于不同售后操作时的既有审计身份冲突并明确返回命令冲突，不能把唯一约束异常吞成成功。其他售后写命令继续沿用既有 WriteAsync，不迁移其协议。确认审计保留前后快照和原因，机器回执由公共表负责。两阶段保存/确认仍为独立 HTTP 命令和事务，同步实现保存未知与确认未知的分别恢复。
4. 两个生产父入口均已能独立重放完整结果、且已验证父回执覆盖来源写入后，才移除 `SourceDemandReceptionService.ReceiveAsync` 对 `BusinessOperationLog.GetByCommandAsync`、审计指纹和结果反序列化的依赖。保留来源业务日志及唯一审计身份，`ChangedFieldsJson` 改为可读数量变化，`RelatedObjectsJson` 只放来源行或关联身份；审计插入失败仍使父事务失败。`IBusinessOperationLogRepository.GetByCommandAsync` 仍供销售取消、售后其他命令等调用，不能因来源不再使用而删除。无旧业务库，不做日志到回执的历史数据迁移，不保留无消费者的来源重放兼容壳。
5. 最后单独核对并清理历史空版本分支，条件见下一节。任何一步出现回执覆盖缺口，保持现行来源审计重放，不先删除保障。

## 5．`LegacyBusinessContentMatches` 的现行写入证明和删除门槛

`LegacyBusinessContentMatches` 只在**已锁定的活动 `GrossDemand.SourceVersion == null`** 时被调用；它跳过当前 `ContentMatches` 中客户、单位等后来增加的接收元数据，只比较较早业务快照。`ReceiveAsync.Validate` 要求传入 `SourceVersion > 0` 且 SourceType 只允许 SO/CR；销售 `ConfirmAsync` 将确认状态写入后的头版本传给 `CreateSourceDemandCommand`，售后 `ConfirmDemandAsync` 将 `head.Version + 1` 传给来源；`Apply` 对每条新建/更新的 SO/CR 来源写入该正版本。因此当前两条生产接收路径不会**新写**空 `SourceVersion`。现有测试未发现为 SO/CR 主动构造空版本的生产写入分支。

删除条件：实施前再次全局搜索 SO/CR `GrossDemand` 的生产写入，确认没有绕过 `ReceiveAsync.Apply` 的新增、导入或同步路径。已有活动 SO/CR 来源缺少 SourceVersion 时按异常事实拒绝并提示核查，不自动补齐；添加定向测试后删除 LegacyBusinessContentMatches 和失真注释，保留普通版本前进、同版不同内容及下游阻断测试。**不能把 GrossDemand.SourceVersion 改成全表非空**：手工 MD 来源没有上游版本，继续合法允许 NULL。无业务库，不运行历史迁移。

全批验收还需按真实调用顺序验证同一 `DbSession`、父回执锁先于来源业务锁、取消时父子业务和审计均回滚、提交未知时沿用原 ID、错误码经 HTTP 出口保持失败状态。内存替身不能证明 SQL Server 的锁竞争、全局唯一索引或跨仓储真实原子性；无隔离业务库时如实列为未验证，不运行数据库测试。

**实施边界**：按本次用户要求完善方案并交执行窗口实施 A→B→C→D。当前窗口只写文档。权限和异常空版本按正文规则执行；遇到新的业务歧义再提出具体问题，不重复询问已明确范围。
