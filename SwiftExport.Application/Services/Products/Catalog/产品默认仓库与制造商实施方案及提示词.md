日期：2026-09-26。状态：实施中，待确认既有关联停用后的无关字段保存规则。用户已授权实施并发送至任务 `01a0cedf-d7b2-73c1-8532-223f84df2074`，本文件是执行范围。

## 一、确认的语义

Product 增加三个可空字段：

| 字段 | 类型 | 职责 |
| --- | --- | --- |
| DefaultWarehouseSiteId | Guid? | 默认仓库，逻辑关联 WarehouseSite.Uid，供入库和出库参考 |
| ManufacturerId | Guid? | 制造商，逻辑关联 Supplier.Uid；不要求当前向其采购 |
| ManufacturerModel | string? | 制造商型号；没有选择制造商也允许独立保存 |

ManufacturerId 表示谁生产，DefaultSupplierId 表示通常向谁采购，可以相同，也可不同。制造商复用现有供应商档案，不建立制造商表、供应商链表、品牌表或“是否制造商”的强制资格字段。不自动创建 SupplierProduct，不自动改变默认采购供应商。

三个字段均不必填，不存占位 Guid。ManufacturerModel 去首尾空白，空白规范化为 null；建议长度 200，由实体元数据、后端校验和前端保持一致，不截断用户输入。型号不全局唯一，也不按制造商与型号建立唯一约束，因为当前没有这种业务要求。

制造商编码／名称、默认仓库编码／名称只作查询展示，不冗余持久化进 Product，不当作历史单据快照。这里记录 Product 自身的制造商；组合产品内某零件的制造商信息应保存到那个零件 Product，不能写成整套产品的制造商。

## 二、当前事实及默认仓库使用边界

- Product 目前已有 DefaultSupplierId、ProductMasterId 等逻辑关联，没有本次三个字段。
- 普通新增、修改及批量保存由 ProductMaintenanceService 的 ValidateBeforeCreate/Update 和批量事务组织。本轮保留这些机制，不接 FluentValidation、不拆保存 DTO、不增加 CommandId。
- 入库 InboundManagerViewModel 当前从采购来源选行，单头独立选仓，多个产品共用一个单头仓库。
- 出库 OutboundManagerViewModel 要求先选择 WarehouseSiteId，然后按该仓库存货选品。不能为了产品默认仓库绕过这个条件。

本轮把默认仓库落地为可维护、可查询、入出库可见的参考值：

1. 在入库来源候选、出库存货候选中显示产品当前默认仓库名称；需要时加编码，不制造冗余列。按批次 SQL 投影或现有批量查询取得，不逐行请求 Product。
2. 不自动修改单头 WarehouseSiteId，不在产品切换时覆盖用户选择，不根据多个产品的默认仓库自动拆单、切仓或合并。
3. 出库候选仍只返回当前所选仓库符合原规则的库存；默认仓库不是额外库存、不提供可用数量、不参与扣减决策。
4. 默认仓库与实际仓库不同不构成业务错误；原仓库有效性、业务资格、来源和库存检查继续生效。默认字段为空不阻止既有入出库。
5. 不更新历史单据、库存余额、流水、自动入出库端口及 PackingList 仓库决策。若后续需要自动带入或“按产品找仓”的新交互，另行确定多产品冲突和用户手选优先级。

## 三、实施范围

### 1. 实体、元数据和建库基线

修改 Core/Entities/MasterData/Product.cs，加中文职责注释。EntitySchemaMetadata 添加两个可选 LogicalReference，不建物理 FOREIGN KEY。ManufacturerModel 明确最大长度；不增加不必要的索引。通过现有离线 SchemaGenerator 更新唯一生成基线并 verify，不手改生成 SQL、不运行数据库部署或历史回填。

### 2. 保存与查询

- ProductDto 增加三个可写字段及只读展示字段 ManufacturerCode、ManufacturerName、DefaultWarehouseCode、DefaultWarehouseName（以现有命名惯例为准，实施记录固定最终名称）。Contracts 保持 netstandard2.0。
- ProductMaintenanceService 的单条新增、更新、批量保存均需覆盖。可空关系能保存并清除；明确的 Guid.Empty 返回输入错误，不当有效关联。
- 新选或改选非空关系应验证真实目标未删除、符合现有可选项有效性规则；制造商不得要求已有采购关系、SupplierProduct 或对应仓库。
- 既有关系后续停用时，读取不能丢失 Product。对于未改变的停用关联，复用现有产品关联维护规则；若默认仓库与制造商不存在可复用规则且会影响无关字段保存，向用户确认，不静默制定整行拒绝策略。空关联和普通独立字段工作可继续。
- 批量校验按 ID 去重批量取数，不每行调用仓储。保持当前事务所有者、Version、批量全成全败及当前权限。
- 检查 Mapster、单条保存和批量完整更新路径，确保 null 真能清除关联，防止 IgnoreNullValues 造成清除失败。
- ProductRepository 的列表、详情、按 SKU 查询和有实际消费者的 Lookup 补必要投影。与 Supplier 用独立 manufacturer 别名 LEFT JOIN，避免与默认供应商别名混用；仓库也 LEFT JOIN。展示失效目标时保留 Product 及原关联 ID，不伪造名称。
- 产品详情若仍通过 BaseService/实体映射返回，需要使新展示字段能正确读取；不能只改分页 SQL，导致再次打开没有名称。不得顺手改其他查询业务。
- Inbound 来源 Query、Outbound 库存候选 Query 的 DTO 和 SQL 仅增加默认仓库参考字段；读取当前 Product，不把参考值当单据持久化仓库。无须在所有销售、采购 DTO 扩散三个字段。

### 3. WPF

- ProductList 的行模型、映射、批量请求、列／编辑入口加入默认仓库、制造商、制造商型号。复用现有供应商／仓库选择器，允许清空。制造商选择不得自动改 DefaultSupplierId。
- 制造商型号可独立输入；清除制造商不清除型号。默认仓库清空只影响该字段，不影响其他 Product 属性。
- 入库选源、出库选库存界面加入“产品默认仓库”只读参考信息，保持第二区别于实际单头仓库的语义，避免展示为强制要求。
- 新增、编辑、保存、重开、撤销修改均应保留正确值；保存后展示可以按现有读取机制刷新。遵守当前 MVVM、选择器异步取消／过期结果和 Busy 门禁，不重构整个页面。
- VSTO 若有直接保存 ProductDto 的消费者，核实完整更新不会将原值意外清空；新增字段的旧客户端缺省语义有风险时先报告，不自行建立补丁更新或兼容回填框架。

## 四、交付顺序与测试

一次连续完成：数据与保存 → 产品编辑和查询 → 入出库参考展示 → 定向验证，最后统一 Review。

必要用例：

1. 三字段全空可保存；型号单独保存；制造商与默认供应商不同可保存。
2. 单条／批量新增更新正常；清空关系可持久化；无效 ID、空 Guid、超长型号按输入错误拒绝。
3. 保存和重开后 ID、型号、展示名称正确；撤销修改恢复原值。
4. 查询可选关联不丢行、无一对多重复；厂商别名不污染默认供应商展示。
5. 入库候选展示参考仓库但不覆盖手选仓；多个产品默认仓不同不自动拆单或报错。
6. 出库仍先选实际仓，候选不跨仓，默认仓库不同／为空不绕过库存校验。
7. 原产品版本冲突、批量回滚行为保持。SchemaGenerator --verify 一致。

构建后端和 WPF，运行直接相关无数据库测试，精确筛选产品维护、产品模型、入出库选源／选仓测试。不要用全仓测试扩大范围，不删除旧有效断言，不用未重编译的测试产物。禁止连接业务库／LocalDB、执行 DbSeed／DDL／库存操作。真实 SQL null 写入和锁竞争标为未验证。

保留现有工作区（含已暂存）改动，不自动提交、重置、回退。完成后在本文记录实际文件、输入／展示字段来源、选仓行为、测试命令和结果，停止在统一 Review。
