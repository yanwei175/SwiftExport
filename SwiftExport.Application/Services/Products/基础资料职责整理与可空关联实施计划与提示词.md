# 基础资料职责整理与可空关联实施计划与提示词

本文为待实施计划。编制日期：2026-09-25。当前只完成源码盘点和范围确认，尚未按本文修改业务代码。

## 1. 本轮目标与已确认决策

围绕 Product 核心产品、客户资料、供应商资料及辅助建档资料，完成可空关联规则修正和职责归位。一次连续实施，内部按两个步骤推进，最后统一 Review；不必每个模块单独等待批准。

用户已明确：

- Product 是实际公司产品的核心身份，辅助建档资料不能变成另一套必须同步的产品主线。
- 关联采用逻辑外键，不建立数据库物理 FOREIGN KEY。
- 客户产品、供应商产品允许不关联 Product，关联 ID 为 null 时允许保存。
- **客户产品的 CustomerId、供应商产品的 SupplierId 仍必填**。所属对象与可选 Product 关联是两种不同职责。
- 不强制选择 Product，不自动创建 Product，不用 Guid.Empty 或虚构记录补齐关联。
- 本轮整理普通资料查询和维护，不引入审批、确认、过账等单据流程。

可空不是所有字段一律改成 nullable。已有可选辅助关联保持可选；ProductNeutral 的 ProductMasterId 等聚合所属字段不因本次决策自动变成可空。发现其他必填辅助关联与本决策矛盾时，列出具体字段及调用场景，向用户确认，不自行扩大数据含义。

## 2. 源码事实与需处理差异

| 对象 | 当前事实 | 本轮处理 |
| --- | --- | --- |
| ProductService | 同时含分页、SKU 查询、Lookup 和批量保存，继承 BaseService | 分离 Query 与 Maintenance，保留实际 CRUD 能力 |
| CustomerService / SupplierService | 简单主数据维护，包含查询和原子批量保存 | 按资源归位；只有确实降低耦合才拆查询接口，不机械增加服务 |
| CustomerProduct | SkuId 已是 Guid?，查询 LEFT JOIN Product；所属客户必填 | 保持可空语义，归位查询和维护，补关联为空的回归覆盖 |
| SupplierProduct | Entity、DTO、WPF 行模型的 SkuId 为 Guid；保存要求标准 SKU；仓储 INNER JOIN Product | 修正完整保存与读取链路，使未关联资料可保存、可见、可重新编辑 |
| SupplierProductService | 还负责 SetProductDefaultSupplierAsync，实际修改 Product | 从供应商资料维护职责中分离，保留原 HTTP 入口与业务规则 |
| ProductMasterService | 分页、详情、主从保存、中性产品保存、分类分配混合 | Query / Maintenance 分离；明确主从保存事务所有者 |
| ProductNeutralManagerService | 独立列表和批量维护 | 去掉页面 Manager 命名，按 ProductNeutrals 资源归位 |
| ProductCategory / ProductColor / CustomerPoConfig | 相对小的查询维护服务 | 按 Categories / Colors / PoConfigs 归位，允许一个小服务保留查询和维护 |

另外两处需要保留的事实：

1. ProductMaster 保存存在显式同步 Product 描述和默认供应商的请求选项，不是单纯写一个表。保持选项含义、影响范围、版本更新和现有事务原子性，不改成无条件同步，也不删除现有同步能力。
2. 已盘点的批量维护存在任一失败整批回滚语义。不得为了拆服务改为逐行提交、部分成功。

上述事实以实施时最新源码为准；开工时核对差异，不将旧文件名当作不变事实。

## 3. 目录与职责目标

以资源定位，再按必要的能力分文件夹。以下是 Application 实现目录；Interfaces 使用相同资源和职责层级。

```text
SwiftExport.Application/
  Services/
    Products/
      Catalog/
        Query/                 Product 查询、SKU 查询、Lookup
        Maintenance/           Product 创建、修改、删除、批量保存
        DefaultSupplier/       明确修改 Product 默认供应商的用例
      ProductMasters/
        Query/                 主型号列表与详情
        Maintenance/           主型号保存、主从聚合保存、分类分配
      ProductNeutrals/
        Query/                 独立中性产品查询
        Maintenance/           独立中性产品维护、指定主型号下的中性产品维护
      Categories/              分类查询、维护和层级规则
      Colors/                  颜色查询与维护
    Customers/
      Management/              客户基本资料查询与维护
      CustomerProducts/
        Query/
        Maintenance/
      PoConfigs/               客户 PO 配置
    Suppliers/
      Management/              供应商基本资料查询与维护
      SupplierProducts/
        Query/
        Maintenance/
```

目录职责约定：

- Query 只读；Maintenance 负责本资源的保存校验、版本、批量结果与事务协调。
- Lookup 当前归 Query；只有消费者和查询依赖明显独立时才单设 Lookup，不为一个方法多建一层。
- 已有 ProductUnitPolicy、ProductMasterMainImagePolicy、ProductDefaultSupplierPolicy 随实际所属资源归位；真正跨资源共用者才留在 Products 的公共规则位置。不建立万能 Helper。
- ProductMaster 主从保存继续有一个事务所有者；中性产品内部写入参加该事务。可提取同模块内部协作对象，但不能通过调用另一个会独立提交的公开维护入口完成主从保存。
- 小型主数据允许保留 BaseService。需分离 Query 的资源，用窄接口限定消费者；不要为了让 BaseController 构造函数通过而保留旧宽接口转发壳。若继承结构阻碍分离，局部显式声明 Controller 原有动作，不重写全项目 BaseController。
- 不把本轮所有公共能力塞进 Commands。现有 Commands 继续承载其已有公共命令机制，本轮资源维护文件放各资源目录。

其他层对应归位：

| 层 | 归位方式 | 边界 |
| --- | --- | --- |
| Core Repository Interfaces | 按 Products / Customers / Suppliers 的资源目录归位 | 查询、写入确实有独立依赖时拆窄接口；不为每个方法建仓储 |
| Infrastructure Repositories | 与资源接口对应 | CustomerProductRepository 从 Products 归入 Customers/CustomerProducts；SupplierProduct 按资源归位；保留 SQL 语义 |
| WebApi Controllers | 按同样资源分目录 | 一个小资源可保留一个 Controller 注入查询与维护；类名影响 api/[controller]，不能随目录移动改变路由 |
| Contracts DTO / API | 按资源和 Requests / Responses 等既有约定归位 | 一个公开顶级 DTO 一文件；仅移动时保留公开 namespace、类型名、Refit 签名与序列化字段 |
| WPF | 仅修改可空关联链路和直接消费者 | 不做页面、ViewModel、布局的全面重构 |

后端内部移动文件同步迁移 namespace、DI、using 和测试引用；删除迁移后无消费者的旧宽类型，不保留兼容转发壳。Core Entity 和公开 Contracts 不因目录美化任意更名；生成器、反射或序列化依赖必须检查。

## 4. 第一步：可空 Product 关联闭环

### 4.1 数据、契约与保存

1. SupplierProduct.SkuId、SupplierProductDto.SkuId 和对应 WPF 模型统一支持 null，检查 Mapster、请求构造和所有直接消费者。
2. 普通供应商产品保存不再要求 SkuId / ProductSku 非空。仍验证所属供应商、供应商产品自身编码、价格等现有独立规则；不放宽无关校验。
3. 客户产品保持同样可空 Product 语义，不改所属客户必填和客户自身编码规则。
4. 未选择或明确清除 Product 时，客户端发送 null，不以 Guid.Empty 表示有效关联。服务端不得持久化空 Guid 作为替代关联；已有统一空值规范可复用，否则在对应请求边界明确拒绝空 Guid 并提示清除选择。
5. ProductSku 等辅助编码允许无值，不要求用户为未关联记录伪造标准 SKU。清除关联时清除由该选择器带入的标准产品显示值，不能清除客户／供应商自有编码、描述、规格、价格等独立资料字段。
6. 不根据字符串 SKU 自动绑定 Product，不新增级联更新／删除，不将“逻辑关联”升级成所有历史记录必须实时关联活动 Product 的强制约束。非空关联沿用现有操作校验；遇到新的规则分歧先问用户。

### 4.2 读取与专用操作

1. SupplierProduct 的普通列表、详情查询对 Product 使用可选关联，检查 WHERE 条件避免将 LEFT JOIN 再过滤成必选关联。所属 Supplier 的既有规则不变。
2. 未关联记录必须能显示、搜索自身编码、打开编辑并再次保存。Product 显示字段为空不能导致行被过滤、映射报错或空值解引用。
3. 专门以 Product 为目标的采购候选、默认供应商操作继续要求具体 Product。不得将未关联供应商资料混入某个 Product 的候选，也不得让普通保存因为不满足专用操作前置条件而失败。
4. SetProductDefaultSupplierAsync 分离到 Product 的 DefaultSupplier 职责；原接口路由转发至新用例，不保留 SupplierProductService 的旧业务实现壳。原有锁、版本、权限、事务、响应保留。

### 4.3 数据库结构来源

只修改 Entity／必要元数据并通过现有 SchemaGenerator 更新建库基线，检查生成差异仅包含本任务预期结构变化。不要手改生成 SQL，不新增物理外键，不设计旧业务库迁移或回填。

生成器当前 Program.cs 使用实体程序集离线生成文件，不连接数据库；实施时复核后可执行：

```powershell
dotnet run --project .\_tools\SchemaGenerator\SchemaGenerator.csproj
dotnet run --project .\_tools\SchemaGenerator\SchemaGenerator.csproj -- --verify
```

禁止运行 DbSeed、数据库部署或 LocalDB 测试。生成基线不等于已验证数据库运行行为。

- 不统一给普通 CRUD 添加 CommandId、CommandReceipt、BusinessCommandExecutor 或客户端未决命令框架。

- 不改变币种权威来源、价格计算、null 与零的差异、主图策略、分类层级或版本冲突规则。

是否接入持久化命令回执由重复执行风险和跨对象副作用决定，不由有没有审批决定。完成本轮后，只列出 ProductMaster 显式同步、设置 Product 默认供应商等特殊写入的当前重试机制和剩余风险，另行决定协议升级；不借此扩大实施。
