# 入库过账拆分第二阶段实施计划

状态：第二阶段代码已实施并完成定向替身验证；真实 SQL 验证及已有业务库的历史回执转换与上线切换未完成。

## 目标与范围

将 PreviewPostAsync、PostAsync 从剩余 InboundManagerService 提取到 IInboundPostingService / InboundPostingService，正式 Post 接入已有 CommandPipeline、BusinessCommandExecutor 和 CommandReceipt。只读 Preview 仍保持原行为，不开写事务、不写回执和审计。

不拆出库或 Reversal，不改变 HTTP 路由、请求与响应 DTO、业务资格、数量计算、权限要求、库存流水身份和锁顺序。不新增通用框架、实体或表，不运行业务数据库部署。

## 文件与调用方

- 新接口：Application/Interfaces/Inventory/Inbounds/IInboundPostingService.cs。
- 新实现：Application/Services/Inventory/Inbounds/InboundPostingService.cs。
- 正式请求格式验证：同模块 Validation/PostInboundCommandValidator.cs，使用现有自动扫描注册，规则仅为 CommandId、ExpectedVersion 等输入格式；路由 uid 单独校验并参与指纹目标。
- 复用 InboundServiceSupport、模块现有采购来源判断及库存内核；不复制新的事务、回执、日志框架。
- 更新 InboundManagerController 对两个 Post 方法的注入与调用、DI、测试夹具、采购 SQL 集成测试中的真实调用方，以及路径契约测试。
- 删除原 InboundManagerService.Posting.cs 和旧接口中两个 Post 成员，不保留转发壳。Manager 本批仅保留 PreviewReverseAsync、ReverseAsync 及必需辅助方法；不得误删反向仍使用的锁、指纹和审计查询接口。

## 执行协议

1. 当前身份、库存模块访问权限及 InventoryInboundPost 细权限必须先于回执读取；验证失败通过既有 HTTP 契约返回。
2. 正式命令类型使用服务端稳定标识 Inventory.Inbound.Post，RequestTargetUid 为路由 uid；指纹包含 ExpectedVersion 及请求中全部影响业务语义的字段，排除 CorrelationId 和 CommandId 本身。
3. 外层事务与命令身份锁由公共执行器负责。已有成功回执先重放，不因当前版本或已过账状态再次拒绝同一请求；不同用户、类型、目标或内容返回冲突。
4. 首次执行保留原顺序：发现来源集合 → 按原顺序锁采购来源 → 锁入库头行 → 复核版本与完整来源集合 → 根据最新事实重做业务校验 → 库存内核 → 入库状态 → 审计 → 公共回执 → 提交。
5. 保持 CommandItemId 等库存事实身份不变；库存内核加入外层事务，不独立提交。先核对真实事务参与行为，若发现不兼容并且需要修改跨模块业务机制，向用户说明并询问，不静默扩大范围。
6. 过账审计保留 Module/OperationType 等原业务分类；CorrelationId 来自 ICorrelationContext，ChangedFieldsJson 表达实际过账变化，RelatedObjectsJson 表达关联对象，不再承载指纹和机器重放结果。
7. 结果格式保留原 InboundPostResult。公共执行器的内部 IsReplay 仅用于日志，不能序列化进对外结果或替代原业务结果快照。
8. 回滚、取消、提交结果未知沿用公共协议，不能在模块重新包一套事务。完成日志覆盖成功、重放、拒绝、Busy 和 Unknown，不重复审计。

## 历史与部署边界

代码切换以现有统一回执设计为准，不新增旧审计双读兼容分支，不删除已有业务历史。旧成功 Post 若只有审计回执，新机制不能声称已支持其重放；在文档中明确本次只完成代码接入，历史数据转换与上线切换未完成。

不得猜测业务库为空或用户已执行建表脚本。无需数据库操作即可进行代码拆分和替身验证；如需连接数据库、转换旧记录或部署，先向用户确认目标及保留要求。业务含义不明或需要更改状态、权限、数据语义时同样询问用户，继续不受影响的工作。
