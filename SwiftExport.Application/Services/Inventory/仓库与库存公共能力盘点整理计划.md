# 仓库与库存公共能力盘点整理计划

> 2026-09-24，按五批完成仓库与库存公共能力整理；实施记录见文末。以入库服务的清晰入口、独立事务内业务方法为样板，不照搬单据生命周期。以下“当前事实”已按实施后源码更新，分批章节保留执行范围和验收依据。

## 一、当前事实与优先级

| 对象 | 当前职责与边界 | 整理结果 |
|---|---|---|
| `WarehouseQueryService`、`WarehouseManagementService`、`InventoryQueryService` | 仓库查询四项、管理命令五项、库存查询三项分别由窄服务承接 | 旧 `IInventoryService` / `InventoryService` 已删除；Controller 按职责注入 |
| `WarehouseManagementService` | 五个正式命令经 `CommandPipeline` 授权和验证，再由 `BusinessCommandExecutor` 独占事务与回执 | `BusinessOperationLog` 只记录前后值、原因、操作者和链路标识；仓库专用命令锁及日志重放已删除 |
| `WarehouseCandidateQueryService` | 采购专用仓库候选、独立权限投影和 `Serializable` 一致性读取事务 | 保留独立接口、仓储、模型及 HTTP 用例，不并入库存 Picker |
| `InventoryPostingService` | Post、Reverse、Correct 共用 Apply、内核命令锁、CommandItemId 重放、余额和不可变流水 | 位于 `Posting`；参与外层事务，失败时回滚外层事务但不释放或清空它 |
| 库存 Query / Posting 仓储 | Query 承接五个只读方法；Posting 承接事实锁、余额与流水写入 | 旧 `IInventoryRepository` / `InventoryRepository` 已删除，两实现共享请求级 `DbSession` |
| 仓库 Query / Management 仓储 | Query 承接四个投影读取；Management 承接锁定、资格与版本写入 | 旧 `IWarehouseSiteRepository` / `WarehouseSiteRepository` 已删除，`GetForUpdateAsync` 留在 Management |
| 采购 Candidate 仓储 | 独立采购候选投影 | 接口与实现归入 `Warehouses`，权限与 SQL 保持原样 |
| `AutomaticPostingScope`、`AutomaticPostingPorts` | 在外层事务中声明并锁定资源，生成或反向自动单据并调用库存内核 | 位于 `AutomaticDocuments`，PackingList 正反向顺序保持原样 |
| `IAutomaticDocumentRepository` / 实现 | 自动入出库单据持久化 | 位于 `AutomaticDocuments`，不与库存余额/流水仓储合并 |
| 库存及仓库 DTO | 原 `InventoryDtos.cs` 的十二个类型按查询、管理、余额、流水、Trace 和 Posting 分文件 | 公开 namespace、字段和 Refit 签名未改；内核请求/结果模型仍在 Application |

仓库虽然是主数据，但当前有显式 CommandId、ExpectedVersion、启停和删除资格，不能降级成无版本的通用 CRUD。也不需要给仓库制造 Draft、Confirmation、Posting 目录。

## 二、必须保持的调用关系

```text
WarehouseSitesController → Warehouse Query / Management
                         → WarehouseCandidateQueryService（采购候选）
InventoryController      → Inventory Query

入库/出库正式命令 → BusinessCommandExecutor 开事务
                 → InventoryPostingService → 库存写仓储
PackingList 正式命令 → BusinessCommandExecutor 开事务
                    → AutomaticPostingScope + 自动单据端口
                    → InventoryPostingService → 库存写仓储
最外层保存回执并提交；内层不另开命令事务。
```

- `InboundDraftService`、`OutboundDraftService`、`InventoryPostingService` 使用仓库锁定读取；仓库仓储迁移必须同步这些消费者。
- `AutomaticPostingScope`、`AutomaticPostingPorts` 使用 `IInventoryPostingRepository`，与内核共享请求级事务。
- 自动端口/Scope 还通过 `IRepository<WarehouseSite>` 读仓库。先保留现有 SQL/锁行为，不因目录迁移替换成管理 DTO 查询。
- 内核 CorrectAsync 已有实现和测试，本轮不新增公开 HTTP 纠错接口；没有生产调用方也不据此删除业务能力。

## 四、不可改变的边界

1. 仓库管理写权限保持 InventoryWarehouseManage，仓库管理读取保持 ModuleInventoryAccess；采购候选保持现有 Create/Confirm 资格，不按统一目录扩大或收窄授权。
2. 保留供应商活动虚拟仓唯一、代码唯一、乐观并发、删除引用阻断、停用余额/历史流水限制。停用与删除的条件不同，不抽成同一个粗糙判断。
3. 仓库命令接公共回执后，授权早于重放；同 ID 不同用户、目标、操作或内容冲突；重放不读取当前仓库状态来重新判定首次结果。创建所生成的仓库 Uid 必须在首次执行业务内产生。
4. 仓库审计继续保存操作前后值、原因和操作者；首次结果由 CommandReceipt 保存。CorrelationId 保持调用追踪语义。清理审计反序列化重放方法及仅供仓库外层使用的专用命令锁，不做审计/回执双写兼容链。
5. 内核的 AcquireCommandLockAsync、CommandItemId 唯一性及请求指纹不能随外层回执统一而删除。Post 当前允许同一 CommandId 分批追加不同明细，这与外层“一次业务意图”的回执不是同一层机制。
6. 内核不使用 BusinessCommandExecutor，不添加单独用户授权，不持有提交权；可信 Application 用例负责授权，内核负责事实正确性。
7. 内核 ProtectAsync 当前在异常时回滚调用方事务，但不 Dispose、不清空 Session.Transaction。这是防止外层误提交部分事实的保护，本轮保留，不顺手改成只抛异常。
8. 保留原流水不可修改、完整反向、纠错组完整性、单位快照、decimal 精度、稳定资源锁序和禁止负库存。Correct 按整组最终余额校验，不改成按中间步骤逐条拒绝。
9. AutomaticPostingScope 的事务绑定、一次资源声明、稳定派生 ID 和所有集合锁序保持。自动单据生成与库存事实属于同一外层事务，不引入嵌套执行器。
10. 候选只读事务仍可能为一致性读取所需；只读不等于无事务。不要因为某注释提及旧采购消耗仓就删除仍有路由的候选能力。

## 五、分批实施

### 第一批：拆清 Application 的查询与仓库维护

- 从 IInventoryService/InventoryService 提取 IWarehouseQueryService、IWarehouseManagementService、IInventoryQueryService 及实现。
- 同批修改两个 Controller 注入、Application DI、直接测试。第一批暂保留仓储接口，降低一次变化范围。
- 将 WarehouseCandidateQueryService 归 Warehouse 目录，保留独立接口、返回包装和权限。
- 保持仓库 10 个 HTTP 用例、库存 3 个 HTTP 用例；IWarehouseSiteApi/IInventoryApi 成员和 URL 不变。
- 核对全部消费者后删除旧 IInventoryService/InventoryService，不保留宽转发壳。
- 验收：WarehouseSiteManagementServiceTests、WarehouseCandidateQueryTests、InventoryQueryContractTests，以及因接口迁移必要的替身调整；读取与维护权限不互换，查询不写库。

### 第二批：五个仓库命令接公共机制

- Create、Update、Deactivate、Activate、Delete 接 CommandPipeline、Validator 自动扫描、BusinessCommandExecutor。
- 每类命令独立 CommandType，输入指纹包含原有实际业务输入和目标；保留原事务默认隔离行为，不擅自升级 Serializable。
- 按入库样板分清入口、执行器接线、事务内业务方法；名称、原因等规范化保持既有语义，不因 FluentValidation 换成不同长度口径。
- 删除仓库私有提交/回滚/审计重放框架，审计仅写业务事实。调整错误包装，让 COMMAND_BUSY、COMMAND_CONFLICT、OUTCOME_UNKNOWN 真实传回。
- 清点仓库 AcquireCommandLockAsync 消费者，仅在已无消费者时删除；库存内核的同名锁不动。
- 验收：五类命令成功、版本冲突、同 ID 原结果重放、同 ID 不同内容/用户冲突、回执或审计失败回滚、提交结果不明。供应商/代码唯一与删除阻断继续覆盖。

### 第三批：查询与写入仓储分离

实施前消费者矩阵（按当前源码核对；同一接口内的方法共用对应实现）：

| 旧方法 | 新接口与实现 | 直接消费者 |
|---|---|---|
| 库存 `SearchBalances`、`SearchLedger`、`GetBalanceDto`、`GetLedgerByBalance`、`GetReconciliation` | `IInventoryQueryRepository` / `InventoryQueryRepository` | `InventoryQueryService`、库存查询 SQL 夹具 |
| 库存 `LockBalance`、`FindLedgerByCommandItem`、`LockLedgerByCommandItem`、`LockLedgerById`、`LockReversalByOriginal`、`LockReplacementByOriginal`、`LockCorrectionGroup`、`GetProductForPosting`、`AcquireCommandLock`、`InsertBalance`、`UpdateBalance`、`NextLedgerSequence`、`InsertLedger` | `IInventoryPostingRepository` / `InventoryPostingRepository` | `InventoryPostingService`、`AutomaticPostingScope`、`AutomaticPostingPorts` 及相关替身 |
| 仓库 `GetPickerPaged`、`SearchSupplierLookup`、`Search`、`GetDto` | `IWarehouseQueryRepository` / `WarehouseQueryRepository` | `WarehouseQueryService`；管理命令写入后读取 DTO；静态查询契约测试 |
| 仓库 `GetForUpdate`、`GetActiveSupplier`、`FindByCodeForUpdate`、`FindActiveSupplierWarehouseForUpdate`、`Insert`、`UpdateName`、`Deactivate`、`Activate`、`Delete`、`GetDeleteBlockers`、`HasBalanceOrLedger` | `IWarehouseManagementRepository` / `WarehouseManagementRepository` | `WarehouseManagementService`、入出库 Draft、`InventoryPostingService` 及替身 |

采购 `IWarehouseCandidateRepository` 继续独立；自动端口原有 `IRepository<WarehouseSite>` 锁仓依赖继续独立。两种仓储实现使用同一请求级 `RepositoryBaseContext.Session`。

- IInventoryQueryRepository 接收 SearchBalances、SearchLedger、GetBalanceDto、GetLedgerByBalance、GetReconciliation 五个方法，其余库存内核方法进入 IInventoryPostingRepository。
- IWarehouseQueryRepository 接收 Picker、供应商 Lookup、Search、GetDto 四个方法；仓库写入、资格及锁进入 IWarehouseManagementRepository。采购 Candidate 接口保持独立。
- 实现拆成对应类，共享现有 DbSession；先列“旧方法→新接口→实现→调用者”矩阵，同批改 Query、Warehouse Management、入出库 Draft、库存内核及自动端口/Scope。
- SQL 仅搬迁：参数、过滤、排序、分页、历史数据口径、锁提示、唯一性处理均保持；不使用 BaseRepository 通用更新替代库存专用条件写。
- 验收：库存查询契约、仓库管理与自动端口替身测试；SQL 测试有隔离环境才运行。检查所有 Dapper 命令仍传当前事务。

### 第四批：库存内核与自动单据归位、降低阅读负担

- IInventoryPostingService 保持 Post/Reverse/Correct 一个内聚接口；拆出同文件模型和异常，业务主体依旧共享 Apply，不复制锁/幂等/余额逻辑。
- 把压成单行的复杂 PostingFact 构造/指纹/流水生成方法格式化并补职责注释；必要时提成内部类型，不为了长度建立新公共框架。
- 将 AutomaticPostingScope、Ports、相关接口/模型、仓储归 AutomaticDocuments；保留正向/反向的既有职责和外层 PackingList 调用顺序。
- 盘点 ReverseLegacyAsync 的实际调用方与测试。此名称不等于可直接删除：现有 Post 接受 Reversal 输入。存在消费者时列清并在独立子批次迁到 ReverseAsync；未证明等价前本批保留，不将删除兼容路径混入目录迁移。
- 验收：InventoryPostingServiceTests、AutomaticPostingPortsTests，以及入库/出库过账与反向、PackingList 编排的受影响测试；覆盖明细重放、失败回滚、最终余额、整组纠错、重复反向和资源绑定。

### 第五批：Contracts、文档与入口收口

- InventoryDtos.cs 按公开类型逐文件归类，不改变字段、类型、默认值、枚举和 JSON 结构。IInventoryPostingService 内部模型不迁 Contracts。
- Controller、Refit 文件归目录，保持 13 项 HTTP 用例和公开签名；新增路由/响应契约测试仅覆盖此次移动的边界。
- 直接改写当前文档的失效路径、旧 IInventoryService 职责与“业务日志承担重放”等描述，不追加相互冲突的历史补丁段落。
- 旧服务/接口/文件只有在真实调用方全部迁移后删除。保留独立用途的内核约束与数据库唯一防线。
