# 采购后端盘点与分批整理实施计划

> 2026-09-24；五批采购后端职责整理已实施。本文件保留分批决策与实施记录；数据库并发与持久化仍待隔离环境验证。
> 参照入库已完成的职责拆分与可读性整理。需求转采购的 ExecutionRequestId/CommandItemId 协议及每来源独立事务仍按已确认边界保留。

## 1. 目标和范围

让维护者从文件夹找到业务能力，从服务入口读到执行顺序：公共管道负责授权、参数验证和技术日志，公共命令执行器负责事务与成功回执，业务方法负责锁定、业务判断、写入和审计。

采购拥有订单、商务保存、确认、取消确认、删行、作废、需求承接和供应商反馈；采购不承担库存过账。因此不创建采购 Posting 文件夹，也不把采购取消确认解释为库存反过账。

- 保持五层架构，复用 `Application/Commands`、`DbSession`，不新增通用单据框架或第二套工作单元。
- 不改变采购确认、Link 贡献、入库资格、供应商反馈和金额计算规则。
- 不重构 WPF 页面；Contracts 优先保持公开类型、namespace、字段及 Refit 签名，先整理物理目录。内部实现 namespace 随目录迁移，同批修改 DI、测试和直接消费者。
- 当前没有业务库。不连接数据库，不安排历史数据兼容、双写或迁移期限，不执行建表或删表。
- 实施某批后删除该批已无消费者的旧服务、接口、重复命令框架及失效文档内容，不保留转发兼容壳。未迁完的有效消费者不能强删。
- 不按代码行数拆文件，不机械为每个动作增加接口。业务主体采用 `入口 → Execute…CommandAsync → …InTransactionAsync`，同一类内用私有方法降低回调嵌套。

## 2. 实施后的源码职责与消费者

### 2.1 Application 与命令机制

- 独立采购草稿由 `ProcurementOrderDraftService` 负责 Create/Save，确认由 `ProcurementOrderConfirmationService` 负责依据读取与 Confirm；三种反向命令由 `ProcurementOrderReversalService` 负责。
- 普通订单与管理查询分别由 `ProcurementOrderQueryService`、`PurchaseOrderManagerQueryService` 负责；供应商跟进分为 Query 与 Report 服务。写命令使用 `CommandPipeline`、`BusinessCommandExecutor`、公共 `CommandReceipt` 与显式 Serializable。确认依据和反向预览仍使用 Serializable 一致性读取。
- 需求转采购的来源候选、预览、创建分别由 `PurchaseDraftCandidateService`、`PurchaseDraftPreviewService`、`PurchaseDraftCreationService` 负责。此链保留 ExecutionRequestId/CommandItemId、每来源事务与部分成功，未接单订单公共回执。
- 原 `ProcurementOrderCommandService`、`ProcurementOrderTransaction`、`PurchaseOrderProgressService`、`PurchaseDraftService`、`ProcurementCommandReceipt` 均已退出生产源码。采购确认只验证采购事实，不恢复旧 BOM 写链。

### 2.2 仓储方法 → 目标接口/实现 → 消费者

| 原方法组 | 目标接口 / 实现 | 直接消费者 |
|---|---|---|
| 订单头行锁定、Insert、Save、Confirm | `IProcurementOrderDocumentRepository` / `ProcurementOrderDocumentRepository` | Draft、Confirmation、ProgressReport |
| GetCustomer、GetSupplier、GetProduct、GetProductCandidate、GetUnit | `IProcurementReferenceReadRepository` / `ProcurementReferenceReadRepository` | Draft、ConfirmationBuilder |
| 按来源→物料→Link→采购→入库锁定确认/反向事实 | `IProcurementOrderFactLockRepository.LockAsync`，由 `ProcurementReversalRepository` 实现 | Confirmation；Reversal 经 `IProcurementReversalRepository` 使用同一实现 |
| 应用取消确认、删行、作废写入 | `IProcurementReversalRepository.ApplyAsync` / `ProcurementReversalRepository` | Reversal |
| 来源执行范围、可追加草稿、头行新增与追加版本 | `IPurchaseOrderDraftRepository` / `PurchaseOrderDraftRepository` | 需求转采购 Creation |
| 订单列表/详情、管理投影、跟进列表/详情 | 三个原窄 Query 接口及对应实现，仅归入 Query/Progress 目录 | 各自 Query 服务 |
| 锁定最新反馈、追加反馈 | `ISupplierProgressReportRepository` / `SupplierProgressReportRepository` | ProgressReport |

`SupplierProgressReportRepository` 原 GetByCommandAsync、GetByPurchaseOrderAsync 无生产消费者，已删除。订单专用回执仓储方法在第二批退出；当前业务命令只写公共回执。仓储继续共用 request scope 的 DbSession，锁序、SQL 筛选、版本条件与取消传递未改。

### 2.3 HTTP、Contracts 与客户端边界

四个既有根路由保留 21 个 HTTP 用例：订单 12、管理 2、需求转采购 4、跟进 3。Controller 已按 Query、Sources、Draft、Confirmation、Reversal、Progress 拆为窄入口；四个 Refit 接口和 DTO 只迁物理目录，公开 namespace、字段、签名与 JSON 契约保持原样。客户端继续消费原接口，无 WPF 行为改动。采购头行及状态仍供入库选源、PackingList 供货与需求 Link 退出判断读取。

## 4. 必须保持的业务与执行规则

1. 独立采购可以没有需求 Link；需求转采购在草稿阶段建立 Link、预留贡献。确认不重复创建 Link，不写库存，也不恢复已经退出的 BOM 确认节点写链。
2. 取消确认保留 Link；删行/作废释放对应贡献。不得在取消确认中顺手调用入库反过账，也不得级联回退需求。
3. 三种反向动作保留各自版本、原因、细权限和下游资格检查。当前权限：Read/Create/Edit/Confirm/Void 对应既有 ProcurementOrder 权限键；取消确认用 Confirm，删行和反馈用 Edit。
4. 常规命令先授权、格式验证，再命令锁与回执，再锁业务事实与校验。命中回执时不重算当前业务资格，不重取号，不重复写审计或释放 Link。
5. 当前采购订单事务使用 Serializable。迁公共执行器显式保留此隔离级别，不套用入库默认值。
6. 订单创建以请求目标为空表达尚无订单身份，首次执行内分配订单 Uid；不要每次重试在进入执行器前生成新目标 Uid。每类命令使用稳定且独立的 CommandType。
7. 回执业务输入明确选择实际请求字段；反向原因保持 Trim 语义，反向行集合保持已有稳定排序。CorrelationId 从调用上下文读取，不再由 CommandId 拼成。
8. 供应商反馈保留空字段继承最新反馈、累计数量下降需纠错原因、头行版本和已确认资格，不能将报告当库存或收货事实。
9. 确认依据与反向预览当前借助 Serializable 和锁定读取构造一致视图。零写入不等于无事务；不得为了删掉旧 Transaction 类将其直接换成多次无保护读取。可在 Support 中保留明确的只读事务方法，禁止写回执、审计、状态或预留。
10. 通用异常必须保留提交结果不明语义，不把 OUTCOME_UNKNOWN 包装成“确定未提交”。

## 5. 分批实施与验收

### 第一批：采购订单草稿和确认

- 从 `ProcurementOrderCommandService` 提取 Draft(Create/Save) 与 Confirmation(Confirm)，迁移接口、Controller 注入和 DI；暂不批量移动 Contracts。
- 接入 CommandPipeline、自动扫描 Validator、BusinessCommandExecutor，显式 Serializable。业务规则继续复用 Policy/ConfirmationBuilder。
- 各自保留一个容易顺序阅读的事务内业务方法。权限映射和错误包装可放模块 Support，不复制通用执行器。
- 专用回执仍被 Reversal 使用，不能在本批提前删除实体或仓储方法；新旧操作不双写，下一批紧接收口。
- 验收：创建/保存/确认成功；授权拒绝零写；版本和确认依据冲突；同命令重放、同 ID 不同请求冲突；审计或回执失败回滚；取号与状态不重复；确认不创建 BOM 节点。
- 复用 `ProcurementOrderPolicyTests`、`PurchaseOrderDiscountSnapshotContractTests`、`ProcurementCapabilityAndErrorContractTests`，补小型命令编排替身测试；不只用纯 Policy 测试证明事务正确。

### 第二批：反向命令与专用回执退出

- Reversal 接公共管道/执行器；三种操作分别使用稳定 CommandType，保持资格预览和 Link 释放规则。
- 确认和反向共同使用的锁定事实读取保留；先命令锁，再来源/物料/Link/采购/入库的既有顺序。
- 全部消费者迁完后删除 `ProcurementCommandReceipt`、`GetReceiptAsync/InsertReceiptAsync` 及其无消费者的专用 SQL/测试夹具代码。先全仓搜索生产、测试及建表工具引用，更新当前初始化定义；不执行数据库操作，不删除历史迁移文件来伪造已经部署的事实。
- 验收：重复反向不重复释放，取消确认不释放，删行只释放选中行，作废整单释放；入库未安全退出时拒绝；旧版本成功命令仍可重放；事务中途失败不留下部分 Link/状态/审计。
- 复用 `ProcurementReversalPolicyTests`，增加 Reversal 命令与公共回执联动测试；SQL 测试无隔离数据库时明确未运行。

### 第三批：查询、确认依据与供应商跟进

- Query 保留订单投影与 Manager 投影，不合并两套筛选契约。ConfirmationContext 移到确认能力；Controller 保留原路径。
- Progress 拆 Query 与 Report；Report 接公共回执，保留 SupplierProgressReport 业务实体、追加历史和唯一约束。
- Report 同 ID 同请求返回首次报告结果；不同用户/采购行/数量/日期/备注冲突。已有报告读取不再充当命令回执。
- 将读操作与命令事务分离；一致性读取继续有明确事务负责人。全部消费者迁完后移除 `ProcurementOrderTransaction`，不得保留一个换名后的通用命令执行器。
- 验收：管理/详情/跟进查询投影与分页不变；Read/Edit 权限不互换；部分反馈继承、纠错原因和重复反馈结果稳定；预览零业务写。
- 复用 `PurchaseOrderManagerQueryContractTests`、`PurchaseOrderManagerFilterSqlTests`、`PurchaseOrderProgressContractTests`、`PurchaseOrderProgressPartialFeedbackTests`，补反馈回执编排测试。

### 第四批：需求转采购职责整理（特殊协议）

- 将候选读取、只读预览、创建编排拆开；保留 PreviewBuilder/WriteModelBuilder 的计算语义。
- 保留按来源排序、每来源一个事务、一来源内多供应商原子创建、不同来源允许部分成功。
- 保留 `ExecutionRequestId`、来源 Token、CommandItemId、追加目标版本和 Link 唯一性。成功来源重试不再创建采购，失败来源结果不携带未提交单据。
- 不为接入统一机制将整个批次改成单事务，也不对批次保存“部分成功永久结果”而阻断失败来源重试。
- 当前候选/创建入口主要依赖 HTTP `[Authorize]`，未像订单命令一样明确 Application 细权限。若要新增细权限，先确认对应键；不能自行套用 Confirm 或仅凭已有角色名授权。
- 用户已确认：本轮保留现有协议，只做职责整理与保持协议的测试。按来源接入公共回执另行设计，本批不设计新 ID，也不迁移 Link 幂等机制。
- 验收：预览不写入；Token 过期拒绝；CreateNew/AppendExisting；两个来源一成一败；同来源中途失败整组回滚；Link/订单/版本/取号一致；成功结果仅提交后发布。
- 复用 `PurchaseDraftPreviewBuilderTests`、`PurchaseDraftWriteModelBuilderTests`、`PurchaseDraftSourceResultBufferTests`、`PurchaseDraftAppendSqlTests`，补来源事务编排用例。

### 第五批：仓储、HTTP、Contracts 与文档收口

- 先建立“原方法→目标接口→实现→全部消费者”清单，再迁仓储。已经窄的查询仓储只归目录，不重新创造同义接口。
- 订单仓储移除回执后，主数据资格读取与单据写入可分离；反向锁定事实与写入是否继续分接口，以 Confirmation 的真实消费为依据，同一锁序不拆散。
- 按目标能力目录迁 Controller、DTO、Refit 文件，21 项路由和公开契约逐项对照；WPF 无功能改动。
- 删除失效路径与旧接线说明，直接重写文档相应段落；不在过期描述后继续追加“补充说明”。源码与地图不一致时注明具体事实，不借本轮推定新业务。
- 完成标准：旧宽接口与服务无生产消费者；没有双套回执；DI 可解析；全部迁移方法可追到新职责；静态路由/序列化检查及最小后端构建通过。

## 6. 验证范围与交付要求

- 每批运行其相关现有测试及必要新增回归，不默认全仓测试或 WPF/VSTO 测试。
- 涉及 DI、Controller、Contracts 时运行后端构建；保持公共 namespace 时无需因纯目录移动重复跑全部桌面测试。
- 替身测试证明命令编排与回滚调用，不能证明 SQL Server 真实锁、死锁或跨连接原子性。没有隔离库时如实列出缺口，不等待不存在的业务库，不声称数据库验收通过。
- 每批报告修改文件、删除旧入口、行为是否变化、测试数量和跳过原因。保持无关工作区改动，不 reset、不替他人提交。
- 完成结构整理后用入库同样标准验收：打开服务先看到清楚的用例入口，再进入一个顺序展开的业务方法；不要为了抽象增加阅读跳转。

## 7. 已确认决定与安全推进边界

1. **需求转采购的公共命令适配范围（用户已确认）**：保留现有 ExecutionRequestId/CommandItemId 协议、每来源独立提交和部分成功，本轮仅整理职责。公共回执适配单独设计，不是本轮实施项；届时再确定稳定来源命令身份、指纹范围、部分成功后的重试和失败结果恢复。本计划的“统一回执”收口仅针对订单命令和供应商反馈，不包含这条明确保留的特殊协议。
2. **需求转采购的细权限键**：当前源码没有与订单命令一致的 Application 授权映射，增加授权前需确认候选、预览、创建分别采用哪些现有能力或是否新增；本计划不替用户扩大或收窄权限。

采购地图中已将确认、反向和管理页接线的过期现状改为当前源码事实；历史决策记录仍按发生时间保留，不作为当前实现入口。
