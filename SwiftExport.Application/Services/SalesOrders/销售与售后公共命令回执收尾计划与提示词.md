# 销售与售后公共命令回执收尾计划与提示词

日期：2026-09-25。状态：已实施，等待统一 Review；下列第 9 节记录本轮实测范围与限制。

## 1. 目标与范围

在已完成的 Query、Draft/Maintenance、Confirmation、Lifecycle 切片上，统一剩余写命令的执行、回执与客户端重试。一次连续实施，按后端、客户端、验证三个内部步骤推进，最后统一 Review，不按入口逐批交接。

复用 Application/Commands 下 CommandPipeline、扫描 Validator、BusinessCommandExecutor 和现有 CommandReceipt。数据库表、Core 单据实体、SQL 业务条件不变；不新增 Redis、日志表、回执表或通用单据框架。没有业务库，不保留旧审计回放兼容分支，不做历史回填。

范围：销售保存（新建/更新）、删除草稿、取消确认、关闭；售后创建/保存、取消确认、结案、重开、作废。已有两个确认服务保留业务流程，配合完成权限与旧命令锁清理。Query 不经过写命令执行器。

## 2. 当前事实与命令身份

| 入口 | 现状 | CommandType 建议与目标 |
|---|---|---|
| 销售 SaveAsync | 无 CommandId，Header.Uid 为空表示新建 | Orders.SalesOrder.CreateDraft / UpdateDraft |
| 销售 DeleteDraftAsync | 无 CommandId，删除后目标不存在 | Orders.SalesOrder.DeleteDraft |
| 销售 CancelConfirmationAsync | 已有 ID，从业务审计重放 | Orders.SalesOrder.CancelConfirmation |
| 销售 CloseAsync | 无 CommandId | Orders.SalesOrder.Close |
| 售后 SaveAsync(create=true/false) | 已有 ID 与客户端生成的 Uid，旧审计重放 | QualityControl.AfterSales.Create / Save |
| 售后 CancelDemandConfirmationAsync | 已有 ID，旧审计重放 | QualityControl.AfterSales.CancelDemandConfirmation |
| 售后 Close/Reopen/Void | 已有 ID，旧审计重放 | QualityControl.AfterSales.Close / Reopen / Void |

实施前核对命令类型唯一性，既有确认 CommandType 字符串原样保留。一个真实意图一个 Guid，由客户端生成，不能每次 HTTP 调用重建。CorrelationId 仍只追踪调用，不参与幂等。已有行 Uid 不改为 CommandItemId，不增加无需求字段。

在 SaveSalesOrderRequest、SalesOrderCommandRequest、CloseSalesOrderRequest 增加 CommandId。其余请求已有字段复用；不改公开类型名、namespace、URL、返回类型和业务字段。Contracts 保持 netstandard2.0。

销售创建仍提交 Header.Uid=Guid.Empty，执行器 RequestTargetUid=null；首次 action 内生成正式头 Uid、单号，完整结果保存到回执。重试先查回执，不能先生成单号或把原创建请求改成更新。销售更新目标为 Header.Uid；售后创建使用原客户端 Uid，创建/更新必须用不同 CommandType。

指纹包括实际目标、所有会影响行为的请求头、活动行、删除行、版本与原因，排除 CommandId/CorrelationId。保存行序影响编号，不能排序消除顺序；版本属于业务输入，不能忽略。不要把可变 DTO 引用当作不可变客户端快照。

## 3. 权限决策

当前销售确认使用 ModuleSalesAccess，售后写命令使用 ModuleQualityControlAccess；其余销售写入口没有等价的独立操作权限门禁。不能把当前实现描述为已具备细粒度操作权限。

用户已明确确认：销售与售后各采用维护、确认、取消确认、生命周期四项独立权限，共八项，本轮一并实施：

| 模块 | 权限键 | 入口 |
|---|---|---|
| 销售 | Orders.SalesOrder.Maintain | 新建、更新、删除草稿 |
| 销售 | Orders.SalesOrder.Confirm | 确认 |
| 销售 | Orders.SalesOrder.CancelConfirmation | 取消确认 |
| 销售 | Orders.SalesOrder.Lifecycle | 关闭 |
| 售后 | QualityControl.AfterSales.Maintain | 创建、保存及已确认单据合法补充 |
| 售后 | QualityControl.AfterSales.Confirm | 确认 |
| 售后 | QualityControl.AfterSales.CancelConfirmation | 取消确认 |
| 售后 | QualityControl.AfterSales.Lifecycle | 结案、重开、作废 |

同步 PermissionKeys 的全部/可分配列表、后端保存读取白名单、现有 WPF 分配入口、服务鉴权与页面实际操作控件。模块访问继续管导航，不能自动授予写权限；沿用既有管理员授权规则。权限校验在验证和回执读取之前。售后“保存后确认”分别要求维护和确认权限，不因拥有确认权限绕过保存鉴权，也不自动新增不保存直接确认的交互。

既有销售、售后确认服务也改用对应确认权限。只有模块访问权限的账号不能执行上述写命令，不自动给旧账号补授操作权限。未登录返回 Unauthenticated，已登录但缺操作权限返回 Forbidden；已确认的权限范围不再重复询问。

## 4. 后端实现边界

入口遵循：鉴权 → 扫描纯输入 Validator → 执行器命令锁/回执 → 事务内加载并锁定事实 → 状态/版本/引用/来源校验 → 写事实与业务审计 → 完整回执 → 一次提交。

1. Validator 只做请求形状、非空 ID、合法版本、原因长度等纯校验；不要查询数据库、查当前状态或改写请求。重复字段规则可复用，不为每个字段造类；使用现有自动扫描。
2. 路由与请求目标一致性在执行前验证；所有依赖当前数据库状态的检查在首次 action 内。重放必须早于存在性、版本和状态检查，所以删草稿后仍能重放 true，取消确认后再次确认也不妨碍原取消命令返回首次结果。
3. 销售沿用原连接默认事务隔离，售后沿用 Serializable。执行器命令锁先于业务锁，其后保留原头、行、来源锁定顺序及来源接收/退出参加父事务的约定；子服务不提交或清空父事务。
4. 保存头行、单号、来源退出、审计和回执同事务。禁止在执行器外先写单据，再写回执；禁止一个服务调用另一个拥有独立事务的命令入口。
5. 售后 Result.AlreadyApplied 仅按本次 IsReplay 修饰响应，持久化首次结果不被改写。销售保持既有结果类型，不为重放新增前端必需字段。
6. 销售错误按具体分支映射 Validation、NotFound、VersionConflict、BusinessBlocked；仓储错误利用结构化 ErrorCode，不解析中文消息。公共 CommandConflict/CommandBusy/OutcomeUnknown 原样透传。售后现有业务专有码（特别结案阻断）保留，不把所有异常统一成 400 或 409。
7. CancellationToken 传到支持它的调用及提交前检查；销售新增 token 参数可使用可选参数同步 Controller/Refit/调用方，不改变 HTTP。未知提交由公共执行器处理，不能被模块 catch 转成“肯定未提交”。
8. 保留售后已确认单据的合法补充范围、销售全量行与删除行/行号暂存、非标身份、取消确认安全退出、销售关闭和售后正数量结案阻断。此次不补交付查询、商业修订、恢复销售订单或新状态。

## 5. 删除旧执行与回放，保留业务审计

- SalesOrderLegacyExecution：删除旧事务包装。Query 若仍使用只读错误包装，将这部分迁回 Query 的小型私有方法，移走仍有消费者的规则/异常后删除该旧文件，不能直接删掉仍被调用的规则。
- AfterSalesLegacyCommandExecution：删除 WriteAsync、ChangeAsync、指纹、回放及旧事务。保留必要审计前后快照能力为模块内部的窄辅助，不承接业务命令调度。
- 售后 LockCommandAsync 接口、实现及确认调用，在全部售后命令接公共执行器后一起删除；确认中的 GetByModuleCommandAsync 历史身份检查同时退出。不能在部分命令仍用旧审计身份时提前删除。
- 销售取消确认的 GetByCommandAsync/机器结果反序列化删除。售后命令不再写 Result+Before+After 回放包，不再把指纹放 RelatedObjectsJson。
- BusinessOperationLog 继续保留真实操作、对象、操作者、原因、相关对象和前后变更事实；CommandId 仍可用于关联，CorrelationId 使用已有独立字段。现有审计不得因回执统一丢失。销售原本没有审计的保存/删除/关闭不顺手扩建详细审计体系。
- 公共审计仓储方法若还有其他模块消费者，不全局删除。本次只删除本模块已无消费者的代码和直接相关旧说明，不批量改历史实施记录。

## 6. 客户端必须同步收尾

重点文件：SalesOrderDetailViewModel、SalesOrderManagerViewModel、AfterSalesDetailViewModel，以及直接 Feature Service、编辑 Model、XAML 和权限分配页面。复用既有 ApiCallRunner，不新建全项目通用重试框架。

### 原请求与互斥

- 请求发出前完成编辑提交/本地验证并深拷贝请求，固定目标 Uid、版本、行 Uid、顺序、原因、创建标记、CommandId。重试不重弹原因、不读取当前选中行替换目标。
- 从发送中开始冻结实际字段、表格、行增删/排序、保存以外会改变该单据的操作及页面关闭。不能只禁用保存按钮。
- 结果未知保留原请求。OutcomeUnknown、CommandBusy、ServiceUnavailable 进入待确认；此前已未知时，后续 RateLimited/Unauthenticated/Forbidden 不清除它；首次明确前置拒绝不能永久锁页。明确业务失败结束意图并允许用户修正，新的意图才换 ID。
- 销售管理页取消确认、关闭、删除草稿都要保留各自原目标，不能只保护现有确认。允许最小方案在未决期间阻止换页/刷新/选中切换，并保留可用重试入口；不得隐式改变批量/逐单语义。
- 售后旧“操作→指纹/ID”缓存不足以保留请求。普通保存及生命周期动作改用完整快照；与现有保存后确认状态互斥，避免普通保存未知时再发另一份保存。
- 页面实例内恢复即可，不增加磁盘缓存或跨进程恢复承诺。

### 成功后的当前事实

- 回执只证明原意图成功。销售保存/取消/关闭、售后写命令成功后读取当前详情，不用历史回执 Version 解锁最新表单。
- 详情刷新失败进入“操作已完成，仅刷新详情”状态，重试只查询，不重发写命令；冻结旧表单。列表可刷新当前事实。删除成功直接移除/刷新列表，不强求读取已不存在的详情。
- 销售新建确认目标后更新页面单据身份/导航键，原空 Uid 创建请求不被改成更新请求。
- 售后保存后确认保留两个不同 CommandId 和阶段状态。保存未知只重试保存；确认未知只重试确认；确认版本取本次保存结果，冲突后由用户重新判断，不自动换成更新版本重试。不要借“刷新当前详情”自动确认他人后续修改。
- 已有确认重试测试全部保留，身份切换不能让另一操作者复用并执行原意图。
