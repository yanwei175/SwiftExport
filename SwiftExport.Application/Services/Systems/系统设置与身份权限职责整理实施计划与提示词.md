# 系统设置与身份权限职责整理实施计划与提示词

编制日期：2026-09-25。状态：待实施。本文依据当前源码盘点；只规划职责和目录整理，不授权改变认证、权限及系统设置业务规则。

## 1. 目标与边界

让开发者通过文件夹区分“维护系统资料”“识别当前用户”“维护账号”“判断权限”“分配权限”。Application 的接口与实现按相同能力路径对应，Core 仓储接口和 Infrastructure 实现按所属资源对应。

一次连续实施，内部先整理系统资料，再拆身份权限，最后清理失效文件和验证，统一 Review。无需每移动一个模块就停下来等待确认。

保留简单 CRUD，不为每个方法创建服务，不引入审批、CommandId、命令回执、第二套事务框架或新的权限模型。保持 HTTP、Refit、公开 DTO namespace／字段与现有客户端行为。内部 namespace 随目录迁移。

当前工作区已有 SalesOrders 扁平目录迁移及空服务删除，不得覆盖或回退；执行者先记录工作区基线，区分本轮与既有改动。


小型 Systems 服务继续以资源服务包含查询和维护，不机械再加 Query/Maintenance 目录。身份权限则按下面的真实消费边界拆分：

| 新接口 | 接收原方法 | 主要消费者 |
| --- | --- | --- |
| IAuthSessionService | AuthenticateAsync、GetCurrentUserAsync、IsCredentialVersionValidAsync | AuthController、CredentialVersionTokenValidator |
| IUserAccountService | RegisterAsync、ChangeOwnPasswordAsync、ResetUserPasswordAsync、GetUsersAsync | AuthController；每个方法保留自己的身份和管理员门禁 |
| IPermissionEvaluationService | GetProjectionAsync、HasPermissionAsync | Session、权限维护、公共命令和业务服务等所有运行时鉴权消费者 |
| IUserPermissionAssignmentService | GetUserModulesAsync、SaveUserModulesAsync | AuthController 的管理入口 |

IUserAccountService 只聚合小规模账号维护及管理用户选择列表，不加入权限投影和分配逻辑；未来用例增长再拆，不预先创建用户 Query 服务。

保留 AuthController 的八个现有动作和路径，注入窄接口即可，不需要拆成四个 Controller。同名 WPF Authentication/IAuthService 是客户端服务，不能被全局替换成后端接口。

## 4. 其他层如何对齐

### 系统资料

- Core/Interfaces/Systems 与 Infrastructure/Repositories/Systems 采用 Dictionaries/Types、Dictionaries/Data、Currencies、ExchangeRates、ViewRoutes、Numbering 对应目录。
- Core/Entities 中相关 Systems 与 SystemEntities 的实体归同一 Systems 能力树，实体名、Table 名、字段及结构元数据不变；只处理本轮对应实体，不清空其他历史目录。
- WebApi/Controllers/Systems 按资源归位，保留 Controller 类名和原路由特性。检查 BaseController 继承动作，不能因搬迁漏掉或新增写入口。
- Contracts/Apis/SystemApis、DTOs/SystemDtos 内按同资源归位，公开 namespace、Refit 签名、序列化字段保持不变。Requests／Responses 放各资源下；ClientVersionInfo 可留现有 Updates 契约目录，不做无意义重复搬迁。

### 身份与权限

- Application/Models/Auth 的认证结果归 Session，权限投影归 Permissions/Evaluation；不要让前端引用 Application 模型。
- Core/Interfaces/Auth 和 Infrastructure/Repositories/Auth 内，认证读取与账号维护归 Accounts，权限事实与分配仓储归 Permissions。本轮允许一个现有仓储供两个窄 Application 服务使用，不为接口对称复制 SQL 或再套转发仓储。
- IAuthRepository、IUserPermissionRepository 及 SysUser／SysRole／SysUserRole 仓储先按事实归位，不在本轮重写持久化协议。GetActiveUsersAsync 可继续由当前权限仓储提供，账号服务注入复用即可。
- ICurrentUser 保持当前 Core 身份上下文位置，WebApi CurrentUser、JWT 签发、凭据校验、DevUser 继续归 WebApi/Authentication。IAuditStampService 属于审计基础能力，本轮不因处于 Auth 文件夹就混入权限分配。
- Application 内移动的密码实现和接口同步所有消费者；不把 BCrypt 或密码策略放到 Contracts。
- Auth DTO 可按 Session、Users、Permissions 物理归位；IAuthApi 保留客户端聚合契约，八条路径和现有账号密码传输契约不变。

根目录的 IBaseService、Core IRepository 是基础抽象，保留现有位置；IBOMService、IBomExecutionReader、BOM 仓储接口属于另一业务模块，本轮不为清空根目录而迁移。完成记录列明保留原因。

## 5. 必须保持的行为

### 认证与账号

- 登录只接受现有活动账号和 BCrypt 密码验证；用户不存在和密码不对保持原响应。
- JWT claims、CredentialVersion、Token 生命周期和验证链不变。密码修改／重置之后旧凭据失效规则必须保留，不能让 Token 验证器误接“仅查用户存在”的新方法。
- me 继续通过唯一权限投影获取角色和权限，不在 Session 复制权限展开规则。
- 注册必须由当前真实 Admin 执行，新用户不自动获取角色或模块权限；保留持久化时管理员身份复核。
- 本人改密仍校验旧密码；管理员重置仍保留目标限制、并发／凭据版本条件和原错误映射。
- 不记录密码、密码哈希、完整 Token；不改变开发身份开关、生产阻断、中间件顺序、匿名端点或授权特性。

### 权限

- Evaluation 是唯一投影和判断入口，未知权限键不放行；所有业务服务迁移到该窄接口，不再持有权限分配能力。
- Admin 固定权限、可分配键集合、现有采购兼容映射保持；模块访问和其他细权限关系不能重新解释。
- 管理用户列表与分配读取仍检查当前真实 Admin。
- 分配保存保持整组替换、目标 Admin 保护、Serializable 事务、仓储内操作者与目标复核、失败回滚与 Session 清理。不要拆成多次独立提交。
- 权限更新何时影响当前 Token、me 和客户端界面沿用现状，不新增缓存或主动刷新协议。

### 系统资料

- 字典类型／数据的层级、受保护记录、删除约束、启用、重复编码与版本规则保持。
- 币种／汇率、页面路由的查询投影和服务端保留字段保持；批量保存仍全成全败。
- 单号格式、序列作用域、事务参加方式和并发分配 SQL 保持，不把编号请求改成只读 Preview 或强制幂等。
- 客户端版本入口保持现有匿名与配置读取行为，不新增数据库表。
