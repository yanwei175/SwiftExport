# 数据迁移与种子总纲

本文定义 SwiftExport 的数据库迁移、SQL 脚本、基础字典、单号规则、开发种子数据和本地数据库初始化原则。

本文补充 [数据模型总纲](数据模型总纲.md)、[测试与验收总纲](测试与验收总纲.md)、[领域模块总纲](领域模块总纲.md) 和 [ERP 业务总纲](erp-business-blueprint.md)。涉及具体表结构时，源码和数据库脚本事实优先于本文。

## 1. 总体目标

数据迁移和种子体系要解决四件事：

1. 新开发环境能稳定初始化基础数据。
2. 新表、新字段、新索引可以通过幂等脚本安全补齐。
3. 基础字典、单号、路由、币种、测试客户、供应商、产品和 BOM 能形成可验证业务样本。
4. 已有业务数据不能因为开发方便被静默删除、重置或覆盖。

本文不要求立即重构所有历史脚本。后续新脚本和新种子按本文执行，旧脚本按兼容迁移逐步整理。

## 2. 文件位置

SQL 脚本：

- `tools/sql/**`：项目级独立 SQL 脚本。
- `SwiftExport.Infrastructure/Migrations/**`：Infrastructure 侧迁移资料。

种子工具：

- `_tools/DbSeed/**`：数据库种子工具。

相关源码：

- `SwiftExport.Core/Entities/**`
- `SwiftExport.Contracts/SysEnums/**`
- `SwiftExport.Infrastructure/Repositories/**`
- `SwiftExport.Application/Services/**`

## 3. SQL 脚本命名

新增脚本建议命名：

```text
yyyyMMdd_<area>_<purpose>.sql
```

示例：

```text
20260702_order_demand_execution_link.sql
20260702_inventory_outbound_tables.sql
20260702_seed_core_dictionaries.sql
```

规则：

- 日期使用脚本创建日期。
- `area` 使用业务模块或技术范围，例如 `product`、`order`、`inventory`、`system`、`seed`。
- `purpose` 简短说明目的。
- 同一个业务任务的表结构和种子数据可以拆成两个脚本，避免初始化数据和结构迁移混杂。

## 4. 幂等脚本规则

数据库变更脚本必须尽量幂等。

新增表：

- 先检查表是否存在。
- 表结构默认包含 `Uid`、`Version`、`IsDeleted`、审计字段。
- 单据行必须包含 `LineNumber`。

新增字段：

- 使用 `COL_LENGTH` 或等价方式判断字段是否存在。
- 给新增非空字段时必须考虑默认值和历史数据。

新增索引：

- 先检查 `sys.indexes`。
- 业务唯一索引优先过滤 `IsDeleted = 0`。

禁止：

- 普通开发任务中直接 `DROP TABLE`。
- 未确认影响范围时批量 `UPDATE` 历史业务数据。
- 用迁移脚本清空正式业务表。
- 用脚本覆盖库存流水、已过账单据或审计字段。

## 5. Entity / SQL 同步规则

修改 Entity 后必须同步检查：

- 数据库表和字段。
- Repository SQL 字段映射。
- DTO / Request / Response。
- Refit API 和 Controller。
- 前端 Model、DataGrid 列和 Mapster 映射。
- 测试与验收场景。

新增字段时要明确：

- 字段是业务事实、展示字段、冗余字段还是临时计算字段。
- 字段由前端输入、后端生成、单据回写还是系统计算。
- 字段是否需要索引、唯一约束、默认值或枚举约束。

## 6. 基础字典种子

基础字典用于稳定页面下拉、业务显示和有限枚举补充。

适合种子的字典：

- 币种和汇率基础项。
- 贸易条款。
- 付款方式。
- 运输方式。
- 物料类型显示值。
- 供给方式显示值。
- 单据状态显示值。
- 仓库类型。

规则：

- 业务逻辑判断优先使用枚举或稳定编码，不依赖前端显示文本。
- 字典种子必须可重复执行，不重复插入。
- 字典项应有稳定编码、显示名称、排序和启用状态。
- 删除字典项要谨慎；历史单据可能仍引用旧值。

## 7. 单号种子

单号服务和 `DocumentSequence` 是业务单据号的来源。

需要种子的单号类型：

- 销售订单 `SO`
- 采购单 `PO`
- 入库单 `RCV`
- 出库单 `OUT`
- PackingList `PL`
- 毛需求 `ID`
- 净需求 `DD`

规则：

- 单号规则必须可读、可排序、可追溯。
- 种子脚本只初始化不存在的单号规则。
- 不在种子脚本中回退当前流水号。
- 如果需要重置开发环境流水号，必须明确只针对本地开发库。

## 8. 基础主数据种子

为了支持本地端到端验收，应准备最小主数据集。

建议最小集合：

- 客户：至少 1 个常规客户。
- 供应商：至少 2 个供应商，用于采购和客供件/供应商仓测试。
- 产品：成品、配件、客供件各至少 1 个。
- 客户产品：客户型号到内部 SKU 的映射。
- BOM：一个成品 BOM，包含普通子物料和客供件子物料。
- 仓库：主仓、供应商虚拟仓。
- 币种：USD、CNY。

规则：

- 种子数据使用清晰业务编码，例如 `TEST-CUST-001`、`TEST-SUP-A`、`TEST-FG-001`。
- 测试数据与真实业务数据通过编码前缀区分。
- 种子数据应支持完整链路验收：销售订单、拆解、转采购、入库、PackingList 过账。

## 9. 业务样本数据

开发和验收样本应按流程分层。

第一层：主数据样本。

- 客户、供应商、产品、客户产品、BOM、仓库。

第二层：未执行业务样本。

- 待确认销售订单。
- 可拆解毛需求。
- 可转采购净需求。

第三层：执行中样本。

- 已确认销售订单。
- 已拆解净需求。
- 已生成采购单。
- 待入库采购行。

第四层：闭环样本。

- 已入库。
- 已出库。
- 已 PackingList 过账。
- 已生成库存流水。

规则：

- 普通种子工具可以生成第一层和少量第二层。
- 第三层和第四层更适合作为验收脚本或手工验收数据，不应随意覆盖。

## 10. 本地开发数据库初始化

推荐本地初始化顺序：

1. 创建数据库和连接配置。
2. 执行基础表结构脚本。
3. 执行增量迁移脚本。
4. 运行 `_tools/DbSeed` 初始化字典、单号、基础主数据。
5. 运行后端构建。
6. 启动 WebApi 并检查 Swagger。
7. 启动前端宿主并跑最小业务场景。

注意：

- 不要在文档和最终回复中复制敏感连接字符串。
- 本地库、测试库、正式库必须明确区分。
- 种子工具默认应面向本地开发或测试库，不应无保护地指向正式库。

## 11. 不可破坏数据边界

以下数据不能被普通种子或迁移脚本清空、覆盖或重置：

- 已确认单据。
- 已过账单据。
- 库存流水。
- 审计字段。
- 业务单号流水。
- 真实客户、供应商、产品、销售订单和采购订单。

允许重建的通常只有：

- 本地开发临时库。
- 明确标记的 `TEST-` 前缀测试数据。
- 未被任何业务单据引用的临时草稿数据。

## 12. 验收要求

迁移或种子任务完成后至少验证：

- 脚本重复执行不报错。
- 新字段、索引、约束存在。
- 软删除过滤和唯一约束符合预期。
- 种子数据不会重复插入。
- 后端构建通过。
- 涉及前端显示时，前端构建或页面加载可用。
- 关键业务样本能跑通最小链路。

如果没有实际执行脚本或种子工具，最终回复必须说明“未执行数据库变更”，并标出需要人工执行的文件。
