# Safe Refactoring Guide

## 适用场景

用于历史代码、大文件、旧架构迁移、模块拆分、Repository / Application Service 抽取等风险较高的重构任务。

## SwiftExport 规则

- 先分析现状，再说明计划，最后修改代码。
- 每次优先只处理一个业务模块。
- 小步修改，控制文件数量和行为变化。
- 重构期间保持 UI 行为、数据库结构和 API 契约不变，除非用户明确要求。
- 大文件采用绞杀式重构：先抽一个方法簇，再逐步转发和替换。
- 修改后输出变更文件、原因、风险和后续建议。

## 修改前检查

- 当前功能入口、调用链和涉及文件是否已确认。
- 准备修改哪些文件，为什么这样改。
- 是否影响数据库结构、UI 行为、API 契约或数据迁移。
- 是否能分成更小步骤。
- 是否有可运行的构建、测试或手工验证路径。

## 禁止事项

- 禁止一次性推倒重写。
- 禁止同时改多个业务模块。
- 禁止为了结构漂亮而改变业务行为。
- 禁止无确认地改数据库结构。
- 禁止静默大规模移动文件或重命名类。
