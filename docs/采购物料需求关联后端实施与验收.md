# 采购物料需求关联后端实施与验收

## 本轮边界

实现已有采购行的独立关联用例，不把用户选择或匹配状态塞入采购详情。待确认和已确认的活动采购均可分次分配剩余未关联数量，整张采购限同一 `SourceType + SourceUid` 来源单据。一个采购行可以贡献给该来源下多个物料需求，同一采购行与物料需求也可以通过新命令多次关联。

本轮只接后端、Contracts 和测试。前端后续做 ShellWindow 可进入的独立页面；采购详情入口仅打开该页面，不传当前单据、选中行或预选内容。采购、采购行、来源和物料选择以及人工匹配全部由独立页面承担。现有采购查询/管理 API 负责选择采购，本用例不复制采购管理查询。

导入或手工创建仍建立 `OriginKind=2` 的无关联草稿；关联不改创建类别或创建回执。来源摘要随后写入头和选定行，完整数量关系仅由 Link 表达，不把多个来源行伪装成一个 `SourceLineId`。

## 接口与接入顺序

四个接口复用 `IProcurementOrderApi`，HTTP 根路由为 `/api/procurement/orders`；全部使用采购编辑权限 `Procurement.Order.Edit`，包括回执重放。Controller 只转发请求，事务、规则和 SQL 分别归 Application、Policy 和 Repository。

| 步骤 | 方法与路由 | 内容 |
|---|---|---|
| 读取所选采购 | GET `/{uid}/demand-association-context` | 头版本、客户、实际供应商、来源摘要、行版本、未关联量、有效贡献及行级阻断原因 |
| 检索所选采购行候选 | POST `/{uid}/demand-association-candidates` | 明确采购行身份，可按来源类型、来源身份、关键词筛选，稳定分页；不自动选择 |
| 预览人工分配 | POST `/{uid}/demand-association-preview` | 提交采购版本及完整分配集合；返回令牌和整组分配后的采购/物料剩余量，不写 Link、不预留数量 |
| 提交冻结命令 | POST `/{uid}/associate-demands` | 同一分配集合、预览令牌、原因及 CommandId；事务内重新验证，不接受客户端推算的释放量或剩余量 |

单条 `ProcurementDemandAssociationItem` 包含独立 `CommandItemId`、采购行及行版本、NetDemandId 及物料版本、`ExpectedSourceDemandVersion`、分配数量、非标人工接受标记。`ExpectedSourceDemandVersion` 是当前 `GrossDemand.Version`，候选字段对应 `SourceDemandVersion`，不是 GrossDemand 保存的原销售/售后单据 `SourceVersion`。

预览与提交共用分配意图 DTO，提交结果复用 `ProcurementOrderCommandResult`。独立上下文和候选是只读数量投影，不能拿 `PurchaseOrderDetailDto` 全单编辑模型代替命令，也不能复用“从需求创建新采购行”的输入来改已有行。

页面提交时冻结完整命令；结果未知只用原 CommandId、CommandItemId 和全部原输入重试。成功后刷新上下文及候选；成功但刷新失败时只重读。新分配使用新身份，不使用旧创建、作废或关联命令去复活历史引用。

## 数量、身份和版本规则

- 本轮保留实体中持久化的可空 `PurchaseOrderLine.UnlinkedQty`；它不是 DemandExecutionLink 字段。查询同时返回有效 Link 汇总，用守恒校验防止两份数量漂移。
- 每个活动采购行必须满足 `QTY = UnlinkedQty + SUM(AllocatedQty - ReleasedQty)`。每次提交按采购行和物料分别汇总本次全部贡献，不能通过拆分贡献超配采购或物料容量。精度四位，数量必须正数。
- 历史 UnlinkedQty 或单位未知不补默认值、不从当前产品或描述猜测。物料单位取 `NetDemand.UnitSnapshot`，采购单位取采购行快照，必须明确且相容，不做隐式换算。
- 标准行检查真实产品、客户、物料类型和采购供货方式。非标来源及采购必须均为非标、同客户和同单位，且每条分配明确提交 `AcceptNonStandardMatch=true`；描述只供人工判断，不自动证明匹配。
- 修复非标确认的 ProductId 强制阻断：明确创建类别、非标行身份、描述及有效单位可确认，标准行仍核验活动产品。非标库存入库能力不在本轮扩展范围。
- 物料及来源必须活动，拆解修订明确，实物依据指纹一致。来源仅技术版本推进且实物依据未变时允许沿用原拆解；提交仍核对当前 GrossDemand、NetDemand、采购头和行版本。预览后事实变化需要重新预览。
- 客供件沿同来源、同根、同修订父子需求及送达父件关系校验；父件已有实际采购供应商时，客供行既定送达供应商须相容。实际供货供应商可不同，不读默认供应商，不绑定收货或消耗仓。
- 采购确认和取消确认都不释放引用；建立草稿或追加关联即占用物料容量并阻断相关物料整组回退。删行、作废按已有规则释放，`ReleasedQty` 不因确认而变化。

## 下游及事务边界

补关联不把入库草稿、正式收货、供应商反馈或历史 PackingList 出货作为统一前置阻断，不读这些下游来决定关联资格。采购数量、产品、报价、实际供应商、送达目标、确认状态和批次保持原事实；不补造历史入库、出货或库存流水。

PackingList 当前过账解析会读取 Link 及采购/物料版本。补关联后旧令牌失效，正式过账按锁定后的当前事实重算；重新预览可继续。已过账历史记录不改写，历史反向仍按原执行证据及流水。本轮没有重构 PackingList；新增 SQL 场景实际验证旧预览提交返回 `PREVIEW_STALE` 且库存不变。

事务使用公共 BusinessCommandExecutor、Serializable 和命令回执。先发现并合并本单新旧引用来源，按来源需求 → 物料需求 → Link → 采购头行顺序锁定，采购锁取得后复核自己的引用集合；发现新来源则冲突返回，不倒序追加锁。已锁来源保护同源执行关系，再读取其实际采购目标用于送达验证。

写入只更新头/选定行的来源摘要、选定行 UnlinkedQty、审计及版本，并新增 Link。仓储返回 RepositoryWriteResult，任一步失败由 Application 在事务内中断，日志及回执同事务。关联保存前后头行、Link 和版本、来源及物料修订、贡献、原因和操作人。命令项身份永久占用；取消 Link 仍保留，数据库约束禁止删除 Link。
