## 改前调用链与事实

`Controller.EstablishFromSourcesAsync → EstablishAsync → RunCommandAsync → CommandPipeline（授权、验证）→ ExecuteEstablishCommandAsync → BusinessCommandExecutor → EstablishInTransactionAsync → BuildPlanAsync → Planner / Initializer → 业务审计 → 执行器回执、提交`。

| 顺序 | 当前步骤 | 读写事实、实现 | 事务角色 |
| --- | --- | --- | --- |
| 1 | AuthorizeAsync、EstablishMaterialDemandsCommandValidator | 登录及 DemandPlanning.Material.Establish 独立权限；CommandId、集合、身份、正版本、重复项 | 事务外；授权先于验证和回执 |
| 2 | ExecuteEstablishCommandAsync | 按 GrossDemandId 排序，将 GrossDemandId、SourceDemandVersion、SourceVersion 投影到匿名对象 `{ Items = input }`；目标为 null | 指纹输入准备 |
| 3 | BusinessCommandExecutor 的准备钩子 | ICommandReceiptRepository → PostgreSqlCommandReceiptRepository：命令租约；来源仓储的 ISourceDemandTransactionPreparation → PostgreSqlGrossDemandDocumentRepository：发现 SourceUid、同来源成员，先来源资源后 Gross 身份租约，并复核集合 | 都在 Serializable 事务及首次快照之前；失败不执行正式写入 |
| 4 | 执行器开启事务、LockAsync、FindAsync | 同一 scoped IDbSession；锁回执身份并读取 command_receipt。相同指纹重放，冲突或未知格式拒绝 | 执行器是唯一事务所有者；重放也由它提交、清理 |
| 5 | EstablishInTransactionAsync 第一轮 | IGrossDemandDocumentRepository → PostgreSqlGrossDemandDocumentRepository.GetByIdForUpdateAsync：逐项按 Guid 排序 `gross_demand ... FOR UPDATE`，先锁完整来源集合 | 父事务参与者 |
| 6 | 主线逐来源校验 | 生命周期 Active，来源需求 Version、SourceVersion；当前依据为空时使用 SourceDemandBasisFingerprintFactory。物料仓储 GetActiveByGrossDemandForUpdateAsync 锁活动 net_demand，同依据跳过，不同依据要求处置 | 父事务参与者；不修改 GrossDemand 状态 |
| 7 | GetNextDecompositionRevisionForUpdateAsync | IMaterialDemandDocumentRepository → PostgreSqlMaterialDemandDocumentRepository：锁全部物料历史，再 MAX+1 | 父事务参与者，保留回退历史 |
| 8 | BuildPlanAsync | IProductRepository → PostgreSqlProductRepository 继承通用 PG 仓储：锁根、直接子产品；IBomRepository → PostgreSqlBomRepository：按有效根 BomNo 读当前共享组成、检查客供子件终端规则。非标不读取产品/BOM | 仓储共享父事务；这里有数据库读取，并非纯计算 |
| 9 | planner.BuildPlan | GrossDemandDecompositionPlanner 纯计算根及直接客供物料、数量、关系、修订、快照；不扣库存/在途，不生成采购 | 无数据库副作用 |
| 10 | 设置来源快照、供应商初始化 | 根+子产品各自 DefaultSupplierId；ISupplierRepository → PostgreSqlSupplierRepository 的批量锁定读取；Initializer 按实际返回的有效供应商独立赋值，不继承父建议 | 仓储共享父事务，其余修改待写实体 |
| 11 | AddDecompositionAsync、EnsureWrites | PostgreSqlMaterialDemandDocumentRepository 逐行 INSERT net_demand，打戳、检查任一写入失败 | 参与同一事务；每来源写入，整批最后提交 |
| 12 | WriteLogAsync、执行器回执和提交 | IBusinessOperationLogRepository → PostgreSqlBusinessOperationLogRepository INSERT business_operation_log；执行器 INSERT command_receipt 后检查取消并 Commit | 只有执行器提交；三类事实共同原子提交 |

事务接线核对：Infrastructure DI 将 IDbSession 指向同一个 scoped DbSession，ServiceBaseContext 和 RepositoryBaseContext 使用它。Gross/Material 仓储 CommandDefinition 传 Session.Transaction，产品/供应商通用仓储传 Transaction，BOM、审计、回执查询/写入均传当前事务。来源/物料仓储不创建业务事务。产品批量 SQL 无新增排序，本批保持原有集合和调用顺序，不宣称它提供额外全局锁序。

失败与重放：未认证/无权限/结构无效在事务外拒绝；已建立同依据计数跳过；失效生命周期、旧版本、不同依据、规划/写入/审计失败均抛入执行器回滚。取消继续向调用方传播。首次提交不能确认返回 OutcomeUnknown，序列化失败由公共执行器分类；事务释放和 Session 清空仍由公共执行器负责，准备租约在事务结束后释放。本批不修改它的失败保护。

下游交接：只建立 NetDemand，记录业务审计与回执，不生成采购订单、DemandExecutionLink、库存流水，不推进 GrossDemand 的状态。后续回退由既有 Reversal 用例保留修订历史，本批不改。

## 辅助类型判断

- GrossDemandDecompositionPlanner：保留。独立数量、根子关系、非标、客供与生产限制规则，有定向测试；不承担读写数据库。
- GrossDemandDecompositionPlan：保留。表达纯规划结果及错误，避免无效行进入写入；不是转发服务。
- CustomerSuppliedMaterialPolicy：保留。真实共享规则，建立、产品/BOM及其他用例使用，不混入当前服务。
- SourceDemandBasisFingerprintFactory：保留。共享依据口径，不能在可读性整改时更换算法。
- EstablishMaterialDemandsCommandValidator：保留。接入公共验证管道，事务前结构验证有独立职责。
- MaterialDemandSuggestedSupplierInitializer：合并并删除。仅这个用例使用、短赋值规则、无独立协作职责；测试通过真实用例保留。
- PlanContext：替换为私有 ProductComposition。携带已读根/BOM/子产品事实；规划与写入仍在主线，不增加 DI 服务或公开 DTO。
- MaterialDemandException、CommandPipeline、BusinessCommandExecutor、CommandRequestValidator：保留。错误协议及真实共享命令机制，本批不修改。
