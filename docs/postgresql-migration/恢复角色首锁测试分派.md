## 两个必要原生场景

1. 独立 owner 先取得角色 SRE，在同一事务建立随机新活动用户和有效管理员关联；使用库中唯一既有有效 SYSTEM_ADMIN 角色，绝不新增/修改/删除该角色。另一真实 backend 调用实际 Store。通过 observer 的 `pg_locks`、`pg_stat_activity` 和唯一连接 ApplicationName 确认候选在角色表锁排队，首 SELECT 尚未执行，不能只等任务未完成或 Sleep。owner 提交后 Store 应读取新管理员并成功恢复；精确验证原五字段、双版本及其他字段/关联原样。随机成功 User/UR 留存登记，主控另行核验，不自动删除成功事实。
2. owner 持角色 SRE、Store 在首锁等待时取消。用新随机不存在用户名即可，无需账号 DML。确认真实等待后取消；等待候选任务和连接终止，然后第三 backend 用有界锁超时取得相同角色锁并回滚。不得吞 OCE、留下异步任务或把等待超时当通过。全库摘要应零变化，由主控实跑核验。

复用现有 PostgreSQLIntegrationEnvironment 门禁，严格固定 `dv_next_pg_failure_tests_20261004`，凭据不输出，`DoNotParallelize`。测试总时限只控制测试屏障，不为生产新增预算或更改隔离。初始化前输出不含凭据的数据库、User/UR/Role UID 登记；成功理论增量 User +1、UR +1，其他 48 表零。初始化失败/预提交拒绝可精确清理本人随机 UID，提交结果未知只能保留清单交主控；不得清库、覆盖角色或删除成功结果。结构/数据前置不满足时明确失败或依现有严格门禁处理，不新建库或修约束。
