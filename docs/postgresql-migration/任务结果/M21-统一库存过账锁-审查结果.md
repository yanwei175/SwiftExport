## 结论与授权

执行 B，Backend 主 Agent，后端 API 工作流。仅新增本结果及更新本人状态；主源码、公共协议、旧交付全部只读。本轮没有实现 PG 写仓储、修改业务代码、连接数据库、执行 DDL、构建测试、Git 操作或启动代理/聊天。

当前 SQL Server 库存内核不是单纯的余额行锁：它同时保护命令身份、CommandItemId、原流水身份、反向/替换不存在的关系、纠错组空集合和缺失余额键。只将 UPDLOCK/HOLDLOCK 改成 FOR UPDATE 不足以接回全部调用。箱单 Serializable 的第一条业务读取也早于 AutomaticPostingScope.PrepareAsync，事务内等到锁不等于得到新快照。

建议主控先串行冻结完整资源准备与偏序，再实施独占 PG 库存写仓储。本文第六节是最小候选，不是已批准协议、已接线或并发验收证据；不引入全局业务锁、占位业务表或长期双库框架。纠错接口有实现和测试，但全 Application 搜索没有生产 CorrectAsync 消费者，不能凭接口新增业务入口。

## 二、库存内核实际顺序、幂等与写入边界

`SwiftExport.Application/Services/Inventory/Posting/InventoryPostingService.cs`：

- PostAsync:23：Protect → 命令/明细校验 → 普通与旧式反向禁止混合 → 库存命令锁 → Apply。普通 CommandItemId 必须请求内唯一；同一库存 CommandId 可分多批追加不同明细，已有明细按指纹逐项重放。
- ReverseAsync:41：命令锁 → 原流水按 .NET Guid 排序，逐条 LockLedgerById → LockReversalByOriginal → 派生原 W/P、负原 delta、历史单位/产品快照 → Apply。不能反向一条反向流水；不同反向明细键占用同原流水时拒绝。
- CorrectAsync:52：命令锁 → LockCorrectionGroup(commandId)。已存在组只走整集合精确重放，要求数量恰好 2×请求数、原身份/反向和替代明细键/输入均一致，不重新验证当前仓库余额。空组才构造反向，再 LockReplacementByOriginal，替代必须与原流水同 W/P、兼容原单位。整组按 W/P/原流水/反向先于替代排序，进入 Apply(validateFinalOnly=true)。
- 旧式反向:110：Reversal 类型输入转换后沿用同路径，额外验证提交的 W/P、delta 和单位等于原流水派生值，不能绕过原事实保护。
- Apply:155：先按 CommandItemId 锁已有幂等事实并比指纹，再只对 pending 取仓库更新锁 → 产品普通读 → W/P 余额锁。全部重放不需要当前仓库/产品/余额仍有效。不能把准备后的权威重放改成强制依赖当前主数据。
- pending 余额缺失：普通事实可建账；全历史反向/纠错不补造余额，要求先数据治理。软删余额拒绝，不自动恢复。反向/纠错可利用原快照构造缺失产品模型；普通事实仍需当前未删除产品及有效单位，IsActive 不属于本方法资格。
- 同 W/P 组每条取 Sequence → 在内存累加 → 插入流水，组尾更新余额一次。普通/单独反向每一步不能负数；纠错允许中间负数但最后余额必须非负。不能新增 BalanceAfter>=0 的数据库 CHECK 破坏合法纠错中间事实。
- 更新返回不等于 1 时 InventoryPostingException 默认 **BusinessBlocked**，并非 VersionConflict。新余额 INSERT 后同一组仍有一次 UPDATE；仓储不会同步更新内存 Version/UpdatedDate，不得借机修正为不同结果。
- Protect:263 只允许已有 Session.Transaction；异常尽力回滚并保留原异常，不自行开/提交事务；其本身没有清空 Session.Transaction。AutomaticPostingScope.Abort 则回滚并清空，外层执行器最终 dispose/清空父事务。调用方不得捕获失败后继续提交先前写入。

`Models/PostingFact.cs` 保留缺省与显式输入语义：JSON 序列化字段集合生成 SHA256 指纹；历史快照回填后不重新计算指纹。无指纹历史流水才走严格旧事实比较。请求比较有 Trim/OrdinalIgnoreCase，但指纹采用原模型规范化字段，不能用 SQL 字典比较或泛型投影代替。

AutomaticPostingScope.cs:31 首条 SQL 是 automatic.IsSchemaReadyAsync，读取 sys.columns/约束元数据，之后才获取库存 CommandIds；它不是一个事务前准备函数。其现有顺序为全部库存命令（.NET Guid）→采购来源→全部入库头/行→全部出库头/行→历史流水发现→全部原流水及反向/替换查询→全部明细键→仓库泛型 GetById(true)→产品更新锁→余额 W/P。泛型仓库 GetById(true) 在 SQL Server 使用 UPDLOCK,ROWLOCK，与内核/删除用同一真实仓库行，但没有显式 HOLDLOCK；不得误记为原 Scope 已使用 IWarehouseManagementRepository.GetForUpdateAsync。

Scope 是批量提前锁定，Ports 后续重复取得已声明资源；RequireGroup/RequireStock/RequireLedger 阻止追加未声明资源，准备时复制输入且不允许换事务或重复准备。箱单已经在 scope 之前锁来源及箱单，PG 只在 scope 内取得事务级 advisory lock 会晚于快照。

人工反向明细键首次业务执行时用 GuidSequentialGenerator 生成，发生时间 DateTime.Now；外层回执成功重放不会再次进入委托。自动反向用 SHA256(AutomaticReverse:command:ledger) 派生稳定键。不要因为自动路径稳定键就改造人工输入/时间或删除回执保护。

## 五、结构、审计和异常不可变约束

Core/DatabaseSchema/EntitySchemaMetadata.cs:249–266：余额 W/P **无过滤全局唯一**，软删旧余额也占用键；仅 LastLedgerSequence>=0 CHECK。流水 DbAppendOnly、IsDeleted=0 CHECK，Sequence 和 CommandItemId 全局唯一，ReversalOf/ReplacementOf 非空部分唯一，W/P/Sequence 普通索引；CorrectionGroupId **没有唯一约束**。LogicalReference 是逻辑外键，当前结构不建数据库外键。

PostgreSqlSchemaGenerator 由同元数据生成序列和只追加触发器（P3100）；已有结构评审不是部署事实，不准关闭保护写夹具。单独取序号不是事实提交顺序：不同库存键可并发，序列消费可能晚提交/回滚留洞。每个余额键的 LastSequence 应等于该键最后成功流水，不要求全库序号连续。

AuditStampService.StampForInsert 使用 `??=`，保留已有创建/更新审计，不重置身份或版本。余额 Update 的时间/操作者由仓储显式计算；流水 INSERT 只追加，不为改主数据回写旧快照。

BusinessCommandExecutor 对分类器认定 SerializationFailure（含业务中及 commit 明确终止）回滚并返回 ServiceUnavailable“并发数据已变化…刷新后重新提交”，无自动业务重试。其他提交不确定错误为 OutcomeUnknown，应原 Command 查询/重试。PG 23505/40001 后事务中止，不能捕获后继续读写；余额零行默认 BusinessBlocked、数据库序列化失败、回执未知结果是不同类别。自动 Ports.MapFailure 目前基于 InventoryPostingException 消息前缀转 COMMAND_CONFLICT，其余 INVENTORY_BLOCKED；数据库未识别异常 WRITE_FAILED。是否让 PG 序列化穿透此层属于主控需确认的错误分类接回点，不能直接宣称现有全部路径已统一映射。

## 六、最小候选及必需准备点（待主控冻结）

### 6.1 不能直接采用的替换

FOR UPDATE 只锁返回行，不锁缺行/空范围。Serializable SSI 检测并发异常而非 SQL Server HOLDLOCK 式阻塞范围；RR/Serializable 从事务首个非事务控制语句固定快照，随后事务级 advisory 等待不能刷新。官方依据：[事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)、[显式锁](https://www.postgresql.org/docs/current/explicit-locking.html)。因此 Scope 内“等完锁后重读”不足以覆盖另一个连接新插入余额/反向；也不能只靠唯一报错就声称幂等重放已等价。

### 6.2 最小资源候选

优先沿用源码已将同仓不同产品通过 W 更新父行串行的事实：准备资源 **库存命令 C_inv(commandId)、全局明细 I(itemId)、原流水关系 L(originalId)、仓库 W(warehouseId)**。W 使用仓库级、非全局身份，保护该仓全部余额，包括缺行；仓库生命周期提交也参与同 W 准备。已有余额仍 FOR UPDATE，Version/唯一索引兜底。这样不再额外造 B(W,P) 租约与余额业务占位表，代价是同仓不同产品额外跨快照串行，与当前父行独占粒度相符。若主控选择细粒度 B，必须另解决删除读取全仓非零余额、父行与 B 锁序及 RR/Serializable 快照问题，不能仅将 W 删掉。

I 是必须：同明细键可能提交不同仓库、不同 Command 内容。L 是必须：反向与纠错竞争同原流水的不同关系，且原流水缺失时无法从 W 派生。C_inv 覆盖原库存命令分批及纠错组（组就是 CommandId），不额外设计 G。直接 LockCorrectionGroup 非 commandId 的任意调用不是当前生产事实，如未来新增须补协议。

全部资源先去重完整声明、稳定排序，在父事务建立快照前取得同物理连接会话租约，父事务 dispose/Session.Transaction=null 后逆序释放；同 scope 不嵌套追加，不借用不同连接/epoch/PID，不支持 Multiplexing/NoResetOnClose；取消、获取结果未知、释放未确认隔离物理连接，清理不覆盖业务结果。可以复用现有生命周期模式，不把库存多资源塞进 DbSession.CommandLease 的单命令占位，不把 SourceDemandLease 变成库存租约。

P04 与来源现状需纠正：DbSession 已有 CommandLease 和 SourceDemandLease；PostgreSqlSourceDemandLock.cs 已有“全部 SourceUID → 全部 GrossUID”30s内部准备租约，SourceType 不分区；但当前全源码引用仅 helper/DbSession/测试，**没有生产仓储/服务调用接线**。此前 M19 未实现结论是旧时间点，本次发现内部实现已出现；也不能把内部存在写成全来源链验收通过。库存准备仍无现成内部实现。

### 6.3 候选偏序及不能跳过的准备入口

建议串行冻结两层偏序，不将此文字当作授权：

1. **事务前**：公共机器 Command 准备 → 全部来源 S → 全部 Gross U → 全部 C_inv → 全部 I → 全部 L → 全部 W（族内同一稳定规则）。该顺序需由主控与来源入口共同确认；当前执行器只接受单 Command 准备，没有业务多资源回调。不能让某路径持来源租约等待 Command、另一条持 Command 再等来源，也不能把自动子库存命令递归当公共 P04 命令租约。
2. **业务事务内**：回执核验 → 来源 Gross/Net/Link → 采购头/行 → 箱单/入出库头行 → 原流水/关系 → I 幂等核验 → W 真实父行 → 自动路径 Product → W/P Balance → 序列/流水 → 余额/单据/审计/回执。同资源已准备可重复校验，但不追加声明。现有箱单“先箱单再 Scope 采购”、人工“先采购再入库”、Scope“库存命令在采购前”不是已经统一的全局顺序，需跨 M19 和箱单草稿锁核对后接回。

锁内批次排序应明确 .NET Guid 与 SQL uniqueidentifier/PG uuid 的差别。现有 C# Order/OrderBy 用 .NET Guid，SQL ORDER BY Uid 用 SQL Server uniqueidentifier；迁移保持结果排序与统一锁键排序各自职责，不能混用后假称稳定一致。

| 必需准备点 | 原因、最小改动边界 |
|---|---|
| 公共执行器 P04 租约之后、BeginTransaction 之前 | 必须在回执 Find 建立快照之前完成业务资源准备；主控可设计必要可选准备回调/用例能力，SQL Server原入口保持；只改 InventoryPostingService 无法达成 |
| 人工入库/反向、出库/反向执行命令外围 | 事务外发现头/行、原流水、仓库、稳定已有明细与来源；事务内按原 ExpectedVersion/来源集合/原事实重验。不把探测当事实，不接收候选变化后临时追加资源；人工反向新明细键生成时机需保持原回执/失败原义 |
| 箱单正向/反向现有 candidate 阶段与完整 AutomaticPostingResources | 在 executor 快照之前准备整批库存子命令/明细/原流水/仓库及来源。Scope 保留父事务声明/验证功能，元数据 SQL、历史发现必须不早于资源保护；无库存交付不凭空申请库存资源 |
| 仓库 Update/Activate/Deactivate/Delete 外层 | 与库存共用 W；否则 Serializable 删除等待父行后仍可能基于老余额事实。不存在/已删仓库仍用身份互斥，不创建仓库占位 |
| 未来直接调用 Post/Reverse/Correct 的父用例 | 必须提供完整准备能力；现有内核不自行开/提交父事务、不自取新的快照、不自动业务重试。全部重放仍由持久化回执/指纹决定，不能强依赖当前失效主数据 |
| 采购/来源退出等提交读者 | 先证明共同 S/U/采购父锁覆盖相关收货/反向；未覆盖的库存否定事实必须加入共同保护或接受现有明确序列化失败路径，不能仅删除 HOLDLOCK |

可探测声明不表示必须让重放读取当前主数据：公共命令先保护身份并确定回执的准备设计须允许已有回执走原权威重放；探测缺失时不能强行拒绝一个已成功命令。库存直接同命令分批也不能被机器回执“一 Command 一结果”的规则误收窄。

上述候选只保护实际生产写路径的参与者。产品修改及未声明的外部 SQL、导入/初始化并非自动服从 advisory；不得声称租约能强制数据库所有写者。上线前由主控清点真实写入口及保护约束。
