2026-10-05主控，来源九方法及M19真实调用审查后核实。仅SQL Server dv_next和PG故障库只读查询、源码阅读；没有新锁实现、比较器、索引或结构变更，不把探针作为全部Unicode兼容验收。

## 已证事实与影响

源GrossDemand.SourceType为Chinese_PRC_CI_AS，实体字符串而非枚举；约束覆盖生命周期0/8/9、Qty正量、标准/非标产品与Version正值，没有SourceType限定SO/CR/MD的CHECK。Receive服务虽规范化SO/CR，原Gross仓储Add仍接受实际传入字符串，不能把服务验证自动变成仓储新规则。

原GetActive/VoidPending按SourceType+SourceUID比较，Manual更新/关闭按SourceType='MD'比较。源常量表明大小写、宽度和部分尾空白等价；直接按原字符串C#哈希会让实际SQL等值来源落不同锁，不能证明空范围互斥。仅ToUpper/ASCII rtrim或当前ICU也不足以覆盖已发现全部字符差异。

当前PG18.6字典collation为und-u-ks-level2、deterministic=false；PG18 catalog使用colllocale，首次旧列colliculocale读取失败已纠正，只读失败保留。前轮PG14值矩阵显示hashtextextended遵循指定非确定collation的case/宽度等值；rtrim四种尾空白后也只证明这些样本哈希一致，未冻结为生产算法。

故障库pg_indexes实际返回：

```sql
CREATE INDEX ix_gross_demand_source ON public.gross_demand (source_type, source_uid)
```
