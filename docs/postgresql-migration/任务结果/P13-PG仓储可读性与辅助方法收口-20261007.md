# P13 PG仓储可读性与辅助方法收口

用户目标：规整项目内类似“属性名称数组 → 元数据名称 → SQL”的写法，检查不必要的共享方法，以开发人员可读性为准；业务编排尽量留在服务层。

本轮使用 Backend 与后端API工作流，主控串行执行，没有启动执行窗口。以本轮开始源码副本为比较基线，保留 P12 及客户产品投影整理的全部未提交成果，不能用 Git HEAD 回退这些成果。本轮源码变化为 Infrastructure 51 个文件（其中删除一个专用辅助文件）和 7 个相关测试文件；Application、Core、Contracts、WebApi、DI、配置、正式数据库结构及业务规则未修改，没有提交、推送或部署。

## 必须保留的元数据/共享实现

不是所有属性名字符串都需要删除。剩余元数据使用已经按真实调用链分类：

- `PostgreSqlDapperRepository<T>`：真正的泛型 CRUD；映射当前持久化集合、写入排除及 CLR 别名，不是 SQL Server 兼容投影。
- `PostgreSqlSalesOrderLineRepository.AddAsync`：沿用基础仓储的 `InsertProperties` 写入集合；调用处有身份、版本和审计差异，因此不改为会重建身份的泛型 Add。
- RBAC、自动入出库、装箱执行证据：私有通用持久化用于多个实际实体，完整实体参数由同一 PG 元数据绑定，保留身份和打戳规则。
- 装箱过账事实读取：私有 `Read<T>` 为多种原始事实执行同一种读取；事实组装由服务的 resolver/preview 完成，仓储不做库存数量决策。
- 入库/出库/采购反向/余额参数读取：`GetProperty` 负责读取实体值及保留 DateTime/枚举/NULL 的 PG 参数类型，不是生成固定 SQL 名称。
- 销售经理关键字数组已经是 PG 物理表达式，仅组合相同 LIKE 条件；不再经过旧名称映射。
- `PostgreSqlInboundReceiptHistoryGuard` 被8个仓储源文件实际调用，保持共用的历史完整性检查；产品中性型号异常分类被两个仓储共用；来源交付 CTE 被两个仓储共用。这些不重复复制到服务层。

服务层辅助类共检查22个，见下表。单一消费者不等于必须内联：独立、复杂且可测试的业务计算器仍有清楚职责。权限通过接口调用，统计包含接口消费者；DI注册计入引用但不等同运行调用。BOM执行 Reader 没有找到生产调用或 DI 注册，但现有测试依赖它，记录为待判断事项，未借本轮删除业务能力或测试。
