## 推荐与当前门槛

**推荐主控评审“资格事务首次查询前，按固定 Kind 对应的一张主表取得 EXCLUSIVE，再取得现有授权锁”的局部方案。** 为使仓储在首次快照前知道 Kind，需要服务/局部接口的最小衔接；当前三方法不能只靠 SQL 翻译完成。保持 Serializable，保留授权→目标存在→ExpectedVersion→状态→写入→审计的业务判断次序，不捕获40001冒充 VERSION_CONFLICT，不自动重试，不新增全局业务锁。

这是**最小写入范围候选，不是最窄阻塞范围方案，也不是已通过验收的实现**。EXCLUSIVE 会阻塞同表其他 UID 的写入及显式行锁读取；授权失败的请求也可能先等待该表。主控须确认这个局部阻塞代价是否符合原约定。若不能接受，本轮没有发现只改资格仓储、且无需其他写入者参与的 UID 级等价方案；应保持阻塞待审，不降为 SSI/通用错误码替换。

当前主控证据为44离线通过、16真实PG中15通过/1失败。失败是 `OrdinaryCrudCompetition_PreservesOriginalVersionConflict`：资格授权已经查询后，普通 Product UPDATE 先提交目标 Version，再到资格 GetForUpdate 产生40001。这个失败未被放宽。本轮独立确认源码能形成该顺序，但没有重跑测试，不能宣称解决。

## 缺口的具体发生点

`ExecutionEligibilityService.SetStatusAsync` 在本地校验、外层事务检查之后，生成随机审计 CommandId，取得同 ID 审计准备租约；随后 BeginTransaction(Serializable)，依次调用 HasExecutionEligibilityPermissionAsync、GetForUpdateAsync、SetStatusAsync 与成功日志。

PG授权方法先锁 sys_role 为 SHARE ROW EXCLUSIVE、sys_permission 为 SHARE，再查询活动用户、角色关系和权限并锁授权行。它没有收到 command.Kind，也不锁三类主数据表。普通客户/供应商/产品 CRUD 不取得这个角色目录锁，所以能在授权读取之后提交同目标的版本改变。GetForUpdate 的 FOR UPDATE 到达时已在旧事务快照内，不能保证读取最新已提交版本。

PG 官方说明：高隔离事务要看到锁等待后的最新数据，表锁须在首个 SELECT/DML 前完成；事后 LOCK 不刷新快照。[LOCK 文档](https://www.postgresql.org/docs/current/sql-lock.html)。因此只在 GetForUpdate 添加目标表锁已经太晚，也不能把 GetForUpdate 简单前移为第一个 SELECT，就宣称等待并发写入后一定返回最新版本。

源 `ExecutionEligibilityRepository` 是授权 HOLDLOCK 查询之后，目标 UID UPDLOCK,HOLDLOCK 读取当前状态；服务用真实 previous.Version 返回 VersionConflict，用 previous=null 返回 NotFound。PG实现目前改变了这个受测普通CRUD竞争场景的可观察结果。审计准备按随机 CommandId，只解决日志准备生命周期，不是同目标互斥。

## 候选模式及具体反例

PG标准锁冲突关系以[显式锁官方文档](https://www.postgresql.org/docs/current/explicit-locking.html)为准。以下等待图为结合本项目调用顺序的推论，未运行死锁复现。

| 目标准备模式 | 判定 |
|---|---|
| 仅 FOR UPDATE / FOR SHARE 目标行 | 需要 SELECT，已有或等待后快照仍可旧；空UID也没有锁对象。不是这次快照前排队的替代方案。 |
| SHARE | 能挡写入，但多个事务可同时持有它，后续UPDATE升级会互等。若先目标SHARE再等全局现有角色目录锁，两个资格请求可形成“第一个等第二个SHARE、第二个等第一个角色目录”的环。不能用当前授权串行假定升级安全。 |
| SHARE ROW EXCLUSIVE | 单独保护写入且自互斥，但与ROW SHARE相容。实际主型号拉取等事务可先持Product FOR UPDATE，再准备Product UPDATE；资格持该表锁后GetForUpdate等待前者行锁，前者UPDATE需ROW EXCLUSIVE又等待资格表锁，形成两方反向死锁。即使读者永不更新该表，它也可能持其他表锁/等其他目标，扩大多方环。 |
| EXCLUSIVE，且先目标再授权锁 | 与写入和显式行锁读取的表锁均冲突；资格在第一步等待时尚无角色/权限/主数据行锁，排队结束后再建快照。普通无行锁SELECT仍可进行；只针对当前Kind对应表，不锁另外两张表。是本轮推荐评审候选。 |
| EXCLUSIVE，但先角色目录再目标 | 不能保留。E1(Product)持角色目录，等W的Product行锁；W是产品拉取等真实产品→供应商持锁事务，等E2持Supplier EXCLUSIVE；E2等E1的角色目录。构成角色→产品→供应商→角色三方环。 |
| ACCESS EXCLUSIVE / 三主表一起锁 | 超出所需，普通SELECT也会受阻，或扩大成无必要的多表协议；不推荐。 |

推荐顺序强调 **target → sys_role → sys_permission → 用户/角色关系/权限行 → 目标行 → UPDATE/审计**。原授权锁内部顺序不变。每个资格请求只有一个Kind，不追加另一主表锁。RBAC锁管理员角色/操作者/角色关系，其当前仓储不调用Product/Customer/Supplier；因此不从RBAC现有逻辑推导反向主数据依赖。以后若新增角色目录持有者读取/锁定主数据，须重新评审这个前提。

EXCLUSIVE不消除其他服务已经存在的产品→供应商与供应商→产品交错，也不刷新其他早已开始的Serializable事务。普通SELECT产生的SSI依赖、授权用户/定义其他写入入口的竞态仍可能产生40001；本轮不得对它们统一做版本冲突映射。

## 最小具体生产衔接与归属

**首选局部契约：** 在现有 `IExecutionEligibilityRepository` 增加一个明确“事务已开始，但任何SELECT/DML之前调用”的准备方法，例如 `PrepareTargetBeforeSnapshotAsync(ExecutionEligibilityKind kind, CancellationToken token)`。这不是事务外审计租约，也不拥有事务，不返回第二连接或创建业务表。只传Kind；表锁方案不需要新增Uid键映射或可配置范围。

## 必须明确的保留与不能保留

- B在目标表准备取得前先提交Version+1：A准备等待结束，再读授权/目标，用最新Version按原判断返回VersionConflict；若ExpectedVersion正好是新Version，应继续原状态检查/正常变更，不能无条件冲突。
- A已取得准备锁并读授权：B普通UPDATE不能继续在A到GetForUpdate之前提交，必须等待A结束。业务判断顺序不变，但原失败测试安排的这个可达插入点被协议消除，不能继续让测试同步等待B提交后才释放A。
- 删除后当前仍不可见：应是NotFound；软删SQL未必增Version，不能用“任何40001=版本变化”判断。删除恢复最终存在且Version符合时按当前状态处理；B回滚则没有成功版本变化。测试恢复仅用已明确范围的随机夹具，不创建新恢复业务。
- 授权已被撤销：必须返回Forbidden且无目标写入/成功审计，优先于目标NotFound/VersionConflict；目标表锁不代替角色权限验证。等待RBAC撤销提交后才首次查询仍须看到撤销事实。
- 无关SSI依赖或数据库故障：保留原异常/HTTP处理，不用查询另一个连接或回滚后补读猜测版本，也不返回预期版本错误掩盖故障。
- 表范围的阻塞代价、未授权操作者在拒绝前可能等待目标表、三个Kind请求分别持各自主表并等待既有角色目录时的队列叠加，均是方案实质限制。若要求“未授权立即拒绝且不影响主数据写入”或“不同UID完全并行”，该方案不能声称完全保留；主控应向用户确认明确需求后取舍，不能用迁移授权自动扩大这类约定。

## 测试屏障与真实PG验收

原失败测试的 `PermissionGate` 停在真实授权读取后，然后同步等待B UPDATE提交再释放A。修复后A已经持EXCLUSIVE，这个屏障会变成测试自身互等/超时。**保持VersionConflict语义断言，拆成两个真实顺序场景，而不是放宽到40001：** B先持写锁/提交、A在目标准备阶段排队，释放B后检查最新版本；另一个A授权后停住，B UPDATE必须实际阻塞，释放A后验证两个事务的正确先后结果。可用已有独立观察连接与本地Npgsql ProcessID，避免用业务连接查询PID提前建立快照。

最小验收矩阵：

1. Product/Customer/Supplier三Kind分别以真实普通仓储更新竞争：B未提交→A准备排队→B提交，A旧ExpectedVersion为VersionConflict；B回滚则A按原版本继续。不能只保留Product的直接version UPDATE。
2. 竞争后ExpectedVersion恰为最新版本，以及新版本同状态：依次验证成功或StateBlocked，不接受统一VersionConflict；版本检查先于同状态判断。
3. 普通软删（Version可未增）、物理删除、受控删除/恢复最终可见与不可见，分别验证NotFound/VersionConflict/正常状态路径；无成功审计的业务拒绝保持原子性。
