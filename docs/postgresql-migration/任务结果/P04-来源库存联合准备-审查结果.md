`PackingListRepository.SourceExit.cs` 的来源退出检查还通过 Gross→PL 行→头及关联最终出库读取活动草稿/已过账/异常历史计数。该历史 Guard 必须保留；同源 U 只有在装箱草稿等全部绑定写者参加时才保护新增关联空范围。已知下游头由相应 T/D 锚点稳定，不能用“只锁目前查到的行”宣称覆盖未来关联。

## 3. 可执行的全局资源顺序候选（待主控冻结）

```text
已有 C_cmd → 全局需求 C_item → S → U → P → G_group → T
           → D_in → D_out → C_inv → 库存 I → 原流水 L → 物理 W
```

每个资源族先收齐全集，再按稳定命名空间计算的有符号 64 位 key 升序去重；跨族实际 key 碰撞只持有一次，释放逆序。S/U/C_item 沿用已冻结算法；新域由主控冻结精确字符串/编码/键算法。C_cmd 与 C_inv 语义不同，需求 C_item 与库存 I 也不同，即使 GUID 一样不得合并语义。缺失但已知的 P/G/T/D/L/W 仍声明；未知绑定不伪造上级身份。没有来源的消费者跳过 C_item/S/U；不存在原机器回执的逐来源采购不新增 C_cmd。

此候选保留来源前缀和库存 C_inv→I→L→W 的相对顺序。G 原来先于来源行 SQL，但联合准备全部在 SQL 事务前取得，业务仍保持原查询/错误顺序；生产混用旧 G 事务锁和新 S/U 准备期间，不能假定已统一顺序。跨组获取必须由一个联合所有者协调，禁止库存先持有再调用可能等待的 Source helper，禁止在 Scope/业务中补拿较早的资源。

实际物理 SQL 顺序并不完全统一：PL 头行后 Scope 锁 PO，采购反向 PO 后读下游；Scope L→I，统一库存 Apply I→仓/余额。优先保留业务 SQL 和 Guard 的位置，依共同且完整的事务前资源锚点阻止两个相交消费者同时进入反向物理锁序；这只在**所有相关写者参加相同域**时成立。尚未参加的草稿/反馈/仓库/直接服务调用不在此证明内。若真实 PG 用例仍出现物理锁环，按共享文件归属单独评估最小重排，不能在报告中提前宣布无需变化或全站无死锁。

W 粗粒度与当前锁仓实体语义相符，不增加任意全局业务锁。自动产品行锁保留原位置/职责；普通库存产品读取的可见/单位与重放规则不改成本次额外全局 Product 锁。产品其他写链没有全站审查，相关专项需主控确认覆盖。

## 4. 最小联合发现、获取、重验算法

1. **原授权/纯输入检查后，原 C_cmd 先取得。** 使用同一物理连接，禁止父/环境事务、Multiplexing、NoResetOnClose、同 Session 并发获取和重复/嵌套准备；核验现有命令租约当前 held 且非 AttemptPending。普通库存用例只有原 C_inv，不强加机器回执。
2. **事务外发现身份和绑定，限定为本用例读取/写入的资源足迹。** 需求 Item→所有历史 Link→Net→Gross→Source→同 Source 全部 Gross；输入已知 Gross/Source 合并。目标 PO 查历史行与 ownLinks（头或行归属），关联输入 Net/Item 合并；IN 的 SourceLine→PO owner；PL 合并旧/新 Gross、历史行 owner/group/warehouse；自动命令按已验证候选的稳定派生身份列出 IN/OUT/I/C_inv；反向查原执行、文档历史流水及 reversal/replacement、更正组成员、真实 W/Product。不能只读 active/非软删/正数量，不能把缺源过滤为独立 PO。也不能递归锁所有邻居的全部单据，扩张成 ERP 全局连通分量。
3. **收齐候选后按第 3 节顺序获取整组 session advisory locks。** 来源 lease 与新增窄库存/目标 lease 可分开实现，但须由联合 owner 逆序收放，复用 DbSession 物理连接/epoch/PID 和异常分类，不能把库存业务字段塞入 Source lease 或创建提供者切换框架。原事务内库存/Scope 锁入口应检查并借用已完成 lease，缺声明直接拒绝，不能开始新的等待。
4. **最后一个资源取得后，在同连接、无父事务下重新读全部绑定投影和成员覆盖。** 比较 Item→Net、Net→Gross、Gross→Source、同源新增成员、PO 行 owner/ownLink 身份、PL 行→Gross/group/仓、IN 来源→PO、单据→历史流水及库存 key 等。本次生产消费者还读取了某种会决定资源身份的绑定，就纳入这次重验，不能只调用 Source 原先的重验后返回。
5. **绑定出现/消失/迁移或新增未覆盖成员：释放全部联合业务组后重新发现。** 库存/目标和 Source C_item/S/U 一并逆序释放；原固定 C_cmd 可以继续持有，但其连接/身份不可信时全数放弃并失败。不要边持有库存边单独释放/重拿 Source，不把发现循环升级为业务 action/事务重试。发现、等待、重验和再次发现共享一个绝对截止时间。
6. **资源重验通过才进入原 Begin/回执/业务流程。** 不提前取号、确认供应商/业务版本、重建预览 token、新增业务回执；保留各来源原独立提交和缓冲发布时点。仅业务 Version/状态/数量改变但资源身份未变时，进入原校验返回原错误，不为了让预览通过反复替换候选。准备期间回执候选只能用于规划重放最小资源，最终仍以原事务内 Find/fingerprint 为准，避免历史重放被当前已删除主数据阻挡；候选消失而原事务无回执时沿用原无有效执行候选错误。
7. **进入事务后新发现未声明资源/归属变化：回滚并返回原冲突/SourceChanged/未声明错误。** 不补拿逆序锁，不回到发现阶段执行 action 第二次，不自动重取号。真实 `40001` 按现有数据库类别返回可用性失败，不改为 VersionConflict、不吞掉后继续提交。
8. **退出先结束父事务并 Dispose，清空 Session，再逆序释放库存/目标、来源，最后 C_cmd。** Scope.Abort 清空 Session 引用不代表外层事务对象已 Dispose；租约不能由内部库存方法提前释放。获取结果未知、unlock 失败、连接 epoch/PID 变动、仍有父事务时按现有隔离模式关闭/清池该物理连接并使全部相关槽无效，不把可能携带 session lock 的连接放回池。提交未知不重新执行；沿原 CommandId 查询回执/原证据。

现有 `PostgreSqlGrossDemandDocumentRepository.MaterialPreparation.cs:17–61` 已实现历史 Item/Net/Gross/Source 发现、Source 整组获得后重验和共享来源截止时间；`PostgreSqlSourceDemandLock.cs:22–85` 有 held/AttemptPending、连接检查和释放保护。可复用这些机制，**但它们当前不知道 P/G/T/D/C_inv/I/L/W，所以并不完成联合第 4/5 步**。在已覆盖 S 下给本事务新生成 Gross 借用事务 U 的既有规则，也不能泛化成任意新库存 I/旧 L/新仓可以事后补拿。
