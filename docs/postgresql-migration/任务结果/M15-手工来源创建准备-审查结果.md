## 2. 身份分配与数据库取号不是同一件事

- GuidSequentialGenerator直接Guid.NewGuid字节并混入UTC天/毫秒尾部，不读数据库、不推进DocumentSequence、不调用产品、不修改请求。
- 候选提前分配会改变随机值及尾部时间的生成时点；原契约没有预先指定UID，不能承诺字节或时间尾部完全等同旧action时点。非标NS SKU用该UID前12位；首次写入、SKU、BasisFingerprint、Workspace/回执必须共用这一身份。
- SourceDemandBasisFingerprintFactory的输入含SkuSnapshot、物料快照、数量/交期等，不含SourceNo。不可提前计算快照或指纹；提前身份不等于提前业务实物事实。
- DocumentNoService把DocType Trim/Upper，默认SerialWidth=4，以BusinessDate的yyyyMM调用DocumentSequence，再构造MD年月号码。
- SQL原GetNextAsync传当前Transaction，UPDATE UPDLOCK/HOLDLOCK后缺键INSERT；PG使用同父事务的单语句INSERT ON CONFLICT递增并RETURNING。不使用nextval，取号行更新在代码接线中属于业务事务；真实回滚仍须实库证明。
- 两仓储为DocumentSequence行生成另一个UID，不能拿它作为Gross UID。不得把数据库取号移到准备阶段，不因提前Gross UID给SourceNo预占号码。
- DateTime.Today继续在原取号位置求值，准备等待跨天/月时仍按业务action实际日取号，不提前冻结BusinessDate。取号后的Add/重读/回执失败仍走原父回滚；成功回执重放不再分配数据库单号。

## 4. 缺失U、身份碰撞和重放边界

PGGross AcquireBeforeTransactionAsync复制Distinct集合；事务外Bindings包括所有生命周期和软删，先查声明Gross现存绑定，再并声明S，发现这些S所有Gross成员，统一先全部S再全部U稳定long键获取；获取后重查绑定及成员覆盖。绑定变化时全释放重新发现，30秒总预算，不执行业务action重试。

- 缺失候选：显式S(uid)+U(uid)仍能取得会话锁；无需先INSERT占位。Add既有S/U覆盖，允许正常单行INSERT；不存在事实不能被伪造为现存需求。
- 候选UID已存在：准备会发现其真实SourceUID，纳入S；含软删、关闭、作废身份，不把它当不存在。原INSERT仍提交给唯一约束/原异常路径，不能先读取后返回“创建成功”、覆盖现存行、吞重复错误或重新抽UID重做action。
- 获取等待期间别的受协议保护写者提交同U：after重查发现映射变化会释放并重新取得完整S集合，再由业务INSERT暴露原碰撞。资源准备重试与重新生成身份/重试业务是两件事。
- 不同Source抢同Gross U、同Source抢不同Gross U均串行；S不按SourceType分区。非合作直接SQL写者不受会话锁保护，不能把协议当成数据库全局强制锁；唯一约束仍最终判重。
- 手工创建没有客户端ExpectedVersion。不能新增版本前置；Add保留给定非空UID/正Version、缺省版本1，碰撞不可映射Update版本冲突。Update/Close才有原Version校验。
- 不同CommandId合法相同业务输入仍是两个独立创建，不按内容去重。
- 同CommandId成功后的准备候选不是原成功UID；prior权威结果必须胜出，新候选不能参与fingerprint/target，不读原需求当前状态来替代历史结果。关闭/修改/产品变化后同命令也应返回旧DTO。
- 同CommandId并发第二请求先等Command租约，再生成自己的候选和准备，随后Find重放。通常其新资源无竞争；“绝不额外阻塞重放”不能由随机概率推断。需要人工构造冲突/等待测试。
- 指纹冲突、旧回执格式、损坏JSON也在准备之后判断；不得提前业务验证改变回执错误优先级。新准备失败时还未读回执，这一技术可用性差异必须保留说明。
- 生成器、锁摘要、初始化数据库不作绝对无碰撞假设。准备协议只保证合作写者与读者的资源发现/互斥；真实物理连接与首次快照必须另验。
