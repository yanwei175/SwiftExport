## 实际缺口与最小修复

真实PG两backend复现SQLSTATE40001：Serializable外层已固定快照，测试装饰器在实际自动端口兼容审计读取后，第二backend对已登记测试单位行执行同值UPDATE，外层FOR UPDATE发生“由于同步更新而无法串行访问”。这不是手工构造PostgresException，也不是RAISE模拟。

首次测试m24-automatic-serialization-red.trx整体1失败：真实40001进入AutomaticPostingPorts.CreateAsync后被MapFailure包装成AutomaticPostingException/WRITE_FAILED，BusinessCommandExecutor现有分类器失去原驱动身份，不能产生既有ServiceUnavailable。原失败TRX保留。

生产改动仅三个已有Application文件，共新增8行：
- AutomaticPostingScope.cs：一个内部判断，复用当前会话IDatabaseExceptionClassifier，只有SerializationFailure为真。
- AutomaticPostingPorts.cs及AutomaticPostingPorts.Reversal.cs：原catch之前加限定filter，仍Abort全组，然后throw原异常。
未改MapFailure其余业务/取消/版本/写入映射、外层执行器、SQLServer分类器、API/DTO、DI、隔离、资源顺序或业务规则；没有添加重试、数据库框架或新业务锁。原SQLServer分类器不会返回SerializationFailure，所以此限定分支不改变原SQL行为。Application修改仅为PG真实失败可按已有协议分类的必要技术修复。
