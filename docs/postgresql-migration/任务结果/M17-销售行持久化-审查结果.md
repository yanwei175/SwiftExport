## 2. StageLineNumbers算术与唯一键

令M为当前有效行最大LineNumber（空集合0），N为最终活动行Count，Offset=`(long)M + (long)N + 1`。源再检查`Offset + (long)M > 2147483647`，成立时THROW **52720**、原消息 **销售订单行号暂存超出 int 范围。**，否则将每个当前有效行号加`CONVERT(int,Offset)`。

实际保存先要求至少一条明细并完整申报现有行；N>=1，既有表CHECK LineNumber>0。在该合法输入范围中，暂存结果区间为`[M+N+2, 2M+N+1]`（有行时），高于旧区间`[1,M]`及最终`[1,N]`；不同旧号加同Offset仍不同。因此**暂存这一条集合UPDATE的新号不占任何旧号，执行次序不影响合法唯一性**。恢复先软删待删行，再逐条更新现有行，再逐条新增最终行；所有还未恢复行仍在安全区，最终请求行号又由index+1生成，故不需要另设负行号、倒序更新、临时表、可延迟约束或禁用唯一索引。

例：旧号1、2，最终两行交换，M=2/N=2/Offset=5，先暂存到6、7，再按请求UID恢复2、1，唯一键安全。直接把1↔2压成普通单条交换UPDATE没有此保证。PG非可延迟唯一性立即检查，不能用SET CONSTRAINTS对现有索引推迟；本结论依据[官方约束检查说明](https://www.postgresql.org/docs/current/sql-set-constraints.html)及源码区间推导，尚非本实例实测。

上界包含`2M+N+1`，不能只检查Offset<=int.MaxValue，也不能以int先算出溢出再转long。N=2时M=1073741822达到上界成功，M=1073741823应拒绝；必须测试边界相等/超1。空集合也先做源算术，N=int.MaxValue时仍应拒绝，不能提前return0改变THROW路径；正常空集合返回0。软删行不参与MAX或UPDATE，即使其历史号很大也不应阻断。

源仓储没有N非负参数门禁，但实际保存输入满足N>=1；负N的任意端口调用不是本轮已授权业务用例，不新增验证或宣传全面等价。若主控需要扩展该契约应单独决定。

**观察阶段不可合并**：MAX不等于先前GetLines缓冲最大值。Offset冻结于本次MAX观察，UPDATE仍按其执行时的全部有效行筛选，不能改成初次UID数组或再MAX。服务用stagedLineCount与existingLines.Count比较，数量增减必须可观察；这也不能证明同数量行替换没有发生。若不遵循头锁的写者在两个阶段间插入新高号，原门禁可能已过而UPDATE仍因溢出/唯一键失败；应保持异常及外层回滚，不变成自动重新计算/重试或伪造并发成功。

52720是SQL Server异常Number，不是已使用的API/Repository返回码。全源码搜索没有针对52720的消费者，SqlServerExceptionClassifier归Unknown，Draft通用catch返回原Unexpected及“销售草稿命令失败，请核实命令结果。”。最小PG替代建议在独立MAX之后、任何UPDATE之前用long门禁抛普通本地异常并保留原中文消息，在职责注释中注明源52720；不伪造SqlException/PostgresException/SQLSTATE52720，不新增全局分类或把它转换CONCURRENCY_CONFLICT/Validation。具体CLR异常类型需主控在实施冻结中写明；这属于提供者技术异常载体差异，不能宣称SQL异常类型或事务aborted状态完全相同。现有销售执行器无论该技术失败都回滚外层事务。
