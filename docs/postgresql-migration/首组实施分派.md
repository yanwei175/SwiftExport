## A：事务及授权翻译决定

SQL Server 当前服务没有开启显式事务；批次内预判和最终写入是不同语句。不能因接口说明“原子”便推断预判与写入享有同一永久快照/锁。采用同一连接、传递当前事务的分阶段参数化命令，保留原判断顺序：创建先重名预查，再授权 INSERT；重置依次操作者、目标有效性、目标管理员，再最终带双版本、操作者权限和目标非管理员条件的 UPDATE。没有外层事务时不自行开启；有外层事务时全部传同一个 Transaction，不提交、回滚或释放它。不把多次授权检查全部折叠成同一 CTE 快照，不新增 M10 父行锁协议或业务锁。

创建用针对用户名表达式/未删除谓词的 `ON CONFLICT ... DO NOTHING RETURNING` 防重名竞争，不能无目标吞掉所有唯一异常；若 INSERT 零行，再查用户名判定竞争重名或 ActorNotAdmin，保留返回枚举。Uid 等其他唯一错误保持提供者失败，不伪装重名。正常重名路径不通过异常破坏外层 PG 事务。审计及参数复用现有组件。

最终写入条件仍须重验授权；主控针对“预判后、最终语句开始前已提交撤权/目标晋升管理员”的场景验证。单语句执行过程中 PG 快照与 SQL Server 锁读取的竞争差异仍属实库验收风险，不能宣称已解决全部 M10 竞争，也不能顺手改变 RBAC。发现不能保持有效业务边界时记录阻塞，由主控决定最小必要修改。

技术依据：[SQL Server autocommit 逐语句事务](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/transactions-transact-sql?view=sql-server-ver15)、[Npgsql 批次可能引入隐式事务](https://www.npgsql.org/doc/basic-usage.html)、[PG Read Committed 每语句快照](https://www.postgresql.org/docs/current/transaction-iso.html)。这些依据用于翻译当前代码，不作为业务规则变更理由。

## B：缺失配置与范围保护决定

真实调用者是采购创建的当前默认事务；预览无锁。`withUpdLock=true` 不能仅追加 `FOR UPDATE`，因缺失配置没有可锁行。采用 PG 对 **customer_po_config 单表**的 `LOCK TABLE ... IN SHARE ROW EXCLUSIVE MODE`，先取得锁，再在同一当前事务中执行完整 DTO 查询；事务结束释放，配置的 INSERT/UPDATE/DELETE 由 PG 自带写锁参与，无需改泛型仓储或新增锁表。普通预览不加该锁。这不是全系统业务锁，影响仅配置表写入及锁定读取；采购提交期间会串行该表维护，记录这一较宽锁粒度的吞吐限制。

锁定分支要求已有事务，支持当前真实调用链的 ReadCommitted/ReadUncommitted（PG 等价 ReadCommitted）；高隔离分支不能借此声称可见最新已提交数据，应明确拒绝并记录待后续调用链验收。本组不降调用方隔离、不添加自动重试、不修改采购服务。测试缺失组合时并发插入等待、现存配置更新等待、提交/回滚释放及普通预览不占用该锁。若真实源码出现同一事务先写本表再升级锁等额外调用方，先报告主控。

依据：[PG 表锁与兼容矩阵](https://www.postgresql.org/docs/current/explicit-locking.html)、[LOCK 与后续读取](https://www.postgresql.org/docs/current/sql-lock.html)。此为保护原 HOLDLOCK 读取结果的必要 PG 实现选择；未通过实库竞争测试前，M12 只能标代码完成待验证。
