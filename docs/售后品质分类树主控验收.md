## 实现范围

售后品质分类使用独立 `after_sales_quality_category` 表与专用维护页，参考产品分类的层级编辑、拖动、排序、批量保存、版本与引用删除保护。父级和末级均可选择；分类可空，新选/改选要求存在且启用，未改选历史草稿及确认保留停用资格。没有增加叶子限定、父停用级联、产品分配、结案、库存或公共业务锁。

新增 Core 实体与仓储接口、Contracts 查询/编辑 DTO 与专用 Refit API、Application 分类服务、Infrastructure PG 仓储、WebApi 两个显式入口及对应 DI。现有售后候选改读新表，草稿与确认只新增分类核验。客户端新增分类树模型、维护 View/ViewModel、树选择器、Feature 映射及导航/API/模板接线，原售后单仍使用 QualityCategoryId。

共享 SchemaGenerator 与 Generated PG 基线纳入新实体、编码索引和逻辑引用。增量迁移脚本保留旧 Uid、版本、审计、启用及英文名称，不删除旧字典数据，不覆盖迁入后维护的数据。通用 DictCodeList 恢复五项；DictionaryManager 同时排除旧附加类型，其他自定义字典仍可维护。保留旧识别码常量用于迁移追溯，不是双库兼容层。

具体文件清单见[后端结果](售后品质分类树后端结果.md)、[前端结果](售后品质分类树前端结果.md)及[实施协调](售后品质分类树实施协调.md)。主控另修改 `DictCodes.cs`、`DictionaryManagerViewModel.cs`、字典回归测试、共享结构文件和售后用例说明，并在窗口停止后修正必要问题。已修改业务代码；没有修改产品分类实现、公共会话/通用仓储、原单据契约或其他业务规则。

## 试运行发现的端点权限漏登与修复

2026-10-07用户报告保存API返回“此API尚未登记具体权限”。实际原因是全局 `EndpointPermissionFilter.SingleKeys` 未登记新分类Controller的两个入口；Application服务中的权限校验无法绕过这层拒绝。先前分类服务测试没有覆盖端点登记，原本批Review未识别这一缺陷。

已最小补齐 `GetAllAsync → QualityControl.AfterSales.View`、`BatchSaveAsync → QualityControl.AfterSales.Maintain`；不新增权限键、不派生Create/Edit/Delete权限，不改分类业务规则或数据库。修改 `EndpointPermissionFilter.cs`、`EndpointPermissionFilterTests.cs` 及本记录。单键矩阵数量225→227，保留逐项鉴权断言；新增真实MVC Action描述符测试，分别验证无权限/错误权限拒绝、未认证拒绝、正确权限放行。

修复前两项分类端点测试实际失败，证据 `TestResults/quality-category/端点登记缺口.trx`。最终执行 `dotnet build SwiftExport-WebAPI.slnx --no-restore -v quiet` 通过（0错误、1项既有NU1900）；执行 `dotnet test SwiftExport.Application.Tests/SwiftExport.Application.Tests.csproj --no-build --no-restore --filter 'FullyQualifiedName~EndpointPermissionFilterTests|FullyQualifiedName~EndpointPermissionHttpTests|FullyQualifiedName~AfterSalesQualityCategoryServiceTests|FullyQualifiedName~AfterSalesQualityCategoryContractTests' --results-directory TestResults/quality-category --logger 'trx;LogFileName=分类树端点权限修复.trx' -v minimal`，27通过/0失败/0跳过。HTTP用例为既有回环管道回归，分类新端点通过真实MVC描述符的权限过滤器测试；没有伪称运行库写入验收通过。实际diff复核与空白检查通过；重启当前代码的后端后才会加载新增登记，无需重跑数据库迁移。
