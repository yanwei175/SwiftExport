## 执行步骤

1. 备份目标数据库，并停旧版后端和客户端。归档保留在同一个数据库中，不能代替独立备份。整个迁移及首轮重新授权期间保持停机，不允许旧版继续写入。
2. 在 SSMS 选择正确目标库，查询现有活动用户并确认管理员 Uid；脚本不会新建账号或重置密码：

```sql
SELECT DB_NAME() AS 当前数据库;
SELECT Uid, UserName, NickName
FROM dbo.SysUser
WHERE IsActive=1 AND IsDeleted=0
ORDER BY UserName;
```

3. 打开执行脚本，只填写顶部参数（示例中的库名和 Uid 必须换成实际值）：

```sql
DECLARE @ExpectedDatabase sysname = N'实际数据库名';
DECLARE @AdminUserUid uniqueidentifier = '实际用户的Guid';
DECLARE @Apply bit = 0;
```

4. 保持 `@Apply=0`，整份执行。它会真实执行结构变更、填充和校验，再全部回滚，输出“演练成功，全部修改已回滚”。这不是只读预览，会短暂持有表锁，因此也要在停机时执行。
5. 确认无错误，将 `@Apply=1`，再次整份执行。输出目录 111 项、普通角色授权 0 项和明确的管理员标识，最后提示“迁移已提交”。重复执行同一脚本/管理员参数会直接无操作返回，不会覆盖后来分配的权限或重新提权。
6. 部署新版，用指定账号原密码登录，检查用户、角色、权限定义与字典界面；给普通角色重新分配所需权限，确认用户角色关系后，再恢复普通用户访问。旧 Token 的权限也由新数据库实时评估，客户端应重新登录取得新的权限快照。

执行身份需有目标库结构变更和数据读写权限。不要向普通应用账号额外授予归档 schema 的访问权限。

## 数据如何处理

| 数据 | 迁移行为 |
|---|---|
| `SysUser` | 不改账号、密码、CredentialVersion、状态或 Uid |
| `SysRoles` | 原表完整移动到归档；新表保留原 Uid、名称、说明、版本和审计字段。旧角色生成 `LEGACY_` 加无连字符 Uid 的稳定编码，无继承；新增独立 SYSTEM_ADMIN |
| `SysUser_Roles` | 原表归档；新表保留直接关系的 Uid、UserId、RoleId、软删除和审计信息，移除冗余用户名/角色名；仅给指定用户新增管理员关系 |
| `SysPermissionDefinitions` | 按当前 PermissionCatalog 填入 111 项定义，名称、分组和排序与 DbSeed 一致 |
| `SysRole_Permissions` | 若旧表存在则完整归档；新表初始为空，普通角色需重新授权。管理员通过稳定角色代码自动拥有所有已知权限，不插入 111 条关系 |
| `SysUser_ModulePermissions`、`SysViewRoute` | 若存在则整表移出 dbo，保留到归档 schema |
| `SysDictType.TargetViewKey` | 先归档每行 Uid 和旧路由键，再移除该列；字典类型、字典值和其他业务表保留 |

归档 schema 为 `PermissionMigration_20260927`，同时保存完成记录。脚本不删除归档。旧权限、父角色和路由可以查询追溯，但新应用不读取归档。全部结构与数据变更处于同一事务；失败自动回滚。正式提交后若需退回旧版，应在停机下恢复迁移前数据库备份并配套旧应用；不要只恢复部分表，否则可能丢失迁移后写入。脚本不自动执行提交后的逆迁移。
