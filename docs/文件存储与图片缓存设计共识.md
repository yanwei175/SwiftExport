# 文件存储与图片缓存设计共识

日期：2026-09-26。

本文记录本窗口讨论，供后续规划与实施使用；不是功能已实现的证明。本次仅保存文档，不修改业务代码、安装依赖、建立数据库表或执行迁移。以下区分用户明确要求、当前建议和待定事项，后续不得把建议当成已经确认的业务规则。

## 一、目标与当前事实

底层文件操作采用独立类库 `DvFileStorage`，编译为 DLL，由现有 SwiftExport.WebApi 进程加载，供产品、售后及其他业务使用；不做独立微服务。HTTP 边界和业务编排仍在宿主项目。WPF、VSTO 和未来 Web 通过 HTTP API 使用服务器文件，不直接引用存储 DLL 访问服务器磁盘或 NAS。

本轮源码核对结果：

- Product.MainImage 当前保存图片路径；产品页使用 CachedImage 展示。
- SwiftExport.Client.Wpf/Services/Images/ImageCacheService.cs 当前只接受本地绝对路径，明确排除 HTTP/HTTPS。
- 现有图片缓存已有内存 LRU、磁盘缩略图缓存及并发请求合并。因此“新增 HTTP 图片只使用内存”不等于项目原有磁盘缓存已经删除。
- 主型号、中性产品及其他页面也有图片路径消费者。将来实施时需核对这些入口，不能只修改 ProductsView.xaml 就宣称全项目完成 HTTP 图片接入。

## 二、用户要求的文件能力

- 上传、下载、删除、判断存在、获取访问地址。
- 首期支持服务器本地磁盘和 NAS，未来可切换 MinIO／S3。
- 支持图片、视频、PDF 等普通文件；图片解码属于图片使用方的职责。
- 支持大文件流式传输；希望有 Range 和断点能力。
- 支持临时上传，业务保存后转正式。
- 产品主图使用固定命名路径，允许人工在服务器批量替换图片。
- Product.MainImage 落库，允许多个产品共用同一图片。
- 售后附件使用独立目录及数据库附件记录。
- 存储实现统一抽象，业务代码不直接依赖具体磁盘或对象存储 SDK。

大文件流式传输、下载 Range、上传断点续传是三项不同能力，不能混为一谈。下载支持 Range 不代表上传已经能够断点续传。

## 三、存储根目录和业务目录

建议结构：

```text
可配置的服务器存储根目录
├─ ProductImages/     产品主图，固定业务子目录
├─ AfterSales/        售后附件，内部层级后续确定
├─ Temporary/         临时上传
└─ 其他业务目录/
```

示例：

| 配置项 | 本地磁盘 | NAS |
| --- | --- | --- |
| 根目录 | D:\ERPFiles | \\NAS01\ERPFiles |
| 产品引用 | ProductImages/ABC123.jpg | ProductImages/ABC123.jpg |

数据库中的业务引用不保存父磁盘目录。移动完整目录后可切换服务器根目录，原有相对引用保持不变；修改配置本身不会搬迁文件。

“本地目录”指 WebAPI 所在服务器的目录。其他用户电脑上的目录只能作为上传来源，不能直接作为服务端根目录。NAS 使用服务器进程账户访问，不依赖客户端映射盘符。

当前建议：首期根目录放服务端配置；系统设置页面日后可展示存储状态。暂不建设在线修改根目录或自动搬迁功能，也不因此修改现有系统设置模块。最终配置键名、目录可用性检查及部署切换步骤由实施方案确定。

## 四、产品主图：已明确的特殊规则

### 1. 固定路径、内容可替换

采用 ProductImages/{Sku}.jpg。首次上传时由当时 SKU 确定路径，Product.MainImage 保存该相对引用；以后读取以保存的引用为准，不随当前 SKU 重新推算。

```text
根目录：D:\ERPFiles
MainImage：ProductImages/ABC123.jpg
实际文件：D:\ERPFiles\ProductImages\ABC123.jpg
```

- 用户可以直接在服务器替换同路径图片，不需要修改数据库。
- 多个产品引用同一路径时，替换图片会影响所有引用者，这是预期行为。
- SKU 更名不自动重命名图片、不自动修改 MainImage。
- 不采用此前讨论过的 FileId／Version 物理目录方案来替代产品固定路径。
- 删除产品或清空引用不应自动删除共享文件；主动删除共享文件的入口和影响提示待实施时明确。
- 产品主图不进入 StoredFile 表，不为每张主图额外建立文件元数据记录。
- 用户不希望给产品主图设计逐产品权限。讨论建议读取采用统一策略；上传、覆盖、删除仍要求适当身份和维护权限，这部分具体策略尚未确认，不应默认开放匿名写入。

### 2. 文件类型与替换

固定 .jpg 必须对应真实 JPEG 内容，不能只改扩展名。是否只接收 JPEG，还是服务端将其他图片转码，尚待确定。

服务端覆盖建议先写临时文件，完成后再替换正式文件，避免读取半张图。临时转正式不能假装与 SQL 是同一个可回滚事务；尤其主图覆盖会同时影响共享引用，需单独明确“上传完成即替换”还是“业务保存确认后替换”的时机。

服务端应校验固定目录下的合法相对路径和 SKU 命名，客户端不能提交任意绝对路径来读写。SKU 中不适合作为文件名的字符如何处理、大小写与重名行为需在实施前确定，不能擅自清洗后造成不同 SKU 撞名。

### 3. 地址输出

MainImage 保持相对引用；界面需要完整 HTTP 图片地址。当前建议由后端查询输出访问地址，具体是增加展示字段还是采用其他查询投影，后续盘点契约后确定。不能覆盖持久化相对引用，也不将签名有效期地址作为永久引用保存。

图片缓存组件不拼接根地址、不理解 ProductImages、不根据 SKU 构造网址。

## 五、其他文件与数据库记录

售后及普通业务附件可以使用公共 StoredFile 记录管理文件身份、相对位置、原名称、类型、大小、上传人、临时状态和过期时间。售后另外使用 AfterSalesAttachment 等业务记录表达“哪张售后单关联哪些附件”。这两个名称目前是建议，不是已建表事实。

- 产品主图明确排除在 StoredFile 之外。
- 售后等业务目录与产品主图分开，但复用底层存储读写能力。
- 目录不替代业务归属及访问授权；产品主图的简化策略不能自动推广到售后附件。
- 上传先完成文件，再保存业务关联，失败的临时文件由后续清理处理；不能在整个大文件传输期间持有业务数据库事务。
- 解除业务关联与物理删除分开，防止共享文件被误删。
- StoredFile 和售后附件表的最终字段、生命周期及首期是否落表，随文件业务实施范围确定。本轮没有授权建表。

## 六、WPF 网络图片缓存：最新讨论方向

用户要求：缓存组件仅接收图片地址，能加载和解码则显示，失败返回空图；不做业务路径拼接和产品类型判断。

用户担心 HTTP 图片写入磁盘持续产生文件。最新建议采用：HTTP 图片仅下载到内存并解码，复用容量受限的内存缓存，不新增 HTTP 图片磁盘缓存。该方案尚未实施。

| 输入 | 建议行为 |
| --- | --- |
| 本地绝对路径 | 保留现有加载行为 |
| 完整 HTTP/HTTPS 地址 | 流式下载到受限内存缓冲，解码后返回图片 |
| 相对业务路径 | 不由缓存拼接地址；上游应提供完整地址 |
| 空值、无效地址、HTTP 失败、非图片或无法解码 | 返回空图，不在缓存组件弹业务提示 |

组件内部保留必要的超时、取消、大小/解码限制、并发去重和内存淘汰，避免无响应地址或巨大图片影响 UI。这些是资源保护，不是业务校验。

同一 URL 内容会被人工替换，不能永久缓存。首期建议采用简单有效期，到期后下一次读取重新获取；具体时长待定。不强制首期实现 ETag/Last-Modified，但未来可优化。有效期只在再次请求图片时生效，不代表当前打开的所有图片会自动推送刷新；页面刷新触发方式需要联调明确。

不要误解为：

- 支持 HTTP 就必须写本地磁盘。
- 只使用内存就完全不需要缓存失效机制。
- 需要推倒重写现有缓存。
- 本轮已经决定删除现有本地图片磁盘缩略图缓存或清理用户文件。

## 七、实现选型与首期建议

### 补充：缩略图集中生成与切换顺序

后续建议由服务器统一生成并缓存缩略图，WPF 与 Web 共用。列表读取小尺寸缩略图，查看大图时读取原图。该能力属于图片处理模块，普通文件存储只负责字节读写，不对视频、PDF 等任意文件强行做图片解码。

服务器生成缩略图可减少重复缩放、传输量及客户端解码开销，但客户端显示 JPG/PNG 仍需解码；只有复用内存中已经解码的图片才能避免重复解码。Web 优先利用浏览器自身 HTTP 缓存，不自行建立用户磁盘缩略图目录；浏览器是否落盘由浏览器管理。

人工替换固定路径原图后，服务器必须使衍生缩略图失效并重新生成，不能只依赖上传 API 或数据库更新时间。具体文件变化检测、缩略尺寸和并发生成规则在实施方案确定；客户端仍需要缓存刷新规则。

当前 WPF 本地图片缓存先保留。现有实现默认磁盘上限 512 MB，超过后以约 80% 为清理目标，实际值以部署配置为准；它按容量而非文件数量清理。现有缩略图数量多不等于没有清理机制。

采用以下顺序，避免影响当前使用：

1. 当前仅更新设计文档，不删除缓存代码、磁盘缩略图或数据库中的本地路径。
2. HTTP 图片支持可以单独增量开发：保留本地路径分支，增加完整 URL 的内存加载分支，用模拟 HTTP 测试验证。服务器暂未提供图片时，不切换现有业务数据。
3. 服务端原图、缩略图接口可用后，上传或迁入实际图片，联调完整 URL、同路径换图刷新与失败空图，再切换相关业务页面。
4. 本地图片来源全部退出且完成验收后，再决定是否删除原本地磁盘缩略图逻辑及提供一次性旧缓存清理；不自动清理用户文件。

如果只提前关闭现有磁盘缩略图缓存，本地原图通常仍可读取，但冷启动和大列表可能重复解码、缩放，性能可能退化，且需先检查实现是否支持关闭；因此本轮不作此变更。网络图片可以直接读取原图，不强制依赖服务器缩略图，但大量原图会增加网络与内存开销，不作为大列表的最终方案。

### 独立存储 DLL：已确认的项目边界

建立一个普通 C# 类库项目 `DvFileStorage`，目标框架 **.NET 10（net10.0）**，使用 Microsoft.NET.Sdk，不使用 Web SDK 或 Windows 专用目标框架。首期接口与本地实现放同一项目，不拆成多个包，不预先发布 NuGet 包。

不要选 .NET Core 2.0。若所说的“2.0”是 .NET Standard 2.0，它是不同的兼容性目标；本类库只供当前 .NET 10 后端使用，不需要为 .NET Framework 客户端降低目标框架。Contracts 的 netstandard2.0 约束不适用于此存储类库。客户端通过 HTTP 调用，不能为了 VSTO 而让客户端直接引用服务器存储库。

```text
DvFileStorage/
├─ Abstractions/       IFileStorage 等小型接口
├─ Local/              本地文件系统实现
├─ Configuration/      根目录等普通配置对象
└─ Models/             确实需要的文件信息、写入结果
```

文件夹随实际类型建立，不为目录完整而创建空壳类型。类库负责流式写入、打开读取流、删除、判断存在、文件信息、根目录内路径约束和明确的覆盖行为。接口使用相对文件标识、Stream、CancellationToken 等普通 .NET 类型，明确流的释放归属；不接受 IFormFile、HttpContext、Product 或数据库实体。写入失败不得留下可见的半成品正式文件，具体本地替换与失败清理在实施方案中说明。

| 职责 | 归属 |
| --- | --- |
| 文件字节操作、相对路径与物理目录映射 | DvFileStorage |
| ProductImages/{Sku}.jpg 命名、共享覆盖时机、更新 MainImage | 产品 Application 业务 |
| 附件归属、临时上传转正式及数据库记录 | 对应 Application 业务 |
| HTTP 上传下载、Range 响应、认证授权 | WebApi |
| 公共访问 URL 或未来签名 URL 的输出 | 宿主访问地址能力，不混入首期本地存储接口 |
| 读取 JSON、配置绑定、依赖注入组合 | WebApi 启动配置 |

类库不依赖 Core、Application、Infrastructure、Contracts、WebApi 或 WPF，不读宿主 appsettings.json。由宿主读取 FileStorage 配置并传入配置对象。Application 在确实需要调用时引用类库接口，由 WebApi 组合根选择并注册本地实现；业务服务不 new 具体实现。不再把同一 IFileStorage 重复放进 Core，也不在 Infrastructure 再包装一层仅转发的仓储。

首期用 .NET 文件流实现服务器本地磁盘，不引用第三方文件框架。未来 NAS 可在确认进程账户及 UNC 访问后复用本地文件系统实现，不能把本地测试通过当成 NAS 验收；MinIO/S3 在有真实需求时增加实现，再评估 SDK。HTTP 上传断点续传是另一个模块，届时再评估 tusdotnet。

### 手动创建项目

在 Visual Studio 中“添加 → 新建项目 → C# 类库”，名称 `DvFileStorage`，位置为仓库根目录，框架选择 `.NET 10.0`。不要选择 .NET Framework 类库或 ASP.NET Core Web API 模板。生成目标应为 `<TargetFramework>net10.0</TargetFramework>`。默认 Class1.cs 无业务用途，可以删除。

已按用户要求创建 DvFileStorage/DvFileStorage.csproj（net10.0），纳入后端及总解决方案；仅有项目骨架和说明，尚未实现存储接口，也未添加第三方包或业务项目引用。正式实施时再按需要添加引用，不让五层项目和所有客户端提前引用它。

WPF 网络图片加载及 Review 已由另一执行窗口负责，按 [收窄后的计划](WPF网络图片与产品主图地址实施计划及提示词.md) 执行，不在存储类库任务中接管或扩展。下一步存储任务先明确最小接口与本地实现，不顺带建立上传、附件、缩略图和产品地址迁移全套功能。

目标框架依据：[微软 .NET Standard 与现代 .NET 目标选择说明](https://learn.microsoft.com/en-us/dotnet/standard/net-standard)。

## 九、官方参考

## 首批细化：服务端根目录与内网 HTTPS 图片读取

本节补充后续讨论：首批只考虑内网服务器独立磁盘目录，通过现有 WebAPI 提供 HTTPS 产品图片读取，NAS 和对象存储暂不实施。系统不面向公网；服务器／NAS 具公网 IPv6 不改变该部署边界。

### 配置归属

根目录属于部署配置，建议放服务端 appsettings.Production.json（开发使用相应环境文件），不进业务数据库，不新增系统设置表或在线切换页面。图片目录应在程序发布目录之外，避免升级覆盖。配置通过 builder.Configuration 绑定读取；实际路径变更采用维护时切换并重启，不热切根目录。

建议配置样例，字段尚未在代码中实现，路径须核对服务器实际磁盘：

```json
{
  "FileStorage": {
    "RootPath": "D:\\ERPFiles"
  }
}
```

首期只有本地文件系统实现，不先加多后端选项。未来 NAS 可用 UNC 根目录并配置服务器服务账户权限。证书密码、NAS 凭据不写入该 JSON，也不提交至仓库。

### 图片访问映射

固定子目录 ProductImages；建议固定 HTTP 路径 /files/ProductImages。仅映射该子目录，不把整个根目录公开，不暴露 Temporary 或未来 AfterSales 附件目录，不开启目录浏览。

```text
磁盘：D:\ERPFiles\ProductImages\ABC123.jpg
引用：ProductImages/ABC123.jpg
URL：https://<现有内网API地址>/files/ProductImages/ABC123.jpg
```

此 URL 为模板，不是已部署地址；若现有 API 有虚拟路径，需包含实际基路径。首期可用 ASP.NET Core 静态文件中间件配合 PhysicalFileProvider 映射外部目录，无需建表、引入第三方文件框架或建立上传接口。提供产品图片读取，不扩展到匿名写入。配置缺失、根目录不可访问时应明确报告启动配置问题；根目录由部署人员创建并给服务账户配置所需权限，首期只读访问不要求全盘写权限。

不使用长期 immutable 缓存策略，因为固定路径下内容允许人工替换。建议首期 HTTP 响应采用 Cache-Control: no-cache 并配合标准文件 Last-Modified/ETag，以便请求时验证文件变化。no-cache 不等于禁止浏览器存储。图片处理和 WPF 内存缓存是后续单独能力，不能声称静态文件映射已实现缩略图或 WPF 网络支持。

### HTTPS 与内网部署

优先复用 API 已有 HTTPS 入口和证书，不额外开一个文件服务端口。如果当前只有 HTTP，需按实际 IIS、反向代理或 Kestrel 托管方式配置 TLS；UseHttpsRedirection 只负责重定向，不生成证书或自动开放 HTTPS 监听。

客户端必须信任证书链，证书名称应匹配所用内网域名；使用 IP 地址时证书需有对应 IP SAN。可采用内部 CA 颁发并分发信任的证书，不使用忽略证书错误的代码。内网服务无需为了 HTTPS 开放公网；公网 IPv6 存在时也应将入口按部署要求限制在内部网络。

托管方式、当前 API URL、证书现状、实际根目录尚待用户提供，不能据示例擅自改服务器、证书或防火墙。

### 首批验收与测试边界

1. 放入一张已知 JPEG，内网另一台电脑通过真实 HTTPS URL 取得图片，证书校验通过。
2. 不存在的文件返回 404；不能列目录或读取根目录外和其他业务目录的文件。
3. 同路径完整替换图片后，重新请求／刷新可获取新内容；验证条件请求与缓存响应，不承诺已打开图片自动推送更新。
4. 代码测试可使用临时目录与测试宿主，不依赖先部署 NAS 或实际服务器。真实服务器部署只是在客户端联调和跨机器 HTTPS 验收前必需。
5. 现有 WPF 尚不支持 HTTP，所以浏览器访问成功不等于 WPF 已接入；本地图片原流程继续保持。

本批不做：上传、删除、附件表、临时转正式、缩略图、断点上传、客户端地址迁移和现有缓存删除。后续在这些需求进入实施时建立完整 IFileStorage 及业务生命周期，本批的公开图片 URL 保持稳定。
