# 采购独立执行第一切片实施与验收

2026-08-31。实施依据为同目录《采购独立执行第一切片契约审计》。本切片只建立新的后端链路；旧页面、旧 DTO/API 继续存在。能力地图偏差没有因新增一条链路而全部关闭。

## 一、入口与职责

新 API 根为 `api/procurement/orders`，Refit 接口为 `IProcurementOrderApi`。全部要求认证，并由 Application 在事务内重新读取真实账号和角色授权。

| 方法与子路由 | 专用契约与职责 |
|---|---|
| POST `/search` | ProcurementOrderSearchRequest / ListItem，订单管理分页，不带跟进筛选 |
| GET `/{uid}` | ProcurementOrderDetailDto，只读订单自身及采购行快照 |
| POST 根路径 | CreateIndependentPurchaseOrderCommand，独立手工创建 |
| PUT `/{uid}/commercial` | SaveProcurementOrderCommand，仅商务白名单 |
| GET `/{uid}/confirmation-context` | ProcurementConfirmationContextDto，草稿当前严格 BOM 依据 |
| POST `/{uid}/confirm` | ConfirmProcurementOrderCommand，按指纹和完整路径目标确认 |
| GET `/{uid}/confirmation-snapshot` | ProcurementConfirmationSnapshotDto，单独读取已冻结依据，不重读当前 BOM |

查询、命令、确认依据构建、已确认快照查询分别由专用 Application 服务承担。新详情没有旧 ListItem Head、来源贡献、跟进历史、业务日志或库存集合。新增 DTO 每个公开类型独立文件；旧 14 类型所在聚合文件及 8 方法签名不变，不机械拆旧文件，不复用旧 Workspace 服务。

最小主数据前置为 `POST api/master-data/execution-eligibility/status`：按类型、Uid、预期版本、目标启停状态及原因变更 Product/Customer/Supplier 的 IsActive。它不是主数据工作台；没有新增前端或全模块更名、默认值和包装管理。

## 二、已经落实的业务边界

- 单头必须有一个有效客户及一个实际采购供应商；一至500行有效标准采购产品。产品必须采购供给、非虚拟、非未关联非标，基础单位必须匹配唯一启用 Unit 字典项。
- 产品供应商目录关系不作为必需前提；不把默认供应商当作本次实际供应商，不重新应用客户当前包装默认覆盖历史。包装要求为本切片明确录入的商务文本。
- 每行必须指定已有、启用的供应商虚拟仓作为收货目标，不自动建仓。实际供货供应商、收货仓所属供应商、客供件消耗仓所属供应商可以不同。
- 创建后客户、实际供应商、产品、数量、基础单位和收货目标固定。保存只更改价格、交期、供应商型号、描述、备注和包装商务要求；不增加、删除或替换行。
- 币种固定 CNY。数量为正且最多四位；价格非负且最多六位；金额最终按四位 AwayFromZero 舍入并校验范围。草稿价格可空；确认含税价必填，明确零价有效。超长文本和输入精度超限拒绝，不截断、不依靠 SQL 静默舍入。
- 确认重新校验客户、实际供应商、产品、单位、收货仓资格；物料角色、供货方式、单位或收货仓归属改变时拒绝，不混用草稿身份与当前事实。
- 新采购不读取、不写入 GrossDemand、NetDemand、Allocation、DemandExecutionLink，也不生成收货、库存或出库事实。

## 三、确认依据、事务和权限

严格 BOM 读取按产品 Uid 读取完整可达当前结构，产品、组成范围与单位字典都持锁至调用方事务结束；不存在的组成范围也锁定，防止读取中插入组成造成部分旧结构、部分新结构。

无 BOM、有效 BOM 但没有客供件、有客供件三种情况分别表达。缺失节点、循环、非法比例、无效单位、同父重复、非终端客供件均失败，不将失败当作无 BOM。跨分支共享组件保留完整路径。读取/展开节点上限10000，路径最多4000字符，超限拒绝整个操作。

比例使用原始整数分子/分母与 BigInteger 分数累计，输出累计比例时才四位 AwayFromZero 舍入；溢出或正比例舍入为零均拒绝。快照保留原始因子、完整路径、父子身份与编码、单位、物料角色、指纹、确认命令和行版本及策略标记。所有客供件路径必须且只能各绑定一个有效消耗仓库，并冻结仓库及其供应商快照；不使用收货目标或 Allocation 自动推导。

采购头行仍是一套事实；确认行依据、节点、命令回执使用新增专用表。确认状态、整批快照、原始回执及业务日志在同一可串行化事务内提交。BusinessOperationLog 不充当幂等存储。命令键全局唯一，绑定操作者、操作和请求指纹；相同请求返回当时的原始结果，相同键不同内容/用户拒绝。权限校验先于回执读取，撤权不能通过重放绕过。

当前权限使用已有有效 SysUser、SysUser_Roles、SysRoles；Admin 可执行全部动作，普通账号需对应角色名：

| 角色名 | 可执行动作 |
|---|---|
| Procurement.Order.Read | 管理查询、当前确认上下文和已确认快照 |
| Procurement.Order.Create | 独立创建 |
| Procurement.Order.Edit | 商务保存 |
| Procurement.Order.Confirm | 确认 |

主数据启停仅 Admin。此处没有假设 SysPermission/SysRolePermission 已建表，也没有建设完整权限资源模型或默认授予所有登录用户。

## 四、历史兼容与数据库部署

采购单只保留业务来源类别，手工来源为 `OriginKind=2`；不得用客户端、API 或页面迁移状态切割采购事实，也不推测历史客户身份、未关联数量或 BOM。

旧列表、详情、Trace、跟进、四种写命令及日志回放，以及需求侧追加、取消和减量入口都显式限制旧链。新入口反向只处理新链。旧 DTO、Refit、WPF ViewModel/页面、导出、导航、注册与有效旧测试不变。

部署文件为 `SwiftExport.Infrastructure/Migrations/020_独立采购执行.sql`。必须先审核备份与目标环境，将脚本开头的 `@ExpectedDatabaseName` 从 NULL 改为明确目标库名，再在该库完整执行。新建库在 FreshInstall 030/040/050/055/060 之后同样执行此增量，不复制一套会漂移的新基线 SQL。FreshInstall README 已同步。

迁移新增客户/供应商/产品 IsActive，旧资料更新仓储排除该列，避免旧 DTO 保存意外重新启用。Unit 引用冻结由数据库触发器兜底：已有单据、库存流水、有效 BOM 或确认依据引用后不能改变基础单位；不会按库存余额为零解冻。新采购读取产品持锁到引用提交，可与单位变更串行化；没有声称已经修复全仓旧写入路径的所有并发引用问题。

新增执行身份约束、旧/新所有权守卫以及不可改写快照/回执触发器。DemandSource 与行来源允许真实 NULL，以表达独立采购没有需求来源；旧非空历史值保持原样。迁移不会删除业务数据，不在业务库自动执行。

## 五、验证与明确不包含的能力

行为测试覆盖输入精度、商务白名单、旧链隔离、严格 BOM 和最小主数据启停边界。真实 SQL 测试通过 `SWIFTEXPORT_RUN_SQL_TESTS=1` 显式开启，使用唯一命名的 LocalDB 临时库，运行真实 FreshInstall 030 与本次020迁移，测试后清理；不会读取应用业务连接字符串。不开启时明确标记未执行，不以假仓储替代 SQL 证据。

命令示例：

```powershell
dotnet build .\SwiftExport-WebAPI.slnx --no-restore
dotnet test .\SwiftExport.Application.Tests\SwiftExport.Application.Tests.csproj --no-restore
$env:SWIFTEXPORT_RUN_SQL_TESTS='1'
dotnet test .\SwiftExport.Application.Tests\SwiftExport.Application.Tests.csproj --no-restore --filter 'FullyQualifiedName~IndependentProcurementSqlTests'
```

- 后端解决方案和现有 WPF 客户端构建通过，均0警告、0错误。
