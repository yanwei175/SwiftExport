# SwiftExport ERP Onboarding Report

> Draft generated by AI on 2026-06-21. This is an initial technical orientation report. No business code was changed.

## Executive Summary

SwiftExport is a C# ERP system with a desktop WPF frontend, an Excel VSTO host, and an ASP.NET Core Web API backend. The backend follows a layered structure:

- `WebApi`: HTTP/API boundary
- `Application`: business orchestration and services
- `Core`: entities, domain models, read models, repository interfaces
- `Infrastructure`: Dapper repositories, SQL Server connection/session, unit of work
- `Contracts`: shared DTOs and Refit API interfaces

There is no JavaScript SPA frontend in this repository. The practical frontend is the WPF view layer in `SwiftExport.View.FW`, hosted by `SwiftExport.DevApp` for standalone development and by `SwiftExport.VSTO` for Excel add-in scenarios.

## Development Workflow Notes

### Adding or Changing a Backend API

Likely touch points:

1. Entity/read model in `SwiftExport.Core` if domain shape changes.
2. Repository interface in `SwiftExport.Core/Interfaces`.
3. Repository implementation in `SwiftExport.Infrastructure/Repositories`.
4. Service interface and implementation in `SwiftExport.Application`.
5. Controller endpoint in `SwiftExport.WebApi/Controllers`.
6. DTO and Refit API interface in `SwiftExport.Contracts`.
7. WPF API registration in `SwiftExport.View.FW/DI/DependencyInjection.Apis.cs` if it is a new API interface.

### Adding a WPF Page

Likely touch points:

1. Add View under the correct `*Views/Views` folder.
2. Add ViewModel under the matching `*Views/ViewModels` folder.
3. Add UI model under `*Views/Models` if needed.
4. Register ViewModel and View in `SwiftExport.View.FW/DI/DependencyInjection.Pages.cs`.
5. Add route in `SwiftExport.View.FW/Routing/ViewRoutes.cs` or DB route config if the page is route-driven.
6. Add host navigation/opening logic where appropriate, for example `SwiftExport.DevApp/MainWindow.xaml.cs` in the dev shell.

### Adding a Repository

Likely touch points:

1. Add interface in `SwiftExport.Core/Interfaces`.
2. Add implementation under `SwiftExport.Infrastructure/Repositories/<Module>`.
3. Register implementation in `SwiftExport.Infrastructure/DependencyInjection.cs`.
4. Inject into an Application service via the service context or constructor pattern used by the module.

## Initial Risks / Questions

- The frontend API base URL is hardcoded in `SwiftExport.View.FW/DI/DependencyInjection.Apis.cs`. This is convenient for local development but should eventually move to config.
- Connection strings with credentials are present in config/tool files. Treat them as local-only and avoid spreading them.
- Several source files contain garbled Chinese comments, likely encoding mismatch. This does not necessarily affect runtime, but it makes maintenance harder.
- No automated test project was found. Risk is higher for broad refactors or business-rule changes.
- Full solution includes .NET Framework WPF and VSTO projects; command-line build reliability depends on Visual Studio/MSBuild workloads, not just the .NET SDK.
- The backend targets `net10.0`, so local SDK availability matters.
