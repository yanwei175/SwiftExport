# SwiftExport 开发测试与回归验证机制自查报告

调查日期：2026-10-15（Asia/Hong_Kong）。本报告只调查和提出建议，不实施规则或代码修改。

## 结论与证据边界

**当前没有“每次修改必须完整回归、启动完整 WPF 客户端并截图分析”的全局规则。** 根规则、测试总纲和审查工作流已经要求最小验证、复用有效证据、区分历史失败并禁止无限修复。实际问题集中在下层命令示例与总纲不完全一致、测试项目混合多种环境、测试分类不完整，以及 UI 测试与截图输出耦合。

建议保留现有高风险业务门禁，把普通开发的默认执行单位明确为“受影响项目和测试类/方法”，将模块验收与阶段回归分开。优先修改治理表述和执行记录方式，再依据实际测量决定是否拆项目；没有依据直接删减测试或降低断言。

全文采用四类标记：

- **【事实】** 当前文件、项目引用、测试源码或已有结果直接支持。
- **【疑问】** 缺少任务、命令、源码版本或进程记录，尚不能确认的行为。
- **【推断】** 从机制推导出的可能原因，不代表已经证明实际发生。
- **【建议】** 待后续授权实施的调整，不是当前有效规则。

调查覆盖根和业务目录 AGENTS、`.agents` 角色/路由/工作流/参考规则、项目 Skills、全部发现的 .NET 测试入口、解决方案、现有 runsettings、Codex 环境配置、CI/钩子目录、相关工具脚本及现有测试记录。规则先全局检索，再完整读取命中的主规则与质量门禁，源码按触发机制抽样追踪；未逐个证明所有测试的业务正确性。

历史证据取自仓库现存文件，没有读取 `弃用资料/**`，没有调用其他聊天历史。排除 `.git`、`node_modules`、`bin`、`obj` 后，以包含隐藏和被忽略文件的搜索找到 **476 份 TRX、473 个不同 TestRun ID**，记录时间范围为 2026-09-04 至 2026-10-15。文件数不等于开发任务数，也不能直接换算为测试频率；同一运行存在副本，固定结果文件还可能被覆盖。

本次没有执行构建、测试、数据库查询、WPF 启动、桌面操作或截图。所有耗时均来自已有记录；没有测量当前工作树的性能，也不把历史结果视为当前代码通过。工作区开始时已有大量业务、测试及文档的未提交变更，本报告不判定其归属、不修改这些文件。

### A3. 后端 PG、宿主和隔离机制

【事实】真实 PG 测试通常使用环境启用开关、连接变量及实例/库名校验；未配置时 `Assert.Inconclusive`，不自动证明通过。见 [PostgreSqlIntegrationEnvironment:10](D:/Documents/source/CSharp/SwiftExport/SwiftExport.Application.Tests/Database/PostgreSqlIntegrationEnvironment.cs:10)。它同时保留原 `dv_next` 和专用 failure/command 库入口；这些历史代码不能替代每次写入授权。

类别并不统一。静态检索当前后端字面量得到 42 种 TestCategory，其中 35 种以 `Integration` 结尾；这不是运行时完整分类清单。例如：

- [ProductDetailPostgreSqlTests:34](D:/Documents/source/CSharp/SwiftExport/SwiftExport.Application.Tests/MasterData/ProductDetailPostgreSqlTests.cs:34) 没有统一 PG 类别，调用 [产品属性专用库夹具:65](D:/Documents/source/CSharp/SwiftExport/SwiftExport.Application.Tests/MasterData/ProductAttributePostgreSqlFixture.cs:65) 的开关/库校验。

【事实】[LegacyTestDatabase:25](D:/Documents/source/CSharp/SwiftExport/SwiftExport.Application.Tests/Database/PostgreSqlLegacyTestDatabase.cs:25) 对固定专用库使用文件租约、所有权标记和固定 schema SHA；[DisposeAsync:109](D:/Documents/source/CSharp/SwiftExport/SwiftExport.Application.Tests/Database/PostgreSqlLegacyTestDatabase.cs:109) 逐例导出 50 表及结构，再校验并重置 public，失败保留现场。真实网络往返、导出和恢复具有结构性成本；没有分段计时，不能给出各阶段耗时占比。固定 SHA/表数也使结构变化可能阻断旧夹具，不能简单当作业务回归修复。

【事实】不少类有 `DoNotParallelize`。它限制测试运行器内调度，不能隔离另一个 Agent 的独立进程。Legacy 夹具有跨进程文件租约，但不能推定所有专用库都具备同样保护；总纲已禁止多个窗口同时重置共享 failure 库。没有证明所有测试互不影响，也没有发现可据此认定测试必须按特定顺序运行的统一要求。

### A4. WPF 窗口与截图的实际来源

## C. 建议的测试执行矩阵

三级策略适合本项目，但应增加“文档静态检查无需进入业务测试等级”的出口。等级由可观察行为、共享依赖及数据风险决定，不能只看文件后缀，也不能等到发布前才补高风险定向测试。下表全部为建议。

| 变更类型 | 编译/静态检查 | 单元/契约 | 集成/PG | WPF UI/视觉 | 扩大范围与级别 |
| --- | --- | --- | --- | --- | --- |
| 纯治理文档、注释，无代码语义变化 | 引用、结构、diff；无需 .NET 构建 | 无需业务测试 | 不运行 | 不启动 | 静态出口 |

## D. 优化方案与测试代码修改策略

### D1. 必须保留的质量保护

保留订单确认、过账/反向、库存、权限、Version/CommandId、数据库事务与并发的定向失败场景；保留真实 PG 验证与模拟测试的证据区分。保留数据库实例/库名/数据范围授权、租约、导出恢复和失败保全。锁预算/超时变化仍应运行真实时间和锁释放验证，不得把 30 秒等待改成模拟后宣称等价。

保留 WPF 原生编辑提交、未保存输入保护、焦点/键盘/生命周期的 STA 测试；它们能发现 VM 单测无法覆盖的故障。截图不是这些测试的替代，也不能因为窗口可见就直接删除测试。

### D2. 缩小默认执行范围

1. 将 L1 默认明确为“受影响项目 + 已定位的测试方法/类”，将现有整项目命令标为 L2/L3 示例。后端 solution build 改为共享依赖或交付组合需要时执行，普通服务小改允许受影响项目/测试构建。
2. 先建立影响清单：修改的公开行为、直接消费者、共享组件和高风险边界。选择一个能覆盖它的最小测试集合，完成一个可审阅切片后统一验证，不按文件/方法逐次全量。
3. 对失败基线明确：复用同代码/环境的已知结果，或先跑相关最小复现；建立基线不等于每次先完整回归。实施后的定向与模块回归可有重叠，但扩大必须注明共享依赖或最终整合依据。
4. 一次有效构建/测试可以满足多个 Skill 的相同义务。Review 默认消费实施证据；没有新改动或具体疑点不重建、不重跑。
5. 四个 `_tools` 专项入口与主项目采用二选一的覆盖关系记录。只有主项目存在真实编译阻断或隔离必要时使用专项入口，不把专项与主项目相同测试默认累计执行。

### D3. WPF 窗口和截图按需触发

- 纯 VM、策略、映射、DTO、后端逻辑：默认不启动完整客户端，不进行桌面操作或截图分析。
- Binding/焦点/原生编辑/控件加载：优先定向 STA 测试，可显示必要测试窗口；不因此执行登录和整页所有功能。
- 视觉布局、主题/缩放、裁切、遮挡、用户明确要求截图或无法靠行为断言诊断：才采集代表性截图，并说明观察目标。
- 建议将普通交互断言与可选 PNG 输出分离；如需保留输出，按任务/运行 ID 建独立目录并只保留必要代表性状态。失败截图有助排错，但单纯输出 PNG 不能算自动视觉验收。
- 整个页面切片的人工验收归 L2；共享主题、Shell 或发布版本按实际影响扩大。不要把质量矩阵所有代表场景作为每次普通任务清单。

### D4. 何时新增、修改或仅运行测试

| 情况 | 建议动作 | 必须保留的约束 |
| --- | --- | --- |
| 新业务行为、新边界、不变量或可复现 Bug 尚无覆盖 | 新增能揭示故障的最小行为测试；先证明失败条件，再修复并验证 | 不机械复制实现算法；业务规则未确认不先写预期答案 |
| 既有测试已经直接覆盖本次行为 | 只运行该测试及必要邻接场景，可以不改 Test 文件 | 不要求为每次实现变化“配一份新测试” |
| 私有方法整理/文件移动，公开行为不变 | 复用定向行为测试；仅更新确实依赖合法结构契约的路径/命名 | 不批量改断言和邻近测试；无意义内部结构断言另列建议 |
| 接口成员/签名变化使测试替身无法编译 | 同步最小替身与调用方，必要时补新协议场景 | 替身修编译属于依赖维护，不等于证明新行为已覆盖 |
| 用户确认了业务契约变更 | 更新相应预期，并说明旧行为为何失效；保留其余成功/失败/安全断言 | 禁止只根据实际返回值改预期 |
| 旧夹具与当前正式约束不符 | 对照实体、SQL、业务规则确认后修夹具；保留原测试目标与故障注入可达性 | 不放宽唯一/库存/权限等生产规则迁就夹具 |
| 总端点数、字典条目数、源码路径变化 | 核实这是刻意的完整目录门禁还是脆弱结构断言；优先断言相关键和语义，必要完整性校验仍保留 | 数字变化本身既不能证明回归，也不能证明改数字合法 |
| 无关既有测试失败/环境缺失 | 分类、记录证据和影响；完成未受阻的当前验证；独立安排后续修复 | 不扩大当前业务范围，不删断言、不广泛 skip、不声称全套通过 |
| 同一失败重复出现且无新信息 | 暂停相同大集合，缩至失败方法诊断环境/夹具/产品原因；新的修复假设才触发下一轮 | 高风险失败仍阻断对应交付，不能靠次数上限视为通过 |

### D5. 模块验收、完整回归与 CI 的职责

建议模块完成时由独立验收步骤统一执行模块测试、实际 API/PG 和必要 WPF 主流程，消费开发阶段证据，并对最终整合版本补足缺口。独立工作流不等于每次自动创建新聊天或子 Agent，也不等于重新测试所有已验证对象。

建议后续 CI 分为离线后端/契约、Windows WPF/STA、授权隔离 PG、产品发布验收几个作业；在合并或发布等明确事件触发相应集合。纯业务单元、架构静态检查、PG 并发和视觉人工证据应分别报告，避免一份“通过”掩盖未运行环境。PG CI 必须使用独立实例/库及初始化/清理授权，不能直接复用运行库；WPF 交互作业须有满足显示/Dispatcher 条件的 Windows 环境。

当前分类不完整，建议先梳理可执行清单，再逐步统一如 Unit/Contract/HttpIntegration/PgIntegration/WpfSta/Visual 的用途标签与模块标签；先核查副作用，再决定默认排除规则。不要直接把现有 `TestCategory!=PostgreSqlIntegration` 包装成“离线 CI”。是否拆分测试项目，等构建链/宿主启动/测试执行分段计时证实收益后决定，不先大规模移动测试。

### D6. 避免多 Agent 重复验证

建议保留一个最终验收执行者，开发子任务默认只做其必要定向测试，共享构建和模块回归由主控合并执行。只有明确授权协作时采用，不自动创建任务。

使用轻量验证记录即可：任务与执行者、源文件/依赖指纹或提交加工作树摘要、项目和配置、筛选集合、输出目录、开始/结束、通过/失败/未运行、数据库/窗口占用、失效条件。源码未变、环境等价、覆盖满足时复用；新增变化只使受影响部分失效。TRX 使用唯一运行名，不覆盖原失败证据。

对同一个可见桌面测试会话及同一共享 PG 库只保留一个执行者；主控声明租用和释放。`DoNotParallelize` 不能当作跨进程锁。固定库 fixture 的已有租约/现场保护继续保留，没有明确隔离依据前不并行重置；不同 Agent 也不要用相同固定 PNG/TRX 路径。

### D7. 以证据评估提速

建议后续仅对正常开发中本来就需要执行的命令追加分段记录：restore、build、测试发现/宿主准备、用例执行、截图/导出、清理、人工等待。没有必要为了统计再主动跑全套。

优先检验：同一个代码批次构建次数、无变化同集合重跑次数、定向/模块集合重叠原因、WPF 窗口启动和 PNG 数、环境阻断重试次数、失败分类及任务扩张次数。先获得基线，再比较改进后的相同场景；本次不承诺固定节省比例或统一秒数门槛。
