# 采购前置：仓库候选实施与验收

日期：2026-09-01。阶段二，Backend。基线为 `main`、HEAD `8fe3158a7e124de24555b67e30064ee1a198abc2`；开始时保留阶段一主数据候选的17项未提交改动。

## 1. 实现与边界

在既有 `IWarehouseSiteApi` 根 `api/inventory/warehouse-sites` 下新增 `POST /candidates/search`。旧 search/get/create/update/deactivate 的签名和语义保持不变；旧 search 是仓库管理查询，可展示停用项且没有采购授权和完整资格，不直接复用于采购新增选择。

新查询只返回采购创建收货仓、确认客供件消耗仓所需的已有供应商虚拟仓：仓库 Uid/Version/Code/Name/SiteType/IsActive，以及所属供应商 Uid/Code/Name/SupplierIsActive。仓库和供应商都须未软删除、启用且身份资料完整；仓库须为 SupplierVirtual。归属使用 `WarehouseSite.SupplierId -> Supplier.Uid`，不能以历史快照补造当前资格。

- `Procurement.Order.Create` 可为采购行选择收货仓；`Procurement.Order.Confirm` 可为确认阶段选择消耗仓；Admin 可查询。只读权限不自动获得选择资格。
- 候选不要求仓库所属供应商等于本次实际采购供应商。收货目标与消耗目标由采购命令明确保存，仓库域不推导或自动绑定。
- 候选是当前资料，选择后仍可能失效；采购创建与确认必须保留事务内最终校验。它不构成预留、过账或库存可用事实。
- 历史详情继续读取采购单自身的仓库和供应商快照；停用或改名不能让已保存历史消失。本次不新增历史仓库筛选，因为采购 UI 当前没有对应真实用例。
- 未新增建仓、余额、过账、客户库存归属、BOM、WPF、迁移或业务库操作。

## 2. 契约与分层

`WarehouseCandidateDto` 是新增窄 Query DTO；没有复用 `WarehouseSiteDto`，因为后者缺少 SiteType 和 SupplierIsActive，且管理 search 的权限、停用展示和演进语义不同。分页直接复用稳定 `PagedRequestBase/PagedResponseBase`，关键词最多100字、每页1至100项，搜索仓库或供应商编码/名称并按字面转义 SQL 通配符。

- Contracts：在 `IWarehouseSiteApi` 增加 `SearchCandidatesAsync`，不创建第二个同根 API。
- Application：`IWarehouseCandidateQueryService` / `WarehouseCandidateQueryService` 验证身份、分页、取消和真实权限，并拥有短只读 Serializable 事务。
- Core/Infrastructure：专用 `IWarehouseCandidateRepository` / Dapper 实现，避免改变仓库管理仓储；参数化 SQL、稳定 `Code + Uid` 分页。
- WebApi：既有 `WarehouseSitesController` 新 action 仅做 HTTP 边界，401由认证管道，403/400/500按异常类型映射；CancellationToken 透传。
- DI：只在阶段一已有注册后追加本阶段两个 scoped 注册，未覆盖主数据注册。

INV-004 只新增本用例独立类型，未拆 `InventoryDtos.cs`；MD-005 只落实新增候选资格，不更改全模块停用规则。旧 WPF `WarehouseSitesViewModel` 与所有旧方法保持兼容。
