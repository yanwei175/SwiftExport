# 应用服务层逐项盘点与可读性建议

核对日期：2026-10-07。目标是让读者从一个入口看清业务步骤和一起提交的数据。当前服务层主要问题是业务主体被包装层、辅助命名和文件位置遮住；不宜据此把所有服务合并，也不宜继续增加微型公共服务。

先读 [调用链阅读指南](D:/Documents/source/CSharp/SwiftExport/docs/应用服务层调用链阅读指南.md)，再通过下面的索引定位具体服务。本次按源码中名称以 Service 或 Ports 结尾的独立类型盘点，共 90 个，partial 文件合并计数，包含 BaseService 和内部端口；其中 27 个类型同时直接接入 CommandPipeline 与 BusinessCommandExecutor。这个数量描述调用形态，不是质量评分。非此命名的关键协作者另列。

## 可行的改善方向

### R01 让一个方法显露完整业务主线

现有 `…InTransactionAsync` 形式值得保留：主体中直接写出锁定、业务校验、计算、仓储写入和审计。公开入口只需表达公共管线与执行器如何围住主体。私有方法用于当前用例的校验和组装，不要求每一步一个类。

物料建立主体已经具备这条主线。建议将它作为首个试点：梳理方法顺序与职责注释，让读者先看到 EstablishAsync 和 EstablishInTransactionAsync，再看到版本校验、取数和组装辅助。无需改变算法、事务或公开接口。验收时，读者应能在主体中回答“哪些表只读，哪些表写入，谁提交”。

### R02 减少包装和嵌套带来的跳转

箱单正向当前经过 `PostAsync → ExecutePipelineAsync → Execute → ExecutePostCommandAsync → PostInTransactionAsync`，期间多次在业务结果、ServiceResult 和 CommandExecutionResult 之间转换。主体在 `.Execution.cs`，构造依赖也在那里。箱单来源关联还将长业务主体放入多层委托中。

建议先给草稿创建、编辑、来源关联建立本类内的命名业务主体；正向过账随后减少单纯做结果转换的包装，保留一次清楚的边界转换。不是新增 Coordinator 或再搬到其他 Service。保持现有权限顺序、回放标记、错误码、预览复核、稳定锁序及回执内容，不能因为“简化”改变这些行为。

### R03 明确哪些辅助会读取数据库

PurchaseDraftCreationService 注入具体 PurchaseDraftPreviewService，调用 internal BuildLockedPreviewRequestAsync；PreviewService 一方面是公开预览用例，另一方面又为正式创建准备事务内锁定事实。这个真实双角色比文件多本身更容易误导读者。

可在后续实施中把两入口共同需要的事实准备集中到一个采购领域内的辅助，例如 PurchaseDraftFactsReader；预览和创建都直接依赖它。它只取数和组装事实，不开启或提交事务。纯 PreviewBuilder 和 WriteModelBuilder 保持纯计算。这个提取有两个现有消费者，应替代旧角色混合，不能再叠加一层转发。

ProcurementConfirmationBuilder 也持有仓储，BuildAsync 会查询客户、供应商、产品及单位。可先把方法/职责说明为“读取并验证确认依据”，必要时再改为体现角色的名称；其身份校验被独立草稿、确认和补关联使用，不能仅因叫 Builder 就全部内联。确认入口里的 `reversalFacts` 只是共享锁定读取，适合后续改为 `factLocks`。

### R04 以业务规则和真实消费者决定公共化

保留来源接收、来源退出证明、库存过账内核、权限投影和单据取号。这些有实际多消费者或跨域业务不变量；直接拆散到各调用方会复制来源版本、退出历史、库存守恒等规则。

建议保持当前用例的简单验证、结果组装和一次性字段赋值为私有方法。MaterialDemandSuggestedSupplierInitializer 的生产调用目前只有物料建立，类型独立也有单元测试价值；可保留并明确它不查库。若维护时发现它只增加跳转，可内聚为建立用例的私有计算辅助，或与该用例纯计算辅助一起组织，不需要上升为全局公共服务。Planner 有较完整业务计算及测试，应保留清晰的独立计算边界。

公共 Commands 已提供事务、回执、输入验证及执行事件。本次未发现有必要另建全局 DocumentService、Repository Manager、Universal Policy 或流程总线来解决阅读问题。

### R05 让文件位置与声明类型一致

ProductMasterMaintenanceService.Neutrals.cs 实际声明 ProductMasters.Maintenance 命名空间下的 ProductMasterMaintenanceService，却放在 ProductNeutrals/Maintenance。IProductNeutralMaintenanceService 也解析到主型号维护的同一实例。仅从目录树阅读会误以为存在第二个执行服务。

建议未来单独做文件移动，把同一类型的 partial 放在同一职责目录，保持命名空间和行为；同时说明主型号页的 SaveNeutrals 与中性资料管理页的独立 BatchSave 是不同入口。主型号服务还含同步、拉取和分类分配，是否拆同步用例要看真实依赖与事务范围，不能按行数裁切。

ProductMaintenanceService.SaveBoundary、BomService.兼容写入和 PackingListDraftService.Association 的 partial 都属于原类型。文件拆开不代表又多一个 Service，入口导航必须体现此事实。

### R06 区分父事务提交权与内部失败保护

InventoryPostingService.ProtectAsync 会尝试回滚父事务；AutomaticPostingScope.Abort 会回滚并清空共享 Session.Transaction。后者与项目“内部端口不得清空调用方事务”的目标约定不一致。箱单用例当前有 TRANSACTION_ABORTED 检查，异常继续向最外层传播，执行器还持有自己的局部事务对象。本次不据此判为 P0 或声称存在已证实的数据破坏。

后续应专门统一失败所有权，评估让内部失败传播、外层负责事务引用清理；若必须提供内部立即失效保护，则应明确其契约。不能仅删除 Abort，因为现有保护用于阻止调用方在局部失败后继续提交。涉及 Prepare、Create、Reverse 各失败点、父事务不可提交及清理路径的定向验证后才可改变。

### R07 不为形式统一改变特殊事务协议

需求转采购按每来源一个事务，使用 ExecutionRequestId 和 CommandItemId/Link 核验重放，允许跨来源部分成功；这与公共执行器的单命令事务协议不同。普通主数据的批量保存、权限管理、受控启停和文件上传也有各自边界。

先把这些差异文档化，不按“没有使用 Commands”自动判为欠缺或强制迁移。必要的公共错误/清理代码可在后续触碰时评估复用，但保持业务事务范围、幂等身份和部分成功结果。普通查询与一致性读取也要区分，不能删除看到的所有查询事务。

### R08 清理会误导阅读的遗留说明

BomExecutionReader 和 BomExecutionSnapshotBuilder 当前有接口/测试，但 Application DI 和本次搜索到的生产用例未使用它们；不能把它们当采购确认或箱单执行的必经步骤。当前实际采用由物料拆解及 PO Link 支持。

源码中仍可见“SQL 原路径”“过渡期旧仓储”等说明，实际运行接线是 PostgreSQL。后续触碰这些位置时应校正职责说明，不据旧注释恢复双库实现，不在本次文档盘点中自动删代码。

公共 CommandPipeline 还直接认识 AfterSalesException，用于日志结果分类，增加公共设施对具体业务域的认知。建议后续公共设施维护时让分类根据稳定公共错误语义表达；当前不需要仅为这一个判断增加庞大异常框架。

## 建议实施顺序与验收

| 顺序 | 可以单独评审的范围 | 成本判断 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 物料建立主线导航与局部名称/职责说明 | 低 | 能直接读出来源、BOM、建议、物料写入、审计及父事务 |
| 2 | 主型号 partial 文件归位 | 低 | 类型与 DI 保持一致，引用和编译通过 |
| 3 | 需求转采购事实准备的角色拆清 | 中 | 创建不再依赖公开 PreviewService 的内部方法；每来源部分成功、完整重放和追加行为保持 |
| 4 | 箱单嵌套主体及结果包装简化 | 中 | 权限、预览、端口、证据、回执和错误语义保持，跳转减少 |
| 单独安排 | 内部事务失效与外层清理所有权 | 中至高 | 全部内部失败不得产生部分提交，运行 PG 定向回滚/并发验证 |

成本为相对实现复杂度，不是工时承诺。若后续只改注释或文件位置，验证限定到引用、差异和必要构建；触及业务编排、预览、幂等或事务时，再按相关测试与 PostgreSQL 定向场景验收。

相关验证入口包括 MaterialDemandPublicCommandTests、SourceDemandReceptionServiceTests、SourceExitSafetyTests、PurchaseDraftSourceOrchestrationTests、PurchaseDraftSourceResultBufferTests、ProcurementOrderCommandOrchestrationTests、PackingListPostingCoordinatorTests 和 AutomaticPostingPortsTests。这里列的是后续验证候选，本次没有运行这些测试。

每条建议都是本次可读性判断，不是已授权的代码改动，也不是 P0 缺陷清单。
