# 阶段 01：目标模型与权限目录

状态：设计完成，待阶段 02—05 实施。前置：[实施总览](00-实施总览.md)。全量设计产物：[权限目录与接口页面矩阵](权限目录与接口页面矩阵.md)。本阶段未修改业务代码或执行 SQL。

## 1. 业务流程

系统管理员维护角色和角色权限，给用户分配一个或多个角色。用户登录后从 `/api/auth/me` 获得有效权限；界面据此显示入口和操作，后端每次请求重新核对当前有效授权。

用户无角色时没有业务权限，但仍可登录、读取本人身份、修改本人密码。禁用用户不能通过已有 Token 继续访问。角色停用或移除后不再贡献权限。

## 2. 五实体职责与字段建议

| 实体 | 保留/新增 | 删除/不保存 | 影响 |
|---|---|---|---|
| SysUser | 保留账号、PasswordHash、IsActive、CredentialVersion 及基类字段 | 不新增直接权限、角色名称列表或 UI 状态 | 注册、启停、当前身份、管理员保护 |
| SysRole | 保留 RoleName、Description；新增稳定 RoleCode、IsActive、IsSystem | 删除 ParentRoleId | 仓储、初始化、复制脚本、DTO、旧继承说明 |
| SysUserRole | 保留 UserId、RoleId、Uid/Version/软删除/审计 | 删除冗余 UserName、RoleName | 关联查询及展示 DTO 联表获取名称 |
| SysPermission | 新建 Uid、PermissionKey、DisplayName、GroupKey、SortOrder、IsActive 和基类字段 | 不放路由、ViewModel 类型、角色列表或权限继承关系 | 目录同步、角色权限分配、全部权限计算 |
| SysRolePermission | 补齐持久化实体，RoleId、PermissionId 及基类字段 | 不冗余权限名称、用户字段 | 替换授权 SQL，生成表与唯一约束 |

PermissionKey 和 RoleCode 为稳定业务身份，名称可展示或改名，不参与管理员识别。SysPermission 由代码目录和显式初始化工具维护，不开放任意新增/删除/改键 API。IsActive 表示发布目录生命周期，不由普通管理页面自由更改。

以上是目标字段，不代表当前都存在。实施时复用项目基类和实体 partial 元数据风格，不把本表当作可直接执行 SQL。

## 3. 关系与约束

| 关系/业务键 | 目标约束 | Application 责任 |
|---|---|---|
| SysRole.RoleCode | 唯一且不可通过普通编辑改动 | 禁止伪造、创建或重命名为 SYSTEM_ADMIN |
| SysPermission.PermissionKey | 唯一、与代码目录一致 | 未定义或停用键拒绝，不接受通配符 |
| SysUserRole(UserId, RoleId) | 有效关系唯一，按 RoleId 查询有索引 | 用户和角色有效；整组替换原子完成 |
| SysRolePermission(RoleId, PermissionId) | 有效关系唯一，按 PermissionId 查询按需建索引 | 角色和权限有效；未知 ID 拒绝 |
| 管理员用户关系 | 使用同一 SysUserRole | 删除/停用用户、移除角色时保护最后一名有效管理员 |

数据库使用逻辑关系，不生成 FOREIGN KEY。关系表使用活动行过滤唯一约束；业务编码不复用以免混淆身份。默认值和审计沿用 BaseEntity/AuditStampService，不能重复打戳。当前不存在需要随本次清理删除的业务单据历史快照。

最后管理员保护必须覆盖并发：两个管理员同时互相撤权不能最终清零，所有影响路径在同一事务协议下串行核验管理员集合，不能只在 UI 检查人数。

## 4. 管理员与管理权限

服务端确认用户持有有效 SYSTEM_ADMIN 角色后返回全部有效已定义权限。该角色不维护逐项勾选，名称可以展示为“系统管理员”。内置角色不可删除、停用、改 RoleCode 或转为普通角色。

第一版用户、角色和授权分配的写管理只对系统管理员开放；管理权限键作为保留能力，不允许普通角色通过自我分配取得管理权限。这样延续现有管理边界，不在本轮引入“可委派权限管理员”和防越权授权额度体系。

建议以 `System.Users.View/Manage`、`System.Roles.View/Manage`、`System.Permissions.View` 表达管理面能力；这些键标记为内置保留权限，由目录 API 告知 UI 不可分配。普通业务角色只分配业务权限。具体命名在本阶段矩阵冻结时统一。

## 5. 权限键设计方法

权限键先表达业务能力，再映射页面和端点；不从菜单名称反推权限，不把“模块可见”解释为“模块所有操作”。代码中的唯一目录同时定义稳定常量、显示名、分组和可分配标记；SysPermission 是目录的持久化投影，管理 UI 从目录 API 读取。

推荐新键采用 `Resource.Action`；已有明确业务语义的键可保留。不要为了字符串整齐一次性改掉全部业务权限。`View`、`Create`、`Edit`、`Delete`、`Confirm`、`CancelConfirmation`、`Post`、`Reverse` 各自表达真实操作。SalesOrder.Approve 只是讨论示例；源码是确认流程时继续使用 Confirm，不凭名称新增审批业务。

已有 Maintain/Lifecycle 是组合能力，是否拆分必须逐操作盘点；不能把原组合键简单改名为 Edit 后仍然允许删除或作废。

| 当前项 | 初步处理方向 | 本阶段必须核对 |
|---|---|---|
| Module.Products.Access | 拆清产品、BOM、分类、颜色等读取与写入能力 | 同一模块下多个资源的真实端点及页面 |
| Module.Customers.Access / Suppliers.Access | 定义对应资源 View 与写入能力 | 主数据及关系维护入口 |
| Module.Sales.Access | 盘点订单/履约读取权限 | 列表、详情、跟踪、查询 API |
| Orders.SalesOrder.Maintain / Lifecycle | 显式保留组合语义或按真实操作拆分 | 保存、删除、关闭/恢复消费者 |
| Procurement.Order.Read/Create/Edit/Confirm/Void | 保留显式操作语义，取消隐式赠送 | 字典目录必须可明确分配这些权限 |
| Module.DemandPlanning/Inventory/Shipping/QualityControl.Access | 分清导航分组、资源读取和操作权限 | 不能仅移除模块键却漏掉查询保护 |
| Post/Reverse/Establish/Rollback 等独立键 | 优先复用 | 保持正反向独立，按钮/API 同义 |
| System.Settings.Manage | 映射到具体管理能力或确有用途时保留 | 设置中心、字典、账号管理入口分别登记 |

本表是设计方向，不是已冻结的全量新旧映射。阶段 01 的交付必须补充逐键明细，覆盖 PermissionKeys.All 的每一项；每项登记“保留/改名/拆分/删除”、消费者及验证场景。尚未盘点的权限不得在阶段 03 自动猜测授权范围。

## 6. 必须产出的映射矩阵

| 矩阵 | 每行至少包含 |
|---|---|
| 权限目录 | PermissionKey、中文名、分组、普通角色可分配性、精确定义 |
| API 权限 | Controller/Action、HTTP 方法/路由、匿名或身份要求、具体键、Application 检查点 |
| WPF 权限 | 页面 RouteKey、进入权限、按钮/命令权限、调用 API |
| 旧新映射 | 旧键、目标键集合、是否改变能力范围、所有消费者、切换阶段 |

不加隐含权限继承。写操作若确实同时要求 View 和 Edit，应在 API/UI 矩阵显式登记两个条件；否则 Edit 只授权编辑，不能由客户端自动赠送 View。角色界面可以提示缺少读取权限，但不能静默勾选或保存额外权限。

## 7. DTO 与查询来源

| 类型 | 类别 | 来源与边界 |
|---|---|---|
| 用户/角色列表及详情 | Query DTO | SysUser/SysRole 当前数据；不得返回密码哈希 |
| 权限目录 | Query DTO | SysPermission 与代码目录的保留能力元数据；全目录不等于用户有效权限 |
| 用户角色列表 | Query DTO | SysUserRole inner join SysRole，按 UserId 过滤软删除与启停 |
| 角色权限列表 | Query DTO | SysRolePermission inner join SysPermission，按 RoleId 过滤 |
| 用户有效权限 | Query DTO | 用户→有效关系→有效角色→有效权限去重，管理员由服务端目录生成 |
| 整组保存用户角色/角色权限 | Command DTO | 目标 Uid、所选 Uid 集合、ExpectedVersion；不信任客户端名称和权限结论 |
| MeDto | 会话 Query DTO | 保留身份和 Permissions；Roles 明确为展示名称，另输出稳定 RoleCodes 和服务端 IsAdmin |

Join 均为当前状态，不是历史快照；缺失、删除或停用的授权来源不贡献有效权限，不能因 inner join 吞掉无效输入而让保存成功。写入前校验整组 ID。Contracts 继续兼容 netstandard2.0。
