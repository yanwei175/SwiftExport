# SwiftExport 代码审查报告（销售订单 -> SalesDemand -> RequirementPool -> 采购 -> PackingList + 客供件入库）

## 1. 审查范围

本次审查覆盖以下主链路与关键服务：

1. 销售订单审批与毛需求生成：`SalesOrderService`
2. 毛需求拆解与防重：`SalesDemandService`
3. 需求池拆解、转采购与供应商策略：`RequirementPoolService`
4. 入库回写与库存联动：`ReceiveService`
5. 装箱过账（正常项入库+出库）：`PackingListService`
6. 前端需求池页面行为：`RequirementPoolManagerViewModel`
7. API 路由注入：`DependencyInjection.Apis`

---

## 2. 结论总览

### 2.1 已做得较好的点

- 主流程分层明确：`SalesOrder` 与 `SalesDemand` 职责已分离。
- 已引入非标件（SKU 为空）支持。
- 已引入 `SalesDemand` 拆解防重标记（`IsDecomposed/DecomposedTime`）。
- 已将 `StatusFlag` 统一为 `RequirementStatusEnums` 字符串语义。
- RequirementPool 转采购支持“手工 Supplier 优先，默认供应商兜底”。

### 2.2 主要风险结论（按优先级）

- **P0（必须尽快修复）**
  1. 需求池“手工指定供应商”目前仅前端内存修改，未持久化到后端，导致“强制指定后可转单”在真实流程中不可闭环。
  2. 入库智能分摊最后一行未做缺口上限保护，存在 `ReceivedQty` 超过 `NetQty` 风险。
  3. SalesDemand 状态闭环与入库事实未完全打通：`ReceiveService` 未直接回写 `SalesDemand.FilledQty`，导致“已到货”判断可能滞后或依赖外部调用。

- **P1（建议本迭代修复）**
  1. `ValidateBusinessRulesAsync` 仅检查首个异常行，可能漏检后续行。
  2. `RequirementPoolService.ConvertSourceToPurchaseOrdersAsync` 仅按 `SourceNo` 查询，未带 `SourceType`，跨来源单号重复时有串单风险。
  3. `RejectSalesOrderAsync` 中大量 `.GetAwaiter().GetResult()`，建议完全异步化。

- **P2（优化项）**
  1. 客供件“跨仓入库（A供方 -> B供方仓）”尚未形成专用数据模型与服务闭环。
  2. 状态推进规则建议固化成统一领域方法（避免分散在多个 Service）。

## 3. 详细问题与建议

## 3.1 P0-1：需求池手工指定供应商未持久化

### 现象
- `RequirementPoolManagerViewModel.OnSetSupplierAsync` 仅修改前端模型：
  - `row.SupplierCode = ...`
  - `row.SupplierName = ...`
- 但未调用任何 API 保存到 `RequirementPool` 表。
- 转采购由后端读取数据库，用户前端修改不会生效。

### 影响
- “无供应商禁止转单”会频繁阻断，且用户以为已指定但后端仍认为未指定。

### 建议（新增）
1. 新增接口：`RequirementPoolController` 增加“更新单行供应商”API（按 `Id`）。
2. 新增服务方法：`RequirementPoolService.UpdateSupplierAsync(id, supplierCode, supplierName)`。
3. 前端 `OnSetSupplierAsync` 调用新 API 成功后再刷新列表。

---

## 3.2 P0-2：入库智能分摊最后一行可能超分配

### 现象
- `ReceiveService` 分摊逻辑中，最后一行直接 `allocateQty = leftQty`。
- 未再次 `Math.Min(item.Gap, leftQty)` 限制。

### 影响
- 可能导致 `ReceivedQty > NetQty`。

### 建议（修改）
- 最后一行也需上限保护：`allocateQty = Math.Min(item.Gap, leftQty)`。
- 并统一在写入前做 `ReceivedQty = Min(NetQty, ReceivedQty + allocateQty)` 兜底。

---

## 3.3 P0-3：SalesDemand 到货状态与入库事实未完全联动

### 现象
- 入库回写目前重点在 `RequirementPool.ReceivedQty`。
- SalesDemand 的 `FilledQty` 更新依赖 `UpdateFilledQtyAsync` 外部调用，不在入库主链中。

### 影响
- 可能出现需求池已到货，但 SalesDemand 仍停留“采购中”。

### 建议（新增/修改）
1. 在 `ReceiveService` 回写成功后，按 `SourceLineId` 聚合增量，调用 `SalesDemandService.UpdateFilledQtyAsync`（或仓储批量更新）。
2. 保持状态闭环一致：
   - FilledQty 达标 -> 已到货
   - FilledQty + ShippedQty 达标 -> 已完成

---

## 3.4 P1-1：审批前业务校验存在漏检

### 现象
- `SalesOrderService.ValidateBusinessRulesAsync` 用 `FirstOrDefault` 只取第一条异常。
- 若第一条通过非标件放行，后续行异常可能漏掉。

### 建议（修改）
- 改为逐行 `foreach` 校验，逐条返回具体错误行号。

---

## 3.5 P1-2：转采购未按 SourceType 过滤

### 现象
- `ConvertSourceToPurchaseOrdersAsync(sourceNo)` 仅按 `SourceNo` 查需求池。

### 影响
- 若不同来源类型单号重复，可能混入非销售来源行。

### 建议（修改）
- 方法签名增加 `sourceType`。
- 查询条件改为 `SourceType + SourceNo + StatusFlag + SupplyType`。

---

## 3.6 P1-3：同步阻塞调用

### 现象
- `RejectSalesOrderAsync` 中多个 `.GetAwaiter().GetResult()`。

### 建议（修改）
- 改为完整 `async/await`，避免线程阻塞与潜在死锁风险。

---

## 3.7 P2：客供件独立入库界面与跨仓模型

### 现状
- 当前库存位置使用 `LocationCode = SupplierCode`，适合普通场景。
- 你提出的客供件场景“从 A 供应商入到 B 供应商仓”尚未专门建模。

### 建议（新增）
1. 新增 DTO：`CustomerSuppliedReceiveRequestDto`
   - `FromSupplierCode`、`ToSupplierCode`、`SourceNo`、`SourceType`、`Lines`
2. 新增服务：`CustomerSuppliedReceiveService`
   - 入库到 `ToSupplierCode` 仓位
   - 记录来源 `FromSupplierCode`（可进库存流水扩展字段或备注）
3. 新增页面：客供件入库界面（独立于普通采购入库）
4. 新增回写策略：
   - 回写 RequirementPool（客供件子项）
   - 触发客供件跟踪看板统计（可后续扩展）

---

## 4. 建议增加与删除清单

## 4.1 建议新增

1. RequirementPool 单行供应商更新 API（持久化）。
2. SalesDemand 与入库联动的批量填充回写方法（按 SourceLineId 聚合）。
3. 客供件独立入库服务与 DTO/Controller。
4. 状态机工具方法（统一状态推进，避免逻辑分散）。

## 4.2 建议删除/替换

1. `RejectSalesOrderAsync` 中同步等待调用（替换为 await）。
2. 审批前 `FirstOrDefault` 式单点校验（替换为逐行校验）。

---

## 5. 建议验收用例（重点）

1. **无供应商需求池行转采购**：应被阻断并提示具体行；手工指定后可转。
2. **同销售行拆出多需求池行入库分摊**：总分配量准确、单行不超 `NetQty`。
3. **入库后状态闭环**：FilledQty 达标即“已到货”；发货达标后“已完成”。
4. **跨来源同单号防串单**：`SourceType+SourceNo` 严格隔离。
5. **客供件跨仓入库**：A->B 仓流转可追踪、库存正确。

---

## 6. 最终建议

建议按以下顺序实施：

1. 先修 P0（供应商持久化、分摊上限、SalesDemand入库联动）。
2. 再修 P1（SourceType过滤、全异步化、逐行校验）。
3. 最后落地客供件独立入库模块（P2），并配套页面与报表。

这样可以先保证主交易链“正确且可闭环”，再做客供专项能力扩展。
