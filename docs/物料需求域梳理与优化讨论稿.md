## 2. 用户已明确的边界

1. 本次讨论对象是物料需求域，当前物理名称主要是 `NetDemand`。
2. 物料需求上接来源需求 BOM 分解后的状态，下为采购订单提供数据支撑。
3. 采购订单不强制从物料需求建立，允许独立采购。
4. 本模块不涉及入库与出库。
5. 在物料需求不需要分批采购的前提下，评估 `DemandExecutionLink`、`NetDemandAllocation`、`NetDemandPlanCommandRecord` 的必要性。
6. 先建立文档并逐项讨论，本轮不修改业务代码。
7. 来源需求拆解由物料模块负责，`SourceDemandCandidatePickerView` 是唯一拆解操作入口，后端也收拢至物料用例。
8. 经常使用整单拆解，候选页面需要支持按来源单操作；若 ContentDialog 不适合承载，可改用 Window。具体布局与整单处理规则尚未确认。
9. 物料模块不负责怎么采购、采购多少，也不增加中间 PMC 岗位或分批计划流程。采购方式、数量、取消、减量、替换与关闭属于采购领域。
10. 物料页面不转采购。采购页面主动从物料需求获取数据，建立采购单之后建立关联；取消采购单之后取消关联。独立采购仍合法，不要求补造关联。
11. 采购自身原因的取消、减量、关闭不强制回退物料；撤销上一轮“先整单回退物料，采购才可调整”的通用门禁。整单操作需求保留。
12. 关闭一张采购单不等于关闭来源需求，不要求来源先关闭；来源需求是否继续与采购是否继续分别处理。
13. 供应问题重新采购可从仍有效的物料再次获取，不要求重复 BOM 分解；来源或 BOM 依据确实变化时再讨论重新建立，旧执行历史保留。
14. 允许同来源单多个物料合并采购行，作为采购侧额外支持选项，由采购界面勾选是否合并；默认勾选状态尚未确认。
15. MD-03：变更只需日志，不需要独立计划版本管理；优先保持架构简单，不为 Allocation 继续增加业务流程。

### 尚不能从以上边界直接推导的结论

- 不把“不分批采购”解释成物料领域强制整量采购；采购数量由采购决定，具体关联数量校验仍需在采购交接协议中定义。
- 整单采购操作逐行校验、整单遇阻断如何反馈，见建议 S-04；不再默认联动回退整张来源单。
- 正常采购调整不设计“物料先回退、采购待取消”的中间状态；BOM 纠错的真实回退另见 S-06。
- 拆解入口归物料模块已确认；整单中已建立、不可建立条目的展示和处理规则尚未确认。
- 是否需要独立维护建议供应商和建议交期，尚未确认。
- 不涉及入出库不等于可以删除已有正式事实的安全保护；跨域检查归属仍需安排。

## 3. 当前代码事实

### 3.1 主链路

```text
来源需求 GrossDemand
    ↓ 物料建立用例读取来源版本、实物依据、产品及 BOM
MaterialDemandEstablishmentService
    ↓ 复用 GrossDemandDecompositionPlanner
NetDemand：拆解结果、来源依据、物料及路径快照
    ↓ NetDemandInitialAllocationPlanner
NetDemandAllocation：每条物料一条活动计划
    ↓ 计划选择、采购预览、草稿创建
DemandExecutionLink：物料/计划对采购行的数量贡献
    ↓
采购订单头行
```

当前 BOM 分解在物料建立用例内完成，不是单纯接收上游已经生成的物料清单。建立与回退已迁入 `MaterialDemandEstablishmentService`，不再回写来源四个兼容拆解字段。

来源技术版本、来源事实版本和实物依据指纹保存在 NetDemand。重复建立检查会比较已有活动物料的实物依据；同内容技术版本推进与实际需求变化区别处理。

### 3.2 当前依赖清单

| 对象 | 实际作用 | 初步评价 |
|---|---|---|
| GrossDemand | 身份、来源、数量、交期、生命周期、版本 | 必要上游依赖，方向应是物料读取来源 |
| Product、BOM | 拆解及物料信息 | 必要；实时资料与历史依据必须区分 |
| Supplier、产品默认供应商 | 初始化计划、分组及转采购校验 | 建议资料承担了过重准入责任 |
| NetDemandAllocation | 活动计划、数量、建议、父子送达、命令身份 | 当前是强制依赖，不是可选建议 |
| DemandExecutionLink | 承接数量、采购追溯、释放与历史保护 | 关联事实有价值，但强绑 Allocation |
| PurchaseOrderHead/Line | 建单、取消、释放、状态查询 | 需求服务拥有部分采购规则 |
| 入库/出库/PL 数据 | 追溯数量、退出阻断、旧执行来源 | 与本轮目标边界不符，需迁移消费者 |
| DbSession、命令记录 | 事务、并发与重试一致性 | 必要能力，不能随模型简化丢失 |

### 3.3 采购存在新旧两条链

- 新 `ProcurementOrderCommandService` 的独立采购创建会清空需求来源，以 `UnlinkedQty = Quantity` 建立行；`ProcurementConfirmationBuilder` 不读取需求链。
- 旧 `PurchaseOrderWorkspaceService/Repository` 要求需求来源和有效 Link，部分命令要求采购行数量等于 Link 有效贡献总量，缺关联被视为只读或异常。
- 两条服务均存在 DI 接线。因此不能概括为“系统完全不支持独立采购”，准确问题是：独立采购新链存在，旧需求转采购链的管理与执行边界仍强绑定。
- 本轮没有完成所有界面路由、运行时权限及真实数据库流程的逐项验证，不据此宣称独立采购全链路已验收。
- 采购能力地图第 7 节及 PROC-009 已明确：旧 IPurchaseOrderWorkspaceApi、对应 Application Service 和 DTO 仅暂留兼容，不得重新注入新 Manager；旧链删除另立任务。旧接口依赖 Allocation 是迁移负担，不是新采购架构必须保留 Allocation 的理由。该文档没有提供所有旧接口逐路由删除清单，不能说旧链已经删除。

## 4. 逐项讨论

### MD-01：物料需求的输入与职责

**已确认**：由物料模块负责从来源需求建立物料并执行 BOM 分解。`SourceDemandCandidatePickerView` 是唯一拆解操作入口，不再另建来源侧分解入口。常用操作是整单拆解；ContentDialog 容量或交互不合适时，可以使用 Window 承载同一用例。

**当前前后端调用链（2026-09-09 复核）**：

```text
物料工作台“从来源需求建立”
  → SourceDemandCandidatePickerView / ViewModel 查询并选择来源行
  → NetDemandWorkspaceViewModel.EstablishFromSourcesAsync 提交
  → INetDemandWorkspaceApi
  → POST api/demand-planning/net-demands/source-demands/establish
  → NetDemandWorkspaceController
  → NetDemandWorkspaceService 转发
  → MaterialDemandEstablishmentService.EstablishAsync
  → GrossDemandDecompositionPlanner + NetDemandInitialAllocationPlanner
  → 同事务写 NetDemand 与初始 Allocation
```

后端建立、回退入口已在物料 API；当前 GrossDemandWorkspaceController 没有拆解或回退接口。`GrossDemandDecompositionPlanner` 虽保留旧名称，实际由物料建立服务调用，名称不代表业务仍归来源模块。选择器只负责选择，当前实际提交由物料工作台发起。

**这里与 DemandExecutionLink 的关系**：

- 来源需求到物料的关系是 `NetDemand.GrossDemandId`，不是 Link。
- 初次拆解建立路径不要求存在 Link，也不写 Link；它读取来源、产品/BOM，并写物料和初始 Allocation。
- 同一个 MaterialDemandEstablishmentService 注入 Link 仓储，是因为回退需要检查已有采购等活动执行，不能把这个服务级依赖误解为“拆解必须先有 Link”。
- Link 在物料被采购承接时记录下游关系，属于后续 MD-04 议题。

**整单操作的当前缺口**：

1. 当前是来源行平铺列表，只有关键词查询，没有来源单分组、整单勾选和整单明细状态视图。
2. ViewModel 固定读取第 1 页、最多 200 行；只保留 CanEstablish 条目。不能把当前列表全选视为整单全选，也不能从隐藏的已建立/不可建立行判断整单情况。
3. 后端已有多来源行 Items 批量建立，并在一次事务内处理；这不等于已有“按来源单完整解析所有行”的接口。整单选择需要由服务端证明完整范围，不能仅靠客户端当前页。
4. 当前候选视图由宽度 1100 的 ContentDialog 承载。是否切 Window 由最终内容和操作空间决定，不另外复制建立逻辑。

**下一项待讨论**：选中一张来源单后，如何展示已建立、可建立、不可建立的行；“整单拆解”是否只建立尚未建立的有效行，以及遇到阻断是否整单失败。这里只登记问题，本轮尚未确认具体规则。

**结论**：输入与唯一入口归属已确认；整单交互和后端整单语义待细化，尚未修改页面或业务代码。

### MD-02：采购自主取数与采购调整边界

**现状**：每条物料只允许一条活动 Allocation，且活动 `PlannedQty` 要等于 `NetQty`；但手选转采购允许数量大于零且不超过剩余量，一键入口使用全部剩余量。当前“一条活动计划”并不等于“一次采购”。

**已确认的职责**：物料只负责物料需求，不管采购怎么采购、采购多少，不增加中间 PMC 岗位。采购方式、数量及采购单生命周期均在采购领域处理。此前将本议题理解为“是否由物料要求每条一次全部采购”不准确，该方向不再采用。

**正向流程**：

```text
物料模块从来源需求获取 → 分解并建立物料需求
采购模块从物料需求获取 → 建立采购订单 → 建立物料与采购关联
```

物料页面没有转采购操作；采购取数体验类似物料从来源需求取数。采购单与关联的持久化建议保持原子一致；“先建单后关联”是业务顺序，不据此推导允许两次独立提交留下半成品。

**反向职责（最新已确认方向；具体执行规则见第 4.1 节待审建议）**：

| 采购动作 | 有关联物料需求时的前置条件 | 执行归属 |
|---|---|---|
| 取消采购单 | 不要求物料先回退，校验采购自己的可取消事实 | 采购处理并同步关联结果 |
| 减量 | 不要求物料先回退，不能抹去已执行部分 | 采购决定减量及受影响来源贡献 |
| 替换供应商/重采 | 原物料依据未变则可继续使用 | 旧采购可退出部分与新采购分别留痕，细节待审 |
| 关闭未完成采购单 | 不要求来源需求先关闭 | 采购停止本单剩余执行，来源需求是否继续独立决定 |

需要整单操作。独立采购没有物料关联，不要求为满足上述关联门禁而伪造来源或先走物料回退；仍遵守采购自身规则。

**重新采购**：采购侧再次获取仍有效的物料缺口即可；来源或 BOM 依据未变时不重新拆解。保留旧采购和历史关联，不在物料模块建设分批调度。

**合并选项**：允许同来源单多个物料合并采购行，采购界面提供勾选。该选项不能被实现成强制合并；产品、单位等合并兼容条件及默认是否勾选留在采购设计中细化。

**撤销的方案**：统一“先强制回退物料，再取消采购”会与现有活动 Link 回退阻断互相等待，还会使供应问题引起不必要的重拆，因此不再采用。真实 BOM 纠错回退仍需保护历史，不直接删除原校验。

**结论**：采购侧取数、可选合并、整单操作和不强制回退方向已确认；执行边界、贡献调整及原子性方案留第 4.1 节审阅。

### MD-03：是否仍需独立 Allocation

**现状**：详情没有活动 Allocation 就失败；建立必须同步生成 Allocation；查询将活动计划数量不是一条或计划量不等于物料量视为异常。供应商或日期调整采用新增计划、替代旧计划的方式。

**用户已确认**：只需要变更日志，不需要独立计划版本管理；架构不要复杂化。结合 MD-02，不建设 PMC 分配或采购数量计划。

**Allocation 当前实际承担的职责与去向建议**：

| 当前职责 | 当前实现 | 按已确认边界的安排 |
|---|---|---|
| 计划版本与变更历史 | PlanRevision、ReplacesAllocationId、生命周期、原因及操作人 | 不再需要独立业务计划版本，改用现有日志记录必要变更；旧记录留存解释 |
| 采购/生产/外协执行方式及计划数量 | ExecutionType、PlannedQty；当前一条活动计划覆盖整条 NetQty | 物料本体保留自身要求和拆解供货方式快照；采购数量和安排归采购，不设中间分配层 |
| 供应商与交期建议 | PurchaseSupplierId、供应商快照、PlannedDeliveryDate、AssignmentSource | 实际供应商和采购交期归采购；是否展示默认建议留 MD-05，不因此保留独立 Allocation |
| 客供件送达目标 | DeliveryTargetAllocationId 指向父活动计划，并推导目标供应商 | BOM 父子组成留 NetDemand，实际目标归采购；取消计划身份联动 |
| 采购关联与数量查询锚点 | Link 引用 AllocationId，工作台按活动 Allocation 聚合剩余量 | 关联直接锚定已有 NetDemandId；采购结果仍需可追溯，不能用日志代替关系事实 |
| 旧跨域执行与查询入口 | 入库、PL、销售履约和旧采购查询存在 Allocation 引用 | 分别迁移至其真实来源、采购或正式单据事实；不把旧消费者升级为新领域前提 |
| 计划修改命令回执 | 专用命令记录旧新 Allocation 及受影响子计划 | 旧计划命令退出后评估专用回执退出；必要写命令的幂等保障继续保留 |

**采购旧接口的核对结论**：采购能力地图第 7 节明确旧 `IPurchaseOrderWorkspaceApi` 及对应 Application Service 暂留兼容；PROC-009 明确新 Manager 不得使用旧 Workspace API/DTO，旧链删除另立任务。PROC-002 还记录旧接口混合管理、跟进、Trace 的拆分方向。后续收敛不能为兼容这些已计划退出的接口重新建设一层 Allocation，也不能只删除旧 Workspace 就认为所有引用已清理，入库/PL 等仍需处理。

**架构建议**：Allocation 无需成为目标模型中的独立业务层；保留来源需求、物料需求、采购及其必要关联即可。旧表在迁移期间只承担兼容历史，不作为长期简化版计划模块，不新建一个换名的分配表。该建议尚不等于授权立即删表。

**日志边界**：用户说“只要日志”针对计划变更历史，不表示 BOM 拆解依据、采购关联和反向门禁也全部改为读日志推断。必要事实继续放在各自已有业务对象中，避免以省表为名增加隐式状态。

**结论**：独立计划版本不需要，日志足够；建议 Allocation 从目标业务模型退出。下一步无需继续扩展其功能，仅随后续议题确定少量字段归属及旧消费者迁移。物理删除、MD-05 建议展示和 MD-07 回退协议尚未实施或定稿。

### MD-04：采购关联 Link 保留什么

**现状**：Link 同时保存 NetDemandId、AllocationId、采购头行、命令身份、原始贡献和释放量。采购合并行可保留多条来源贡献。

**建议倾向**：保留 Link 的关联职责，直接以 NetDemandId 为业务锚点，AllocationId 降为旧历史兼容。无需求的独立采购可以没有 Link。

**原因**：物料甲 30、乙 70 合并采购行 100，仍需解释各自贡献。MD-02 已确认采购侧可选合并；取消后重新采购也需要保留旧新关联的区别。具体采用当前 Link 实体还是收窄其字段，仍未确认。

**当前数量口径与后续边界**：当前有效贡献为原始贡献减释放量。未来采购数量及减量归采购；物料不提供分批采购/释放命令。建议采购调整与关联变化一起提交，不新增强制回退等待状态，具体见 S-01 至 S-03。

**待决定**：减量如何选择受影响的来源贡献、部分执行时如何保留历史，以及 Link 的旧字段迁移；已有具体建议见下文。

**结论**：待确认；不建议仅因“不分批”就删除追溯关系。

**官方资料参考**：

**建议的简单边界**：需求回答“还要不要、需要多少”，采购回答“向谁买、买多少、这张订单还执行多少”。采购供应商变化或取消采购，不自动表示来源需求消失；上游需求取消也不自动表示采购和库存历史错误。

| 动作/原因 | 建议处理 | 是否必须回退物料 |
|---|---|---|
| 供应商无法供货，取消或替换采购 | 采购关闭/取消允许退出的未执行部分，更新对应 Link 的有效承接；仍有效的物料可由采购再次获取 | 不需要，来源和 BOM 未变 |
| 采购调整数量 | 采购显式变更并展示受影响物料贡献；已有执行部分受采购自身门禁保护 | 不需要，不自动修改物料需求量 |
| 这张采购不再继续，关闭剩余 | 采购保留已执行部分，关闭尚未执行的剩余；需求仍有效时保留缺口供后续采购 | 不需要，不要求为了换供应商而关闭来源需求 |
| 客户不再需要，或来源要求发生变化 | 来源领域关闭/修改对应要求；物料停止受影响的新获取，采购另行处置未执行承诺 | 是否重拆取决于物料依据是否变化；不机械回滚整套历史 |
| BOM/物料分解确实错误 | 无采购承接时可安全回退；有承接时先处理受影响采购的可退出部分，再决定回退/重建；有已执行事实不能直接重置 | 这是物料回退的真实使用场景 |

**Link 的最小处理建议**：

- 继续复用 DemandExecutionLink，不新建关联表或 Allocation 替身。
- 采购取消/减量与对应关联数量变化同事务完成，保留原关联、原数量、释放量及日志；不先删关联再等采购取消。
- 全部承接退出才将关联整体结束；部分退出保留仍有效的贡献。关闭剩余不把已履行部分的历史关联全部取消。
- 多物料合并采购行减量时，必须确定影响哪几条来源贡献；采购确认前展示分配明细，必要时允许调整。默认如何分配留待确认，不静默让某条物料承担全部差额。
- 未涉及上游真实需求变化时，不需要增加“物料已强制回退、采购等待取消”状态。
- 仍有效需求的未承接数量作为采购获取参考，来自服务端查询，不建立新的 PMC 计划；已承接量不能因换单或重试重复释放。

**整单操作建议**：保留整张采购单的取消/关闭按钮，由后端逐行检查并预览受影响关联；整单是一种批量操作，不要求上游整张来源单一并回退。部分已收货时只能处理剩余，正式执行事实的校验归采购/库存现有边界，物料不承担收发功能。

**重新采购口径**：供应问题重采从原有效物料再次获取；来源或 BOM 改变才评估重拆。此方向已接受，替代上一轮所有重采必须重走全流程的规则。

**下一步审阅**：方向不再重复确认；按第 4.1 节逐项决定取消/关闭、合并减量和需求变化的具体方案。

### MD-05：建议供应商、实际供应商和送达目标

**现状**：采购预览按 Allocation 供应商分组，缺少供应商阻断。初始化时，未配置默认供应商可以待分配，但配置了失效默认供应商会导致建立失败。客供件目标指向父 Allocation，目标供应商由父计划推导。

**已定位的过度联动**：父件仅修改交期也生成新 Allocation，子件必须一起替代以重新指向新父计划；受影响子件已有活动 Link 时，父件修改被阻断。

**建议**：默认供应商仅提供建议；采购决定实际供应商与送达目标。父子 BOM 关系保留组成解释，不决定采购目标，也不作为库存归属。建议变更不回写既有采购。

**待讨论**：物料页是否还要维护供应商建议，还是全部交由采购选择？送达建议是否有实际使用价值？

**结论**：待确认。

### MD-06：物料与采购的交接、页面入口

**现状**：NetDemand Controller 有采购预览、创建、取消、释放接口；需求目录中的 PurchaseDraftCreationService 直接申请采购单号、写采购头行及 Link。物料 Trace 可以取消整张采购草稿。

**已确认**：由采购页面主动获取物料需求，创建采购单后建立关联；物料不转采购。采购拥有采购数量、创建、取消、减量、替换与关闭；自身调整不要求物料先回退。

**原建议处置**：不再采用“物料页保留交给采购的转单入口”。采购側取数提供可选合并；独立采购仍不必有物料关联。只读导航与 Trace 是否保留另议，不借导航保留物料侧建单命令。

**技术建议**：建单和关联保持同事务成功或失败，防止漏关联；这不使物料拥有采购编排。整单获取的候选、版本及数量关联契约待采购侧设计。

**结论**：采购侧取数与入口归属已确认，具体契约尚未设计。

### MD-07：变更、回退与历史

**现状**：安全回退有活动执行 Link 阻断；建议替代也使用执行 Link 阻断。建立用例可识别来源实物依据变化，但完整变更处置能力不应仅凭该检查认为已经实现。

**已确认的边界**：采购自身调整不回退物料；关闭采购不要求关闭来源。真实需求变化在来源/物料侧处理，采购明确处置自己尚未执行的承诺。整单操作保留，不能抹除历史。

**与现有代码的关系**：当前活动 Link 阻断物料回退，不再作为普通采购调整必须突破的障碍；不为采购改量而放开回退。真实分解错误时再核验下游影响，具体建议见 S-06。

**关联退出建议**：采购动作与 Link 变化同事务完成，历史保留；部分执行不整体取消历史贡献。不添加“回退待采购取消”的通用状态。

**历史查询问题**：物料 `GetTraceAsync` 用活动工作台查询取得摘要，已回退物料无法经此入口读取完整自身历史。来源物料 Trace 有另一条历史查询路径，两者应区分并补齐。

**待审阅**：S-01 的取消/关闭区别、S-02 的合并行减量、S-05 的来源需求变化、S-06 的真正回退。

**结论**：各领域独立处理方向已确认；具体规则见待审建议，不再以来源关闭作为采购关闭的通用凭证。

### S-01：取消与关闭分别表达什么

**依据**：R-01 区分未执行剩余和已发生事实；以下按钮命名是本项目建议。

**推荐**：

- “取消采购”：本单尚无必须保留的实际执行，终止整张单的采购承诺；保留原单及关联历史。
- “关闭剩余”：已有部分执行，本单剩余不再执行；保留已执行部分。这里是业务停止供货，不等于财务结案。
- 不把原订购 100、实收 60 的采购单普通覆盖成“原来只订了 60”；保留原数量及停止执行的剩余依据，用现有模型最小扩展表达。
- 关单不自动关闭需求，也不自动生成下一张采购。

**例子**：订购 100，已收 60，供应商不再供货。关闭剩余 40；物料仍需要 100 时，采购可再次获取这 40。已收 60 的事实由采购引用所属领域的有效结果核验，物料不计算收发过程。

**请决定**：是否接受“无执行用取消、部分执行用关闭剩余”的操作区分？

**状态**：待用户决定。实际哪些下游事实阻断，由采购既有边界核对，不预设“只检查收货”足够。

### S-02：合并采购行减量时，减少谁的数量

**依据**：用户已确认同来源单可选合并；R-01 支持只处理剩余。官方资料未指定本项目多 Link 的减量分配算法。

**推荐**：采购减量预览展开原物料贡献，采购人员填写每条减少数量；系统校验总减少量与采购减量一致。第一版不做自动比例分摊或智能排序，避免静默决定来源优先级。

**例子**：A 30、B 70 合并为 100，要减少 20。预览可明确选 B 减 20，也可 A 减 5、B 减 15。物料需求本身不被减量，改变的是本张采购的承接结果。

**边界**：不能释放已被真实执行占用的部分；已收量只有采购行总额、无法证明到各来源的贡献时，需在采购调整预览明确并验证保留贡献分配，不能假装历史已经按 A/B 分摊，也不能将这次分配说成库存所有权。无法证明安全范围则先阻断该调整，而不是猜测。

**请决定**：是否接受第一版由采购明确选择受影响来源贡献，不自动分摊？

**状态**：待用户决定。此操作只在合并行变更时出现，不增加物料计划岗位。

### S-03：关联更新与重新获取

**依据**：R-02 的需求与采购分别管理，以及本项目现有 Link 字段；事务处理是本项目技术建议。

**推荐**：复用 DemandExecutionLink 的 NetDemandId、TargetLineId、AllocatedQty、ReleasedQty 和历史信息。采购建单、取消、减量、关闭的结果与关联更新在同一数据库事务提交；超时重试返回原结果。

**例子**：B 原贡献 70，本次减 20，保留原贡献及释放记录，有效承接为 50。B 仍有效时，采购侧可再获取未承接的 20。全部退出可结束关联，部分退出不取消整条历史。真实已执行部分不能因采购关闭就全部释放。

**数量边界**：需求量、有效承接、剩余未承接是查询口径，不表示库存可用量或已交付量。采购可独立买入，但不能把超出所选物料要求的数量伪记成该物料贡献；额外数量是否允许在同一采购行作为未关联部分，留采购契约另议。

**请决定**：是否接受“关联结果原子更新、有效物料缺口可再次获取”，不增加回退待取消状态？

**状态**：待用户决定；不新增关系表和 Allocation 替身。

### S-04：整单操作如何保持简单

**依据**：用户要求整单操作；R-01 有采购头取消入口。以下失败策略是本项目推荐，不是官方统一规则。

**推荐**：采购提供整单取消/关闭剩余按钮。先列出全部采购行及受影响物料，服务端按完整订单检查；任一行不满足本次动作，则整单不提交并显示原因。第一版不做用户未选择的部分成功。

**例子**：10 行中 1 行存在阻断，提示这 1 行的原因，不先悄悄处理其余 9 行。“整单”限定本次采购单，不级联回退整张来源单、兄弟采购或其他物料。

**请决定**：是否接受整单预览、整单成功或失败？

**状态**：待用户决定；部分执行采购应使用关闭剩余动作而非整单取消。

### S-05：来源需求确实不要了怎么办

**依据**：R-02 的需求显式关闭与已采购状态分离；本项目要求来源拥有需求事实。

**推荐**：来源关闭对应需求后，物料阻止受影响部分被新采购获取；已有采购仍保留，由采购人员取消、减量、关闭剩余或继续备货。显示“来源已结束但采购仍有承诺”的差异及关联采购清单，复用现有页面，不建设审批单、任务流或自动反向库存。

**例子**：需求 100 已全部下采购，客户只要 80。先记录来源的有效要求及变化，停止新增超额承接；采购再明确处理多出的 20，不能直接把原 Link 或历史采购改成 80 来掩盖差异。涉及来源数量修订的准入仍由来源领域负责。

**请决定**：是否接受差异提示加采购显式处置，不自动级联取消、不要求先清完采购才允许来源表达变化？

**状态**：待用户决定；这是对“领域各自结束”的具体交接建议，不能把宽泛方向理解为全部细节已批准。

### S-06：物料真正需要回退的场景

**依据**：项目既有 BOM 历史规则；R-01 只支持保留执行事实这一原则，不直接规定物料拆解回退。

**推荐**：

- 没有有效采购承接、没有阻断的正式历史：允许整单安全回退后重新分解。
- 已有未执行采购承接：先由采购处理可退出部分，再复核是否允许物料回退；不是采购调整之前先强制回退物料。
- 已有实际执行：不提供无条件重置整单，保留旧拆解与执行依据，另行明确变化范围；本轮不预建复杂修订平台。
- 当前 BOM 改了不自动刷新已经建立的物料；普通供应商变化无需重新分解。

**请决定**：是否接受“无承接可安全回退、有承接先处理影响、已执行不重置历史”的最小规则？

**状态**：待用户决定。

### S-07：供应商和交期只作为参考

**依据**：本项目已确认采购拥有方式和数量、无需 PMC；两份外部参考并未规定本项目建议字段归属。

**推荐**：物料只展示来源交期与可选产品默认供应商，不设人工“分配供应商/替代计划”的操作。采购取数时把参考信息带入，由采购决定实际供应商、交期及送达目标；缺少默认供应商不阻断物料建立。

**例子**：产品默认供应商甲，采购选择乙，不需要先返回物料页改计划，也不联动替代客供件计划。

**请决定**：是否接受物料只读参考、不维护独立供应商/交期计划？

**状态**：待用户决定；MD-05 后续围绕此方案讨论。

## 7. 迁移与验证备忘（不是当前实施任务）

### 7.1 依赖迁移顺序建议

1. 以 MD-01、MD-02 最新方向为前提，逐项确认第 4.1 节，再细化关联交接及实体形态。
2. 采购用例拥有实际供应商、目标和单据行为；物料提供承接数据。
3. 解除父计划、建议供应商强绑定。
4. 对入库、PL、销售查询、历史 Trace 的 Allocation 引用分类迁移。
5. 替换 DTO、WPF 和剩余量聚合口径，再停止新建 Allocation。
6. 迁移计划命令回执，最后评估历史表、字段及约束的物理退出。

### 7.2 数据库注意事项

- 现有 006/007 迁移包含 Allocation 关系、目标约束、Link 外键和命令唯一索引；C# 改可空不等于数据库已解除依赖。
- 物理约束以实际部署数据库为准，本轮未连接数据库。
- 保留命令项唯一性，以及非负贡献、释放不超过原始贡献等数量校验。
- 按 NetDemandId、采购头行及有效状态配合查询索引；不对所有采购建立必填需求外键。
- 当前 NetDemandId 已存在于 Link，优先验证并利用已有关系，不新增平行关系表。
- 无法证明的历史单位、来源、父计划关系标记待核实，不猜测回填或删除。

### 7.3 后续需要证明的行为

- 来源重复建立、同内容版本推进、真实依据变化、失败回滚及并发建立正确。
- 无供应商建议可以建立物料；采购能选择实际供应商。
- 独立采购无来源、无物料、无 Allocation、无 Link 仍通过所属采购用例。
- 采购侧勾选合并时，同来源多物料贡献守恒；未勾选不强制合并。
- 物料页面不执行转采购；采购取数、建单与关联写入一致。
- 采购自身取消、减量、关闭不要求物料回退；仍校验自身已执行事实，不能越界减少历史数量。
- 关闭采购不自动关闭来源，来源继续有效时允许采购再次获取剩余缺口；独立采购无须伪造前置关联。
- 整单操作完整解析关联范围，不把当前页或当前选中一行冒充整单。
- 取消、减量、重建及超时重试不重复承接、不丢历史。
- 父件改建议不改子件采购，不要求撤真实收发事实。
- 回退后仍能查询历史物料与采购关联。
- 单位和 BOM 历史依据不随当前主数据变化。
- 新执行消费者不再要求 Allocation，旧历史仍可解释。

现有 NetDemandInitialAllocationPlannerTests、NetDemandPlanReplacementPlannerTests、NetDemandPlanCommandIdempotencyPolicyTests 等可作为回归资料。其中“父件只改日期仍替代子计划”“默认供应商失效拒绝”等断言记录的是旧行为，后续应依据确认结论重写对应行为验收，不机械保留，也不为通过测试直接删断言。
