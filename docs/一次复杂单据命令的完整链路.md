可以理解为“公共能力”，但不能全部叫“公共服务”。

复杂单据后端应分成三层：

1. WebApi 公共管道：认证、异常、关联 ID、防抖。
2. Application 公共执行能力：权限、事务、幂等、审计、单号。
3. 单据自己的业务服务：保存、确认、过账、反向、查询。

最重要的边界是：

> 公共层负责“命令怎样安全执行”；具体单据负责“这个命令业务上能不能执行”。

不能把入库、出库、采购的业务规则抽进一个万能 `DocumentService<T>`。

## 一次复杂单据命令的完整链路

以“入库单过账”为例：

```
WPF 页面
  │
  ├─ UI Busy / 禁止重复点击
  ├─ 生成并保存 CommandId
  ├─ 携带 ExpectedVersion
  ▼
Controller
  │
  ├─ 路由和模型绑定
  ├─ [Authorize]
  ├─ 可选防抖 Filter
  └─ CancellationToken
  ▼
Application Command Service
  │
  ├─ 认证与细粒度权限
  ├─ 参数验证
  ├─ 开启事务
  ├─ 锁定 CommandId
  ├─ 查询命令回执
  │    ├─ 相同内容：返回原结果
  │    └─ 不同内容：幂等冲突
  ├─ 锁定单据与相关业务事实
  ├─ 校验 ExpectedVersion
  ├─ 校验状态和业务资格
  ├─ 写单据状态/库存流水
  ├─ 写命令回执
  ├─ 写 BusinessOperationLog
  └─ 提交事务
  ▼
ServiceResult<TResult>
```

这里至少有四种容易混淆的保护：

| 机制              | 解决问题                     | 是否保证业务正确 |
| ----------------- | ---------------------------- | ---------------- |
| 页面 Busy         | 用户连续点击                 | 否               |
| API 防抖          | 几秒内重复到达               | 否               |
| `ExpectedVersion` | 别人已经改过单据             | 是               |
| `CommandId`       | 网络重试导致同一命令重复执行 | 是               |
| 数据库事务和锁    | 多事实必须全成全败           | 是               |
| 唯一索引/约束     | 最后的数据库一致性防线       | 是               |

页面 Busy 和 Filter 是体验增强；真正可靠的是后四项。

## 建议保留多少公共能力

我建议控制在 **8 个核心公共服务 + 4 个 WebApi 管道组件**。不是每项都必须单独建一个巨大的类，但职责要明确。

### 8 个核心公共服务

#### 1. 当前用户服务 `ICurrentUser`

职责：

- 当前用户 UID；
- 用户名；
- 是否已认证；
- 当前请求身份。

现有项目已经有。它避免每个服务自己解析 `HttpContext.Claims`。

必要性：必需。

#### 2. 权限服务 `IUserPermissionService`

职责：

- 校验当前用户是否具备某个稳定权限键；
- 例如查询、编辑、确认、过账、反过账分别授权。

现有项目已经有。

必要性：必需。仅有 `[Authorize]` 只能说明“登录了”，不能说明“允许反过账”。

#### 3. 请求关联上下文 `ICorrelationContext`

职责：

- 保存一次 HTTP 请求的 `CorrelationId`；
- 串联 Serilog、异常日志和业务审计；
- 它不等于 `CommandId`。

现有项目已有 [CorrelationIdMiddleware.cs (line 6)](D:/Documents/source/CSharp/SwiftExport/SwiftExport.WebApi/Middlewares/CorrelationIdMiddleware.cs:6)。

必要性：必需。

#### 4. 数据库会话 `DbSession`

职责：

- 当前 request scope 共用一个 Connection；
- 保存当前 Transaction；
- 保证多个 Repository 参加同一事务。

现有项目已经有，并通过 `ServiceBaseContext` 交给 Application。

必要性：必需。

#### 5. 业务命令执行器

建议职责：

- 检查已有事务；
- 开始、提交、安全回滚事务；
- 锁定 `CommandId`；
- 读取命令回执；
- 比较用户、操作名和请求指纹；
- 成功后保存结果；
- 统一处理取消令牌；
- 把可预期异常转换为稳定错误码。

项目目前缺少统一版本。

现状是采购有 `ProcurementOrderTransaction`，入库、出库、仓库、PackingList 又各写了一套。这是最应该补齐的公共能力。

建议概念名称类似：

```
IBusinessCommandExecutor
ICommandReceiptStore
BusinessCommandRequest
BusinessCommandExecutionResult
```

但执行器只处理机械流程，不判断“采购是否允许确认”。

必要性：复杂单据必需。

#### 6. 命令回执服务

职责：

- 持久化 `CommandId`；
- 保存 Operation、Actor、AggregateUid；
- 保存 RequestFingerprint；
- 保存执行状态和成功结果 JSON；
- 支持相同命令安全重放；
- 拒绝同一个 ID 被用于不同内容。

采购已有 `ProcurementCommandReceipt`，PackingList 有专门执行证据；入出库草稿目前主要借用 `BusinessOperationLog`。

建议建立统一接口，底层可以：

- 使用统一 `BusinessCommandReceipt` 表；或者
- 不同领域使用自己的执行表，但实现相同接口。

必要性：有 CommandId 的正式命令必需。

#### 7. 业务审计服务

职责：

- 写 `BusinessOperationLog`；
- 保存操作人、原因、单据、前后变化和关联对象；
- 面向业务人员追溯；
- 只追加，不修改、不删除。

现有项目已经有 Repository，但建议在 Application 上封装为语义化服务，例如：

```
IBusinessAuditService.AppendAsync(...)
```

这样各服务不用反复手工填写 `Module`、`AggregateType`、`UserNameSnapshot`、`OccurredDate`。

必要性：确认、取消、作废、过账、反向、权限敏感修改必需；普通查询不需要。

注意：它不应继续兼任命令回执。

#### 8. 单号服务 `IDocumentNoService`

职责：

- 按单据类型和期间生成唯一业务单号；
- 处理并发；
- 不由 Controller 或客户端拼接单号。

项目已有。

必要性：有业务单号的单据必需。

## 4 个 WebApi 公共组件

### 1. 全局异常处理

现有 `GlobalExceptionMiddleware`。

目标职责：

- 捕获未处理异常；
- 写结构化日志；
- 不泄露数据库异常；
- 返回统一错误结构和正确 HTTP 状态。

未处理系统异常返回 HTTP 500 和统一失败包装，并复用 MVC 的 Newtonsoft.Json 配置。业务错误、模型校验、认证拒绝和防抖分别接入同一错误出口，详见《统一错误与HTTP响应契约》。

### 2. 认证和授权

包括：

- JWT Authentication；
- `[Authorize]`；
- Application 细权限校验。

两层都需要：

```
[Authorize]                = 必须登录
IUserPermissionService     = 是否能执行这个业务动作
```

### 3. CorrelationId 中间件

用于追踪一次请求。

必须与 `CommandId` 分开：

```
CorrelationId：这一次 HTTP 调用
CommandId：这一次业务意图，可跨多次 HTTP 重试
```

### 4. 防重复请求 Filter

现有 `[PreventDuplicateRequest]` 适合：

- 主数据保存；
- 普通按钮短时间防抖；
- 降低误点击压力。

不适合当作：

- 正式幂等；
- 分布式锁；
- 单据过账防并发；
- 多实例部署下的唯一保护。

正式单据如果已有可靠 CommandId，可以不用防抖 Filter，或仅把它作为体验补充。

## 返回结果应该怎样统一

项目已有 `ServiceResult<T>`，建议继续使用，但需要固定语义：

```
Success
Data
ErrorCode
Message
Field
CorrelationId（可以考虑由响应头提供）
```

错误码至少分为：

```
VALIDATION_ERROR
UNAUTHENTICATED
FORBIDDEN
NOT_FOUND
VERSION_CONFLICT
COMMAND_BUSY
COMMAND_CONFLICT
STATE_BLOCKED
BUSINESS_BLOCKED
OUTCOME_UNKNOWN
UNEXPECTED
```

其中：

- `VERSION_CONFLICT`：刷新单据；
- `COMMAND_BUSY`：使用原 CommandId 稍后重试；
- `COMMAND_CONFLICT`：当前 CommandId 已污染，不能换内容继续提交；
- `OUTCOME_UNKNOWN`：不要生成新 CommandId，应查询或使用原 ID 重试；
- `BUSINESS_BLOCKED`：业务条件不满足。

当前项目缺少的是统一的“错误码到 HTTP 状态”策略。不要让每个 Controller 自己写 try/catch。

## 还缺少什么

按优先级，我认为还缺以下能力。

### 第一优先级：统一命令执行与回执

这是当前最大缺口。

现在采购、仓库、入库、出库、PackingList 都在分别实现：

- 事务；
- 命令锁；
- 指纹；
- 回执；
- 重放；
- 日志；
- 异常转换。

继续发展会越来越难保持一致。

### 第一优先级：统一异常和 HTTP 状态

需要明确：

| 结果                   | 推荐 HTTP |
| ---------------------- | --------- |
| 参数验证失败           | 400       |
| 未认证                 | 401       |
| 无权限                 | 403       |
| 单据不存在             | 404       |
| Version/CommandId 冲突 | 409       |
| 防抖或频率限制         | 429       |
| 未知系统错误           | 500       |

即使前端最终主要读取 `ServiceResult`，HTTP 也不能所有情况都返回 200。

### 第一优先级：细粒度权限规范

每种复杂单据至少应区分：

```
Document.Read
Document.Create
Document.Edit
Document.Confirm
Document.CancelConfirmation
Document.Post
Document.Reverse
Document.Void
Document.Trace
```

不是每个模块都必须全部拥有，但不能只靠一个 `Module.Access` 覆盖所有危险操作。

### 第二优先级：统一请求验证入口

目前参数校验散落在服务方法里。

建议公共化的是验证执行机制，不是业务规则本身：

- 空值、长度、分页范围、Guid、decimal 精度可以统一；
- 状态能不能确认、库存够不够必须留在业务服务。

可以使用现有手写 Validator/Policy，不一定要引入新框架。

### 第二优先级：统一系统时钟

大量业务代码直接调用 `DateTime.Now`。

正式单据建议提供：

```
ISystemClock.Now
```

收益：

- 测试确认日、过账日、期间边界；
- 避免测试依赖机器时间；
- 未来统一时区策略。

### 第二优先级：请求日志与耗时监控

现有 Serilog 有异常和业务日志，但请求级耗时、状态码、慢请求还不够系统。

建议补充：

- 请求方法和路径；
- HTTP 状态；
- CorrelationId；
- 当前用户；
- 耗时；
- 慢请求告警；
- 禁止记录密码、Token 和完整敏感请求体。

### 后续再考虑：分布式防抖/限流

只有部署多实例或开放公网后才需要优先考虑：

- ASP.NET Core Rate Limiting；
- Redis 分布式缓存；
- 分布式命令锁。

当前单体 SQL Server 项目，可靠幂等最好仍以数据库唯一约束和事务为中心，不需要为了“先进”先引入 Redis。

### 当前不建议增加

- 消息总线；
- 通用工作流引擎；
- 全局 UnitOfWork 大框架；
- MediatR 只为减少 Controller 调用；
- 通用 `DocumentService<THeader,TLine>`；
- 所有请求都使用 Serializable；
- Repository 自己开启业务事务。

这些会让当前项目更复杂，而不是更清楚。

## 一个正常单据需要哪些 API

以普通“草稿—确认—过账—反向”单据为例，建议分四组。

### 查询

```
POST /search
GET  /{uid}
GET  /{uid}/trace
```

按页面需要可增加窄查询：

```
POST /sources/search
POST /items/search
GET  /{uid}/confirmation-context
```

### 草稿编辑

```
POST /drafts
PUT  /drafts/{uid}
POST /drafts/{uid}/delete
```

删除使用 POST 命令还是 DELETE，要看是否需要原因和复杂请求体。复杂业务删除用显式 POST 命令是可以接受的。

### 状态命令

```
POST /{uid}/confirm
POST /{uid}/cancel-confirmation-preview
POST /{uid}/cancel-confirmation
POST /{uid}/void-preview
POST /{uid}/void
```

### 库存类命令

```
POST /{uid}/post-preview
POST /{uid}/post
POST /{uid}/reverse-preview
POST /{uid}/reverse
```

Preview 只读，不预占资源；正式提交必须重新校验，不能相信 Preview 结果仍然有效。

## 一个正常单据怎么拆服务

建议按用例族拆，而不是按页面按钮一个类，也不是所有东西一个 ManagerService。

```
IDocumentQueryService
  SearchAsync
  GetDetailAsync
  GetTraceAsync

IDocumentSourceQueryService       // 有选源时才需要
  SearchSourcesAsync

IDocumentDraftService
  CreateAsync
  UpdateAsync
  DeleteAsync

IDocumentConfirmationService      // 有确认节点时才需要
  GetContextAsync
  ConfirmAsync
  PreviewCancelAsync
  CancelAsync

IDocumentPostingService           // 有正式过账时才需要
  PreviewPostAsync
  PostAsync

IDocumentReversalService          // 有复杂反向时才需要
  PreviewReverseAsync
  ReverseAsync
  VoidAsync
```

实际一个普通复杂单据通常是 **3～5 个 Application Service**：

- Query；
- Draft；
- Confirmation；
- Posting；
- Reversal。

没有确认或过账的单据不要机械创建空服务。

## 每个文件负责什么

### Controller

只负责：

- 路由；
- HTTP 方法；
- `[Authorize]`；
- 模型绑定；
- CancellationToken；
- 调用 Application Service；
- 返回结果。

不负责：

- 开事务；
- 判断状态；
- 读取 Repository；
- 生成单号；
- 写日志；
- 计算库存。

### Contracts API/DTO

只负责前后端协议：

- 请求；
- 响应；
- Refit 路由；
- 稳定错误码；
- 共享枚举。

不要直接暴露 Entity。

### Query Service

负责：

- 权限；
- 查询参数校验；
- 调用 Query Repository；
- 组装只读 DTO。

普通查询不应默认开启 Serializable 事务。

### Draft Service

负责：

- 创建、保存、删除草稿；
- 版本校验；
- 草稿可编辑状态；
- 头行整体保存；
- CommandId 幂等；
- 事务；
- 审计。

### Confirmation/Posting/Reversal Service

每个正式命令拥有自己的事务边界：

- 权限；
- 状态资格；
- 锁顺序；
- Version；
- CommandId；
- 下游事实；
- 日志；
- 回执。

### Policy/Validator

保存纯业务判断，例如：

```
RequireDraft
RequireConfirmed
RequirePostable
RequireReversible
ValidateQuantity
ValidateSource
```

它不访问 Controller，不开启事务。需要读取数据库事实的复杂校验，可以由 Service 先取事实，再交给 Policy 判断。

### Repository

负责：

- SQL；
- 锁定读取；
- 写 Entity；
- 返回 DTO；
- 传入当前事务。

不负责：

- 决定是否允许确认；
- 返回 `ServiceResult`；
- 开启跨仓储业务事务；
- 写 HTTP 错误。

## 最终建议

你可以把复杂单据的标准理解为：

```
公共 WebApi 管道
+ 8 个稳定公共能力
+ 每种单据 3～5 个用例服务
+ 每种单据自己的 Policy 和 Repository
```

当前项目不是公共服务太少，而是：

- 有些公共能力已经存在但没有统一使用；
- `BusinessOperationLog` 和命令回执职责混合；
- 入出库各复制了一套命令执行框架；
- 错误返回和事务策略不统一；
- Application Service 仍按“页面 Manager”聚合得太宽。

优先建设顺序应当是：

1. 统一错误码和 HTTP 映射；
2. 建立统一命令执行器与命令回执；
3. 明确审计日志不承担正式回执；
4. 拆分入库、出库、库存的 Application 接口；
5. 最后收口 Controller 和 Contracts 文件组织。

本次只做架构说明，没有修改任何文件或业务代码，也没有运行构建测试。
