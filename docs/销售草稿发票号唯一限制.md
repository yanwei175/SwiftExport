# 销售草稿发票号唯一限制

销售创建及更新草稿通过现有 `POST /api/sales-orders/detail/save` 保存。保存服务在命令事务内重查 InvoiceNo：所有未软删除销售订单均占用非空发票号，不限客户、确认或关闭状态；更新排除当前订单自身。已软删除订单释放该编号，空值不参与去重，不额外增加必填要求。

比较沿用销售导入编号口径，忽略首尾普通空格和大小写；数据库使用 `btrim` 与 `public.erp_dictionary_ci`。订单号及客户 PO 规则不变。原命令成功后的同 CommandId 重试仍重放回执，不被自身新增订单误判为重复。

重复返回 `VALIDATION`，字段为 `Header.InvoiceNo`，提示“发票号已被未删除的销售订单使用，请删除原来的草稿或修改发票号后重新保存。”如果原订单已确认或关闭，原有删除限制仍有效，此时应核实并修改新单的发票号。导入检查时确认已有订单提示不再能绕过保存查重。

保存前查询提供友好反馈，部分唯一索引 `ux_sales_order_header_invoice_no` 负责并发最终防线。仓储仅转换此索引的唯一冲突，其他数据库异常保持原分类，外层执行器回滚头、行和回执。

## 已有数据库升级

由管理员人工执行 [增量脚本](../SwiftExport.Infrastructure/Database/PostgreSQL销售发票号唯一限制.sql)。脚本先列出重复，再在维护事务中复查并创建索引，不自动清理历史数据。有重复时整个升级失败，需要管理员根据业务事实处理后重试。新库基线由实体元数据生成。

必须先完成索引升级再启用此规则的后端版本；仅部署代码只能完成查询查重，不能证明并发唯一性。生成脚本、构建及离线测试不代表业务库已部署或实库并发已验收。
