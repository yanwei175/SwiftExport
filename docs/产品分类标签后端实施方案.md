## V2 目标和实体

保留 ProductCategory 的实体、表及 DTO，不新增标签字段。ProductAttributeGroup 移除 CategoryId，编码按现有 erp_dictionary_ci 比较基线全局唯一。新增 ProductCategoryAttributeGroup : BaseEntity，仅保存 CategoryId、AttributeGroupId；有效关联对唯一，按组反查有索引，身份不可修改。Option、MasterSelection 身份和业务字段保持。

## V2 契约与保存

GET /api/ProductAttribute/definitions 返回全局组、值及 CategoryRelations，包含未关联组；GET /definitions/{categoryId} 返回继承后的有效组与来源。新 POST /definitions/batch-save 原子提交 GroupChanges、OptionChanges、CategoryChanges，并返回三类回执和完整快照。旧分类 POST 明确拒绝并提示升级。

新增组 ClientUid 可供值和分类关联同时引用。选项或关联变化的既有组同样提交组版本，组聚合版本每批推进一次；任何失败全回滚。值/组被产品引用时拒绝删除；未被产品选择的组原子删除其选项、直接关联及自身。解除关联、调整分类树按最终图检查，失去适用性的有效主型号数量大于零则拒绝；其他来源仍适用时允许。

## V2 并发与旁路

锁序为分类 Uid → 组 Uid → 主型号，保留其他父资料稳定顺序。选择取组共享锁，定义/关联修改取更新锁；纯定义不反向申请分类锁。分类路径锁后重验。分类单项和批量保存统一最终树校验，保留现有全树锁；分类删除检查直接关联。详情 null 保持、[] 清空、非空替换与同事务版本协议保持；列表、快速归类、导入允许全部已选仍适用的分类变更，否则拒绝。

读取登录可用；维护 Category.Edit；详情 Master.Edit，不新增权限键。

## 1. 业务场景与已确认边界

在现有产品分类树中创建“顶喷”，为该分类建立“安装方式”组，选项为“吸顶”“挂墙”；建立“尺寸”组，选项为“8寸”“10寸”。每组自行设置单选或多选，主型号选择这些预定义选项。关系归属于 `ProductMaster`，中性产品及 SKU 通过现有主型号关系查询，不复制选择值。

- 复用 `ProductCategory`；第一期按精确分类适用，不继承父分类定义。
- 分类标签组与选项只提供新增、修改、删除，不提供启用/禁用，不新增 `IsActive`、`IsEnabled`。
- 已被产品使用的组或选项阻止删除，并显示引用提示；未使用组可连同子选项删除。
- 主型号打标签在详情聚合保存中完成；主型号管理页只显示摘要，沿用现有 `OpenDetailCommand` 和“编辑”入口打开详情，不新增标签编辑命令或入口。
- 换分类由详情页确认清除旧标签，在同次保存中选择新分类选项；列表批量归类与导入不静默清空标签。
- 既有 `ProductType`、字符串 `ProductTag` 保留兼容；它们与新属性组没有既定耦合，不自动解析、迁移或写回摘要。
- 不建设自由文本/数字属性引擎、通用 `OwnerType`、SKU 覆盖、标签发布版本、跨客户端实时推送。

## 3. 实体设计

建议新模块目录使用 `Products/Attributes`；现有实体分层和命名风格在实施前再核对，独立实体不塞入 ProductMaster 或通用字典大类。三实体沿用 `BaseEntity` 的 Uid、Version、IsDeleted、审计字段；仅技术软删除，不做业务停用。

### 3.1 ProductAttributeGroup：分类下的选项组

| 字段 | 建议存储/语义 | 约束 |
| --- | --- | --- |
| CategoryId | uuid，所属分类 | 非空逻辑关系；建立后不改归属 |
| GroupCode | varchar(100)，组编码 | Trim、非空；分类内唯一；支持编码维护 |
| GroupName | varchar(200)，如“安装方式” | Trim、非空；展示名称可修改 |
| SelectionMode | integer，共享枚举 Single=0/Multiple=1 | 仅合法枚举；不混入第三种自由输入 |
| SortOrder | integer，显示顺序 | 默认 0；同序按 Uid 稳定排序 |

关联始终使用稳定 Uid，编码不承担展示名称或关联身份职责；支持编码修改，仍按有效唯一索引校验，不能通过更改分类转移整个组。多选改为单选时，检查所有有效主型号，同组已选多项则拒绝，并提示受影响产品；单选改多选允许。

### 3.2 ProductAttributeOption：组内选项

| 字段 | 建议存储/语义 | 约束 |
| --- | --- | --- |
| AttributeGroupId | uuid，所属组 | 非空逻辑关系；建立后不改归属 |
| OptionCode | varchar(100)，选项编码 | Trim、非空；组内唯一；支持编码维护 |
| OptionName | varchar(200)，如“吸顶” | Trim、非空；展示名称可修改 |
| SortOrder | integer，显示顺序 | 默认 0；同序按 Uid 稳定排序 |

“8寸”本期是受控选项名称，不额外拆出 numeric/unit 字段。对已引用选项改显示名称，会改变当前主数据展示；若实质含义改变，应新增选项而非把旧值改成另一含义。

### 3.3 ProductMasterAttributeSelection：主型号选中关系

| 字段 | 建议存储/语义 | 约束 |
| --- | --- | --- |
| ProductMasterId | uuid，主型号身份 | 非空逻辑关系；不使用 MasterSku 代替 |
| OptionId | uuid，选中选项 | 非空逻辑关系；经 Option→Group 得到分类 |

不重复保存 AttributeGroupId、CategoryId、组/选项名称、UI 勾选状态。单选组最多一条选择、多选组允许多条；允许不选，不增加全分类必填规则。所属分类、单选基数由应用用例校验，主型号版本承担整个选择集合的并发保护。

## 4. PostgreSQL 结构、索引及删除边界

建议表：`product_attribute_group`、`product_attribute_option`、`product_master_attribute_selection`，实际物理名称由项目元数据生成器确认。

| 表 | 主键/唯一键 | 查询索引与 CHECK |
| --- | --- | --- |
| group | Uid；有效 `(CategoryId, GroupCode)` 唯一 | 按 CategoryId/SortOrder 查询；GroupCode/GroupName 非空；SelectionMode 合法 |
| option | Uid；有效 `(AttributeGroupId, OptionCode)` 唯一 | 按 AttributeGroupId/SortOrder 查询；OptionCode/OptionName 非空 |
| selection | Uid；有效 `(ProductMasterId, OptionId)` 唯一 | 按 OptionId 反查引用；主型号方向复用唯一键前缀 |

有效唯一键过滤 `is_deleted = FALSE`，编码比较按现有 PG 大小写及尾部空格规范，不能仅靠客户端去重。软删除后创建新记录使用新 Uid；不公开通用恢复入口，不将已删除选项的新身份当作旧选项。逻辑关系沿用项目默认策略，不机械增加跨表物理 FK。

删除必须在事务及共同分类锁内完成：

1. 删除选项：检查有效主型号的有效选择。有引用则阻止整批删除，返回数量及有限主型号示例，不能假成功。
2. 删除组：任一子选项被引用则阻止；无引用时软删该组有效选项和组。回执明确哪些是请求项、哪些是组删除的关联效果，避免客户端重复接纳。
3. 删除主型号：与现有中性产品清理一起软删其选择关系，再删主型号，整批失败回滚。
4. 删除分类：分类下还有有效组时拒绝，提示先删除标签定义；不留下悬空组。未分类状态不是可维护标签的真实分类。
5. 批次中先取消选择或删除主型号后再删除定义的跨用例组合本期不提供；用户先完成产品修改，再删定义。单个定义批次按最终图验证，拒绝在已删除组下创建或移动选项。

## 5. DTO、Refit 与 API 契约

Contracts 保持 netstandard2.0 和传统 class/namespace 语法；不带 WPF 状态，不引用 Core Entity。结构复制走现有 Mapster 配置。

### 5.1 标签定义查询及维护

建议新增 `IProductAttributeApi`，由 Refit 注册设置 `/api/ProductAttribute` 基地址，接口内路径与 Controller 对齐。

| HTTP 路由 | 用途 | 返回/输入 |
| --- | --- | --- |
| GET `/api/ProductAttribute/definitions` | 会话基础资料缓存读取全部有效组与选项 | 单次一致的定义快照 DTO |
| GET `/api/ProductAttribute/definitions/{categoryId}` | 分类页读取某分类定义及当前版本 | 分类定义 DTO，含 Groups/Options |
| POST `/api/ProductAttribute/definitions/{categoryId}/batch-save` | 原子保存两张定义 DataGrid | 请求 GroupChanges/OptionChanges；返回两组标准逐行回执和提交后的定义快照 |

只读 Group/Option DTO 含 Uid/Version、归属、编码、名称、模式及排序。写 DTO 只包含允许修改的字段；归属以路由及服务已读记录为权威，不接受修改已有归属。新增组写 DTO 可带客户端逻辑 Uid，用于同批新增选项关联；它是临时身份，不视为已持久化。

定义 GET 返回没有选项的空组（`Options=[]`），不能把空组过滤掉。有效空分类或全部空定义也返回 `Success=true` 和空集合；无效/已删除目标分类、认证失败及实际查询异常仍返回对应失败，不能混淆成正常空结果。

维护请求复用 `BatchSaveRequestBase<TDto>` 的 GroupChanges、OptionChanges，以及 `CreateItemRequest/UpdateItemRequest/DeleteItemRequest` 的 ClientKey、RowIndex、Uid、Version。响应分别复用标准 `BatchSaveResponseBase/SaveItemResult`，保留客户端定位和新版本。

已落地的契约：`ProductAttributeDefinitionsDto.Groups` 包含 `ProductAttributeGroupDto.Options`；具体分类返回 CategoryId，全部快照使用 Guid.Empty。新增组的临时身份字段为 `ProductAttributeGroupWriteDto.ClientUid`。保存请求为 `SaveProductAttributeDefinitionsRequest`，响应为 `SaveProductAttributeDefinitionsResponse.GroupResults/OptionResults/Definitions`。版本使用每条组、选项的 BaseDto.Version，不新增分类发布版本。详情展示集合名为 `ProductMasterDetailDto.AttributeSelections`。

同批新增流程：验证临时组 Uid 不为空、不重复且不冒充现有组 → 创建组 → 建立临时 Uid 到真实 Uid 映射 → 改写新增选项 AttributeGroupId → 保存选项 → 返回映射可接纳的组回执及选项回执。服务不能把临时 Uid 当外键直接写入。任一步失败整批回滚，客户端保留草稿；失败响应不回报已回滚行是成功或计入成功数量。

### 5.2 主型号读写扩展与旧客户端兼容

- `ProductMasterDetailDto` 增加 `SelectedOptionIds` 和只读选择展示信息，读取时返回已保存的有效关系；缺失/失效异常关系可报告，不默默当作用户清空。
- `ProductMasterListItemDto` 增加 `TagSummary`，由组选项查询生成；不回写 ProductTag，不因联表关系扩大主型号分页行数。可先取得页内主型号，再批量读取选择，避免每行查询。
- `SaveProductMasterDetailRequest` 新增 `SelectedOptionIds`，默认 null，不初始化空列表。Contracts 虽不使用可空引用标注，运行时仍保留 null 语义。

| 保存请求的 SelectedOptionIds | 服务端含义 |
| --- | --- |
| 旧客户端省略 / null | 保留既有选择；新建主型号保持空选择 |
| `[]` | 明确清空全部选择 |
| 非空数组 | 替换最终集合，不是增量追加 |

规范化不能把 null 变成空数组。空 Guid、重复选项、已删除/不存在的选项、跨分类选择、单选组多项均拒绝。省略字段而改分类时，保留后的旧选择若不属于新分类则拒绝，不能清空。列表 BatchSave、AssignCategory、导入提交缺少选择编辑能力，存在不兼容旧标签时引导到详情处理。

详情保存原子顺序：验证父资料与定义 → 锁定并重读主型号 → 核对 ExpectedVersion → 计算最终分类与选择 → 保存主型号并递增版本 → 差量软删/新增选择 → 保存中性产品 → 按既有开关同步 Product → 返回提交后完整详情。只改标签也必须推进主型号版本；新增选择使用服务端生成的主型号 Uid。

### 5.3 权限

权限目录、过滤器及前端能力消费采用现有 RBAC；不硬编码角色，本期不增加权限键。

- 两个定义 GET 注册为 `AuthenticatedReadActions`，允许任意已登录用户读取基础资料；没有分类编辑权限仍可正常显示已有标签，未登录拒绝。
- 定义 POST 统一使用 `Products.Category.Edit`，覆盖组与选项的新增、修改、删除；只有查看权限不能通过 batch-save 写入。组/选项删除虽然是删除动作，此新用例仍采用已确认的分类编辑权限，不静默拆成新权限。
- 当前 SaveDetail 端点固定使用 `Products.Master.Edit`，本期沿用该实际权限；标签详情保存也需 Edit，不顺手改变详情创建时的权限行为。列表新增仍按其既有 `Products.Master.Create`，查看沿用现有读取边界；不新增独立选择写入口绕过主型号权限及版本。
- 不新增权限同步 SQL 或默认角色授权；确认现有 `Products.Category.Edit` 与 Master 权限已正确分配即可。认证读取入口与 POST 权限映射仍须做端点测试。

## 6. 仓储、事务与并发

新增独立属性仓储接口和 PG 实现，承担定义查询、批量保存、选择集合查询、引用计数及选择差量写入。不要让 ProductCategoryRepository 或 ProductMasterRepository 变成新模块的通用容器。为既有分类删除提供明确属性引用查询端口，业务一致性仍由 Application 持有。

应用服务沿用 ServiceBaseContext、IDbSession 及同 scope RepositoryBaseContext。Controller 仅调用用例，不写 SQL；仓储不开始/提交外层事务，不依赖 Application。保持取消、Version 冲突、唯一键及异常分类的项目既有语义。

### 6.1 最小共同锁顺序

复用现有“父资料先于主型号”的分类行锁，建立以下同一规则，不新增全局业务锁：

| 用例 | 共同父锁后续顺序 |
| --- | --- |
| 定义新增/修改/删除 | 分类按 Uid → 组按 Uid → 选项按 Uid；锁内检查引用/单选转换，不反向锁主型号 |
| 主型号选择保存 | 旧/新分类去重按 Uid → 既有父供应商/颜色 → 主型号 → 选择/中性产品 → 关联 Product |
| 列表归类/导入 | 先锁相关分类及既有父资料 → 主型号；重验版本及已有选择归属 |

旧分类需要先只读观察；拿齐父锁并锁主型号后，重新读取分类及版本。如果旧分类在期间改变，返回并发冲突，不能继续沿预读结果写入。定义维护也锁同一分类，因此选择校验期间定义不会被并发删除或改变模式，不额外建立独立锁表。实现时核对既有多父资料顺序，确保任何新入口都不在主型号锁后反向申请分类锁。

多选改单选、删除无引用选项都存在“检查后新增选择”的竞争，必须通过共同分类锁消除；单选不能仅靠两个选择关系行上的 Version 或 UI 限制。唯一 `(ProductMasterId, OptionId)` 只防重复选项，不能替代单选基数校验。
