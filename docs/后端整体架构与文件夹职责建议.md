# 后端整体架构与文件夹职责建议

本文结合通用后端能力地图、复杂单据链路和 SwiftExport 当前目录，提出一份按文件夹理解后端的总体建议。重点是能力归属和协作关系，不展开类、方法、表结构及算法设计。

**建议保留现有五个后端项目：第一层按技术职责分，第二层按公共能力或业务模块分，复杂模块内部再按真实用例分。** 文件夹是帮助理解和维护职责的工具，不会自动建立权限、事务隔离或项目依赖约束。

本文是讨论与实施规划依据，不表示目录已经调整，也不替代项目 Skill。后续按模块实施，每批切换完成后删除被替代的旧实现和旧文档，不长期保留两套入口。

## 1. 先从五个项目理解后端

```text
SwiftExport/
├─ SwiftExport.Contracts/        前后端共同遵守的协议
├─ SwiftExport.WebApi/           HTTP 入口和出口
├─ SwiftExport.Application/      业务用例及执行编排
├─ SwiftExport.Core/             业务实体和基础接口
├─ SwiftExport.Infrastructure/   数据库与外部资源的具体实现
├─ SwiftExport.Application.Tests/ 后端验证
└─ docs/                        架构说明和实施建议
```

| 项目 | 可以把它理解为 | 主要回答的问题 |
|---|---|---|
| Contracts | 协议说明书 | 前端提交什么，后端返回什么？ |
| WebApi | 接待与传输边界 | 请求交给谁，身份如何验证，结果如何返回？ |
| Application | 业务执行部门 | 这个操作能不能做，需要协调哪些步骤？ |
| Core | 业务事实和接口定义 | 系统管理什么对象，需要哪些持久化能力？ |
| Infrastructure | 技术执行部门 | SQL 怎样执行，数据怎样保存，外部资源怎样访问？ |

请求通常经过 WebApi → Application → Repository 实现 → 数据库，结果沿原路返回。Contracts 定义传输协议，Core 提供实体与接口；它们不是额外的请求转发层。

当前源码中 Application 直接引用 Infrastructure，并通过 ServiceBaseContext 使用 DbSession。本文按这个事实规划目录，不把它描述成已经实现了完全反向依赖的纯领域架构；是否进一步调整项目引用应另立明确任务。

## 2. 目录同时表达两种职责

### 横向：公共机制

身份、错误、事务、命令幂等、追踪、审计等机制可以被多个业务模块复用，但分布在各自所属技术层，不集中到一个万能 CommonServices。

### 纵向：业务模块

产品、客户、供应商、销售、需求、采购、库存、出货、售后等模块，在多个技术层都有对应目录。处理采购时，沿各项目的 Procurement 找到协议、入口、用例、实体和 SQL。

```text
                   公共机制                 采购模块             库存模块
Contracts          Wrappers / Errors       Procurement          Inventory
WebApi             Middlewares / Responses Controllers/Procurement Controllers/Inventory
Application        Services/Execution      Services/Procurement Services/Inventory
Core               基础接口                 Entities/Procurement Entities/Inventory
Infrastructure     Data / 执行持久化         Repositories/Procurement Repositories/Inventory
```

这张表是职责索引，不要求各层拥有完全一样的目录，也不要求一个模块对应一个服务。

## 3. WebApi：请求怎样进入和离开

以下是建议职责树；Responses 是拟议的统一出口位置，其余主要沿用现有目录。

```text
SwiftExport.WebApi/
├─ Controllers/             按业务模块组织 HTTP 接口
│  ├─ Products/
│  ├─ Procurement/
│  ├─ Inventory/
│  └─ ...
├─ Middlewares/             请求追踪、异常兜底、开发环境辅助
├─ Filters/                 端点级处理，例如可选防抖
├─ Services/
│  └─ Auth/                 HTTP 身份与 Token 等适配能力
├─ Responses/               建议：统一结果、HTTP 状态和错误出口
└─ Program.cs               注册依赖并组合请求管道
```

这里负责路由、模型绑定、HTTP 认证授权、序列化及响应。Controller 将请求交给 Application，不自己计算库存、写 SQL 或控制跨仓储事务。

认证中间件和授权能力可直接使用框架，不需要为每个能力另建自定义中间件。业务细权限和数据可见范围仍由用例负责。防抖是 Filter，不能替代正式命令的幂等机制。

统一出口需要覆盖业务结果、未处理异常、模型验证和认证拒绝，并同步验证客户端读取方式；不是只把某个中间件的 HTTP 200 改成 500。

## 4. Application：公共执行机制与业务用例分开

建议保留 Interfaces、Services、Contexts、Mappings、Models 的基本结构，让接口与实现按相同能力名称对应。

```text
SwiftExport.Application/
├─ Contexts/                现有服务上下文，不扩成万能依赖容器
├─ Interfaces/              应用服务和执行能力的接口
│  ├─ Execution/            按实际需要声明公共执行接口
│  ├─ Procurement/
│  ├─ Inventory/
│  └─ ...
├─ Services/
│  ├─ Auth/                 认证用例、权限判断
│  ├─ Base/                 现有标准 CRUD 基础能力
│  ├─ Execution/            建议：公共命令、事务和结果处理机制
│  ├─ Systems/              系统基础资料及单号等系统能力
│  ├─ Products/             产品与 BOM 用例
│  ├─ Customers/            客户用例
│  ├─ Suppliers/            供应商用例
│  ├─ Orders/               销售订单用例
│  ├─ DemandPlanning/       来源需求、物料需求及交接
│  ├─ Procurement/          采购与供应商进度
│  ├─ Inventory/            仓库、库存、入库、出库
│  ├─ Shipping/             PackingList、交付与追溯
│  └─ QualityControl/       品控与售后
├─ Mappings/                DTO 与应用模型、实体的映射
└─ Models/                  应用层内部模型
```

Execution 负责“怎样安全执行”，业务模块负责“业务上能否执行”。前者可收敛事务生命周期、幂等回执流程和错误包装；后者保留状态、数量、资格、权限要求、指纹输入和业务锁集合。

普通查询不因为使用公共执行边界就开启写事务。内部业务端口加入外层事务时，也不能另行提交。不要将 Execution 再拆成大量空接口，先用真实消费者证明复用价值。

现有 SystemServices 与 Systems、部分根目录接口和分散辅助类，需按实际职责归位。名称相近只是盘点信号，不代表可以直接批量合并。

## 5. Core：业务事实与能力接口

```text
SwiftExport.Core/
├─ Entities/
│  ├─ Products/             产品和 BOM 事实
│  ├─ Procurement/          采购事实
│  ├─ Inventory/            库存、入库、出库事实
│  ├─ Shipping/             出货及执行证据
│  ├─ Auditing/             业务审计事实
│  └─ ...
├─ Interfaces/
│  ├─ Auth/                 当前用户等基础接口
│  ├─ Auditing/             审计与追踪相关接口
│  ├─ Procurement/          采购持久化接口
│  ├─ Inventory/            库存持久化接口
│  └─ ...
├─ Common/                  稳定基础类型
├─ Models/                  Core 内部模型
└─ DatabaseSchema/          现有实体元数据及数据库约束声明
```

Core 不放 Controller、HTTP 状态、WPF 状态或具体 SQL 实现。前后端传输模型放 Contracts，实体不直接充当 API 返回模型。

未来若确定通用回执模型，再增加相应的实体与仓储接口位置。本文不预先创建通用回执表，也不把 PackingList 执行证据等领域事实改名搬走。

## 6. Infrastructure：把技术动作做完

```text
SwiftExport.Infrastructure/
├─ Data/                    连接与 DbSession
├─ Contexts/                仓储共享上下文
├─ Repositories/
│  ├─ Base/                 通用 Dapper 与元数据能力
│  ├─ Auditing/             审计持久化
│  ├─ Execution/            按回执方案需要：命令锁、公共回执持久化
│  ├─ Products/
│  ├─ Procurement/
│  ├─ Inventory/
│  ├─ Shipping/
│  └─ ...
├─ Services/                已有审计打戳等技术实现
├─ Database/                数据库脚本与生成结果
├─ DatabaseSchema/          数据库结构处理工具
├─ Migrations/              结构与数据变更脚本
└─ DependencyInjection.cs   技术实现注册
```

Repository 执行 SQL，并加入调用方事务；它不决定整条采购、入库或出货流程。数据库约束、参数化 SQL 和锁实现也在这一层落实。

缓存、文件存储、邮件、外部 API、任务和消息适配，有需求时在本层建立职责明确的目录，不提前生成所有文件夹。跨外部系统的副作用也不能假定由本地数据库事务一起回滚。

Database、DatabaseSchema、Migrations 的现有边界需单独核对，不能仅凭名称相似删除或合并生成工具与部署脚本。

## 7. Contracts：前后端的共同语言

```text
SwiftExport.Contracts/
├─ Apis/                    按模块组织 Refit API
│  ├─ Products/
│  ├─ Procurement/
│  ├─ Inventory/
│  └─ ...
├─ DTOs/                    按模块与真实用例组织请求、响应
│  ├─ Errors/               稳定错误契约
│  ├─ Products/
│  ├─ Procurement/
│  ├─ Inventory/
│  └─ ...
├─ Wrappers/                结果、分页、批量传输包装
├─ SysEnums/                共享业务枚举
└─ Common/                  前后端均需要的纯工具
```

这是目标命名示意：当前仍有 ProductApis、CustomerApis、SystemDtos 等命名。各模块实施时统一所属目录，并迁移真实消费者，不为美观先全仓改命名。

Contracts 不依赖数据库连接、HTTP 服务端上下文或业务执行服务。当前仍承担其他客户端共享内容，不能因本图只展示后端协议就直接删除未列出的目录。

## 8. 一个业务模块怎样贯穿文件夹

以入库为例，只展示职责位置，不要求生成全部子目录：

```text
Contracts/Apis/Inventory/Inbounds/           前端可以调用哪些入库 API
Contracts/DTOs/Inventory/Inbounds/           Query、Sources、Draft、Posting、Reversal 请求和响应；根目录保留共享阻断项与错误码
WebApi/Controllers/Inventory/Inbounds/     Query、Sources、Draft、Posting、Reversal 五个 Controller
Application/Interfaces/Inventory/Inbounds/  入库查询、选源、草稿、过账、反向接口
Application/Services/Inventory/Inbounds/    入库五类用例实现及验证器
Core/Entities/Inventory/                    入库事实
Core/Interfaces/Inventory/                  入库持久化接口
Infrastructure/Repositories/Inventory/      入库 SQL 实现
Application.Tests/Inventory/                入库验证
```

业务复杂时，模块内部可按 Query、Source、Draft、Confirmation、Posting、Reversal、Trace 分工；规模较小时，直接使用职责清楚的文件名即可，不机械再建七层目录。

各层拆分粒度可以不同：当前入库五个 Controller 分别对应五个用例服务。其他模块可按实际职责选择粒度。不得将必须原子执行的步骤拆成前端多次调用，也不得只切 partial 文件便宣称完成职责拆分。

库存过账虽然被入库、出库、PackingList 共用，仍属于 Inventory；来源接收属于 DemandPlanning，BOM 读取属于 Products。**被多个模块使用，不等于失去领域归属。**

## 9. 现有目录如何对照建议

| 当前观察 | 建议方向 |
|---|---|
| 已有五层项目、DbSession、上下文、权限、单号和审计打戳 | 保留并统一使用，避免重建一套基础设施 |
| 公共执行器和回执已位于 Application/Commands，部分模块仍有旧编排 | 按模块迁移剩余命令，不复制执行器 |
| 统一错误与 HTTP 出口已落地 | 继续保持 Contracts、WebApi 与客户端契约联验 |
| 审计日志和命令回执职责混用 | 分清职责，确定回执方案后转换历史结果并删除旧重放代码 |
| Inventory 内同时存在仓库、库存查询、入库、出库与过账 | 按业务能力分组，保留库存领域内公共端口 |
| 采购等模块存在宽接口和多个相关入口 | 先列用例及消费者，再决定合并或拆分，不凭名字删除 |
| Systems/SystemServices、SystemRepositories/Systems 等并存 | 按职责收口命名，跟随模块实施完成调用方迁移 |
| DTO/API 目录命名与业务层不完全一致 | 逐模块建立对应关系并统一，不额外制造一套过渡命名 |

## 10. 建议怎样推进

### 第一批：公共边界

统一错误契约、HTTP 出口、客户端读取及公共命令机制已完成第一批接入。入库草稿、正式过账、人工整单反向及出库草稿已使用公共执行器；入库五类用例已拆为窄服务。目前没有业务库，入库按新空库推进；真实 SQL 原子性仍待隔离数据库验证。后续按模块核对回执、审计及事务协议后继续迁移。

### 第二批：第一个完整业务模块

选择基础物料作为完整目录整理的起点，先盘点 Product 主档及直接消费者；BOM 按独立能力分析。明确当前模块的协议、入口、用例、实体、仓储和测试位置，完成后作为可读示例。

### 后续：按依赖逐模块完成

逐步处理仓库与库存、入库、出库、采购、PackingList，再安排销售、需求、售后等模块。跨域依赖需要时调整顺序，不并行切开必须共享事务的链路。

每批交付必须做到：调用方已经切换，旧实现和 DI 注册已清除，文档原位重写，相关构建与测试通过。有效业务历史、审计和重试结果应保留或转换，不随旧代码一起删除。

## 11. 建议结论

本项目适合继续采用“分层项目 + 层内模块目录”的结构，先收敛公共机制，再整理模块内部用例。暂不新增万能公共项目，不把后端拆成微服务，不一次性移动所有文件。

判断目录是否清楚，只需要检验三件事：找一个业务是否能沿同名模块找到完整链路；找一个公共机制是否只有明确的负责人；修改一个用例是否不必理解无关模块。
