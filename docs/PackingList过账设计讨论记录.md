# PackingList 过账设计讨论记录

## 第一项：Picker 准入（已实现）

- 普通来源仍需活动 NetDemand 和未释放 DemandExecutionLink（AllocatedQty > ReleasedQty）。
- 当前售后均为供应商免费补做、直接发客户；以 GrossDemand.SourceType = ComplaintReplenishment（CR）识别，免物料需求、采购及 Link 前置条件。
- 两类来源共同要求有效、属于当前客户、待交付数量大于零。非标继续允许，不新增标准产品限制。
- 待交付数量为来源数量减有效已过账 PackingList 行数量；按 GrossDemandId 汇总，同来源可分批出现在多个箱单。草稿不计数，反过账退出有效交付。
- 前端继续扣除当前草稿有效行已选数量，扣完后不再可选。分页总数为服务端结果，本页可选数为前端扣除后的结果。
- 保留只读多选、批量关键词搜索、ImagePath；数量在草稿详情调整。后端准入在统计和分页前执行，不新增 API 或修改布局。

## 第二项：过账总线与来源解析（已确定，待实现）

- PackingList Application Service 持有唯一事务；入库、出库内部服务及仓储共用同一 DbSession，不自行提交，不通过 HTTP 自调用。
- 先解析并校验来源和库存，再生成必要成品入库单、余额增加和流水，随后生成成品发货及客供件耗用出库单、余额扣减和流水，最后保存箱单过账状态、关联事实和日志，一次提交。任一步失败全部回滚。
- 同连接同事务内，出库可以读取并扣减此前自动入库增加的库存，不需要先提交。PackingList 不直接写其他模块库存流水，由入出库内部服务调用统一库存内核。
- 按 GrossDemandId 汇总本次有效箱单行数量，保留物理行身份；拆尾箱不能重复计算客供件。售后直发与非标无库存行分流，只参与交付校验。
- 普通库存行查活动、未删除的当前拆解需求，校验唯一根、根子归属及拆解批次；不任意挑选历史或多个根。根需求对应出货产品，客供件根据 ParentNetDemandId、RootNetDemandId、DeliveryTargetNetDemandId 和 DeliveryMode 识别，不重读当前 BOM。
- 成品根需求沿有效 DemandExecutionLink 查采购目标行，核对目标头行和产品。首版只支持采购执行目标。多 Link 全部保留贡献，相同采购行去重读取，不能重复计算收货容量或任取第一条。
- 箱单决定本次出货量，需求快照提供客供件数量依据；Link 的 AllocatedQty − ReleasedQty 是有效执行贡献，不等于本次入库或耗用量。
- 客供件按产品实际可用库存耗用，不按采购单分配或限制消耗；库存足够时不要求自身采购 Link 存在，关联采购仅用于可选追溯。供应商自主使用现有材料，不能因缺对应采购单或对应采购行未收货而阻断。
- 客供件允许跨有效可出库仓分配；最终记录每个实际扣减仓和数量，不只扣一个全局合计。不得自动补入客供件库存或产生负库存。
- Repository 批量读取事实，PackingList 服务负责解析规则；本阶段无需新增公共 API、通用框架或来源分摊表。后续是否需保存执行计算依据，在持久化设计时单独确定。

## 第三项：成品库存与自动入库数量（已确定，待实现）

- 成品允许使用同产品现有库存，不按来源需求或采购单划分库存归属；关联采购行只约束新增自动入库的依据和剩余可收容量。
- 先分配本次可使用的同产品现有库存，未覆盖的发货数量才生成自动入库；不能因为采购行已有入库记录就认定全部入库，也不能重复入库采购总量。
- 同箱单多来源使用同一产品库存时，共享一份可用余额，不能各自重复计算；同一采购行被多条 Link 引用时，共享一份剩余可收容量。
- 库存余额与采购累计净收货是不同事实：前者决定当前可用量，后者约束还能新增入库多少。不得通过额外入库突破采购剩余容量。

## 第四项：仓库分配（已确定，待实现）

- 成品自动入库进入对应采购供应商的有效虚拟仓，随后从该仓出库；找不到唯一有效供应商仓时提示配置问题，不自动创建或任意选仓。
- 使用现有成品库存优先关联采购供应商仓，不足再使用其他有效可出库仓的同产品库存。
- 客供件也优先关联成品供应商仓，不足跨仓扣减；供应商关系只作优先级，不是库存使用限制。
- 同优先级多个仓按仓库编码、Uid 固定顺序分配，允许分仓满足数量，保存实际扣减仓及数量。该分配顺序不替代事务内统一锁序。
- 无需每次手动选仓，ShippingLocationSnapshot 不参与库存判断。

## 第五项：多采购行自动入库分配（已确定，待实现）

- 候选仅限本来源成品需求通过有效 Link 关联、且允许收货的采购行；按采购单号、行号、Uid 固定顺序补足自动入库缺口，不新增人工分配页面。
- Link 只证明关联资格，不建立独立 Link 收货额度；采购行剩余可收量复用入库模块口径，包含有效手动／自动入库及反向结果。
- 同一采购行被多个来源或 Link 引用时，共享一份剩余可收容量。来源待交付量控制不超发，采购剩余可收量控制不超收。
- 分配结果分别进入对应供应商仓并出库；全部候选容量不足时提示缺口，整单阻断。

## 第六项：客供件耗用数量与扣减（已确定，待实现）

- 入库仍关联采购行，用于采购已收、未收及入库单追溯；出库不按采购行、采购日期或入库批次分摊，不新增采购批次剩余库存账。
- 本次应耗 = 本次成品出货数量 × 客供件拆解数量快照 ÷ 成品根需求拆解数量快照。采用 NetDemand.GrossQty 的根子数量比例，不读取当前 BOM、采购数量或仓库余额决定应耗量；根数量必须大于零。
- 同 GrossDemand 的箱单物理行先合计出货数量，再分别计算各客供件需求应耗；保留来源计算依据，相同产品和单位汇总后分仓扣减。
- 本次计算按四位小数、AwayFromZero 舍入；采用简单逐批计算，不采用累计应耗减历史已耗，也不在最后一批补偿累计尾差。历史实际耗用仍需保存用于追溯和准确反向。
- 成品使用现有库存或本次自动入库，均以本次箱单出货量计算耗用；本流程以 PackingList 正式过账为客供件扣账时点，不在成品入库时重复扣料。
- 按第四项仓库优先级依次扣减，前仓不足再扣下一仓，不均摊；足够即停止，不按采购单限制材料使用。总可用库存不足整单阻断，不自动补入客供件。

## 第七项：过账预览与最小阻断（已确定，待实现）

- 点击过账先展示只读预览，用户确认后才正式执行。展示成品自动入库的产品、采购单、仓库及数量，成品出库与客供件耗用的产品、实际扣减仓及数量，以及售后／非标只登记交付的说明。
- 预览不生成单据、不预占资源，不提供手工数量或仓库分配；正式执行在同一事务中重读、重算并验证预览仍有效。
- 必要阻断：箱单状态或版本不允许；来源失效、跨客户或超交付；必要需求、产品、单位或数量依据异常；成品缺口无法由关联采购剩余可收容量覆盖；需要自动入库却无法唯一确定供应商仓；客供件库存不足；确认时影响预览的数据已变化。
- 已有成品库存足够时，不因某条采购不能新增收货而阻断；客供件不检查对应采购是否收过货。无关采购问题不得升级为整单阻断。

## 第八项：执行记录、整单反向与历史纠错（方向已确定，待实现）

- 保存箱单过账时间、操作人、命令标识，以及生成入出库单据的关联；自动单据保留 TriggerPackingListId。保存客供件采用的来源、根子需求数量快照、本次出货及实际耗用依据并关联出库明细，不建立采购批次库存账。
- 普通反过账表示整张交付记录撤销：按原记录先反向成品出库和客供件耗用，再反向本箱单生成的自动入库，最后更新箱单状态；全部同事务完成。不重新读取当前 BOM 计算，不撤销历史手工入库，不删除原单及流水。
- 自动单据在入出库工作台可查看，不允许独立修改或反过账。重复命令返回原结果，不重复执行。普通已反过账箱单不再次过账，需要重新发货时另建草稿。
- 实际发 A、箱单误记 B，即使数月后才发现，也属于历史录单纠错，不是新发货或客户退货。采用受控过账纠错：指定错误行，录入实际产品、来源、数量及原因，预览撤销错误记录和登记正确记录的影响，在一个事务内完成，保留原始记录及纠错关联。
- 纠错按原实际执行依据撤销，只处理错误行相关事实；不能把全部 B 入库机械替换为 A，更不能撤销真实 B 手工入库。A 的补记入库仍需正确依据，来源交付、入出库和客供件耗用需一致修正。
- 历史纠错可在专用权限、原因及明确确认下允许负库存，并真实保存负余额、反向／更正流水和待处理差异；不得跳过库存写入或强制归零。该例外不自动放开普通正式过账的库存不足、采购超收等限制。
- 原单据或流水缺失、关联损坏、无法确定撤销对象仍阻断，不能以业务放行为由猜测。普通反过账是否也开放负库存例外，尚未单独确认；不得默认为普通用户可放行。
- 合法来源的 B 被误选时，库存检查无法证明现场实际装的是 A；过账预览应突出图片、客户型号、SKU、来源单号和数量供核对。本阶段不新增扫码或第二人审批。

下一项待讨论：纠错在首版的交付范围、单据修订呈现、权限与待处理差异的落点，以及执行记录和接口的具体设计。尚未确定的细节不作为已实现能力。

## 第一阶段实施进度

已加入自动入出库内部 Port、同事务资源准备、正常反向、专用单据持久化、幂等结果和采购净收货反向兼容分支。接口及调用示例见 [自动入出库内部接口交接](PackingList自动入出库内部接口交接.md)。

当前已通过内存仓储配合真实库存内核的行为测试；真实 SQL Server 集成测试默认关闭，尚未执行数据库验收。PackingList 过账入口、来源解析和分配仍属于第二阶段，历史纠错属于第三阶段。三阶段全部纳入最终交付，第一阶段不能代表箱单已可过账。

## 边界与后续

Picker 准入不操作库存；第一阶段只提供自动入出库内部执行能力，不接箱单过账、纠错或工单。供应商直发售后只记交付、不记库存的正式接线仍为第二阶段目标。

旧能力地图中统一准入及所有标准品必须有采购依据的描述，不适用于本次确定的售后例外。其余过账细节继续逐项讨论。

验收关注售后免执行关系、普通来源保留限制、共同客户与余额条件、非标、分页前过滤、交付投影、关键词参数化及图片字段；无数据库单元测试不替代真实数据库验收。
