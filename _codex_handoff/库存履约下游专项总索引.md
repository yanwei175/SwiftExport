## 4. 已冻结的业务决策

- 公司当前没有需要在系统内管理的自有实体仓库；库存地点以各供应商的虚拟仓为主。
- 每个供应商首期最多一个活动虚拟仓，供应商和仓库关系以 Uid 为权威，编码只用于人工查账和历史快照。
- 客供件到达父件生产供应商后，由跟单人员手工建立正式入库单，收进该供应商虚拟仓。
- 供应商“已备好数量”来自跟单人员根据供应商反馈手工登记，不等于库存，不得直接增加库存余额。
- PackingList 表示最终客户装柜/发货。执行“提交并过账”后，系统按需要生成正式入库单、正式出库单和库存流水。
- 最终客户已发货数量以已过账的最终客户出库事实为准，不以 PackingList 草稿数量或采购单字段为准。
- 已手工入库的成品直接出库；尚未入库但本次确定装柜的成品，由 PackingList 自动补正式入库后再出库。
- 客供件在父件成品发货时，按净需求拆解快照比例从父件执行供应商的虚拟仓扣减。
- 正常出库不允许负库存。特殊业务必须使用专门的“允许负库存异常出库”流水类型、特殊权限、强提示和必填原因。
- 所有库存变化都必须来自正式入库/出库/反向单据，并生成不可变库存流水；禁止直接编辑库存余额。
- 库存流水产生后不靠删除或普通更新纠错，必须反过账或红冲。
- Serilog 继续负责技术诊断；另建持久化业务操作日志。库存流水是领域账本，不等同于业务操作日志。

## 5. 统一业务主线

```text
净需求 NetDemand
  -> 活动计划 NetDemandAllocation
  -> 采购草稿/采购单行
  -> DemandExecutionLink（需求到采购执行的数量关系）
  -> 跟单反馈“供应商已备好数量”（非库存）
  -> 手工入库或 PackingList 自动入库
  -> Supplier Virtual Warehouse 库存余额 + 不可变流水
  -> PackingList 提交并过账
  -> 最终客户出库 + 客供件耗用出库
  -> 销售订单/毛需求/净需求/采购/库存全链路 Trace
```

## 6. 统一数据模型边界

| 概念 | 权威事实 | 禁止做法 |
|---|---|---|
| 供应商虚拟仓 | `WarehouseSite.SupplierId` | 用 SupplierCode 充当逻辑主键 |
| 当前库存 | `InventoryBalance` | 页面或服务直接写 OnHandQty |
| 库存历史 | `InventoryLedgerEntry` | 更新或删除历史流水 |
| 入库事实 | 已过账 `InboundDocument/Line` | 只改采购行 ReceivedQty |
| 出库事实 | 已过账 `OutboundDocument/Line` | 只改 PackingList 的 ShippedQty |
| 需求执行 | `DemandExecutionLink` + 单据行来源关系 | 恢复旧 DependentDemand.Target 字段为权威 |
| 供应商已备好 | 跟单反馈记录 | 当作已入库或可用库存 |
| 技术错误 | Serilog | 用业务日志替代异常堆栈 |
| 业务审计 | `BusinessOperationLog` | 从文本文件推断谁做了什么业务动作 |

## 7. 统一状态规则

所有单据使用分层状态，不再建立万能 `OrderStatus`：

- `LifecycleStatus`：`Active=0, Closed=8, Voided=9`。
- `PostingStatus`：`Unposted=0, Posted=1, Reversed=8`。
- “草稿”计算规则：`Active + Unposted`。
- 已过账单据不可普通编辑、软删或作废。
- 反过账必须提交 `ExpectedVersion`、`CommandId` 和原因。
- 页面展示状态由上述事实计算，不新增重复持久状态。

Contracts 的持久枚举值一经迁移冻结，不得随意重排。

## 8. 统一技术原则

- 新 Core 类型采用 `WarehouseSite`、`InventoryBalance`、`InventoryLedgerEntry`、`InboundDocument`、`OutboundDocument`、`PackingListDocument` 等新语义名称，禁止复活已清理旧类型。
- Contracts 保持 `netstandard2.0`：普通 `class`、块级 namespace、`get/set`，不使用 `record/init/required/nullable reference`。
- Controller 只处理 HTTP 边界；Application 编排业务事务；Infrastructure 使用 Dapper 和当前 `DbSession.Transaction`。
- 库存过账由一个共享 `IInventoryPostingService` 编排，入库、出库和 PackingList 不得各自复制余额更新 SQL。
- 库存键按绝对 Uid 排序加锁，避免多 SKU、多仓库过账死锁。
- 头行关系允许评估强 FK；跨需求、采购、仓库、客户关系默认逻辑外键加索引，由 Application 校验。
- Query DTO 可以扁平化实时名称；单据成立时的编码、名称、SKU、单位等必须保存快照。
- 每个业务命令携带 `CommandId`，每个写入实体携带 `ExpectedVersion`，重试必须幂等。

## 9. 数据库策略：现有表优先

- 保留并优先复用现有 `Warehouse`、`Inventory`、`InventoryTransaction`、`PurchaseOrder*`、`FollowUpLog`、`PurchaseReceive*`、`Outbound*`、`PackingList*` 物理表和 003–008 迁移历史。
- “不恢复旧 C# 链路”不等于“放弃旧物理表”：Core/Application 使用新的专用业务语义，Infrastructure 通过 `[Table]` 或显式 SQL 映射现有表。
- 现有列能表达的事实直接复用；只有 Uid 关系、分层状态、来源追溯、并发、幂等或反向关系缺失时才 `ALTER TABLE ADD`。
- 默认不新建同义头表、行表、余额表或流水表，避免双表双写。唯一已确认没有合适旧表的是 `BusinessOperationLog`；它允许新建一张追加式表。
- `FollowUpLog` 通过扩字段承载追加式供应商进度报告，不另建 `SupplierProgressReport` 物理表。
- `PackingListLine` 首期一条物理行对应一个需求贡献；WPF/导出层可以按产品视觉汇总，因此不新建 Contribution 关系表。
- 新专项从 009 起使用最小增量扩字段脚本；不得修改已经执行过的迁移文件。
- 禁止自动猜测供应商编码、SKU 或旧整型 Id 到新 Uid 的关系。能证明的记录才回填，不能证明的保持空值并排除在新写命令之外。
- 遗留库存非零时，必须先输出异常清单并由用户确认，不能直接把旧余额推定为可信新余额。
- 新功能启用前必须有完整备份、恢复演练和 postflight；共享库/生产迁移需单独授权。

### 物理表复用矩阵

| 新 C# 业务语义 | 复用物理表 | 迁移原则 |
|---|---|---|
| WarehouseSite | `Warehouse` | 增加 SupplierId/状态等必要字段 |
| InventoryBalance | `Inventory` | 增加 WarehouseId/ProductId/Version 等权威关系 |
| InventoryLedgerEntry | `InventoryTransaction` | 增加交易枚举、来源 Uid、幂等和反向字段 |
| PurchaseDocument | `PurchaseOrderHead/Line` | 继续使用 006–008 已扩字段，只补确认/关闭缺口 |
| SupplierProgressReport | `FollowUpLog` | 保留 NoteContent，追加安排/备妥/序号/幂等字段 |
| InboundDocument | `PurchaseReceiveHead/Line` | 补状态、WarehouseId、来源 Uid 和反向字段 |
| OutboundDocument | `OutboundHead/Line` | 补状态、ProductId、来源 Uid、异常放行和反向字段 |
| PackingListDocument/Contribution | `PackingListHead/Line` | 一行一来源贡献，补需求/仓库/幂等字段 |
| BusinessOperationLog | 新表 | 唯一确认需要新增的物理表 |

## 10. 实施顺序

### Phase 1：采购与供应商跟单（下一步优先）

- 直接承接已经可用的净需求采购草稿，完成采购查询、确认/取消确认和供应商进度反馈。
- 主要复用 `PurchaseOrderHead/Line` 和 `FollowUpLog`，数据库变化最小，且能最快提供“已安排、未安排、已备好”数据。
- 同步建立最小 `CorrelationId` 和 `BusinessOperationLog` 写入基座；完整日志查询工作台可后补。

### Phase 2：供应商虚拟仓与库存内核

- 建立仓库主数据、库存余额、库存流水和统一过账服务。
- 完成余额锁、流水幂等、期初余额、库存查询和 Trace。

### Phase 3：入库

- 实现采购入库、客供件手工入库、PackingList 自动入库及反过账。

### Phase 4：出库

- 实现最终客户出库、客供件耗用出库、负库存异常授权及反过账。

### Phase 5：PackingList

- 实现多销售来源装箱、过账预览、自动入库/出库、客供件耗用和全链路回退。

PackingList 不得先于库存、入库和出库内核单独实现。

### Phase 6：日志查询与治理完善

- 完成业务日志全局查询、模块 Trace 跳转、XLSX 导出和敏感字段治理。

## 11. 推荐的单模块实现流程

为控制数据库分析和迁移成本，每个模块固定按以下顺序实施：

1. **源码兼容审计**：只读迁移脚本、旧实体历史和当前仓储 SQL，列出现有字段；默认不连接数据库。
2. **字段缺口表**：逐项标记“直接复用、业务编码快照、新增 Uid、新增状态、新增幂等/反向”，没有明确调用方的字段不加。
3. **C# 先行**：先冻结 Contracts、Application 命令、专用 Repository 接口和显式 SQL；不恢复旧通用服务。
4. **单一最小 SQL**：每模块只交付一份可重复执行的 `ALTER TABLE ADD`/索引脚本和少量示例数据，不生成另一套同义表。
5. **用户执行数据库**：共享库由用户确认并执行；Codex 根据执行结果修正兼容问题，不反复全库评估。
6. **后端纵向闭环**：Repository -> Application -> Controller -> Refit，先通过单元/静态契约测试。
7. **WPF 接入**：后端契约稳定后再做导航、查询、命令、Trace 和导出。
8. **阶段门禁**：构建、对应测试、`git diff --check`、旧 C# 链路扫描；不要求每个小改动都启动数据库集成环境。

### 下一步采购最小可交付切片

1. 复用现有采购草稿 Search/Detail/Trace，补采购确认与取消确认。
2. 将新 `SupplierProgressReport` 专用模型映射到 `FollowUpLog`，登记安排状态、累计已备好量、预计备妥日期和纠错原因。
3. WPF 增加“采购工作台”，实现按采购单号、销售订单号、供应商和安排状态查询。
4. 已入库、最终已发货首期显示为“下游模块尚未启用”或可证明遗留只读值，不临时写采购行累计字段。
5. 采购关闭/剩余释放在上述闭环稳定后实现，避免第一批同时扩张过多命令。

## 13. 本专项明确不做

- 生产执行工作台和产能排程。
- 供应商门户或供应商直接登录反馈。
- 财务总账、移动平均成本和完整成本核算。
- 条码、批次、序列号和多级库位管理。
- 自动同步第三方物流或船公司状态。
- 复杂审批流；只实现特殊权限、原因、强提示和审计。
