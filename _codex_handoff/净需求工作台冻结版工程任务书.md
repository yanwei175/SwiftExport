## 1. 业务目标与本期范围

### 1.1 净需求定位

净需求是毛需求拆解后、采购/生产/外协执行前的计划需求池：

```text
销售订单 / 手工需求 / 投诉补货
  -> 毛需求 GrossDemand：为什么需要、原始需求是多少
  -> 净需求 NetDemand：BOM 拆解出了什么计划需求
  -> 计划分配 NetDemandAllocation：准备怎样执行、由谁执行、何时交付
  -> DemandExecutionLink：计划数量实际释放到了哪张执行单、哪一行
  -> 采购 / 未来生产 / 未来外协
```

净需求不是采购单，不是库存余额，也不是跟单进度表。它承上启下、支持分类汇总和计划调整，但下游业务事实必须来自正式执行单和追溯关系。

### 1.2 本期实现

- `Product.DefaultSupplierId` 默认供应商权威关系及兼容回填方案。
- 毛需求拆解时同步生成 NetDemand 初始计划分配。
- 净需求工作台 Search/List/Detail/Trace。
- 采购/生产/外协计划方式保存；当前只执行采购。
- 计划供应商、计划交期和 A/B 客供关系维护。
- 人工勾选转采购草稿。
- 按毛需求来源单一键转采购草稿。
- 采购行保持明细或合并的预览与用户选择。
- 部分数量转采购、幂等重试、逐来源事务和结果反馈。
- 新建采购草稿；人工入口可显式追加到安全草稿。
- `DemandExecutionLink` 建立、取消草稿后的释放边界及 Trace。
- WPF `.NET 10 + CommunityToolkit.Mvvm + EnterpriseGrid` 净需求工作台。
- 新链路测试、迁移草案和旧需求链路隔离检查。

### 1.3 本期不实现

- 完整采购工作台重构、采购确认、正式收货和采购反向流程。
- 生产工单、外协工单和传统 MRP。
- 库存/在途抵扣形成的传统净额计算；首期 `GrossQty = NetQty`。
- 入库、出库、PackingList、仓库和库存模块重构。
- 装柜预占、PackingList 自动入出库、异常负库存流水的代码实现。
- 一条 NetDemand 任意比例拆给多个供应商的首期 UI/命令；模型保留未来扩展能力。
- 旧物理表改名和旧列删除。

## 3. 冻结业务原则

### 3.1 来源关系

- 净需求唯一业务来源是毛需求。
- 销售订单只是毛需求来源之一，另有手工需求 MD、投诉补货 CR。
- 权威链路：

```text
GrossDemand
  -> NetDemand
  -> NetDemandAllocation
  -> DemandExecutionLink
  -> PurchaseOrderLine / 未来生产行 / 外协行
```

- 销售订单号和行号用于搜索、展示、Excel 和人工查账，不作为净需求到采购行的直接权威外键。
- 销售来源稳定关联继续使用毛需求的 `SourceUid/SourceLineId`；`SourceNo/SourceLineNumber` 是可读快照。

### 3.2 默认供应商

- 毛需求拆解以 `Product.DefaultSupplierId` 为默认供应商权威来源。
- `DefaultSupplierId` 指向 Supplier Uid；系统内部关系不得只依赖供应商代码。
- 当前 `Product.DefaultSupplierCode` 兼容期保留并同步，用于旧查询和人工查账；新计划判断以 Uid 为准。
- 不在 Product 保存默认供应商名称；当前名称实时 Join Supplier。
- 供应商产品管理页面提供显式“设为默认供应商”命令，在同一事务中更新 Product Uid、兼容代码和 Version。
- 设置默认供应商时必须存在有效 Supplier 和 SupplierProduct 关系；设置完成后 Product 默认关系可以独立存在，删除 SupplierProduct 时必须强提示但不静默清空 Product 默认供应商。
- Product 默认供应商变更只影响以后新拆解；既有 Allocation 不自动跟随。
- 工作台可以显式“应用当前产品默认供应商”，通过替代 Allocation 实现并保留历史。

### 3.3 拆解与初始计划

毛需求拆解在同一事务中完成：

```text
写入一个完整 NetDemand revision
  -> 为每条 NetDemand 创建初始 Allocation
  -> 更新 GrossDemand 拆解状态
```

初始 Allocation 规则：

- `ExecutionType` 默认取 `Product.SupplyType`。
- 采购型计划的 `PurchaseSupplierId` 取 `Product.DefaultSupplierId`。
- 没有默认供应商时仍生成完整数量 Allocation，供应商为空，状态查询显示“待分配供应商”。
- 非标件默认采购，供应商为空。
- A 与 B 各自读取自己 Product 的默认采购供应商。
- B 的送达目标指向 A 的 Allocation；A 尚无供应商时显示“送达目标待父件分配”。
- 初始计划数量等于 NetDemand.NetQty。

### 3.4 净需求不审批

- 净需求不增加确认或审批流程。
- 不使用旧 `DependentDemandStatusEnum` 或万能 `OrderStatus`。
- 净需求拆解后直接进入计划池。
- 待分配、可转采购、部分转采购、已转采购、已备好、已发货、齐套等均为查询计算状态，不写回 NetDemand 作为业务真相。

### 3.5 数量

- `GrossQty`：BOM/非标拆解形成的理论需求快照，禁止普通修改。
- `NetQty`：首期等于 GrossQty，禁止在工作台普通修改。
- `Allocation.PlannedQty`：计划执行数量；首期每条 NetDemand 只有一条活动 Allocation，数量等于 NetQty。
- 活动 Allocation 的 PlannedQty 合计必须等于 NetQty。
- 部分转采购通过 Link.AllocatedQty 表达，不通过修改 NetQty 表达。
- 人工转采购允许本次数量小于未转数量；默认带出全部未转数量。
- 剩余可转数量：

```text
Active Allocation.PlannedQty
  - Active DemandExecutionLink.AllocatedQty 合计
```

- 额外备品、损耗或 MOQ 通过独立手工毛需求说明来源；本期不增加快捷追加命令。

### 3.6 三日期模型

- `DemandRequiredDate`：毛需求传下来的原需求交期，不可修改。
- `PlannedDeliveryDate`：计划员要求供应商交付的日期；初始取原需求交期，净需求工作台可调整。
- `SupplierExpectedDate`：供应商反馈的预计完成日期，来自未来跟单进度报告。
- 采购行交期取 PlannedDeliveryDate。
- 合并采购行时计划交期不同可以合并，但必须在预览中强提示，采购交期取最早值。
- 每条 Allocation/Link 仍保留自己的原需求交期和计划交期，供延期分析。

### 3.7 执行方式

- 持久化执行方式：采购、生产、外协。
- 当前只允许采购型 Allocation 执行“转采购”。
- 生产、外协可以保存计划，但显示“执行工作台尚未接入”。
- 一键转采购只处理采购型 Allocation；生产和外协列为本次不处理，不算采购错误。

## 4. A 与客供件 B 的冻结规则

### 4.1 两类供应商概念

```text
A Allocation
  PurchaseSupplier = A 的采购/执行供应商甲

B Allocation
  PurchaseSupplier = B 自己的采购供应商乙
  DeliveryTargetAllocation = A Allocation
  DeliveryTargetSupplier = 甲
```

- B 的采购供应商和送达供应商是两个独立概念。
- 修改 A 供应商：B 的采购供应商保持不变，B 的送达目标供应商同步变化。
- 修改 B 采购供应商：不影响 A。
- B 的送达关系必须结构化保存，不能只写备注或 `DeliveryTo` 文本。

### 4.2 A/B 分开转采购

- 人工勾选入口允许 A、B 分开转采购。
- 单独转 B 的条件：
  - B 采购供应商已确定。
  - A 计划供应商已确定。
  - B 送达目标已解析到 A Allocation 和 A 供应商。
- 单独转 A 时，如果关联 B 仍有未转采购数量，必须强提示；用户确认后允许继续。
- 按来源单一键转采购必须完整处理所有尚未转的采购型 A/B 计划；任一采购计划信息不完整则整单阻断。

### 4.3 A 供应商变更阻断

- A 自身或任何以 A Allocation 为送达目标的 B 存在活动 Link 时，禁止普通修改 A 供应商。
- 系统返回所有阻断采购单号、采购行和 B 需求。
- 用户必须先取消相关安全采购草稿，使 Link 进入 Cancelled。
- 然后替代 A Allocation，并同步替代 B Allocation 的送达目标。
- 最后重新转采购。

### 4.4 未来多供应商拆分

- 实际业务极少出现一条 A 分给多个供应商，首期不突出或实现比例拆分命令。
- Allocation 数据模型不得锁死一条 NetDemand 只能有一个活动 Allocation，以便未来扩展。
- 未来启用拆分时，A 按比例拆分，B 按四位小数最大余数法同步分配，保证 B 分配总和严格等于原 NetQty。
- 未来拆分仍必须保持 B Allocation 指向具体 A Allocation。

## 5. 转采购草稿业务流程

### 5.1 三个入口，一个后端命令

入口：

1. 净需求工作台人工勾选。
2. 按毛需求来源单一键转采购；销售来源时用户按销售订单号操作。
3. 未来采购工作台“从净需求获取”。

三个入口必须复用同一套 Preview/CreatePurchaseDrafts 契约和 Application 编排，不允许建立三套转采购逻辑。

### 5.2 人工勾选

- 勾选粒度是活动 Allocation；首期页面表现为一条净需求计划行。
- 用户可以填写每行本次采购数量，默认全部剩余量。
- 允许只选 A 或 B，并按 4.2 提示或校验。
- 可以一次勾选多个来源单，但系统必须按来源单分组执行。
- 默认新建采购草稿。
- 若存在同来源、同供应商且满足安全条件的采购草稿，预览中允许用户显式选择追加。

### 5.3 按来源单一键转采购

- 一个来源单指毛需求的 `(SourceType, SourceUid)`；销售订单号只是可读检索入口。
- 查找该来源单全部活动毛需求、活动 NetDemand 和活动 Allocation。
- 所有采购型计划必须：
  - 供应商完整。
  - B 送达关系完整。
  - 数量和剩余量有效。
  - 没有数据一致性或并发异常。
- 任一采购型计划不完整，整次不生成任何采购草稿。
- 一键入口处理所有采购型剩余数量，不提供部分数量输入。
- 一键入口始终默认新建采购草稿，不自动追加既有草稿。
- 已全部转完时返回幂等结果和既有采购单，不重复建单。

### 5.4 禁止跨来源单合并

无论一键还是人工勾选，采购单头的最低分组边界是：

```text
GrossDemand.SourceType
+ GrossDemand.SourceUid
+ PurchaseSupplierId
```

因此一次选择 SO001、SO002：

```text
SO001 + 供应商甲 -> PO001
SO001 + 供应商乙 -> PO002
SO002 + 供应商甲 -> PO003
```

不同来源单可以在一次请求中提交，但不得进入同一张采购单。

### 5.5 保持明细或合并

转采购预览弹窗提供：

- 保持来源明细。
- 合并同类采购行。

默认保持来源明细。用户选择合并后，仅在以下条件兼容时合并：

- 同一来源单。
- 同一采购供应商。
- 同一 Product/SKU。
- 同一执行方式，且均为采购。
- 同一送达供应商。
- 同一单位和数量精度。
- 同一采购价格口径；价格缺失可以一起生成待补资料草稿。

计划交期不同允许合并，但必须列出差异并由用户确认，采购行取最早 PlannedDeliveryDate。

保持明细时允许同一采购单内同 SKU 多行，采购行以稳定 LineNumber 区分。

### 5.6 来源追溯与老板 Excel 查询

- 采购单头冗余保存来源快照：
  - `DemandSourceType`。
  - `DemandSourceUid`。
  - `DemandSourceNo`。
- 采购工作台以后可直接按销售订单号查采购单头。
- 权威逐条追溯仍为 Link -> Allocation -> NetDemand -> GrossDemand。
- 合并采购行产生多条 Link，每条 Link 保存自己的分配数量。
- Excel 应提供“来源—采购追溯明细”，按每个来源贡献展开，而不是只导出采购单头：

| 来源单号 | 来源行号 | SKU | 毛/净需求量 | 采购单号 | 采购行号 | 供应商 | Link数量 | 原需求交期 | 采购交期 |
|---|---:|---|---:|---|---:|---|---:|---|---|

- 采购单头来源快照与 Link 链路不一致时为数据异常，权威以 Link -> GrossDemand 为准。

### 5.7 价格与人民币

- 当前供应商采购仅人民币，不在净需求、预览和分组中设计币种选择。
- 采购草稿需要币种字段时系统统一填人民币。
- 价格不保存在 NetDemand 或 Allocation。
- 转采购时按 `(ProductId, SupplierId)` 查询活动 SupplierProduct，能找到则带出供应商 SKU、建议单价和含税价。
- 找不到 SupplierProduct 或价格时仍允许创建采购草稿，并标记“采购资料待补充”。
- 价格属于采购草稿，SupplierProduct 后续变化不自动修改既有草稿或历史采购单。

### 5.8 新建与追加草稿

- 默认新建采购草稿，避免静默修改已经交给老板或供应商查看的采购单。
- 人工入口预览发现安全草稿时，可以选择追加到指定草稿。
- 安全草稿必须同时满足：
  - 同一来源单。
  - 同一供应商。
  - 未确认、未关闭、未作废。
  - 无正式收货。
  - 无库存流水。
  - Version 未变化。
- 追加也必须在一个来源单事务中完成；失败全部回滚。

## 6. 采购草稿修改与取消

### 6.1 取消草稿

安全采购草稿取消时，在同一事务中：

1. 锁定采购头、行和活动 Link。
2. 再次确认未确认、无收货、无库存流水。
3. 采购草稿进入作废/取消状态，保留历史。
4. 对应 Link 进入 `Cancelled`，记录取消人、时间和原因。
5. Allocation 自动恢复剩余可转数量。

不得物理删除 Link，不得清空 NetDemand 的旧 `TargetNo/TargetLineId` 作为新流程回退方式。

### 6.2 减少采购数量

- 采购行数量不能普通编辑而绕过 Link。
- 减少数量必须执行显式“释放需求数量”命令并显示来源释放预览。
- 默认按以下反向顺序释放：

```text
原需求交期降序
-> 来源行号降序
-> Allocation Uid 稳定降序
```

- Link.AllocatedQty 同步减少；释放数量回到 Allocation 剩余量。
- 已有收货或库存流水后禁止使用该命令。

### 6.3 增加采购数量

- 不允许把采购行 QTY 增加到超过 Link 数量合计并自动冒充需求。
- 额外采购必须来自新的或剩余的净需求 Allocation，或明确创建无需求来源的独立采购行。
- 本专项不实现无来源采购行流程。

### 6.4 修改供应商

- 已由净需求生成采购草稿后，不允许直接修改采购头供应商。
- 正确流程：取消采购草稿 -> Link Cancelled -> 净需求重新计划 -> 再次转采购。
- 采购草稿允许按采购模块规则调整价格、备注等商务字段；需求来源、供应商和追溯数量必须走显式命令。

`NetDemandAllocation`：

### 7.2 查询计算状态

| 页面状态 | 计算依据 |
|---|---|
| 待分配供应商 | 采购型活动 Allocation.SupplierId 为空 |

| 可转采购 | 采购计划完整且剩余量大于 0 |
| 部分转采购 | 活动 Link 合计介于 0 与 PlannedQty 之间 |
| 已转采购 | 活动 Link 合计等于 PlannedQty |
| 下游草稿 | Link 目标采购单为草稿 |

### 7.3 未来跟单数据事实源

| 指标 | 权威来源 | 本期处理 |
|---|---|---|
| 需求数量 | NetDemand | 实现 |
| 计划数量 | 活动 Allocation | 实现 |
| 已安排采购 | Active Link.AllocatedQty | 实现 |
| 未安排/未转数量 | Allocation - Active Link | 实现 |
| 供应商累计已备好 | PurchaseProgressReport | 预留，后续实现 |
| 供应商预计完成日期 | PurchaseProgressReport | 预留，后续实现 |
| 客供件已到供应商虚拟仓 | 正式入库单和库存流水 | 后续实现 |
| 客户已发货 | PackingList 生成的正式出库单/流水 | 后续实现 |
| 齐套数量 | 父件备好覆盖量与客供件虚拟仓可用量查询计算 | 后续实现 |

### 7.4 供应商已备好数量

- 由跟单人员根据供应商反馈手工登记累计已备好数量。
- `PurchaseProgressReport` 保存不可覆盖的历次报告：采购行、累计已备好、报告时间、供应商预计完成日期、备注、登记人、修正原因。
- 采购行可以保存当前累计值作为查询缓存，但报告历史是原始事实。
- 已备好不等于库存，不产生库存流水。
- 合并采购行的已备好覆盖量按：

```text
DemandRequiredDate 升序
-> SourceLineNumber 升序
-> Allocation Uid 稳定升序
```

分配给各来源，只用于跟单展示和预警。报告向下修正后重新计算覆盖，不修改历史报告。

- PackingList 实际出货归属未来由用户选择，以正式出库追溯为最终事实，可以与预计覆盖顺序不同，但必须提示早交期需求未满足。

## 8. 未来入出库与 PackingList 冻结边界

本节只冻结接口边界，本专项不实现代码。

### 8.1 供应商虚拟仓

- 父件 A 和客供件 B 都进入 A 执行供应商的虚拟仓。
- 手工入库的 A 与 PackingList 自动入库的 A 使用同一库存闭环。
- 客供件 B 由跟单人员手工建立正式入库单，进入 A 供应商虚拟仓。
- PackingList 出货时，从同一虚拟仓扣减 A 和对应 B。
- A 出库表示客户发货；B 出库表示随 A 被消耗。
- 供应商仓关系以 SupplierId 为权威，供应商代码作快照。

### 8.2 PackingList 自动入库数量

```text
父件自动入库数量
= max(本次出货数量 - 当前可用于本次出货的父件正式库存, 0)
```

供应商累计已备好 100、本次出货 60、当前正式库存 0 时，只自动入库 60，再出库 60；剩余已备好 40 仍不是库存。

### 8.3 缺料特殊授权

- 缺少父件备好量、客供件库存或存在装柜预占冲突时允许特殊授权放行，但必须强提示、权限校验、填写原因并保存异常快照。
- 特殊授权不修改真实已备好量，不伪造入库。
- 客供件不足时使用专门允许负库存的异常流水类型。
- 正常库存部分生成普通出库流水，缺口生成异常负库存流水。
- 后续补录客供件入库时自然冲平负库存，并按时间顺序核销缺口；不修改或删除原异常流水。
- PackingList 提交后客户已发货数量以正式出库单和流水为准。

### 8.4 架构边界

- PackingList Application Service 掌握最外层事务。
- PackingList 不直接拼装多个泛型 Repository 写入业务闭环。
- 后续先重构最小入库/出库/库存过账处理器，再由 PackingList 调用；处理器共享当前 DbSession.Transaction，不自行开启业务事务。

## 10. Allocation 替代与毛需求回退

### 10.1 修改计划采用替代

修改供应商、执行方式或计划交期时不覆盖旧 Allocation：

1. 锁定当前活动 Allocation 和相关 A/B Allocation。
2. 检查自身与被引用关系的活动 Link。
3. 旧 Allocation -> Superseded。
4. 创建 PlanRevision+1 新 Allocation，`ReplacesAllocationId` 指向旧记录。
5. A 供应商变化时同步替代所有 B 的送达目标 Allocation。
6. 保留操作人、时间和原因。

普通列表只显示活动计划，Trace 展示替代历史。

### 10.2 应用当前默认供应商

- 仅用于活动、未执行的采购型 Allocation。
- 重新读取 Product.DefaultSupplierId 和 Supplier 当前代码/名称。
- 与当前计划相同则返回 AlreadyApplied。
- 不同则走 Allocation 替代命令。
- Product 没有默认供应商时返回明确错误，不清空现有人工计划。

### 10.3 毛需求安全回退

无活动 Link 时允许回退：

1. 锁定 GrossDemand、活动 NetDemand、活动 Allocation 和 Link 键范围。
2. 活动 Allocation -> Cancelled，`CancelReasonCode=GrossDemandRollback`。
3. 当前 revision 的 NetDemand -> RolledBack。
4. GrossDemand -> Pending，revision 不递减。
5. 保留全部历史。

存在活动 Link 时继续阻断，用户必须先取消下游安全草稿或完成未来反向流程。

## 11. 事务、并发和幂等

### 11.1 事务粒度

- 一次人工请求可以包含多个来源单。
- 以 `(SourceType, SourceUid)` 为独立事务单位。
- 同一来源单可能生成多个供应商采购草稿；这些采购头、行、Link 必须全部成功或全部回滚。
- 不同来源单互不回滚。
- 一键转采购只有一个来源单，因此整次完全原子。

示例：

```text
SO001：成功，生成 PO001/PO002
SO002：供应商缺失，全部回滚
MD001：成功，生成 PO003
```

### 11.2 锁顺序

同一来源事务使用稳定顺序：

1. 按 Uid 排序锁定 GrossDemand。
2. 锁定活动 NetDemand。
3. 锁定活动 Allocation。
4. 使用 `UPDLOCK,HOLDLOCK` 锁定活动 Link 范围。
5. 新建模式锁定幂等请求范围；追加模式再锁定目标采购头、行。
6. 计算剩余量并创建采购头、行、Link。

不得并发复用同一个 scoped DbSession；不同来源按请求顺序逐项执行。

### 11.3 幂等

- Preview 返回服务端签名/版本集合和客户端 `ExecutionRequestId`。
- Execute 必须携带：
  - ExecutionRequestId。
  - 每个 Allocation Uid + Version。
  - ExpectedRemainingQty。
  - CommandItemId。
  - PreviewSignature 或等价受控版本信息。
- 相同请求重试：
  - 已成功来源返回 AlreadyApplied 和原采购单号。
  - 失败来源可以重新处理。
  - 不重复建采购头、行或 Link。
- 数据版本或剩余数量变化时返回预览失效，要求重新预览。

### 11.4 部分失败

- 来源单内部不允许部分成功。
- 请求整体返回逐来源结果：Succeeded/AlreadyApplied/Failed。
- 错误码必须稳定，至少覆盖：供应商缺失、送达目标缺失、剩余量不足、版本冲突、活动 Link 变化、目标草稿不安全、采购资料待补警告、数据损坏。

### 13.3 毛需求拆解联动

修改 `GrossDemandWorkspaceService.DecomposeOneAsync`：

- 计划器继续只计算 NetDemand。
- Application 在获得完整 NetDemand 集合后，批量读取默认供应商并建立初始 Allocation。
- A Allocation Uid 预生成后再建立 B.DeliveryTargetAllocationId。
- NetDemand + Allocation + GrossDemand 状态同事务写入。
- 任何 Allocation 写入失败，整个毛需求拆解项回滚。
- 重复拆解幂等检查同时验证活动 NetDemand 与活动 Allocation 完整性。

修改安全回退：

- 在 Link blocker 前锁定活动 Allocation。
- 无活动 Link 时取消 Allocation，再回退 NetDemand。
- 活动计划缺失或数量合计不一致时返回 CORRUPTED_STATE，不假装成功。

### 13.4 Product 默认供应商命令

供应商产品管理 Service 增加显式命令，不把动作藏进普通批量保存：

1. 校验 Product、Supplier、SupplierProduct 活动且 Uid/Code 匹配。
2. 锁定 Product，校验 Version。
3. 更新 DefaultSupplierId 和兼容 DefaultSupplierCode。
4. 增加 Version 和审计。
5. 返回更新后的 Product/SupplierProduct Query DTO。

已有 NetDemand Allocation 不自动更新。

### 16.3 007 BackfillAndConstraints

- Product 默认供应商：仅在 DefaultSupplierCode 唯一匹配 Supplier 时回填 Uid；无法证明的输出异常，不猜测。
- 活动 NetDemand：优先以旧 PreferredSupplierId/Code 可证明值回填初始 Allocation；否则使用 Product.DefaultSupplierId；仍无值则创建待分配 Allocation。
- B Allocation：根据 DeliveryTargetNetDemandId 找同 revision A Allocation，回填目标；无法唯一证明时阻断。
- 历史 RolledBack/Voided NetDemand 不强行生成活动 Allocation；需要 Trace 时可生成历史取消计划或保留为空，由迁移方案明确。

- 调整采购行 QTY 精度。
- 删除 `(OrderNo,Sku)` 唯一约束，建立 `(PurchaseOrderId,LineNumber)` 唯一约束。
- 建立 Allocation FK/索引/检查约束。
- 重构 Link 唯一索引为 CommandItem 幂等和 Allocation 查询索引。
- 全部断言通过后再收紧新 Link 必填字段；历史兼容是否允许空值由实际数据决定。

所有脚本必须校验数据库、`SET XACT_ABORT ON`、幂等、事务执行、失败完整回滚；禁止包含演示数据清库。

## 19. 旧需求链路隔离与兼容边界

### 19.1 新代码禁止引用

新增或修改的 NetDemand 专项代码不得引用：

- `IndependentDemand/DependentDemand` 旧 Entity。
- `IndependentDemandDto/DependentDemandDto`。
- `IIndependentDemandApi/IDependentDemandApi`。
- `IIndependentDemandServices/IDependentDemandService`。
- `IIndependentDemandRepository/IDependentDemandRepository`。
- `IndependentDemandStatusEnum/DependentDemandStatusEnum`。
- 旧 BomService 递归拆解入口。

物理表名 `IndependentDemand/DependentDemand` 和历史兼容列不是旧业务依赖；新专用 Repository 可继续使用显式 SQL 映射。

### 19.2 客户端切换

- 注册 `INetDemandWorkspaceApi("demand-planning/net-demands")`。
- 净需求 WPF 页面不得注入旧 IDependentDemandApi。
- 全仓确认当前新客户端无引用后移除旧 IDependentDemandApi 注册。
- 导航从毛需求 Trace 打开新净需求工作台并带 Uid/来源筛选。

### 19.3 后端清理顺序

- 新 Controller 不注入旧服务。
- 旧 Controller/Service/Repository 当前仍可能被未重构入库、PackingList 等兼容代码引用，不能在本专项盲删。
- 先建立新链路并用 `rg`/编译检查证明无新引用。
- 下游模块重构后，再单独评审旧 DI、Controller、Service、DTO、Repository 和 005 LegacyCleanup。
- 不允许新旧服务同时写净需求计划、执行状态或 Link。
