# SwiftExport 销售订单“准备改单”实施代办

> 建立日期：2026-08-27  
> 状态：待在独立 Codex 窗口实施  
> 当前窗口边界：不实施本计划；当前窗口继续只处理净需求工作台专项。  
> 权威依据：`AGENTS.md`、`.agents/router.toml`、`.agents/planner.toml`、`.agents/workflows/业务规划工作流.md`、`.agents/references/业务架构总纲.md` 及真实源码。

## 1. 业务目标

为“销售订单已经确认并进入需求/采购草稿链路后需要修改”的场景提供一个清晰、安全、可预览、整单原子的业务入口：`准备改单`。

该入口只负责把仍处于安全草稿边界的整张销售订单恢复为 `Open + 待确认`，使用户可以修改并重新确认；不得越过已确认采购或正式履约事实静默删除历史。

## 2. 已确认的业务决定

1. `准备改单`由销售订单工作台作为唯一执行入口；毛需求和净需求工作台只提供来源影响查询和导航。
2. 同一销售订单内全成全败，不能只恢复部分销售行，也不能由 WPF 串行调用多个写 API 模拟事务。
3. 第一期仅自动处理 `Active + 待确认`、来源 Link 完整且没有收货/库存事实的安全采购草稿。
4. 已确认但尚未入库的采购单，第一期作为阻断项展示；用户先在采购工作台取消确认，再重新执行 `准备改单` Preview。
5. 已出现入库、库存流水、PackingList 或出库事实时，即使相关正式单据已经完成反向，也不让原销售订单恢复普通编辑。原订单和正式事实保持不可变；未来另建销售变更版本/变更单专项。
6. 不新增单条 NetDemand 删除或回退命令。拆解回退单位固定为 `GrossDemand + DecompositionRevision`。
7. Allocation 的供应商、执行方式或交期改错继续使用计划替代，不属于销售改单。

## 3. 当前源码事实

### 3.1 已存在能力

- `GrossDemandWorkspaceService.RollbackAsync`：无活动 Link 时，取消当前 revision 的活动 Allocation、将 NetDemand 标记为 RolledBack、毛需求恢复 Pending。
- `PurchaseDraftLifecycleService.CancelAsync`：安全采购草稿整单作废、活动 Link 取消、Allocation 剩余可转量恢复。
- `PurchaseDraftLifecycleService.ReleaseAsync`：按 Preview 释放部分 Link 并同步减少采购行数量；该能力不等同于拆解回退。
- `PurchaseOrderWorkspaceService.CancelConfirmationAsync`：已确认采购在没有收货/库存事实时可人工取消确认。
- `SalesOrderWorkspaceService.CancelConfirmationAsync`：整单校验毛需求和历史完整性后，物理删除从未拆解毛需求、作废保留已回退毛需求，并恢复销售订单待确认。

### 3.2 当前缺口

- 用户必须跨净需求 Trace、毛需求和销售订单页面手工执行多步操作，没有统一 Preview 和下一步导航。
- 毛需求回退只返回活动 Link 阻断，不能直接解释哪些采购草稿可安全取消、哪些正式事实必须人工处理。
- 现有三个写操作分属不同服务/事务，WPF 顺序调用会产生部分成功风险。
- `PurchaseDraftLifecycleService` 当前接收 `CommandId`，但安全取消本身未形成完整的业务幂等日志闭环；新编排服务不能只依赖客户端防重。
- 销售取消确认对入库、出库、PackingList 等采用历史事实存在即阻断；这与“正式事实产生后原订单不可普通编辑”的目标一致，应保留该边界。

## 4. 目标业务流程

### 4.1 安全草稿链路

```text
已确认销售订单
  -> 准备改单 Preview
  -> 识别整单所有毛需求、当前拆解 revision、活动 Allocation 和活动 Link
  -> 识别可自动取消的待确认采购草稿
  -> 确认不存在已确认采购或正式履约阻断
  -> 用户填写改单原因并确认
  -> 同一事务取消安全采购草稿及 Link
  -> 同一事务回退全部活动毛需求拆解
  -> 同一事务取消销售订单确认
  -> 写 BusinessOperationLog 和幂等结果
  -> 销售订单恢复 Open + 待确认并打开编辑页
```

### 4.2 已确认采购但未入库

```text
准备改单 Preview 返回采购阻断和单据号
  -> 用户打开采购工作台
  -> 人工取消采购确认
  -> 重新执行准备改单 Preview
  -> 采购单已成为安全草稿后，允许统一事务自动取消
```

第一期不在销售改单事务中静默取消采购确认，避免跨岗位边界和用户误操作。

### 4.3 已有正式履约事实

```text
准备改单 Preview 返回正式阻断
  -> 用户按模块完成 PackingList/出库/入库/库存的正式反向
  -> 原销售订单仍保持历史不可编辑
  -> 未来通过销售变更版本/变更单表达新的商业事实
```

不得因为正式反向净额恢复为零，就物理删除原单据、流水或需求追溯。

## 5. 状态与历史结果

| 对象 | 准备改单成功后的状态 |
|---|---|
| SalesOrderHeader | `DocumentStatus=Open`、`ConfirmationStatus=待确认`、Version+1 |
| 从未拆解 GrossDemand | 允许物理删除 |
| 曾拆解并完整回退 GrossDemand | `LifecycleStatus=Voided`，保留 Trace |
| 当前 revision NetDemand | `LifecycleStatus=RolledBack` |
| 当前活动 Allocation | `LifecycleStatus=Cancelled` |
| 安全 PurchaseOrderHead | `LifecycleStatus=Voided`、仍为待确认历史草稿 |
| 对应 DemandExecutionLink | `LinkStatus=Cancelled`，保留数量与取消原因 |
| BusinessOperationLog | 追加一条整单准备改单成功记录，包含原因和结果摘要 |

## 6. API 契约草案

建议销售工作区新增：

| API | 作用 |
|---|---|
| `POST /api/sales-orders/workspace/{uid}/change-preparation-preview` | 只读计算整单安全反向影响 |
| `POST /api/sales-orders/workspace/{uid}/prepare-change` | 按有效 Preview 执行整单事务 |

### 6.1 Preview 请求

`SalesOrderChangePreparationPreviewRequest`

- `Uid`
- `ExpectedVersion`

### 6.2 Preview 响应

`SalesOrderChangePreparationPreviewResponse`

- 销售订单摘要：单号、Version、活动行数。
- 毛需求摘要：Uid、来源行、状态、DecompositionRevision。
- 拆解摘要：NetDemand/Allocation 数量及状态统计。
- `CancellablePurchaseDrafts`：采购头 Uid、单号、Version、供应商、行数、有效 Link 数量和数量合计。
- `Blockers`：阻断类型、模块、目标头行 Uid、单据号、原因、推荐目标工作台。
- `ExpectedEffects`：预计取消草稿、Link、Allocation、NetDemand，以及删除/作废毛需求数量。
- `HasBlockers`。
- `PreviewToken`。

### 6.3 Execute 命令

`PrepareSalesOrderChangeCommand`

- `Uid`
- `ExpectedVersion`
- `CommandId`
- `PreviewToken`
- `Reason`：Trim 后必填，建议沿用销售取消确认的 1000 字符上限。

### 6.4 Execute 结果

`PrepareSalesOrderChangeResult`

- `Uid`
- 新销售订单 Version。
- 取消采购草稿数、采购行数、Link 数和数量合计。
- 回退 NetDemand 数、取消 Allocation 数。
- 物理删除毛需求数、作废保留毛需求数。
- `Outcome`、`Message`。

### 6.5 PreviewToken

Token 至少覆盖：

- 销售订单 Version 和活动销售行集合。
- 毛需求 Uid、Version、LifecycleStatus、DecompositionStatus、DecompositionRevision。
- 当前 revision 的 NetDemand/Allocation Uid、Version、状态和数量。
- 活动 Link Uid、Version、状态、AllocatedQty、ReleasedQty、目标采购头行。
- 采购草稿 Uid、Version、生命周期、确认状态和行数量。
- 已确认采购与正式履约阻断摘要。

Execute 必须在固定锁序下重新读取并校验事实，不能信任客户端 Preview 内容。

## 7. 后端实施任务

### Phase 0：权威文档冻结

- 将本文件第 2 节业务决定写入 `.agents/references/业务架构总纲.md` 的销售订单反向规则。
- 明确“安全准备改单”和“正式事实后的销售变更版本”是两个专项。

### Phase 1：只读 Preview

- 在 Contracts 增加 Preview Request/Response、阻断项和影响摘要 DTO；保持 `netstandard2.0` 兼容。
- 在 Application 增加销售改单准备服务接口和 Preview 实现。
- 在 Core 增加最小必要 Repository 查询接口。
- 在 Infrastructure 实现按销售来源聚合毛需求、NetDemand、Allocation、Link、采购和正式事实的只读查询。
- Controller 与 Refit 路由保持一致。
- Preview 不开启写事务、不改变任何状态。

### Phase 2：统一 Execute 事务

- 由销售改单 Application 编排服务掌握最外层事务。
- 固定锁序：销售头 → 幂等日志 → 销售行 → 毛需求 → NetDemand → Allocation → Link → 采购头 → 采购行 → 正式下游事实。
- 复用现有领域规则，但不要在已有事务中调用会自行开启事务的公开 Service 方法；应抽取或新增可在当前 `DbSession` 事务中使用的内部协作方法/Repository 命令。
- 校验 PreviewToken 和所有 Version；任一变化返回 `PREVIEW_EXPIRED` 且零写入。
- 同事务依次取消安全采购草稿和 Link、回退全部活动拆解、执行销售取消确认分类、更新销售状态、写幂等业务日志。
- `CommandId` 重试返回首次成功结果；换订单、换原因或不同请求指纹复用时拒绝。
- 任一步影响行数不符时回滚整单事务。

### Phase 3：错误码与日志

至少提供稳定错误码：

- `SALES_ORDER_NOT_EDITABLE`
- `VERSION_CONFLICT`
- `PREVIEW_EXPIRED`
- `PURCHASE_CONFIRMED`
- `FORMAL_FULFILLMENT_EXISTS`
- `CORRUPTED_DEMAND_HISTORY`
- `COMMAND_REUSED`

BusinessOperationLog 保存整单操作摘要和必要关联对象，不保存完整 DTO、Token 或敏感信息。

## 8. WPF 实施任务

- 销售订单管理页和详情页对 `Open + 已确认` 订单提供“准备改单”。
- 点击后打开 Preview 对话框/抽屉，分组展示：预计自动处理、人工阻断、处理后结果。
- 阻断项显示准确单据号和模块；能导航时提供“打开采购工作台”等入口。
- 有阻断时禁止 Execute，不执行任何写调用。
- 无阻断时要求填写原因并二次确认；提交期间 Busy 防重。
- 成功后刷新订单 Version、恢复待确认，并打开或保持在可编辑详情。
- 净需求、毛需求页面未来只增加“查看来源影响/打开销售订单准备改单”导航，不复制整单执行逻辑。

## 9. 测试与验收

### 9.1 Application/Repository 自动测试

1. 只有活动拆解、无 Link：成功回退拆解并取消销售确认。
2. 一个安全采购草稿：草稿 Voided、Link Cancelled、拆解回退、销售待确认。
3. 同一订单多个毛需求、多个供应商草稿：全部安全时整单成功。
4. 部分转采购但全部下游仍为安全草稿：取消所有相关草稿后整单成功。
5. 存在已确认采购：Preview 阻断，Execute 零写入。
6. 存在入库、库存流水、PackingList 或出库任一事实：Preview 正式阻断，Execute 零写入。
7. Preview 后采购草稿 Version、Link 数量或毛需求 revision 变化：`PREVIEW_EXPIRED`，零写入。
8. 任一采购草稿取消写入发生并发冲突：销售、毛需求和其他草稿全部回滚。
9. 重复相同 CommandId：返回首次结果，不重复修改或写日志。
10. CommandId 换订单、原因或请求指纹重用：拒绝。
11. A+B 客供件：同一 revision 整体回退，不能只处理 A 或 B。
12. 历史 revision/Allocation 不完整：Preview 或 Execute 返回数据损坏阻断。

### 9.2 契约与 WPF 测试

- Controller 与 Refit 路由、HTTP 方法、DTO 和返回包装一致。
- Preview 有阻断时按钮禁用且不调用 Execute。
- Busy 状态防重复提交。
- Version/Preview 失效后提示刷新并重新预览。
- 成功后订单进入待确认并允许既有编辑命令。
- 阻断项导航携带正确目标 Uid/单据号。

### 9.3 构建与手工验收

- `dotnet build .\SwiftExport-WebAPI.slnx`
- `dotnet build .\SwiftExport.Client.Wpf\SwiftExport.Client.Wpf.csproj`
- 运行新增的后端与 WPF 最小测试集合。
- 使用一次性开发数据跑安全草稿、已确认采购、已入库和 A+B 客供件四条主场景。
- 实施窗口必须先检查并保护当时所有未提交改动，不得创建新 worktree，除非用户另行授权。

## 10. 明确不做

- 不允许直接编辑已确认销售订单。
- 不新增单条 NetDemand 物理删除或回退接口。
- 不自动取消已确认采购。
- 不自动反向入库、库存、PackingList 或出库。
- 不在本专项实现正式事实后的销售变更版本/变更单。
- 不让 WPF 编排跨模块写事务。
- 不以开发库可重建为理由删除正式历史。
