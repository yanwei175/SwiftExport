# SwiftExport 业务操作日志冻结版工程任务书

## 1. Codex 新任务启动提示词

> 请先完整读取本任务书和同目录《库存履约下游专项总索引》，再读取根目录 `AGENTS.md`、`.agents/router.toml`、命中的日志/后端 workflow/skill 和真实源码。先审计当前 Serilog、Middleware、当前用户、AuditStampService、Application 事务与配置，不要假设“已有日志服务”已经覆盖业务审计。技术日志、实体审计字段、业务操作日志和库存流水必须分层，不得互相替代。默认只生成增量迁移脚本，不连接或修改共享数据库。

## 2. 当前基线与问题

当前源码已经具备：

- Serilog 技术日志，面向异常、诊断和运行信息，主要写滚动文件。
- `AuditStampService`，为业务实体填写 CreatedBy/CreatedDate/UpdatedBy/UpdatedDate。
- 当前用户和认证上下文，可获得操作者信息。

这些能力仍不足以稳定回答：谁在何时确认了采购单、谁把供应商已备好数量从多少纠正为多少、谁允许了负库存、某次 PackingList 过账生成了哪些入出库单，以及某业务命令是否已经成功执行。

因此需要新增持久化、追加式、可查询的业务操作日志；无需用它替换 Serilog。

## 3. 四类记录的职责

| 类型 | 解决的问题 | 权威性 |
|---|---|---|
| Serilog 技术日志 | 程序异常、耗时、SQL/外部调用诊断、运行上下文 | 技术诊断，不作为业务事实 |
| 实体审计字段 | 某行何时/由谁创建或最后更新 | 轻量元数据，不保存操作历史 |
| BusinessOperationLog | 谁对哪个业务聚合执行了什么成功命令及原因/结果 | 业务审计与命令追踪 |
| InventoryLedgerEntry | 某仓某产品为何增减、过账后余额多少 | 库存领域账本 |

禁止把异常堆栈塞进 BusinessOperationLog，也禁止把库存流水当成通用“用户操作日志”。

## 4. 已冻结原则

- 业务操作日志只追加，不提供 Update/Delete。
- 成功日志与被记录的业务状态必须在同一个数据库事务提交；业务回滚时成功日志也回滚。
- 业务校验失败、系统异常和被权限拒绝主要写 Serilog；首期不建立独立失败尝试表。
- 每个 HTTP 请求都有 `CorrelationId`；每个业务写命令都有 `CommandId`。Serilog、业务日志和领域流水用这两个 Id 关联。
- 同一个成功 CommandId 在同一 Module/OperationType 下只能有一条主日志；幂等重试返回原结果，不重复写日志。
- 日志保存业务身份 Uid 和当时的单号/名称快照；查询不依赖对象后来是否被改名或停用。
- Before/After 只记录本操作需要审计的字段，不序列化整个 Entity/DTO。
- 禁止记录密码、JWT、连接字符串、数据库凭据、完整请求头、银行卡号或无关个人信息。
- 日志使用 UTC 或项目统一时间策略持久化，WPF 按用户时区展示；同一项目不得混用无标识本地时间。
- 首期应用内无限期保留；未来归档只能搬迁冷数据，不能改变审计语义。

## 5. CorrelationId 技术链路

新增/完善 Middleware：

1. 接受合法的 `X-Correlation-ID`，否则生成 Guid。
2. 写入 `HttpContext.TraceIdentifier`、响应头和 Serilog LogContext。
3. Application 从请求上下文只读取得 CorrelationId；非 HTTP 任务自行生成。
4. Controller 不手工拼接日志字段。

Serilog 最低结构字段：CorrelationId、CommandId（有则写）、UserId、RequestPath、HTTP Method、StatusCode、ElapsedMs、ExceptionType。生产环境不得默认记录完整请求/响应正文。

## 6. BusinessOperationLog 数据模型

| 字段 | 类型建议 | 规则 |
|---|---|---|
| Uid | uniqueidentifier | 主键 |
| CorrelationId | uniqueidentifier / nvarchar(64) | 请求链路 |
| CommandId | uniqueidentifier | 业务命令幂等关联 |
| Module | nvarchar(50) | DemandPlanning、Procurement、Inventory、Shipping 等 |
| AggregateType | nvarchar(80) | NetDemand、PurchaseOrder、InboundDocument 等 |
| AggregateId | uniqueidentifier nullable | 聚合 Uid |
| AggregateNoSnapshot | nvarchar(100) nullable | 人工可读编号快照 |
| OperationType | nvarchar(80) | 稳定机器代码 |
| OperationName | nvarchar(100) | 中文展示名称快照 |
| ResultType | tinyint | 首期仅 `Succeeded=1` |
| Reason | nvarchar(1000) nullable | 取消/反向/异常放行等必填 |
| Summary | nvarchar(1000) | 人工可读结果摘要 |
| ChangedFieldsJson | nvarchar(max) nullable | 字段名、Before、After 白名单 |
| RelatedObjectsJson | nvarchar(max) nullable | 生成/影响的单据 Uid、类型、编号 |
| UserId / UserNameSnapshot | Uid/string | 操作者关系与快照 |
| ClientApp / ClientVersion | nvarchar | 调用客户端信息，可空 |
| OccurredDate | datetime2 | 业务成功时间 |
| CreatedDate | datetime2 | 持久化时间 |

建议唯一索引：`(Module, OperationType, CommandId)`；查询索引：OccurredDate、AggregateId、UserId、CorrelationId、AggregateNoSnapshot。

`ChangedFieldsJson` 采用稳定小型结构，如字段代码、旧值、新值和显示名。不得直接序列化循环对象或任意异常对象。JSON Schema 随 Contracts 版本维护。

## 7. 首期必须记录的操作

### 净需求

- 替代计划、应用产品当前默认供应商、批量分配供应商。
- 采购草稿创建、追加、取消和数量释放。

### 采购与跟单

- 草稿修改、确认、取消确认、关闭。
- 登记供应商进度；ReadyQty 下降纠错必须记录前后值和原因。

### 仓库与库存

- 创建/修改/停用供应商虚拟仓。
- 期初余额过账、反向。
- 每次库存正式过账可记录一个命令级主日志；逐行数量细节由 RelatedObjectsJson 和 InventoryLedgerEntry 承担。
- 负库存异常放行必须记录仓库、SKU、不足量、过账后余额、来源单和原因。

### 入库、出库、PackingList

- 草稿创建/修改可只记录有业务价值的保存结果，避免每次自动保存产生噪音。
- 正式过账、反过账、作废。
- PackingList 过账记录生成的入库单、出库单及库存流水范围。

## 8. Application 接口和用法

建议接口：

- `IBusinessOperationLogWriter.AppendAsync(BusinessOperationLogEntry entry, DbSession session)`：只在现有事务写入。
- `IBusinessOperationLogQueryService.SearchAsync`、`GetAsync`、`GetByCorrelationAsync`、`ExportAsync`。
- `IBusinessOperationLogFactory`：从 CurrentUser、CorrelationContext 和规范化命令构造公共字段。

禁止：

- 在 Controller 中直接插表。
- 业务服务提交事务后再异步“尽力写日志”。
- Writer 自己创建/提交事务。
- 用 AOP 自动记录所有 DTO 作为业务日志；关键 OperationType、摘要、原因和变更字段必须由业务命令显式决定。

典型顺序：业务服务开启事务 -> 执行业务与领域流水 -> Append 成功日志 -> Commit。若命令识别为 AlreadyApplied，查询并返回既有业务结果，不新增第二条日志。

## 9. OperationType 命名

使用稳定英文机器代码，前端通过字典显示中文，示例：

- `NetDemand.PlanReplaced`
- `PurchaseDraft.Created`
- `PurchaseOrder.Confirmed`
- `SupplierProgress.Reported`
- `Inbound.Posted`
- `Outbound.NegativeStockOverridden`
- `PackingList.Posted`
- `PackingList.Reversed`

已发布代码不改名；需要语义升级时新增代码并保留旧查询兼容。

## 10. Repository 与安全

- 新建专用 `IBusinessOperationLogRepository`，只提供 Insert、Search、Get，不提供 Update/Delete。
- 使用显式列和参数化 Dapper SQL；JSON 作为 nvarchar(max)，写入前限制字段数量和总长度。
- 默认查询受业务日志查看权限控制；导出需要单独权限。
- 普通业务用户只看自己有权访问的业务聚合日志，管理员可全局查询。
- 用户名是快照，不用于授权；授权使用当前 UserId/角色。
- 配置文件中的敏感连接信息属于现有安全风险，日志专项不得将其复制进文档、日志或测试快照。

## 11. HTTP/Refit 契约

只读基址 `/api/system/business-operation-logs`：

- `POST /search`
- `GET /{uid}`
- `GET /correlations/{correlationId}`
- `POST /export`

不提供 Create/Update/Delete 公共 API。日志写入只由 Application 内部接口完成。

Search DTO 支持：日期范围、Module、OperationType、AggregateType/Id/No、UserId/用户名、CorrelationId、CommandId 和关键词。关键词只搜索摘要/编号等有索引或受限字段，不对无限 JSON 做默认全表扫描。

## 12. WPF 日志工作台

在 Settings/系统管理下新增“业务操作日志”：

- 服务端分页和上述筛选。
- Grid 显示时间、模块、操作、业务单号、操作者、摘要和 CorrelationId。
- RightDrawer 展示变更字段 Before/After、相关对象链接和命令信息。
- 可从净需求、采购、入库、出库、PackingList Trace 精确打开已筛选的日志标签。
- 管理员可导出 XLSX；页面完全只读。
- 技术 Serilog 文件不在普通业务日志页面展示，异常排查仍走运维渠道。

## 13. 数据库与迁移

- 源码和迁移脚本中未发现可安全承载结构化业务审计的现有物理表；`FollowUpLog` 是供应商业务反馈，不得混作全局操作日志。
- 使用 009+ additive schema 新建 BusinessOperationLog 和索引，不修改历史 003–008。
- 这是本下游专项唯一预先确认需要新建的物理表；首期可以先实现最小写入字段和索引，完整查询/导出字段按实际调用方再扩展。
- 现有技术日志文件和审计字段不做历史回填。
- 旧系统没有可证明的结构化业务操作历史时不从文本日志猜测生成记录。
- postflight 检查唯一索引、字段长度、行数和测试命令幂等；共享库执行需用户当次授权。

## 14. 分阶段实施

### Phase 0：日志审计

- 核对 Serilog、异常 Middleware、CurrentUser、CorrelationId、AuditStampService 和所有目标业务命令事务边界。
- 建立 OperationType 清单和敏感字段黑名单。

### Phase 1：基础设施

- 实现 Correlation Middleware、Contracts、Core 模型、Repository、Writer/Factory 和迁移。
- 先接一个低风险业务命令验证同事务提交/回滚。

### Phase 2：模块接入

- 按净需求 -> 采购 -> 库存 -> 入库 -> 出库 -> PackingList 顺序接入。
- 每次接入要求成功、失败回滚和幂等测试。

### Phase 3：查询工作台

- 实现查询、Detail、业务页面跳转和 XLSX 导出。

## 15. 测试与验收

至少覆盖：

- 请求有/无外部 CorrelationId，响应和 Serilog 上下文一致。
- 业务成功与日志同事务提交；业务回滚时无成功日志。
- 幂等重试不重复日志；同 CommandId 不同内容仍由业务幂等层阻断。
- 用户、编号、原因、ChangedFields 和 RelatedObjects 内容正确。
- ReadyQty 下降、取消确认、反过账和负库存异常均有必需原因。
- 敏感字段黑名单不进入 JSON/摘要。
- 日志无 Update/Delete 路径；权限和导出权限生效。
- 从销售订单/采购/PackingList Trace 能定位同一 CorrelationId 的操作。

## 16. 明确不做

- 取代 Serilog、APM、数据库审计或安全 SIEM。
- 保存所有请求/响应正文、SQL 参数或异常堆栈到业务表。
- 通用可配置工作流审批和电子签名。
- 自动从旧文本日志猜测并回填业务历史。
