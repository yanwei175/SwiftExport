# 净需求数据表与拆解流向说明

## 1. 先说结论

当前 C# 业务名称和数据库物理表名并不完全相同，这是为了兼容已有数据库：

| C# 业务实体 | 中文职责 | 数据库物理表 |
|---|---|---|
| `GrossDemand` | 毛需求，保存销售订单、手工需求等原始业务需求 | `dbo.IndependentDemand` |
| `NetDemand` | 净需求，保存一次 BOM 拆解产生的需求事实 | `dbo.DependentDemand` |
| `NetDemandAllocation` | 净需求执行计划，保存采购/生产/外协、供应商、计划交期和送达目标 | `dbo.NetDemandAllocation` |
| `DemandExecutionLink` | 净需求计划与采购单行等下游执行事实的追溯关系 | `dbo.DemandExecutionLink` |

因此，“毛需求拆解进入净需求”不是只写一张表，而是在同一事务中完成三件事：

1. 将拆解得到的净需求行写入 `dbo.DependentDemand`。
2. 为每条净需求建立初始执行计划，写入 `dbo.NetDemandAllocation`。
3. 更新原毛需求所在的 `dbo.IndependentDemand`，标记拆解状态和修订号。

如果任何一步失败，整个事务回滚，不应出现只写净需求但没有计划的半成品状态。

## 2. 为什么净需求和 Allocation 分开

`NetDemand` 回答“需要什么”：

- 从哪条毛需求拆出来。
- 是根产品还是客供子件。
- SKU、物料类型、供货方式和 BOM 路径是什么。
- 数量和原始需求交期是多少。

`NetDemandAllocation` 回答“准备怎么执行”：

- 采购、生产还是外协。
- 计划数量和计划交期是多少。
- 采购供应商是谁。
- 客供件要送到哪个父件计划、哪个供应商。
- 供应商来自产品默认值、待分配还是人工修改。

净需求是拆解事实，计划可以调整。计划调整时不会覆盖历史，而是把旧 Allocation 标记为被替代，再新增下一修订记录。

## 3. 实际拆解写入顺序

```text
dbo.IndependentDemand（毛需求）
        │
        │ 锁定毛需求并校验 Version / DecompositionRevision
        ▼
GrossDemandDecompositionPlanner
        │
        ├─ 生成根产品 NetDemand
        └─ 如有客供件，生成客供子件 NetDemand，并指向根净需求
        │
        ▼
dbo.DependentDemand（净需求事实）
        │
        ▼
NetDemandInitialAllocationPlanner
        │
        ├─ 根据 Product.SupplyType 决定采购/生产/外协
        ├─ 根据 Product.DefaultSupplierId 建立初始采购供应商
        └─ 无有效默认供应商时生成“待分配供应商”计划
        │
        ▼
dbo.NetDemandAllocation（执行计划）
        │
        ▼
更新 dbo.IndependentDemand 的拆解状态和修订号
```

对应 Application 入口是 `GrossDemandWorkspaceService.DecomposeOneAsync`。实际写入顺序为：

```csharp
netDemandRepository.AddDecompositionAsync(...);
allocationRepository.AddInitialAsync(...);
grossDemandRepository.UpdateDecompositionStateAsync(...);
```

## 4. A 产品包含客供件 B 的示例

假设一条毛需求要求生产 10 个 A，A 的 BOM 中每个 A 需要 2 个客供件 B：

### `IndependentDemand`

- 1 条毛需求：A，数量 10。

### `DependentDemand`

- 第 1 行：根产品 A，净需求数量 10。
- 第 2 行：客供件 B，净需求数量 20。
- B 的 `ParentNetDemandId`、`RootNetDemandId` 和 `DeliveryTargetNetDemandId` 可以追到 A。

### `NetDemandAllocation`

- A 的计划：按 A 的供货方式和默认供应商建立。
- B 的计划：按 B 自己的默认供应商采购。
- B 的 `DeliveryTargetAllocationId` 指向 A 的计划。
- B 的送达目标供应商由 A 的活动计划供应商推导，不允许客户端随意填写。

## 5. 什么时候才写采购单和 Link

毛需求拆解时不会创建采购单，也不会创建 `DemandExecutionLink`。

用户在净需求工作台执行“转采购草稿”时：

1. Preview 只计算，不写数据库。
2. Create 成功后写入 `PurchaseOrderHead` 和 `PurchaseOrderLine`。
3. 同时写入 `DemandExecutionLink`，记录每条 Allocation 对采购行贡献了多少数量。

取消或减少安全采购草稿时，通过 `DemandExecutionLink.ReleasedQty` 释放数量，净需求剩余量由有效 Link 贡献计算，不直接修改一个含义模糊的“已执行数量”字段。

## 6. 阅读代码时只需抓住五个实体

1. `GrossDemand`：原始毛需求。
2. `NetDemand`：BOM 拆解事实。
3. `NetDemandAllocation`：当前执行计划及历史修订。
4. `DemandExecutionLink`：计划到下游单据行的数量追溯。
5. `NetDemandPurchaseDraftHead/Line`：净需求链路所需的最小采购草稿模型。

旧数据库表名 `IndependentDemand`、`DependentDemand` 只是兼容物理名称。业务代码中不要重新引入旧 `IndependentDemand/DependentDemand` Entity、Service、DTO、API 或 Repository。
