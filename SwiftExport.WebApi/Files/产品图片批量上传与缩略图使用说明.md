# 产品图片批量上传与缩略图使用说明

本模块提供实时 Admin 保护的产品图片批量上传 API。它把 JPEG、PNG、WebP 按实际内容解码后重新编码为 JPEG，同时生成最长边 256 像素的缩略图，并在缩略图 JPEG 的标准 COM 段内记录最终原图来源指纹。模块不查询产品、不写 `Product.MainImage`，也不改变通用文件 API 默认拒绝覆盖的语义。

## 依赖与许可

- `SkiaSharp` `4.152.1`。
- `SkiaSharp.NativeAssets.Win32` `4.152.1`，显式放在 WebAPI 可执行项目，Release 输出包含 `win-x64`、`win-x86`、`win-arm64` 的 `libSkiaSharp.dll`。
- SkiaSharp 由 Microsoft 维护并按 MIT License 发布。版本和平台信息以 [NuGet SkiaSharp.NativeAssets.Win32 4.152.1](https://www.nuget.org/packages/SkiaSharp.NativeAssets.Win32/4.152.1)、[官方包选择说明](https://github.com/mono/SkiaSharp/blob/main/documentation/dev/packages.md)及[官方 LICENSE](https://github.com/mono/SkiaSharp/blob/main/LICENSE.md)为准。

本实现没有使用 `System.Drawing.Common`，也未引入第三方文件存储框架。

## JSON 配置

### 本机开发测试

本机 `appsettings.Development.json` 已配置产品图片上传及独立的通用 `files` 容器，无需先部署服务器。

- 开发 WebAPI 和 WPF API 地址：`https://localhost:7286`，使用 WebAPI 的 `https` 启动配置（Development）。
- 本机存储根目录：`D:\Documents\source\CSharp\SwiftExport\.tmp\ERPFiles`。
- 原图目录：根目录下的 `ProductImages`；通用容器目录：根目录下的 `Uploads`。
- 两个目录须提前存在；`.tmp` 已由 Git 忽略，图片不提交入库。它是本机测试数据，清理 `.tmp` 会删除这些测试文件。
- 克隆到其他路径时修改本机 `RootPath` 及 `Containers:files:RootPath`，不要照搬其他电脑的绝对路径。
- 该配置只对 Development 生效，修改后重启 WebAPI；环境变量或用户机密中的同名配置可覆盖 JSON。

首次在新电脑准备目录（当前电脑已准备）：

```powershell
New-Item -ItemType Directory -Force -Path `
  "D:\Documents\source\CSharp\SwiftExport\.tmp\ERPFiles\ProductImages", `
  "D:\Documents\source\CSharp\SwiftExport\.tmp\ERPFiles\Uploads"
```

重启开发 WebAPI 后，以管理员账号在 WPF 中打开“更多功能 → 批量上传主图”，选择一张测试图片并上传。成功后访问 `https://localhost:7286/files/ProductImages/文件名.jpg`；缩略图地址为 `https://localhost:7286/files/ProductImages/Thumbnails/文件名.jpg`。此操作不会更新产品 `MainImage`。

### 服务器部署

开发配置不会替代服务器配置。部署时将下面的 `FileStorage` 节合并到服务器 `appsettings.Production.json`，保留原有数据库、JWT 等配置；根目录使用服务器的 `D:\ERPFiles`，地址使用 `https://192.168.3.12/`。如需通用容器，另外按[容器文件 API 使用说明](容器文件API使用说明.md)配置 `Containers`。

原先只读图片的 IIS 目录权限不足以支持上传：需为应用池授予下文列出的写入权限，随后重启应用。仅复制新程序或切换 WPF 地址不会自动打开上传开关。

以下内容只用于人工合并到目标环境，不能覆盖真实 JWT、连接字符串或服务器配置：

```json
{
  "FileStorage": {
    "Enabled": true,
    "RootPath": "D:\\ERPFiles",
    "ApiBaseUrl": "https://192.168.3.12/",
    "ProductImages": {
      "UploadEnabled": true,
      "DirectoryName": "ProductImages",
      "RequestPath": "/files/ProductImages",
      "MaxFileBytes": 10485760,
      "MaxBatchBytes": 26214400,
      "MaxFiles": 20,
      "MaxPixels": 24000000,
      "MaxConcurrentProcessing": 2
    }
  }
}
```

- `UploadEnabled` 缺失时默认为 `false`；升级程序不会自动开放写入口。
- 开启上传时 `Enabled` 也必须为 `true`，使成功结果中的公开地址实际可读。
- `DirectoryName` 必须是安全单目录段；同一个值驱动上传目标和静态读取目录。
- `RequestPath` 必须是固定绝对请求前缀；默认继续使用 `/files/ProductImages`。
- `ApiBaseUrl` 是客户端可达的 HTTP/HTTPS 部署基址，可包含虚拟路径，不采用请求中的 Host。
- `MaxFileBytes` 是单个文件节净字节上限；`MaxBatchBytes` 包含 multipart 边界和头部开销，且不得小于单文件上限。
- `MaxFiles`、`MaxPixels`、`MaxConcurrentProcessing` 必须为正值。原生解码和编码由进程级信号量限制，不会为每个请求无限创建任务；处理槽已满时不排队，当前文件节会被安全排空并返回逐项错误 `PRODUCT_IMAGE_PROCESSING_BUSY`，调用方可稍后重试该文件。

配置在启动时验证并形成快照，修改后必须重启。通用 `FileStorage:Containers` 仍禁止与产品图片目录或遗留保留目录 `.product-image-state` 重复、嵌套，不能借通用上传绕过图片规则。程序不再读写该遗留目录，但继续保留边界以防旧文件被公开或被通用容器占用。

## 目录与权限

部署管理员必须预先创建：

```text
D:\ERPFiles\
  ProductImages\
```

首次经授权发布时，模块会按需创建：

```text
D:\ERPFiles\
  .dvfilestorage-tmp\
  ProductImages\Thumbnails\
```

应用池身份需要对顶层存储临时目录、原图目录和 `Thumbnails` 拥有最小读写权限。公开静态入口只映射 `ProductImages`，不会映射整个根目录；DvFileStorage 临时文件无法通过该入口读取。

IIS `requestFiltering/requestLimits/maxAllowedContentLength`、反向代理和 ASP.NET 请求体限制必须允许至少 `MaxBatchBytes`。首期同一图片目录只支持单 IIS worker/单应用实例；进程内同名锁不能保护多个 worker、多个服务器或管理员直接覆盖文件。

## HTTP 调用

入口：

```http
POST /api/product-images/batch
Authorization: Bearer <token>
Content-Type: multipart/form-data; boundary=...
```

multipart 中只允许多个同名 `files` 文件字段，不接收路径、产品 ID、覆盖开关或部署目录。示例：

```bash
curl -X POST "https://192.168.3.12/api/product-images/batch" \
  -H "Authorization: Bearer <token>" \
  -F "files=@ABC123.png" \
  -F "files=@DEF456.webp"
```

```powershell
$headers = @{ Authorization = "Bearer <token>" }
$form = @{
    files = Get-Item "C:\Upload\ABC123.png"
}
Invoke-RestMethod -Method Post `
    -Uri "https://192.168.3.12/api/product-images/batch" `
    -Headers $headers `
    -Form $form
```

匿名和失效账号返回 `401`，活动普通用户返回 `403`，只有实时权限投影仍为 `Admin` 的账号可读取 multipart 主体并写入。令牌不要写入脚本库、日志或配置示例。

批次正常解析完成返回 `ServiceResult<ProductImageBatchUploadResultDto>`。整体 `Success=true` 只表示批次解析完成；调用方必须检查 `Succeeded`、`Failed` 和每个 `Items[i].Success`。转换后同名的后续项目返回 `DUPLICATE_TARGET_IN_BATCH`，前面已经完成的项目不会回滚。文件数或请求总量等导致无法继续解析的错误返回 `400`/`413`，此前成功项目仍可能已经生效。

## 命名与图片规格

- 输入文件名不能包含目录、盘符、ADS、Windows 保留设备名、控制字符、尾点或尾空格；服务不会用 `Path.GetFileName` 静默修正危险名称。
- 仅接受 `.jpg`、`.jpeg`、`.png`、`.webp`，扩展名必须与实际编码一致。
- 去除原扩展名后生成同名 `.jpg`，保持原有空格和大小写；Windows 下按大小写不敏感目标去重。
- 动画或多帧图片拒绝，不取第一帧。
- EXIF 方向转换为实际像素方向，透明像素铺白底，输出不保留源 EXIF/GPS。
- 原图按方向修正后的尺寸重新编码，JPEG 质量 90；缩略图最长边 256、等比且不放大小图，JPEG 质量 85。

成功项返回原图/缩略图公开 URL 以及对最终 JPEG 字节计算的两份 SHA-256。固定地址覆盖后使用者会立即看到新内容；既有静态入口继续使用 `no-cache` 重新验证。

## 缩略图来源指纹与发布边界

缩略图包含一个 JPEG 标准 COM 注释段，ASCII 内容固定为：

```text
SwiftExportThumbnail:v1
SourceSha256=<64位大写十六进制>
Spec=jpeg-v1;maxEdge=256;quality=85;noUpscale=1;whiteBackground=1;orientationNormalized=1
```

三行均以 LF 结尾。`SourceSha256` 针对服务端最终重新编码、实际发布的原图完整 JPEG 字节，不是用户上传源文件；原图不写该标签，避免自引用。API 的 `ThumbnailSha256` 针对插入 COM 后实际发布的缩略图完整字节。

该标签是确定性的自定义来源标记，不是数字签名，也不保证发现任意人为篡改。读取器只在 SOS 前按 JPEG marker 和大端段长解析头部；标签缺失、版本未知、重复、SHA 或规格非法时均视为“不能确认匹配”，不会靠全文搜索扫描压缩数据。

发布顺序为：

1. 完整解码并生成最终原图 JPEG、裸缩略图 JPEG；失败时不触碰旧图。
2. 计算最终原图 SHA-256，在缩略图首个 SOS 前插入 COM，得到最终缩略图。
3. 在同名进程锁内通过 DvFileStorage 先完整替换原图，再完整替换最终缩略图。
4. 两张均发布成功后才返回逐项成功和两份最终文件哈希。

两张文件不是一个文件系统事务。进程故障可能出现新原图与旧缩略图短暂混合；任何中途失败都不会返回逐项成功，也不会盲目删除已经生效的正式文件。重新上传同名图片可修复。

旧原图和旧缩略图继续由原地址读取；没有来源标签的旧缩略图只是在未来检查工具中被视为需要重建，本轮不会自动迁移、扫描或读取时重建。旧 `.product-image-state` JSON 不再读取或更新；升级完成且所有旧写入进程停止后，管理员可确认目录内容再人工删除，程序不会自动递归清理。

## 当前边界

- 本次来源指纹替换不修改现有 WPF 上传弹窗、文件选择、进度、Refit 签名或图片缓存行为。
- 产品表、`Product.MainImage`、产品 DTO 或数据库写入。
- StoredFile、删除/列表 API、断点或 ZIP 上传。
- 缩略图读取时重建、后台扫描、人工同步检查/补建工具。
- 多 worker/多实例分布式锁、跨双文件事务、版本化 URL。

真实 IIS、应用池 ACL、证书、反向代理、服务器磁盘、进程强杀和人工同步后的失配恢复仍需部署环境另行验收。本实现不会自动部署或修改服务器文件。
