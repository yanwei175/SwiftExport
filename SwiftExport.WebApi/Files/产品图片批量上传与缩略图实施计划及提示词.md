# 产品图片批量上传与缩略图实施计划及提示词

日期：2026-09-26。状态：已实施；配对机制现已按后续方案改为缩略图 JPEG COM 来源指纹。指定执行窗口：01a0dc40-ceff-7873-af01-7406fe888fb7。

## 一、已确认目标

只建设后端至 WebAPI 的产品图片批量上传能力：当前真实 Admin 上传，按文件名覆盖产品原图，同时生成缩略图并记录配对指纹。普通用户和匿名用户不能上传。只输出 API 和使用说明，不改 WPF，不做前端设计。

用户已确认：不做读取时检查重建、不做后台扫描。以后直接在服务器同步原图时，再做独立校验/补建工具；本轮只为该工具留可靠的元数据，不实现工具。

本模块负责图片处理，DvFileStorage 保持根目录实例＋相对路径＋Stream 的通用语义，不增加图片、容器、SKU 或 HTTP 依赖。

## 二、业务边界

- 输入是用户选择的命名图片，不查询产品是否存在，不从数据库查 SKU。
- 上传名称去除扩展名后对应目标 `<名称>.jpg`，不接受目录，不擅自截取恶意路径的文件名，也不自动去空格/改大小写导致撞名。
- 默认覆盖：图片服务调用 WriteAsync 时显式 overwrite=true；通用文件 API 和 DvFileStorage 的默认拒绝覆盖保持不变。
- 上传成功即生效，共享同名图片的使用者都会受到影响；不等待产品保存，不纳入 SQL 事务。
- Product.MainImage 将来只存实际文件名，如 ABC123.jpg，但本轮不写表、不迁移数据、不改 Product DTO/实体，也不实现产品保存接线。
- 不添加文件删除 API、StoredFile、业务临时附件、CommandId、数据库审计或产品逐项权限。

接受 JPEG、PNG、WebP，按实际内容验证并转为 JPEG；不得仅改扩展名。透明像素铺白底，处理 EXIF 朝向，输出不保留不必要的 EXIF/GPS。原图输出保持经旋转后的像素尺寸，不额外放大/缩小，重新编码 JPEG（初始质量 90）。缩略图最长边 256 像素、等比、不放大，JPEG 质量 85。多帧/动画图片明确拒绝，不悄悄取第一帧。以上是本轮约定规格，写入规格版本。

同一批转换后重名（例如 a.png 与 a.jpg，Windows 文件名大小写等价）不能让后一张悄悄覆盖前一张：后续重名项返回 DUPLICATE_TARGET_IN_BATCH，前项已经完成的结果保留，文档明确非整批原子性。

## 四、配置和公开目录

复用顶层 FileStorage 根目录与现有公开入口，产品图片专用配置仅加实际需要的选项。默认仍读取 `D:\ERPFiles\ProductImages`，默认 URL `/files/ProductImages`，不中断已部署地址。

合并示例（具体键名可按实现统一，但说明必须与代码一致）：

```json
{
  "FileStorage": {
    "Enabled": true,
    "RootPath": "D:\\ERPFiles",
    "ApiBaseUrl": "https://192.168.3.12/",
    "ProductImages": {
      "UploadEnabled": true,
      "DirectoryName": "ProductImages",
      "RequestPath": "/files/ProductImages",
      "MaxFileBytes": 10485760,
      "MaxBatchBytes": 26214400,
      "MaxFiles": 20,
      "MaxPixels": 24000000,
      "MaxConcurrentProcessing": 2
    }
  }
}
```

- UploadEnabled 缺失默认 false，不因为升级程序就开放新上传能力。启用需已有合法根目录/原图目录及可用访问配置；没有配置时旧只读入口可继续使用默认名称。
- DirectoryName 为合法单个目录段、RequestPath 为合法固定 HTTP 前缀，启动时验证；由同一个配置对象驱动上传目标、读取映射和通用容器冲突检查，不能只改上传路径导致读不到，也不能放宽通用上传边界。请求体里不能指定这些部署项。
- 缩略图固定为该图片目录下 `Thumbnails/<文件名>.jpg`，启用上传时模块自动创建所需子目录；根目录及原图目录继续由管理员准备。配置错误不回退到工作目录。
- 来源指纹内嵌在缩略图 JPEG COM 段，不再创建或更新独立 JSON。遗留 `.product-image-state` 目录继续作为内部保留路径，不能被公开图片目录或通用容器占用，但程序不做兼容读写。
- 临时文件和 `.dvfilestorage-tmp` 不得通过 jpg 扩展名伪装成可公开资源；不得公开整个根目录。读图只开放实际图片扩展名白名单。
- API 返回 URL 从已验证部署基址生成，不信任 Request.Host；虚拟路径和文件名 URI 编码正确。URL 可选用相同 ApiBaseUrl，不新增另一套硬编码 IP。
- 只修改示例/说明，不覆盖用户真实 JSON，不远程修改 ACL。说明需要原图、Thumbnails 及存储临时目录的最小写权限；原本 IIS 只读权限不足以上传。

## 五、HTTP 批量协议

新增 `POST /api/product-images/batch`，multipart/form-data，多项同名 `files` 文件字段。只上传内容和文件名，不接受任意目标路径、产品 ID 或客户端提供的真实磁盘位置。

认证及实时 Admin 校验先于读取主体、创建目录或写入。复用 FileAccessPolicy，不信任静态 JWT role。匿名/失效身份 401，非管理员 403。只使用测试替身查询权限，不接真实库。

通过 MultipartReader 顺序读取请求流，不使用整批 IFormFile 集合或 ReadFormAsync 默认缓冲。单张在限制内生成/暂存，整批不驻留内存；HTTP multipart 的顺序读取是传输要求，不是所有文件全局排队。不同请求/文件允许最多配置数量的图像处理并发，使用有界限流，不无限排队或创建无限多解码任务。

限制单张实际字节、请求总字节（含 multipart 开销）、文件数量、维度及解码像素数；未声明长度时同样有效，先读图像头再分配大像素缓冲。原生解码也要受全局处理并发限制。首期不允许断点上传或 ZIP 上传。

每张独立成功/失败，返回 `ServiceResult<ProductImageBatchUploadResultDto>`，整体成功表示批次正常解析完成，不表示每张都成功。结果含 Total/Succeeded/Failed 和按输入顺序的 Items；逐项含输入序号、原名称、安全目标名称、Success、错误码/短消息，成功项含原图/缩略图 URL 与指纹。若全部业务项失败，也正常返回批次结果，消费者检查计数。

无法继续解析的请求错误（非法 boundary、请求总量超限、文件数量超限等）返回对应 400/413；已完成项可能已生效，文档明确不回滚整批、不伪造未读取项结果。连接中断通常无法再返回完整结果，已完成文件不撤销。

单张损坏、类型拒绝、重复目标或超单张限制可在安全读完该节后继续；总量检查仍有效，无法安全排空就停止请求。模型和使用说明表达“批量允许部分成功”，不得使用数据库事务包装。

默认覆盖不在请求中留隐藏的 false 分支。只接受文件名、拒绝 `/`、`\`、盘符、ADS、保留设备名、尾点空格等非法输入，不能依赖 Path.GetFileName 将危险输入静默修正。

本轮仅需要 Contracts 结果类型，不为尚未开发的客户端新增 ViewModel 或强行设计 Refit 批量前端。使用说明提供 curl/PowerShell multipart 调用范例，令牌用占位符，不写入日志。

## 六、原图与缩略图来源指纹

缩略图 JPEG 的标准 COM 段保存固定 v1 协议：最终原图完整 JPEG 字节的 SHA-256，以及最长边 256、JPEG 质量 85、不放大、透明白底和方向规范化规格。原图不嵌入标签，避免自引用；API 的缩略图哈希对插入 COM 后的最终完整字节计算。

帮助类只遍历首个 SOS 前的 JPEG marker 和两字节大端段长，不扫描熵编码数据。标签缺失、未知版本、重复、非法 SHA 或规格时均不能确认匹配。标签是自定义来源标记而非数字签名。未来工具比较当前原图哈希与缩略图标签及规格，不匹配则重建；本轮不实现该工具。

## 七、完整发布、并发与失败

1. 验证并解码输入，生成最终原图、裸缩略图，计算原图 SHA-256 并插入缩略图 COM；全部成功后才开始替换正式文件。转码失败不触碰旧图。
2. 同一目标文件名的发布在当前进程内互斥，锁覆盖原图和缩略图；不同文件可并行。锁条目有清理策略，不随所有上传过的名字永久增长。Windows 名称比较一致，避免大小写绕过。
3. 在同名锁内通过 DvFileStorage 先完整发布原图，再完整发布带标签缩略图；两张均成功才返回 Success。
4. 任一发布失败不得返回 Success。可以重新上传相同目标修复，不用危险的盲目删除补偿去删另一请求的文件。
5. 这不是双文件事务：中途故障可能已替换原图、尚未替换缩略图，短暂读取也可能跨版本。明确告知用户和使用说明，不声称原子切换；本轮不引入版本 URL、数据库事务或复杂恢复平台。
6. 发布开始前取消不触碰正式图；发布开始后不要将已经成功发布的文件因晚到取消删除。库内部临时清理仍归库，不接管全局临时目录。
7. 首期按当前单 IIS worker 使用。同目录多进程/多实例发布及人工直接覆盖不受进程锁保护，不能宣称已支持跨进程一致性。部署说明要求此首期入口单 worker；如实际部署要求多 worker，先提出跨进程方案，不默默放任并发破坏配对。

人工同步原图后缩略图可能暂时过期，这是本轮明确取舍；不做每次 GET 校验，也不按上传接口不存在的事件假装已自动更新。校验工具以后单独实施。

- HTTP 401/403 零写入、Admin 正常处理、匿名 GET 图片沿用现有策略；不再产生 JSON，通用容器仍不能写公开图片或遗留状态目录。

不扩大到 WPF 或全量业务测试，不删除有效断言，不使用旧产物 no-build 验证。记录包版本、许可来源、文件清单、完整命令和未验证边界。提供后端 JSON、IIS 总请求大小/单 worker、文件权限及 multipart 调用说明，不自动部署、不改服务器配置、不写数据库。

### 已实现行为

- `POST /api/product-images/batch` 只接受多个 `files` 文件节；认证和实时 Admin 校验先于主体读取、目录创建及写入。
- JPEG、PNG、WebP 按实际编码验证，拒绝扩展名伪装及动画/多帧，修正 EXIF 方向、透明铺白，重新编码质量 90 的 JPEG，并生成最长边 256、质量 85、不放大的缩略图。
- 单文件、整批、文件数、像素和进程级原生处理并发均受限；处理槽满时不建立等待队列，排空当前节并返回 `PRODUCT_IMAGE_PROCESSING_BUSY`。
- 同批目标按 Windows 大小写语义去重；同名跨请求在当前进程内互斥，不同目标不使用全局发布锁。
- 缩略图 JPEG COM 保存最终原图 SHA-256 与固定生成规格；API 返回的缩略图哈希按带 COM 的最终字节计算。
- 在同名锁内先完整替换原图，再替换带标签缩略图；任何中途失败不返回成功、不盲删正式文件，可同名重传修复。
- 上传目标、公开读取和通用容器冲突检查共用 `DirectoryName`；启动阶段拒绝 `.dvfilestorage-tmp`、`.product-image-state` 等内部保留目录，避免公开或占用内部路径。
- 公开图片继续使用固定静态入口和 `no-cache`；不再读写状态 JSON，DvFileStorage 临时文件及顶层存储根目录不通过 HTTP 映射。
