# 架构文档缺口盘点（提炼 Skill 之前）

> **状态**：历史讨论记录。其中的业务决定（单位、成本、编号、退货、容差等）**不进入技术 Skill**，后续由业务文档治理任务按代码实际行为写入 `.agents/references`。本文仅供参考。

结论先行：现有两份文档（`Backend-Architecture-Guide.md`、`ReferenceDesign/`）覆盖了**一条单据写请求的骨架**：分层、授权、校验、事务、幂等、错误、日志、状态机、命名。
对一个外贸 ERP 而言，还缺三类内容：**横切业务规则**（金额、币种、单位、时间、编号）、**数据与运维**（迁移、部署、配置）、**非单据型功能**（导入导出、打印、文件、报表、下拉选择）。
另外，**现有代码到目标架构的迁移规则**没有写，Agent 会在新旧两套写法之间摇摆。

下面按优先级列出。证据列为本仓库快速检索结果（未深入阅读）。

---

## P0：不补就会让 Agent 写错数据的

| # | 缺口 | 为什么重要 | 现状证据 | 需要定的规则（建议） |
|---|---|---|---|---|
| 1 | **金额、数量精度与舍入** | 行金额、合计、汇率换算各处舍入方式不一致会对不上账 | 未见统一规定 | 数量 numeric(18,4)、单价 numeric(18,6)、金额 numeric(18,2)；只在“行金额”和“折算本币”两处舍入，`MidpointRounding.AwayFromZero`；合计 = 已舍入行金额之和；C# 只用 `decimal` |
| 2 | **币种与汇率** | 外贸业务核心；单据需记录交易币种与当时汇率，事后改汇率不能影响历史单据 | 有 `SysDicCurrencyExchangeService`、`sys_dic_currency` | 单据头：`currency_code`、`exchange_rate`（快照）、`amount`（原币）、`amount_base`（本币）；汇率取值时点（单据日期）与来源；汇率表只用于默认值 |
| 3 | **日期与时间** | `DateTime` 与 `timestamptz` 混用会出现差 8 小时 | `.sql` 中未见 `timestamptz`；只有 DvFileStorage 用 `DateTimeOffset` | 业务日期（单据日期、交期）：`date` ↔ `DateTime`（只取日期部分）；时间戳（创建、确认、过账）：`timestamptz` ↔ `DateTimeOffset`；服务器时区固定 Asia/Shanghai；禁止 `DateTime.Now` |
| 4 | **计量单位** | 采购单位与库存单位不同（箱/件）时数量错位 | 未找到换算逻辑 | 先明确业务：是否只有一个基本单位？若有换算，行上存 `unit`、`qty`、`base_unit`、`base_qty`、`conversion_rate` 快照，库存只按基本单位记账 |
| 5 | **单据编号** | 并发生成重复号、作废后是否断号 | 有 `DocumentNoService` | 规则：PostgreSQL 序列或 `UPDATE ... RETURNING` 计数表；允许断号（作废/删除不回收）；编号在**草稿创建时**生成还是**确认时**生成需决定 |
| 6 | **软删除与唯一约束** | 软删除后新建同编码会撞唯一约束 | 未见规定 | 唯一索引一律带 `WHERE is_deleted = false`（部分索引） |
| 7 | **数据库结构变更（迁移）** | 没有版本化迁移，Agent 改实体后不知道如何改库；多环境结构漂移 | 有散落的 `.sql` 与“Generated preview”，未见版本表 | 采用版本化 SQL 脚本 + 迁移表（DbUp，MIT）或手写 `schema_migrations` 表；一个脚本只增不改；Agent 只能**新增脚本**，不能直接改库 |
| 8 | **现有代码迁移规则** | 新旧写法并存期间，Agent 不知道该照哪个写 | — | 新功能一律按 ReferenceDesign；修改旧功能时“只修 Bug 不重构”或“整条用例迁移”二选一，禁止半迁移；旧组件清单与删除顺序 |

## P1：ERP 常见功能，缺了 Agent 会各自发明

| # | 缺口 | 建议的规则方向 |
|---|---|---|
| 9 | **上下游关联与追溯** | 统一“来源行引用”字段（`source_type`/`source_id`/`source_line_id`）；“下推生成下游单据”（采购单 → 入库单）的接口形状：`POST api/purchase-receipts/from-purchase-order` 返回**未保存的草稿 DTO**，用户编辑后再保存 |
| 10 | **部分执行与超量** | 部分收货/发货、超收容差（如 ±5%）、余量计算放在哪里（上游行 `received_qty` 维护 vs. 实时汇总） |
| 11 | **退货 / 红字单据** | 采购退货是独立单据（出库方向），还是负数入库？建议独立单据类型，引用原入库行 |
| 12 | **复制单据** | “复制为新单”只在客户端组装 Save 请求，后端无需专门接口 |
| 13 | **下拉/选择器查询** | 统一形状 `GET api/{资源}/lookup?keyword=&take=20` 返回 `{ Id, Code, Name }`，只返回启用数据；与分页查询分开 |
| 14 | **Excel 导入** | 两阶段：`POST .../import/validate`（返回逐行错误，不写库）→ `POST .../import`（全部成功才提交，一个事务）；行级错误模型 |
| 15 | **Excel 导出 / 打印 / 报表** | 当前未见 Excel 库引用（VSTO 端承担？）。需定：导出由后端生成文件还是客户端（VSTO/Web）生成；报表查询走只读 SQL、可设语句超时；大结果流式返回 |
| 16 | **附件** | 已有 DvFileStorage。规则：附件表 `(owner_type, owner_id, file_id)`；上传独立接口；单据删除时附件处理；权限跟随所属单据的 View/Edit |
| 17 | **期间关账 / 过账日期限制** | 未找到。小型 ERP 至少需要“某日期之前不允许过账/冲销”的系统参数，放在 StockService 统一检查 |
| 18 | **库存成本** | 未找到成本字段。需业务确认：只管数量，还是要移动平均成本？若要，流水需存 `unit_cost`、`amount`，冲销按原流水成本 |
| 19 | **批量操作** | “批量确认 N 张单”：逐张独立事务 + 返回逐张结果，还是全部成功才提交？建议逐张独立、每张独立幂等键 |

## 已确认的业务决定

| 问题 | 决定 | 对规则的影响 |
|---|---|---|
| 计量单位 | 只有一个基本单位 | #4 关闭：行上只存 `qty`，不做换算字段 |
| 库存成本 | 只管数量 | #18 关闭：库存流水不存成本 |
| 单据编号 | 草稿创建时生成 | 保存草稿（首次）时在同一事务内取号；允许断号 |
| 退货 | 独立退货单据 | 采购退货/销售退货为独立库存单据，行引用原入库/出库行，按 `source_line_id` 校验可退数量 |
| 迁移工具 | 引入 DbUp (MIT) | #7：脚本嵌入 Infrastructure，命名 `yyyyMMddHHmm_描述.sql`，只增不改，启动或独立命令执行 |

| Excel 导出 | 单据类由客户端（VSTO/WPF）导出；基础数据由服务器维护模板文件并生成导出 | #15：单据导出不新增后端文件接口，只提供查询 DTO；基础数据导出走服务器模板 |
| Excel 导入 | 平表导入 | #14：一行一条记录，先校验返回逐行错误，再整批一个事务提交 |
| 期间关账 | 不需要 | #17 关闭 |
| 超收/超发 | 允许，容差在系统设置中配置 | #10：过账时读系统设置的容差，超出容差拒绝；容差校验放在库存单据服务 |
文档已统一为 `command_receipt`；

## 仍待确认的业务问题（原清单已全部回答，下列已作废，仅保留编号参考）

1. 计量单位：是否存在采购单位 ≠ 库存单位？
2. 库存：只管数量，还是需要成本（移动平均）？
3. 单据编号：草稿创建时生成，还是确认/过账时生成？
4. 采购退货、销售退货：独立单据还是负数单据？
5. 是否需要期间关账（某日期前禁止过账）？
6. Excel 导入导出：后端生成文件，还是由 VSTO/Web 客户端处理？
7. 数据库迁移工具：引入 DbUp（MIT），还是手写迁移表？
8. 超收/超发是否允许容差？
