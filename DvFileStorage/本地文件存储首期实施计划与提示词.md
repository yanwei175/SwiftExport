## 3. 最小接口及固定语义

建议目录如下，按实际类型建立，不生成空壳：

```text
DvFileStorage/
├─ Abstractions/IFileStorage.cs
├─ Configuration/LocalFileStorageOptions.cs
├─ Local/LocalFileStorage.cs
├─ Models/StoredFileInfo.cs
└─ Exceptions/（仅必要的稳定错误类型）
```

建议签名（实现时可调整命名，不改变语义）：

```csharp
Task WriteAsync(string path, Stream source, bool overwrite = false,
    CancellationToken cancellationToken = default);
Task<Stream> OpenReadAsync(string path,
    CancellationToken cancellationToken = default);
Task<bool> ExistsAsync(string path,
    CancellationToken cancellationToken = default);
Task<StoredFileInfo?> GetInfoAsync(string path,
    CancellationToken cancellationToken = default);
Task DeleteIfExistsAsync(string path,
    CancellationToken cancellationToken = default);
```

- path 是根目录下的逻辑相对路径；不接受服务器绝对路径或 URL。合法的中文、空格等名称允许，库不重命名、不解析 SKU、不限制文件业务类型。
- 写入由调用方明确选择 overwrite，默认 false。不能用 Exists→Write 的先查后写作为排他保证；最终发布必须由文件系统操作保证拒绝覆盖。同一路径并发拒绝覆盖只能有一个成功；覆盖时不保证业务先后顺序，最后成功发布者生效，业务版本控制不在本库。
- WriteAsync 成功表示完整文件已经发布，不返回 ERP ServiceResult。源流从当前位置读取，不要求可 seek，不把大文件整体读进内存；源流所有权属于调用方，成功/失败/取消均不关闭它。
- OpenReadAsync 返回流由调用方释放，不存在抛 FileNotFoundException。尽可能允许持有旧读取流时发布新版本（本地 FileShare 策略），但遇到其他进程独占锁可明确失败，不先删除旧文件。
- ExistsAsync：文件不存在 false；GetInfoAsync：文件不存在 null。权限不足、I/O 故障不得伪装成不存在，不直接用吞异常的 File.Exists 实现全部判断。文件信息仅包含相对路径、长度和 UTC 修改时间，不泄漏物理根目录。
- DeleteIfExistsAsync 以“使目标文件不存在”为成功语义，不存在正常完成；不返回无法在本地并发场景可靠保证的“本次确实删除”布尔值。访问拒绝、占用等故障抛出；不删除目录、不递归删除、不清理父目录。调用方决定业务上如何呈现，不需要额外的缺失开关。
- 路径非法、目标已存在、文件缺失、权限/I/O 错误、取消要能区分，优先沿用标准异常；必要时仅为“目标存在”增加小型稳定异常。取消保持 OperationCanceledException，不包装成普通失败。
- 文件流字节操作不判断 MIME、不生成网址、不统计业务引用、不访问数据库。

## 4. 根目录与路径边界

LocalFileStorageOptions 只保留本轮需要的 RootPath 等配置，先不增加 Provider、Bucket 或热切换选项。

- RootPath 必须为已存在的绝对目录，构造/启动时校验，不默认为进程工作目录或应用发布目录；不自动创建根目录，避免错误配置悄悄写到错误位置。
- 配置快照在实例生命周期内保持不变，修改根目录需重启。类库不读取 JSON，宿主传入普通配置对象。
- 相对路径统一使用 `/`；首期拒绝反斜线、绝对路径、盘符、空段、`.`、`..`、Windows ADS 等绕过形式，不能仅用字符串 StartsWith 判定。Windows 比较考虑大小写，并按目录边界校验。
- 不进行 URL 解码，输入就是文件标识；不擅自 trim/替换字符造成两个名称碰撞。Windows 尾部点/空格、保留设备名等非稳定名称明确拒绝。
- 检查已有路径段及目标的符号链接/junction/reparse point，首期拒绝而非跟随到根外。根目录和子目录须由受控服务账户管理；记录检查与打开之间无法完全抵御有本机目录写权限者竞争替换的边界，不声称这是 OS 沙箱。
- 写入时可创建合法相对子目录，不在失败时递归删除目录。物理路径仅库内部使用。

## 5. 写入、取消与临时清理

由模块自动处理，调用方不需要 catch 后再调用清理：

1. 验证输入，创建模块专用临时文件。
2. 有限缓冲异步复制源流，支持取消；完成 flush 并关闭写入流。
3. 发布前检查取消，然后通过同卷的文件系统替换/移动发布；不能先删目标再复制。
4. 发布成功就返回成功；不要在成功后追加取消检查并回报取消，更不能误删新正式文件。
5. 写入或提交前失败/取消时，模块关闭自身流并尝试删除自己的临时文件，不能用已经取消的 token 跳过清理。原正式文件在发布前失败时保持原样。

使用根目录下保留的内部目录，例如 `.dvfilestorage-tmp`，随机文件名、独占创建，业务 API 不允许访问该保留路径。临时目录不位于 ProductImages 下，也不公开到 HTTP。确保本地同卷发布，不使用系统 TEMP 的跨卷复制作为替换。写入首次需要时再创建内部目录。

正常失败与取消清理必须测试。若清理本身因权限/占用失败，应保留原始异常原因，并以稳定的附加异常信息报告清理失败，不能吞掉或谎称已清理；不引入仅为此服务的日志框架。进程强杀/断电可能留下内部临时文件，本轮不实现后台扫描器，不宣称能即时清理。运维说明允许在停止所有使用该根目录的写入进程后人工清理该专用目录，禁止运行中按时间随意删除潜在活动写入。

这与“业务上传完成但尚未保存单据”的临时附件不同，后者不是库自动删除的对象。本库不承诺 SQL 事务、不承诺断电持久性或未来远程对象存储与 NTFS 完全相同；未来适配需要重新验证提交语义。

## 6. 本轮必须完成的宿主 JSON 接线

复用已有配置节，不让用户再维护另一套根目录：

```json
{
  "FileStorage": {
    "Enabled": true,
    "RootPath": "D:\\ERPFiles"
  }
}
```

Enabled 当前属于 ProductImageHosting 的 HTTP 读取开关，不将它改造成通用库是否允许文件操作的开关。类库只使用 RootPath。

在 WebApi/Files 下建立小型注册扩展，由组合根调用，并添加 WebApi→DvFileStorage 项目引用。宿主读取 RootPath：

- 未配置或为空：保持既有未启用环境可启动，不注册 IFileStorage，不使用任何默认根目录；如果旧图片入口 Enabled=true，继续由既有校验报告缺失配置。
- 显式配置非空：启动时完成根目录合法性、存在性及必要读取访问校验；非法值启动失败。使用配置快照注册线程安全的本地实例为 IFileStorage。
- Enabled=false 但 RootPath 有效仍可注册底层库；这样通用存储与图片公开入口不耦合。
- 启动校验不为测试写权限创建/删除探针文件，写权限在实际写操作报告；不能将读取校验成功称为可写验证。

更新服务器配置示例与项目说明，给出开发环境合并示例及实际初始化方式。当前服务器已有 RootPath，无需重新生成整份配置。不得自动调整服务器 ACL；说明调用方未来启用写入前需给应用池对选定目录及内部临时目录适当写权限，不授予整盘权限。

保留现有 ProductImageHosting，不让整个根目录暴露到 HTTP，也不要求静态图片读取改为通过 IFileStorage。没有业务消费者时不提前添加 Application/Core/Infrastructure 的引用。

## 7. 验证范围

新增独立 net10.0 MSTest 项目 DvFileStorage.Tests，仅引用类库，测试框架版本沿用仓库当前版本；不依赖 ERP。加入后端和总解决方案。宿主 JSON/DI 测试放已有 Application.Tests/Files，使用最小配置和 ServiceCollection，不启动数据库。

必须覆盖：

- 任意二进制流写读一致、空文件、非 seek 源流、源流所有权及读取流可释放。
- 默认拒绝覆盖且旧内容保留；显式覆盖成功；同键并发拒绝覆盖只有一个成功。
- 缺失读取/信息/存在检查/删除的约定；权限或 I/O 故障不伪装为缺失（按测试运行环境选可验证场景）。

- 两个实例隔离、重复读取、不全量缓冲；重点测可观察行为，不用源代码字符串断言。
- JSON 有效、缺失、不合法，Enabled 与底层注册独立；启动无需 DB，DI 获得正确根目录的实例。

运行类库测试、宿主 Files 定向测试及后端 Release 构建，避免 Debug DLL 被开发进程占用。不跑 WPF、库存或其他全量业务测试，不接真实库/服务器。构建和测试使用当前编译产物。实际命令在实施记录中填写，不用泛泛的“已验证”代替。

完成标准：通用 DLL 单独可构建；宿主配置实际生效；上述成功/失败/取消语义有测试；中文职责注释齐全；差异和空白检查通过；未验证 NAS、断电、实机写权限等边界如实说明。

- [MinIO .NET API](https://docs.min.io/aistor/developers/sdk/dotnet/api/)：流式对象操作与宿主业务分离。
