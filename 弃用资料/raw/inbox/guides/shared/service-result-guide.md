# Service Result Guide

## 适用场景

适用于 Application Service、Web API、客户端服务之间需要统一表达成功、失败、错误消息和数据返回的场景。

## 推荐做法

- 优先沿用项目已有返回模型，不随意引入新 Result 类型。
- Result 应清晰表达成功状态、错误码、错误消息和数据。
- 应区分业务失败、验证失败、系统异常和权限失败。
- UI 层展示消息前，应确认消息是否适合直接给用户看。
- API 层错误模型应与客户端解析方式一致。

## 禁止事项

- 禁止在同一项目中混用多套返回模型。
- 禁止用异常替代所有业务失败。
- 禁止把内部异常堆栈作为 Result 消息返回。
- 禁止 Result 中塞入 UI 控件状态。
- 禁止为了包装而包装，导致简单方法难以阅读。

## Codex 修改前检查清单

- 项目是否已有统一 Result、ProblemDetails、异常中间件或验证模型。
- 调用方期望异常还是返回失败对象。
- 错误消息是否面向用户、开发者还是日志。
- 是否影响 API 契约或 Refit 客户端。

## 常见错误

- 业务失败和系统异常混为一类。
- 返回模型字段名不统一。
- UI 直接展示技术异常。
- Controller 重复手写错误包装逻辑。
- Result 泛型层级过深，调用方难以使用。
