# 事务、锁与 Preview 规则

## 查询与 Preview

- 普通 Search、GetDetail、Lookup 默认不使用显式业务事务，不取得更新锁。
- 只有需要跨多次读取保持一致的专用查询才选择事务，并说明隔离级别、锁影响和超时风险。
- Preview 不创建正式绑定、回执、流水或资源预留。
- Preview Token 必须覆盖会影响正式执行的版本、日期、来源集合或计算依据；正式命令仍须重新读取和校验。

## 写命令

- 事务外读取只能用于发现候选锁集合或减少事务时长，不能作为最终提交依据。
- 进入事务后重新取得权威事实并复核版本、状态、数量、权限和唯一性。
- 对相同资源集合使用确定排序，避免调用路径不同导致锁顺序反转。
- 需要同时处理命令键、单据、来源、容量和库存时，模块必须记录自己的稳定锁顺序；公共执行器不猜测业务锁集合。
- 数据库唯一索引、检查约束和受控锁是最后防线，不能只靠先查询后写入。
- 禁止普通查询机械使用 `Serializable`；禁止为了避免思考而给全部命令复制同一隔离级别。

## 嵌套与失败

- 最外层 Application 用例负责事务提交。
- 被调用领域端口检测并使用现有 `DbSession.Transaction`，不得自行提交、释放或清空。
- 若内部端口失败，可标记或回滚当前事务，但必须让外层知道事务已失败，禁止继续提交部分结果。
- `finally` 必须释放本层创建的事务并清空 Session 引用；不得清理调用方拥有的事务。
- 死锁、触发器或连接错误可能已让事务失效，安全回滚失败只记日志，不覆盖原始异常类别。

## 反向命令

- 反向必须引用原正式事实，不靠删除或恢复草稿伪装。
- 正向与反向分别使用独立 CommandId，并保存原命令或原执行事实关系。
- 反向前重新验证原事实完整性、后续依赖、当前净额和权限。
- 不可变流水只追加反向记录，不更新或删除原记录。
