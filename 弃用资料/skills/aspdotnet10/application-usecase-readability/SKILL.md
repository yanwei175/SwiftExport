# 应用服务用例可读性整改

## 单一入口

从本 Skill 开始，按 [应用服务用例可读性整改工作流](../../../../.agents/workflows/应用服务用例可读性整改工作流.md) 执行。每个用例只维护一张整改卡，模板及物料需求示例见 [单用例整改卡](references/单用例整改卡.md)。无需先读完服务层全部盘点文档。

可以直接使用以下请求：

- “按应用服务用例可读性整改 Skill，解释物料需求建立的调用链。”
- “按这个 Skill，整改物料需求建立用例，保持业务行为、事务和接口兼容，完成验证。”
- “按这个 Skill，分批整改采购服务；先列范围和顺序，再实施已授权的批次。”

## 意图与范围

| 用户意图 | 执行动作 | 写入边界 |
| --- | --- | --- |
| 解释、盘点、审查 | 源码追踪，形成调用链和建议 | 默认只读；明确要求文档时才落盘 |
| 设计整改方案 | 给出整改卡、依赖影响和验证计划 | 只写已授权文档，不改业务代码 |
| 明确实施整改 | 按已授权用例实施并验证 | 必要的 Application 及其依赖层、DI、调用方与测试；不顺手整治邻近用例 |

一次处理一个明确用例或一个已划定的用例族。全层整改先排分批顺序，共享组件修改作为单独批次。调用本 Skill 不自动授权业务规则变更、数据库写入、部署、推送或委派任务。已有实施授权覆盖的必要联动修改继续完成，不逐文件重复询问。

## 可读性的目标

读者从公开入口能够找到一段按业务顺序排列的主线，并回答：先锁什么、检查什么、生成什么、写到哪里、谁提交、失败如何恢复。允许权限、验证、幂等和错误包装围绕主线，但应能从入口直接定位主线所在方法。

- 一个用例的业务步骤集中在一个主方法；局部校验、组装、日志使用清楚命名的私有方法。不要把所有细节塞进入口，也不要把每个步骤都拆成服务。
- 简单的仓储读写直接调用 Core 仓储接口。不要只为隔离 Infrastructure 再包一层转发服务：现有接口已经提供隔离。
- 纯计算可以保留 Planner/Policy；只在一个用例使用的短辅助逻辑优先私有方法。提取独立类型应有真实复用、独立复杂规则或可单独验证的价值，不能只凭行数决定。
- 共享业务服务必须承载真实重复的业务规则或完整协作职责。它参与父事务时须写清前置条件、读写事实和副作用；不能调用另一个独立用例入口以“顺便复用”其事务。
- 查询、命令、纯计算的类型职责要可辨认。会读取数据库的 Builder 不能描述成纯计算；服务间共用锁定事实时，评估提取明确的事实读取职责，避免命令依赖查询用例的内部方法。
- 用例主线应展示下游动作的业务意义。库存过账等完整共享能力内部可以调用多个仓储，不要求把其内部实现摊平到调用方。
- 文件与目录围绕实际职责组织；移动 partial 文件必须核对声明类型、命名空间和真实归属。减少跳转要靠消除无意义间接层，不能靠扩大接口或万能服务。

## 跨层修改判断

| 需要解决的问题 | 最小影响范围 | 必须核对 |
| --- | --- | --- |
| 主线被多层私有转发或委托淹没 | Application 目标服务、定向测试 | 调用顺序、异常映射、命令输入和结果不变 |
| 局部辅助服务合并/改名，或 partial 文件归位 | Application、其消费者、Application DI、相关测试 | 无其他消费者遗漏；公开契约是否真的需要变化 |
| 真正共享的业务规则重复 | Application 参与者及全部真实消费者 | 规则一致性、父事务参与约定，避免新增独立提交入口 |
| 仓储接口语义不清、读写边界需调整 | Core 接口、Infrastructure 实现、调用方、DI、所有测试替身 | 实际 SQL、Session.Transaction 传递、版本条件和锁行为 |
| 只是认为“确认涉及多个表” | 优先复用现有仓储，无需自动改 Infrastructure | 多仓储是否共享同一 scoped Session，是否统一提交 |
| SQL/锁/约束/隔离级别确有问题 | Infrastructure、必要契约、Application、数据库契约测试 | PostgreSQL 实证范围；建脚本不等于部署，源码测试不等于并发验收 |
| 改共享执行器或事务生命周期 | 公共组件及全部受影响消费者、DI、事务测试 | 单独实施；不能混入普通文件整理，必须覆盖失败阶段和清理 |
| 改公开 API/DTO | Contracts、Controller、Application、实际客户端/其他消费者 | 先确认是否必要；跨前后端未拆清时按路由由 Planner 拆解 |

修改仓储接口前，搜索其全部实现、调用方、DI 注册和测试替身；不能只改眼前的一个服务。Application 仍只依赖 Core 接口，Infrastructure 不反向引用 Application。

## 事务和协议保持条件

最外层用例拥有事务，仓储共享 Core `IDbSession`，参与服务不独立提交。采用 `BusinessCommandExecutor` 的命令应清楚表现为：准备/授权 → 执行器 → 业务主线 → 业务审计与回执 → 统一提交；事务前准备、回执重放和提交异常须按真实源码补充。

以上是所有权约束，不是要求所有用例改用同一种命令模板。先核实现有协议，再保持以下内容：

- `CommandId` / `CommandItemId`、指纹内容和排序、结果版本、回执重放、权限检查时机。
- `Version`、Preview 复核、锁集合及顺序、隔离级别、取消和错误码。
- 单次整批原子性或逐来源部分成功语义。部分成功不能在整理时变成整批统一事务。
- 下游单据、Link/贡献、库存、审计的创建与释放规则。确认不必然生成下游单据，取消确认不必然删除 Link，必须按当前用例事实解释。
- 普通查询与一致性查询的差别；文件系统副作用不宣称受数据库事务保障。

发现参与者自行回滚/清空父事务等现有偏差时，登记实际行为、规范要求、调用方防护和测试证据。不得仅为满足目标结构删除现有故障保护；改事务语义另列步骤，按已授权范围及业务规则清晰程度处理。

## 完成条件

- 整改卡能够独立解释入口、业务顺序、读写事实、基础设施映射、事务提交和失败路径。
- 每个修改文件都对应一个明确问题；接口与消费者迁移完整，没有留下只转发一次的空壳。
- 业务行为保持条件有相应证据，验证按实际风险选择；没有运行真实 PostgreSQL 测试就不宣称锁和数据库并发已验收。
- 更新同一张整改卡及必要职责级中文注释，检查实际 diff；不为每个步骤另建互相引用的报告。
