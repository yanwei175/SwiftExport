# 测试与验收总纲

本文定义 SwiftExport 开发任务完成后的验证方式，用来回答“这次改动怎么证明没有破坏项目、业务是否真的可用、哪些风险还需要人工确认”。

本文不要求当前立刻建立完整自动化测试体系。SwiftExport 是小团队内部 ERP，现阶段以构建检查、契约检查、静态检查和关键业务手工验收为主；后续再逐步补充自动化测试。

## 1. 验收总原则

每次任务结束时都要说明：

- 改了哪些文件。
- 是否修改业务代码。
- 运行了哪些构建、测试或检查。
- 哪些检查没有运行，以及原因。
- 是否需要人工业务验收。
- 是否存在连接字符串、编码、未提交改动、构建环境或数据迁移风险。

验证顺序优先为：

1. 静态范围检查：确认只改了任务相关文件。
2. 构建检查：按改动范围选择最小可靠构建。
3. 契约检查：涉及 API/DTO/Refit 时核对前后端路由和模型。
4. 手工业务验收：涉及 ERP 流程时跑关键业务场景。
5. 回归风险说明：列出未覆盖场景和需要用户确认的部分。

## 2. 解决方案构建矩阵

本仓库包含四个主要解决方案：

| 解决方案 | 作用 | 适用场景 |
| --- | --- | --- |
| `MateWpfThemes.FW.slnx` | WPF 主题/控件库 | 修改 MateWpfThemes 控件、主题、资源字典、附加属性时优先运行 |
| `SwiftExport-WebAPI.slnx` | 后端 WebApi 项目 | 修改 WebApi、Application、Core、Infrastructure、Contracts 后端契约时优先运行 |
| `SwiftExport-Frontend.slnx` | 前端 WPF/VSTO 相关项目 | 修改 `SwiftExport.View.FW`、`SwiftExport.VSTO`、前端 Contracts 调用时优先运行 |
| `SwiftExport.slnx` | 总项目，包含所有项目 | 跨前后端、主题库、VSTO 或发布前综合验证时运行 |

常用命令：

```powershell
dotnet build .\SwiftExport-WebAPI.slnx
msbuild .\SwiftExport-Frontend.slnx /p:Configuration=Debug /p:Platform=AnyCPU
msbuild .\MateWpfThemes.FW.slnx /p:Configuration=Debug /p:Platform=AnyCPU
msbuild .\SwiftExport.slnx /p:Configuration=Debug /p:Platform=AnyCPU
```

注意：

- WPF、VSTO、.NET Framework 项目完整构建依赖本机 Visual Studio / MSBuild / VSTO 工作负载。
- 后端目标框架和本机 SDK 版本会影响 `dotnet build`。
- 如果环境缺失导致无法运行构建，最终回复必须说明原因。

## 3. 按改动类型选择验证

纯 wiki / Markdown：

- 不运行构建。
- 检查链接目标存在。
- 检查 `wiki/index.md` 和 `wiki/log.md` 是否按规则更新。
- 确认没有修改业务代码。

后端业务代码：

- 优先运行 `dotnet build .\SwiftExport-WebAPI.slnx`。
- 涉及 SQL、Repository、DbSession、事务时检查 Dapper skill 和数据库脚本。
- 涉及业务流程时补充手工业务验收。

前端 WPF/VSTO：

- 优先运行 `msbuild .\SwiftExport-Frontend.slnx /p:Configuration=Debug /p:Platform=AnyCPU`。
- 涉及主题控件时追加 `msbuild .\MateWpfThemes.FW.slnx /p:Configuration=Debug /p:Platform=AnyCPU`。
- 跨前后端时运行总项目 `SwiftExport.slnx`，或说明为什么只运行局部构建。

Contracts / DTO / Refit：

- 检查 DTO 字段、Refit Interface、Controller 路由、HTTP 方法、返回包装是否一致。
- 前端依赖变更时检查 `DependencyInjection.Apis.cs` 注册。
- 同时改后端时运行后端构建；同时改前端调用时运行前端构建。

数据库 / SQL：

- 检查脚本是否幂等。
- 检查表、字段、索引、唯一约束、软删除、审计字段是否符合数据模型总纲。
- 如果未实际执行脚本，最终回复必须说明。

主题库：

- 修改 MateWpfThemes 控件或资源时运行 `MateWpfThemes.FW.slnx`。
- 影响 SwiftExport 页面时再运行 `SwiftExport-Frontend.slnx`。
- 全局资源修改必须说明影响范围。

## 4. API 契约验收

涉及 Controller、DTO、Refit、Swagger/OpenAPI 时至少检查：

- Controller 路由与 Refit 路由一致。
- HTTP 方法一致。
- Request / Response DTO 一致。
- 返回包装遵循项目既有 `ServiceResult` 或统一返回模型。
- 新增 API 已注册到前端 DI，或明确当前只定义契约不接前端。
- 不返回 Entity。
- 不把 UI 状态放进 DTO。
- 业务命令有明确接口，不藏在普通保存接口里。

涉及未来 BS 可消费性时检查：

- Swagger 能表达路由、请求体、响应体。
- DTO 字段名是业务语言，不暴露数据库细节。
- 错误消息和错误码可被非 WPF 客户端理解。

## 5. 前端页面验收

WPF 页面改动至少检查：

- 页面能通过 DI 创建。
- Refit API 已注册。
- 页面路由或打开入口可用。
- 加载、搜索、分页、刷新可用。
- 未保存变更在刷新、搜索、分页、关闭前有提示。
- 保存成功后行状态清理，`BaseLineModel` / `BaseListModel` 状态正确。
- 删除新增行和删除已持久化行行为正确。
- 命令按钮启用/禁用状态正确。
- Busy 状态防止重复提交。
- 错误提示不会静默吞掉关键异常。

可编辑 DataGrid 重点检查：

- 绑定前端 Model，不直接绑定 DTO。
- 行模型继承或复用 `BaseLineModel`。
- 集合模型继承或复用 `BaseListModel`。
- `IsChecked`、`IsSelected`、`IsExpanded` 等纯 UI 状态不触发脏数据。
- Excel 风格编辑、撤销、软验证和汇总行没有被破坏。

选择器和搜索控件重点检查：

- 新搜索选择场景优先使用 `SearchableTextBoxPlus`。
- 搜索关键字和选中显示值不混用。
- 选择器返回结果，调用方负责回填。

## 6. ERP 主流程手工验收

涉及销售、需求、采购、入库、出库、PackingList 的任务，应按影响范围选择以下场景。

销售订单：

- 新建销售订单并保存。
- 编辑待确认订单头字段和明细行。
- 确认订单后生成毛需求。
- 已确认订单禁止普通删除或越界编辑。
- 取消确认遵守状态机边界。

毛需求 / 净需求：

- 销售订单行到毛需求是一对一。
- 毛需求拆解生成多条净需求。
- BOM 拆解保留来源、父子关系、数量和物料类型。
- 客供件根据子物料 `MaterialType` 被识别。
- 重复拆解不会产生重复有效净需求。

净需求转采购：

- 净需求可按供应商、物料、交期等规则转采购。
- 多条净需求聚合到采购行时写入 `DemandExecutionLink`。
- 净需求展示执行数量、执行单号、剩余数量正确。
- 生产/外协暂未实现时，不误转采购。

采购 / 入库：

- 采购单保存、查询、详情加载正常。
- 待入库行能被选择。
- 入库过账生成正式入库单。
- 入库过账生成库存流水并更新库存余额。
- 入库后采购和需求执行进度正确回写。

出库 / PackingList：

- PackingList 保存和详情加载正常。
- PackingList 过账触发需要的自动入库和出库。
- 自动入库也必须生成正式入库单。
- 自动出库必须生成正式出库单。
- 客供件在父物料出货完成后按规则扣减供应商仓库存。
- 每个库存动作都有库存流水。

改单 / 反过账 / 红冲：

- 库存流水之前，允许按轻量改单机制回退未过账下游并重跑。
- 已产生库存流水后，不靠删除或普通编辑修正。
- 需要反过账或红冲的场景有明确命令和审计原因。

## 7. 数据验收

涉及数据模型、SQL、Repository、库存、状态回写时检查：

- 新表或新字段符合 `Uid`、`Version`、`IsDeleted`、审计字段规则。
- 业务编码可读且唯一约束合理。
- 单据行有 `LineNumber`。
- 软删除不影响有效查询。
- 库存流水只新增，不普通修改或删除。
- `DemandExecutionLink` 作为净需求执行追溯的权威来源。
- Repository 查询字段别名能正确映射 DTO。
- SQL 分页、排序字段和筛选条件安全。

## 8. 验收报告格式

最终回复建议包含：

- 修改范围：列出主要文件。
- 业务代码：说明是否修改。
- 构建/测试：列出运行的命令和结果。
- 手工验收：列出已验证场景。
- 未验证项：说明原因。
- 风险提示：连接字符串、编码、未提交改动、构建环境、数据迁移、兼容性。

如果只改文档，可简化为：

- 改了哪些 wiki 文档。
- 未修改业务代码。
- 未运行构建，原因是纯 Markdown。
- 已做链接和范围检查。

## 9. 当前测试体系现状

当前未发现独立 xUnit / NUnit / MSTest 自动化测试项目。后续如果引入自动化测试，应优先覆盖：

- Application Service 业务命令。
- 状态机和改单边界。
- Repository SQL 映射和分页查询。
- API 契约一致性。
- 前端 Model / BaseListModel 变更集。
- ERP 主流程关键闭环。

自动化测试缺失时，不代表可以省略验收；必须用构建检查和手工业务验收补足。
