# 数据模型总纲

本文是 SwiftExport 数据模型设计的总入口，用来统一后续数据库表、Core Entity、DTO、Repository、状态机和业务重构的建模原则。

本文只规定长期模型规则，不要求立即修改业务代码或数据库脚本。源码事实优先于本文；如果源码与本文冲突，先记录差异，再按具体任务逐步迁移。

## 1. 当前事实

当前新实体已经统一继承 `BaseEntity`：

- `Uid`：全链路唯一主键，使用 `Guid`。
- `Version`：乐观并发版本号。
- `IsDeleted`：软删除标记。
- `CreatedDate` / `CreatedBy`：创建审计字段。
- `UpdatedDate` / `UpdatedBy`：更新审计字段。

当前仍存在一些早期 SQL 脚本或历史表使用 `Id int identity`，例如早期 PackingList 和 SysUser 脚本。后续新设计统一使用 `Uid`；历史 `Id` 表按兼容迁移逐步处理，不在普通业务任务中顺手推翻。

当前项目已经倾向使用“`Uid` 精确关联 + 业务编码冗余”的模型：

- `CustomerProduct` 同时保存 `CustomerId` 和 `CustomerCode`。
- `IndependentDemand` / `DependentDemand` 保存 `SourceUid`、`SourceNo`、`SourceLineId`。
- `PurchaseOrderLine` 保存 `SourceType`、`SourceNo`。
- `PackingListLine` 保存 `SourceType`、`SourceNo`、`SourceLineId`、`DependentDemandId`、`PurchaseOrderLineId`。
- `DemandExecutionLink` 已用于承接净需求到采购、生产、外协等执行单据的关系。

## 2. 主键规则

新表统一使用 `Uid uniqueidentifier` 作为技术主键。

默认字段：

```text
Uid uniqueidentifier not null primary key
Version int not null default(1)
IsDeleted bit not null default(0)
CreatedDate datetime2 null
CreatedBy nvarchar(100) null
UpdatedDate datetime2 null
UpdatedBy nvarchar(100) null
```

规则：

- 新增 Entity 必须继承 `BaseEntity`，除非它是明确的只读投影或数据库视图模型。
- 新增业务表不再使用 `Id int identity` 作为主键。
- 旧表如已有 `Id`，可以临时兼容；迁移时优先补 `Uid`，再逐步让业务代码转向 `Uid`。
- 外部 API、DTO、前端选中行和命令入参优先使用 `Uid`。
- 不要把业务单号当作技术主键。

## 3. 业务键规则

业务键用于人工查账、业务唯一性和跨系统沟通。技术关联用 `Uid`，人工追溯用业务键。

主数据业务键：

| 模块 | 业务键 | 说明 |
| --- | --- | --- |
| 产品 | `Sku` | 产品、配件、客供件的核心业务编码 |
| 客户 | `CustomerCode` | 客户编码 |
| 供应商 | `SupplierCode` | 供应商编码 |
| 仓库 | `WhseCode` | 仓库编码 |
| BOM | `BomNo + BomVersion + LineNumber` | BOM 明细行唯一定位 |

单据业务键：

| 单据 | 业务键 |
| --- | --- |
| 销售订单 | `OrderNo` |
| 采购单 | `OrderNo` |
| 入库单 | `ReceiveNo` |
| 出库单 | `OutboundNo` |
| PackingList | `PackingListNo` |

规则：

- 业务编码应唯一且可读。
- 业务编码不应随意修改；确需修改时，后续应设计编码变更或别名策略。
- 唯一索引应过滤软删除数据，例如 `WHERE IsDeleted = 0`。
- 单据号由单号服务生成，避免手工随意输入导致重复。
- 用户自定义编号可以存在，但不能替代系统业务主键。

## 4. 关系建模规则

SwiftExport 默认采用“弱外键 + 索引 + Application Service 校验”。

弱外键策略：

- 数据库侧不大面积强制跨模块外键。
- 通过索引、唯一约束和 Application Service 校验保证业务一致性。
- 适合当前快速重构、改单、回退、反过账和历史数据兼容场景。

可考虑强父子关系的场景：

- 单据头与单据行，例如 `SalesOrderHeader -> SalesOrderLine`。
- 入库头与入库行，例如 `ReceiveHead -> ReceiveLine`。
- 出库头与出库行，例如 `OutboundHead -> OutboundLine`。
- PackingList 头与行。

即使增加数据库外键，也应先确认历史数据是否干净，以及回退、删除、软删除是否会被外键阻塞。

## 5. 来源追溯字段

所有从上游业务生成的下游记录，应尽量保留统一来源字段。

推荐字段：

```text
SourceType
SourceUid
SourceNo
SourceLineId
```

含义：

- `SourceType`：来源单据类型，例如销售订单、手工需求、投诉补货。
- `SourceUid`：来源单据头或来源对象 `Uid`。
- `SourceNo`：来源业务单号。
- `SourceLineId`：来源行 `Uid`。

规则：

- `Uid` 用于精确关联。
- `SourceNo` 用于列表查询、人工查账和报表。
- 同一业务链路不要混用多个含义相同的字段名。
- 如果来源可能不是单据，也仍然保留 `SourceType` 和 `SourceNo`，避免投诉补货、手工需求形成孤岛。

## 6. 目标执行字段

当一个需求行生成采购、生产、外协、入库、出库等执行单据时，应保留统一目标字段。

推荐字段：

```text
TargetType
TargetHeadId
TargetNo
TargetLineId
```

含义：

- `TargetType`：目标执行单类型，例如采购单、生产单、外协单。
- `TargetHeadId`：目标单据头 `Uid`。
- `TargetNo`：目标业务单号。
- `TargetLineId`：目标单据行 `Uid`。

规则：

- 简单一对一关系可以直接保留在实体上。
- 净需求到采购行这类多对一、多对多关系，必须使用 `DemandExecutionLink` 作为权威追溯。
- `DependentDemand.TargetNo` 和 `TargetLineId` 可以保留为快速入口，但不应作为唯一事实来源。

## 7. DemandExecutionLink 规则

`DemandExecutionLink` 是净需求到执行单据的主链路表。

职责：

- 承接 `DependentDemand` 到采购、生产、外协等执行单据的关系。
- 支持多个净需求聚合成一条采购行。
- 支持一个净需求未来拆分成多个执行单据。
- 回写执行数量、入库数量、完工数量和关闭状态。
- 为改单、回退、反过账、红冲提供追溯依据。

建议长期字段：

```text
DependentDemandId
IndependentDemandId
SourceType
SourceUid
SourceNo
SourceLineId
TargetType
TargetHeadId
TargetNo
TargetLineId
RequiredQty
ExecutedQty
ReceivedQty
ReadyQty
PostedInQty
PostedOutQty
IsClosed
Remark
```

规则：

- 转采购时必须写入或维护 `DemandExecutionLink`。
- 入库、出库和 PackingList 回写需求时，应优先通过 `DemandExecutionLink` 找到相关净需求。
- 不要只靠采购行的 `SourceNo` 反推需求关系。

## 8. 单据头行规则

所有单据行必须有 `LineNumber`。

原因：

- 保持人工核对顺序。
- 支持 Excel 导入导出。
- 支持前端 DataGrid 稳定排序。
- 支持改单时比较旧行和新行。
- 支持打印、报表和外贸单据展示。

规则：

- 行号只表达显示顺序，不作为技术主键。
- 删除行后是否重排，由具体业务决定；但保存时必须保持唯一、稳定。
- 单据头保存汇总字段时，应以当前有效行重新计算。
- 单据行应保留头表 `Uid` 和头表业务单号冗余，例如 `PurchaseOrderId + OrderNo`。

## 9. 软删除规则

主数据和业务单据默认软删除。

规则：

- 查询默认过滤 `IsDeleted = 0`。
- 唯一索引默认过滤 `IsDeleted = 0`。
- 未确认、未过账、无后续引用的数据可按业务允许删除；实现上优先软删除。
- 已确认但未产生库存流水的数据，应先取消确认或回退，再删除。
- 已过账或产生库存流水的数据不能删除，只能关闭、作废、反过账或红冲。
- 库存流水永不删除。

草稿硬删除不是默认策略。只有在某个模块明确需要清理临时草稿，并且无任何下游引用时，才可单独设计。

## 10. 审计与并发规则

审计字段来自 `BaseEntity`。

规则：

- 新增时写入 `CreatedDate`、`CreatedBy`。
- 更新时写入 `UpdatedDate`、`UpdatedBy`。
- `Version` 用于乐观并发控制。
- 更新业务表时应尽量带 `Uid + Version`，并在命中失败时提示并发冲突。
- 过账、反过账、红冲等关键命令还应记录业务操作人和业务时间。

禁止：

- Controller 手工打审计字段。
- 前端传入审计字段并覆盖后端事实。
- 静默吞掉并发冲突。

## 11. 库存模型规则

库存模型分为当前余额和库存流水。

`Inventory`：

- 保存当前库存余额。
- 按仓库、库位、SKU 聚合。
- 适合快速查询当前可用库存。

`InventoryTransaction`：

- 保存每一笔库存变动。
- 只新增，不修改，不删除。
- 错误通过反向流水或红字流水修正。
- 是库存审计、对账、反过账、红冲的依据。

推荐长期字段：

```text
PostingBatchNo
SourceDocType
SourceHeadId
SourceLineId
SourceNo
WhseCode
LocationCode
Sku
BizType
BizNo
BizLineId
InQty
OutQty
ChangeQty
PostQty
ReverseOfTransactionId
IsReversal
IsRed
Reason
```

规则：

- 入库必须生成入库单和库存流水。
- 出库必须生成出库单和库存流水。
- PackingList 自动入库/出库也必须生成正式单据和库存流水。
- 库存余额可以被更新，库存流水不能被更新。

## 12. 仓库与供应商虚拟仓

仓库主数据使用 `Warehouse`。

当前供应商虚拟仓可采用：

```text
WhseCode = V_WH
LocationCode = SupplierCode
```

规则：

- `WhseCode` 表示仓库。
- `LocationCode` 表示库位；在虚拟仓场景下可保存供应商编码。
- 客供件入到供应商仓库时，应明确目标 `WhseCode` 和 `LocationCode`。
- 后续如果供应商仓库模型变复杂，可以新增库位表或供应商仓库关系表，不要把复杂逻辑塞进库存流水备注。

## 13. BOM 与产品模型规则

产品使用 `Sku` 作为业务键。

BOM 推荐业务键：

```text
BomNo + BomVersion + LineNumber
```

规则：

- `Product.SupplyType` 只表示采购、生产、外协，不表示是否有 BOM。
- 是否有 BOM 由 `BomVersion`、`BomNo` 和 BOM 明细决定。
- BOM 明细保留父项和子项的 `Uid` 与 `Sku`，兼顾准确关联和人工查账。
- 客供件由子物料 `MaterialType = 客供件` 判断，不写死供应商角色。
- BOM 拆解后，净需求应保留父项、子项、BOM 层级和来源关系。

## 14. 迁移脚本规则

数据库变更优先通过幂等 SQL 脚本处理。

规则：

- 脚本放在 `tools/sql/**` 或当前约定的迁移目录。
- 新增表前检查 `OBJECT_ID`。
- 新增字段前检查 `COL_LENGTH`。
- 新增索引前检查 `sys.indexes`。
- 不在一个普通任务里自动删除历史表。
- 涉及历史 `Id` 到 `Uid` 迁移时，必须单独设计数据迁移方案。
- 改表前说明 API、DTO、Repository、前端和历史数据影响。

## 15. DTO / Entity / ReadModel 边界

Entity：

- 对应核心业务表。
- 放在 `SwiftExport.Core/Entities/**`。
- 不承载前端 UI 状态。

DTO：

- 用于前后端传输。
- 放在 `SwiftExport.Contracts/DTOs/**`。
- 可以为具体页面和命令设计，不要求与 Entity 一一对应。

ReadModel：

- 用于后端只读查询或聚合查询。
- 放在 `SwiftExport.Core/ReadModels/**`。
- 不反向作为写入模型。

规则：

- 前端的 `IsSelected`、`IsDirty`、展开状态、弹窗状态不要写入业务表。
- 查询展示字段不一定要污染 Entity，可以使用 DTO 或 ReadModel。
- 命令 DTO 应表达业务动作，而不是直接暴露整张表。

## 16. 当前默认决策

本项目当前采用以下默认决策：

| 主题 | 默认决策 |
| --- | --- |
| 文件命名 | 总纲级 wiki 文档使用中文文件名 |
| 技术主键 | 新表统一使用 `Uid` |
| 历史表 | 兼容迁移，不在普通任务中顺手推翻 |
| 外键策略 | 弱外键 + 索引 + Application Service 校验 |
| 业务键 | 唯一且可读，不随意修改 |
| 删除策略 | 主数据和业务单据默认软删除 |
| 库存流水 | 只新增，不修改，不删除 |
| 需求执行追溯 | `DemandExecutionLink` 是权威链路表 |
| 单据行 | 必须有 `LineNumber` |

## 17. 后续待细化

以下内容后续可作为专题继续完善：

1. 编码变更策略：如果 `Sku`、客户编码、供应商编码确实需要修改，如何保留历史映射。
2. 强父子外键策略：哪些头行关系值得加数据库外键。
3. 库存可用量模型：当前库存、预占、在途、可用量如何拆表。
4. 批次、箱号、柜号模型：PackingList 和库存是否需要批次维度。
5. 投诉补货来源模型：投诉单如何进入毛需求并追溯到原客户订单。
6. 历史 `Id` 表迁移计划：旧 PackingList、SysUser 等表如何逐步统一到 `Uid`。
