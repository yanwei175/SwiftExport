# 应用服务用例可读性整改工作流

## 入口与职责

技术决策入口：[应用服务用例可读性整改 Skill](../../.codex/skills/aspdotnet10/application-usecase-readability/SKILL.md)。本工作流组织执行步骤，不另设业务规则。

明确实施服务整改时，主 Agent 为 Backend，基础门禁沿用 [后端 API 工作流](后端API工作流.md)，本流程作为专项实施顺序。只审查由 Reviewer 执行，只设计方案由 Planner 执行；建立或修改本 Skill/工作流由 Architecture Governor 执行。角色选择不授予额外写入或委派权限。

## 执行步骤

1. **确定一个整改单元。** 写明目标入口及用户授权是解释、方案还是实施。检查目标 Git 状态并保护原有改动；整层请求先排批次，每批明确目标与共享依赖。已经授权实施且范围清晰时自主推进。
2. **从真实调用方向下追踪。** 读 Controller/直接调用方 → Application 接口与入口 → 公共命令包装 → 业务主方法 → 私有辅助/共享参与者 → Core 仓储接口 → Infrastructure DI 对应实现 → 实际 SQL 与 Session 使用。按需读取既有 Skill、能力地图和测试；不凭文件名判断职责，不遗漏 partial 声明和内部方法消费者。
3. **填写同一张整改卡的现状。** 使用 Skill 内模板。按业务顺序记录“调用的方法、读/写事实、实际实现、事务角色”，同时标记纯计算和事务外准备。指出事务创建、共享、提交、回滚、释放位置；业务主线与异常/重放分支分别写清。下游生成要说明在哪个动作发生、插入哪些单据与 Link、如何回退，不能按用户的假设补写项目行为。
4. **定位读不懂的具体原因。** 把每个问题对应到源文件和方法：无意义转发、主线跨文件、重复业务规则、命令依赖查询内部方法、职责名与数据库行为不符等。可读性问题与正确性故障分别定级；P0 要有影响及可复现证据，不能因为文件多或存在规范偏差直接判 P0。
5. **划定改动依赖。** 按 Skill 的跨层矩阵列出每个文件“为什么改、怎么改、谁受影响、怎么验证”。区分已确认实施与后续建议。涉及 Core 接口时穷尽实现、DI、消费者与替身；涉及公共命令/Session 时扩大到全部受影响用例。仅局部整理不自动改仓储或公开 DTO。
6. **写出目标主线和保持条件。** 用业务步骤或短伪代码说明目标，明确事务所有者和各参与者。优先服务内私有方法及现有仓储；只有规则重复或独立职责有价值时保留/提取共享服务。保留命令协议、锁与隔离、权限、版本、下游事实和部分成功语义。业务含义不清时只暂停依赖该决策的实现，继续不依赖该决策的核对；既有授权覆盖的机械调整不额外索要批准。
7. **按依赖小步实施。** 只读/方案请求不进入此步。若仓储契约确需变化，先同步接口、实现、替身和注册，再迁移 Application 消费者；简单主线整理直接修改目标服务。先迁移真实调用方，再删除不再使用的旧辅助类型/注册。不要为重构建立长期双入口或兼容框架；用户已有改动不得回退。将公共事务行为整改与普通主线整理分开验证。
8. **验证行为与阅读效果。** 根据后端质量门禁运行最小相关测试及构建；跨公共组件时扩大回归。无代码改动只核对事实、引用和 diff。对变更后的入口再次向下追踪，确认一段主线即可看出主要业务步骤，每个参与者职责清楚。将实际命令、结果与未验证项写回整改卡。
9. **完成交付。** 更新同一张卡，列出修改文件、业务行为是否变化、事务所有者、验证结果和剩余问题。只有目标用例完成并验证，才进入已授权的下一批；未授权的后续事项保留为建议。不得把源码可编译、离线测试通过或历史数据库报告描述为当前运行库验收。

## 定向验证选择

| 本批改动 | 核心证据 |
| --- | --- |
| 解释/文档/Skill | 源码及引用核对、结构校验、diff；不运行业务构建 |
| 文件移动、私有方法整理 | 受影响构建与已有定向测试；检查声明、命名空间、调用顺序及 DI |
| 命令主线或共享参与者迁移 | 成功、版本冲突、幂等重放/冲突、权限拒绝、中途失败回滚、取消及 Session 清理 |
| 下游单据与 Link 编排 | 原子单元、贡献守恒、回退语义、重复请求；逐来源部分成功须独立覆盖 |
| 共享事务/库存组件 | 受影响消费者回归、每个失败阶段、零部分提交、守恒及清理；不能只有成功路径 |
| 仓储 SQL、锁或约束 | SQL 契约；涉及数据库特性时安排明确实例、库名和写入范围的 PostgreSQL 定向验证 |

具体测试选择以既有后端质量 Skill 为准。数据库检查默认只读；需要写入测试但缺少范围授权时，完成其他可执行验证并报告剩余缺口，不自行初始化、清库或部署。

## 使用顺序

优先以物料需求建立验证这种整理方式，再处理依赖交叉较多的采购草稿创建/预览、箱单过账。共享执行器与事务清理独立成批，不从最复杂的公共组件开始改。该顺序是选择建议，不是自动启动这些整改的授权。
