# SwiftExport 入库工作台冻结版工程任务书

## 1. Codex 新任务启动提示词

> 请先完整读取本任务书和同目录《库存履约下游专项总索引》《供应商虚拟仓与库存冻结版工程任务书》《采购与供应商跟单工作台冻结版工程任务书》，再读取净需求说明、根目录 `AGENTS.md`、路由、workflow/skill 和真实源码。旧 `Receive/PurchaseReceive` C# Entity、DTO、API、Service、Repository 已清理，不得复活；新 `InboundDocument` 专用模型优先映射现有 `PurchaseReceiveHead/Line` 物理表。新入库必须调用统一库存过账服务，不得直接修改库存余额。先做只读审计和决策完整计划；默认不执行共享数据库迁移。

## 2. 业务目标

入库工作台记录“某种货物在某个供应商虚拟仓被正式收货”的事实。首期支持：

- 采购入库：供应商采购货物到达指定供应商虚拟仓。
- 客供件手工入库：跟单人员确认客供件已到达父件生产供应商后手工收货。
- PackingList 自动入库：本次装柜成品尚未手工入库时，由 PackingList 提交并过账自动补足。
- 反过账：在没有破坏后续事实时，用反向单据纠正错误入库。

“供应商已备好”不是入库来源事实；它可以帮助跟单人员填写，但不能自动过账。

## 3. 已冻结业务规则

- 入库单保存为草稿时不改变库存；只有“提交并过账”成功后才增加库存。
- 一个入库头可包含多行，但所有行必须属于同一目标 WarehouseSite。
- 一条入库行只绑定一个可证明的执行来源贡献。多个净需求、采购行或销售行不得压成无法拆分的一条来源关系。
- 采购入库必须关联活动且已确认的采购行，并保留对应 `DemandExecutionLink`/Allocation 来源。
- 客供件允许购买供应商 A 与收货仓供应商 B 不同；B 是父件 A Allocation 的执行供应商虚拟仓。
- 客供件手工入库必须从净需求拆解快照或采购 Link 选择来源，禁止仅输入 SKU 和数量后丢失需求关系。
- PackingList 自动入库数量只补本次将发货成品在目标执行链路上的未入库缺口，不使用全局 SKU OnHandQty 猜测。
- 正常累计入库不得超过采购行或执行 Link 的有效数量。确有超收业务时首期阻断，不做容差。
- 已过账入库单不可普通编辑、删除或作废；纠错使用反过账。
- 反过账会生成相反库存流水并把原单标记 Reversed，不删除原单/流水。
- 如果反过账会导致后续已过账出库没有足够来源数量，必须先反向后续单据；首期不提供越权穿透反过账。

## 4. 入库类型

冻结 `InboundDocumentType`：

- `PurchaseReceipt=10`
- `CustomerSuppliedReceipt=11`
- `PackingListAutoReceipt=12`
- `OpeningBalance=100` 仅由库存专项内部使用，不进入普通入库工作台。

冻结 `PostingStatus`：`Unposted=0, Posted=1, Reversed=8`。生命周期沿用 `Active=0, Closed=8, Voided=9`；草稿为 Active + Unposted。

## 5. 业务流程

### 5.1 采购入库

1. 用户选择已确认采购单/行，系统展示供应商、目标虚拟仓、采购量、已入库量、可入库剩余量和需求来源。
2. 用户填写本次数量、收货日期和备注；`0 < Qty <= RemainingReceivableQty`。
3. 保存草稿只建立入库单。
4. 过账时重新锁定采购头行、Link、入库来源范围和库存余额。
5. 成功后写入入库事实、库存余额、不可变流水和业务日志，同一事务提交。

### 5.2 客供件手工入库

1. 从净需求/采购来源选择客供件 B Allocation。
2. 系统只读计算收货目标为父件 A 的当前执行供应商虚拟仓；用户不得自由改成无关仓库。
3. 展示来源销售单、父件、客供件 SKU、应供数量、已入库量和剩余量。
4. 跟单人员登记本次实际收货并过账。

### 5.3 PackingList 自动入库

- 仅由 PackingList Application Service 内部调用，不提供人工伪造“自动入库”的公共入口。
- 每个自动入库行必须记录 PackingList 行、需求贡献、执行供应商仓和计算快照。
- PackingList 整体事务失败时，自动入库和所有库存变化全部回滚。

### 5.4 反过账

1. Reverse Preview 列出原库存流水、预计反向后的余额及下游阻断。
2. 用户提交 ExpectedVersion、CommandId 和原因。
3. 锁定原单、来源、相关下游出库和库存键。
4. 生成反向入库单/反向流水，原单 PostingStatus=Reversed。

## 6. 目标数据模型与现有表映射

- `InboundDocument` 映射 `dbo.PurchaseReceiveHead`。
- `InboundDocumentLine` 映射 `dbo.PurchaseReceiveLine`。
- 复用 ReceiveNo、PoNo/OrderNo、SupplierCode、ReceiveDate、Handler、Remark、SKU、Qty、Unit、LineNumber、WarehouseCode/LocationCode 等现有列。
- 只追加现有表无法表达的 Uid 关系、分层状态、过账/反向、来源和幂等字段，不新建第二套 Inbound 头行表。
- 遗留行中的 `PoLineId/SoLineId` 若为旧整型且无法唯一证明新 Uid，原样保留；新命令写新增的 `PurchaseOrderLineId`、`SalesOrderLineId` 等 Uid 字段。

### 6.1 InboundDocument

| 字段 | 说明 |
|---|---|
| Uid / Version / 审计字段 | 稳定身份、并发和审计 |
| DocumentNo | 人工可读编号 |
| DocumentType | 冻结入库类型 |
| LifecycleStatus / PostingStatus | 分层状态 |
| WarehouseSiteId | 目标仓权威 Uid |
| WarehouseCode/NameSnapshot | 历史展示 |
| SupplierId / SupplierCode/NameSnapshot | 仓所属供应商快照 |
| ReceiptDate | 业务收货日期 |
| PostedDate / PostedBy | 过账事实 |
| ReversedDate / ReversedBy / ReverseReason | 反过账事实 |
| SourcePackingListId | 自动入库时填写 |
| CommandId | 创建/过账命令幂等范围 |

### 6.2 InboundDocumentLine

| 字段 | 说明 |
|---|---|
| Uid / InboundDocumentId / LineNumber | 稳定行身份 |
| ProductId / Sku/Description/UnitSnapshot | 产品关系与快照 |
| Quantity | `decimal(18,4)`，必须大于 0 |
| SourceType | PurchaseOrderLine、NetDemandAllocation、PackingListContribution |
| SourceUid | 对应唯一来源 Uid |
| DemandExecutionLinkId | 可为空；采购/客供件来源应填写 |
| NetDemandAllocationId | 需求 Trace |
| GrossDemandId / SalesOrderNo/LineNumberSnapshot | 来源快照，便于查询但不替代关系 |
| OriginalLineId | 反向行关联 |
| Version / 审计字段 | 并发与审计 |

推荐唯一约束：活动单据 `(InboundDocumentId, LineNumber)`；自动入库按 `(SourcePackingListId, PackingListContributionId)` 幂等。

## 7. 数量守恒与下游查询

- 某采购行已入库量 = 其来源对应的已过账正常入库行数量 - 已生效反向数量。
- 某 Link 已入库量 = 同一 Link 的有效入库贡献净额。
- 可入库剩余量 = `有效 Link 数量 - 已入库净额`，不得读采购行上的缓存累计字段。
- 客供件 B 的目标仓必须来自对应 A Allocation 的执行供应商；Allocation 已有活动 Link 后供应商不能再修改。
- 入库工作台查询可以扁平化显示供应商/产品/销售单，但业务写入始终使用 Uid。

## 8. Application 服务与事务

新建 `IInboundWorkspaceService`：Search、Detail、SourceLookup、CreateDraft、UpdateDraft、PostPreview、Post、ReversePreview、Reverse、Trace。

过账锁序：

1. InboundDocument 头和行。
2. PurchaseOrder/Allocation/Link 来源，按 Uid 排序。
3. 已入库贡献范围。
4. WarehouseSite。
5. InventoryBalance 键，按统一排序。
6. 幂等 Command 范围。

过账事务内调用 `IInventoryPostingService`；不得在入库服务内重复写余额 SQL。成功后同事务写业务日志。

## 9. Repository 与兼容检查

建议：

- `IInboundDocumentRepository`：草稿读写、ForUpdate、状态更新、插入反向单。
- `IInboundSourceRepository`：查询采购/Allocation/Link、锁来源、计算已入库净额。
- `IInboundQueryRepository`：Search、Detail、Trace。

上线过渡期：

- 遗留 `PurchaseReceiveHead/Line` 行保持只读；同一物理表中的新行由新专用仓储写入，并以新增状态/来源字段区分。
- 新采购取消、释放、取消确认和关闭安全检查必须同时考虑同表中的遗留事实与新 InboundDocument 事实。
- 不能证明旧记录来源的采购单标记遗留不可操作，不能为了放行而忽略。

## 10. HTTP/Refit 契约

基址 `/api/inventory/inbounds`：

- `POST /search`
- `GET /{uid}`
- `POST /sources/search`
- `POST /drafts`
- `PUT /drafts/{uid}`
- `POST /{uid}/post-preview`
- `POST /{uid}/post`
- `POST /{uid}/reverse-preview`
- `POST /{uid}/reverse`
- `GET /{uid}/trace`

Post/Reverse DTO 必须携带 CommandId、ExpectedVersion 和逐行 ExpectedRemainingQty/ExpectedVersion。PreviewToken 由服务端规范化事实生成，Execute 重新加锁验证，不能只信 Token。

## 11. WPF 工作台

Shell“库存”下新增“入库工作台”：

- 服务端分页；按入库单号、类型、状态、收货日期、供应商/仓库、采购单号、销售单号和 SKU 筛选。
- 顶部命令：采购入库、客供件入库、编辑草稿、过账预览、反过账预览、Trace、刷新。
- 来源选择弹窗显示采购/需求剩余量，禁止输入超过剩余数量。
- 客供件目标仓只读，展示“送达父件供应商”。
- PackingList 自动入库在页面有清晰来源标记，只读查看，不允许普通编辑。
- 已过账/已反向单据表单只读；强提示和错误码直接展示业务原因。

## 12. 分阶段实施

### Phase 0：源码与数据只读审计

- 审计遗留 PurchaseReceive、净需求采购 Link、目标仓匹配和下游检查调用点。
- 输出 preflight 和不可证明来源清单，不执行 DML。

### Phase 1：Contracts 与现有表扩展

- 新增入库专用实体、DTO、枚举、仓储，并映射/最小扩展 `PurchaseReceiveHead/Line`。
- 验证脚本重复执行、旧表行数不变。

### Phase 2：手工入库

- 采购入库、客供件入库、统一过账、Trace 和反过账。

### Phase 3：WPF 与 PackingList 内部入口

- 完成工作台；提供给 PackingList 的内部批量自动入库能力。

## 13. 测试与验收

至少覆盖：

- 草稿不改库存；过账原子增加库存和流水。
- 采购部分入库、多次入库、累计超量阻断、重复命令幂等。
- 客供件供应商 A 到父件供应商 B 的目标仓正确且不可编辑。
- PackingList 自动入库按需求链路补缺，不按全局 SKU 猜测。
- 任一行失败时头行、余额、流水和业务日志全部回滚。
- 反过账成功、存在后续出库阻断、重复反过账幂等。
- 已入库数量由过账事实净额计算，不读取采购缓存字段。
- 遗留不可证明 PurchaseReceive 阻断采购变更。

## 14. 明确不做

- 质检、退货、批次、序列号、库位和收货容差。
- 扫码、移动端和供应商自助收货。
- 普通用户期初余额、盘点或库存调拨。
- 直接迁移或删除旧 PurchaseReceive 表。
