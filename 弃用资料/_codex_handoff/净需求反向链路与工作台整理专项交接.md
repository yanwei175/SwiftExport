## 3. 当前源码事实

### 3.1 采购草稿为什么阻断毛需求回退

净需求转采购成功后会建立活动 `DemandExecutionLink`。Link 是 Allocation 到采购行的数量追溯权威，因此只要 Link 仍为活动状态，毛需求回退就必须阻断，不能直接取消 NetDemand 或 Allocation。

当前毛需求回退服务在 `GrossDemandWorkspaceService.RollbackAsync` 中：

| 校验 | 当前行为 |
|---|---|
| 毛需求状态 | 必须为 Active + Decomposed |
| Version | 必须匹配 |
| DecompositionRevision | 必须匹配 |
| 净需求和 Allocation 完整性 | 不完整时返回 `CORRUPTED_STATE` |
| 活动 Link | 存在时返回 `DOWNSTREAM_EXECUTION_EXISTS` |
| 无活动 Link | 取消活动 Allocation、回退 NetDemand、毛需求恢复 Pending |

因此，“生成采购草稿后不能回退”是故意的安全边界，不是数据错误。

### 3.2 当前已经存在的安全草稿取消能力

`PurchaseDraftLifecycleService.CancelAsync` 已实现以下事务：

1. 锁定采购草稿头。
2. 校验采购单是新链路建立的 Active + 待确认草稿，Version 匹配。
3. 阻断已有收货或库存事实的采购单。
4. 校验采购草稿具有完整的新净需求 Link。
5. 将该采购草稿的活动 Link 全部置为 Cancelled。
6. 将采购草稿置为 Voided。
7. 通过 Link 失效恢复 Allocation 的可转剩余量。
8. 同一事务提交；任一步失败则整体回滚。

现有净需求 API：

| 操作 | 路由 |
|---|---|
| 取消采购草稿 | `POST /api/demand-planning/net-demands/purchase-drafts/{uid}/cancel` |
| 减量预览 | `POST /api/demand-planning/net-demands/purchase-drafts/{uid}/release-preview` |
| 执行减量 | `POST /api/demand-planning/net-demands/purchase-drafts/{uid}/release` |

当前净需求 Trace 抽屉已有“取消采购草稿”按钮，但入口隐藏较深，用户不能从毛需求或销售订单阻断信息直接到达该处理动作。

### 3.3 销售订单为什么仍不能修改

销售订单已确认后，普通保存不应直接覆盖已经进入需求链路的订单行。当前设计要求先执行“取消确认”：

| 销售取消确认条件 | 当前规则 |
|---|---|
| 订单状态 | Open + 已确认 |
| 毛需求数量和订单行 | 必须一一对应 |
| 活动拆解 | 必须已经安全回退 |
| 活动 Link/正式履约 | 必须不存在 |
| 历史完整性 | revision、NetDemand 和 Allocation 历史必须完整 |
| 从未拆解的毛需求 | 可物理删除 |
| 曾拆解且已安全回退的毛需求 | 保留历史并置为 Voided |

因此当前原始设计的正确操作顺序是：

```text
取消所有可安全取消的采购草稿
  -> 活动 DemandExecutionLink 失效
  -> 回退所属毛需求的当前拆解版本
  -> 毛需求恢复 Pending
  -> 销售订单取消确认
  -> 曾拆解毛需求作废保留历史
  -> 销售订单恢复待确认
  -> 修改销售订单
  -> 重新确认并生成新毛需求/新拆解事实
```

问题在于该顺序目前分散在净需求、毛需求、采购和销售页面，没有统一 Preview、阻断解释或下一步导航。

## 4. 业务语义必须冻结

### 4.1 不建立“单条净需求直接回退”

`NetDemand` 是某个毛需求拆解修订产生的事实。一条毛需求可能生成 A、B 及更多组件净需求，数量和 A/B 关系必须整体守恒。因此：

- 不允许从净需求工作台单独删除或回退某一条 NetDemand。
- 回退单位必须是一个 `GrossDemand + DecompositionRevision`。
- 若同一销售订单包含多个毛需求，是否整单一起准备改单，需要由 Preview 明确展示并由用户确认。
- Allocation 的供应商、执行方式或交期改错，应使用计划替代；这不是拆解回退。

### 4.2 反向层级

| 最深事实 | 允许的反向方式 | 是否可自动串联 |
|---|---|---|
| 只有 NetDemand/Allocation，无 Link | 毛需求安全回退 | 可在确认后执行 |
| Active + 待确认采购草稿，且无收货/库存 | 取消草稿并取消 Link，再回退毛需求 | 可以纳入安全向导 |
| 采购草稿只需减少部分数量 | Preview 后释放部分 Link | 不等同于整次拆解回退 |
| 采购已确认但无入库 | 先走采购取消确认/作废规则 | 不应由净需求静默处理 |
| 已有入库或库存流水 | 入库反向、库存反向 | 禁止自动删除或直接取消 |
| 已有 PackingList/出库 | PackingList 整单反向和正式出库反向 | 禁止自动级联 |

### 4.3 推荐命名

用户真正要解决的是“让销售订单回到可修改状态”，推荐把面向用户的流程命名为：

- `准备销售改单`：跨销售、毛需求、净需求和安全采购草稿的 Preview/执行流程。
- `回退来源拆解`：只表示回退毛需求当前拆解版本。
- `取消采购草稿`：只表示采购头作废并取消全部 Link。
- `释放采购数量`：只表示减少采购草稿及 Link 数量。

不要用模糊的“净需求回退”同时表达上述四件事。

## 5. 推荐的目标流程

### 5.1 首选方案：从销售订单发起“准备改单”

该方案最符合用户最终目的，也能避免净需求工作台继续承担所有模块职责。

#### Preview

用户在已确认销售订单点击“准备改单”，服务端返回：

| 分类 | 展示内容 |
|---|---|
| 销售订单 | 单号、版本、活动行数 |
| 毛需求 | 数量、拆解状态、revision |
| 净需求计划 | 活动 Allocation 数量和计划状态 |
| 安全采购草稿 | 可自动取消的采购单号、供应商、数量 |
| 正式阻断 | 已确认采购、入库、库存、PackingList、出库等事实 |
| 预计结果 | 将取消多少草稿、回退多少拆解、作废保留多少毛需求 |

#### Execute

- 只有全部下游均处于安全边界时，才允许执行。
- 用户必须填写改单原因，并携带订单 Version、PreviewToken、CommandId。
- 推荐由一个后端 Application 编排服务掌握固定锁序和事务，不让 WPF 顺序调用三个 API 后产生部分成功。
- 同一销售订单内必须全成全败：取消安全采购草稿及 Link、回退全部相关毛需求、取消销售确认必须在统一业务事务中完成。
- 成功后销售订单进入 Open + 待确认并打开编辑页；所有历史采购草稿、Link、NetDemand、Allocation 和毛需求均保留其 Voided/Cancelled/RolledBack 状态。
- 有任一正式阻断时不执行任何写操作，只返回应先处理的模块和单据号。

### 5.2 净需求工作台保留的入口

净需求工作台不直接承担整条销售改单事务，只提供：

- `查看来源影响`：展示当前净需求所属毛需求、同 revision 的全部净需求和下游阻断。
- `回到毛需求`：精确打开对应毛需求。
- `打开销售订单准备改单`：销售来源时跳转到销售订单的 Preview 入口。
- `取消安全采购草稿`：可作为 Trace 中的单据级修复入口，但应逐步迁到采购工作台。

如果用户坚持从净需求工作台直接发起，按钮名称仍应为“准备来源改单”或“回退来源拆解”，且必须按来源聚合，禁止看起来像只回退当前行。

## 7. 工作台 UI 信息架构建议

### 7.1 净需求工作台职责

冻结为三类能力：

1. 查询和计划：修改计划、应用默认供应商、批量分配供应商。
2. 下达执行：人工转采购、按来源一键转采购。
3. 追溯和导航：查看计划历史、执行 Link、打开采购/毛需求/销售来源。

采购确认、采购取消确认、供应商跟单、收货、库存和正式反向不应继续堆入净需求顶部工具栏。

### 7.2 按操作范围重新布局

| 范围 | 建议位置 | 操作 |
|---|---|---|
| 当前行 | 顶部主工具栏 | 修改计划、应用默认供应商、追溯 |
| 已勾选行 | 条件式批量操作条 | 批量分配供应商、人工转采购、清除选择 |
| 当前来源单 | 左侧来源面板或来源操作菜单 | 来源一键转采购、回到毛需求、准备来源改单 |
| 全局 | 查询区右侧 | 查询、刷新、清空筛选 |

按钮应显示其作用范围，例如“转采购（已选 3 条）”，不能让用户猜测操作当前行、勾选行还是整张来源单。

## 10. 最小验收场景

| 场景 | 预期 |
|---|---|
| 只有拆解，无采购 Link | Preview 可执行；回退拆解并取消销售确认 |
| 一个安全采购草稿 | 草稿 Voided、Link Cancelled、拆解回退、销售恢复待确认 |
| 同来源多个供应商草稿 | 全部安全时整单全成全败 |
| 部分转采购后仍是安全草稿 | 取消全部相关草稿后数量恢复并允许回退 |
| 采购草稿已有收货/库存 | Preview 阻断且零写入 |
| 采购已经确认 | 第一期 Preview 阻断并导航采购工作台 |
| 已有入库、PackingList 或出库 | 必须正式反向，禁止自动级联 |
| Preview 后并发修改采购草稿 | Execute 因 Version/Token 变化失败且零写入 |
| 重复 CommandId | 返回首次成功结果，不重复取消或回退 |
| A+B 客供件 | 同一 revision 整体回退，不能只删 A 或 B |
