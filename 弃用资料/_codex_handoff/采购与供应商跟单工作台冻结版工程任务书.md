# SwiftExport 采购与供应商跟单工作台冻结版工程任务书

## 1. Codex 新任务启动提示词

> 请先完整读取本任务书和同目录《库存履约下游专项总索引》，再读取《净需求工作台冻结版工程任务书》《净需求数据表与拆解流向说明》、根目录 `AGENTS.md`、`.agents/router.toml`、命中的 workflow/skill 和真实源码。正式 `PurchaseOrderHead/Line`、`DemandExecutionLink`、`IPurchaseOrderDraftRepository` 和 `IPurchaseOrderWorkspaceRepository` 是必须保留的基线；不得恢复已删除的旧采购 CRUD、`PurchaseOrderService`、旧 Refit API、DTO、Entity 或通用仓储。先做只读审计和决策完整计划，再按阶段实施。默认只生成迁移脚本，不连接或修改共享数据库。

## 2. 目标与业务定位

采购是净需求计划的第一个执行方向，首期不实现生产执行。净需求决定“向谁采购、送到哪里、需要多少”，采购工作台负责把已生成的采购草稿变成可跟单的正式采购事实，并持续收集供应商反馈。

本模块必须回答：

- 哪张销售订单、哪一行毛需求/净需求形成了哪张采购单。
- 已下单、供应商已安排、未安排、已备好、已入库和最终已发货分别是多少。
- 哪些采购资料仍不完整，哪些订单可以确认、修改、关闭或取消。
- 跟单人员的供应商反馈发生在何时、由谁登记，是否属于纠错。

“供应商已备好数量”只表示供应商反馈已经做好的货，用于跟单和未来集装箱计划；它不是库存，也不代表已经入库。

## 3. 当前源码基线

- 净需求已具备采购草稿 Preview/Create、人工部分转单、按来源一键全量转单、幂等、追加、安全取消、数量释放和 Trace。
- 采购草稿和正式采购单共用正式实体 `PurchaseOrderHead/Line`；“草稿”是生命周期与确认状态，不再存在 `NetDemandPurchaseDraftHead/Line` 第二套实体。
- 净需求创建、追加、取消和释放通过 `IPurchaseOrderDraftRepository`；采购查询、编辑、确认和跟单通过 `IPurchaseOrderWorkspaceRepository`，两者都不是通用 CRUD 仓储。
- `DemandExecutionLink` 是 Allocation 到采购行的逐来源数量贡献，采购工作台不得用采购行 SKU 反推来源。
- 草稿的计算语义为 `LifecycleStatus=Active + ConfirmationStatus=待确认`；正式 C# 实体和新建表脚本已移除遗留 `OrderStatus`。
- 旧采购 CRUD、Receive、FollowUp 相关 C# 链路已经清理；新实现不得从 Git 历史复制回来。
- 取消/释放目前通过遗留 `PurchaseReceiveLine`、`InventoryTransaction` 物理表进行只读安全阻断。新入库上线前必须保留这层兼容检查；新入库上线后改为同时检查新旧事实。

## 4. 已冻结业务规则

### 4.1 来源与建单

- 采购草稿只能来自净需求活动 Allocation，不提供脱离净需求的普通“新增采购单”。
- 三个入口共享同一套 Preview/Create 内核：净需求人工勾选、按来源单一键转采购、采购工作台“从净需求获取”。
- 人工入口允许 `0 < PurchaseQty <= RemainingQty`；一键入口只允许全部剩余量。
- 禁止跨来源单合并。采购头最小分组键是“来源单 + 采购供应商”。
- 同来源、同供应商默认保持来源明细，也允许用户在预览弹窗选择合并兼容行。
- 不同计划交期合并必须强提示并由用户确认，采购交期取最早日期；Link 仍逐来源保留。
- 固定人民币，首期不建立币种换算。
- 缺 SupplierProduct 或价格时允许生成草稿，但必须标记“采购资料不完整”；缺采购供应商或 B 类需求送达目标时阻断。

### 4.2 草稿与确认

- 草稿允许修改采购单号以外的可编辑商业字段：计划交期、含税单价、备注和允许的行展示信息。
- 来源、供应商、送达目标、需求贡献和采购数量不得通过普通编辑绕过净需求释放规则。
- 确认采购单前必须满足：活动供应商、有效行、数量大于零、价格和必要采购资料完整、全部 Link 数量守恒、没有并发版本变化。
- 确认后禁止普通修改供应商、来源、数量和价格。确需修改时先执行“取消确认”，再编辑草稿。
- 取消确认要求没有任何新旧入库/库存下游事实，必须提交 `ExpectedVersion`、`CommandId` 和原因。
- 遗留采购单若无法证明来源、SupplierId、生命周期或 Link，不允许进入新命令，只提供只读查询并标记“遗留不可操作”。

### 4.2.1 下一步最小数据库变化

第一批只实现“采购查询 + 确认/取消确认 + 供应商反馈”，优先复用 006–008 已存在的采购字段。preflight 确认缺失后才补：

- `PurchaseOrderHead`：`ConfirmedDate`、`ConfirmedBy`。`ConfirmationStatus`、SupplierId、来源和 ExecutionRequestId 已由净需求迁移提供，不重复新增。
- `FollowUpLog`：`RefLineType`、`Sequence`、`ArrangementStatus`、`ReadyQty`、`ExpectedReadyDate`、`SupplierReportedDate`、`IsCorrection`、`CorrectionReason`、`CommandId`。
- 必要唯一/查询索引：采购行+Sequence、CommandId、采购行+反馈日期。

第一批不增加关闭字段、不改采购数量结构、不接入入库/库存表；关闭与剩余释放在第二批实现。

### 4.3 跟单反馈

- 安排状态冻结为：`Unknown=0, NotArranged=1, Arranged=2, NotApplicable=8`。
- 每次供应商反馈新增一条不可覆盖的报告，至少包含采购行、累计已备好数量、安排状态、预计备妥日期、供应商反馈日期、登记人和备注。
- 页面“当前已备好数量”取该采购行最新有效报告，不在采购行维护可变累计字段。
- 累计已备好数量必须在 `0..当前有效采购数量` 内。低于上一条报告视为纠错，必须填写纠错原因并强提示；仍然新增记录，不修改历史。
- 跟单反馈不产生库存余额、库存流水或入库单。
- 已入库数量只从已过账入库行汇总；最终客户已发货数量只从已过账最终客户出库贡献汇总。

### 4.4 关闭、取消和剩余量

- 生命周期冻结为 `Active=0, Closed=8, Voided=9`；确认状态沿用现有共享枚举。
- 安全取消草稿继续走净需求采购草稿生命周期服务：采购头置 Voided、Link 置 Cancelled并恢复净需求剩余量。
- 减少草稿数量继续使用 Release Preview/Release，按已冻结的确定性顺序释放 Link。
- 已确认采购单仅在全部有效行已入库完成，或用户对未执行剩余量执行“关闭预览并确认释放”后才能关闭。
- 关闭释放的只能是尚未形成入库/库存事实的 Link 贡献；存在超额入库、无法定位来源或并发变化时阻断。
- 已关闭采购单不可重新打开；纠错走后续调整单专项，不在首期实现。

## 5. 状态和计算口径

| 页面指标 | 权威来源 |
|---|---|
| 采购数量 | 采购行有效数量及活动 Link 贡献 |
| 未安排/已安排 | 最新供应商进度报告 |
| 已备好数量 | 最新供应商进度报告的累计值 |
| 已入库数量 | 已过账入库行按采购行来源汇总 |
| 待入库数量 | `max(采购有效量 - 已入库量, 0)` |
| 最终已发货数量 | 已过账最终客户出库贡献按需求来源汇总 |
| 净需求剩余量 | Allocation 数量减活动 Link 净贡献 |
| 草稿 | Active + 待确认 |

已备好、已入库、已发货是三个不同事实，不得互相覆盖或用一个万能进度字段替代。

## 6. 目标数据模型

### 6.1 采购头行

`PurchaseOrderHead/Line` 同时是 C# 权威实体和物理表模型，不再建立净需求专用采购头行实体。采购头不缓存行数、总数量、总金额、已备好、已入库或已发货；采购行不缓存 `ReadyQty/RecQty/LastRecDate`。这些指标必须从采购行、跟单报告、入库和出库事实实时计算。

采购头至少需要：

| 字段 | 说明 |
|---|---|
| Uid / Version / 审计字段 | 并发与审计 |
| OrderNo | 人工检索编号，不作为幂等键 |
| SupplierId / SupplierCodeSnapshot / SupplierNameSnapshot | 权威关系与历史展示 |
| DemandSourceType / DemandSourceUid / SourceOrderNoSnapshot | 来源单与老板按销售单号检索 |
| LifecycleStatus / ConfirmationStatus | 分层状态 |
| ConfirmedDate / ConfirmedBy | 确认事实 |
| ClosedDate / ClosedBy / CloseReason | 关闭事实 |
| ExecutionRequestId | 创建幂等范围 |

采购行至少需要：

| 字段 | 说明 |
|---|---|
| Uid / PurchaseOrderId / LineNumber | 稳定行身份 |
| ProductId / SkuSnapshot / DescriptionSnapshot / UnitSnapshot | 产品关系和快照 |
| Quantity / UnitPrice / Amount | 采购商业事实，数量精度 `decimal(18,4)` |
| PlannedDeliveryDate | 采购计划交期 |
| DeliveryWarehouseId / DeliverySupplierId | 送达目标，B 类通常是 A 的执行供应商虚拟仓 |
| ProcurementDataComplete | 草稿资料完整性结果 |
| Version / 审计字段 | 并发与审计 |

### 6.2 SupplierProgressReport（复用 FollowUpLog）

不新建同义物理表。新 C# 专用模型 `SupplierProgressReport` 映射现有 `dbo.FollowUpLog`，复用 Uid/BaseEntity、RefLineId、NoteContent，只追加当前表无法表达的字段。旧通用 `FollowUpLog` Entity/Service 不恢复。

| 字段 | 类型建议 | 规则 |
|---|---|---|
| Uid | uniqueidentifier | 主键 |
| PurchaseOrderLineId | uniqueidentifier | 逻辑外键，建索引 |
| Sequence | int | 每行单调递增，唯一 `(PurchaseOrderLineId, Sequence)` |
| ArrangementStatus | tinyint | 冻结枚举 |
| ReadyQty | decimal(18,4) | 累计已备好量 |
| ExpectedReadyDate | date nullable | 供应商预计备妥日期 |
| SupplierReportedDate | datetime2 | 供应商反馈时间 |
| Note | nvarchar(500) nullable | 跟单备注 |
| IsCorrection / CorrectionReason | bit / nvarchar(500) | 下降纠错必填 |
| CommandId | uniqueidentifier | 唯一幂等键 |
| CreatedDate / CreatedBy | 审计字段 | 不提供 Update/Delete |

`RefLineType` 固定写采购行语义，避免将来其他跟单对象混入时无法区分。迁移只增加 `RefLineType`、Sequence、ArrangementStatus、ReadyQty、ExpectedReadyDate、SupplierReportedDate、IsCorrection、CorrectionReason、CommandId 及必要索引。

## 7. Application 服务与事务

建议新建 `IPurchaseOrderWorkspaceService`，负责 Search、Detail、Trace、草稿编辑、确认、取消确认、关闭和进度报告；净需求 Preview/Create/Cancel/Release 仍保留在 `INetDemandWorkspaceService`，采购工作台只调用其同一内核，不复制规则。

关键事务锁序：

1. 采购头。
2. 采购行，按 Uid 排序。
3. DemandExecutionLink，按 Uid 排序。
4. 下游入库/库存事实只读检查。
5. 幂等命令或进度报告范围。

确认、取消确认、关闭和报告登记成功后，在同一事务写 `BusinessOperationLog`。失败与阻断写技术日志，不生成“成功业务日志”。

## 8. Repository 与 Infrastructure

- 净需求草稿写入固定使用 `IPurchaseOrderDraftRepository`，采购工作台固定使用 `IPurchaseOrderWorkspaceRepository`；禁止恢复通用 CRUD 仓储。
- 查询仓储可以联表，但必须显式列名和显式 DTO 映射，不得 `SELECT *`。
- 下游检查通过专用只读 SQL 查询新 `InboundDocumentLine`、库存流水及遗留 `PurchaseReceiveLine/InventoryTransaction`。
- 进度报告仓储只提供 Insert、GetLatest、SearchHistory；禁止 Update/Delete。
- 锁定使用当前 `DbSession.Transaction`，所有写操作共用一个连接和事务。
- 销售单号追溯固定通过 `DemandExecutionLink -> Allocation -> NetDemand -> GrossDemand`，不能靠备注或模糊单号猜测。

## 9. HTTP/Refit 契约

新建 `IPurchaseOrderWorkspaceApi`，基址 `/api/procurement/purchase-orders`：

- `POST /search`
- `GET /{uid}`
- `GET /{uid}/trace`
- `PUT /{uid}/draft`
- `POST /{uid}/confirm`
- `POST /{uid}/cancel-confirmation`
- `POST /{uid}/close-preview`
- `POST /{uid}/close`
- `GET /{uid}/progress`
- `POST /{uid}/progress`

“从净需求获取”继续调用 `INetDemandWorkspaceApi` 的 Preview/Create，不另建重复路由。已有采购草稿 Cancel/Release 路由也继续归属净需求 API。

所有 Command DTO 必须携带 `CommandId` 和 `ExpectedVersion`；修改行还要携带行 Uid/ExpectedVersion。Contracts 遵守 `netstandard2.0` 普通 class 写法。

## 10. WPF 工作台

在 Shell 新增一级“采购”，子项“采购工作台”，不恢复旧占位 ViewModel。

工作台应具备：

- 服务端分页；按采购单号、销售订单号、来源单、供应商、SKU、确认状态、生命周期、安排状态、交期和备妥日期筛选。
- 当前页选择，不做跨页隐式勾选。
- 顶部命令：从净需求获取、编辑草稿、确认、取消确认、关闭、登记供应商反馈、Trace、刷新。
- Detail/RightDrawer 展示采购头行、逐来源 Link、最新跟单反馈和反馈历史。
- “已备好、已入库、最终已发货”分列展示，并在列头/提示中说明口径。
- 供应商反馈弹窗在 ReadyQty 下降时显示强警告并要求纠错原因。
- Trace 支持按销售订单号展开并导出 XLSX。
- 使用当前 CommunityToolkit MVVM、Supplier Lookup 和 EnterpriseGrid；Busy 防重入，查询 latest-wins。
