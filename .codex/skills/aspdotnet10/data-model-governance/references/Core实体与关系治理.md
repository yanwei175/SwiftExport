# Core 实体与关系治理

## 字段分类

审查每个 Entity 字段时，将其归入以下类别：

- 技术字段：`Uid`、`Version`、`IsDeleted` 和审计字段。
- 实体自身业务字段：该实体独立负责维护的当前业务事实。
- 逻辑关系字段：指向其他实体的 Uid 或业务编码。
- 历史快照字段：单据成立时需要冻结的编码、名称、规格、单位、价格或其他业务事实。
- 派生字段：可通过计算或关联获得，不应重复持久化为当前事实。
- 展示字段：只为列表、详情、报表或 Lookup 服务。
- UI 状态：勾选、选中、展开、Busy、验证提示等客户端状态。

派生字段和展示字段通常进入 Query DTO；UI 状态不得进入 Core Entity。不能仅因字段可联表获得就删除历史快照。

## 字段结论

每个字段必须给出一种明确结论：

- 保留。
- 改名并说明兼容影响。
- 移至 Entity DTO、Query DTO 或 Command DTO。
- 明确为历史快照并禁止自动跟随主数据更新。
- 删除候选，并列出所有引用和数据迁移影响。
- 待业务确认，并说明阻断决策的问题。

## 关系策略

- 内部稳定关联优先保存目标 `Uid`。
- 业务编码用于唯一约束、人工查账、外部交换和可读追溯。
- 需要保留单据成立时业务语义时，保存 `Uid + 业务编码/名称快照`。
- 实时名称、分类或供应商信息通过 Query DTO 联表取得。
- 历史快照不跟随主数据更新，也不用于验证当前主数据是否存在。
- 跨模块关系默认采用逻辑外键；无法独立存在的头行关系可以评估数据库强 FK。

## Application 一致性责任

业务命令至少评估：

- 目标 Uid 是否存在、有效且未软删除。
- 提交的 Uid 与业务编码是否指向同一记录。
- 当前单据状态是否允许建立、替换或解除关系。
- 数量、单位、币种、仓库、供应商和物料类型是否兼容。
- 业务编码修改后是否仍能追溯历史单据。

## 风险检查

- 孤立逻辑外键。
- Uid 与业务编码指向不同记录。
- 同一关系由多个字段重复表达但没有主来源。
- 实时字段和历史快照混用。
- 主数据软删除后仍被新单据引用。
- 可修改业务编码破坏追溯或唯一性。
- Entity 保存页面展示字段，导致多个写入入口产生不一致数据。
