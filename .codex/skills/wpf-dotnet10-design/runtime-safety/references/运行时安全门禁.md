# WPF 运行时安全门禁

## 0. 阶段范围

本文是 WPF 前端横向治理的阶段一门禁，只定义查询取消与过期结果、写命令并发、Busy 所有权、页面存活、错误/反馈边界、导航生命周期、资源释放和未保存变更。

以下内容明确排除：模块能力地图；Feature Service、权限体系、普通表单验证、导航参数与 Dialog 返回协议；自动化测试体系、可访问性、本地化、性能、日志合规、缓存和导入导出治理。错误分类可以读取现有稳定信号，但不得借本阶段设计新的跨层错误协议。

## 1. 操作分类与所有权

先为每个异步入口标注操作类型：

| 类型 | 示例 | 并发策略 | 取消策略 | 完成后的 UI 提交 |
|---|---|---|---|---|
| 替代型查询 | 搜索、筛选、分页、选择项详情、Lookup | latest-request-wins | 新请求取消旧请求 | 仅当前请求且页面仍存活时提交 |
| 显式刷新/初始化 | 页面首次加载、用户刷新 | 同一入口不重复执行 | 页面离开可取消 | 当前页面实例仍有效时提交 |
| 写命令 | 保存、确认、取消确认、删除、过账、反过账 | 默认拒绝并发 | 不用查询 CTS 静默取消 | 只按服务端明确结果接纳状态 |
| 延迟 UI 工作 | 防抖、临时消息、延迟关闭 | 新任务替代旧任务 | 替代或离开时取消 | 身份和值仍匹配时提交 |

不得让查询和写命令共享一个 `CancellationTokenSource`。不得以“最后完成者覆盖页面”的竞速方式处理查询。

## 2. 查询取消与过期结果

替代型查询必须同时具备两层保护：

1. **取消旧请求**：置换 CTS 时先取消旧实例，再释放；外部生命周期 Token 与本次请求 Token 使用 linked token 连接。
2. **提交前验证**：取消不是充分条件。API 可能忽略 Token，因此更新集合、选中项、分页、验证摘要和 ResultSummary 前，还要确认请求仍是当前请求且页面未离开/释放。

推荐持有本次 CTS 或单调递增 request version。只有 `ReferenceEquals(currentCts, requestCts)` 或 request version 仍相等时才能提交结果。`finally` 只能清理由当前请求拥有的字段，旧请求不能清空新请求的 CTS 或 Busy 状态。

用户取消的查询：

- 不显示错误、不覆盖 ResultSummary、不清空已有集合。
- `OperationCanceledException` 只有在对应 Token 已请求取消时才视为正常取消；超时不能一律当作用户取消。
- fire-and-forget 任务必须在内部完整观察异常和取消，不能留下未观察异常。

## 3. 写命令与 Busy

- 写命令使用 `[RelayCommand(CanExecute = ...)]`、生成命令 `IsRunning` 或页面 `IsBusy` 阻止重复进入；仍要防止快捷键、程序调用或多个入口绕过按钮禁用。
- 保存、确认、过账等命令进入后，以服务端返回作为唯一成功依据。失败时不得提前 `AcceptChanges()`、清除 `IsDirty` 或刷新掉用户输入。
- 写成功后再接纳版本、状态和脏状态；随后刷新失败时应提示“写入成功但刷新失败”，不能把整体描述为保存失败。
- 写命令不得复用“新请求取消旧请求”的查询策略。除非后端命令明确支持安全取消，否则发出提交后关闭页面应等待完成或禁止关闭。
- 危险命令确认发生在进入写 Busy 前；真正提交阶段必须防并发。

Busy 所有权规则：

- 一个用户操作只有一个最外层 Busy owner。
- `RunBusyAsync`/`RunWriteAsync` 内需要刷新时调用 `LoadCoreAsync`，不再调用另一个默认 `skipIfBusy=true` 的包装方法。
- 并行子请求属于同一操作时共享外层 Busy；独立可取消的搜索可以维护自己的查询状态，但不得覆盖页面写 Busy。
- Busy 结束必须在 `finally`；旧请求不能结束新请求拥有的 Busy 或改写 BusyMessage。

## 4. 页面生命周期

每个长期存在或可关闭页面必须明确：

- **首次进入**：初始化幂等，同一实例重复调用不会重复加载、注册事件或建立多个 Timer。
- **重复激活**：默认只恢复现有状态；确需刷新时使用显式策略，且先处理未保存变更。
- **离开/关闭**：先执行未保存检查；允许离开后取消查询、防抖和延迟 UI 工作。
- **释放**：标记页面不再存活，取消并释放 CTS，停止 Timer，解除事件和 Messenger 注册，再释放子模型或其他资源。

异步延续在页面离开后可能仍被调度，因此 `Dispose` 不能只取消 CTS；提交 UI 前仍须检查存活状态。释放必须幂等，多次调用不能抛出异常。

普通事件遵循“谁订阅谁解除”。`WeakReferenceMessenger` 不等于允许离开页面后继续处理消息：页面不再活跃时仍应取消注册或通过明确激活状态拒绝处理。`DispatcherTimer` 必须 `Stop` 并解除 Tick；防抖 CTS 必须取消并释放。

## 5. 错误分类与反馈边界

| 分类 | 识别依据 | 用户反馈 | 状态处理 |
|---|---|---|---|
| 用户取消 | 对应 Token 已取消 | 默认无提示 | 保留原页面状态 |
| 字段/输入验证 | 稳定字段错误或本地验证结果 | 字段提示 + 摘要 | 保留编辑和焦点 |
| 业务失败 | `ServiceResult`/业务错误码 | 业务语言说明 | 不接纳保存状态 |
| 并发冲突 | HTTP 409 或稳定并发错误码 | 提示数据已变化并提供刷新/保留选择 | 不自动覆盖本地修改 |
| 未认证 | HTTP 401 | 提示登录失效并交给会话边界处理 | 不把它描述为普通失败 |
| 无授权 | HTTP 403 | 明确无权执行 | 不通过前端绕过后端授权 |
| 网络/超时 | 连接失败或真正超时 | 可重试的连接/超时提示 | 保留当前数据和输入 |
| 未知异常 | 其他未预期异常 | 稳定通用提示和操作上下文 | 记录技术异常，不暴露堆栈 |

- 优先使用 HTTP 状态、业务错误码和结构化字段错误；禁止在 ViewModel 中按中文消息包含关系猜测分类。
- API Runner/基础设施负责记录异常、HTTP 状态和技术上下文；ViewModel 只增加当前业务动作上下文并选择一次反馈载体。
- 同一失败不得同时由 Runner、ViewModel 和全局异常处理器重复弹窗。字段错误使用就地提示；页面级失败使用状态区；必须立即关注的写失败使用消息服务。
- 阶段一只规定日志职责和严重级别边界；敏感字段脱敏、日志保留和审计合规属于后续质量治理。

## 6. 未保存变更门禁

以下动作可能替换或丢弃编辑上下文，执行前必须统一检查：

- 搜索、刷新和分页。
- 切换当前主记录或重新加载详情。
- 关闭 Tab、退出会话或重置导航。

用户取消放弃操作时，页面、页码、选中项和筛选条件要恢复到动作前状态。关闭期间若正在执行写命令，默认返回不可关闭；不能用取消查询的 CTS 去假装取消已经发出的写命令。

未保存判断以编辑模型/列表模型的真实变更集为准，Tab 标题上的脏状态只是镜像。成功保存后才清理脏状态；加载失败或并发冲突不得清理。

## 7. 现有基线与迁移提醒

当前源码已有 `ViewModelBaseEx.RunBusyAsync/RunWriteAsync`、`ApiCallRunner`、`IDocumentTabViewModel`、`NavigationTabItem.Dispose` 和若干页面 CTS 置换模式，可作为迁移起点，但不能据此假设所有门禁已经满足。

阶段一抽样偏差账本：

| 位置 | 当前事实 | 渐进迁移要求 |
|---|---|---|
| `Mvvm/ViewModelBaseEx.cs` | `RunBusyAsync` 吞掉所有 `OperationCanceledException`，默认异常反馈直接使用 `exception.Message` | 触碰基类或调用链时区分调用者取消、超时和未知异常；未知异常交给技术边界记录并返回稳定用户提示 |
| `Services/Api/ApiCallRunner.cs` | 调用者取消被映射为空消息失败；`TaskCanceledException` 把超时与取消合并；409 尚无稳定专类 | 触碰错误管线时保留结构化类别，不让页面按消息文本二次推断 |
| `Navigation/NavigationService.cs` | Tab 在异步初始化前加入集合；初始化失败/取消和重复激活没有显式生命周期回滚或通知 | 触碰导航时定义初始化失败收尾、进入/离开/重复激活语义，并保证未保存门禁先于破坏性切换 |
| `Shell/ShellViewModel.cs` | 订阅导航/状态事件并持有延迟 CTS，但没有对称释放入口 | 触碰 Shell 生命周期时补齐幂等取消、解除订阅和释放 |
| `Features/Procurement/PurchaseOrders/ViewModels/PurchaseOrderWorkspaceViewModel.cs` | 查询已具备 CTS 置换和请求身份检查，但页面无释放/存活标记，离开后仍可能提交 | 沿用请求身份模式，并补齐页面存活与释放闭环；不得把它直接当作完整模板复制 |
| `Features/DemandPlanning/NetDemand/ViewModels/NetDemandWorkspaceViewModel.cs` | 多数查询已有身份检查和 `Dispose`，但集合事件防抖使用 `async void` 且只显式观察取消 | 触碰该防抖时让所有异常被观察，并保证释放后不再执行命令或反馈 |

重点审查现有模式：

- 只有 CTS 取消、没有请求身份和页面存活检查。
- `RunBusyAsync` 吞掉所有 `OperationCanceledException`，无法区分调用者取消和超时。
- API Runner 将取消映射为空失败或把超时与取消合并，导致 UI 无法稳定分类。
- 初始化失败后 Tab 已经加入导航，但没有明确回滚或生命周期收尾。
- Shell 或长生命周期 ViewModel 订阅事件、创建 CTS，却没有对称释放入口。
- fire-and-forget 防抖只捕获取消，没有观察其他异常。

发现这些模式时按“触碰即治理”处理：只治理本次涉及的操作闭环，不自动批量重构整个客户端；若基础设施限制使页面无法满足门禁，在实施计划中明确列出最小基础设施改动和受影响调用方。

## 8. 实施与审查清单

- 是否给每个异步入口标注查询、写命令或延迟 UI 工作。
- 查询是否取消旧请求，并在 UI 提交前验证请求身份与页面存活。
- 是否把 Token 传到 Refit/API Runner/Delay/Dialog 的最深可取消边界。
- 写命令是否拒绝并发，失败时保留编辑和脏状态。
- Busy 是否只有一个外层 owner，嵌套刷新是否调用 Core 方法。
- 用户取消、超时、401、403、409、字段验证、业务失败和未知异常是否可区分。
- 是否只有一个用户反馈 owner，未知异常是否在技术边界记录。
- 初始化是否幂等，重复激活是否避免重复订阅和隐式覆盖。
- 离开/释放是否取消查询并对称释放事件、Messenger、Timer、CTS 和子对象。
- 搜索、刷新、分页、切换和关闭是否处理未保存变更并能恢复取消前状态。
- 是否记录无法在本次范围内修复的现有偏差，而没有静默复制为新模式。
