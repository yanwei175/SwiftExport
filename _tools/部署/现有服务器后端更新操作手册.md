## 二、普通更新不需要重复什么

- 不重新安装 IIS、Hosting Bundle，不重新创建网站或应用池。
- 不重新创建 SQL 登录、不重新授予数据库权限。
- 不重新生成 JWT 密钥，保留生产配置。
- 不重新生成根证书，不重新给每台客户端安装根证书。
- 不移动或清空 D:\ERPFiles，不把图片放进程序目录。
- 不需要重新启动服务器或 SQL Server，只停止、启动本项目的网站和应用池。

有数据库字段变更时，程序发布不会自动更新数据库；先准备独立数据库升级方案、备份及匹配的回退方案。不要对已有库执行整份建库基线。更换 .NET 主版本时再单独检查 Hosting Bundle。接口不兼容时需同步安排客户端更新。

## 三、开发电脑：生成新发布包

在开发电脑 PowerShell 中执行。普通打包不需要管理员权限：

```powershell
cd D:\Documents\source\CSharp\SwiftExport
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force

$releaseName = "SwiftExport_WebApi_" + (Get-Date -Format "yyyyMMdd_HHmmss")
$releasePath = Join-Path "D:\ERPDeploy" $releaseName
& .\_tools\部署\打包后端.ps1 -OutputDirectory $releasePath
```

记下输出的新目录名，下面用 `SwiftExport_WebApi_20261001_090000` 举例，操作时替换成你这次的真实目录名。

看到“发布目录已生成”才继续。如果失败，不复制半成品。脚本使用 `--no-restore`；若提示缺少还原资产，先执行 `dotnet restore .\SwiftExport.WebApi\SwiftExport.WebApi.csproj`，再换一个不存在的新输出目录重试。NU1900 是漏洞数据源访问失败，和编译失败区分处理。

打包脚本会移除发布包中的 appsettings 配置，并生成空的 appsettings.json，避免把开发配置带到服务器。**发布包不能直接覆盖服务器配置。**

通过远程桌面等方式，把整个新发布目录复制到服务器的 D:\ERPDeploy 下。此时线上程序仍可运行。

## 四、服务器：停止本项目

通知正在使用 ERP 的人先结束保存/过账等操作，再进入维护。维护期间客户端会暂时无法访问；结果未知的命令不要换新 CommandId 反复提交。

在服务器管理员 PowerShell 执行：

```powershell
Import-Module WebAdministration
Stop-Website -Name "SwiftExport_WebApi"
Stop-WebAppPool -Name "SwiftExport_WebApi"
Get-WebAppPoolState -Name "SwiftExport_WebApi"
```

确认显示 `Stopped`。如果提示仍有文件被占用，先停止操作、检查应用池是否已退出，不强制删除文件。无需运行 iisreset，避免影响其他网站。

## 五、服务器：保留旧版本，放入新版本

在服务器资源管理器操作，下面每步完成后再继续：

1. 将 `D:\Apps\SwiftExport_WebApi` 重命名为 `SwiftExport_WebApi_backup_20261001_090000`，使用本次唯一时间后缀。旧目录完整保留，包含旧程序、配置、日志和 web.config。
2. 在 `D:\Apps` 下新建 `SwiftExport_WebApi` 文件夹。IIS 的物理路径不变。
3. 将服务器暂存的新发布目录中的全部内容复制到新建目录。确认 `D:\Apps\SwiftExport_WebApi\SwiftExport.WebApi.dll` 直接存在，不要多套一层目录。
4. 从旧备份目录复制 `appsettings.json` 和 `appsettings.Production.json` 到新目录，覆盖发布包的空 appsettings.json。若以后新增了其他服务器专用配置文件，也按发布清单保留；不要带入开发机的 Development 配置。
5. 从旧备份目录复制 `Logs` 文件夹到新目录，保留日志连续性。

**新版本使用新发布包里的 web.config。** 当前站点按默认 Production 环境运行；若以后曾在旧 web.config 增加环境变量或其他定制，更新前对比并合并这些定制，不能整份旧文件覆盖新版托管配置，也不能悄悄丢掉定制。

新版本需要新增配置项时，在原生产配置上补充指定项；不要重跑首次随机生成 JwtKey 的命令。备份目录中包含密钥，应仅保留在受控服务器目录，不发送到聊天或客户端。

然后在服务器管理员 PowerShell 执行，恢复新目录的运行权限：

```powershell
New-Item -ItemType Directory -Path "D:\Apps\SwiftExport_WebApi\Logs" -Force
icacls "D:\Apps\SwiftExport_WebApi" /grant "IIS AppPool\SwiftExport_WebApi:(OI)(CI)RX"
icacls "D:\Apps\SwiftExport_WebApi\Logs" /grant "IIS AppPool\SwiftExport_WebApi:(OI)(CI)M"
```

每条 icacls 应显示失败数为 0。图片目录不变，不需要重新复制或授权。

采用新目录装新程序，可以避免只覆盖 DLL 后残留已删除的旧程序集。旧版本保留到新版本验收完成，先不要删除。

## 六、服务器：启动并验证

```powershell
Start-WebAppPool -Name "SwiftExport_WebApi"
Start-Website -Name "SwiftExport_WebApi"
curl.exe -i http://127.0.0.1:5080/
```

根路径没有首页，返回项目 JSON `NOT_FOUND` 和 HTTP 404 是预期结果。它只能证明后端管道已启动，不能证明数据库正常。

再完成三项验证：

1. 在已信任根证书的电脑浏览器打开 `https://192.168.3.12/files/ProductImages/test.jpg`（保留了测试图片才使用这个地址），确认图片正常且没有证书警告。
2. 用 WPF 的 `Api.BaseUrl=https://192.168.3.12` 登录并打开产品列表，确认数据库及认证查询正常。
3. 按本次改动检查对应功能；需要写入验证时使用明确的测试数据，不用正式过账来随意试接口。

正常后结束维护。如果失败，先查看 `D:\Apps\SwiftExport_WebApi\Logs` 中最新日志，记录错误时间和 CorrelationId。500.19/500.30 等启动错误可能还需看 Windows 事件查看器中的应用程序日志。不要将含密码或令牌的完整配置发出来。

## 七、更新失败如何回到旧版本

以下仅适用于数据库结构及数据仍与旧程序兼容的情况。若本次执行过数据库迁移，不能认为换回 DLL 就能回退数据库，应使用本次专项回退方案。

1. 再执行第四节的停止网站和应用池命令，确认 Stopped。
2. 将当前失败版本目录 `D:\Apps\SwiftExport_WebApi` 改名为 `SwiftExport_WebApi_failed_本次时间`，保留错误日志。
3. 将第五节保存的旧备份目录改回 `D:\Apps\SwiftExport_WebApi`。完整旧配置、旧 web.config 和旧程序随之恢复。
4. 执行第六节启动命令并重新验证。

不要让新旧两个版本同时运行，也不需要重新生成证书或改数据库登录权限。

## 八、证书及当前限制备忘

- 内部 CA 是在服务器上创建的，签发私钥留在服务器 LocalMachine\My 且不可导出。保护这个环境；只备份 Root.cer 并不能恢复签发能力。
- 根证书指纹：`78C89519F2F84B0595F1E769BD6084C4768C26D7`。
- 当前服务器证书指纹：`FDB0AEEBB495F796BCD43E035506645E79847462`。
- 服务器证书到期前续签，复用已有根，不传 -CreateRoot；续签与 IIS 新证书绑定是单独维护事项。服务器 IP 改变也要重新签发匹配的证书。
- 客户端只分发 Root.cer，不分发 Server.pfx 或根私钥；信任安装需要管理员权限。
- 当前简化证书没有吊销列表发布地址。Windows curl 默认可能报 CRYPT_E_NO_REVOCATION_CHECK；诊断可用 `curl.exe --ssl-revoke-best-effort -I https://192.168.3.12/files/ProductImages/test.jpg`，这不是完整吊销验证通过，也不要改成 -k 或全局关闭证书校验。Edge、Chrome 和 WPF 连接已经由用户实际验证。
- 当前跨电脑可访问，但尚未盘点服务器已有防火墙规则的开放范围；不要因为能访问就宣称仅内网可达。后续应单独核对，普通更新不新增放行规则。
