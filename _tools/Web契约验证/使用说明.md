# 首批 Web HTTP 契约验证工具

此目录验证现有后端接口是否能由 OpenAPI 生成可用的 Fetch 客户端。它没有业务前端、令牌存储、CORS 策略或数据库初始化脚本。

## 环境与入口

- .NET 10 SDK；本轮使用 `10.0.401`。
- Node.js 24 与 npm；本轮使用 Node `v24.16.0`。Node 直接运行 TypeScript 验收文件。
- `package.json` 与 `package-lock.json` 固定 Orval `8.40.0`、TypeScript `7.0.2`。使用 `npm ci`，不要通过全局生成器覆盖产物。
- 后端 NuGet 缓存可复用项目配置的 `D:\DevCaches`。首次缺包时需要可用的包源网络。

在仓库根目录运行：

```powershell
& .\_tools\Web契约验证\验证契约.ps1
# 本地已按锁文件安装依赖时：
& .\_tools\Web契约验证\验证契约.ps1 -SkipNpmInstall
```

脚本依次执行定向测试、后端解决方案构建、OpenAPI 选择与核对、Orval 生成、严格类型检查、Fetch 请求验收。任一阶段失败立即终止；恢复原来的目录和环境变量。NuGet 临时文件、构建输出与测试回执写入本目录 `.artifacts`。测试不使用业务数据库。

已有实际导出的 `.artifacts/OpenAPI完整.json` 时，可单独重复客户端验证：

```powershell
Set-Location .\_tools\Web契约验证
npm.cmd ci --no-audit --no-fund
npm.cmd run verify
```

## 输入与产物

| 文件 | 职责 |
| --- | --- |
| `.artifacts/OpenAPI完整.json` | HTTP 测试从真实 Swagger 出口导出的全量文档；本地证据，不纳入 Git |
| `核对首批OpenAPI.mjs` | 选择九个已验收端点、递归保留引用组件，并核对权限描述、JSON、枚举、Guid、日期和 null |
| `openapi.json` | 上述实际文档的首批切片；保留原字段、类型与组件身份，供生成器使用 |
| `orval.config.mjs` | 固定 Fetch、HTTP 状态联合类型、路径参数编码；不把错误响应当成功返回类型 |
| `generated/client.ts` | Orval 实际生成文件；禁止手工修改，修改来源后重新生成 |
| `产品调用样例.ts` | 同源分页调用与原子批量回执分类的最小样例 |
| `Fetch请求验收.ts` | 模拟 Fetch 的请求/响应验收；不是浏览器或正式服务器端到端测试 |
| `tsconfig.json` | 严格检查生成代码与手写样例，不输出 JavaScript |

首批端点为登录、me、产品分页、产品批量保存、分类、Unit 字典、颜色、供应商分页和产品参考仓库查询。完整清单与验收证据见 [Web首批接口契约验收](../../docs/Web首批接口契约验收.md)。

## 调用约定

- 登录/me 成功直接返回 DTO；其他首批成功响应使用既有 `ServiceResult<T>`。失败正文是 `ServiceResult<object>`。
- Fetch 返回 `{ data, status, headers }`。HTTP 400/401/403/422/429/500/503 不自动抛异常；调用方按 `status` 和 `error.code` 处理。网络失败与取消会抛异常。
- 调用方通过 `RequestInit` 提供 Bearer 和 `AbortSignal`；示例不决定令牌持久化策略。
- 枚举 `SaveOperation` 是字符串；Guid、日期是字符串，decimal 是 JSON number。生成器不进行日期对象转换。
- 产品批量保存只有整批成功回执才能接纳草稿；还须由实际页面按提交内容核对 `ClientKey/Uid/Version`。样例没有草稿管理功能。
- 当前产品过期版本是 `422 / BUSINESS_BLOCKED`，不能根据泛型行级冲突推导为 409。`503 / OUTCOME_UNKNOWN` 和不完整回执需要核实；防抖不是幂等，本工具不自动重试。
- `AbortSignal` 只证明 Fetch 取消传递；不证明业务事务已取消或回滚。

## 验证范围

HTTP 宿主保留实际 Controller、JWT、Newtonsoft、权限过滤器、错误及追踪中间件，只替换业务端口。宿主清空外部配置，禁止数据库连接工厂调用，并关闭开发身份和文件服务。真实服务的事务边界另由已有内存夹具测试覆盖。

本轮在并行 BOM 修改期间使用基准提交与六个本轮源码文件的隔离快照验收，155 项测试和后端构建通过。随后共享工作区构建恢复成功，但组合测试为 154 通过、1 失败：BOM 新增三个权限路由后，既有测试仍断言路由数为 232，实际为 235。首批 19 项 HTTP 测试和从共享工作区最新导出生成的客户端验证均通过；组合脚本仍会在该权限门禁处终止。该测试归并行任务负责，修复后须重新执行组合入口。详见验收报告。
