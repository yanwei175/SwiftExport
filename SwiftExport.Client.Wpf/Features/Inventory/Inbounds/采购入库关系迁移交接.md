# 采购侧入库关系迁移交接

本窗口继续入库 Manager 前端接线。另一个窗口只处理采购侧消费者，避免同时编辑入库文件、通用基类或共享 DI。

## 已核对的受影响 API

| 优先级 | API | 已发现的源码依据 |
|---|---|---|
| 高 | POST /api/procurement/order-manager/search | PurchaseOrderManagerQueryRepository.SearchAsync 的收货汇总仍使用入库行 SourceType/SourceUid |
| 高 | GET /api/procurement/order-manager/{purchaseOrderId}/lines | 同仓储 GetLinesAsync 的 ReceivedQty/UnreceivedQty 仍使用旧字段 |
| 高 | POST /api/procurement/orders/{uid}/cancel-confirmation | ProcurementOrderRepository 的下游事实检查仍按 i.SourceUid 关联采购行 |
| 高，沿调用链核对 | POST /api/procurement/purchase-drafts/{uid}/cancel、release-preview、release；preview/create 的安全追加候选 | PurchaseOrderDraftRepository.GetSafeAppendCandidatesAsync/HasDownstreamFactsAsync 及共享 SQL 使用旧 SourceType/SourceUid 和 Link |
| 兼容入口，先核实消费者 | GET /api/procurement/purchase-orders/{uid}、{uid}/trace；PUT {uid}/draft；POST {uid}/confirm、{uid}/cancel-confirmation | PurchaseOrderWorkspaceRepository.GetLineDetailsAsync/HasDownstreamFactsAsync 仍按入库 SourceUid → Link 关联 |

上述并非要求删除全部 SourceType/SourceUid：采购、需求自身同名字段仍有其他含义。仅迁移指向 InboundDocumentLine 的旧字段引用。其他采购 API 应沿调用图确认间接影响，不凭路由名字批量改动。

## 可直接复制给采购窗口的提示词

请实现采购侧对精简入库实体的消费适配。先读项目 AGENTS、backend 工作流、采购/入库/库存能力地图的最新增补，重新核对当前源码与 git diff。只改采购侧相关 Application、Repository、必要契约和测试；不要修改入库 Manager/Picker、入库服务/仓储/契约、库存过账内核、通用 MVVM、共享 DI，不访问或修改共享数据库。若确实需要共享文件，先列出阻塞及接口要求，等待协调。

当前入库事实：

1. InboundDocumentLine.SourceLineId 才是实际采购行 Uid；由单头 DocumentType=PurchaseReceipt(10) 解释。单头 CreationMode 区分人工/自动，不改变采购来源身份。旧入库行 SourceType、SourceUid、PurchaseOrderLineId、DemandExecutionLinkId、Allocation/销售快照已不作为新模型字段。不要恢复这些字段，也不要把采购自身 SourceUid 误删。
2. 无需求/无 Link 采购合法。新普通收货不要 inner join Link；Link 仅用于可选向上追溯。来源号、供应商等从采购获得。
3. 收货进度按采购行聚合有符号正式入库数量，不扣草稿，不读采购缓存累计数量，不读全局 SKU 库存。目前入库查询约定将 Posted(1)、Reversed(8) 原事实与对应负向单一并求和；本批未实现新反过账，必须审查历史实际结构，不能机械套用导致双扣或漏扣。无法证明历史来源时明确报异常，不能当成零。
4. 区分“数量进度”和“安全检查”：净额为零不代表没有历史流水。取消确认、减量、关闭等不得仅凭净额零放行；保留已有正式事实和无法证明历史的保守保护。草稿引用如何处理要按现有用例分别核对，不把所有草稿自动当正式收货，也不静默放宽现有安全条件；业务含义不明时先报告。
5. 入库 Picker 不按仓库筛选，Manager 的收货仓库独立选择；本任务不重新锁定入库仓库，也不修改采购已确认的原始仓库字段或消耗规则。
6. 逐项检查本文件列出的 API 和四个采购仓储中的 SQL，保持参数化、稳定分页、按事实先聚合及当前事务锁；不要全局替换 SourceUid。维护现有返回 DTO/路由兼容性，错误通过返回体明确说明。
7. 补行为/SQL 验证：无 Link 采购、同采购行多个 Link 不倍增、多次收货、草稿不计收货、完整反向净额、历史未知阻断、正式流水存在但净额为零不误放行。构建 WebApi、运行采购相关测试；不得删除有效断言或顺手修无关失败。不连接共享库，真实数据库验证未做须明确报告。
8. 完成后说明各 API、字段映射、数量算法、安全门禁、测试及未解决项；更新采购能力地图相关条目。不要宣称入库过账、PL 自动入库或全链路已经完成。
