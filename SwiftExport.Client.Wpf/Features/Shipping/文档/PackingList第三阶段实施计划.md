# PackingList 第三阶段实施计划

更新：2026-09-18。状态：**业务范围已确认，尚未实施。** 本版取代此前赠送、受控负库存及差异处理草案。

## 一、目标与范围

第三阶段只有两个独立操作：

1. **撤销原行过账**：撤销错误物理行对应的交付及库存执行。
2. **正常补记**：通过现有 Picker 选择合格来源，按正常规则补记并执行必要的自动入出库。

两次操作独立提交，不捆绑成自动替换事务。B 撤销成功后，即使 A 没有合格来源，也不恢复 B 的错误记录。

没有合格来源时本模块到此为止。是否从来源需求开始重新走物料需求、MRP、采购，由经理、总经理或采购/MRP 负责人决定并人工操作；PackingList 不代建或绕过上游链路。

## 二、撤销原行过账

以原物理行的执行记录、实际流水和数量归属为依据，在一个事务内：

1. 撤销本行成品出库，恢复原仓库存。
2. 撤销归属于本行的自动入库，恢复对应采购行可收容量；历史手工入库及使用的已有库存不反向入库。
3. 客供件只撤销本行耗用出库，恢复原仓原量，不撤销客供件入库。
4. 撤销本行交付量，恢复原 GrossDemand 的待交付数量。

库存执行先恢复出库，再撤销自动入库。“回到未入库”指对应自动收货数量恢复，不回退需求或采购单据的业务状态，也不删除历史或把原行直接改成可编辑草稿。

例如出库 10，自动入库 6、已有库存 4：先恢复 10，再扣回自动入库 6，净恢复已有库存 4。全部自动入库则成品库存净变化为零。

- 正常完整、未重复撤销的执行链不应因该配对操作本身制造负库存。已有异常余额、缺失流水或重复处理仍须校验，不新增负库存放行。
- 多条物理行可能共享生成单据，必须只撤销本行归属量，不能反向整张共享入出库单影响其他行。
- 客供件使用原执行分配数量与快照，不读当前 BOM 重算历史。
- 售后直发、非标无库存行只恢复交付，不增加库存动作。
- 原箱单行、单据及流水保留，展示已撤销标识；原因记录在日志及相应反向单据。
- 复用现有执行记录及流水关联，不新增专门纠错关联表。行身份、命令及数量的必要关联不能仅写在自由文本备注里。

## 三、正常补记与来源边界

正常补记打开现有 Picker，选源、填写补记行，再按正常预览确认及过账规则处理。

- Picker 判断来源准入和待交付量，并扣除当前草稿已选量，不以“仓库有库存”作为唯一准入条件。
- 普通来源保持现有有效物料需求、执行 Link 等要求；走到采购仍需满足具体有效性条件，并非任意采购草稿都当然可选。
- 库存为零但来源合格、关联采购有剩余可收容量时，允许正常自动入库后出库。
- 成品库存分配、采购容量和客供件耗用沿用正常过账规则；客供件不足仍正常阻断，不自动补入。
- 原来源已全部交付时不突破数量限制。没有合格来源就停止，不新增强制补记、赠送或上帝按钮。
- 业务负责人可以从来源需求重新组织物料需求/MRP、采购；形成合格来源后再回到 Picker。是否这样做及如何做，不属于 PackingList 管辖范围。
- 既有售后直发、非标无库存规则不变，不借本次调整要求它们强制新增采购。

补记是新执行，不覆盖被撤销的原行，也不重放原箱单全部已执行行。只处理本次新增有效行，按所选来源正常计交付。

## 四、实施拆分

### 1. 内部执行与交付查询

- 核对现有行级反向能力及执行记录，以原物理行定位可撤销数量，保护共享单据中的其他行。
- 有效交付统计排除已撤销数量，不能只按头已过账状态累计原行 Qty。
- Picker、来源剩余、售后及相关交付追踪采用一致净额；采购仍是关联来源进度，不变成采购行自身出货数量。
- 历史证据不可证明时只读；重复撤销不能二次恢复库存和需求。
- 不新增专门关联表，必要字段扩展须先核对现有结构，不直接改历史流水。

### 2. 服务、契约与事务

- 行撤销提供预览和确认，使用期望版本、业务日期、原因、稳定命令 ID、预览令牌。具体路由和 DTO 在实现时核对，不在本轮创建占位 API。
- Application 持有事务：锁命令及原执行链，声明资源，锁后重读验证，执行反向，保存撤销事实、交付变化及日志，一次提交。
- 正常补记复用正常计算与自动入出库能力，限定本次新增行；不重新执行已有行。
- 两个操作各自幂等、各自原子，任一步失败或取消不能留下本次操作的部分结果。
- 不直接修改余额，不新增通用 AllowNegative 开关。

### 3. WPF 接线

- 两个入口：“撤销本行过账”“正常补记”。
- 撤销展示成品、自动入库、客供件对应反向量，填写原因并确认；保留原行及撤销标识。
- 补记使用现有 Picker；无来源时说明由业务负责人处理上游链路，不提供绕过入口。
- Busy 防重入，未知网络结果保留原命令，重要阻断 ShowWarning；成功刷新详情及来源剩余。

### 4. 实施前核对的技术细节

业务范围不再扩展，但需结合源码确定：补记行编辑承载方式、现有执行表字段复用、共享单据部分反向状态，以及行撤销后的整单反向处理。

整单反向不能再次恢复已撤销行；未适配完成前必须明确阻止该路径，不沿用旧逻辑重复处理。这是实现安全约束，不代表已批准永久取消整单反向。

## 五、验收

- 全自动入库行撤销：成品库存净变化为零，采购可收容量及来源待交付恢复。
- 混合已有库存与自动入库：只反向对应自动入库；手工入库不动。
- 客供件原仓原量恢复，不反向入库；无库存行只恢复交付。
- 同来源拆箱、多行共享单据时，其他有效行不受影响。
- B 撤销成功、A 无来源时，撤销结果保持，本模块不生成上游单据。
- 零库存、有合格采购容量可补记；来源无剩余、容量不足或客供件不足时按正常规则阻断。
- 上游人工形成合格来源后可再次选入；不重复计原来源交付或重放旧行。
- 重复命令、内容冲突、并发撤销、日志或库存写入失败、取消，以及整单反向防重复均有测试。
- 运行相关后端/WPF 构建测试与真实 SQL 事务、并发验证；数据库执行按当次授权范围进行。
