# PackingList 第三阶段实施计划

日期：2026-09-17。状态：**规划草案，尚未实施；第四节待确认后再冻结实现范围。**

## 一、目标与现有基础

支持箱单过账后发现产品、来源或数量记错时，有记录地纠正交付及库存账；必要时通过独立权限容许纠错产生库存差异，后续核对关闭。不得删除历史流水、直接改余额或把普通过账改成任意负库存。

第二阶段已经具备预览、同事务自动入出库、执行证据、整单反向及重复命令保护；真实 SQL 专项已通过。剩余验收见 [Shipping 入口](../README.md)。第三阶段不是重做这套正常流程，也不要求先修复所有无关 WPF 测试。

本阶段工作量明显大于增加按钮：主要新增的是行级执行证据、纠错后的交付净额、部分库存反向、差异记录和权限边界。

## 二、业务边界

### 1. 先分清两种错误

| 场景 | 处理原则 |
|---|---|
| 实际发了 A，箱单记成 B | 更正记录，使交付和库存账反映实际 A；保留原 B 记录及更正关系 |
| 实际发了 B，但客户应该收到 A | B 的实际出库仍是真实事实；不能通过反向凭空认为 B 回到仓库。补发 A、实际退货与责任处理另走对应业务 |

两个月后发现记录错误，时间跨度本身不应成为唯一阻断；仍须检查历史执行证据、关联来源、版本、库存和业务日期规则。不能靠减少校验预防 A/B 录错，预览核对和纠错追踪分别解决事前确认、事后修正。

### 2. 建议的纠错流程

选择原已过账物理行 → 填写更正内容与原因 → 预览交付和库存差额 → 明确确认 → 同事务保存更正证据、库存单据/流水、交付变化及日志。

- 原箱单、执行记录和流水不可覆盖；展示原记录、更正链及当前有效结果。
- 旧产品/来源恢复多少，新产品/来源登记多少，分别列明；不同单位不相加。
- 售后直发、非标无库存行仍只调整交付事实，不凭纠错生成库存。
- 正常纠错库存不足先阻断；受控负库存是独立例外，不自动启用。
- 来源无效、客户不符、单位不明、超交付、证据缺失、并发冲突不能被负库存权限绕过。
- ShippingLocationSnapshot 仍只是文本；InvoiceDate 修改不改历史库存日期。

### 3. 必须补齐的执行能力

现有内部 Reverse 面向整张自动单据。多个箱单行可能共用一张入出库单，不能为纠正一行反向整张单据，影响其他行。

- 入出库模块增加受限的行级纠错能力，依据原执行映射及实际流水确认可撤销数量；PackingList 负责业务编排，不直接写余额。
- 优先复用现有库存纠错内核与反向关联字段；实施前核对其实际语义、数量限制和并发保护，不预先另建第二套库存账。
- 原出库反向使用原仓、原数量及原依据。客供件恢复依据原计算快照，不读取当前 BOM 重新推算历史。
- 自动入库不能一律跟随出库纠错撤销：若原收货真实有效，应保留；确属收货记录也记错才纠正，并调整采购净收货容量。
- 新交付及必要库存动作必须有明确、可验证的依据；无法证明时阻断，不补造采购或收货事实。

### 4. 交付与状态

- 第三阶段必须引入包含更正增减的有效交付投影，不能继续只按箱单头已过账状态统计原行 Qty。
- Picker、来源剩余、售后追踪以及销售/采购关联来源展示统一使用该口径。采购展示仍是关联来源进度，不冒充采购行自身耗用。
- 来源纠正时原来源恢复、新来源扣减同事务完成；同来源多物理行不重复累计。
- 存在行纠错后，原整单反过账不可直接沿用旧逻辑。建议首版明确阻断，提示先处理更正链；后续若开放，必须按当前有效执行净额反向，不能重复恢复已撤销数量。
- 历史缺少可证明执行记录的箱单保持只读，不猜测库存恢复。

## 三、实施拆分与验收

### A. 先冻结规则与契约

- 确认下一节的业务选择；补充原记录、纠错记录与当前结果的关联模型。
- 核查现有执行表和库存纠错字段的复用范围；需要新表时仅提供增量 SQL，不建强外键、不改历史数据。
- 契约区分查询、预览和命令，继续使用期望版本、业务日期、稳定命令 ID、预览令牌及原因。
- 拟增加纠错预览、确认、记录查询；受控负库存和差异处理契约后续单独定义。路由与 DTO 名称本轮不冻结、不创建占位 API。

### B. 实现不允许负库存的行级纠错闭环

- Application 持有一个事务：锁命令与原执行链，声明完整库存资源，锁后重读并验证预览，执行行级库存更正，写交付更正及日志，一次提交。
- 扩展有效交付查询，保留原始历史展示；实现重复更正、超量撤销、同来源竞争保护。
- WPF 增加只读差额预览、原因与确认；写命令 Busy、未知网络结果保留原命令，重要阻断 ShowWarning。
- 验收：A/B 记录错误、数量错误、拆箱多行、共享生成单据、售后无库存、更正后来源剩余，以及整单反向限制。

### C. 独立增加受控负库存

- 仅对已授权纠错操作开放独立权限；普通过账、反过账仍保持当前负库存阻断。
- 预览明确仓库、产品、修改前后余额及缺口；必须填写原因并二次确认，不能藏在通用 AllowNegative 参数中。
- 差异事实与纠错、库存、日志同事务保存；失败不得留下“库存已变但差异未登记”的状态。
- 验收权限越权、未确认、并发导致新缺口、负库存原因审计；其他业务阻断仍有效。

### D. 差异核对与关闭

- 记录受影响仓库/产品、原纠错、差异数量、原因、处理人及后续处理依据。
- 后续通过实际业务单据或正式库存调整处理；不能直接修改余额，也不能仅因余额变正就自动认定该差异已解决。
- 建立轻量待处理/已核对关闭流程，不增加复杂审批；关闭必须留依据及审计。
- 验收重复关闭、无处理依据、部分处理、与无关入库的区别、完整追踪。

每个实现批次均包含 Contracts/后端/WPF 对应接线与测试，不以“只写了接口”作为业务闭环。真实 SQL 测试覆盖同事务可见性、任一点失败回滚、取消、幂等、并发纠错与缺失余额键；再次执行数据库变更仍需当次授权。

## 四、实施前需要确认的最小决策

1. **纠错粒度：建议首版整条物理行更正**，可替换产品/来源及数量；暂不做同一行任意部分数量多次拆分纠错。若必须部分纠错，需要增加剩余可撤销量和分配尾差设计。
2. **范围：建议先只做“记录错误”**；实际错发的补发/退货流程另列需求，不通过本功能伪造回库。
3. **入库处理：建议不自动一并撤销真实有效收货**；预览分别明确只改交付/出库，还是收货记录也有错。替换来源和客供件新计算依据须可证明，不能默认当前 BOM 就是历史事实。
4. **负库存例外：建议只用于本阶段授权纠错**；是否扩大到既有整单反过账，需要另行明确，不顺带放宽。
5. **更正后的整单反向：建议首版禁止直接反向**，避免重复撤销。若必须支持，纳入本阶段额外实现和验收。

上述建议不代表用户已经确认。确认后同步更新业务能力地图中的旧规则及状态边界，再开始代码实施。

- 本计划不开放通用负库存入口、不直接改已过账箱单原行、不删除历史、不增加采购分摊权威、不实现财务结算、实际客户退货或自动判断责任。
- 第二阶段遗留人工 UI 与全量测试问题继续登记和归因，不用它们掩盖第三阶段验收，也不声称本次文档整理已完成代码或测试。
